📌 1. 현황 진단 — 목업이 약속한 것과 실제로 가능한 것

Domain 03은 백엔드 모델이 0개이고 DigitalEstatePage.tsx의 로컬 state로만 존재합니다(→ 03-01 §1).

그런데 단순 미구현보다 중요한 문제가 있습니다. **현재 목업이 화면에서 약속하는 기능 상당수는 구현이

어려운 게 아니라 법적으로 해서는 안 되는 것**입니다.

목업이 약속한 것 (`mockData/digitalEstate.json`)실제 판단
"업비트/빗썸 — 상속 포트폴리오 자산 상속 출금"❌ **배제.** 가상자산 상속은 거래소 고유의 상속인 확인 절차. 중개하면 무인가 영업 리스크
"카카오뱅크/페이 — 계정 정산"❌ **배제.** 상속 예금 지급은 금융기관 고유 업무
"쿠팡/11번가 — 정산금 환급", "넥슨 — 유료 자산 상속"❌ **배제.** 재산적 청구권 = 상속재산 처리 영역(→ Domain 02)
"Naver OCR로 정당한 상속인 여부를 **즉시 검증**"❌ **허위 표현.** OCR은 글자를 읽을 뿐 서류 진위·상속권을 판정하지 못함
"계정 정산 신청" (이어봄이 대행하는 것처럼 읽힘)⚠️ **재정의 필요.** §2 참조
추모관(헌화·방명록·앨범)⚠️ 방향은 유효하나 **고인 1명당 1개**라는 기본 구조가 없음. §4 참조

1.1 왜 "대행"이 성립하지 않는가

1. 제3자 대행 창구가 존재하지 않습니다. 주요 플랫폼(구글·메타·애플·네이버·카카오)은 유족 요청을

각 사 공식 폼으로 접수해 자체 심사합니다. 제휴사·대리인용 API나 B2B 채널을 공개한 곳이 없습니다.

즉 "이어봄이 대신 처리"할 기술적 경로 자체가 없습니다.

2. 고인 계정 자격증명(ID/PW)을 받아 로그인하는 것은 하면 안 됩니다. 계정 이용권은 일신전속적

성격이 강해 당연히 상속되지 않는다는 것이 통설이고, 유족이라 해도 타인 계정 접속은

정보통신망법상 침해행위로 평가될 소지가 있습니다. **이어봄은 고인의 자격증명을 어떤 형태로도

수집·저장·입력하지 않습니다.** 이것은 협상 대상이 아닙니다.

3. 위임에 의한 신청 대행이 필요하다면 그것은 행정사 업무 영역입니다. 우리에게는 이미

Domain 02에 ADMINISTRATIVE_SCRIVENER(행정사) 직역이 있고, 02-03 §7.1이 이 직역을

"디지털 유품 행정사"로 이미 명명해 두었습니다.

그래서 Domain 03은 대행하지 않고, 대행이 필요한 유족을 Domain 02로 보냅니다. 이 역할 분담이
이 문서 전체의 뼈대입니다.

🎯 2. 이 도메인의 재정의 — "대행"이 아니라 "안내 + 진행 추적"

2.1 이어봄이 하는 일 / 하지 않는 일

이어봄이 하는 일이어봄이 하지 않는 일
플랫폼별 **공식 유족 절차 안내**(필요 서류·신청 경로·예상 소요)고인 계정에 **대신 로그인**
유족이 직접 신청한 건의 **진행 상태 추적**(체크리스트)플랫폼에 **대신 신청서 제출**
필요 서류 **체크리스트 제공**증빙 서류 **수집·보관** (§3.3)
대행이 필요하면 **Domain 02 행정사 연결**금융·가상자산·정산금 등 **재산 처리 개입**

2.2 이 재정의가 만드는 이득

  • 증빙 서류를 우리가 받지 않아도 됩니다. 유족이 각 플랫폼에 직접 제출하므로,

가족관계증명서·사망진단서(주민등록번호 등 고유식별정보 포함 가능성이 높은 최고 민감도 서류)를

이어봄 서버에 저장할 이유가 사라집니다. 가장 큰 개인정보 사고 경로를 설계 단계에서 제거합니다.

  • 법적 리스크가 "정보 제공"의 수준으로 내려갑니다. 남는 의무는 안내 정보를 정확하게 유지하는 것뿐입니다.
  • Domain 02의 상담 인프라(ConsultRequest)를 그대로 재사용합니다. 새 정산·과금 구조가 필요 없습니다.

2.3 이번 범위 (Stage 1)

1. 플랫폼 안내 카탈로그(DigitalPlatform) — 운영자가 관리하는 마스터 데이터

2. 유족 개인의 정리 진행 추적(DigitalCleanupItem) — 체크리스트 + 상태

3. 온라인 추모관(Memorial + 헌화·방명록·사진)

4. 운영자 화면에서 회원 상세 조인 조회(→ 03-01 §2 원칙)

2.4 이번 범위 제외

제외 항목이유
현물 유품 수거업체계정 형태 기획 보류 — 대표 지시로 이번 제외(→ 03-01 §3)
위임 대행 실행행정사 업무 영역 → Domain 02 상담으로 연결(§3.4)
금융·가상자산·정산금§1.1 — 상속재산 처리는 Domain 02(세무사·변호사)
추모관 유료화(화환 결제 등)PG 연동 = 돈이 드는 외부 연동 → roles.md §4 대표 승인 대상
부고 문자 발송Domain 04(상중·행정 케어)의 모바일 부고장과 중복 — 그쪽 스펙에서 다룰 것

Stage 1은 결제가 없으므로 대표 승인 없이 착수 가능합니다(02-03 Stage 1과 동일 구조).

🔐 3. 디지털 계정 정리 — 설계

3.1 플랫폼 안내 카탈로그는 코드가 아니라 데이터다

플랫폼별 유족 정책은 자주 바뀌고 우리가 통제할 수 없습니다. 절차를 코드나 문서에 하드코딩하면

바뀔 때마다 배포가 필요하고, 낡은 안내는 그 자체로 유족에게 피해를 줍니다.

따라서 DigitalPlatform 테이블로 관리하고 운영자가 화면에서 갱신합니다.

(01-05 §12의 "하드코딩 제거" 원칙과 같은 판단입니다.)

각 레코드는 lastVerifiedAt(최종 확인일)을 필수로 보유하고, 화면에 함께 노출합니다.

확인일이 오래된 항목은 운영자 화면에서 경고 표시합니다.

⚠️ 초기 데이터 입력 시 주의: 각 플랫폼의 실제 유족 처리 절차는 **입력 시점에 공식 고객센터
문서를 직접 확인해서** 채워야 합니다. 기억이나 추정으로 채우면 안 됩니다 — 유족이 그대로 따라
하다가 시간을 버리는 실질적 피해가 발생합니다. 확인 못 한 플랫폼은 **레코드를 만들지 않는 편이
낫습니다**(빈 카탈로그가 틀린 카탈로그보다 낫습니다).

3.2 지원 대상 분류

분류처리예
**A. 안내 대상**카탈로그에 등록, 유족이 직접 신청이메일·SNS·클라우드·구독 서비스 계정의 삭제/추모 전환/해지
**B. 연결 대상**안내만 하고 **Domain 02 상담으로 유도**위임 대행이 필요한 건, 절차가 복잡한 건
**C. 배제 대상****카탈로그에 넣지 않음** + 안내 문구로 명시적 차단금융계좌, 가상자산, 정산금·포인트 등 재산적 청구권

**C를 화면에서 그냥 빼는 것으로 끝내지 않고, "이런 항목은 이어봄이 다루지 않으며 금융기관/거래소에

직접 문의하셔야 합니다"라고 적극적으로 안내**합니다. 목업이 이미 이 기능을 약속했었기 때문에,

조용히 사라지면 유족이 계속 찾게 됩니다.

3.3 증빙 서류는 받지 않는다

§2.2대로 가족관계증명서·사망진단서를 이어봄 서버에 업로드받지 않습니다.

현재 목업의 파일 업로드 UI는 제거합니다.

  • 대신 각 플랫폼이 요구하는 서류를 체크리스트로 안내만 합니다("이 서류를 준비해 ○○에 제출하세요").
  • 유족이 "준비 완료"를 스스로 체크할 수는 있지만, 파일 자체는 저장하지 않습니다.
  • 위임 대행 때문에 서류가 꼭 필요해지면, 그건 §3.4대로 행정사(Domain 02)와 유족 사이의 일이며

이어봄 서버를 경유하지 않습니다.

이 결정은 되돌리기 쉽지 않은 방향으로 되돌리기 쉽습니다 — 나중에 필요하면 업로드를 추가하는 것은
간단하지만, 한 번 수집한 민감 서류는 유출되면 회수할 수 없습니다. 안 받는 쪽을 기본값으로 둡니다.

3.4 Domain 02 연결 지점

DigitalPlatform.needsAgentHelp = true인 항목, 또는 유족이 "직접 하기 어렵다"를 선택하면

CounselingPage(SCR-007)의 행정사 카테고리로 연결합니다.

  • 새 API를 만들지 않고 기존 POST /api/experts/:id/consult-requests를 그대로 씁니다(02-03 §5.2).
  • 상담 신청 시 content에 어떤 플랫폼 건인지 프리필하면 전문가가 맥락을 바로 파악합니다.
  • 주의: 이 연결은 단순 화면 이동이며, Domain 03이 상담 수수료를 갖는 구조를 만들지 않습니다.

변호사법·02-03 §3의 가드레일은 그쪽 문서가 정본이며 여기서 새로 만들지 않습니다.

🕯️ 4. 온라인 추모관 — 설계

4.1 현재 목업의 근본 문제: 추모관이 하나뿐이다

목업의 추모관은 전역 싱글턴입니다. 헌화 수가 42로 하드코딩돼 있고 방명록도 하나입니다.

누구의 추모관인지가 없으므로 실제 서비스로는 성립하지 않습니다.

추모관은 고인 1명당 1개이며, 유족이 개설하고, 고유 URL로 조문객이 방문합니다.

이것이 이 기능의 최소 성립 조건입니다.

4.2 공개 범위 — 기본값은 "링크를 아는 사람만"

값의미검색 노출
PRIVATE개설자와 지정 유족만❌
**LINK****URL을 아는 사람만 (기본값)**❌
PUBLIC이어봄 내 추모관 목록에 노출⭕

기본값을 PUBLIC이 아니라 LINK로 두는 이유: 사망 사실과 유족 구성이 공개적으로 색인되면

부고 사칭 보이스피싱의 표적 정보가 됩니다. 실제로 부고 문자를 가장한 피싱은 이미 사회 문제입니다.

부고는 널리 알리는 것이 본래 성격이지만, "널리"의 주체는 유족이어야 하며 검색엔진이 아닙니다.

유족이 명시적으로 PUBLIC을 고르기 전까지 색인되지 않습니다.

  • PUBLIC이어도 생년월일·주소·유족 실명 등은 공개 응답에서 제외합니다(§5.4 화이트리스트).
  • 비공개 URL은 추측 불가능한 토큰(slug)을 씁니다 — 순번(/memorial/1)이면 열람이 가능해집니다.

4.3 허위 추모관 방지

살아있는 사람의 추모관을 만드는 것은 심각한 명예훼손이며, 실제로 발생할 수 있는 악용입니다.

그렇다고 개설 시 사망진단서를 요구하면(§3.3과도 모순) 아무도 쓰지 않습니다. 균형점:

1. 개설은 로그인 필수 — 최소한 누가 만들었는지 추적 가능해야 합니다(비회원 개설 불가).

2. 기본 비공개(LINK) — 확산 자체가 제한적입니다.

3. 신고 창구 + 즉시 비공개 전환 — 신고가 접수되면 운영자 확인 전까지 PRIVATE로 자동 전환합니다.

사후 확인보다 선차단이 맞습니다. 피해가 되돌릴 수 없는 종류이기 때문입니다.

4. 개설 시 "허위 개설은 법적 책임을 질 수 있다"는 고지 동의를 받고 시점을 기록합니다.

4.4 헌화 — 로그인을 요구할 것인가

조문객 대부분은 비회원입니다. 로그인을 강제하면 헌화가 사실상 일어나지 않습니다.

그래서 비회원 헌화를 허용하되 중복은 억제합니다.

  • 로그인 사용자: userId로 1인 1회 보장(DB 유니크 제약).
  • 비회원: 브라우저 토큰 + IP 해시 조합으로 중복을 억제합니다.

완벽하지 않다는 점을 명시합니다 — 브라우저를 바꾸면 우회됩니다. 헌화 수는 정확한 집계가 아니라

추모의 표현이므로 이 수준이 적정합니다. 정확성이 필요한 지표로 쓰지 마십시오.

  • IP는 원문 저장하지 않고 해시로만 보관합니다(개인정보 최소 수집).

4.5 방명록 — UGC 관리

방명록은 사용자 생성 콘텐츠이므로 악성 글·스팸이 들어옵니다. 유족이 사별 직후에 그런 글을 보게

되는 것은 서비스가 만든 2차 피해입니다.

  • 개설자(상주)는 자기 추모관의 방명록을 삭제할 수 있습니다. 별도 심사 없이 즉시.
  • 운영자는 강제 비공개(hiddenAt) 처리가 가능합니다 — 하드 삭제가 아니라 소프트 삭제로

분쟁 대비 원문을 보존합니다(SocialAccount.unlinkedAt에서 검증된 패턴).

  • 비회원 작성 허용(조문객 대부분이 비회원) — 이름·관계는 스냅샷 저장(§5.5).

4.6 사진 앨범 — 저장소 한계를 먼저 인정한다

추모 사진은 유족이 영구 보존을 기대하는 자산입니다. 그런데 현재 이미지 저장은

백엔드 로컬 디스크이고 백엔드는 아직 배포조차 되지 않았습니다(→ systems.md §5).

이 상태로 추모 사진 업로드를 실서비스로 열면 안 됩니다. 유실 시 복구가 불가능하고, 그 성격상

"죄송합니다"로 끝나지 않습니다.

  • Stage 1에서는 사진 업로드를 구현하되, 실서비스 오픈은 오브젝트 스토리지(S3 등) 전환 이후로 묶습니다.
  • 이 의존성을 systems.md에 등록하고, 배포 결정과 함께 처리합니다.
  • 업로드 용량·장수 상한은 policy.ts(→ 01-05 §12.3)에 둡니다. 하드코딩 금지.

5.5 `User` 변경 — `03-01` §2 원칙 반영

model User {
  // ... 기존 필드
  digitalCleanupItems DigitalCleanupItem[]  // docs 03-02 — 디지털 정리 진행 항목
  memorials           Memorial[]            // docs 03-02 — 개설한 추모관
  memorialTributes    MemorialTribute[]
  memorialGuestbooks  MemorialGuestbook[]
  memorialPhotos      MemorialPhoto[]
}

03-01 §2가 요구한 것이 바로 이것입니다 — 03 도메인의 모든 모델이 userId FK로 User에

연결되어야 운영자가 회원 상세에서 prisma.user.findUnique({ include: {...} }) 한 번으로

조인 조회할 수 있습니다(§6.4).

비회원이 만드는 데이터(헌화·방명록)는 userId가 nullable이므로, 회원 상세에서는 그 회원이 남긴

것만 보입니다. 나머지는 추모관 단위로 조회합니다. 이 비대칭은 의도된 것입니다 —

비회원 조문객을 회원으로 강제하지 않기 위한 대가입니다.

신청자 정보 스냅샷 원칙(01-05 §4.4)을 그대로 승계합니다: authorName을 User에서 조인해

표시하지 않고 작성 시점 값을 복사해 둡니다. 작성자가 나중에 이름을 바꾸거나 탈퇴해도

조문 당시의 기록이 보존되어야 하기 때문입니다.
