03-01. 현물 유품 수거 — 계정 형태 보류 메모 (+ 회원 연동 설계 원칙)

🔵 2026-08-12 — Domain 03(현물 유품 수거)의 유일한 문서가 됨.
도메인 재편(00-12 §7)으로 구 Domain 03이 **03(현물 유품 수거) / 04(디지털 자산·계정 정산) /
05(디지털 추모관)** 셋으로 갈라졌습니다. 이 메모는 §3(현물 유품)이 살아 있는 유일한 내용이라
신 Domain 03에 배치됐습니다.

>

⚠️ 즉, Domain 03은 지금 "기획 보류 상태인 도메인"입니다. 확정 스펙도, 상위 기획서도 없습니다.
§3이 이 도메인 전체의 착수 조건입니다.

>

§2의 userId FK 원칙은 04-01 §4.3 · 05-01 §3.5에 반영 완료되었습니다. 앞으로 그 원칙을
인용할 때는 그쪽을 참조하십시오. (구 03-02 §5.5·§6.4가 원래 자리였습니다.)
🔵 도메인 성격 확정(2026-08-12): 현물 유품 수거는 유가족 전용입니다. 대표 확정 사항이며,
생전(WellDying) 축이 없으므로 00-12 §2.4의 생전 위임(PreDeathDirective) 대상이 아닙니다.
문서 성격: 정식 스펙이 아니라 구현 메모입니다. 대표가 "운영자 대시보드에서 회원 클릭 시 도메인
데이터를 볼 수 있어야 하지 않나"라고 제안한 원칙을, 실제 착수 전에 근거를 남겨두기 위해
[Claude:Sonnet]이 대표 직접 지시로 작성했습니다(같은 방식이 02-02 문서에도 있었음 — 정식 스펙
작성은 원래 [Claude:Opus] 몫이나, 이번엔 사용자가 "md 파일 만들어달라"고 직접 요청).

>

등록: 2026-08-11 · 작성자: [Claude:Sonnet]

1. 지금 상태 (사실관계)

  • 구 Domain 03(디지털 유품 정리 · 추모관)은 백엔드 모델이 전혀 없습니다. schema.prisma에는 User 모델

하나만 있고, SNS 계정 삭제 신청·현물 유품 수거·추모관 방명록/헌화 등은 전부 DigitalEstatePage.tsx

안의 프론트 로컬 state(useState)로만 존재하는 100% 목업입니다.

  • 따라서 지금 시점에는 "운영자 대시보드에서 회원 클릭 시 도메인 데이터 확인"을 만들 수 있는 실제

DB 데이터가 없습니다. 이 문서는 나중에 실제 백엔드로 구현될 때 지켜야 할 설계 원칙을

남겨두는 용도입니다.

  • 현물 유품 수거(신 Domain 03)는 그중에서도 가장 뒤에 있습니다 — 계정 형태조차 정해지지 않아

모델을 그릴 수조차 없습니다(§3).

2. 설계 원칙 (대표 제안, 2026-08-11)

디지털 유품·추모관 관련 데이터는 성격상 특정 회원(User)에 종속된 데이터입니다. 운영자가 회원을

검색해서 찾을 수 있다면, 그 회원을 클릭했을 때 연결된 도메인 데이터(예: SNS 삭제 신청 처리 현황,

추모관 방명록/헌화 이력 등)를 함께 확인할 수 있어야 합니다.

구현 시 반영할 것: 신규 Prisma 모델(예: DigitalCleanupItem, MemorialGuestbook 등)은

전부 userId FK로 User와 연결되어야 합니다. 그래야 운영자 대시보드의 "회원 상세" 화면에서

prisma.user.findUnique({ where: { id }, include: { ... } }) 형태로 조인해서 한 화면에 보여줄 수 있습니다.

이 원칙은 Domain 06(엔딩노트)에도 동일하게 적용됩니다(→ 06-01 참고, 다만 06은 열람 범위에 별도 제약이 있음).

반영 완료: 04-01 §4.3(정리 항목) · 05-01 §3.5(추모관 4종). **현물 유품(이 도메인)은
모델이 아직 없어 미반영**이며, §3이 풀린 뒤 같은 원칙으로 설계해야 합니다.

3. 🔴 보류된 것 — 현물 유품 수거·정리 업체 (**이 도메인의 착수 조건**)

현물 유품 수거/정리를 어떤 사업자 형태로 다룰지(신규 계정 유형을 만들지, 기존 Partner/Expert를

확장할지, 외주 제휴사로 처리할지)는 기획이 아직 나오지 않아 보류합니다. 착수 전 반드시 [Claude:Opus]

기획 검토를 거쳐야 합니다 — 회원 유형을 잘못 설계하면(예: Expert에 억지로 끼워맞추기) 나중에

다시 뜯어고쳐야 할 가능성이 높습니다.

재편으로 이 보류의 무게가 커졌습니다. 예전에는 한 도메인의 한 탭이 빠지는 문제였지만, 이제는

Domain 03 전체가 이 결정을 기다리는 상태입니다. 구 03-02 §10-3이 *"DigitalEstatePage에서

탭이 사라지므로 재개 시점을 정해야 한다"* 고 지적한 사안이 그대로 이어집니다.
