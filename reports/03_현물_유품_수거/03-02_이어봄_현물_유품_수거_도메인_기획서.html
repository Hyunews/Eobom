🔑 3. 계정 설계 — Partner 확장

3.1 🔴 현행 Partner는 "장사시설 사업자"를 암묵적으로 전제하고 있습니다

schema.prisma:98의 Partner에는 업종을 구분하는 필드가 없습니다. 지금까지 파트너가

장사시설뿐이었기 때문입니다. 그리고 관계 필드 3개가 01 전용입니다.

facilities  Facility[]        // 01 전용 — 수거 업체는 시설을 갖지 않음
claims      FacilityClaim[]   // 01 전용 — 클레임할 공공데이터 시설이 없음
leads       Lead[]            // ✅ 공용 가능
settlements Settlement[]      // ✅ 공용 가능

→ 최소 변경으로 업종 축을 추가합니다.

model Partner {
  // ... 기존 필드 전부 유지

  partnerType String @default("FUNERAL_FACILITY")
  // FUNERAL_FACILITY(01 장사시설) | ESTATE_CLEANUP(03 유품 수거)
  // 기본값을 01로 두어 기존 데이터·기존 흐름이 그대로 유효합니다(마이그레이션 무해)

  serviceAreas String[]  // ESTATE_CLEANUP 전용 — 출동 가능 시·군·구 코드
  serviceTags  String[]  // ESTATE_CLEANUP 전용 — 일반정리 | 특수청소 | 폐기물운반 | 기부연계 ...
  licenseNo    String?   // ESTATE_CLEANUP 전용 — 폐기물처리업 허가·신고 번호(§6.1)
}
✅ **contextType(02-04 §5) · partnerType 둘 다 "기본값으로 무해하게 축을 하나 더한다"는
같은 패턴입니다. 이 프로젝트에서 두 번째이므로 패턴으로 굳혀도 좋습니다** —
열거형 컬럼 + 안전한 기본값 = 기존 데이터 무영향.

3.2 🟡 업체 목록은 어디서 오나 — 01과 결정적으로 다른 점

이것이 03에서 가장 과소평가되기 쉬운 문제입니다.

Domain 01Domain 03
초기 목록공공데이터 1,552건(e하늘 등)0건
제휴 전 상태목록은 이미 있고, 사업자가 자기 시설을 클레임아무것도 없음
사용자가 보는 것전국 시설 + 제휴사 강조제휴 업체만

01은 "먼저 지도를 그려놓고 사업자를 불러들이는" 구조였는데, 03에는 그릴 지도가 없습니다.

유품정리업은 공공 데이터셋이 없습니다(§6.1 — 법정 업종이 아니기 때문).

🔴 **그래서 FacilityClaim에 해당하는 절차가 03에는 없고, 대신 "직접 등록 심사"가 그 자리를
대신합니다.** 업체가 스스로 가입 신청 → 운영자가 서류를 보고 승인. Partner.status
(PENDING → APPROVED)를 그대로 씁니다.

>

⚠️ 부작용: 제휴 업체가 0건인 동안 화면에 보여줄 것이 없습니다.
00-14 §2-5가 지적한 *"제휴 업체 10곳 목업 + 별점"* 문제가 여기서 나온 것이며,
업체를 모으기 전에 화면을 열면 같은 문제가 반복됩니다. → §7.2

🗄️ 5. 데이터 모델 — 신규는 최소한으로

Partner 확장(§3.1) 외에 신규 모델은 1개입니다.

// 유품 수거 요청 — 유족이 남기는 견적 요청. Lead로 이어짐
model CleanupRequest {
  id         String   @id @default(uuid())
  userId     String              // FK → User (03-01 §2 원칙)
  deceasedId String?             // FK → Deceased (00-12 §2.1) — 확정 후 부착
  partnerId  String?             // 지정 요청이면 값, 지역 일괄 요청이면 null

  areaCode     String            // 작업 지역 시·군·구
  propertyType String            // APARTMENT | HOUSE | VILLA | OFFICE ...
  sizePyeong   Int?              // 평수 — 견적의 핵심 변수
  serviceTags  String[]          // 요청 항목(§3.1 serviceTags와 같은 어휘)
  preferredAt  DateTime?         // 희망 일정
  memo         String?

  status    String   @default("REQUESTED")  // REQUESTED | MATCHED | DONE | CANCELED
  createdAt DateTime @default(now())

  @@index([userId])
  @@index([areaCode, status])
}
04-01 DigitalCleanupItem · 07-01 AdminTaskProgress와 같은 형태입니다 —
유족 개인의 요청 1건 = 레코드 1건. 플랫폼 전체가 같은 모양을 반복하고 있고, 그게 맞습니다.
🟡 사진 첨부는 1차에서 넣지 않습니다. 견적 정확도는 올라가지만 고인의 주거 내부 사진은
민감도가 높고, 00-11 오브젝트 스토리지 전환 전에는 저장할 곳도 마땅치 않습니다
(05-01 §2.6 추모 사진과 같은 제약).

⚠️ 6. 이 도메인 고유의 위험 — 01·02와 다릅니다

6.1 🔴 "유품정리업"은 법정 업종이 아닙니다

확인 결과, 유품정리업·특수청소업이라는 이름의 허가·등록 제도는 없습니다.

업체들이 실제로 하는 일을 쪼개 보면 각각 다른 법에 걸립니다.

실제 행위관련 규제이어봄이 확인할 것
폐기물 수집·운반을 업으로 수행폐기물관리법 §25 폐기물처리업 허가 / 신고🔴 허가·신고 번호(licenseNo)
