📌 1. 현황 진단

이 도메인은 백엔드 모델이 0개이고 DigitalEstatePage.tsx의 로컬 state로만 존재합니다.

목업이 약속한 것실제 판단
추모관(헌화·방명록·앨범)⚠️ 방향은 유효하나 고인 1명당 1개라는 기본 구조가 없음

1.1 목업의 근본 문제: 추모관이 하나뿐이다

목업의 추모관은 전역 싱글턴입니다. 헌화 수가 42로 하드코딩돼 있고 방명록도 하나입니다.

누구의 추모관인지가 없으므로 실제 서비스로는 성립하지 않습니다.

추모관은 고인 1명당 1개이며, 유족이 개설하고, 고유 URL로 조문객이 방문합니다.

이것이 이 기능의 최소 성립 조건입니다.

🕯️ 2. 설계

2.1 공개 범위 — 기본값은 "링크를 아는 사람만"

값의미검색 노출
PRIVATE개설자와 지정 유족만❌
LINKURL을 아는 사람만 (기본값)❌
PUBLIC이어봄 내 추모관 목록에 노출⭕

기본값을 PUBLIC이 아니라 LINK로 두는 이유: 사망 사실과 유족 구성이 공개적으로 색인되면

부고 사칭 보이스피싱의 표적 정보가 됩니다. 실제로 부고 문자를 가장한 피싱은 이미 사회 문제입니다.

부고는 널리 알리는 것이 본래 성격이지만, "널리"의 주체는 유족이어야 하며 검색엔진이 아닙니다.

  • PUBLIC이어도 생년월일·주소·유족 실명 등은 공개 응답에서 제외합니다(§4.1 화이트리스트).
🔴 00-13 §2.2가 이 조항의 전제를 흔듭니다. *"URL을 아는 사람만"* 이라는 표현은 **1차 수신자
에만 참이고 2차 재전파 이후에는 거짓**입니다. 링크 모델 확정 시 이 절을 정정해야 합니다.

2.2 링크(slug) — 🔴 00-13 결정 대기

  • 비공개 URL은 추측 불가능한 토큰(slug)을 씁니다 — 순번(/memorial/1)이면 열람이 가능해집니다.
  • 현행 설계는 slug 1개 영구 불변입니다. 00-13이 이를 *"비밀번호 없는 영구 마스터 키 한 장"* 으로

진단하고 4개 안(A 단일영구 / B 회전가능 / C 단계분리 / D 초대기반)을 제시했습니다.

  • C안이 채택되면 Memorial.phase(OBITUARY → MEMORIAL)와 **장례 정보 컬럼(빈소·발인일시·장지·

조의금 계좌)이 이 문서에 신설**되며, Domain 07의 모바일 부고장이 이 도메인으로 흡수됩니다.

2.3 허위 추모관 방지

살아있는 사람의 추모관을 만드는 것은 심각한 명예훼손이며, 실제로 발생할 수 있는 악용입니다.

그렇다고 개설 시 사망진단서를 요구하면 아무도 쓰지 않습니다. 균형점:

1. 개설은 로그인 필수 — 최소한 누가 만들었는지 추적 가능해야 합니다(비회원 개설 불가).

2. 기본 비공개(LINK) — 확산이 제한적입니다(단 §2.1의 00-13 경고 참조).

3. 신고 창구 + 즉시 비공개 전환 — 신고가 접수되면 운영자 확인 전까지 자동 비공개로 전환합니다.

사후 확인보다 선차단이 맞습니다. 피해가 되돌릴 수 없는 종류이기 때문입니다.

4. 개설 시 "허위 개설은 법적 책임을 질 수 있다"는 고지 동의를 받고 시점을 기록합니다.

🔵 00-12 §4 사다리 적용: 추모관 개설은 L1(자기신고+로그인), PUBLIC 전환만 L2(운영자
검토)입니다. 이것이 05-02 §6.1이 미결로 남긴 개설 게이트의 답입니다.

2.4 헌화 — 🔴 로그인 요구 여부 재검토 중

현행 스펙: 조문객 대부분은 비회원이므로 비회원 헌화를 허용하되 중복을 억제합니다.

  • 로그인 사용자: userId로 1인 1회 보장(DB 유니크 제약).
  • 비회원: 브라우저 토큰 + IP 해시 조합으로 중복을 억제합니다.

완벽하지 않다는 점을 명시합니다 — 브라우저를 바꾸면 우회됩니다. 헌화 수는 정확한 집계가 아니라

추모의 표현이므로 이 수준이 적정합니다. 정확성이 필요한 지표로 쓰지 마십시오.

  • IP는 원문 저장하지 않고 해시로만 보관합니다(개인정보 최소 수집).
🔴 개발자 지적(2026-08-12): *"비로그인 사용자가 서비스를 이용한다? 나는 별로라고 생각해."*
로그인 필수로 전환하면 위 "억제만 가능" 문단과 IP 해시 수집이 통째로 사라집니다.
00-13 §6.1에 링크 모델별 함의가 정리돼 있으며, 링크 모델 확정 후 결정합니다.

2.5 방명록 — UGC 관리

방명록은 사용자 생성 콘텐츠이므로 악성 글·스팸이 들어옵니다. 유족이 사별 직후에 그런 글을 보게

되는 것은 서비스가 만든 2차 피해입니다.

  • 개설자(상주)는 자기 추모관의 방명록을 삭제할 수 있습니다. 별도 심사 없이 즉시.
  • 운영자는 강제 비공개(hiddenAt) 처리가 가능합니다 — 하드 삭제가 아니라 소프트 삭제로

분쟁 대비 원문을 보존합니다(SocialAccount.unlinkedAt에서 검증된 패턴).

  • 비회원 작성 허용 — 이름·관계는 스냅샷 저장(§3.3). §2.4와 같은 재검토 대상입니다.
🔴 05-02 §4가 지적한 공백: 작성자 본인의 방명록 삭제 권한이 없습니다. 로그인 유저가
자기 글을 못 지우는 건 부자연스럽습니다. 로그인 필수로 가면 자동 해소됩니다.

2.6 사진 앨범 — 저장소 한계를 먼저 인정한다

추모 사진은 유족이 영구 보존을 기대하는 자산입니다. 그런데 현재 이미지 저장은

백엔드 로컬 디스크입니다(→ systems.md §5).

이 상태로 추모 사진 업로드를 실서비스로 열면 안 됩니다. 유실 시 복구가 불가능하고, 그 성격상

"죄송합니다"로 끝나지 않습니다.

  • Stage 1에서는 사진 업로드를 구현하되, 실서비스 오픈은 오브젝트 스토리지(S3 등) 전환 이후로 묶습니다(00-11).
  • 업로드 용량·장수 상한은 policy.ts(→ 01-05 §12.3)에 둡니다. 하드코딩 금지.

🔒 5. 개인정보 (→ .harness/security.md)

1. 고인의 개인정보는 본인이 동의할 수 없습니다. 개설자가 대신 등록하는 구조이므로,

공개 범위 기본값을 좁게(LINK) 두는 것으로 위험을 상쇄합니다(§2.1).

2. IP는 해시로만 저장합니다(§2.4). 원문 저장 금지. §2.4가 로그인 필수로 바뀌면 이 항목은 삭제됩니다.

3. 방명록·헌화는 비회원 데이터를 포함하므로 최소 수집 원칙을 지킵니다 — 이름·관계·본문 외에

연락처·이메일을 받지 않습니다. 받을 이유가 없습니다.

4. 추모관 보존기간은 §8-1 사장님 확정 대상입니다. 무기한 보관은 스토리지 비용과 개인정보

최소보유 원칙 양쪽에 걸립니다.

7.1 구현 시 반드시 지킬 것

1. slug는 추측 불가 토큰으로 생성할 것 — 순번·UUID 노출 모두 부적절(§2.2).

2. 비공개 추모관 조회는 403이 아니라 404(존재를 숨김).

3. 공개 API 응답은 화이트리스트 select — deceasedBirthDate·개설자 정보 유출 금지(§4.1).

4. 신고 접수 시 운영자 확인 전에 먼저 비공개로 전환할 것(§2.3-3). 선차단 후 확인입니다.

5. IP 원문을 저장하지 말 것 — 해시만(§2.4).

6. 사진 업로드는 구현하되 실서비스 오픈은 오브젝트 스토리지 전환과 묶을 것(§2.6).

7. 업로드 상한 등 수치는 policy.ts에 둘 것 — 하드코딩 금지(01-05 §12).
