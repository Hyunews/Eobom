🔍 2. 더미 데이터 5종의 실제 구현 가능성 및 상세 기획 판단

현재 프론트엔드 코드(FacilityPage.tsx, facilities.json)에 포함된 5가지 핵심 데이터 항목은 기술적 및 비즈니스적으로 100% 실제 구현이 가능하며, 서비스의 본질적인 경쟁력이므로 모두 '유지'합니다.

2.1 [항목 1] 별점 (Star Rating)

  • 현재 코드 상태: facilities.json 내 rating: 4.9, rating: 4.8 등의 하드코딩된 더미 수치 노출.
  • 실제 구현 기술 방안:

* 자체 검증 리뷰 시스템 DB (facility_reviews) 구축: 단순 외부 카카오/네이버 별점이 아닌, 이어봄 플랫폼을 통해 실제 답사/상담/장례를 완료한 검증된 이용자만 리뷰 및 별점(1.0~5.0)을 작성할 수 있도록 구현.

* 집계 로직: DB 레벨에서 AVG(rating) 산술 평균값을 수신하여 실시간 업데이트.

* 초기 운영 전략: 서비스 출시 초기에는 지자체 및 보건복지부 공시 서비스 만족도 수치를 기본 부여하고, 실이용 유저의 리뷰가 5건 이상 누적되면 실제 유저 평점 가중치로 자동 전환.

  • 기획 최종 판단: [유지] — 유족 및 자녀 보호자가 장례식장을 비교할 때 가증 신뢰하는 핵심 지표임.

2.2 [항목 2] 주소 및 위경도 (Location & Address)

  • 현재 코드 상태: 실제 한국 도로명 주소(예: "서울 강남구 일원로 81") 및 정확한 위경도 좌표(lat: 37.4882, lng: 127.0856)가 들어있어, 모달 클릭 시 실제 카카오 맵 핀이 렌더링됨.
  • 실제 구현 기술 방안:

* 카카오 로컬 REST API (query=장례식장) 및 Kakao Maps JavaScript SDK 100% 연동:

* 사용자의 현위치(navigator.geolocation)를 수신하고, 하버사인(Haversine) 거리 계산 로직으로 5km, 10km, 20km 반경을 동적으로 필터링.

* 전국의 모든 장례식장/수목장의 정확한 주소, 전화번호, 지번, 위경도 좌표를 카카오 API로 실시간 수집 및 동기화.

  • 기획 최종 판단: [유지] — 기술적으로 이미 검증 완료되었으며 100% 실데이터 연동 가능.

🗺️ 3. 전국 장례식장 데이터 구축 및 노출 전략 (하이브리드 디렉토리 모델)

3.1 전략 채택 배경: Cold Start (초기 데이터 부족) 문제 방지

초기 스타트업이 "가입/제휴된 장례식장만 노출하는 입점제"를 선택하면, 서비스 오픈 초기 등록 시설이 수십 개에 불과하여 유저가 동네 장례식장을 검색했을 때 "검색 결과가 없습니다"가 발생하여 유저가 즉시 이탈하게 됩니다.

따라서 전국의 모든 장례식장을 첫날부터 검색할 수 있는 [하이브리드 디렉토리 모델]을 채택합니다.

3.4 하이브리드 모델의 3대 비즈니스 효과

1. 첫날부터 전국 100% 커버리지 확보: 유저가 전국의 어떤 대학병원이나 지역 장례식장을 검색해도 무조건 노출되어 UX 만족도 극대화.

2. B2B 입점 영업의 압도적 명분: 장례식장 사업자에게 *"이미 플랫폼에 등록되어 검색되고 있으나, 제휴 전환 시 [VR 360], [할인 견적], [상단 노출] 혜택이 부여됩니다"* 라며 자연스러운 입점 전환 유도.

3. 토탈 케어 브랜드 신뢰도 구축: 제휴 여부와 상관없이 모든 정보를 투명하게 개방함으로써 서비스의 공공성과 신뢰성 확보.

🛠️ 4. 개발 전달용 백엔드 DB 스키마 타겟 규격

개발팀(eobom/backend) 구현 시 아래 테이블 구조로 확장 반영을 진행합니다:

// 시설 마스터 테이블
model Facility {
  id           String   @id @default(cuid())
  name         String
  type         String   // "장례식장", "묘지/수목장"
  location     String   // 도로명 주소
  lat          Float
  lng          Float
  price        String
  priceValue   Int
  rating       Float    @default(0.0)
  religion     String
  guests       String
  isPartner    Boolean  @default(false) // 제휴 파트너 여부
  vrImages     Json?    // VR 투어 이미지 JSON
  createdAt    DateTime @default(now())

  tags         FacilityTag[]
  reviews      FacilityReview[]
  bookings     FacilityBooking[]
}

// 시설 리뷰 테이블
model FacilityReview {
  id         String   @id @default(cuid())
  facilityId String
  userId     String
  rating     Float
  content    String
  createdAt  DateTime @default(now())

  facility   Facility @relation(fields: [facilityId], references: [id])
}
ℹ️ 위 §4는 2026-08-05 작성 당시의 타겟 규격이며, 실제 구현 스키마는 그 뒤로 크게 확장됐다.
현행 정본은 00-05_DB_요구사항_및_테이블_사전.md (schema.prisma에서 자동 생성, 13개 테이블·146개 컬럼).

🆕 5. "업체 자세히 보기" — 답사 예약 대체 설계 (2026-08-11 신설, 미구현)

§2.5에서 답사 예약을 폐기하면서 생긴 공백을 메우는 과제다. **답사를 가야만 알 수 있던 정보를 화면에서

충분히 보여줘서 답사 필요성 자체를 없애는 것**이 목표다.

5.1 왜 필요한가

현재 시설 카드는 이름·주소·평점·태그·가격문자열·사진 정도만 보여준다. 유족이 "여기가 어떤 곳인지"

판단하기엔 부족한데, 답사 예약도 없앴으므로 판단 근거를 화면이 대신 제공해야 한다.

이게 없으면 유족은 결국 전화를 걸게 되고, 전화는 수수료 청구 근거가 안 된다(→ 01-05 §9).
