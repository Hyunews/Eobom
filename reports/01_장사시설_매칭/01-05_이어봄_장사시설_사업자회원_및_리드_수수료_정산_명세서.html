🏢 16. 장사시설 사업자 회원 & 리드 수수료 정산 명세서

문서 목적: 장사시설(장례식장·묘지/수목장) 사업자가 B2C 유저와 분리된 사업자 계정으로 가입·관리되고, 유저가 남긴 문의·견적요청을 추적 가능한 리드(Lead)로 적재하여 수수료 청구의 법적·상업적 근거로 삼는 체계를 정의합니다.

>

근거: 2026-08-10 사장님 지시(개발자 전달) 2건 —
① 장사시설 업체가 사업자로 따로 회원가입하고 우리가 따로 관리한다.
② 유저가 웹을 통해 문의·견적요청을 남기면 로그/견적요청 번호를 우리가 보유하여, 추후 그것을 근거로 수수료를 청구한다.

>

선행 문서: 13(견적 데이터 한계 3대 대안) · 14(답사예약 vs 직통전화 리드 수수료 검토) · 10(§3.3 제휴/비제휴 차별화)
본 문서는 위 검토서들이 "필요하다"고 결론 낸 것을 실제 구현 가능한 스펙으로 확정하는 문서입니다.

📌 1. 이 문서가 푸는 문제

14가 이미 지적한 핵심 문제는 이것입니다 — 직통 전화(tel:)로 연결되면 장례식장 원장은 그 유족이 이어봄을 보고 왔는지 알 방법이 없고, 우리도 수수료를 청구할 명분이 없다.

사장님 지시(개발자 전달)는 이 문제의 해법을 두 축으로 확정한 것입니다.

축무엇을 만드나왜 필요한가
① 사업자 회원 체계수수료를 청구할 상대방(법인격)을 시스템에 등록청구서를 보낼 대상이 DB에 없으면 정산 자체가 불가능
② 리드 로그 + 견적요청 번호청구의 증거"이 번호의 유족을 우리가 보냈다"는 대조 가능한 물증

둘은 분리 불가능합니다. 리드만 쌓으면 청구할 상대가 없고, 사업자만 받으면 청구할 근거가 없습니다.

🏢 3. 사업자 회원 체계

3.1 왜 User 테이블에 role만 추가하지 않는가

기존 User는 소셜 로그인(카카오/네이버/구글) 전제로 설계되어 있고 role 필드에 'USER' | 'EXPERT' | 'ADMIN'이 있습니다. 여기에 'PARTNER'를 얹는 것이 가장 적은 코드로 보이지만 채택하지 않습니다.

이유설명
인증 방식이 다름사업자는 담당자 퇴사·교체가 잦아 개인 소셜 계정에 묶으면 안 된다. 업체 이메일 + 비밀번호가 맞다.
필수 정보가 다름사업자등록번호·상호·대표자명·정산 계좌는 B2C User에 전부 null로 남아 스키마가 오염된다.
법인격 단위가 다름한 법인이 장례식장 2곳을 운영할 수 있다. 계정(사람)과 사업자(법인)를 1:1로 묶으면 확장이 막힌다.
탈퇴 정책이 다름B2C 유저는 탈퇴 시 삭제 대상이지만, 사업자는 정산 이력 때문에 함부로 지울 수 없다.

→ Partner 모델을 신설하고 User와 분리합니다. 사장님 지시의 "따로 회원가입 / 따로 관리"와도 일치합니다.

자동 승인은 채택하지 않습니다. 사업자등록번호 진위는 API로 검증되지만, "그 사업자가 그 시설의 운영자인가"는 자동 검증이 불가능합니다. 이걸 자동화하면 타인이 남의 장례식장 리드(=유족 개인정보)를 열람하게 됩니다. 개인정보 사고의 직접 경로이므로 수동 심사를 필수로 둡니다.

3.3 시설 소유권 클레임

시설 마스터(Facility 1,552건)는 공공데이터·카카오 API로 우리가 먼저 만들어 둔 것이라, 사업자는 "이미 있는 내 시설"을 자기 것이라 주장(claim)하는 형태가 됩니다.

  • 가입 시 또는 가입 후, 사업자가 디렉토리에서 자기 시설을 검색해 클레임 신청
  • 운영자가 승인하면 Facility.partnerId가 채워지고 그 시점부터 해당 시설의 리드가 이 사업자에게 귀속
  • 한 사업자가 여러 시설 클레임 가능 (Partner 1:N Facility)
  • 이미 다른 사업자에게 승인된 시설은 중복 클레임 불가 — 신청은 받되 운영자에게 분쟁 건으로 표시

3.4 isPartner 필드 처리 (기존 스키마와의 정합성)

Facility.isPartner(Boolean)가 이미 존재하고 10 §3.3·13 대안 B가 이 값으로 UI를 분기합니다. 신설되는 partnerId와 의미가 겹치므로 한쪽을 정본으로 못 박습니다.

  • 정본(SSOT): Facility.partnerId — 승인된 클레임이 있으면 채워짐
  • isPartner: 목록 조회 필터·정렬 성능을 위한 파생 캐시 컬럼으로 재정의. 클레임 승인/해지 트랜잭션 안에서만 갱신한다.
  • 두 값이 어긋나면 partnerId가 이긴다. 정합성 점검 배치를 운영 초기에 1회 이상 돌린다.
파생 컬럼을 두는 이유: 목록 API가 매 요청 partnerId IS NOT NULL 조인 없이 인덱스만으로 파트너 우선 정렬을 하도록. 단, 동기화 지점을 트랜잭션 한 곳으로 제한해야 썩지 않는다.

🎫 4. 리드(Lead)와 견적요청 번호

4.1 리드 유형

유형발생 지점개인정보 수집수수료 청구 근거로서의 강도
QUOTE 업체 문의업체 문의 폼 모달(InquiryModal)✅ 이름·연락처강함 — 유저가 명시적으로 신청, 번호 발급
CONSULT 1:1 상담신청상담 신청✅강함
CALL 전화 버튼 클릭tel: 링크 클릭❌ 익명 이벤트약함 — §9 참조. 기본 비청구
2026-08-11 정정 — BOOKING(답사예약) 유형 폐기. 개발자·사장님 논의로 답사예약 기능 자체를 도입하지 않기로 확정(→ 01-01 §2.5, 01-04 폐기 배너)되면서 FacilityBooking 모델·API가 제거됐고, BOOKING 리드를 만들 생산자가 사라졌습니다. 스키마의 Lead.type에서도 값이 삭제됐습니다(구현: walkthrough 2026-08-11 (6)). 남은 유형은 위 3종입니다.

>

QUOTE는 원래 "견적요청"이었으나 견적 비교 기능도 함께 폐기(→ 01-01 §2.3)되면서 실제 화면은 "업체 문의"로 바뀌었습니다. enum 값 QUOTE는 그대로 두고 표시 문구만 바꿨습니다 — 이미 적재된 리드의 타입 값을 바꾸면 과거 정산 근거가 흔들리기 때문입니다.
CALL을 청구 근거로 쓰지 않는 이유는 §9에 따로 적었습니다. 클릭했다고 통화한 것이 아니고, 통화했다고 계약한 것도 아니기 때문에 업체가 반박하면 우리가 증명할 수단이 없습니다. 약한 근거로 청구하면 파트너 신뢰를 잃습니다. 지표로만 씁니다.

4.2 견적요청 번호 (사장님 지시 ②의 핵심)

전화로 "EB-260810-0001 건입니다"라고 대조할 수 있어야 하므로, 내부 PK(uuid)와 별개의 표시용 번호를 발번합니다.

EB - 260810 - 0001
│    │        └─ 그날의 일련번호 (4자리, 일 단위 리셋)
│    └─ 발생일 YYMMDD
└─ 고정 접두어
  • 불변: 발번 후 절대 변경·재사용 금지. 상태가 바뀌어도 번호는 그대로.
  • 유니크 제약을 DB에 건다(@unique). 동시 요청 시 중복 발번을 애플리케이션 로직으로만 막지 않는다.
  • 번호만으로는 조회 불가: 번호는 대조용 식별자일 뿐, 상세 조회는 반드시 인증(파트너 본인 시설 / 운영자)을 거친다. 번호가 순차적이라 추측이 쉬우므로 인증 없는 조회 API를 만들면 그대로 개인정보 유출이 된다.

4.3 리드 상태 머신

 REQUESTED ──▶ NOTIFIED ──▶ RESPONDED ──┬─▶ CONVERTED  (계약 성사 → 청구 대상)
  (접수)       (업체전달)     (업체응답)   │
                                        └─▶ LOST       (무산 → 비청구)
      │
      └────────────────────────────────────▶ INVALID    (허수·중복·장난 → 비청구)
  • 상태 변경은 누가·언제 했는지 statusHistory에 누적한다. 정산 분쟁 시 이 이력이 유일한 방어 수단이다.
  • CONVERTED 판정은 업체 신고 + 운영자 확인의 2단계. 업체 자기신고만 믿으면 축소 신고(수수료 회피) 유인이 생긴다.
  • INVALID 처리 권한은 운영자만. 업체가 임의로 허수 처리하면 청구를 무력화할 수 있다.

4.4 신청자 정보 스냅샷 — 왜 userId 참조만으로 부족한가

리드에 userId만 걸어두면, 유저가 탈퇴하는 순간 정산 근거가 사라집니다. 반대로 개인정보를 영구 보관하면 개인정보보호법 위반입니다. 둘 다 피해야 하므로:

  • 리드 생성 시 신청자 이름·연락처를 스냅샷으로 복사 저장한다(applicantName, applicantPhone).
  • 정산 확정 후에는 스냅샷을 마스킹한다 — 홍길동 → 홍*동, 010-1234-5678 → 010-****-5678.
  • 마스킹 후에도 leadNo·발생시각·시설·금액·상태이력은 보존된다 → 청구 근거는 유지, 개인정보는 최소화.
  • 보유기간·마스킹 시점은 §7.3.

🗄️ 5. 데이터 모델 (Prisma)

기존 모델 변경은 추가(additive)만 합니다. 2026-08-05 마이그레이션으로 User/SocialAccount가 유실된 사고가 있었으므로(→ .harness/security.md §6), 마이그레이션 전 pg_dump 필수입니다.

5.1 신규 모델

// 사업자 (법인격 단위) — B2C User와 완전 분리
model Partner {
  id            String   @id @default(uuid())
  email         String   @unique          // 로그인 ID
  passwordHash  String
  refreshToken  String?

  bizRegNo      String   @unique          // 사업자등록번호 (하이픈 제거 10자리)
  companyName   String                    // 상호
  ownerName     String                    // 대표자명
  contactName   String                    // 담당자명
  contactPhone  String
  bizLicenseUrl String?                   // 사업자등록증 사본 (비공개 스토리지)

  status        String   @default("PENDING") // PENDING | APPROVED | REJECTED | SUSPENDED
  rejectReason  String?
  approvedAt    DateTime?

  settlementBank    String?
  settlementAccount String?               // 암호화 저장 (평문 금지)

  facilities   Facility[]
  claims       FacilityClaim[]
  leads        Lead[]
  settlements  Settlement[]
  commissionPolicies CommissionPolicy[]    // 이 파트너 전용 특약 요율 (없으면 기본 요율 적용)

  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  @@index([status])
}

// 시설 소유권 클레임
model FacilityClaim {
  id          String   @id @default(uuid())
  partnerId   String
  partner     Partner  @relation(fields: [partnerId], references: [id], onDelete: Cascade)
  facilityId  String
  facility    Facility @relation(fields: [facilityId], references: [id], onDelete: Cascade)

  status      String   @default("PENDING") // PENDING | APPROVED | REJECTED
  evidenceUrl String?                      // 시설 인허가증 등 소유 증빙
  reviewNote  String?                      // 운영자 심사 메모
  reviewedAt  DateTime?
  createdAt   DateTime @default(now())

  @@unique([partnerId, facilityId])        // 같은 사업자의 중복 신청 방지
  @@index([status])
}

// 리드 (업체 문의 · 상담신청 · 전화클릭)
model Lead {
  id          String   @id @default(uuid())
  leadNo      String   @unique             // EB-260810-0001 (표시·대조용, 불변)
  type        String                       // QUOTE | CONSULT | CALL (BOOKING 폐기 → §4.1)

  facilityId  String
  facility    Facility @relation(fields: [facilityId], references: [id])
  partnerId   String?                      // 발생 시점 귀속 파트너 (없으면 비제휴)
  partner     Partner? @relation(fields: [partnerId], references: [id])

  userId      String?                      // 로그인 유저면 참조 (탈퇴 시 null)

6.4 인증 분리 원칙

  • 사업자 토큰과 B2C 유저 토큰은 payload에 aud(대상) 필드를 넣어 구분하고, 미들웨어에서 교차 사용을 차단한다.
  • /api/partner/*에 B2C 토큰이 들어오면 401. 반대도 동일.
  • **/api/admin/*는 별도 Admin 모델 + aud='admin' 토큰으로 보호**한다.
2026-08-11 정정 — 운영자 인증 방식 변경. 초안은 "User.role === 'ADMIN'으로 보호(기존 role 필드 활용)"였으나, 구현 단계에서 독립 Admin 모델로 바꿨습니다(구현: walkthrough 2026-08-10 (3)). 이유는 두 가지입니다.

>

1. B2C 로그인 경로와 운영자 권한이 한 테이블에 얽히면 사고 반경이 커진다. 소셜 로그인으로 들어온 계정에 role 하나만 잘못 세팅돼도 즉시 운영자가 됩니다. 초안 스스로 "demo-login의 ADMIN 발급 경로를 실배포 전 반드시 차단할 것"이라는 위험을 적어뒀는데, 이는 차단해야 할 구멍이 애초에 생기는 설계라는 뜻이었습니다.
2. 운영자는 공개 가입이 없어야 한다. Admin에는 signup API를 만들지 않고 prisma/seed-admin.ts 스크립트로만 계정을 생성합니다. 가입 폼이 존재하는 것 자체가 공격면입니다.

>

결과적으로 초안이 경고했던 demo-login ADMIN 발급 문제는 경로 자체가 사라져 해소됐습니다(demo-login은 프로덕션 가드도 별도로 적용됨). 3종 토큰(aud: user/partner/expert)에 admin이 더해져 총 4종이며, 교차 사용은 전부 401입니다.

🔐 7. 개인정보 — 이 문서에서 가장 위험한 부분

유족의 이름·연락처를 장례식장에 넘기는 행위는 개인정보 제3자 제공(개인정보보호법 제17조)입니다. 동의 없이 넘기면 서비스 자체가 중단될 수 있는 위험이므로, 아래는 선택이 아니라 구현 필수 조건입니다.

7.1 동의 없이는 리드를 만들지 않는다

업체 문의 폼에 필수 동의 체크박스를 두고, 아래 4가지를 명시합니다.

고지 항목내용
제공받는 자신청한 해당 장사시설 사업자 (상호 명시)
제공 목적업체 문의 연락
제공 항목이름, 연락처, 요청 내용
보유·이용 기간목적 달성 후 파기 (§7.3)
2026-08-11 정정: 답사예약 폐기(§4.1)에 따라 고지 문구에서 "답사 예약 연락"을 뺐습니다. 코드의 고지 문구와 noticeVersion도 함께 갱신됐습니다(구현: walkthrough 2026-08-11 (6)). 문구를 바꿔도 과거 동의 건의 consentSnapshot은 그대로 보존되므로, 그 시점에 무엇에 동의했는지는 계속 증명됩니다 — 아래 항목이 요구하는 바 그대로입니다.
  • 체크 없이 제출 불가. thirdPartyConsentAt이 null인 리드는 파트너에게 노출하지 않는다.
  • 동의 시점의 고지 문구 전문을 consentSnapshot에 저장한다. 나중에 문구를 바꿔도 "그때 무엇에 동의했는지"를 증명할 수 있어야 한다.

7.2 비제휴 시설은 개인정보를 전달하지 않는다

partnerId가 없는 시설(전국 대부분)에도 견적요청은 들어올 수 있습니다. 이때:

  • 리드는 적재하되, 제공받을 사업자가 특정되지 않으므로 개인정보를 아무에게도 전달하지 않는다.
  • 이어봄 상담원이 직접 응대한다(13 대안 C의 해피콜 모델).
  • 영업용으로는 건수만 사용한다 — *"귀 시설에 지난달 문의 12건이 접수됐습니다. 제휴하시면 바로 연결됩니다"*. 10 §3.4의 B2B 영업 명분과 정확히 일치하며, 개인정보를 넘기지 않고도 영업이 된다.

7.3 보유기간과 마스킹

시점처리
리드 생성이름·연락처 평문 저장 (업무 수행에 필요)
상태 CONVERTED/LOST 확정 + 정산 확정마스킹 실행 (maskedAt 기록)
그 이후leadNo·시각·시설·금액·상태이력만 보존 → 청구 근거 유지
  • 마스킹은 배치로 돌린다. "정산 끝났는데 개인정보가 남아있는" 상태가 길어지지 않도록 주기와 실행 로그를 남긴다.
  • 파트너 어드민에서는 응답 완료 후 연락처를 마스킹 표시한다. 필요 이상으로 오래 원문을 보여줄 이유가 없다.

7.4 기타

  • bizLicenseUrl(사업자등록증 사본)은 공개 정적 경로에 두지 않는다. 인증된 운영자만 접근 가능한 비공개 스토리지 + 서명 URL.
  • settlementAccount(정산 계좌)는 암호화 저장. .harness/security.md §1의 평문 금지 원칙 적용.
  • 문서·테스트 픽스처에는 실제 업체·유족 정보를 쓰지 않는다(홍길동, 010-0000-0000).

  ② t 시점에 유효한 정책을 찾는다
       partnerId = 이 리드의 파트너  →  있으면 특약 요율 (우선)
       partnerId = null             →  없으면 기본 요율
       조건: effectiveFrom <= t AND (effectiveTo IS NULL OR t < effectiveTo)
  ③ basis에 따라 금액 산출
  ④ 결과를 Lead.billedAmount + Lead.commissionPolicyId 에 **스냅샷으로 박는다**

④가 핵심입니다. 계산 결과만 저장하면 "왜 이 금액인지" 설명할 수 없고, 요율 ID만 저장하면 정책 레코드가 수정될 때 과거 금액이 흔들립니다. 둘 다 남겨야 정산 분쟁에서 방어됩니다.

  • 요율을 바꿀 때는 기존 레코드를 수정하지 않는다. 이전 레코드의 effectiveTo를 닫고 새 레코드를 추가한다. 과거 정산 재계산이 항상 같은 값을 내야 하기 때문이다.
  • 같은 이유로 CommissionPolicy는 삭제하지 않는다. 잘못 넣었으면 즉시 effectiveTo로 닫는다.
  • 산정 기준이 미확정이어도 구조는 지금 만든다. 확정되면 레코드 1건을 넣는 것으로 끝난다(→ §10-1).

⚠️ 9. 알려진 한계 — 전화 문의는 지금 구조로 증명되지 않는다

사장님 지시 ②는 "문의 혹은 견적 요청"이라고 하셨는데, 전화 문의는 현재 기술로 증명이 안 됩니다.

단계우리가 아는가
유저가 tel: 버튼을 눌렀다✅ 이벤트 로그로 알 수 있음
실제로 통화가 연결됐다❌ 브라우저는 통화 결과를 알려주지 않음
그 통화로 계약이 성사됐다❌ 전혀 알 수 없음

즉 CALL 리드로 수수료를 청구하면 업체가 "그런 전화 온 적 없다"고 할 때 반박할 물증이 우리에게 없습니다. 그래서 §4.1에서 CALL을 기본 비청구로 둡니다.

해결 경로는 050 안심번호(가상번호)입니다. 시설마다 우리 명의의 050 번호를 발급해 착신 전환하면 통화 발생·시각·통화시간이 우리 로그에 남아 청구 근거가 됩니다. 부수 효과로 유족 번호가 업체에 직접 노출되지 않아 §7 개인정보 부담도 줄어듭니다. 다만 통신사 계약과 회선당 과금이 발생하므로 파트너 수가 확보된 뒤 도입하는 것이 합리적입니다. → 별도 검토 문서로 분리 제안.

그 전까지 실무적으로 유효한 방법은 업체 문의 폼으로 유도하는 것입니다(01-04 대안 1과 동일한 결론). 제휴 시설에는 [업체 문의] 버튼을 눈에 띄게 배치합니다.

2026-08-11 정정: 원안은 "전화는 보조 수단으로 둔다"였으나, 2026-08-10 개발자 지시로 시설 카드에서 전화번호(tel: 링크) 노출 자체를 제거했습니다(구현: walkthrough 2026-08-10 (5)). 따라서 현재 CALL 리드를 만들 진입점이 화면에 없습니다 — CALL 유형은 050 도입 또는 전화 노출 재개 시를 대비해 스키마에만 남아 있는 상태입니다.

안내용장점단점

⚙️ 12. 설정·정책 관리 방침 (하드코딩 제거 원칙)

2026-08-10 확정. "돈과 법에 닿는 값은 DB에 이력과 함께, 나머지 정책은 파일 한 곳에, 환경 차이만 .env에."

12.1 왜 .env에 넣으면 안 되는가

.env의 원래 용도(Twelve-Factor App 3원칙)는 "배포 환경마다 달라지는 것"입니다. 수수료율은 개발 서버와 운영 서버에서 다를 이유가 없습니다. 환경 차이가 아니라 경영 판단입니다.

  • .env에 정책을 넣으면 → *"스테이징만 수수료 10%"* 같은 환경별 값 어긋남 사고
  • .env는 변경 이력이 남지 않는다 → 정산 분쟁에서 "그때 요율이 얼마였는지" 증명 불가

12.2 3계층 배치

계층담는 것위치이력
환경 설정DB 주소, OAuth 키, JWT 키, 지도 키eobom/backend/.env · eobom/frontend/.env남기지 않음(시크릿)
운영 정책로그인 요구 여부, 이의제기 기간, 비제휴 수용, leadNo 접두어, 마스킹 주기eobom/backend/src/config/policy.ts 단 한 곳git 커밋 이력
요율(돈)수수료 기준·금액·정률, 파트너별 특약DB CommissionPolicy + 유효기간레코드 자체가 이력

요율만 DB인 이유는 §8.2에 있습니다 — 요약하면, 9월에 요율을 올린 뒤 8월 정산서를 재발행하면 파일 방식은 9월 요율로 계산해버립니다. 이미 청구한 금액과 어긋나고 증명할 방법이 없습니다. 요율은 값이 아니라 기간이 붙은 레코드여야 합니다. 부수 효과로 파트너별 특약 요율(초기 입점 할인, 대형 법인 협상가)이 구조 변경 없이 가능해집니다.

나머지를 파일로 두는 이유는 비용 대비 효용입니다. 이 값들은 과거 시점 재현이 필요 없고 1년에 몇 번 안 바뀌므로, 어드민 화면을 만들 값어치가 없습니다. 자주 바꾸게 되면 그때 DB로 옮기면 됩니다 — 파일 → DB는 쉽고, DB → 파일은 어렵습니다.
