🏢 장사시설 매칭 명세서 Doc #01-05

장사시설 사업자 회원 & 리드 수수료 정산 명세서

B2B 사업자 계정(Partner), 시설 소유권 클레임, 리드 로그 & 견적요청 번호(EB-YYMMDD-NNNN), 제3자 제공 동의, 월 정산, 3계층 설정/정책 관리

문서 목적: 장사시설(장례식장·묘지/수목장) 사업자가 B2C 유저와 분리된 사업자 계정으로 가입·관리되고, 유저가 남긴 문의·견적요청을 추적 가능한 리드(Lead)로 적재하여 수수료 청구의 법적·상업적 근거로 삼는 체계를 정의합니다.
근거: 2026-08-10 대표 확정 지시 2건 및 2026-08-11 정정 반영
선행 문서: 01-03(견적 데이터 한계 3대 대안) · 01-04(답사예약 vs 직통전화 검토) · 01-01(§3.3 제휴/비제휴 차별화)

📌 1. 이 문서가 푸는 문제

01-04가 이미 지적한 핵심 문제는 이것입니다 — 직통 전화(tel:)로 연결되면 장례식장 원장은 그 유족이 이어봄을 보고 왔는지 알 방법이 없고, 우리도 수수료를 청구할 명분이 없다.

축 무엇을 만드나 왜 필요한가
① 사업자 회원 체계 수수료를 청구할 상대방(법인격)을 시스템에 등록 청구서를 보낼 대상이 DB에 없으면 정산 자체가 불가능
② 리드 로그 + 견적요청 번호 청구의 증거 "이 번호의 유족을 우리가 보냈다"는 대조 가능한 물증

🧭 2. 범위

2.1 이번 범위에 포함

  • 설정·정책 관리 방침 — 수수료율·운영 정책을 코드에서 분리 (§12)
  • 사업자 회원가입·심사·승인 및 사업자 전용 로그인 (B2C 소셜 로그인과 완전 분리)
  • 사업자 ↔ 시설(Facility) 소유권 연결 및 클레임 심사
  • 리드(업체 문의·상담신청·전화클릭) 적재 및 리드 번호 발번 (답사예약 폐기 → §4.1)
  • 리드 상태 추적 (접수 → 전달 → 응답 → 성사/무산)
  • 개인정보 제3자 제공 동의 절차 (법적 필수 — §7)
  • 파트너 어드민 최소 화면 · 내부 운영자 어드민 최소 화면
  • 월 단위 정산서 생성 및 이의제기 처리

🏢 3. 사업자 회원 체계

3.1 왜 `User` 테이블에 role만 추가하지 않는가

Partner 모델을 신설하고 User와 분리합니다. 이유: 인증 방식 다름(이메일+비밀번호), 필수 정보 다름(사업자등록번호·상호·정산계좌), 법인격 단위 다름(1:N 시설 관리), 탈퇴 정책 다름(정산 이력 보존).

3.2 가입 → 승인 플로우

[사업자]                          [이어봄 운영자]
   │
   │ ① 가입 신청 (상호/사업자번호/대표자명/담당자/이메일/비밀번호 + 사업자등록증 사본)
   ▼
 status = PENDING ───────────────▶ ② 심사 큐에 노출
   │                                   │ (사업자번호 진위확인 + 증명서 대조 + 소유관계 확인)
   │◀──────────────────────────────────┤
   │
   ├─ APPROVED  → 로그인·리드 열람 가능
   ├─ REJECTED  → 사유 통보, 재신청 가능
   └─ SUSPENDED → 계약 해지·연체 시

자동 승인은 채택하지 않습니다. 남의 장례식장 리드(=유족 개인정보) 열람 사고 방지를 위해 수동 심사를 필수로 둡니다.

3.3 시설 소유권 클레임 & 3.4 isPartner 필드 처리

사업자가 기존 1,552개 Facility 중 자기 시설에 소유권 클레임(Claim) 신청 → 운영자 승인 시 Facility.partnerId 연결(SSOT). Facility.isPartner는 파생 캐시 컬럼으로 재정의하여 승인/해지 트랜잭션 내에서 동기화합니다.

🎫 4. 리드(Lead)와 견적요청 번호

4.1 리드 유형

유형 발생 지점 개인정보 수집 수수료 청구 근거 강도
QUOTE 업체 문의 업체 문의 폼 모달(InquiryModal) ✅ 이름·연락처 강함 — 명시적 신청, 번호 발급
CONSULT 1:1 상담신청 상담 신청 ✅ 이름·연락처 강함
CALL 전화 버튼 클릭 tel: 링크 클릭 ❌ 익명 이벤트 약함 — 기본 비청구

2026-08-11 정정 — BOOKING(답사예약) 유형 폐기. 답사예약 기능 미도입 확정으로 FacilityBooking 모델·API 삭제 및 Lead.type 값 제거 완료.
QUOTE는 화면 표시 문구가 "업체 문의"로 변경되었으나 enum 값 QUOTE는 과거 정산 이력 보존을 위해 그대로 유지합니다.

4.2 견적요청 번호 (EB-YYMMDD-NNNN)

EB-260810-0001 형태의 표시용 불변 번호 (DB @unique 제약). 인증 없는 조회 API는 절대 제공하지 않습니다.

4.3 리드 상태 머신 & 4.4 신청자 정보 스냅샷

REQUESTED ──▶ NOTIFIED ──▶ RESPONDED ──┬─▶ CONVERTED (계약 성사 → 청구 대상)
                                      └─▶ LOST      (무산 → 비청구)
INVALID (허수·중복 → 운영자만 지정 가능)

신청자 정보는 applicantName, applicantPhone 스냅샷으로 복사 저장 후, 정산 확정 시 마스킹 처리합니다 (예: 010-****-5678).

🔌 6. API 명세 (구현 현황)

6.1 사업자 인증 · 계정 `/api/partner`

  • ✅ POST /api/partner/signup (PENDING 가입)
  • ✅ POST /api/partner/login & refresh (APPROVED만 로그인)
  • ✅ GET /api/partner/me & PATCH /api/partner/me (정보/정산계좌 수정)
  • ✅ GET /api/partner/facilities & POST/GET /api/partner/claims
  • ✅ POST/DELETE /api/partner/facilities/:id/images (시설 사진 업로드)
  • ⬜ GET /api/partner/leads & PATCH /api/partner/leads/:leadNo/status (정산 수수료 확정 대기)

6.2 운영자 어드민 `/api/admin`

  • ✅ POST /api/admin/login & GET /me (독립 Admin 모델)
  • ✅ GET /api/admin/partners & PATCH /api/admin/partners/:id/status
  • ✅ PATCH /api/admin/partners/:id (담당자명·연락처 등 운영 편의 정보 수정)
  • ✅ GET /api/admin/claims & PATCH /api/admin/claims/:id/status

운영자의 회원정보 수정 범위 원칙 (2026-08-11 신설)
- 운영 편의 정보(담당자명, 연락처): 직접 수정 허용
- 검증된 신원 정보(사업자등록번호, 자격증번호, 상호): 직접 수정 금지 — 심사 이력 보존을 위해 반려 후 재신청 수순 적용.

2026-08-11 정정 — 운영자 인증 방식 변경: 초안의 User.role === 'ADMIN' 방식에서 독립 Admin 모델 + aud='admin' 토큰으로 변경. 공개 회원가입 경로가 없는 보안 구조를 확립했습니다.

🔐 7. 개인정보 보호 & 💰 8. 정산 체계

  • 제3자 제공 동의: 업체 문의 모달에서 동의 필수, 동의 시점 문구를 consentSnapshot에 보존.
  • 비제휴 시설: 개인정보 전달 없이 이어봄 상담원이 응대하고 건수만 영업 자료로 활용.
  • 수수료 정책 (CommissionPolicy): 코드 하드코딩이나 .env가 아닌 DB CommissionPolicy 레코드(유효기간 effectiveFrom/To) 기반 계산 스냅샷 박음.
