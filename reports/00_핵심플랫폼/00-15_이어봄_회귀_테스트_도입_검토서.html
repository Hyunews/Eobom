🎯 2. 왜 이 프로젝트에서 문제가 되는가 — 일반론이 아닌 부분

*"테스트가 있으면 좋다"* 는 어느 프로젝트에나 해당하는 말이라 결정 근거가 되지 못합니다.

이어봄에만 해당하는 논점은 다음 셋입니다.

2.1 🔴 검증 게이트가 이미 있지만, 자동 테스트의 대체재가 아니라는 것이 실증됐습니다

이 프로젝트에는 이미 사람 손 회귀 장치가 있습니다 — **walkthrough.md 게이트 + Gemini

교차검증**(roles.md §2). *"그럼 자동 테스트는 중복 아닌가"* 라는 반론이 가능합니다.

그런데 게이트가 실행 불가로 우회된 사례가 이미 두 번 나왔습니다.

walkthrough (19)·(22) — [Opus]의 docs/ 산출물과 [Gemini]의 reports/ 전건 재생성이
한 커밋에 섞여 들어갔습니다(개발자 판단). 그 결과 게이트 항목 **§2-4(미선언 변경 대조)가
커밋 diff만으로는 항목별 귀속을 가를 수 없게 되어**, (22) ⑥의 단서 조항 — *"귀속 대상은
열거된 10개 경로뿐"* — 으로 우회 처리됐습니다.

여기서 읽어야 할 것은 "커밋을 나눠 담자"가 아닙니다.

사람이 운영하는 게이트는 운영 사정(커밋 묶음·시간·피로)에 의해 무력화될 수 있다는 것이고,

자동 테스트는 그 사정에 영향받지 않는다는 것입니다. 둘은 대체재가 아니라 보완재입니다.

2.2 🔴 3주체 협업 구조가 "돌려봤다"의 증거를 요구합니다

roles.md §2의 구조는 [Sonnet]이 구현하고 [Gemini]가 판정합니다.

그런데 지금 판정의 재료가 스크린샷과 문장뿐입니다.

walkthrough (21)의 검증 필드를 그대로 보면 이렇습니다:

*"tsc --noEmit·vite build 통과. Chrome dev 서버로 /care-guide 전체 스크롤 확인 —
…배너, 카테고리 헤더·항목·배지·링크 전부 렌더 확인."*

이것은 성실한 기록이지만 재현 가능한 증거는 아닙니다.

record.md §1-1이 *"결과는 반증 가능하게"* 를 요구하는데,

npm test 한 줄이 그 요구에 대한 가장 싼 답입니다. 판정자가 직접 돌려볼 수 있기 때문입니다.

2.3 도메인이 얽히기 시작했습니다

05-02 §6.4가 예견한 상황이 이미 왔습니다.

최근 사례얽힘

00-13 E안부고장(07) ↔ 추모관(05) 링크 중첩 — 한쪽 개설이 다른 쪽을 자동 생성

앱 로직은 조용히 깨질 수 있습니다. 이런 것이 회귀 테스트의 정확한 표적입니다.

🔴 4. 도입하지 말아야 할 이유 — 같은 비중으로 적습니다

4.1 지금 쓰는 테스트의 상당수가 곧 폐기 대상입니다

이것이 가장 무거운 반론입니다. 현재 프로젝트 상태:

  • Deceased 미확정 — 04·05·07의 데이터 모델이 아직 안 섰습니다(context.md).
  • 04·05 프론트 보류, 06은 전 기능 목업, 03은 구현 0건.
  • 스펙이 계속 뒤집히고 있습니다 — 최근만 봐도 00-13 권고 C안 → E안, 02-05 직역 권고 철회,

00-16 L3 서류 근거 변경.

아직 굳지 않은 것에 테스트를 붙이면 테스트가 부채가 됩니다.
스펙이 바뀔 때마다 테스트를 고쳐야 하고, **고치기 귀찮아지면 테스트를 지우거나 무시하게 되며,
그 순간부터 "빨간 테스트가 정상"이 됩니다.** 이것은 테스트가 없는 것보다 나쁩니다.

4.2 1인 개발에서 테스트는 "지금 시간"을 확실히 쓰고 "나중 시간"을 불확실하게 아낍니다

00-11 §3.3이 확인한 팀 여건은 전담 인프라·보안 인력 없음이고, 개발도 사실상 1인 + 3에이전트입니다.

테스트를 짜는 시간만큼 기능이 늦어집니다. 오픈 전이고 사용자가 0인 지금, 그 교환이 유리하다는

보장이 없습니다.

4.3 러너 도입 자체에도 비용이 붙습니다

TypeScript + Prisma + Express 조합은 테스트 DB 준비(별도 스키마 또는 컨테이너), 마이그레이션

적용, 시드·격리·정리가 필요합니다. "jest 설치"로 끝나지 않습니다.

4.4 🔴 잘못 도입하면 게이트가 약해질 수 있습니다

*"테스트 통과했으니 됐다"* 가 되면 §2.1의 사람 게이트가 형식화됩니다.

지금 이 프로젝트에서 실제로 버그를 잡고 있는 것은 문서 대조와 실측입니다

(예: 03-02 §4.1의 facilityId 필수 제약은 스키마를 직접 읽어서 찾았습니다).

자동 테스트는 이런 종류를 못 잡습니다.

🟡 5. 그래서 권고 — 전면 도입이 아니라 "안 바뀌는 것부터"

§4.1이 옳고 §2가 옳다면, 답은 "도입/미도입"이 아니라 "무엇에만" 입니다.

5.1 안 바뀌는 것 = 테스트 가치가 높은 것

도메인 화면·목업 데이터❌ 지금 붙이면 안 됨 — §4.1 대상—

사람 눈으로 회귀를 잡기 가장 어려운 종류입니다.

5.3 도입한다면 지켜야 할 것

1. 빨간 테스트를 방치하지 않습니다. 고칠 수 없으면 지웁니다. 무시되는 테스트는 부채입니다.

2. 커버리지 목표를 세우지 않습니다. 숫자를 좇으면 §4.1의 폐기 대상을 늘리게 됩니다.

3. 테스트가 게이트를 대체하지 않는다는 것을 record.md에 명시합니다(§4.4).

4. 테스트 데이터는 security.md §2를 그대로 따릅니다 — 실제 개인정보 금지.

❓ 6. 결정에 필요한 것

#물어야 할 것답이 필요한 이유
①0단계(스크립트 보존 규칙)만 지금 켜는 데 이견이 있으신지비용 0이라 사실상 *"안 할 이유가 있나"* 만 확인하면 됩니다

③3단계(CI)는 00-11 배포 사업자 확정에 종속지금 정할 수 없습니다
🟡 작성자 권고: ①은 지금 켜고, ②는 Deceased 확정 사이클과 함께.
이유는 §4.1입니다 — Deceased가 서면 04·05·06·07의 모델이 함께 굳고, 그때가 테스트를
붙여도 폐기되지 않는 첫 시점입니다. 그 전에 붙일 가치가 있는 것은 §5.1의 1번뿐이고,
그건 Deceased와 무관하므로 먼저 넣어도 손해가 없습니다.
