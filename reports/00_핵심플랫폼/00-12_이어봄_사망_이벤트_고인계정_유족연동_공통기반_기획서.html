📌 1. 이 문서가 푸는 문제

이어봄은 사별을 다루는 플랫폼인데, "사망"이라는 사건을 시스템이 표현하는 방법이 정의된 적이 없습니다.

지금 상태를 나란히 놓으면 모순이 바로 보입니다.

도메인"고인"을 무엇으로 다루나"사망 확인"을 어떻게 하나
추모관(05-01)**문자열** (Memorial.deceasedName)**안 함** — 자기신고
계정 정산(04-01)다루지 않음 (유족 본인 관점)**안 함** — 증빙서류 미수집(§3.3)

User 모델**개념 없음** — 살아있음이 암묵 전제—

엔딩노트는 이미 사용자에게 약속했습니다: *"생전에는 철저히 비밀이 보장되며, 사후 사망진단서

확인 및 지정 유족의 이중 동의 완료 시에만 안전하게 복호화되어 전송됩니다."*(EndingNotePage.tsx,

그런데 "사망진단서 확인"도 "지정 유족"도 데이터 모델이 없습니다. 약속만 화면에 걸려 있습니다.

1.1 이걸 안 풀면 생기는 일

1. 생전에 엔딩노트를 써둔 회원이 사망 → 받을 유족을 시스템이 모릅니다. 기능이 영원히 미완성.

2. 유족이 추모관을 만들어도 → 고인의 이어봄 계정과 연결되지 않습니다. 별개의 데이터로 남습니다.

3. 고인의 계정이 → 살아있는 채로 방치됩니다. 로그인 가능, 마케팅 발송 대상, 보유기간 무기한.

4. 대표님이 제안한 생전 정산 신청(본인이 미리 처리 방식 선택)을 얹을 자리가 없습니다.

🧩 2. ✅ 핵심 개념 4개

2.1 `Deceased` — 고인은 문자열이 아니라 엔티티다

이것이 3-1 문제의 답입니다. 고인을 독립 엔티티로 만들고, 이어봄 회원이었으면 그 계정과 연결합니다.

두 경우를 하나의 모델로 다뤄야 합니다.

케이스상황`Deceased.userId`
**A. 회원이었던 고인**생전에 엔딩노트를 쓰거나 정산 계획을 신청해둔 사람값 있음
**B. 비회원 고인**유족이 추모관만 개설한 경우 (대다수 예상)null

Deceased가 있으면 추모관·정산·엔딩노트가 전부 같은 고인을 가리킬 수 있습니다. 지금은 각자

따로 놉니다. B 케이스도 자연스럽게 담깁니다 — 계정 없는 고인도 고인입니다.

2.2 `DeathVerification` — 사망 확인은 "있다/없다"가 아니라 강도다

04-01 §3.3은 증빙서류를 안 받기로 했고, 06-01은 사망진단서를 약속했습니다. **이 둘은 충돌이

아니라 층위 차이입니다** — 행위마다 필요한 확인 강도가 다릅니다. §4에서 사다리로 정리합니다.

2.3 `BereavedRelation` — 유족에는 두 종류가 있다

종류누가 정하나신뢰도권한
**지정 유족****본인이 생전에 지정**높음엔딩노트 개봉 동의, 정산 실행 요청
**자칭 유족**사후에 스스로 주장낮음추모관 개설·관리 정도

이 구분이 없으면 §4의 검증 사다리를 만들 수 없습니다. 지금은 전부 "로그인한 아무나"입니다.

2.4 `PreDeathDirective` — 생전 위임 (대표 제안의 자리)

대표 지시(2026-08-12): *"죽기 전의 고인이 정산에 대한 계획을 미리 신청해놓고, 처리 방식을 미리
선택하는 선택지를 주는 게 옳지 않나. 1)유족처리 2)행정사처리 3)운영자가 대신처리 를 모두 제공."*

이 제안이 04-01의 가장 큰 제약을 풀어버립니다. 제가 "이어봄은 대행할 수 없다"고 단정한 근거는

*"고인의 위임 의사를 사후에 확인할 방법이 없다"* 였는데, **본인이 생전에 위임 의사를 명시해두면

전제가 달라집니다.** 유족이 사후에 주장하는 위임과 본인이 생전에 남긴 위임은 법적 무게가 다릅니다.

처리 방식이어봄 역할수익법적 근거
**① 유족 처리**안내·진행 추적없음(무료 훅)낮음 — 이미 구현됨
**② 행정사 처리**연결·중개중개 수수료02-01 기존 검토 활용
**③ 운영자 대행****직접 처리****대행 수수료**🔴 **신규 법률 검토 필수**

③은 생전 위임이 있어도 자동으로 합법이 되진 않습니다. 각 플랫폼의 약관이 제3자 대리를 금지할

수 있고, 유상 대행이 행정사법 저촉 소지가 있는지 별도 확인이 필요합니다. 다만 **"검토할 가치가

생겼다"는 점이 중요합니다** — 사후 위임만 있을 때는 검토 자체가 무의미했습니다.

🗄️ 3. 🟡 데이터 모델 초안

// 고인 — 회원이었을 수도, 아닐 수도 있다(§2.1)
model Deceased {
  id           String    @id @default(uuid())
  userId       String?   @unique   // 이어봄 회원이었으면 연결. 비회원 고인이면 null
  name         String              // 고인 성명
  birthDate    DateTime?
  deathDate    DateTime?
  registeredBy String              // 이 고인 정보를 등록한 User (자칭 유족일 수 있음)

  verifications DeathVerification[]
  relations     BereavedRelation[]
  // memorials, cleanupPlans 등 각 도메인이 여기 붙는다
}

// 사망 확인 — 강도별로 여러 건이 쌓일 수 있다(§4)
model DeathVerification {
  id         String    @id @default(uuid())
  deceasedId String
  level      String    // SELF_DECLARED | OPERATOR_REVIEWED | DOCUMENT_VERIFIED
  reviewedBy String?   // 운영자 확인 시
  verifiedAt DateTime?
  // ⚠️ 서류 파일 자체는 저장하지 않는 것을 기본으로 한다(§5)
}

// 유족 관계 — 지정(생전) vs 자칭(사후)(§2.3)
model BereavedRelation {
  id           String  @id @default(uuid())
  deceasedId   String
  userId       String
  kind         String  // DESIGNATED(본인이 생전 지정) | SELF_CLAIMED(사후 자칭)
  relationship String? // 자녀·배우자 등
  designatedAt DateTime?  // DESIGNATED일 때, 본인이 지정한 시각
  @@unique([deceasedId, userId])
}

// 생전 위임 — 본인이 살아있을 때 작성(§2.4)
model PreDeathDirective {
  id         String @id @default(uuid())
  userId     String @unique          // 작성자(생전 본인)
  handlerType String                 // FAMILY | AGENT | OPERATOR (①②③)
  // 대상 플랫폼별 처리 지시는 하위 테이블로
  createdAt  DateTime @default(now())
}

🪜 4. ✅ 검증 강도 사다리 — 이것이 "검증 체계"의 정본

대표님이 지적한 *"검증이 부족하다"* 의 답입니다. 검증은 도메인별이 아니라 행위의 위험도별입니다.

단계확인 수준어떤 행위에 요구되나근거
**L0****없음**안내 카탈로그 열람, 추모관 조문(헌화·방명록)정보 제공·조의 표현일 뿐
**L1****자기신고 + 로그인**추모관 개설(LINK), 정리 체크리스트 사용확산 제한적, 되돌릴 수 있음
**L2****운영자 검토**추모관 PUBLIC 전환, 유족 관계 자칭 등록색인·공개 노출은 위험도가 다른 층
**L3****서류 기반 사망 확인****운영자 대행 신청, 엔딩노트 개봉**되돌릴 수 없음. 재산·비밀에 접근
**L4****L3 + 지정 유족 이중 동의**엔딩노트 중 민감 항목06-01이 화면에서 이미 약속한 수준

4.1 이 사다리가 해결하는 것

  • 04-01 §3.3(서류 미수집)과 06-01(사망진단서 확인)이 더 이상 충돌하지 않습니다. 전자는

L0~L1 행위였고 후자는 L3~L4 행위입니다. 층이 다른 얘기였습니다.

  • Domain 05(추모관)에만 게이트가 없다는 05-02 §6.1 지적도 여기서 풀립니다 — 추모관은 L1이 적정이고,

PUBLIC만 L2로 올리면 됩니다.

  • 운영자 대행(③)이 왜 어려운지가 분명해집니다 — L3가 필요하고, L3는 서류를 봐야 하며,

서류를 보려면 §5 문제가 따라옵니다.

4.2 🔴 L3의 서류를 저장할 것인가

04-01 §3.3은 *"안 받는 쪽을 기본값으로"* 라고 했고 그 판단은 지금도 유효합니다. 하지만 L3

행위(대행·엔딩노트 개봉)에는 확인이 필요합니다. 절충안:

  • 운영자가 화면에서 확인하되 서버에 파일을 남기지 않는다 — 확인 사실(verifiedAt, reviewedBy)만 기록
  • 또는 단기 보관 후 자동 파기(확인 완료 시점에 즉시 삭제)

🔴 실제 운영 가능성과 법적 증빙 필요성을 함께 봐야 하는 사안이라 대표·전문가 확인 대상입니다.

🔐 5. ✅ 고인 계정 처리 정책 — "계속 남겨두는 게 옳은가"

결론: 그냥 두면 안 되고, 그냥 지워서도 안 됩니다. 새로운 상태가 필요합니다.

5.1 왜 방치하면 안 되나

  • 로그인이 살아있습니다 — 비밀번호를 아는 사람이면 누구나 고인 행세를 할 수 있습니다
  • 마케팅·알림 발송 대상에 남습니다 (유족에게 2차 상처)
  • 개인정보 보유기간이 무기한이 됩니다

5.2 왜 삭제해서도 안 되나

  • 엔딩노트가 그 계정 안에 있습니다 — 삭제하면 유족에게 전달할 대상이 사라집니다

7.1 ✅ "양쪽"은 두 가지 뜻이었습니다 — 대표 지적으로 드러난 정정

초안은 04만 "양쪽" 으로 표시했는데, 대표님의 진입 분류(WellDying / 유가족)를 대보니

02도 양쪽입니다. 그런데 같은 라벨이 전혀 다른 구조를 가리키고 있었습니다.

"양쪽"의 의미승계
**02** 전문가 매칭같은 기능을 **두 주체가 각자** 쓴다❌ 없음
**04** 디지털 정산**한 주체가 시작해 다른 주체가 끝낸다**⭕ 있음

7.2 ✅ 승계 원칙 — 통로는 06 하나

대표 지적(2026-08-12): *"굳이 전문가가 연결되어야 하나 싶음. 유언 등을 남길 것이었다면 06과

이어지는 게 자연스러움."* → 채택.

생전 도메인고인이 남기는 것유족 연결근거
**02** 전문가상담 이력❌거래 이력이지 유산이 아님. 넘기면 **유족 간 분쟁 소지 + 전문가 비밀 위반**. 유족은 본인 자격으로 새로 신청
**04** 정산PreDeathDirective⭕유족이 **집행 주체**. 연결 안 되면 지시가 소멸
**06** 엔딩노트유언·메시지⭕**이 도메인의 존재 목적 그 자체**(§1.1-1)
✅ 원칙: 고인이 유족에게 무언가를 남기는 통로는 06 하나입니다. 다른 도메인이 각자 승계 경로를
만들지 않습니다 — 경로가 하나여야 §4의 L4 게이트도 하나로 족합니다. 도메인마다 게이트를 만들면
가장 약한 게이트가 플랫폼 전체의 보안 수준이 됩니다.

>

04만 예외인 이유: 04는 "전달"이 아니라 "위임"이고, 수신자가 유족이 아닐 수도 있어
(②행정사·③운영자) 06을 경유할 수 없습니다.

>

고인이 담당 전문가를 알리고 싶으면 엔딩노트에 적어서 보냅니다 — 02가 직접 연결되는 것이
아니라 06이 매개합니다.

7.3 🔴 아직 안 풀린 것 — 연결의 "발견" 단계

승계 대상은 정해졌지만, 유족이 *"고인이 이어봄 회원이었다"* 는 사실을 어떻게 아는지는

미해결입니다. 순환 구조가 있습니다:

이어봄이 지정 유족에게 알리려면 → 사망을 알아야 함 → 누군가 신고해야 함 →
신고할 사람은 유족인데 → 유족은 계정 존재를 모름

🟡 권고(대표 상의 대기): 생전 지정 시점에 지정된 유족에게 즉시 통지하면 순환이 끊깁니다.

덤으로 §2.3 BereavedRelation에 없는 "지정당한 사람의 수락" 절차도 생깁니다 — 지금은 본인

동의 없이 남을 지정 유족으로 박아넣을 수 있는 상태입니다.

제약: 비회원 고인이 다수(§2.1 케이스 B)이므로 연결 기능이 기본 동선에 끼어들면 안 됩니다.

매칭 실패와 "요청자가 지정 유족이 아님"을 구분 없이 무반응 처리해야 합니다(05-01 §4.1의

404 원칙과 같은 사상).
