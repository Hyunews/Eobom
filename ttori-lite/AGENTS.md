# AGENTS.md — ttori-lite 행동 규칙

> 이 파일이 SSOT(단일 진실 공급원)다. `CLAUDE.md`/`GEMINI.md`는 이 파일을 가리키는 포인터일 뿐이다.
> 대상: **1인 + 에이전트 1개**(Claude Code / Gemini CLI(Antigravity) / Codex CLI 등 무관) + Obsidian 볼트.
> biz-ttori(회사용, 멀티에이전트 오케스트레이션)의 후속작. 멀티에이전트 전용 장치(AI호출 3단계 정책, inbox/outbox 메일박스, 호칭관리)만 빼고
> 나머지(G-Brain, 구조화 메모리, 헬스체크 툴링)는 그대로 가져온다 — 그건 혼자 써도 가치있는 엔지니어링이었다.
> 설계 배경: `projects/_meta/스펙초안.md`

---

## 0. SESSION_START — 세션 시작 시 반드시

1. `memory/context.md` 읽고 "지금 상태" 파악 (1화면 이내로 유지, 늘어지면 다이어트)
2. `memory/MEMORY.md` 훑기 — 관련 있어 보이는 타입별 메모리(user/feedback/project/reference) 있으면 열어서 확인
3. 반복 작업이면 `skills/`에 이미 정리된 절차 있는지 먼저 확인 (없으면 이번에 처음 하는 거고, 두 번째부터 여기 남긴다)
4. 실프로젝트 작업이면 `projects/<name>/context.md` 확인 — 실제 코드는 여기 없고 다른 워크스페이스에 그대로 있음(외장 두뇌 모델, 절대경로로 참조)
5. 가끔(매번 아니어도 됨) `tools/memory-sync-check.sh`로 메모리 레이어 정합성 점검, 실프로젝트 만졌으면 `tools/staleness-check.sh`로 문서-코드 최신성 확인

## 1. 작업 순서

```
PLAN → CONFIRM → CODE/WRITE → (선택) SELF-REVIEW → SAVE → UPDATE
```

- **UPDATE**: `memory/context.md` "지금 상태" 갱신 + 반복 작업이었으면 `skills/`에 절차 남기기
- 서브에이전트(리뷰 분신 등)를 지원하는 툴이면 코드 작성과 리뷰를 분리해서 돌려도 좋음. 지원 안 하면 생략 — 필수 아님.

## 2. 재사용 가능한 스킬 흡수 (`skills/`)

- **다른 사람의 좋은 워크플로우를 가져왔거나, 같은 작업을 두 번째로 하게 되면 `skills/<name>.md`로 남긴다.** 상세 컨벤션: `skills/README.md`
- 이게 "초기 환경구성" 다음으로 이 하네스의 핵심 가치다 — 시간이 지날수록 스스로/남에게서 배운 절차가 쌓여서 매번 처음부터 삽질하지 않게 되는 것.

## 3. G-Brain — 코드 ↔ 문서 지식 그래프 (경량판)

> 전체 원칙은 `memory/g-brain-map.md`에. 핵심만 요약:

- 링크는 **파일/모듈 단위로만**. 함수 단위 링크 금지 — 코드가 바뀌는데 링크가 안 따라가면 "링크가 거짓말 = 환각 소스"가 된다.
- 안정적 앵커(자주 안 바뀌는 파일·계약)에만 링크. 세부 구현엔 걸지 않는다. 링크 남발 금지.
- 주기적으로 `tools/gbrain-doctor.sh`로 깨진 `[[링크]]` 점검.
- **외장 두뇌 모델**: 이 레포는 코드 저장소가 아니라 프로젝트들의 컨텍스트·계약·기획만 담는 허브다. 실프로젝트가 생기면 `projects/<name>/context.md`를 만들고 실제 코드 경로는 절대경로 포인터로만 남긴다(복사 금지). 이 레포 루트에서 에이전트를 띄워야 이 규칙이 로드된다.

## 4. 구조화된 메모리 (`memory/`)

- 배운 것/들은 것을 아무렇게나 `context.md`에 다 우겨넣지 않는다. 타입별로 나눠서 쌓는다: `user`(나에 대해) / `feedback`(교정·확인 이력, 이유 포함) / `project`(진행 배경·결정·기한) / `reference`(외부 시스템 포인터).
- 각 메모리는 `memory/<slug>.md`로 파일 하나, `memory/MEMORY.md`에 한 줄 인덱스. 형식은 `memory/MEMORY.md` 참고.
- **코드 패턴·git 히스토리·이미 문서화된 것은 메모리로 안 남긴다** — 코드/git이 이미 진실 공급원이니 중복.

## 5. 검색·정보 품질

- 라이브러리 버전/API 스펙처럼 빠르게 바뀌는 정보는 "확인 필요" 또는 "컷오프 기준" 명시하고 자신있게 단정하지 않는다.
- 공식 문서(공식 사이트/GitHub 릴리즈 노트) 우선, 커뮤니티 글은 교차검증 후 보조로만 사용.

## 6. 작업일지

- `daily/yymmdd.md`에 그날 한 실무 작업만 기록. 이 하네스 자체의 스펙업/설정 변경은 일지에서 제외(이력 오염 방지).
