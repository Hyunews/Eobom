# Gemini 문서화·검증 핸드오프 프롬프트

> 언제 쓰나: Claude가 의미 있는 작업 단위를 끝내고 `[Gemini]` 차례로 넘길 때. 매번 프롬프트를 새로 짜지 않는다.

## 왜 템플릿이 필요한가

Gemini에게 "정리해줘"라고만 넘기면 **자기가 안 한 일을 추측으로 채운다.** 2026-08-07에 실제로 두 번 났다 —
Render로 결정된 배포를 `context.md`에 "Railway 배포 대기"로 적었고, `pending-approvals` 배너를 두 차례 지웠다.
그래서 이 템플릿은 매번 **원본 경로를 명시**하고 **금지사항을 같이 실어 보낸다.** 원본이 없는 항목은 아예 시키지 않는다.

## 절차

1. 먼저 Claude가 `walkthrough.md` 5개 필드를 채운다 — **이게 원본이다.** 이걸 안 쓰고 Gemini에게 넘기면 템플릿이 무의미하다.
2. 아래 블록의 `<>` 부분만 채워 응답 맨 끝에 출력한다(→ `roles.md` §6).
3. Gemini 판정이 `❌반려`면 Sonnet이 수정, `🔄스펙갱신`이면 **Opus**가 `docs/`를 고친다(Gemini는 `docs/` 쓰기 권한 없음).

## 템플릿 — 게이트 검증 + 시각화

```
──────────────────────────────
▶ 다음: Gemini (Antigravity)
아래를 복사해서 붙여넣으세요:

.harness/GEMINI.md 읽고 아래 두 가지만 해줘.

1) 게이트 검증: docs/작업일지_및_기록/에이전트_기록/walkthrough.md 의
   "<YYYY-MM-DD | 작업 제목>" 항목을, 근거 스펙 <docs/경로.md> 와 대조해서
   그 항목 바로 아래에 판정 1줄만 덧붙여줘 (✅통과 / ❌반려(사유) / 🔄스펙갱신(문서)).
   특히 `편차` 필드의 <편차 요약>이 스펙상 허용되는지 판단해줘.

2) 시각화: <reports/경로.html> 를 위 스펙 정본에 맞춰 갱신해줘.

지키기: 코드는 읽지 마(요약과 스펙만 대조). docs/ · eobom/ · .harness/ 는 읽기 전용이야.
원본에 없는 내용은 채우지 마 — 모르면 "확인 필요"라고 적어.
gemini_tasks.md 에 검토 메모 남기고, 끝나면 Claude 핸드오프 블록 출력해줘.
──────────────────────────────
```

시각화할 게 없으면 2)를 빼고 1)만 보낸다. 반대로 검증할 항목이 없으면 1)을 뺀다 — **없는 일을 시키면 지어낸다.**

## 주의사항 / 함정

- **`context.md`를 Gemini에게 갱신시키지 않는다.** 세션 상태 요약은 해석적 기록이라 전언 오류가 가장 잘 나는 지점이다. 마지막 작업자가 직접 쓴다(→ `roles.md` §1-2).
- **`pending-approvals.md`는 언급조차 하지 않는다.** 항목 해제는 사용자만 한다. 프롬프트에 넣으면 "정리"하다가 지운다.
- 프롬프트 안의 작업 제목·경로는 **실존하는 것만** 넣는다. 없는 경로를 주면 비슷한 파일을 찾아 엉뚱한 걸 고친다.
- 판정을 받아오면 그것으로 끝이다. **통과한 항목을 Claude가 다시 검토하지 않는다** — 중복 검증을 없애려고 만든 구조다.
