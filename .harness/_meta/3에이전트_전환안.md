# 3에이전트 체제 전환안

> 2026-08-07 논의 중 사용자 퇴근으로 중단 → **2026-08-10 사용자 승인, 같은 날 반영 완료.**
> 반영 내역은 맨 아래 §반영 결과 참조.

## 사용자 제안

| 역할 | 담당 |
|---|---|
| 개발·구현 | Claude **Sonnet** |
| 기획·설계 | Claude **Opus** |
| 문서화·교차검증 | Gemini **Flash** |

Claude는 CLI에서 `/model`로 Sonnet↔Opus 전환. 사용자 질문: *"문서 읽고 쓰는 권한은 특별히 달라지지 않아도 된다고 보는데 어떻게 생각해?"*

## Claude 검토 결과 — 바꿔야 할 건 딱 하나

```diff
  roles.md §1-1 소유권 표
- | docs/ (기획 SSOT) | Gemini | Claude |
+ | docs/ (기획 SSOT) | Claude:Opus | Gemini |
  | reports/ (HTML·PDF) | Gemini | Claude |   ← 유지
```

- **`docs/`는 필수 변경**: 기획 주체가 Gemini → Claude:Opus로 옮겨갔으므로, 이걸 안 바꾸면 Opus가 자기 일(기획서 작성)을 못 한다.
- **`reports/`는 Gemini 유지**: 시각화 HTML 생성 = 기계적 문서화라 새 역할에 오히려 부합.
- **나머지 변경 불필요**: `eobom/`(Claude), `.harness/`(Claude), `assets/`(사람), 기록 파일 1:1 분리 모두 그대로.

## 함께 지적한 2가지

### 1. Sonnet/Opus는 파일 소유권으로 구분 불가능

같은 CLI·같은 도구·같은 파일시스템 권한이라 소유권 표로 나눌 수 없고 `harness-doctor`도 구별 못 한다.
→ **소유권상으로는 "Claude" 한 주체**로 두고, 구분은 "누가 쓰냐"가 아니라 "어떤 모드로 일하냐"로 관리.

다만 `context.md` 태그는 세분화가 필요하다 — 사용자가 **어느 모델로 바꿔야 하는지** 알아야 하므로:

```
[Claude:Opus]   → /model opus 후 기획
[Claude:Sonnet] → /model sonnet 후 구현
[Gemini]        → Antigravity 창
[사용자]         → 계정·대시보드 조작
```

`harness-doctor.sh` 5-1 검사의 태그 정규식도 같이 수정 필요.

### 2. Flash에게 "해석적 문서화"를 맡기는 건 위험

**실제 사례(2026-08-07)**: Gemini가 `context.md`에 "Railway 배포 수순 대기 중"이라 기재(실제 결정은 Render), `pending-approvals` 배너 2회 삭제.
Gemini 능력 문제가 아니라 **자기가 안 한 일을 옮겨 적는 구조** 자체의 전언 게임 리스크이며, Flash는 가장 약한 모델이라 이 리스크가 커진다.

| 종류 | 담당 | 이유 |
|---|---|---|
| **기계적** — HTML 시각화, 인덱스 갱신, 포맷 정리 | Gemini Flash ✅ | 원본이 이미 있어 왜곡 여지 적음 |
| **해석적** — "무엇을 왜 했는지" 사실 기록 | 작업 당사자(Claude) | 당사자만 정확히 앎 |
| **교차검증** — 스펙 대조 후 판정 | Gemini Flash ✅ | 읽고 판단만, 새 사실 안 만듦 |

현행 `walkthrough.md` 구조(Claude가 항목 본문 + Gemini가 판정 1줄)가 이미 이 원칙에 부합하므로 **변경 불필요**.

### 반영하며 추가로 정한 것

- **스펙갱신 판정의 실행 주체**: Gemini가 `🔄스펙갱신`을 내려도 `docs/`를 못 고친다(쓰기 권한 없음). 판정만 남기고 수정은 `[Claude:Opus]`가 한다 — `roles.md` §2, `done.md` §4에 명시.
- **맨 `[Claude]` 태그 금지**: 사용자가 어느 모델로 전환할지 알 수 없으므로 doctor가 실패시킨다. 규칙을 글이 아니라 장치로 강제하는 원칙(README §3) 적용.
- **`roles.md`가 예산 한계 → 분리로 해소**: §0 추가로 8188B / 8192B(여유 4B)까지 찼다. 예산을 올리는 대신 **기록 형식(구 §3)을 `.harness/record.md`로 분리**했다(2026-08-10). `roles.md` 7628B(여유 564B), `record.md` 2727B / 6144B.
  - 분리 기준: `roles.md`에서 유일하게 "역할 분담"이 아닌 섹션이었고, 기록할 때만 필요해 조건부 로드에 적합했다.
  - **§ 번호는 재배치하지 않았다.** `roles.md` §3은 `record.md`를 가리키는 포인터로 남긴다 — §4·§5·§6을 당기면 `AGENTS.md`·`done.md`·`CLAUDE.md`·`skills/`에 흩어진 참조가 전부 어긋난다.
  - 반영: `AGENTS.md` §0-1 조건부 로드 표 +1행, `harness-doctor.sh` 검사 2 목록 +`record.md`(6KB 예산), 참조 4곳(`CLAUDE.md`·`done.md`·`GEMINI.md`·`walkthrough.md` 머리말) 갱신. doctor 95개 항목 통과.
- **`done.md` 기획 체크리스트 신설**: 기존엔 Gemini용 한 덩어리였는데, 기획(Opus)과 문서화·검증(Gemini)은 완료 기준이 달라 분리했다.
