### 3.1 테스트 → `00-15_회귀_테스트_도입_검토서` (08-18)

> 고치기 귀찮아지면 지우거나 무시하게 되며, 그 순간부터 '빨간 테스트가 정상'이 됩니다.

② 발번 규칙 ③ 정책 계산**. **04·05·06·07 데이터 모델은 `Deceased` 확정 전까지 금지**입니다.

🔵 **판단**: Gemini의 "커버리지부터 올리자"는 `00-15` §4.1·§5.3-2(*"커버리지 목표를 세우지

## 6. 🟡 C군 — 정말 새로운 지적 (여기만 남습니다)

A군은 결론이 있고 B군은 틀렸으니, **실제로 논의할 것은 이 셋입니다.**

### C-1. 🔴 API 클라이언트·토큰 접근 파편화 — **가장 값있는 지적**

```
fetch(  51곳 / 23파일        ← 공통 래퍼 없음
sessionStorage|localStorage  67곳 / 18파일  ← 토큰 키가 컴포넌트에 하드코딩
src/ 아래 api·client·store 디렉터리  없음   (hooks/는 useProfileContact.ts 1개뿐)
```

**왜 이게 A군의 것들보다 값있나** — 나머지는 "코드가 지저분하다"지만 이건 **보안 경계에 닿습니다.**

- **`00-04`의 토큰 종류가 4종(`aud`)** 입니다. 그 4종이 **18개 파일에 문자열로 흩어져** 있습니다.
- 토큰 만료·회전 정책을 바꾸면 **18곳을 다 찾아 고쳐야** 하고, **한 곳을 빠뜨려도 타입 검사에
  안 걸립니다.** `tsc --noEmit`은 문자열 키를 못 봅니다.
- `00-15` §5.1이 **최우선 테스트 대상으로 꼽은 것이 바로 권한 경계**입니다. 그런데 **테스트를
  붙일 표면 자체가 없습니다** — 검증할 함수가 없고 컴포넌트마다 인라인 `fetch`뿐입니다.

> 🟡 **그래서 C-1은 테스트의 대안이 아니라 전제입니다.** `src/lib/api.ts` 하나로 토큰 부착·401
> 처리·베이스 URL을 모으면, **`00-15` §5.1-1이 테스트할 수 있는 대상이 처음으로 생깁니다.**
> 🔵 라이브러리 도입(axios·TanStack Query)은 **불필요**합니다 — `fetch` 래퍼 함수 하나면
> 됩니다. 의존성 4개짜리 프론트에 두 개를 더 얹을 이유가 지금은 없습니다.

### C-2. 🟡 암호화 키 로테이션 마이그레이션 도구 부재

키 분리는 돼 있으나(§4.1), **키가 유출되면 복구 경로가 없습니다.** DB에 이미 들어간 암호문을
**옛 키로 풀어 새 키로 다시 넣는 스크립트**가 없습니다.

- 🔴 **그런데 이 스크립트를 짜는 것 자체가 `db-safety.md` 대상**입니다 — 기존 행 전량
  `updateMany`. **DB 유실 2회(08-05·08-27)** 를 낸 프로젝트에서 **가장 위험한 종류의 스크립트**입니다.
- 🟡 **KMS·Vault 도입은 과합니다**(Gemini 제안). `00-11` §3.3이 확인한 팀 여건은 전담 인프라·보안
  인력 0명입니다. **필요한 건 키 관리 제품이 아니라 "봉투 암호화 + 행별 키 버전 컬럼"** 입니다 —
  스키마에 `keyVersion` 한 칸을 두면 **전량 재암호화 없이 점진 전환**이 됩니다.
- 🔵 **오픈 전에 결정해야 하는 이유**: 데이터가 쌓인 뒤에는 스키마를 바꾸는 것 자체가 위험 작업이
  됩니다. **지금은 행이 적어서 싸고, 나중엔 비쌉니다.**

### C-3. 🟡 컴포넌트 분리 기준선 부재

`260731.md`에 **"인라인 모달이 100줄을 초과하면 독립 컴포넌트로 분리"** 라는 원칙이 있는데

- 🟡 다만 **`EndingNotePage`를 지금 쪼개는 것은 권하지 않습니다.** `00-15` §4.1과 같은 논리 —
