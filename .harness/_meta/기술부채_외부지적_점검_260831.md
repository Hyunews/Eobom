### 3.1 테스트 → `00-15_회귀_테스트_도입_검토서` (08-18)

Gemini의 로드맵 **1단계 = "테스트 코드 작성"** 인데, `00-15`는 **정반대에 가까운 결론**을 냈습니다.

> `00-15` §4.1 — *"아직 굳지 않은 것에 테스트를 붙이면 테스트가 부채가 됩니다. (…)
> 고치기 귀찮아지면 지우거나 무시하게 되며, 그 순간부터 '빨간 테스트가 정상'이 됩니다.

`00-15` §5.1의 권고는 **"안 바뀌는 것부터"** 이고 대상은 딱 셋 — **① 권한 경계(4종 `aud` 토큰)
② 발번 규칙 ③ 정책 계산**. **04·05·06·07 데이터 모델은 `Deceased` 확정 전까지 금지**입니다.

🔵 **판단**: Gemini의 "커버리지부터 올리자"는 `00-15` §4.1·§5.3-2(*"커버리지 목표를 세우지
않는다"*)와 정면으로 어긋납니다. **`00-15`를 유지합니다.** 다만 —

- 🔴 **`00-15` §6 ①(0단계: 검증 스크립트 보존)이 아직 답을 못 받았습니다.** 비용 0인데

### C-1. 🔴 API 클라이언트·토큰 접근 파편화

#### C-1-1. 왜 일어났는가 — **개인의 실수가 아니라 하네스의 사각지대**

원인을 셋으로 봤고, **세 번째가 진짜 몸통**입니다.

**① 반응형 대응이었고, 그 자리에서만 고쳤습니다.**

> `260811.md` — *"`AdminPage.tsx`·`BizDashboard.tsx`에 401 감지 시 자동 로그아웃하는
> `authFetch` 래퍼 추가(**액세스 토큰 2h 만료 후 방치되던 버그 수정**)."*

**버그 리포트가 두 화면에서 올라와서 두 화면만 고쳤습니다.** 같은 버그가 나머지 19곳에도
있다는 판단은 그때 하지 않았습니다. `BizDashboard.tsx:61` 주석이 *"`AdminPage.tsx`의
authFetch와 동일 원칙"* 이라고 **복제를 스스로 인정**하면서도 공통화로 가지 않았습니다.

**② 상수를 둘 자리는 있었지만 동작을 둘 자리가 없었습니다.**

`config.ts`는 이미 있고 **`formatPhoneForDisplay`·`providerLabel` 같은 공통 함수까지 들어
있습니다** — 즉 *"공통으로 빼자"* 는 감각 자체는 이 프로젝트에 있습니다. 그런데 `config.ts`는
**값(상수)의 집이지 요청 파이프라인의 집이 아닙니다.** `src/lib/`·`src/api/`가 없어서
**갈 곳이 없는 코드는 부르는 자리에 그대로 남았습니다.**

**③ 🔴 어느 기획 문서도 이걸 소유하지 않습니다 — 이게 진짜 원인입니다.**

`docs/`를 전수 검색했습니다. **`authFetch`·API 클라이언트·프론트 공통 레이어를 규정한 문서가
없습니다.** 일지(`260811.md`)에 사후 기록만 있습니다.

우리 협업 구조는 **`docs/` 확정 스펙 → Sonnet 구현**이고, `roles.md` §2는 Sonnet에게
*"스펙을 재해석하지 말고 그대로 신뢰하라"* 고 합니다. **좋은 규칙인데, 여기서 역효과가 납니다:**

> **스펙에 없는 것은 만들어지지 않습니다.** 그리고 `docs/`는 **도메인별로 쪼개져 있습니다**
> (01 장사시설 · 02 전문가 · 06 엔딩노트 · 07 상중행정 …). **횡단 관심사(cross-cutting)는
> 어느 도메인에도 속하지 않으므로 주인이 없습니다.** 주인이 없으니 스펙이 없고, 스펙이 없으니
> 각 화면이 자기 자리에서 `fetch`를 직접 씁니다. **51번 반복된 이유가 이것입니다.**

### C-2. 🔴 `keyVersion`만으로는 **부족합니다** — 재검토 결과 처음 권고를 정정합니다

*"`keyVersion`만 하면 상용화 후 고칠 게 없을지 재검토"* 지시에 따라 `crypto.ts`와 스키마를
전부 읽었습니다. **결론: 부족합니다. 특이점 6개가 나왔고, 그중 2개는 `keyVersion`이
구조적으로 못 푸는 종류입니다.**

#### 🔴 특이점 1 — 결정적 해시(`hashField`)는 `keyVersion`으로 안 됩니다 **(가장 큼)**

`crypto.ts`에는 암호화(`encryptField`) 말고 **`hashField`(HMAC-SHA256)** 가 있습니다.
암호문은 IV가 매번 랜덤이라 중복검사가 불가능해서, **검색·중복방지용 결정적 해시**를 따로 둡니다.

```prisma
model FamilyDesignation {
  phoneEnc   String   // AES-256-GCM 암호문
  phoneHash  String   // 중복 지정 방지용 인덱스
  @@unique([userId, phoneHash])   // 🔴 같은 사람을 두 번 지정하지 못하게
}
```

**키가 바뀌면 같은 전화번호의 해시가 달라집니다.** 그러면:

- 옛 행은 v1 해시, 새 행은 v2 해시 → **같은 사람인데 유니크 제약에 안 걸립니다.**
- 🔴 **에러가 나지 않습니다. 그냥 중복 지정이 조용히 통과합니다.** 불변식이 소리 없이 죽습니다.
- **암호문은 섞여 있어도 각자 열리지만, 해시는 섞이면 안 됩니다** — 유니크 제약은 값 하나만 봅니다.
  즉 **암호문은 점진 전환이 되고 해시는 원자적 전환이어야 합니다. 성격이 다릅니다.**

#### 🔴 특이점 2 — 정산 키를 돌리면 **가족지정 기능이 깨집니다** (도메인 결합)

`hashField`가 **`SETTLEMENT_ENCRYPTION_KEY`에서 파생**됩니다. 주석이 사유를 밝힙니다 —
*"새 환경변수를 추가하지 않으면서 (…) 암호화 키와 인덱스 키를 갈라놓기 위함."*

**환경변수를 안 늘리려던 절약이 도메인 결합을 만들었습니다:**

> **01(정산 계좌) 키를 교체하면 → 00-27(가족 지정)의 `@@unique`가 무효화됩니다.**
> 전혀 다른 두 도메인이 **env var 한 개로 묶여** 있고, 코드 어디에도 그 사실이 안 적혀 있습니다.

🟡 **해시 전용 env var(`HASH_INDEX_KEY`)로 분리해야 합니다.** 그래야 정산 키를 **가족지정을
건드리지 않고** 돌릴 수 있습니다. 지금 분리하면 비용은 재해시 1회뿐입니다.

#### 🔵 특이점 3 — `keyVersion` **컬럼**보다 **버전 프리픽스**가 맞습니다 *(처음 권고 정정)*

제가 §6 초판에 *"`keyVersion` 컬럼 하나"* 라고 썼는데 **저장 형식을 보고 나니 틀렸습니다.**

```
지금:  base64(iv) : base64(authTag) : base64(ciphertext)
권고:  v2 : base64(iv) : base64(authTag) : base64(ciphertext)      ← 앞에 한 토막
```

**프리픽스가 컬럼보다 나은 이유 셋:**

| | 컬럼 방식 | 프리픽스 방식 |
| :--- | :--- | :--- |
| 스키마 변경 | 🔴 **필요** → 마이그레이션 = `db-safety.md` 대상 | ✅ **불필요** |
| 한 행에 암호 필드가 여럿일 때 | 🔴 **불가** — `FamilyDesignation`은 `phoneEnc`+`emailEnc` 2개인데 컬럼 하나로는 따로 못 굴림 | ✅ 필드별 독립 전환 |
| 복호화 | 컬럼을 같이 읽어야 함 | ✅ **문자열만 보고 스스로 판단** |

🔵 **DB 유실 2회를 낸 프로젝트에서 "스키마 변경이 필요 없다"는 것만으로도 프리픽스가 이깁니다.**

#### 🔴 특이점 4 — 스키마 주석이 **틀려 있습니다** (지금 당장 고칠 것, 비용 0)

```prisma
model FarewellMessage {
  bodyEnc String  // 🔴 AES-256-GCM 암호문(utils/crypto.ts encryptField)   ← ❌ 틀림
}
```

**실제 코드는 `encryptNoteField`(= `ENDING_NOTE_ENCRYPTION_KEY`)를 씁니다**
(`farewellMessageController.ts:149·191`). 08-27에 06 전용 키로 바꾸면서 **주석만 안 고쳤습니다.**

> 🔴 **로테이션 스크립트를 이 주석 보고 짜면 정산 키로 복호화를 시도합니다.**
> AES-GCM은 authTag가 안 맞으면 예외를 던지니 **조용한 파손은 아니지만**, 전량 작업 도중에
> 터지면 **어디까지 처리됐는지 모르는 채로 멈춥니다.** 유실 2회 프로젝트에서 가장 나쁜 상태입니다.

#### 🟡 특이점 5 — 옛 키를 버리면 **과거 백업이 복원 불가능**해집니다

백업 dump에는 **옛 키로 잠긴 암호문**이 들어 있습니다. 로테이션 후 옛 키를 폐기하면
**그 백업은 영구히 못 엽니다.**

- 🔴 그런데 **키가 유출돼서 돌리는 경우, 옛 키를 보관하는 것은 유출 대응으로서 의미가 반감**됩니다.
- 🟡 **이건 기술로 못 푸는 트레이드오프**라 정책으로 정해야 합니다 — *"옛 키는 백업 보존기간
  (`00-20`)만큼만 보관하고 그 후 폐기"* 가 현실적입니다. **문서에 안 적으면 사고 납니다.**

#### 🟡 특이점 6 — 키 강도가 **운영자 입력에 종속**됩니다

```ts
return crypto.createHash('sha256').update(raw).digest();   // 임의 길이 문자열 허용
```

주석은 *"운영자가 임의 길이 문자열을 넣어도 안전하도록"* 이라 했지만, **sha256은 길이를
맞춰줄 뿐 엔트로피를 만들지 못합니다.** `raw`가 `eobom1234`면 sha256해도 약합니다.
🟡 상용화 시 **32바이트 랜덤 강제 + 부팅 시 검증**이 필요합니다(약한 키면 서버가 안 뜨게).

#### 🔵 C-2 결론 — 필요한 것은 3층입니다

| 층 | 대상 | 방식 | 전환 성격 |
| :---: | :--- | :--- | :--- |
| **1** | 암호문(`*Enc` 5종) | **버전 프리픽스**(특이점 3) | ✅ 점진 — 섞여 있어도 됨 |
| **2** | 결정적 해시(`phoneHash`) | **전용 키 분리**(특이점 2) + 재해시 | 🔴 **원자적** — 섞이면 불변식이 깨짐 |
| **3** | 옛 키 보관 정책 | 문서(특이점 5) | 정책 |

> 🔴 **"`keyVersion` 하나면 된다"는 제 처음 권고는 1층만 본 것이었습니다.**
> 2층을 빼먹으면 **상용화 후에 반드시 다시 손대야 하고, 그때는 데이터가 쌓여 있습니다.**
> ✅ 반면 **특이점 4(주석 수정)는 지금 당장, 비용 0**입니다.
