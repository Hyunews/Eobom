# roles.md — 역할 분담과 검증 게이트

> **언제 읽나**: 에이전트를 전환할 때 / "이거 누가 쓰는 거지?"가 헷갈릴 때 / 상대 작업물을 검토해야 하나 고민될 때
>
> 이 문서가 존재하는 이유: 같은 것을 두 번 검증하던 낭비를 없애기 위해.

## 0. 3주체와 태그 (2026-08-10 전환)

| 태그 | 담당 | 전환 방법 |
|---|---|---|
| `[Claude:Opus]` | 기획·설계 `docs/` | CLI `/model opus` |
| `[Claude:Sonnet]` | 개발·구현 `eobom/` | CLI `/model sonnet` |
| `[Gemini]` | 기계적 문서화 `reports/` + 교차검증 | Antigravity 창 |
| `[사용자]` | 계정·대시보드·승인 | — |

Opus/Sonnet은 같은 CLI·권한이라 소유권으로 못 나눈다 — §1 표에선 `Claude` 한 주체, 구분은 태그로만.
Gemini에겐 **기계적 문서화와 판정만** 준다. 자기가 안 한 일을 옮겨 적으면 전언 오류가 난다(2026-08-07 실제 2건).

## 1. 소유권 표

원칙은 **"한 파일 한 주인"**이다. 공유가 필요한 곳은 소유자를 두지 않고 **덧붙이기 전용 + 에이전트 태그**로 충돌을 없앤다.

### 1-1. 산출물 영역 (단독 소유)

| 영역 | 쓰기 | 읽기 | 비고 |
|---|---|---|---|
| `docs/` (기획 SSOT) | **Claude**(Opus 모드) | Gemini | 도메인 명세·API/DB 스펙 |
| `reports/` (HTML·PDF) | **Gemini** | Claude | `docs/` 정본의 시각화본. 🔴 **2026-08-20부터 git 커밋 제외**(로컬 전용) — 아래 |
| `eobom/frontend`, `eobom/backend` | **Claude** | Gemini | 실제 소스코드 |
| `.harness/` (규칙·메모리·툴) | **Claude** | Gemini | 하네스 유지보수 |
| `assets/` (원천 데이터·로고) | **사람** | 둘 다 | 에이전트가 임의 추가 금지 |

> ## 🔴 `reports/`는 커밋하지 않는다 (2026-08-20 결정)
>
> `docs/` 마크다운에서 **재생성되는 파생물**이라 저장소에 둘 이유가 없다(당시 64개·5.3MB로
> 저장소의 절반). `.gitignore`에 등록했고 `git rm -r --cached reports`로 추적을 끊었다.
> **파일은 로컬 디스크에 그대로 있고 Gemini가 언제든 다시 만든다.**
>
> **커밋 여부의 기준은 "혼자냐 팀이냐"가 아니라 "재생성 가능한가"다.**
> 없으면 재구성 불가한 것(소스·마이그레이션·`docs/` 결정 기록)은 커밋하고,
> 다른 것에서 자동 생성되는 것(빌드 산출물·`reports/`)은 제외한다.
>
> ⚠️ **`reports/`에만 있고 `docs/` 정본이 없는 문서를 만들지 말 것**(§1-2 역방향).
> 2026-08-20에 `00-24`가 그 상태였고 `docs/00_핵심플랫폼/00-24_프론트엔드_UIUX_개선_제안서.md`로
> 정본화해 해소했다. **정본 없는 시각화본은 커밋에서 빠지는 순간 소실된다.**

### 1-2. 기록 영역 `docs/작업일지_및_기록/` (파일 단위로 나눔)

기록은 양쪽 다 남겨야 하므로 폴더 통째로 한쪽에 주지 않는다.

| 파일 | 쓰기 | 규칙 |
|---|---|---|
| `에이전트_기록/claude_tasks.md` | **Claude** | 본인 날것 로그. 상대는 읽기만. |
| `에이전트_기록/gemini_tasks.md` | **Gemini** | 본인 날것 로그. 상대는 읽기만. |
| `에이전트_기록/walkthrough.md` | **Claude**(항목) + **Gemini**(판정) | Gemini는 항목 **아래 판정 1줄만** 덧붙인다. 남의 항목 본문은 안 고친다. |
| `YYMMDD.md` (일별 일지) | **둘 다** | 덧붙이기 전용. 줄 앞에 §0 태그. 남이 쓴 줄은 수정·삭제 금지. |
| `에이전트_기록/history.md` | 아카이브 | 손대지 않는다. |
| `.harness/memory/context.md` | **마지막 작업자** | 세션 끝낼 때 갱신 |

> 충돌이 안 나는 이유: 각자 자기 파일에 쓰거나(1:1), 덧붙이기만 하기 때문. 같은 줄을 둘이 고칠 일이 구조적으로 없다.

### 상대 영역을 건드려야 할 때
직접 고치지 않는다. §2-1 편차 보고 절차를 따른다.

## 2. 파이프라인과 단일 검증 게이트

```
  [Claude:Opus]    docs/ 기획·스펙 확정
      │
      │  ← Sonnet은 여기서 스펙을 재해석·재검토하지 않는다.
      │     이해 안 되는 부분만 질문하고, 나머지는 그대로 신뢰하고 구현한다.
      ▼
  [Claude:Sonnet]  eobom/ 구현 + 빌드/테스트
      │     완료 후 walkthrough.md에 요약 1건 추가 (편차 필드 포함)
      ▼
  ★ 검증 게이트 (딱 여기 한 번)
  [Gemini]  walkthrough.md만 읽고 스펙 대조 → 3가지 중 하나
      │
      ├─ 통과      → 종료. 다시 확인하지 않는다.
      ├─ 반려      → 사유 1줄. Claude가 수정 후 재제출.
      └─ 스펙갱신 필요 → 현실이 맞고 기획이 틀렸다. Gemini는 판정만 남기고,
                        docs/ 수정은 [Claude:Opus]가 한다(Gemini는 docs/ 쓰기 권한 없음).
```

**게이트는 `walkthrough.md` 한 곳뿐이다.** Gemini는 **리뷰하지 않되(품질 판단은 Claude의 빌드/테스트 책임),
보고된 사실이 실제인지는 검증한다** — 제거·추가했다는 문자열을 직접 검색해 재현하고, "빌드 통과"
주장을 실제로 돌려보고, 선언되지 않은 변경을 찾는다. **절차·반려 기준·개정 경위는 `GEMINI.md` "검증 범위"가 정본**(2026-08-14 개정).

## 2-1. 편차(Drift) — 구현이 기획과 틀어질 때

가장 자주 일어나고, **여기서 문서가 썩는다.** (실제 사례: 카카오 API 45건 캡, 위치정보법상 GPS 트랙 사용 불가)

**Sonnet이 편차를 발견하면** — 아래 3가지를 하지 않는다:
- ❌ 조용히 다르게 구현 → 문서가 거짓말이 되고 다음 세션이 잘못된 전제로 쌓는다
- ❌ 구현 중에 `docs/`를 직접 수정 → 기획 판단은 Opus 몫. 같은 CLI라 **쓸 수는 있지만 쓰지 않는다**
- ❌ 멈추고 대기 → 사람이 창을 전환할 때까지 진행이 막힌다

✅ 대신: **동작하는 쪽으로 구현 + `walkthrough.md`의 `편차` 필드에 기록.** 판정은 Gemini가 게이트에서, 스펙 수정은 Opus가.

**진행 자체가 막히는 급한 편차**는 `context.md`에 올린다:
```
▶ 다음 할 일
[Claude:Opus] 확인요청: docs/01_장사시설_매칭/01-01 — 예약 API 응답에 전화번호
필드가 없어 직통전화 UX 구현 불가. 스펙 보완 필요. (Sonnet 대기 중)
```

`docs/`를 고쳤으면 **왜 고쳤는지 한 줄**을 남긴다. 이유 없는 스펙 변경은 다음 사람이 되돌린다.

## 4. 에스컬레이션 — 혼자 결정하지 않는 것

**호칭(08-14 정정)**: CLI 앞의 사용자 = **개발자**. `대표님`=`사장님`은 **이 자리에 없는 별도
결정권자**다(옛 기록의 "대표 지시"는 대부분 개발자 지시 — 새로 쓸 때 섞지 않는다).
**설계·UX·데이터모델은 개발자 확정**이라 묻지 않는다. `대표 사진`·`대표자명`은 필드명이라 그대로.

아래(돈·사람·외부계약·법적리스크)만 사장님에게 묻고, 나머지는 알아서 진행한다.

- 되돌리기 어려운 것: 파일 대량 삭제·이동, `git commit`/`push`, 배포, 외부 발행
- 돈이 드는 것: 유료 API 연동, 인프라 증설
- 법·규제: 개인정보 수집 범위 변경, 위치정보 사업자 신고 (→ `security.md`)
- 스펙과 구현이 충돌하는데 어느 쪽이 맞는지 판단이 안 설 때

## 5. 사람(사용자)의 역할

모드·창 전환(`/model opus|sonnet`, Antigravity ↔ Claude CLI), `assets/` 데이터 투입, §4 승인.
전환 시 할 일은 **§6 블록을 복사해 붙여넣기**뿐이어야 한다 — 그 이상을 매번 확인해야 한다면 하네스가 실패한 것이니 고칠 것.

## 6. 핸드오프 안내 (턴을 넘길 때 반드시)

다음 차례로 넘어가면 **응답 맨 마지막에** 아래 블록을 출력한다. 사용자가 "이제 뭐라고 하지?"를 고민하지 않고 그대로 복사할 수 있어야 한다.

```
──────────────────────────────
▶ 다음: <Claude:Opus(/model opus) | Claude:Sonnet(/model sonnet) | Gemini(Antigravity)>
아래를 복사해서 붙여넣으세요:

<상대에게 줄 프롬프트 1~3줄>
──────────────────────────────
```

**작성 규칙**
- 상대가 **바로 착수할 수 있게** 구체적으로. "확인해줘"(❌) → "게이트 확인 — walkthrough.md 유품정리 항목의 편차 판단 필요"(✅)
- `context.md`의 "다음 할 일"과 **같은 내용**이어야 한다. 블록은 말로 옮긴 것일 뿐, 정본은 `context.md`.
- 사용자 승인이 필요한 항목(§4)이 있으면 블록 **위에** 따로 묻는다. 블록 안에 섞지 않는다.
- 아직 자기 차례가 안 끝났으면 출력하지 않는다.
- **모드 전환도 핸드오프다.** 기획→구현으로 넘어갈 때 `/model` 안내를 빠뜨리면 사용자가 Opus로 코딩하게 된다.
