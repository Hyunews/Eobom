# db-safety.md — 🔴 DB 쓰기 게이트 (유일 정본)

> **언제 읽나**: **DB에 쓰는 명령을 돌리기 직전.** 스키마 변경만이 아니다 — §1의 표에 하나라도
> 걸리면 이 문서를 연다.
>
> 2026-08-27 `security.md` §6에서 분리(경위 → `_meta/db-safety_게이트_신설.md`).
> 데이터 유실은 이 프로젝트에서 **가장 비싼 사고 유형**이고, 이미 **2회** 났다.

---

## 1. 언제 발동하나 — **스키마 변경만이 아니다**

**DB의 기존 행을 지우거나 덮어쓸 수 있는 것이면 전부다.**

| 종류 | 예 |
|---|---|
| 마이그레이션 | `prisma migrate dev` / `migrate reset` / `db push` |
| 삭제·일괄수정 | 🔴 **`deleteMany`** · **`updateMany`** · `truncate` · raw `DELETE`/`UPDATE` |
| **정리 스크립트** | 🔴 **검증 끝나고 "테스트 데이터 치우기" — 08-27 사고가 정확히 여기서 났다** |
| 시드 재적재 | `seed` 재실행(기존 행을 덮는다) |

> **한 문장 판정**: *"이 명령이 내 의도보다 한 줄 더 지워도 되돌릴 수 있나?"*
> **아니면 백업이 먼저다.** 애매하면 백업하는 쪽이 항상 싸다 — **백업은 30초, 복구는 불가능**이다.

## 2. 순서 — 건너뛰지 않는다

0. 🔴 **사람에게 먼저 묻는다**(`AGENTS.md` §1) — **무엇을 몇 건 지우는지** 말하고 승인받는다.
1. 🔴 **어느 DB를 건드리는지 정한다** — 대상이 다르면 명령이 다르다.

| 대상 | 명령 |
|---|---|
| **로컬**(기본 개발 환경 — Docker `eobom-postgres`, **5433**) | `powershell -File .harness/tools/backup-db.ps1 -Target local` → `backups/local-*.dump` |
| **운영**(Supabase) | `powershell -File .harness/tools/backup-db.ps1 -Target prod` → `backups/prod-*.dump` |

> 🔴 **`-Target`은 필수이고 기본값이 없다**(09-30, TS-002) — 없거나 `local`/`prod`가 아니면 사용법을 찍고
> 실패한다. 예전엔 스크립트가 `.env`로 대상을 스스로 골라 로컬 작업 중 운영을 떴다. **유실 2건은
> 둘 다 로컬**이었다(§7) — 지금 쓸 DB와 **같은 `-Target`을 골랐는지**가 사람의 몫이다.
> `-Target prod`는 `BACKUP_DATABASE_URL`만 읽고(없으면 `DIRECT_URL`로 폴백하지 않고 실패) 로컬 주소면 거부한다.
> 끝에 대상·경로·크기를 크게 찍는다 — 파일명의 `local-`/`prod-` 접두사와 함께 확인할 것.
> ⚠️ 포트 **5432**는 다른 프로젝트다. 이어봄은 **5433**.

2. 🔴 **파일이 생겼는지 확인한다.** 실패 시 0바이트를 **지우고** `exit 1` 한다 — *"돌렸다"* 가
   아니라 **파일이 있다**가 통과 조건. **없는 백업을 있다고 믿는 것이 더 위험하다.**
3. 그 다음에 쓰기를 실행한다.

> 운영 접속 함정(pooler·유저명·버전)은 **`systems.md` §4**.

### 2-1. 🔴 운영 스키마 변경은 **push와 분리한다** (2026-09-30 사람 결정)

**경위**: `backend/package.json`의 `start`가 `prisma migrate deploy && node dist/server.js`였다 —
**push → Render 재시작 → 운영 DB에 미적용 마이그레이션 자동 적용.** 09-30에 테이블 2개 삭제
(`drop_digital_cleanup_models`)가 이 경로로 **백업 없이** 운영에 들어갔다(직전 백업은 1시간 반 전).
결정된 삭제라 결과는 괜찮았지만, **위 §2 순서가 push 한 번에 통째로 건너뛰어진다**는 것이 확인됐다.
→ `start`에서 `migrate deploy`를 뺀다. **운영 마이그레이션은 사람이 직접, 아래 순서로만.**

> ✅ **사람이 칠 명령은 하나다**(09-30): `powershell -File .harness/tools/migrate-prod.ps1`
> — 운영 백업(실패하면 멈춤) → 대기 목록 표시 → `prod` 입력 확인 → `migrate deploy` → 결과. 에이전트는 실행하지 않고 **이 명령과 아래 순서만 안내**한다.

| 마이그레이션 종류 | 순서 |
|---|---|
| **추가형**(테이블·컬럼 추가) | `migrate-prod.ps1` → push |
| **삭제형**(테이블·컬럼 제거·이름 변경) | push(새 코드가 더는 안 씀) → `migrate-prod.ps1` |

- 🔴 **스키마를 바꾸는 커밋을 push하기 전에 이 표부터 본다.** 잊으면 새 코드가 없는 컬럼을 찾다 에러가
  난다 — 조용한 유실보다 **시끄러운 에러가 낫다**는 것이 이 결정의 이유다.
- 운영 `migrate deploy`는 **직결 URL(`DIRECT_URL`)**이 필요하다(`render.yaml` 주석 · `systems.md` §4).
- 🟡 사람의 기억에 맡기는 단계가 하나 늘었다 — 또 빠지면 §7.1대로 **백업 없으면 안 도는 래퍼**로 간다.

### 2-2. 🔴 `.env`는 항상 로컬이다 — 운영은 정해진 통로로만 (2026-10-07 개발자 결정)

**경위**: 10-06 운영 처리 기록을 보려고 `.env`의 `DATABASE_URL`을 운영 주소로 바꿨다가 다음 날 되돌렸다.
운영 조회 통로가 없어서 생긴 일이다. 되돌리기를 한 번 잊으면 개발 서버·시드·`purge --confirm`·`migrate`가
전부 운영을 향한다. **주석을 번갈아 풀어 대상을 바꾸지 않는다.**

| 상황 | 통로 | 운영 주소 출처 |
|---|---|---|
| 운영 스키마 반영 | `migrate-prod.ps1` (§2-1) | `BACKUP_DATABASE_URL` |
| 운영 백업 | `backup-db.ps1 -Target prod` (§2) | `BACKUP_DATABASE_URL` |
| 운영 기록 조회 | `npm run report:heavy -- --target prod` (🆕 10-07, 출력 첫 줄에 대상 DB 표시) | `BACKUP_DATABASE_URL` |
| 시험 | `npm test` | `TEST_DATABASE_URL` (`_test`로 끝나는 로컬 DB만) |

- 새 스크립트가 운영을 읽거나 써야 하면 **같은 방식(`--target prod` + 대상 표시)으로 이 표에 한 줄을 더한다.**
- 표에 없는 운영 작업은 터미널 한 창에서만 `$env:DATABASE_URL`을 임시 지정한다. `.env`는 고치지 않는다.

## 3. 🔴 `where` 절이 소유자 단위면 **남의 것도 지운다**

**08-27 사고의 정확한 원인이다.**

```ts
// 🔴 "내가 방금 만든 것만" 이라고 생각했지만, 실제로는 그 사용자의 전부를 지운다
await prisma.familyDesignation.deleteMany({ where: { userId } })
```

- **내가 만든 행만 지우려면 `id`로 지운다.** 생성 시 받은 id를 들고 있다가 그것만 지운다.
- **조건이 넓으면 지우기 전에 `count`/`findMany`로 몇 건이 걸리는지 먼저 본다.**
  예상보다 많으면 그 자리에서 멈춘다.

## 4. 🔴 테스트 데이터는 **지우지 않는다 — 남긴다**

**사용자 지시**: 테스트·데모 데이터는 **발견 즉시 지우지 말고 일괄 정리 대상으로 남긴다.** 편의가 아니라 **안전 규칙이다 — 지우는 순간이 곧 사고 지점**이기 때문이다.
🔴 ***"테스트 데이터니까 다시 만들면 된다"* 는 두 번 다 틀렸다**(§7.1 ③).

## 5. 🔴 로컬 dev DB도 **예외가 아니다**

유실 2건 다 **로컬이었고 복구 불가였다.** 실기동으로만 만들 수 있는 데이터가 로컬에만 남아
있는 경우가 있다 — **두 번 다 지워진 것이 정확히 그것이다.**

## 6. 🔴 이미 지웠으면 — **숨기지 않는다**

백업 없이 돌렸고 데이터가 사라졌다면, 그 작업은 **"완료"가 아니라 사고 보고**다.

1. **무엇이 몇 건** 지워졌는지 센다(모르면 모른다고 적는다 — 추정치를 사실처럼 적지 않는다).
2. **사용자에게 즉시** 알린다 — 세션 끝이 아니라 그 자리에서.
3. `walkthrough.md`의 **`다음 에이전트가 알아야 할 것`** + `context.md`에 남긴다.

> **숨기는 것이 유실 자체보다 비싸다** — 다음 세션이 **없는 데이터를 있다고 믿고** 그 위에 쌓는다
> (`done.md` §2와 같은 원리).

## 7. 사고 2회 — **진짜 공통점이 이 문서 전체의 근거다**

**표면 원인은 다르다**(08-05 = `migrate diff`의 shadow DB 자리에 실 DB / 08-27 = `deleteMany`의
`where`가 소유자 단위). 🔴 **둘 다 "테스트 데이터 정리"가 아니다.**
사고별 상세는 `_meta/db-safety_게이트_신설.md`. **겹치는 것은 아래 셋이다.**

| # | 공통점 | |
|:---:|---|---|
| **①** | **"이 명령은 내가 지정한 것에만 작용한다"는 전제가 틀렸다** | *"shadow DB만 초기화되겠지"* / *"내가 만든 행만 지워지겠지"*. **실제 작용 범위가 믿음보다 넓었다** |
| **②** | **파괴가 목적이 아닌 작업 중에 났다** | *"지금 위험한 일을 하고 있다"* 는 자각이 없었고, 그래서 **백업도 없었다** |
| **③** | 🔴 **유실분이 둘 다 "테스트로 만든 데이터"였는데 그게 오히려 비쌌다** | 소셜 3사 연동 계정 / 실기기 가족 연결. **실기동으로만 만들 수 있어 재현 비용이 컸다** |

> 🔴 **①이 §1을 명령 단위로 잡은 이유다.** *"내가 뭘 하려는지"* 로 판단하면 **두 번 다 안전해
> 보였다.** 판단할 것은 의도가 아니라 **그 명령이 실제로 닿는 범위**다.
> 🔴 **③이 가장 반직관적이고, §4가 "지우지 말고 남긴다"인 이유다.**

### 7.1 3회차가 나면

🔴 **규칙을 더 쓰지 말 것.** `deleteMany` 사용을 막는 lint, 또는 백업 없이는 쓰기 스크립트가
안 돌게 하는 래퍼로 간다. **규칙이 세 번 실패했다면 규칙으로 풀 문제가 아니라는 뜻이다.**
