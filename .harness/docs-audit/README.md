## 2. 판정 값 (대장 `판정` 칸)

| 판정 | 뜻 | `근거` 칸에 쓸 것 |
|---|---|---|
| `유지` | 지금 사실과 맞음 · 고칠 것 없음 | 확인한 코드 경로 또는 최신 문서 § |
| `갱신` | 내용은 살리되 **지금 사실과 다름** → 고쳐야 함 | 무엇이 다른지 + 사실의 출처(코드·최신 문서) |
| `통합` | 다른 문서의 절과 **같은 내용** → 한 곳으로 합침 | `통합 → 문서ID §` (어느 쪽이 정본인지) |
| `경위` | 결정 과정·폐기된 안·정정 기록 → **문서 끝 부록으로 이동** | 무엇을 대체한 기록인지 |
| `폐기` | 더 이상 맞지 않고 경위 가치도 없음 | 폐기 이유 · 🔴 드물어야 함 — 애매하면 `경위` |
| `색인` | 목차·색인·링크 모음(내용 없음) → 자동 색인으로 대체 대상 | — |
| `묶음` | 🤖 **build가 자동으로만 채운다** — 제목 아래가 다음 제목까지 비어 있는 절(하위 절을 묶기만 함). 사람이 적지 않는다 | 자동 |

- 🔴 **결정을 기다리는 제안**(결정서의 권고안 등)은 `유지` + `메모`에 **`결정대기`** 라고 적는다. 판정 값을 따로 만들지 않는다(사람 결정 09-29). 4단계에서 태그 `status: 결정대기`로 옮긴다.
- 한 절 안에 섞여 있으면 **주된 것**을 판정하고 `메모`에 나머지를 적는다(예: `갱신` + 메모 "🔄 08-19 문단은 경위로").
- 판정 뒤에 짧은 말을 붙여도 됨: `갱신(메뉴명)`. 스크립트는 앞 단어만 본다.
- `메모`에 **태그 후보**(§5 topics)를 적어 두면 4단계에서 다시 읽지 않아도 된다.

## 3. 읽기 규칙

- 🔴 **절 단위로 전부 읽는다** — 제목만 보고 판정하지 않는다. 큰 파일은 `limit≤400`으로 나눠 읽는다(`AGENTS.md` §10 read-guard).
- 같은 파일을 두 번 읽지 않도록 **한 파일을 다 읽고 그 파일의 판정을 한 번에** 적는다.
- 다른 문서와 겹친다고 느끼면 그 문서를 바로 열지 말고 `메모`에 `겹침? → 문서ID`로 적는다 → 그 도메인 차례에 확인.

## 6. 🔴 규칙 — 세션 절차 · 판정을 헛되게 만들지 않기 (09-29 사람 지시로 규칙화)

> `AGENTS.md` §0-1 표가 이 절을 가리킨다. 5단계가 끝나면 그 줄을 지운다.

### 6-1. 판정 세션 (2단계) — 도메인 하나 = 창 하나

1. **시작**: 사람은 새 창에서 *"docs 정리 2단계 — 02 판정"* 한 줄만 말하면 된다. 에이전트는 이 README §2·§3·§6만 읽고 대장 `ledger_<도메인>.md`를 연다.
2. **읽기**: 파일 하나를 끝까지 읽고 → 그 파일의 판정을 **JSON 하나로 모아 `fill`로 한 번에** 적는다. 대장 표를 한 줄씩 Edit하지 않는다(느리고 표가 깨지기 쉽다).
   ```
   node .harness/tools/docs-ledger.js fill 02 <scratchpad>/02.json
   // { "02-01": { "16": ["갱신","근거","메모"], "30": ["유지","…",""] }, "02-02": { … } }
   ```
   - 줄 번호는 대장의 `줄` 칸 그대로. `묶음`은 적지 않는다(자동).
   - 코드 대조 grep이 15회를 넘을 것 같으면 먼저 Sonnet에게 "문서에 나온 파일·필드·줄번호가 코드에 있나" 목록 추출을 맡긴다(§4).
3. **끝**: `check <도메인>` **✅ 통과** → 이 README §1 표 상태 칸 · `context.md` 한 줄 갱신 → 사람에게 **"정하실 일"**을 쉬운 말로 따로 모아 보고(배경·선택지·추천).
4. 🔴 **모델·범위 (10-01 개발자 결정, 00-E부터)** — 판정은 **`[Claude:Sonnet]`** 이 한다(읽기·코드 대조 위주라 단가 5배인 Opus를 쓰지 않음, `AGENTS.md` §10). 대신 **판정 세션에서는 코드를 고치지 않는다** — 결정이 나서 코드가 필요하면 **핸드오프 블록으로 별도 세션에 넘긴다**(00-D에서 판정·구현을 한 흐름에 섞었다가 walkthrough 기록이 빠졌다). 되돌리기 어려운 판정(폐기·경위)은 사람 결정을 거치고, 4단계에서 Opus가 `docs/`에 반영하며 한 번 더 본다.

### 6-2. 🔴 판정이 끝난 도메인의 문서를 고칠 때 (모든 `[Claude:Opus]` 작업에 적용)

판정은 "그 시점의 문서"에 대한 것이다. 판정 뒤에 문서가 바뀌면 판정이 낡는다. 그래서:

- 대장은 판정한 때의 **문서 지문(`sha`)**을 기억한다. 문서가 바뀌면 `check`가 **🔴 판정 뒤 바뀐 문서**로 잡는다.
- 🔴 **`docs/`를 고친 작업은 끝나기 전에 `node .harness/tools/docs-ledger.js check`를 돌린다.** 🔴가 뜨면 `git diff`로 **바뀐 절만** 다시 보고 판정을 고친 뒤 `ack <도메인>`으로 기준점을 새로 찍는다.
- 제목을 바꾸거나 지운 절의 판정은 **대장 맨 아래 "⚠ 사라진 절" 표**에 남는다(버려지지 않음). 새 절로 옮겨 적고 그 줄을 지운다.
- 🔴 **4단계(실행) 전에 판정을 몰래 실행하지 않는다**(원칙 3). 다른 작업 중에 "갱신" 판정 절을 마침 고쳤다면, 그 판정의 `메모`에 `선반영 MM-DD`를 붙인다.

### 6-2-1. 🔴 빠뜨림 방지 — 판정이 끝나도 "할 일"이 사라지지 않게 (09-30 사람 우려로 신설)

대장은 **"모든 절을 봤다"**만 보장한다. **"본 것을 다 고친다"**는 아래 3가지로 지킨다.

1. **채팅에서 나온 결정은 그 자리에서 적는다** — README §4 해당 도메인 블록 + (필요하면) 문서 결정 블록 + 대장 `메모`에 `선반영 MM-DD`. 대화에만 있는 결정은 없는 것으로 본다.
2. **판정 때 확인 못 한 것은 메모에 정해진 말로 남긴다** — `미대조`(코드와 안 맞춰 봄) · `미확인`(외부 사실) · `겹침?`(다른 문서와 중복 의심). 09-30 이전 판정은 `확인 필요`·`확인필요`·`모름`으로도 적혀 있다 — 🔴 **3단계 시작 때 대장 `메모`·`근거` 칸을 정규식 `미대조|미확인|겹침\?|확인 ?필요|모름`으로 전 대장에서 검색해 목록을 만들고, 0건이 될 때까지 4단계에 들어가지 않는다.**
3. **3단계 `plan.md`는 대장에서 기계적으로 뽑는다** — `유지`·`묶음`이 아닌 판정 전부 + 메모에 🔴가 있는 `유지` 전부. 손으로 골라 담지 않는다(고르는 순간 빠진다). 4단계는 도메인마다 `plan.md` 줄을 하나씩 지우고, **남은 줄 0**이 끝의 기준.
