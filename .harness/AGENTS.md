# AGENTS.md — 이어봄 하네스 행동 규칙 SSOT

> 이 파일이 유일한 행동 규칙 본문이다. `CLAUDE.md`(코딩) / `GEMINI.md`(기획)는 각자의 역할만 덧붙이는 얇은 파일이며, 규칙이 충돌하면 **이 문서가 이긴다**.
>
> 대상: **1인 + 3주체** — `[Claude:Opus]` 기획·설계 / `[Claude:Sonnet]` 개발·구현 / `[Gemini]` Flash, 기계적 문서화·교차검증. 사람이 `/model`과 창을 직접 전환하며 쓴다. 에이전트가 다른 에이전트를 자동 호출하지 않는다. (태그·전환 방법 → `roles.md` §0)

---

## 0. 부팅 — 매 세션 반드시 읽는 것 (이 2개가 전부)

| 순서 | 파일 | 무엇을 얻나 |
|---|---|---|
| 1 | `.harness/memory/context.md` | **"다음 할 일" 한 줄** + 지금 상태. 맨 위 3줄만 봐도 바로 작업 시작 가능해야 한다. |
| 2 | `.harness/memory/pending-approvals.md` | **사람 승인 대기 목록. 여기 있는 건 착수 금지.** `context.md`를 통째로 새로 써도 이 파일은 별도라 안 지워진다 — 그게 존재 이유. |
| 3 | `.harness/AGENTS.md` (이 파일) | 행동 규칙 + 아래 조건부 로드 표 |

**부팅 파일 합계 11KB를 넘기지 않는다.** 넘으면 `tools/harness-doctor.sh`가 실패시킨다 — 부팅이 무거워지면 매 세션 비용이 되기 때문.
`pending-approvals.md`는 사람만 항목을 지운다(승인/반려 의사를 밝혔을 때). 에이전트가 스스로 판단해서 지우지 않는다.

## 0-1. 조건부 로드 — 해당 작업일 때만 읽는다

| 작업 유형 | 읽을 파일 |
|---|---|
| 에이전트 전환 / 누가 뭘 쓰는지 헷갈릴 때 | `.harness/roles.md` |
| 개인정보·시크릿·외부 발행(배포/공개) 건드릴 때 | `.harness/security.md` |
| 작업을 "끝났다"고 선언하기 직전 | `.harness/done.md` |
| `walkthrough.md`·일지에 기록을 남길 때 | `.harness/record.md` |
| 외부 연동(OAuth·지도·공공데이터·DB·배포) 건드릴 때 | `.harness/systems.md` |
| 반복 작업(2회차 이상)일 때 | `.harness/skills/` |
| 과거 결정 이유가 궁금할 때 | `.harness/memory/MEMORY.md` → 해당 메모리 |

> 위 표에 없으면 읽지 않는다. "혹시 몰라서 다 읽기"가 컨텍스트를 태우는 주범이다.

---

## 1. 작업 순서

```
PLAN → CONFIRM → CODE/WRITE → SAVE → UPDATE
```

- **CONFIRM**: 되돌리기 어려운 작업(파일 삭제·대량 이동·커밋·배포·외부 발행)은 실행 전 사용자 확인. 그 외 일반 작업은 확인 없이 진행한다.
- **UPDATE**: `memory/context.md`의 "다음 할 일" 갱신. 반복 작업이었으면 `skills/`에 절차 남기기.
- **핸드오프**: 상대 에이전트 차례로 넘어가면 응답 맨 끝에 **복사용 프롬프트 블록**을 출력한다(→ `roles.md` §6). 사용자가 무슨 말을 해야 할지 고민하게 두지 않는다.

## 2. 소유권 — 한 파일은 한 에이전트만 쓴다

**중복 검증을 없애는 핵심 규칙.** 상대가 확정한 것은 다시 검토하지 않고 신뢰한다.

| 영역 | 쓰기 | 읽기 |
|---|---|---|
| `docs/` (기획 SSOT) | Claude(Opus 모드) | Gemini |
| `reports/` (시각화 HTML) | Gemini | Claude |
| `eobom/`, `.harness/` | Claude | Gemini |
| `assets/` | 사람 | 둘 다 |
| `docs/작업일지_및_기록/` | **파일별로 나뉨** → `roles.md` §1-2 | |

기록 폴더는 양쪽 다 써야 하므로 통째로 한쪽에 주지 않는다. 각자 자기 로그(`claude_tasks.md` / `gemini_tasks.md`)를 쓰고, 일지는 덧붙이기 전용으로 공유한다.

검증 게이트는 **`walkthrough.md` 단 한 곳**이며 결과는 통과 / 반려 / 스펙갱신 3가지다.
구현이 기획과 틀어지는 **편차 처리 절차는 `roles.md` §2-1** — 조용히 다르게 구현하거나 `docs/`를 직접 고치지 않는다.

## 3. 재사용 절차 (`skills/`)

- 같은 작업을 **두 번째로** 하게 되면 `skills/<name>.md`로 남긴다. 컨벤션은 `skills/README.md`.
- 처음부터 만들지 않는다 — 반복이 확인돼야 재사용 가치가 있다.

## 4. 구조화된 메모리 (`memory/`)

- `context.md`에 다 우겨넣지 않는다. 타입별로 나눈다: `user` / `feedback` / `project` / `reference`.
- 파일 하나당 사실 하나, `memory/MEMORY.md`에 한 줄 인덱스.
- **코드·git 히스토리·이미 문서화된 것은 메모리로 안 남긴다** — 중복이다.

## 5. 문서 ↔ 코드 링크 (G-Brain)

- 링크는 **파일/모듈 단위로만**. 함수 단위 금지 — 코드가 바뀌는데 링크가 안 따라가면 링크가 거짓말이 된다.
- 자주 안 바뀌는 안정적 앵커에만 건다. 남발 금지.
- 자세한 원칙은 `memory/g-brain-map.md`.

## 6. 검색·정보 품질

- 라이브러리 버전/API 스펙처럼 빨리 바뀌는 정보는 "확인 필요" 또는 컷오프 기준을 명시하고 단정하지 않는다.
- 공식 문서 우선, 커뮤니티 글은 교차검증 후 보조로만.

## 7. 산출물 저장 위치 (Dual Document Policy)

| 종류 | 위치 | 형식 |
|---|---|---|
| AI가 읽고 고치는 기획 본문 | `docs/` (도메인별 한글 디렉토리) | Markdown |
| 사람이 브라우저로 보는 보고서 | `reports/` | HTML / PDF / DOCX |
| 원천 데이터·로고 | `assets/` | CSV / PNG 등 |
| 실제 소스코드 | `eobom/frontend`, `eobom/backend` | — |
| 에이전트 규칙·메모리·스킬·툴 | `.harness/` | Markdown / 스크립트 |

- **같은 문서를 두 곳에 복사하지 않는다.** 한 곳이 정본이고 나머지는 링크로 참조한다.
- 이 저장소는 코드·기획·하네스가 **한 레포에 공존**한다(In-Repo Harness Architecture). "코드는 딴 데 있다"는 옛 외장 두뇌 전제는 2026-08-07 폐기됨.

## 8. 작업일지

- `docs/작업일지_및_기록/YYMMDD.md`에 **그날 한 실무 작업만** 기록.
- 하네스 자체의 구조 변경은 일지에 쓰지 않는다(이력 오염 방지) — `.harness/_meta/`에 남긴다.

## 9. 자기 점검

- 구조가 깨졌는지는 사람이 기억해서 확인하지 않는다. `tools/harness-doctor.sh` 하나가 전부 검사한다.
- **검사 대상이 0건이면 성공이 아니라 실패로 처리한다** — 2026-08-07에 점검 스크립트 3개가 경로 변경 때문에 아무것도 검사하지 않으면서 초록불만 띄우던 사고가 있었다. 조용한 통과가 제일 위험하다.
