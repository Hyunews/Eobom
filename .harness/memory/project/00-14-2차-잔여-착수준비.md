## 1. 5-4 → `00-17` 개인정보 인증·국외이전 대응안 · **조사 완료**

> 개발자 지시: *"이것에 대한 구체적 방안을 제시해줘. 문서화."*
> 정본: `00-11` §5.2 ⚠️ · §8-5

### 확인된 사실 (2026-08-14 기준)

| 항목 | 내용 |
| :--- | :--- |
| 근거 법 | **정보통신망법 §47** · **개인정보보호법 §32조의2** |
| 현행 규모 | **2026-02 기준 ISMS 의무대상 593개사** |
| **개편 진행 중** | 인증체계를 **강화(Advanced)·표준(Standard)·간편(Lite) 3단계**로 재편 |
| 개편 의무대상(안) | 주요 공공시스템운영기관 · 이동통신사업자 · 본인확인기관 · **매출액과 처리 개인정보 수를 고려한 대규모 개인정보처리자** |
| 강화 인증군 | **매출 1조원 이상 주요 ISP·IDC**, **매출 3조원 이상 정보통신서비스 제공자** |
| 시행 일정 | 사후관리 **2026 하반기**부터 / **ISMS-P 의무화·차등 적용은 2027년부터** |
| 확정 단계 | **아직 미확정** — 개인정보보호법 시행령·보호위 고시로 확정 예정 |
| 미인증 과태료 | **3,000만원** |

**→ 결론 방향**: 이어봄은 **현행 기준으로도, 개편안 기준으로도 의무대상이 아니다.**
다만 **기준이 2027년까지 유동적**이므로 문서에 **"확인일 + 재확인 시점(2027 시행령 공포 시)"** 을
반드시 박을 것. `00-11` §5.2가 *"오픈 전 전문가 확인"* 이라 한 것을 **"지금은 대상 아님 + 재확인
트리거"** 로 구체화하는 것이 이 문서의 일이다.

### 국외이전 — `00-11` §5.2 서술을 **정밀화해야 한다**

`00-11`은 *"국외 이전에는 별도 고지·동의 등 추가 의무가 따른다"* 고만 적었는데 **부정확하다.**
**개인정보보호법 §28조의8**의 이전 근거는 5가지이고, 그중:

- **정보주체와의 계약 체결·이행을 위해 필요한 처리위탁·보관**이면 **별도 동의 불요** —
  **개인정보처리방침 공개 등으로 갈음**할 수 있다.
- 해외 클라우드 사업자가 **§32조의2 인증(ISMS-P 등)** 을 받고 안전조치·권리보장 조치를 이행한
  경우에도 별도 동의를 요하지 않는다.

**→ 즉 "AWS 해외 리전 = 불법"이 아니다.** 국내 리전 권고의 근거는 *"위법을 피한다"* 가 아니라
**"논점 자체를 만들지 않는다"** 이며, `00-11` §5.2 마지막 문장이 이미 그렇게 말하고 있다.
**`00-17`은 이 구분을 명확히 하고 `00-11` §5.2를 스펙갱신할 것.**

> 참고: 개인정보 보호법 시행령이 **2026-05-19 시행**됐다는 언급이 있었다 — 조문 대조 시 확인.

### `00-17`이 실제로 담아야 할 것 (의무 인증이 아니라 **지금 해야 하는 것**)

의무대상이 아니어도 **안전성 확보조치 의무는 규모와 무관하게 적용된다.** 문서의 본체는 여기다.
`security.md`·`00-11` §7.2와 겹치지 않게 **"어디에 이미 있는지"를 표로 연결**하고, 빈칸만 채울 것.

## 2. 7-4 → `00-16` L3 사망확인 서류 검토서 · **조사 완료**

> 개발자 지시: *"7 기술확인 권고안대로 가되, 7-4 L3 서류에 대한 정보가 부족해서 문서화해서 검토 필요."*
> 정본: `00-12` §4.2 · `04-01` §10-2 · 권고 = **화면 확인 후 미저장**

### 서류 종류와 성격

| 서류 | 누가 발급 | 성격 |
| :--- | :--- | :--- |
| **사망진단서** | 병원 진료 중 사망 시 담당 의사 | 사망 사실 증명 |
| **시체검안서** | 병원 밖 사망·사고사 등, 검안 의사 | 사망진단서와 **같은 증명력** |
| **기본증명서(상세)** | 가족관계등록 관서 / 정부24 | **사망 사실이 기재됨** — 신고 완료 후 |
| **가족관계증명서(상세)** | 동일 | 신청인이 **유족임**을 증명 (사망 증명이 아님) |

- 사망신고는 **의사 발급 원본으로 관할 읍·면·동에 1개월 내**.
- **시간축이 중요**: 사망 직후에는 기본증명서에 아직 사망이 안 뜬다 → **D+0~수일 구간에서는
  사망진단서/검안서밖에 없다.** L3를 기본증명서로만 설계하면 **가장 급한 시점에 작동하지 않는다.**
- **두 가지를 갈라야 한다**: ①**사망 사실**(진단서·기본증명서) ②**신청인이 유족**(가족관계증명서).
  `00-12` §4의 L3는 ①이고, `BereavedRelation`은 ②다. **한 서류로 둘을 다 못 한다.**

### 🔴 미저장 권고의 **법적 근거를 여기서 얻는다** — 이게 이 문서의 핵심

**개인정보보호법 §24조의2(주민등록번호 처리의 제한)**: 다음을 제외하고 **주민등록번호를 처리할 수 없다.**

1. **법률·대통령령·국회규칙·대법원규칙·헌법재판소규칙·중앙선거관리위원회규칙·감사원규칙**에서
   구체적으로 처리를 요구·허용한 경우
2. 정보주체 또는 제3자의 **급박한 생명·신체·재산의 이익**을 위해 명백히 필요한 경우
3. 위에 준하여 불가피한 경우로서 **보호위원회가 고시로 정하는 경우**

> **✅ 핵심: 주민등록번호는 "동의를 받으면 된다"가 아니다. 법령 근거가 없으면 동의로도 처리할 수 없다.**
> (고유식별정보 일반은 별도 동의로 가능하지만 **주민번호는 예외**다.)
>
> 위 서류들에는 **주민등록번호가 인쇄돼 있다.** 이어봄에는 이를 처리할 법령 근거가 없다.
> **→ `00-12` §4.2·`04-01` §10-2의 "미저장" 권고는 운영 편의가 아니라 법적 요구에 가깝다.**
> `00-16`은 이 근거를 명시하고, **불가피하게 화면 확인을 하더라도 주민번호 뒷자리 마스킹을
> 제출 전 단계에서 요구**하는 설계를 권고할 것.

**함께 다룰 것**: 확인 사실만 남기는 기록 범위(`DeathVerification.verifiedAt`·`reviewedBy`),
운영자 확인 절차, `00-12` §8-6(사망확인 주체·비용) 연동, 안심상속 원스톱(`07-02`)과의 경계.

### 이 프로젝트 고유의 논점 — 일반론으로 쓰면 문서 가치가 없다

1. **게이트가 이미 있다.** `walkthrough.md` + Gemini 검증(`roles.md` §2)이 사람 손 회귀 테스트
   역할을 일부 한다. **그런데 (19) 재판정에서 §2-4(미선언 변경 대조)가 "미커밋 혼재로 실행 불가"** 로
   드러났다 — **게이트는 자동 테스트의 대체재가 아니다**를 보여주는 실증 사례로 쓸 것.
2. **3주체 협업이 근거를 강화한다.** Sonnet이 구현하고 Gemini가 판정하는 구조에서
   **"돌려봤다"의 증거가 스크린샷과 문장뿐**이다. `record.md` §1-1이 *"결과는 반증 가능하게"* 를
   요구하는데, **테스트 명령 한 줄이 그 요구의 가장 싼 답**이다.
3. **정직한 단점**: 목업이 많고 스펙이 계속 바뀌는 단계(`Deceased` 미확정 등)라 **지금 쓴 테스트의

   안 바뀌는 것 = 인증·권한 경계, 발번 규칙(`leadNo`/`consultNo` 유니크·동시성), 정책 계산.
4. **비용 0의 1단계가 있다**: `05-02` §6.4가 이미 말한 **"검증 스크립트를 지우지 말고
   `eobom/backend/tests/`에 남긴다"** — 러너 도입 없이 규칙만으로 시작 가능.

## 4. 6-2 → `06-03` 엔딩노트 열람통제·예외열람 정책 · **설계 방향만 정리됨**

> 개발자 지시: *"엔딩노트의 내용은 운영자가 보지 못함. **특수한 상황에서만 열람할 수 있다는 조건과
> 그것에 동의하는 것을 명시**해야 해. 특수한 상황이 뭐가 있을까...? 아니면 그냥 **메타데이터만**
> 보게 해야 하나...?"*
> 정본: `06-01` §3 (A안 메타데이터만 / B안 본문까지, 미확정) · `06-02` §5 · `00-12` §4 L3·L4

### 🔴 먼저 짚어야 할 것 — 질문의 전제부터 흔들린다

개발자 질문은 **"열람 정책"** 을 묻는데, **정책은 약속이지 보증이 아니다.**
서버가 복호화 키를 갖고 있으면 **운영자는 기술적으로 언제든 볼 수 있고**, 그때 "안 본다"는 건
**규칙일 뿐**이다. `06-01`이 지적한 *"화면에 건 비밀보장 약속"* 과 충돌하는 지점이 여기다.

> **→ `06-03`의 뼈대는 "특수 상황 목록"이 아니라 "약속을 구조로 뒷받침하는 층"이어야 한다.**
> 특수 상황 열거는 그다음이다. 이 순서를 뒤집으면 `00-12` §1이 지적한
> *"약속만 화면에 걸려 있다"* 의 재발이 된다.

### 특수 상황 후보 (초안 — 문서에서 검증·취사할 것)

| 후보 | 평가 |
| :--- | :--- |
| **법원 영장·수사기관의 적법한 요구** | ⭕ 거부할 수 없음. **약관에 반드시 명시**해야 함 |
| **본인의 명시적 요청**(고객지원) | ⭕ 정보주체 본인이니 문제 없음. 단 **본인 확인 절차** 필요 |
| **L3·L4 통과 후 유족 전달 집행** | 🟡 **이건 "열람"이 아니다** — 시스템이 유족에게 전달하는 것이고 운영자가 읽는 게 아님. **용어를 갈라야 함** |
| 시스템 장애·복구 | 🟡 암호문만 다루므로 **내용 열람이 아님**. 열람 정책 대상 아님 |
| 생명 위협 징후(자살 암시) 감지 | 🔴 **매우 위험** — 감지하려면 내용을 봐야 하므로 **순환 논리**. 권고하지 않음 |

### 설계 후보 — A안(메타데이터만)을 기본으로 하되 보강

- **A안 채택 + 예외 열람 통제 4종**: ①2인 승인(4-eyes) ②열람 사유 필수 기록 ③**불변 감사 로그**
  ④**본인/지정 유족에게 열람 사실 사후 통지**.
- **기술적 강화 후보**: 봉투 암호화·키 분할(운영자 단독 복호화 불가). **`00-11` 인프라 확정과
  맞물림** — 키 관리 위치가 정해져야 설계 가능하므로 **어디까지 지금 정할 수 있는지 선을 그을 것.**
- **동의 문구**: 개발자가 요청한 *"그것에 동의하는 것을 명시"* 는 **가입·작성 시점의 동의**이며,
  `04-02` §6의 위임 의사 문구와 **같은 화면 계열**이다. 톤을 맞출 것.
