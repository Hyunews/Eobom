## 🔍 2. 시설 데이터 항목 — 3종 유지 · 2종 폐기

초기 화면(`facilities.json` 더미 데이터)에 있던 5개 항목 중 **별점·주소/위경도·태그 3종은 DB 실데이터로 구현해 유지**하고, **견적 비교(2.3)·답사 예약(2.5) 2종은 2026-08-11 폐기**했습니다(→ 부록: 경위).

### 2.1 [항목 1] 별점 (Star Rating)
* **표시 값**: 리뷰가 있으면 리뷰 평균, 없으면 시설에 저장된 기본값을 보여줍니다(`facilityController.ts` `withEffectiveRating`).
* 🟡 **리뷰 작성은 보류**(2026-10-01 개발자 결정): 작성 화면(`FacilityReviewModal`)은 사용처가 없어 삭제됐고(`daccdb4`), 화면 없이 열려 있던 작성 API(`POST /api/facilities/:id/reviews`)도 닫았습니다(`a2a8b05` — 로그인만 확인해 누구나 평점을 바꿀 수 있었음). 리뷰 모델(`FacilityReview`)·조회·평점 집계는 나중을 위해 남겨 둡니다. 재개할 때는 `daccdb4` 이전에서 화면을, `facilityController.ts` `createReview` 주석대로 라우트를 복원합니다.
* **한계(재개 시 풀 것)**: 실제 이용(상담·장례 완료)을 검증하는 장치가 없습니다 — 처음 구현은 로그인 1인 1리뷰가 전부였습니다. 리뷰 수에 따라 가중치를 바꾸는 규칙도 없습니다.
* **기획 판단**: **`[유지]`** — 유족이 시설을 비교할 때 가장 먼저 보는 지표입니다. 지금 화면의 별점은 저장된 기본값입니다.

### 2.2 [항목 2] 주소 및 위경도 (Location & Address)
* **현재 구현**: 주소·좌표는 공공데이터(§1 데이터 출처)로 DB에 적재하고, 좌표가 없는 시설은 주소 지오코딩·카카오 로컬 API로 보강합니다. 지도는 Kakao Maps JavaScript SDK(`KakaoMapModal`)로 그립니다.
* **정렬**: 사용자 현위치(`navigator.geolocation`, 실패하면 기본 위치 — §6 R-3)를 받아 백엔드가 직선거리로 가까운 순 정렬합니다(`facilityController.ts` `haversineKm`). 좌표는 저장하지 않습니다(`01-02` §2.2).
* **필터**: 반경(km) 필터는 없습니다. 시/도·시/군/구 지역 필터(`province`·`district`)로 좁히며, 첫 화면 자동 적용 규칙은 §6입니다.
* **위치정보법**: 위치기반서비스 사업자 신고는 `00-22` B-1(실서비스 개시 전).
* **기획 판단**: **`[유지]`**

### 2.4 [항목 4] 특징 해시태그 (Hashtags)
* **현재 구현**: `Facility.tags`(문자열 배열)를 카드에 태그로 보여줍니다. 화이트리스트(`TAG_CATALOG`, 지금은 공설·사설)에 있는 태그만 누를 수 있고, 누르면 그 태그가 붙은 시설만 걸러집니다(`FacilityPage.tsx` `handleTagClick`). 나머지는 누를 수 없는 라벨입니다.
* **10-15 개정**: 태그는 **운영 주체 · 시설 종류**(장례식장 종류 + 묘지 종류) 2가지 분류의 값만 남기고, 전부 눌러 걸러볼 수 있게 바꿉니다(개발자 결정) — 🔜 구현 전.
* **정본**: 분류·값·걸러보기 규칙은 `01-06`.
* **기획 판단**: **`[유지]`**

## 🗺️ 3. 전국 장례식장 데이터 구축 및 노출 전략 (하이브리드 디렉토리 모델)

### 3.1 전략 채택 배경: Cold Start (초기 데이터 부족) 문제 방지
초기 스타트업이 "가입/제휴된 장례식장만 노출하는 입점제"를 선택하면, 서비스 오픈 초기 등록 시설이 수십 개에 불과하여 유저가 동네 장례식장을 검색했을 때 **"검색 결과가 없습니다"가 발생하여 유저가 즉시 이탈**하게 됩니다.

따라서 전국의 모든 장례식장을 첫날부터 검색할 수 있는 **`[하이브리드 디렉토리 모델]`**을 채택합니다.

### 3.2 현행 데이터 흐름

```
 [ 보건복지부 장례식장 현황 API ]  +  [ 봉안시설 · 자연장지 공공 CSV ]
                            │   (좌표·통용명 보강: 카카오 로컬 API)
                            ▼
              【 시설 DB — 전국 약 2천 건 】
                            │
         ┌──────────────────┴──────────────────┐
         ▼                                     ▼
【 제휴 시설 (사업자 클레임 승인) 】       【 비제휴 시설 】
 • 소개 글·종교·수용 규모·부대시설 수정    • 공공데이터 기본 정보(주소·지도·부대시설)
   (⬜ 01-05 §14-5)
 • 업체 문의 리드 수신·관리(→ 01-05)       • 업체 문의 처리 방식은 결정대기(→ 01-05 §10-4)
```

### 3.3 제휴 vs 비제휴 시설 차별화

> 🟡 **결정대기 — 제휴사 혜택·수익 구조 재설계**(`pending-approvals.md`, 2026-08-11 등록).
> 처음 설계한 차별화 항목 중 가격 분해·직통 답사 예약·VR 360이 폐기돼 제휴 혜택이 비어 있습니다.
> 제휴사에게 줄 실질 혜택과 그 대가(수수료·광고비)를 정해야 사업자 영업이 가능합니다. 처음 설계한 표는 부록: 경위.

| 구분 | 비제휴 시설 | 제휴 시설(사업자 클레임 승인, `01-05` §3.3) | 상태 |
| :--- | :--- | :--- | :--- |
| **기본 정보** | 주소·지도 핀·부대시설 | 같음 | ✅ |
| **업체 사진** | 없음 | 🔄 **결정 대기 — 화면에서 뺌**(2026-10-19 개발자, 디자인 개편 6단계 확정 ⑩ⓓ). 업로드 API(`facilityMediaController.ts`)는 남아 있지만 유족 화면엔 사진 칸이 없고(10-15 카드 사진 뺌), 새 사업자 화면(`01-05` §14-5)도 칸 자리만 둔다. 다시 열 때 저장소 = R2 새 공개용 버킷(버킷 결정도 그때) | ⏸ |
| 🆕 **소개 글 · 시설 정보 수정** | 없음(공공 데이터만) | 사업자가 소개 글·종교·수용 규모·부대시설을 고치면 **유족 화면에 바로 반영**, 문제 글은 운영자가 나중에 숨김(2026-10-19 개발자, `01-05` §14-5) | ⬜ 미구현 |
| **업체 문의** | 담당 업체 없음 — 처리 방식 결정대기(`01-05` §10-4) | 리드 수신·상태 관리(`01-05` §4) | ✅ 구현 |
| **인증 뱃지 · 검색 상단 노출** | — | 처음 설계에 있었으나 화면에 없음 | ⬜ 재설계와 함께 결정 |

전화번호는 제휴 여부와 무관하게 노출하지 않습니다(`01-05` §9).

### 3.4 하이브리드 모델의 3대 비즈니스 효과
1. **첫날부터 전국 커버리지**: 제휴 여부와 무관하게 전국 시설이 검색되므로 "검색 결과 없음"으로 인한 이탈을 막습니다.
2. **사업자 입점 영업의 근거**: 이미 검색되고 있는 시설에 제휴 전환 혜택을 제시합니다 — 🟡 **혜택 내용은 결정대기**(§3.3).
3. **신뢰도**: 제휴 여부와 상관없이 정보를 개방해 공공성과 신뢰성을 확보합니다.

### 5.3 형태 — 🔄 페이지로 확정 (2026-10-19 개발자, 2단계 묶음 5 확정 ㉮·㉯)
- **별도 페이지 `/facility/:id`.** 모달은 병행하지 않는다. 근거: 개별 시설 URL을 공유·북마크할 수 있고(→ `00-10`), 담을 정보가 모달에 넣기엔 많다.
- **들어가는 곳 = 검색 카드(카드형·리스트형)의 시설명만** 누른다(㉮). 카드 전체를 누르게 하면 카드 안 [카카오 지도][상담]과 겹친다.
- **로그인 필요** — `/facility` 검색과 같은 정책(㉯). 카톡으로 링크를 받은 가족도 로그인해야 한다(받아들인 불편).
- [주소 복사]는 넣지 않는다(㉱ — 코드에 없는 새 버튼). 공유는 주소창으로.

## 🆕 6. 첫 화면 = 잡힌 지역만 보여준다 (2026-09-29 사람 지시)

### 6.1 문제
`/facility`에 처음 들어오면 위치(광산구 등)가 잡혀도 **전국 2천여 개가 가까운 순으로** 나열된다.
🔵 원인(코드 읽기): 첫 화면은 좌표(`lat`·`lng`)만 서버에 보내 **정렬에만** 쓴다(`FacilityPage.tsx` 목록 조회 이펙트).
`province`·`district`(하드 필터)는 사람이 직접 골라 `검색`을 눌렀을 때만 간다. 🔵 **직접 검색은 정상** — 고치지 않는다.

### 6.2 규칙

| # | 내용 |
| :---: | :--- |
| R-1 | **첫 화면에서 잡힌 지역을 검색 조건으로 자동 적용한다** — 사람이 시/도·시/군/구를 골라 `검색`을 누른 것과 **같은 상태**가 된다(선택 칸에도 그 값이 채워져 보임). 정렬은 지금처럼 가까운 순 |
| R-2 | **실제 위치든 기본 위치든 똑같이 적용한다**. 기본 위치일 때는 지금 있는 *"위치를 확인하지 못해…"* 안내를 그대로 띄운다 |
| R-3 | 🔄 **기본 위치를 광주 광산구 → 서울 중구로 바꾼다**(`config.ts` `GEOLOCATION_FALLBACK`, 중구청 인근 좌표). 코드 주석의 "광산구" 표기도 같이 고친다. 🔵 약관·처리방침의 **회사 주소(광산구)는 이것과 무관** — 건드리지 않는다 |
| R-4 | **넓혀 가기**: 잡힌 시/군/구가 선택지(`/api/geo/regions` = 실제 시설이 있는 지역)에 없으면 **시/도만** 적용, 시/도도 없으면 **필터 없음**(지금 동작). 시/도 이름이 표시명과 다르면(예: 역지오코딩 `광주광역시` ↔ 표시 `전남광주`) 서버의 표시명 변환 규칙과 같은 기준으로 맞춘다 — 새 표를 만들지 않는다 |
| R-5 | 사람이 지역을 **`선택 안함`으로 바꾸고 검색**하면 전국(필터 없음). 자동 적용은 **첫 화면 한 번**만 — 사람이 바꾼 뒤 다시 덮어쓰지 않는다 |
| R-6 | **유품 수거(`/pickup`)도 같은 규칙** — 지금은 실제 위치일 때만 자동 적용하고 기본 위치면 적용하지 않는다(`applyAsFilter:false`) → R-2대로 기본 위치도 적용. 넓혀 가기(R-4)는 이미 같은 방식이다. 🔵 업체 데이터는 아직 목업이라 서울 중구 업체가 없으면 R-4에 따라 넓어진다. 🔄 **09-29 구현 중 발견** — 목업의 시/도 이름이 표시명 체계와 달라(`광주` ↔ 역지오코딩 표시명 `전남광주`) 진짜 광주에서도 안 맞았다 → **목업의 시/도 이름을 표시명(`/api/geo/regions`와 같은 이름)으로 맞춘다.** 엄격 적용(빈 목록)은 채택하지 않음 — 목업이 적어 대부분 빈 화면이 되고, 장사시설과 규칙이 갈린다 |

🔴 **위치정보법**: 새로 모으는 위치는 없다 — 이미 받던 좌표를 필터에도 쓸 뿐이다. `LOCATION_FEATURE_ENABLED` 스위치·고지 문구는 그대로(`security.md` §4, `00-22` B-1).
