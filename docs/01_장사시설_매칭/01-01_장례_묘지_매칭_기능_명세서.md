## 🔍 2. 더미 데이터 5종의 실제 구현 가능성 및 상세 기획 판단

현재 프론트엔드 코드(`FacilityPage.tsx`, `facilities.json`)에 포함된 5가지 핵심 데이터 항목은 기술적 및 비즈니스적으로 **100% 실제 구현이 가능하며, 서비스의 본질적인 경쟁력이므로 모두 '유지'합니다.**

### 2.1 [항목 1] 별점 (Star Rating)
* **현재 코드 상태**: `facilities.json` 내 `rating: 4.9`, `rating: 4.8` 등의 하드코딩된 더미 수치 노출.
* **실제 구현 기술 방안**:
  * **자체 검증 리뷰 시스템 DB (`facility_reviews`) 구축**: 단순 외부 카카오/네이버 별점이 아닌, 이어봄 플랫폼을 통해 **실제 답사/상담/장례를 완료한 검증된 이용자**만 리뷰 및 별점(1.0~5.0)을 작성할 수 있도록 구현.
  * **집계 로직**: DB 레벨에서 `AVG(rating)` 산술 평균값을 수신하여 실시간 업데이트.
  * **초기 운영 전략**: 서비스 출시 초기에는 지자체 및 보건복지부 공시 서비스 만족도 수치를 기본 부여하고, 실이용 유저의 리뷰가 5건 이상 누적되면 실제 유저 평점 가중치로 자동 전환.
* **기획 최종 판단**: **`[유지]`** — 유족 및 자녀 보호자가 장례식장을 비교할 때 가증 신뢰하는 핵심 지표임.

### 2.2 [항목 2] 주소 및 위경도 (Location & Address)
* **현재 코드 상태**: 실제 한국 도로명 주소(예: "서울 강남구 일원로 81") 및 정확한 위경도 좌표(`lat: 37.4882, lng: 127.0856`)가 들어있어, 모달 클릭 시 실제 카카오 맵 핀이 렌더링됨.
* **실제 구현 기술 방안**:
  * **카카오 로컬 REST API (`query=장례식장`) 및 Kakao Maps JavaScript SDK 100% 연동**:
    * 사용자의 현위치(`navigator.geolocation`)를 수신하고, 하버사인(Haversine) 거리 계산 로직으로 5km, 10km, 20km 반경을 동적으로 필터링.
    * 전국의 모든 장례식장/수목장의 정확한 주소, 전화번호, 지번, 위경도 좌표를 카카오 API로 실시간 수집 및 동기화.
* **기획 최종 판단**: **`[유지]`** — 기술적으로 이미 검증 완료되었으며 100% 실데이터 연동 가능.

## 🗺️ 3. 전국 장례식장 데이터 구축 및 노출 전략 (하이브리드 디렉토리 모델)

### 3.1 전략 채택 배경: Cold Start (초기 데이터 부족) 문제 방지
초기 스타트업이 "가입/제휴된 장례식장만 노출하는 입점제"를 선택하면, 서비스 오픈 초기 등록 시설이 수십 개에 불과하여 유저가 동네 장례식장을 검색했을 때 **"검색 결과가 없습니다"가 발생하여 유저가 즉시 이탈**하게 됩니다.

따라서 전국의 모든 장례식장을 첫날부터 검색할 수 있는 **`[하이브리드 디렉토리 모델]`**을 채택합니다.

### 3.2 3단계 하이브리드 데이터 흐름도

```
 [ 보건복지부 e하늘 공공 Open API ]  +  [ 카카오 로컬 REST API ]
                            │
                            ▼
           【 전국 1,100여 개 장례식장/수목장 마스터 DB 】
                            │
         ┌──────────────────┴──────────────────┐
         ▼                                     ▼
【 🌿 이어봄 제휴 파트너 시설 】          【 일반 공시 시설 (비제휴) 】
 • [🌿 이어봄 인증 파트너] 뱃지 부여        • 기본 주소, 위치, 전화번호 제공
 • [VR 360 사이버 투어] 뷰어 제공        • 보건복지부 공시 기본 비용만 표시
 • [실시간 패키지 할인가 견적] 분해        • 답사 신청 시 "이어봄 대행 예약" 지원
 • 1-Touch 직통 답사 예약 연동            • 검색 목록 하단 기본 순위 노출
 • 검색 목록 최상단 핀 고정 및 스포트라이트
```

### 3.3 제휴 vs 비제휴 시설 기능 차별화 명세

> ⚠️ **재설계 필요 (2026-08-11)** — 아래 표의 차별화 항목 4개 중 3개가 무효가 됐다.
> **가격 정보**(5대 세부 분해) → §2.3 폐기 / **답사 방식**(직통 예약·해피콜 대행) → §2.5 폐기 /
> **시각 자료**(VR 360) → `VRViewerModal.tsx`는 구현돼 있으나 어디서도 import하지 않는 고아 컴포넌트, 존치 여부 개발자 확정 대기.
> 실제로 살아있는 차별화는 **검색 노출 우선순위**와 **업체 사진 업로드**(`Facility.images`)뿐이며,
> 현재 제휴 시설은 **0건**이라 어느 것도 실증되지 않았다.
> **제휴사에게 줄 실질 혜택과 그 대가(수수료·광고비) 구조를 다시 설계해야 한다** — 미착수 과제.

| 구분 | 일반 공시 시설 (비제휴) | 🌿 이어봄 인증 파트너 시설 (제휴) |
| :--- | :--- | :--- |
| **기본 정보** | 도로명 주소, 지도 핀, 전화번호 | 도로명 주소, 지도 핀, 전화번호, **인증 뱃지** |
| **가격 정보** | 보건복지부 공시 기본 총액 범위 | **5대 세부 항목 실시간 분해 & 패키지 할인가** |
| **답사 방식** | 이어봄 상담원 해피콜 대행 예약 | **장례식장 직통 1-Touch 자동 확정 예약** |
| **시각 자료** | 일반 대표 이미지 | **VR 360도 사이버 공간 투어 갤러리** |
| **검색 노출** | 기본 거리순/가격순 정렬 노출 | **검색 결과 최상단 스포트라이트 핀 고정** |

### 3.4 하이브리드 모델의 3대 비즈니스 효과
1. **첫날부터 전국 100% 커버리지 확보**: 유저가 전국의 어떤 대학병원이나 지역 장례식장을 검색해도 무조건 노출되어 UX 만족도 극대화.
2. **B2B 입점 영업의 압도적 명분**: 장례식장 사업자에게 *"이미 플랫폼에 등록되어 검색되고 있으나, 제휴 전환 시 [VR 360], [할인 견적], [상단 노출] 혜택이 부여됩니다"* 라며 자연스러운 입점 전환 유도.
3. **토탈 케어 브랜드 신뢰도 구축**: 제휴 여부와 상관없이 모든 정보를 투명하게 개방함으로써 서비스의 공공성과 신뢰성 확보.

## 🛠️ 4. 개발 전달용 백엔드 DB 스키마 타겟 규격

개발팀(`eobom/backend`) 구현 시 아래 테이블 구조로 확장 반영을 진행합니다:

```prisma
// 시설 마스터 테이블
model Facility {
  id           String   @id @default(cuid())
  name         String
  type         String   // "장례식장", "묘지/수목장"
  location     String   // 도로명 주소
  lat          Float
  lng          Float
  price        String
  priceValue   Int
  rating       Float    @default(0.0)
  religion     String
  guests       String
  isPartner    Boolean  @default(false) // 제휴 파트너 여부
  vrImages     Json?    // VR 투어 이미지 JSON
  createdAt    DateTime @default(now())

  tags         FacilityTag[]
  reviews      FacilityReview[]
  bookings     FacilityBooking[]
}

// 시설 리뷰 테이블
model FacilityReview {
  id         String   @id @default(cuid())
  facilityId String
  userId     String
  rating     Float
  content    String
  createdAt  DateTime @default(now())

  facility   Facility @relation(fields: [facilityId], references: [id])
}
```

> ℹ️ 위 §4는 2026-08-05 작성 당시의 **타겟 규격**이며, 실제 구현 스키마는 그 뒤로 크게 확장됐다.
> **현행 정본은 `00-05_DB_요구사항_및_테이블_사전.md`** (schema.prisma에서 자동 생성, 13개 테이블·146개 컬럼).

## 🆕 5. "업체 자세히 보기" — 답사 예약 대체 설계 (2026-08-11 신설, 미구현)

§2.5에서 답사 예약을 폐기하면서 생긴 공백을 메우는 과제다. **답사를 가야만 알 수 있던 정보를 화면에서
충분히 보여줘서 답사 필요성 자체를 없애는 것**이 목표다.

### 5.1 왜 필요한가
현재 시설 카드는 이름·주소·평점·태그·가격문자열·사진 정도만 보여준다. 유족이 "여기가 어떤 곳인지"
판단하기엔 부족한데, 답사 예약도 없앴으므로 **판단 근거를 화면이 대신 제공해야 한다.**
이게 없으면 유족은 결국 전화를 걸게 되고, 전화는 수수료 청구 근거가 안 된다(→ `01-05` §9).

### 5.2 담을 정보 (이미 DB에 있는 것부터)
| 항목 | 출처 | 상태 |
|---|---|---|
| 시설 사진 갤러리 | `Facility.images` | ✅ 파트너 업로드 구현됨 |
| 부대시설 | `Facility.amenities` (식당·매점·주차장·유족대기실·장애인편의시설) | ✅ 공공 CSV에서 수집됨 |
| 종교·수용 규모 | `Facility.religion`, `guests` | ✅ 보유 |
| 위치·지도 | `lat`/`lng` + 카카오맵 | ✅ 보유 (`KakaoMapModal`) |
| 리뷰 전문 | `FacilityReview` | ✅ API 있음, 실데이터 0건 |
| 운영주체(공설/사설) | `Facility.tags` + `TAG_CATALOG` | ✅ 2026-08-11 구현 |

**핵심**: 신규 데이터 수집 없이 **이미 가진 것만 모아 보여줘도** 상세 화면이 성립한다.

### 5.3 형태 — 모달 vs 페이지
**별도 페이지(`/facility/:id`) 권장.** 근거: (1) 라우팅이 2026-08-11 History 방식으로 바뀌어
개별 시설 URL을 공유·북마크할 수 있게 됐고(→ `00-10`), 장례식장 링크를 가족에게 카톡으로 보내는
시나리오가 실제로 있다. (2) 담을 정보량이 모달에 넣기엔 많다.
단, 목록에서의 빠른 확인용으로 모달을 병행하는 것도 가능하다 — 구현 판단은 `[Claude:Sonnet]`.

### 5.4 전환 동선
상세 화면의 유일한 CTA는 **"업체 문의"**(`InquiryModal` → `Lead type=QUOTE`)다.
전화번호는 노출하지 않는다(2026-08-10 결정 유지).

### 5.5 미해결
- 리뷰가 0건이라 상세 화면의 신뢰 요소가 비어 있다 — 초기 리뷰 확보 방안 별도 필요.
- 비제휴 시설(전체의 100%)은 사진이 없다 — 사진 없는 상세 화면의 기본 표현 설계 필요.
