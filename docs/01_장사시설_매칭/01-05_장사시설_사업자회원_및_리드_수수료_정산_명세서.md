# 🏢 01-05. 장사시설 사업자 회원 & 리드 수수료 정산 명세서

> **문서 목적**: 장사시설(장례식장·묘지/수목장) 사업자가 **B2C 유저와 분리된 사업자 계정**으로 가입·관리되고, 유저가 남긴 **업체 문의를 추적 가능한 리드(Lead)로 적재**하여 **수수료 청구의 법적·상업적 근거**로 삼는 체계를 정의합니다.
>
> **근거**: 2026-08-10 **사장님 지시(개발자 전달)** 2건 —
> ① 장사시설 업체가 사업자로 **따로 회원가입**하고 우리가 **따로 관리**한다.
> ② 유저가 웹을 통해 문의·견적요청을 남기면 **로그/견적요청 번호를 우리가 보유**하여, 추후 그것을 근거로 **수수료를 청구**한다.
>
> **배경 문서**: `01-03`(견적 데이터 한계 3대 대안) · `01-04`(답사예약 vs 직통전화 리드 수수료 검토) — 둘 다 2026-08-11 폐기된 검토서 · `01-01` §3.3(제휴/비제휴 차별화)
> 본 문서는 그 검토서들의 결론 중 **리드(업체 문의) 부분만 이어받아** 구현 스펙으로 확정한 문서입니다. 정정·폐기 기록은 문서 끝 **부록: 경위**.

## 📌 1. 이 문서가 푸는 문제

`01-04`(폐기된 검토서)가 지적한 핵심 문제는 이것입니다 — **직통 전화(`tel:`)로 연결되면 장례식장 원장은 그 유족이 이어봄을 보고 왔는지 알 방법이 없고, 우리도 수수료를 청구할 명분이 없다.**

사장님 지시(개발자 전달)는 이 문제의 해법을 두 축으로 확정한 것입니다.

| 축 | 무엇을 만드나 | 왜 필요한가 |
| :--- | :--- | :--- |
| **① 사업자 회원 체계** | 수수료를 청구할 **상대방(법인격)**을 시스템에 등록 | 청구서를 보낼 대상이 DB에 없으면 정산 자체가 불가능 |
| **② 리드 로그 + 견적요청 번호** | 청구의 **증거** | "이 번호의 유족을 우리가 보냈다"는 대조 가능한 물증 |

둘은 분리 불가능합니다. 리드만 쌓으면 청구할 상대가 없고, 사업자만 받으면 청구할 근거가 없습니다.

## 🏢 3. 사업자 회원 체계

### 3.1 왜 `User` 테이블에 role만 추가하지 않는가

기존 `User`는 소셜 로그인(카카오/네이버/구글) 전제로 설계되어 있고 `role` 필드에 `'USER' | 'EXPERT' | 'ADMIN'`이 있습니다. 여기에 `'PARTNER'`를 얹는 것이 가장 적은 코드로 보이지만 **채택하지 않습니다.**

| 이유 | 설명 |
| :--- | :--- |
| **인증 방식이 다름** | 사업자는 담당자 퇴사·교체가 잦아 개인 소셜 계정에 묶으면 안 된다. 업체 이메일 + 비밀번호가 맞다. |
| **필수 정보가 다름** | 사업자등록번호·상호·대표자명·정산 계좌는 B2C `User`에 전부 `null`로 남아 스키마가 오염된다. |
| **법인격 단위가 다름** | 한 법인이 장례식장 2곳을 운영할 수 있다. 계정(사람)과 사업자(법인)를 1:1로 묶으면 확장이 막힌다. |
| **탈퇴 정책이 다름** | B2C 유저는 탈퇴 시 삭제 대상이지만, 사업자는 **정산 이력 때문에 함부로 지울 수 없다.** |

→ **`Partner` 모델을 신설**하고 `User`와 분리합니다. 사장님 지시의 "따로 회원가입 / 따로 관리"와도 일치합니다.

### 3.2 가입 → 승인 플로우

```text
[사업자]                          [이어봄 운영자]
   │
   │ ① 가입 신청
   │   상호 / 사업자등록번호 / 대표자명
   │   담당자명·연락처 / 이메일 / 비밀번호
   │   + 사업자등록증 사본 업로드
   ▼
 status = PENDING ───────────────▶ ② 심사 큐에 노출
   │                                   │
   │                                   ├─ 사업자등록번호 진위확인
   │                                   │  (국세청 API, 공공데이터포털 무료)
   │                                   ├─ 사업자등록증 사본 대조
   │                                   └─ 시설 소유·운영 관계 확인
   │                                   │
   │◀──────────────────────────────────┤
   │                                   │
   ├─ APPROVED  → 로그인·리드 열람 가능  │
   ├─ REJECTED  → 사유 통보, 재신청 가능 │
   └─ SUSPENDED → 계약 해지·연체 시     │
```

> 🔴 **2026-10-21 코드 대조 — "사유 통보, 재신청 가능"이 지금은 안 된다**: 반려 사유를 볼 곳이 없고, 같은 사업자등록번호로 다시 가입하면 409. 고칠 길은 §14-2(✅ 2026-10-21 개발자 확정 — 8단계 구현).

> **자동 승인은 채택하지 않습니다.** 사업자등록번호 진위는 API로 검증되지만, **"그 사업자가 그 시설의 운영자인가"는 자동 검증이 불가능**합니다. 이걸 자동화하면 타인이 남의 장례식장 리드(=유족 개인정보)를 열람하게 됩니다. 개인정보 사고의 직접 경로이므로 수동 심사를 필수로 둡니다.

### 3.3 시설 소유권 클레임

시설 마스터(`Facility`, 전국 약 2천 건 — `01-01` §1)는 공공데이터(장례식장은 보건복지부 API가 정본, 2026-09-09 · 카카오는 좌표 보강)로 **우리가 먼저 만들어 둔 것**이라, 사업자는 "이미 있는 내 시설"을 자기 것이라 주장(claim)하는 형태가 됩니다.

* 가입 시 또는 가입 후, 사업자가 디렉토리에서 자기 시설을 검색해 클레임 신청
* 운영자가 승인하면 `Facility.partnerId`가 채워지고 그 시점부터 **해당 시설의 리드가 이 사업자에게 귀속**
* 한 사업자가 여러 시설 클레임 가능 (`Partner` 1:N `Facility`)
* **이미 다른 사업자에게 승인된 시설은 중복 클레임 불가** — 신청은 받되 운영자에게 분쟁 건으로 표시

### 3.4 `isPartner` 필드 처리 (기존 스키마와의 정합성)

`Facility.isPartner`(Boolean)가 이미 존재하고 `01-01` §3.3(제휴/비제휴 차별화)이 이 값으로 UI를 나누는 것을 전제로 했습니다. 신설되는 `partnerId`와 의미가 겹치므로 **한쪽을 정본으로 못 박습니다.**

* **정본(SSOT)**: `Facility.partnerId` — 승인된 클레임이 있으면 채워짐
* **`isPartner`**: 목록 조회 필터·정렬 성능을 위한 **파생 캐시 컬럼**으로 재정의. 클레임 승인/해지 **트랜잭션 안에서만** 갱신한다.
* 두 값이 어긋나면 `partnerId`가 이긴다. 정합성 점검 배치를 운영 초기에 1회 이상 돌린다.

> 파생 컬럼을 두는 이유: 목록 API가 매 요청 `partnerId IS NOT NULL` 조인 없이 인덱스만으로 파트너 우선 정렬을 하도록. 단, **동기화 지점을 트랜잭션 한 곳으로 제한**해야 썩지 않는다.

## 🎫 4. 리드(Lead)와 견적요청 번호

### 4.1 리드 유형

| 유형 | 발생 지점 | 개인정보 수집 | 수수료 청구 근거로서의 강도 |
| :--- | :--- | :---: | :--- |
| `QUOTE` **업체 문의** | 업체 문의 폼 모달(`InquiryModal`) — 로그인 필수(§10-2) | ✅ 이름·연락처 | **강함** — 유저가 명시적으로 신청, 번호 발급 |
| `CONSULT` **1:1 상담신청** | 🟡 **생산자 없음** — 값만 남아 있음. 전문가 상담 신청은 별도 모델(`ConsultRequest`)·별도 번호(`EC-`)로 받는다(→ `02-03` §4.1) | ✅ | 강함 |
| `CALL` **전화 버튼 클릭** | `tel:` 링크 클릭 — 🟡 **지금 화면에 전화 노출이 없어 발생하지 않음**(§9) | ❌ 익명 이벤트(`userId` 항상 `null`) | **약함** — §9 참조. 기본 **비청구** |

`QUOTE`는 처음 "견적요청"이던 시절의 값이고, 화면 문구는 **"업체 문의"**입니다. **enum 값은 바꾸지 않습니다** — 이미 적재된 리드의 타입 값을 바꾸면 과거 정산 근거가 흔들리기 때문입니다. 답사예약(`BOOKING`) 유형은 2026-08-11 폐기됐습니다(→ 부록: 경위).

> `CALL`을 청구 근거로 쓰지 않는 이유는 §9에 따로 적었습니다. 클릭했다고 통화한 것이 아니고, 통화했다고 계약한 것도 아니기 때문에 업체가 반박하면 우리가 증명할 수단이 없습니다. **약한 근거로 청구하면 파트너 신뢰를 잃습니다.** 지표로만 씁니다.

### 4.2 견적요청 번호 (사장님 지시 ②의 핵심)

전화로 "**EB-260810-0001** 건입니다"라고 대조할 수 있어야 하므로, 내부 PK(uuid)와 **별개의 표시용 번호**를 발번합니다.

```text
EB - 260810 - 0001
│    │        └─ 그날의 일련번호 (4자리, 일 단위 리셋)
│    └─ 발생일 YYMMDD
└─ 고정 접두어
```

* **불변**: 발번 후 절대 변경·재사용 금지. 상태가 바뀌어도 번호는 그대로.
* **유니크 제약**을 DB에 건다(`@unique`). 동시 요청 시 중복 발번을 애플리케이션 로직으로만 막지 않는다.
* **번호만으로는 조회 불가**: 번호는 대조용 식별자일 뿐, 상세 조회는 반드시 인증(파트너 본인 시설 / 운영자)을 거친다. 번호가 순차적이라 추측이 쉬우므로 **인증 없는 조회 API를 만들면 그대로 개인정보 유출**이 된다.

### 4.3 리드 상태 머신

```text
 REQUESTED ──▶ NOTIFIED ──▶ RESPONDED ──┬─▶ CONVERTED  (계약 성사 → 청구 대상)
  (접수)       (업체전달)     (업체응답)   │
                                        └─▶ LOST       (무산 → 비청구)
      │
      └────────────────────────────────────▶ INVALID    (허수·중복·장난 → 비청구)
```

* 상태 변경은 **누가·언제** 했는지 `statusHistory`에 누적한다. 정산 분쟁 시 이 이력이 유일한 방어 수단이다.
* `CONVERTED` 판정은 **업체 신고 + 운영자 확인**의 2단계. 업체 자기신고만 믿으면 축소 신고(수수료 회피) 유인이 생긴다.
* `INVALID` 처리 권한은 **운영자만**. 업체가 임의로 허수 처리하면 청구를 무력화할 수 있다.
* 🆕 **무산(`LOST`) 사유 = 고르기(필수)**(2026-10-19 개발자, 디자인 개편 6단계 확정 ⑨). 선택지는 이 순서·이 글자 그대로 4개:
  ① 조건(가격, 수용인원 등)이 맞지 않음 · ② 신청자와 연락이 닿지 않음 · ③ 신청자의 계획 변경 · ④ 기타(직접 입력).
  ④를 고를 때만 글 칸이 열린다(이때 글은 필수). 🔴 허수·장난은 선택지에 넣지 않는다 — 그건 `INVALID`이고 운영자만 한다(위).
  이유: 무산은 비청구라 **축소 신고 점검에 사유가 모여야** 한다. 지금 코드는 자유 글(`leadController.ts` `note`, 선택) → 8단계에 사유 코드 칸 + `statusHistory`에도 같이 남김(코드 이름은 구현 때). 운영자 업체 문의 상세에 같은 글자로 보인다(§14-9).

### 4.4 신청자 정보 스냅샷 — 왜 `userId` 참조만으로 부족한가

리드에 `userId`만 걸어두면, 유저가 **탈퇴**하는 순간 정산 근거가 사라집니다. 반대로 개인정보를 영구 보관하면 개인정보보호법 위반입니다. 둘 다 피해야 하므로:

* 리드 생성 시 신청자 이름·연락처를 **스냅샷으로 복사 저장**한다(`applicantName`, `applicantPhone`).
* **정산 확정 후**에는 스냅샷을 마스킹한다 — `홍길동` → `홍*동`, `010-1234-5678` → `010-****-5678`.
* 마스킹 후에도 **`leadNo`·발생시각·시설·금액·상태이력은 보존**된다 → 청구 근거는 유지, 개인정보는 최소화.
* 보유기간·마스킹 시점은 §7.3.

### 6.4 인증 분리 원칙

* 사업자 토큰과 B2C 유저 토큰은 **payload에 `aud`(대상) 필드를 넣어 구분**하고, 미들웨어에서 교차 사용을 차단한다.
* `/api/partner/*`에 B2C 토큰이 들어오면 401. 반대도 동일.
* **`/api/admin/*`는 별도 `Admin` 모델 + `aud='admin'` 토큰으로 보호**한다. B2C `User.role`로 운영자를 가리지 않는다 — 소셜 로그인 계정에 `role` 하나만 잘못 세팅돼도 운영자가 되는 구멍을 처음부터 만들지 않기 위해서다.
* **운영자는 공개 가입이 없다.** `Admin`에는 signup API가 없고 `prisma/seed-admin.ts` 스크립트로만 계정을 만든다. 가입 폼이 있는 것 자체가 공격면이다.
* 토큰은 4종(`aud`: `user`/`partner`/`expert`/`admin`)이며 교차 사용은 전부 401이다. 초안의 `User.role` 방식에서 바뀐 경위는 부록: 경위.

## 🔐 7. 개인정보 — 이 문서에서 가장 위험한 부분

유족의 이름·연락처를 장례식장에 넘기는 행위는 **개인정보 제3자 제공**(개인정보보호법 제17조)입니다. 동의 없이 넘기면 서비스 자체가 중단될 수 있는 위험이므로, 아래는 **선택이 아니라 구현 필수 조건**입니다.

### 7.1 동의 없이는 리드를 만들지 않는다

업체 문의 폼에 **필수 동의 체크박스**를 두고, 아래 4가지를 명시합니다.

| 고지 항목 | 내용 |
| :--- | :--- |
| 제공받는 자 | 제휴 시설: **해당 시설**(`{시설명} (이어봄 제휴 사업자)`) · 비제휴 시설: **이어봄 상담원**(사업자에게 직접 전달하지 않음, §7.2) |
| 제공 목적 | **업체 문의 및 견적 안내 연락** |
| 제공 항목 | 이름, 연락처, 요청 내용(희망일시·규모 등) |
| 보유·이용 기간 | **문의가 끝날 때까지(최대 접수일부터 90일)** — 그 뒤 사업자 화면에서 이름·연락처를 가림(§7.3) |

위 표는 코드의 고지 문구(`leadService.ts` `buildConsentNotice`)와 같아야 합니다. 문구를 바꾸면 `noticeVersion`도 올리고 이 표를 함께 고칩니다.
🔄 **10-15 개발자 결정**: 보유·이용 기간을 "목적 달성 후 파기"(`noticeVersion` 2026-08-11) → 위 문구로 변경 — 실제 처리(§7.3)와 맞추고 언제까지인지 적음. 🔜 코드 반영 시 `noticeVersion` 2026-10-15. `00-19` 제5조와 같은 내용.

### 8.1 흐름

```text
월말 배치 ─▶ Settlement DRAFT 생성 (billable=true 리드 집계)
              │
              ├─▶ 운영자 검토 ─▶ ISSUED (파트너에게 발행)
              │                    │
              │                    ├─ 파트너 이의제기 ─▶ DISPUTED ─▶ 운영자 재판정 ─▶ ISSUED
              │                    └─ 이의 없음 / 기간 경과

```

* **이의제기 기간**을 정하고 그 안에 이의가 없으면 확정으로 간주한다(권장 7일). 기간이 없으면 분쟁이 무한정 열려 정산이 닫히지 않는다.
* `Settlement`에 `@@unique([partnerId, periodYm])`을 걸어 **같은 달 중복 발행을 DB가 막는다**.

### 8.2 수수료 계산 — 요율은 코드가 아니라 `CommissionPolicy` 레코드에서 읽는다

```text
리드 1건의 청구액 계산
  ① 리드의 기준 시점 t = Lead.createdAt
  ② t 시점에 유효한 정책을 찾는다
       partnerId = 이 리드의 파트너  →  있으면 특약 요율 (우선)
       partnerId = null             →  없으면 기본 요율
       조건: effectiveFrom <= t AND (effectiveTo IS NULL OR t < effectiveTo)
  ③ basis에 따라 금액 산출
  ④ 결과를 Lead.billedAmount + Lead.commissionPolicyId 에 **스냅샷으로 박는다**
```

**④가 핵심입니다.** 계산 결과만 저장하면 "왜 이 금액인지" 설명할 수 없고, 요율 ID만 저장하면 정책 레코드가 수정될 때 과거 금액이 흔들립니다. **둘 다** 남겨야 정산 분쟁에서 방어됩니다.

* 요율을 바꿀 때는 **기존 레코드를 수정하지 않는다.** 이전 레코드의 `effectiveTo`를 닫고 **새 레코드를 추가**한다. 과거 정산 재계산이 항상 같은 값을 내야 하기 때문이다.
* 같은 이유로 `CommissionPolicy`는 **삭제하지 않는다**. 잘못 넣었으면 즉시 `effectiveTo`로 닫는다.
* 산정 기준이 미확정이어도 **구조는 지금 만든다.** 확정되면 레코드 1건을 넣는 것으로 끝난다(→ §10-1).

## ⚠️ 9. 알려진 한계 — 전화 문의는 지금 구조로 증명되지 않는다

사장님 지시 ②는 "문의 **혹은** 견적 요청"이라고 하셨는데, **전화 문의는 현재 기술로 증명이 안 됩니다.**

| 단계 | 우리가 아는가 |
| :--- | :--- |
| 유저가 `tel:` 버튼을 눌렀다 | ✅ 이벤트 로그로 알 수 있음 |
| 실제로 통화가 연결됐다 | ❌ 브라우저는 통화 결과를 알려주지 않음 |
| 그 통화로 계약이 성사됐다 | ❌ 전혀 알 수 없음 |

즉 `CALL` 리드로 수수료를 청구하면 업체가 "그런 전화 온 적 없다"고 할 때 **반박할 물증이 우리에게 없습니다.** 그래서 §4.1에서 `CALL`을 기본 비청구로 둡니다.

**해결 경로는 050 안심번호(가상번호)입니다.** 시설마다 우리 명의의 050 번호를 발급해 착신 전환하면 통화 발생·시각·통화시간이 우리 로그에 남아 청구 근거가 됩니다. 부수 효과로 유족 번호가 업체에 직접 노출되지 않아 §7 개인정보 부담도 줄어듭니다. 다만 통신사 계약과 회선당 과금이 발생하므로 **파트너 수가 확보된 뒤 도입**하는 것이 합리적입니다. → 별도 검토 문서로 분리 제안.

그 전까지 실무적으로 유효한 방법은 **업체 문의 폼으로 유도**하는 것입니다. 제휴 시설에는 `[업체 문의]` 버튼을 눈에 띄게 배치합니다.

> **2026-08-11 정정**: 원안은 "전화는 보조 수단으로 둔다"였으나, 2026-08-10 개발자 지시로 **시설 카드에서 전화번호(`tel:` 링크) 노출 자체를 제거**했습니다(구현: walkthrough `2026-08-10 (5)`). 따라서 현재 `CALL` 리드를 만들 진입점이 화면에 없습니다 — `CALL` 유형은 050 도입 또는 전화 노출 재개 시를 대비해 스키마에만 남아 있는 상태입니다.

## ⚙️ 12. 설정·정책 관리 방침 (하드코딩 제거 원칙)

> 2026-08-10 확정. **"돈과 법에 닿는 값은 DB에 이력과 함께, 나머지 정책은 파일 한 곳에, 환경 차이만 `.env`에."**

### 12.1 왜 `.env`에 넣으면 안 되는가

`.env`의 원래 용도(Twelve-Factor App 3원칙)는 **"배포 환경마다 달라지는 것"**입니다. 수수료율은 개발 서버와 운영 서버에서 다를 이유가 없습니다. 환경 차이가 아니라 **경영 판단**입니다.

* `.env`에 정책을 넣으면 → *"스테이징만 수수료 10%"* 같은 환경별 값 어긋남 사고
* `.env`는 **변경 이력이 남지 않는다** → 정산 분쟁에서 "그때 요율이 얼마였는지" 증명 불가

### 12.2 3계층 배치

| 계층 | 담는 것 | 위치 | 이력 |
| :--- | :--- | :--- | :---: |
| **환경 설정** | DB 주소, OAuth 키, JWT 키, 지도 키 | `eobomDev/backend/.env` · `eobomDev/frontend/.env` | 남기지 않음(시크릿) |
| **운영 정책** | 이의제기 기간, 비제휴 수용, `leadNo` 접두어, 마스킹 주기 | **`eobomDev/backend/src/config/policy.ts` 단 한 곳** | git 커밋 이력 |
| **요율(돈)** | 수수료 기준·금액·정률, 파트너별 특약 | **DB `CommissionPolicy` + 유효기간** | 레코드 자체가 이력 |

**요율만 DB인 이유**는 §8.2에 있습니다 — 요약하면, 9월에 요율을 올린 뒤 8월 정산서를 재발행하면 **파일 방식은 9월 요율로 계산**해버립니다. 이미 청구한 금액과 어긋나고 증명할 방법이 없습니다. 요율은 값이 아니라 **기간이 붙은 레코드**여야 합니다. 부수 효과로 **파트너별 특약 요율**(초기 입점 할인, 대형 법인 협상가)이 구조 변경 없이 가능해집니다.

**나머지를 파일로 두는 이유**는 비용 대비 효용입니다. 이 값들은 과거 시점 재현이 필요 없고 1년에 몇 번 안 바뀌므로, 어드민 화면을 만들 값어치가 없습니다. 자주 바꾸게 되면 그때 DB로 옮기면 됩니다 — **파일 → DB는 쉽고, DB → 파일은 어렵습니다.**

### 12.3 `policy.ts` 형태

정본은 **`eobomDev/backend/src/config/policy.ts`의 `POLICY`** 입니다. 이 파일은 다른 도메인 값(전문가 상담 `consult`, 추모관 `memorial`, 보유기간 `retention` 등)도 담으므로, 아래는 **이 문서(01-05)에 해당하는 키만** 옮긴 것입니다(2026-10-08 코드 기준).

| 키 | 값 | 근거 절 |
| :--- | :--- | :--- |
| `lead.numberPrefix` | `'EB'` | §4.2 리드 번호 |
| `lead.acceptForNonPartner` | `true` → 🔄 **`false`로 변경 예정**(10-08 결정, §7.2 — 지금은 읽는 코드 없음) | §10-4 |
| `settlement.cycleMonths` | `1` | §10-3 |
| `settlement.disputeWindowDays` | `7` | §10-3 이의제기 기간 |
| `partner.autoApprove` | `false` | §3.2 자동승인 금지 |

`lead.requireLogin`(§10-2)과 `requirePhoneVerification`은 읽는 코드가 없어 값째 삭제됐습니다(2026-10-06·09-30).

### 12.4 지키는 규칙

1. **정책 값을 컴포넌트·컨트롤러에 직접 쓰지 않는다.** 반드시 `POLICY.*` 또는 정책 조회 함수를 거친다.
2. **기본값을 두 곳에 쓰지 않는다.** `POLICY`가 유일한 출처다. 호출부에서 `?? 7` 같은 폴백을 덧붙이면 정본이 둘이 된다.
3. **요율은 수정하지 않고 새 레코드를 추가한다** (§8.2).
4. **시크릿은 절대 `policy.ts`에 넣지 않는다** — 이 파일은 git에 커밋된다. 시크릿은 `.env` (→ `.harness/security.md` §3).

> 프론트엔드는 백엔드 `policy.ts`를 직접 import할 수 없습니다. 프론트 전용 상수는 `eobomDev/frontend/src/config.ts`에 모으고(예: 위치 폴백 `GEOLOCATION_FALLBACK`, 지도 로드 타임아웃 `KAKAO_MAP_LOAD_TIMEOUT_MS`), **양쪽에 같은 값이 필요하면 API 응답으로 내려보냅니다** — 두 파일에 같은 숫자를 적어두면 반드시 어긋납니다.

- 쪽 제목 줄 *"받은 업체 문의"* (총 n건) + 상태 고르기(전체 상태 · 접수 · 전달됨 · 응답완료 · 성사 · 무산 · 무효 처리, 모바일은 제목 아래 가득 폭).
- 목록 줄 = 문의 번호 · 상태 / 유형(업체 상담 · 상담신청 · 전화클릭) · 시설명 / 신청자 · 전화 / 남긴 글. 아래 쪽 넘김(`00-44` 쪽 넘김 부품: [이전] *"n / m 페이지"* [다음], 첫 쪽 [이전] 흐림).
- 상세 버튼(보조 왼쪽 · 주 오른쪽): 접수·전달됨 = [응답 완료로 표시] · 응답완료 = **[무산 처리] [성사 처리]**(코드는 성사 → 무산 순 → 8단계). 확인 창 없음(2026-10-19 개발자 "지금대로").
- **무산 처리 창** = 입력 창(`00-44` §7-6) — 윗글 *"#번호 · 시설명"* · 제목 *"무산 처리"* · 사유 고르기 4개(§4.3) · ④면 글 칸 · 안 고르면 창 안 오류 글(문구는 구현 때) · 주 버튼(위험색 아님).
- **상태 색**(`00-44` §6-4): 접수 · 전달됨 · 응답완료 = 갈색(처리할 차례) · 성사 = 완료 · 무산 · 무효 처리 = 보조.

### 14-5. 내 시설 정보 (판 6-6, 미구현 · 사진 결정 대기)

시설이 둘 이상이면 위에 **시설 고르기 탭**(모바일은 세로로 쌓음) — 한 곳씩 보인다. 시설 카드 안 세 구역:

| 구역 | 칸 | 하는 일 |
| :--- | :--- | :--- |
| 공공 데이터 기준 정보 | 시설명 · 종류 · 주소 · 전화 · 운영주체(5개, **위치 좌표는 넣지 않음**) | 보기만. 아래 한 줄 *"공공 데이터 기준 · 고치려면 문의"* — "문의"는 메일 글 링크(`config.ts` `CONTACT_EMAIL`, 지금 임시값) |
| 고칠 수 있는 정보 | **소개 글**(새 칸, 여러 줄) · **종교** · **수용 규모** · **부대시설**(체크 5개: 식당 · 매점 · 주차장 · 유족대기실 · 장애인편의시설 — `01-01` §5.2) · [취소][저장] | 저장하면 유족 화면(`01-01` §5)에 **바로 반영** |
| 사진 | 칸 자리만 + *"결정 대기"* 딱지 | 업로드·대표·삭제 버튼 없음(§6.1 주) |

- 🔴 **가격 글은 넣지 않는다**(2026-09-10 지시 · `01-01` §2.3). 공공 출처 칸은 사업자가 못 고친다 — 🔴 **공공 데이터를 다시 적재해도 사업자가 고친 칸(소개 글·종교·수용 규모·부대시설)을 덮지 않게** 한다(`import-facility-mohw.ts` — 지금은 주소·전화를 덮어씀).
- 🔵 **종교·수용 규모 입력 꼴**(Opus 권고 → ✅ 2026-10-21 개발자 확정): 캔버스는 종교 = 고르기(예시 *"종교 없음"*) · 수용 규모 = 숫자 칸 + *"명"* 인데, DB 값은 글(기본값 `전체 종교`·`전체 규모`, 비제휴 3행만 *"100~300명"* 꼴)이고 종교 선택지 목록이 어디에도 없다. → 종교 = 고르기 *"종교 없음 · 불교 · 개신교 · 천주교 · 원불교 · 기타"* · 수용 규모 = 숫자 칸(캔버스대로, *"N명"* 으로 저장). 기본값은 "아직 안 고침"으로 읽고 유족 화면에서 감춘다(`01-01` §5.2).
- **소개 글 규칙**(2026-10-19 개발자):
  - **저장 때 막는 것** — 전화번호 모양 · 홈페이지(링크) · 낱말 *"카톡·카카오·오픈채팅·kakao"* · `open.kakao.com`. 이어봄 밖 연락을 유도하면 수수료 근거가 사라진다(§9). 막힌 칸은 칸 오류 글(문구는 구현 때).
  - **운영자가 나중에 숨기는 것**(3개만) — ① 이어봄 밖 연락 유도(저장 때 못 거른 것) ② 가격·"최저가" 등 가격 글 ③ 다른 업체 비방·욕설. 사실과 다른 정보·시설과 무관한 광고는 숨김 사유가 아니다.
  - 반복하면 계정 정지 — 🔵 다만 **파트너 약관이 아직 없다**(docs 전체 검색 0건). ✅ 2026-10-21 개발자 확정: **지금은 이 절(금지 행위 = 위 3개 · 조치 = 숨김 → 반복 시 정지 §14-9)을 근거로 두고**, 파트너 약관은 제휴 혜택·수익 구조 재설계(`01-01` §3.3 · `pending-approvals` 사장님 결정 대기)와 함께 쓴다. 🟡 그 전엔 정지 근거가 약하다 → 공개 전 법률 자문 대상.
  - 🔵 숨긴 글(Opus 권고 → ✅ 확정): 유족 화면에서 소개 칸이 사라지고, 사업자 화면 소개 칸 위에 숨긴 사실·사유 한 줄(문구 구현 때). 사업자가 고쳐 저장하면 숨김이 풀리고 다시 바로 반영된다.
  - **운영자 숨김 화면 자리**(✅ 2026-10-21 개발자 확정): 운영자 *"전체 시설"*(§14-9)에서 시설을 고르면 **상세**(시설 정보 + 소개 글 + [숨기기](입력 창 · 위험 · 사유 필수) / 숨긴 시설은 [되돌리기](입력 창 · 주))가 열린다. 🔴 캔버스에 없어 **판 1장을 Sonnet이 추가**(묶음 3 운영자 판 옆, 6-16 "전체 시설"과 같은 틀) — 판이 생기면 배치는 판이 정본. ✅ 2026-10-21 판 추가 = 묶음 3 캔버스 **"6-16 전체 시설 상세"**(목록 380 + 상세, 숨긴 시설은 목록 줄·상세에 딱지 *"숨김됨"* 보조색 + 사유 한 줄). Opus 점검(10-21): ① 숨긴 뒤에도 운영자에겐 소개 글 본문이 보인다 — 채택 ② 🔄 [되돌리기]도 **사유 필수**(비면 창 안 오류 글) — 판은 "문서에 없음"으로 오류 글 없이 그렸으나, 추모관 내리기/되돌리기가 둘 다 사유 필수(`00-37` §4 #3)이고 API 행도 "숨김 / 되돌리기(+사유)"라 맞춘다. 기록 행위는 추모관과 같은 `HIDE`/`UNHIDE`(`00-37` §3.2) ③ 시설을 연동하지 않아 소개 글이 없는 시설은 소개 글 줄·[숨기기]를 그리지 않는다(구현 때). 전문가 소개 글은 지금 있는 [정보 수정](`02-03` §7.4)으로 처리한다(숨김 없음).

### 14-8. 상태·창 (판 6-9)
