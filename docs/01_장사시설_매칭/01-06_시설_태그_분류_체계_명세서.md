# 🏷️ 19. 시설 태그(#해시태그) 분류 체계 명세서

> **문서 성격**: `docs/17`과 같은 예외 패턴의 **구현 메모** — 개발자 요청(2026-08-10)으로 `[Claude:Sonnet]`이 직접 작성.
> 관리 파일은 `eobom/frontend/src/components/facility/tagCatalog.ts` 하나뿐이다. 이 문서는 그 파일이 왜 그렇게
> 생겼는지, 새 카테고리를 어떻게 추가하는지에 대한 배경 설명이고, **실제 정본은 코드(tagCatalog.ts)다.**

---

## 1. 문제 — 기존 `#해시태그`는 실제로 "태그"가 아니었다

`Facility.tags`는 클릭도 안 되고 필터에도 연결 안 된, 그냥 화면에 `#{tag}`로 뿌려지는 라벨이었다.

DB 감사 결과(2026-08-10, 로컬 dev DB 1,552건 기준):

| 값 | 건수 | 출처 |
|---|---|---|
| `사설` | 626 | 보건복지부 CSV `공-사설 구분` 컬럼 |
| `공설` | 322 | 보건복지부 CSV `공-사설 구분` 컬럼 |
| 그 외 약 50종 (예: "전남대병원", "24시 대기", "한강 조망" 등) | 각 1건 | 수기 시드(`seed-data/facilities.json`) 14건의 마케팅 문구 |

즉 **분류 가능한 값은 "공설"/"사설" 딱 하나뿐**이고, 나머지는 전부 그 시설 하나만을 위한 1회성 홍보 문구다.
카카오 API로 수집한 590건(전체의 38%)은 애초에 `tags`가 비어 있다(`[]`).

## 2. 설계 — 화이트리스트 방식

태그 문자열 전체를 "필터로 쓸 수 있는 것"으로 취급하지 않는다. 대신 `tagCatalog.ts`에 등록된 값만 클릭 가능한
필터로 승격시키고, 나머지는 지금처럼 클릭 안 되는 일반 라벨로 둔다.

```ts
// eobom/frontend/src/components/facility/tagCatalog.ts
export const TAG_CATALOG: Record<string, TagDefinition> = {
  공설: { category: '운영주체', label: '공설' },
  사설: { category: '운영주체', label: '사설' },
};
```

이렇게 한 이유:
- 마케팅 문구 50여 종을 억지로 카테고리에 끼워 맞추면 오히려 필터 UI가 지저분해진다(대부분 값이 후보 1개짜리 카테고리가 됨).
- "운영주체(공설/사설)"는 장례식장 도메인에서 가격 기대치에 직결되는, 실제로 필터링할 가치가 있는 정보다.
- 화이트리스트 밖 태그는 그대로 남아 있으므로 기존 화면(마케팅 문구 노출)은 전혀 깨지지 않는다 — 순수 추가 기능.

## 3. 구현

- **백엔드**(`facilityController.ts`): `buildWhere`에 범용 `tag` 쿼리파라미터 추가 — `Facility.tags`가 해당 값을
  포함하면(Prisma `has`) 매치. 화이트리스트를 백엔드가 알 필요는 없다(프론트가 클릭 가능하게 보여줄 값만 걸러줌).
- **프론트**(`FacilityPage.tsx`): 카드의 태그가 `TAG_CATALOG`에 있으면 `<button>`으로, 없으면 기존과 동일하게
  `<span>`으로 렌더링. 클릭하면 `tag` 쿼리파라미터로 목록을 다시 조회(서버사이드 페이지네이션과 동일한 방식으로
  기존 필터들과 동일 선상에서 동작). 같은 태그를 다시 클릭하면 해제(토글). 필터 바에는 활성 태그를 보여주는
  칩이 하나 뜨고, 거기서도 해제할 수 있다.

## 4. 새 카테고리를 추가하려면

1. `tagCatalog.ts`의 `TAG_CATALOG`에 항목을 추가한다. 이게 끝인 경우가 대부분이다 — 백엔드는 이미 범용 `tag`
   파라미터를 처리하므로 보통 손댈 필요가 없다.
2. 만약 그 값이 지금 DB에 아예 없다면(예: 새로운 분류축을 도입하는 경우), 데이터를 채우는 시딩/임포트 스크립트
   (`import-facility-csv.ts`, `sync-kakao-funeral.ts`, `seed-data/facilities.json`)도 함께 봐야 한다.
3. 한 필드에 여러 카테고리가 섞여 들어갈 수 있다는 점(`tags`가 배열이라 "공설" + "24시간 운영" 같은 태그가
   공존 가능)은 이미 설계에 반영돼 있다 — 카테고리별로 별도 필드를 만들지 않았다.

## 5. 검증

- 백엔드 `tsc --noEmit` 통과, 로컬 dev 서버 대상 `GET /api/facilities?tag=사설`(626건)/`?tag=공설`(322건) 실호출로 카운트가 DB 감사 결과와 정확히 일치함을 확인.
- 프론트 `tsc --noEmit` 통과. **브라우저 클릭 E2E는 미검증**(자동화 도구 없음) — 카드 태그 클릭 → 필터 적용 → 칩에서 해제까지 사용자가 직접 확인 필요.
