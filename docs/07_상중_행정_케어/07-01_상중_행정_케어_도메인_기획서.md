## 📌 1. 현재 상태 — 그리고 이 도메인만의 위험

### 1.1 지금 있는 것

`CareGuidePage.tsx`(SCR-006) + `mockData/careGuideTasks.json` **6개 항목 하드코딩**.
백엔드 없음, Prisma 모델 없음, 체크 상태는 로컬 `useState`라 **새로고침하면 사라집니다.**

| 라벨 | 항목 |
| :--- | :--- |
| D-Day | 사망진단서 (발급 10부 이상) |
| D-Day | 장례식장 계약 및 영정사진 전달 |
| D+3일 | 화장장 예약 및 운구차 배정 |
| D+14일 | 읍면동 주민센터 사망 신고 (1개월 내 미완료 시 과태료) |
| D+30일 | 정부24 안심상속 원스톱 서비스 |
| D+60일 | 상속세 신고 및 납부 (상속 개시일이 속하는 달의 말일부터 6개월 내) |

### 1.2 🔴 **가장 위험한 기한이 통째로 빠져 있습니다**

> **상속포기 · 한정승인 — 상속개시를 안 날로부터 3개월**(민법 제1019조 제1항)

목록에 **없습니다.** 이것이 이 도메인에서 발견한 가장 심각한 결함입니다.

**놓치면 무슨 일이 생기나**: 기간이 지나면 **단순승인으로 간주**되어, 고인의 채무가 상속인에게
그대로 넘어옵니다. 다른 기한을 놓치면 과태료나 가산세지만, **이 기한을 놓치면 유족이 남의 빚을
평생 집니다.** 되돌릴 수 없습니다.

지금 화면은 사망 후 할 일을 **알려주는 것처럼 보이면서** 이 항목을 빠뜨리고 있습니다.
**아무것도 안 보여주는 것보다 나쁩니다** — 유족은 "이어봄이 알려준 걸 다 했다"고 믿게 됩니다.

### 1.3 🔴 D+N 라벨과 법정 기한이 따로 놉니다

| 항목 | 화면 라벨 | 본문이 말하는 실제 기한 | 문제 |
| :--- | :--- | :--- | :--- |
| 사망 신고 | **D+14일** | "1개월 내" | 라벨과 본문 불일치 |
| 상속세 신고 | **D+60일** | "말일부터 6개월 내" | **라벨이 본문의 1/3** |
| 안심상속 원스톱 | D+30일 | (미표기) | 근거 불명 |

**D+N은 어디서 나온 숫자인지 근거가 없고, 본문과 모순됩니다.** 유족이 라벨만 보고 움직이면
상속세를 4개월 일찍 준비하는 건 무해하지만, **반대 방향의 오류(라벨이 실제보다 늦음)가 하나라도
있으면 기한을 놓칩니다.**

### 1.4 ✅ 이 도메인 고유의 위험 — 틀린 안내의 대가가 다릅니다

`04-01` §3.1은 플랫폼 안내가 낡으면 *"유족이 그대로 따라 하다가 시간을 버리는 실질적 피해"* 가
발생한다고 했습니다. **07은 그보다 한 단계 위입니다.**

| | Domain 04 (계정 정리) | **Domain 07 (이 문서)** |
| :--- | :--- | :--- |
| 정보가 틀렸을 때 | 절차를 다시 밟음 | **기한이 지나면 되돌릴 수 없음** |
| 최악의 결과 | 시간 낭비 | **채무 상속 · 가산세 · 과태료** |
| 정보 출처 | 각 플랫폼 고객센터 | **법령** (개정됨) |

> **✅ 결론: 이 도메인은 "정보 제공"이 아니라 "기한 관리"입니다.** 무엇을 하는지보다
> **언제까지 해야 하는지**가 본질이고, 그래서 정확성 요구가 플랫폼 전체에서 가장 높습니다.

## 🧭 2. 도메인 정의와 경계

### 2.1 ✅ 하는 일 / 하지 않는 일

| 하는 일 | 하지 않는 일 |
| :--- | :--- |
| 사망 이후 **법정 기한 안내 + 진행 추적** | 서류 **대리 작성·제출** |
| 관할 기관 · 준비물 · 신청 경로 안내 | **법률 자문** (→ Domain 02) |
| 기한 임박 **알림** | 상속 재산 분할 **판단** (→ Domain 02) |
| 어려운 항목은 **Domain 02 전문가 연결** | 세액 **계산·신고 대행** (→ Domain 02) |

**`04-01` §2.1과 같은 구조입니다** — 안내 + 진행 추적, 어려우면 02로 넘김. 플랫폼 일관성이 있습니다.

### 2.2 인접 도메인 경계

| 인접 | 겹치는 지점 | 정리 |
| :--- | :--- | :--- |
| **01** 장사시설 | "장례식장 계약"·"화장장 예약" 체크 항목 | ✅ **07은 체크만, 실행은 01로 이동**. 항목에 01 진입 링크를 답니다 |
| **02** 전문가 | 상속포기·상속세 — 안내는 07, 실행은 02 | ✅ §6의 수익 경로. **07의 체크리스트가 02의 최상위 유입구**입니다 |
| **04** 계정 정산 | 둘 다 "체크리스트 + 진행 추적" 구조 | 🟡 **시간축이 다름** — 07은 D+0~6개월(기한 있음), 04는 D+30 이후(기한 없음). §3.1 |
| **05** 추모관 | **모바일 부고장** | 🔴 **`00-13` §8-1 사장님 확정 대기** — §2.3 |

### 2.3 🔴 부고장 — 이 문서에서 확정하지 않습니다

`00-13`이 *"조문객이 받는 링크는 한 개여야 한다"*(§2.3)를 전제로 확정하고, 통합 여부를 사장님
확정 항목으로 올렸습니다. **이 문서는 그 결정을 기다립니다.**

- **통합(권고 C안)** → 부고장은 Domain 05로 이관. 07에는 §4 이후 내용만 남습니다.
- **분리** → 07이 부고장을 유지하되 **링크가 2개가 되는 문제**를 07 기획에서 다시 풀어야 합니다.

> 현재 목업의 부고장은 **입력 폼만 있고 전송이 `alert('[개발중]')`** 입니다. 어느 쪽으로 가든
> 지금 상태로는 쓸 수 없으므로, 결정 전까지 손대지 않는 것이 맞습니다.

## 👥 3. 사용자와 상황

### 3.1 ✅ 이 도메인은 유일하게 "기한"이 주인공입니다

| 도메인 | 시간축 | 지연의 대가 |
| :--- | :--- | :--- |
| 01 장사시설 | D+0~3 (극도로 긴급) | 장례를 못 치름 — 즉시 드러남 |
| **07 (이 문서)** | **D+0 ~ 6개월 (기한 있음)** | **조용히 지나감. 지나야 드러남** |
| 04 계정 정산 | D+30 이후 (기한 없음) | 없음 |
| 05 추모관 | 영구 | 없음 |

**07의 위험이 특이한 이유**: 01은 안 하면 바로 압니다. 04·05는 늦어도 손해가 없습니다.
**07만 "모르는 채로 지나가고, 지난 뒤에야 알게 됩니다."**

→ **알림이 기능이 아니라 이 도메인의 본체입니다.** 체크리스트를 보여주는 것만으로는 부족합니다.

### 3.2 진입 시나리오

| # | 누가 | 언제 | 심리 |
| :---: | :--- | :--- | :--- |
| 1 | 상주 | D+0~3, 장례 중 | 경황 없음. **행정을 볼 여력이 없음** |
| 2 | 상속인 | D+7~30, 장례 후 | "이제 뭘 해야 하지" — **이 도메인의 주 사용자** |
| 3 | 상속인 | D+60~90 | 상속포기 기한 임박 — **가장 중요한 순간** |

**시나리오 1에서 이 도메인을 보여주는 것은 무의미합니다.** 장례 중인 상주는 행정 절차를 읽지
않습니다. 대신 **그때 등록해두면 시나리오 2·3에서 알림이 오는 구조**여야 합니다.

## 🗄️ 4. 설계

### 4.1 ✅ 체크리스트는 코드가 아니라 데이터입니다

`04-01` §3.1과 같은 판단이며, **07에서는 근거가 더 강합니다** — 법령은 개정되고, 틀리면 §1.4의
대가를 치릅니다.

- `AdminTask` 마스터 테이블로 관리하고 **운영자가 화면에서 갱신**합니다.
- 각 항목은 **`lastVerifiedAt`(최종 확인일)을 필수 보유**하고 화면에 노출합니다.
- **`legalBasis`(근거 법령 조문)를 필수**로 둡니다 — `04-01`에 없는 07 전용 필드입니다.
  근거를 적을 수 없는 항목은 **레코드를 만들지 않습니다.**

> ⚠️ **초기 데이터 입력 시 주의**: §1.2 사례가 보여주듯 **기억이나 통념으로 채우면 안 됩니다.**
> 각 항목은 입력 시점에 **법령 원문(국가법령정보센터)과 소관 부처 안내를 직접 확인**해서
> 채워야 합니다. **빈 체크리스트가 틀린 체크리스트보다 낫습니다.**

### 4.2 ✅ `D+N` 라벨을 버리고 법정 기한을 정본으로 둡니다

§1.3의 모순은 **표시 단위를 잘못 골라서** 생겼습니다. 법정 기한은 "며칠"이 아니라
*"안 날로부터 3개월"*, *"속하는 달의 말일부터 6개월"* 처럼 **기준일 + 기간**으로 정의됩니다.

```
deadlineBaseType : DEATH_DATE(사망일) | KNEW_DATE(상속개시를 안 날) | MONTH_END(사망월 말일)
deadlineAmount   : 1 | 3 | 6 ...
deadlineUnit     : MONTH | DAY
```

화면에는 **계산된 실제 날짜**를 보여줍니다 — *"2026년 11월 30일까지"*. 유족이 D+N을 스스로
환산하게 만들면 안 됩니다.

### 4.3 🔴 기준일 문제 — 기술로 풀 수 없는 부분

**상속포기 기한의 기준일은 사망일이 아니라 "상속개시 있음을 안 날"** 입니다. 보통은 같지만
다를 수 있고, **그 판단은 법률 판단이라 이어봄이 할 수 없습니다.**

🟡 **권고**: 시스템은 **사망일 기준으로 계산해 보여주되**, 해당 항목에
*"기준일이 다를 수 있습니다. 정확한 판단은 전문가 상담이 필요합니다"* 를 **항상 병기**하고
Domain 02 연결을 답니다. **이어봄이 기한을 확정해주는 것처럼 보이면 안 됩니다.**

### 4.4 🟡 개인화 — 모든 유족이 모든 항목을 하지 않습니다

고인이 자동차가 없으면 이전등록 항목은 소음입니다. 다만 **초기에는 전체 목록 + 숨기기**로
충분합니다. 조건 분기를 처음부터 만들면 §4.1의 정보 품질 관리 부담만 커집니다.

> ⚠️ **"해당 없음"을 유족이 직접 고르게 하는 것도 위험**할 수 있습니다 — 잘 몰라서 껐다가
> 놓치는 경우. 껐어도 **기한 임박 시 1회는 알리는 것**이 안전합니다.

## 🗃️ 5. 🟡 데이터 모델 초안

```prisma
// 행정 절차 마스터 — 운영자 관리(§4.1). 04-01의 DigitalPlatform과 같은 성격
model AdminTask {
  id               String   @id @default(uuid())
  title            String
  guideSummary     String            // 유족이 읽는 본문
  agency           String?           // 관할 기관 (읍면동 주민센터 등)
  officialUrl      String?           // 정부24 등 공식 신청 경로
  requiredDocs     String[]          // 준비물
  legalBasis       String?           // ⭐ 근거 법령 조문 — 07 전용 필수 원칙(§4.1)
  deadlineBaseType String?           // DEATH_DATE | KNEW_DATE | MONTH_END (§4.2)
  deadlineAmount   Int?
  deadlineUnit     String?           // MONTH | DAY
  severity         String            // CRITICAL(되돌릴 수 없음) | NORMAL | INFO
  needsExpertHelp  Boolean @default(false)  // true면 Domain 02 연결(§6)
  isPublished      Boolean @default(false)
  lastVerifiedAt   DateTime?         // 최종 확인일 — 화면 노출(§4.1)
  sortOrder        Int     @default(0)
}

// 유족 개인의 진행 추적 — 04-01 DigitalCleanupItem과 같은 구조
model AdminTaskProgress {
  id         String   @id @default(uuid())
  userId     String            // FK → User (03-01 §2 원칙)
  deceasedId String?           // FK → Deceased (00-12 §2.1) — 부모 두 분을 구분하려면 필수
  taskId     String?           // FK → AdminTask (직접 추가면 null)
  customName String?
  status     String            // TODO | IN_PROGRESS | DONE | NOT_APPLICABLE
  dueDate    DateTime?         // §4.2로 계산된 실제 기한 (스냅샷)
  memo       String?
  @@unique([userId, deceasedId, taskId])
}
```

> 🔵 **`deceasedId`는 `00-12` §2.1의 `Deceased` 확정 후 붙습니다.** `04-01` §4.2가 같은 이유로
> 같은 미결을 안고 있습니다 — **두 도메인이 같은 대기 상태**입니다.

## 💰 6. ✅ 수익 구조 — 07은 Domain 02의 최상위 유입구입니다

`05-02` §9가 *"추모관만 수익 모델이 없다"* 고 했는데, **07도 직접 수익은 0입니다.**
다만 **05와 달리 07에는 자연스러운 수익 경로가 있습니다.**

| 체크 항목 | 유족의 상태 | 연결 |
| :--- | :--- | :--- |
| 상속포기·한정승인 | **"빚이 있는지 모르겠다"** | → **02 변호사** |
| 상속세 신고 | "얼마나 나오지" | → **02 세무사** (+ SCR-005 간이 계산기) |
| 각종 명의 이전 | "서류가 복잡하다" | → **02 행정사** |

**이것이 우연이 아닌 이유**: 07의 항목들은 대부분 **법률·세무 판단이 필요한 지점에서 막힙니다**(§4.3).
막히는 순간이 곧 상담 수요가 발생하는 순간이고, 그때 이미 유족은 **자기 상황을 화면에 입력해둔
상태**입니다. `02-03` §5.2의 `ConsultRequest`에 맥락을 프리필하면 됩니다.

- **새 과금 구조를 만들지 않습니다.** `02-03`의 인프라를 그대로 씁니다(`04-01` §3.4와 동일 원칙).
- 변호사법 가드레일은 `02-03` §3이 정본이며 여기서 새로 만들지 않습니다.

> 🟡 **그래서 07은 05보다 우선순위가 높다고 봅니다** — 구현 비용이 낮고(스토리지 불필요),
> 02로 이어지는 수익 경로가 있으며, `00-13` 결정을 기다리지 않아도 됩니다.

| **법령 정확성** | 모든 항목에 `legalBasis` + `lastVerifiedAt` 필수(§4.1) | 🟡 설계됨 |
| **기한 계산** | 기준일 유형별 계산 로직 단위 테스트 | 🟡 필요 |

| **면책 표시** | "법률 자문이 아님" 상시 노출(§4.3) | 🔴 문구 확정 필요 |

### 7.1 🔴 초기 데이터 구축은 외부 검증이 필요합니다

§1.2·§1.3이 보여준 것은 **내부에서 작성한 목록이 실제로 틀렸다**는 사실입니다.
초기 카탈로그는 **Domain 02의 제휴 행정사·세무사에게 검수받는 것**을 권고합니다 —
`02-01`의 전문가 풀을 활용하면 비용 없이 가능할 수 있습니다.
