## 🧭 3. ✅ 표시 순서 — "기한 순"이 아니라 "판단 순"

> 🔄 **2026-08-27 — 이 절은 `07-04` §2.2·§4의 재검토 대상입니다.** 사장님이 **D-Day 순
> 재정렬**을 지시하셨고, 검토 결과 **충돌이 아닙니다** — 아래가 반대한 것은 **순수 기한
> 오름차순**이고, `07-01` §4.2는 오히려 *"계산된 실제 날짜를 보여주라"* 고 지시해 두었습니다.
> **개정안: 시간축 5구간 → 구간 내 severity → 기한.** 아래 §3.1 배너는 그대로 유지되며,
> **여전히 미구현**입니다. 확정 전까지 이 절이 정본입니다.

**기한이 짧은 순으로 나열하면 안 됩니다.** 3개월(상속포기)보다 1개월(사망신고)이 먼저 오는데,
**실제로 유족이 먼저 알아야 할 것은 3개월 쪽**입니다. 그것이 되돌릴 수 없기 때문입니다.

**🟡 권고 정렬**: `severity` 우선 → 그 안에서 기한 순

```
1순위  CRITICAL  — 되돌릴 수 없는 것 (상속 승인·포기 4건 + 안심상속 + 24시간 제한 + 유언 검인)
2순위  NORMAL    — 과태료·가산세 (사망신고, 세금 3건, 자동차, 연금)
3순위  INFO      — 실무 편의 (명의변경, 계좌 정리)
```

### 3.1 ✅ 최상단 고정 배너

목록 위에 **항상 보이는 안내 하나**를 둡니다.

> **"고인에게 빚이 있을 수 있다면, 3개월 안에 결정해야 합니다."**
> 상속포기·한정승인 기한은 상속개시를 안 날로부터 3개월입니다. 지나면 채무를 그대로
> 물려받습니다. → [내용 보기] [전문가 상담]

**이유**: 유족은 체크리스트를 끝까지 스크롤하지 않습니다. `07-01` §3.2에 따르면 D+0~3의 상주는
행정을 볼 여력이 아예 없습니다. **한 줄이라도 남으려면 최상단이어야 합니다.**

> | **2** | `AdminTask` 모델 + 마이그레이션 + 시드 + 진행상태 저장 | 모델이 사주는 건 **체크 상태의 영속화**이지 정보의 정확성이 아닙니다. 지금도 체크는 React state라 새로고침하면 사라집니다 — 없던 기능이지 망가지는 기능이 아닙니다 |
>
> 아래 모델 설계는 **2단계의 정본**으로 그대로 유효합니다.

`07-01` §5의 `AdminTask` 모델을 그대로 씁니다. **§2의 22항목이 초기 시드 데이터**입니다.

```
severity        CRITICAL(7건) | NORMAL(11건) | INFO(4건)
deadlineBaseType DEATH_DATE | KNEW_DATE | MONTH_END | MIN_WAIT(신설 — §2.1-2)
```

> 🔴 **`MIN_WAIT` 신설 필요**: §2.1-2(화장 24시간)는 "언제까지"가 아니라 **"언제 이후에"** 입니다.
> `07-01` §4.2의 3가지 기준일 유형으로는 표현되지 않습니다.
