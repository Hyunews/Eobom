## 🎯 2. "카카오톡으로 전송"이 정확히 무엇인지부터 정합니다

**이 기획의 가장 중요한 판단입니다.** *"카카오톡으로 보낸다"* 는 말이 기술적으로 **세 가지 완전히
다른 것**을 가리키고, 비용·법적 책임·개인정보 수집 범위가 셋 다 다릅니다.

### 2.1 세 가지 방식 비교

| | **A. 카카오톡 공유**<br>(JavaScript SDK `Kakao.Share`) | **B. 알림톡 / 친구톡**<br>(카카오 비즈메시지) | **C. 메시지 API**<br>(`talk/memo`·`talk/friends`) |
| :--- | :--- | :--- | :--- |
| 발송 주체 | **유족 본인** (자기 카톡) | **이어봄** (발신 채널) | 이어봄 서버 |
| 수신자 지정 | 유족이 **카톡 피커에서 직접 선택** | **전화번호 명단 필요** | 카카오 친구 목록 |
| 이어봄이 갖는 연락처 | **0건** | 🔴 **조문객 전화번호 전량** | 🟡 카카오 친구 목록 접근 |
| 비용 | **무료** | **건당 과금** (대행사 경유) | 무료 |
| 사전 절차 | **웹 플랫폼 도메인 등록만** (검수 없음) | 비즈니스 채널 개설 + 발신프로필 + **템플릿 심사** | `talk_message` 동의항목 + **검수**(친구 발송은 비즈앱 요건) |
| 법적 지위 | 이어봄은 **도구 제공자** | 이어봄이 **발송자** — 정보통신망법 수신동의 주체 | 발송자 |
| **판정** | ✅ **채택** | ❌ **배제** | 🟡 **보조**(§2.4) |

### 2.2 ✅ A안 채택 — 이미 확정돼 있던 원칙입니다

`00-13` §2.1이 이 답을 이미 냈습니다:

> *"이어봄이 부고를 직접 발송하는 모델은 무겁습니다 — 대량 발송 비용, **수신자 연락처 수집**,
> 발송 주체로서의 법적 책임. **실제 배포는 유족이 카카오톡으로 합니다. 이어봄이 제공하는 것은
> '공유하기 버튼'까지입니다.**"*

**B안을 배제하는 근거는 비용이 아니라 세 가지입니다.**

1. **`00-13` §4.4 D안이 기각된 이유와 동일합니다.** 조문객 명단을 받는 순간 *"3분 안에 개설"*
   (`05-02` §3.2-1)이 깨지고, **부고가 초대장으로 바뀝니다** — 명단에 없는 지인은 조문할 방법이 없습니다.
2. **조문객 연락처라는 신규 개인정보가 발생합니다.** 정보 주체는 조문객인데 동의 주체는 유족입니다.
   `04-01` §3.3(증빙서류 미수집)·`05-01` §2.4(IP 해시만 보관)의 데이터 최소수집 기조와 정면으로 반대입니다.
3. ⚠️ **알림톡의 "정보성 메시지" 요건 충족이 불확실합니다.** 정보성 메시지는 통상 **수신자와
   발송 사업자 간 거래관계**를 전제하는데, **조문객은 이어봄과 아무 관계가 없습니다.**
   광고성으로 판정되면 사전 수신동의가 필요하고, 그러면 애초에 보낼 수 없습니다.
   → 🔴 **B안을 언젠가 검토한다면 이 판단이 선행돼야 합니다**(§10 #5).

### 2.3 ⚠️ 그래서 UI 문구를 바꿔야 합니다

**A안은 "전송"이 아니라 "공유"입니다.** 이어봄은 카톡 공유창을 띄워줄 뿐이고, 실제로 누구에게
갈지는 유족이 카톡 안에서 정합니다. 현재 문구 *"카카오톡 부고장 전송하기"* 는 **이어봄이 대신
보내준다는 오해**를 만듭니다 — 유족이 "보냈겠거니" 하고 창을 닫으면 **아무에게도 안 갑니다.**

| 현행 | 🟡 권고 |
| :--- | :--- |
| `카카오톡 부고장 전송하기` | **`카카오톡으로 부고 알리기`** |
| *"카카오톡으로 간편하게 전송하세요"* | *"카카오톡 대화방을 선택해 부고를 전하실 수 있습니다"* |

### 2.4 ✅ *"대화방 없는 개인에게 친구목록에서 골라 발송"* — A안에 이미 포함돼 있습니다

> 개발자 질문(2026-08-20): *"카카오톡 공유 + 대화방이 없는 상대(개인)에게는 내 친구목록에서
> 선택해서 발송하는 기능 가능한가."*

**A안이 띄우는 것은 "대화방 목록"이 아니라 카카오톡의 공유 대상 선택 화면**이며, 여기에
**채팅 탭과 친구 탭이 함께** 있습니다. 대화방이 없는 개인도 친구 탭에서 고르면 새 1:1 방이 생기며
전달됩니다. **별도 개발이 필요 없습니다.**

- ⚠️ **카카오톡 앱 UI이므로 버전에 따라 달라질 수 있습니다** → **Phase 1 실기기 검증 항목**으로
  편입합니다(§9): *"공유창 친구 탭에서 대화방 없는 개인 선택 → 부고 카드 도달"*.

#### 2.4-1 🔴 그런데 이걸 친구 목록 API로 직접 만들면 **부고 용도로는 작동하지 않습니다**

이어봄 화면 안에 친구 목록을 띄워 고르게 하려면 `GET /v1/api/talk/friends` + 친구 메시지
발송 API가 필요한데, 여기에 **결정적 제약**이 있습니다.

| 제약 | 내용 | 부고에 미치는 영향 |
| :--- | :--- | :--- |
| 🔴 **앱 사용 친구만 조회됨** | 친구 목록 API는 **해당 앱에 카카오 로그인한 적 있는 친구**만 반환하고, 친구 메시지 발송도 같은 범위로 제한됩니다 | **부고 수신자는 대부분 이어봄 회원이 아닙니다** — 회사 동료·친척·동창이 한 명도 안 뜹니다 |
| 동의항목 `friends` | 비즈 앱 전환 + 권한 신청·검수 | 착수 지연 |
| 동의항목 `talk_message` | 별도 동의 + 검수 | 〃 |

> **✅ 결론: 만들려는 기능을 카카오가 이미 공유창으로 제공하고 있고, 직접 만든 버전은 수신자를
> 이어봄 회원으로 제한하는 열화판이 됩니다.** 검수를 전부 통과해도 **친구 목록이 사실상 비어서
> 나오므로**, 비용을 들여 기능을 나쁘게 만드는 선택이 됩니다.
>
> ⚠️ **A안의 친구 탭은 회원 여부와 무관하게 내 카톡 친구 전체**를 보여줍니다. 이 차이가
> C안을 배제하는 실질적 근거입니다.

#### 2.4-2 🟡 그래도 남는 빈틈은 §7 폴백 사다리가 메웁니다

| 상황 | 수단 |
| :--- | :--- |
| 카톡을 안 쓰는 조문객 | **문자 보내기**(`sms:?body=`) — §7 4순위 |
| 이미 열어둔 대화방에 바로 붙여넣기 | **링크 복사** — §7 3순위, **상시 노출** |
| 내 카톡에 먼저 보관해두고 나중에 뿌리기 | `/v2/api/talk/memo/...`(나에게 보내기). ⚠️ `talk_message` 동의항목 필요 → **링크 복사로 대체 가능하므로 1차 제외** |

## 🖼️ 3. 미리보기 카드 — 여기가 진짜 기술적 난점입니다

`00-13` §7.2-2가 짚은 문제입니다:

> *"부고 링크는 카톡에 붙여넣는 순간 미리보기 카드가 떠야 합니다. **'○○○님 부고'라는 카드 없이
> 정체불명 URL만 뜨면 조문객이 클릭하지 않거나, 피싱으로 의심합니다.**"*

### 3.1 카드가 만들어지는 경로는 두 개고, 요구가 다릅니다

| | 경로 | 카드 내용의 출처 | OG 태그 필요? |
| :---: | :--- | :--- | :---: |
| **①** | 유족이 **이어봄 버튼**으로 공유 | **`Kakao.Share`에 코드로 직접 넘김** | ❌ **불필요** |
| **②** | 조문객이 **URL을 복사해 다른 방에 붙여넣음**(재전파) | **카카오 서버가 URL을 스크랩** | ⭕ **필수** |

> **✅ 이것이 이 문제의 실질적인 해법입니다.** ①은 OG 없이도 오늘 당장 완성도 높은 카드를 만들 수
> 있고, ②는 서버 렌더가 필요합니다. **①을 Phase 1, ②를 Phase 2로 나누면**
> 백엔드 배포(§1.2 #2)에 1차 전체가 묶이지 않습니다.
>
> ⚠️ 그리고 `00-13` §2.2가 말한 대로 **재전파는 예외가 아니라 기본 동작**입니다 —
> ②를 "나중 일"로 미룰 수는 있어도 **안 할 수는 없습니다.**

### 3.2 ① 공유 버튼 경로 — `Kakao.Share.sendDefault`

```ts
// 프론트: 사용자 클릭 핸들러 "안에서 동기적으로" 호출해야 팝업 차단에 걸리지 않는다.
Kakao.Share.sendDefault({
  objectType: 'feed',
  content: {
    title: `[부고] 故 ${deceasedName} 님`,
    description: `빈소: ${funeralHall} ${mourningRoom}\n발인: ${formatKST(funeralAt)}`,
    imageUrl: OBITUARY_CARD_IMAGE_URL,          // §3.3 — 영정이 아니다
    link: { mobileWebUrl: obituaryUrl, webUrl: obituaryUrl },
  },
  buttons: [{ title: '부고 보기', link: { mobileWebUrl: obituaryUrl, webUrl: obituaryUrl } }],
});
```

| 항목 | 내용 |
| :--- | :--- |
| SDK | `https://t1.kakaocdn.net/kakao_js_sdk/2.x/kakao.min.js` — **지도 SDK(`dapi.kakao.com`)와 별개 스크립트** |
| 키 | **JavaScript 키**. `VITE_KAKAO_MAP_KEY`와 **같은 앱이면 같은 키**지만 용도가 다르므로 `VITE_KAKAO_JS_KEY`로 분리 노출 |
| 사전 등록 | 카카오 디벨로퍼 > 내 애플리케이션 > **플랫폼 > Web 사이트 도메인** |
| 검수 | **불필요** (카카오 로그인·메시지 API와 달리 공유는 도메인 등록만으로 동작) |
| ⚠️ 제약 | `link.mobileWebUrl`·`webUrl`의 **도메인도 등록된 도메인이어야** 함 |

> 🔴 **`systems.md` §2의 함정이 그대로 재현됩니다.** 현재 등록 도메인은 **`localhost:5173` 포트
> 고정**이고, `https://eobom.vercel.app`은 등록돼 있지 않습니다(지도는 프로덕션에서 아직 안 쓰임).
> **부고장은 프로덕션이 본진이므로 Vercel 도메인 등록이 Phase 0의 필수 항목**입니다(§9).

### 3.3 ✅ 카드 이미지 — **1차 근조 이미지 고정, 스토리지 전환 후 영정 토글** (2026-08-20 개발자 확정)

> 개발자 질문: *"카드에 영정을 넣으면 문제가 생겨? 안 생긴다면 넣는 게 좋지 않을까?"*

**직관에는 근거가 있습니다.** §3이 카드를 중요하게 다룬 이유가 *"정체불명 URL만 뜨면 조문객이
클릭하지 않거나 피싱으로 의심한다"* 였고, **영정이 있는 카드가 그 문제를 가장 확실히 해결**합니다.
근조 이미지는 어느 부고든 똑같이 생겼습니다. 그래서 `00-13` §8-8의 *"영정 제외"* 권고를
**"영구 금지"가 아니라 "조건이 갖춰지기 전까지 보류"로 재해석**합니다.

| 1 | **이미지 스토리지 미전환**(`systems.md` §5·`05-01` §2.6) — 백엔드 로컬 디스크라 **재배포 시 전부 소실** | 🔴 **결정적** | **영정 URL이 죽으면 이미 뿌려진 카톡 카드가 일제히 깨집니다.** 넣고 말고가 아니라 **아직 못 여는 문**입니다 |
| 2 | **카카오 캐시 잔존** | 🟡 남음 | **부고장을 닫아도 캐시된 카드 이미지는 회수 불가.** 텍스트는 흘려보내도 얼굴은 즉시 알아보므로 재전파 시 무게가 다릅니다 |
| 3 | 법적 리스크 | ⚪ 낮음 | **개인정보보호법은 "살아 있는 개인"을 규율하므로 고인 사진 자체는 법상 개인정보가 아닙니다.** 유족 결합 정보·사자의 인격권 논점은 남으나, **유족이 직접 올려 직접 뿌리는** 구조라 약합니다 |

#### 3.3-1 ✅ 확정 — 두 단계로 나눕니다

| 시점 | 카드 이미지(`content.imageUrl`) |
| :--- | :--- |
| **1차 (Phase 1~2)** | **이어봄 공용 근조 이미지 1장 고정**(국화·근조 리본 등 중립 그래픽). `feed` 타입의 `imageUrl` 필수 요건을 채우면서, **스토리지 전환(`00-11`)을 기다리지 않아도 됩니다** — 정적 에셋 1장이라 `eobom/frontend/public/`에 넣고 서빙하면 끝입니다 |
| **스토리지 전환 후 (Phase 3+)** | 🟡 **`portraitShareEnabled` 토글** — 계좌와 동일 패턴. **기본 OFF**, 유족이 켜면 영정을 카드에 사용 |

> **토글로 두는 이유는 §8 #3(계좌)과 같습니다.** **영정이 널리 퍼지는 것을 원치 않는 유족이
> 분명히 있고, 그 판단은 유족이 해야 합니다.** 켤 때 고지 1줄을 붙입니다 —
> *"이 사진은 카카오 서버에 남으며, 부고장을 닫아도 회수할 수 없습니다."*
>
> ✅ **이 결정은 현재 일정에 영향이 없습니다.** 1차는 어차피 근조 이미지이고, 스토리지가 열리는
> 순간 토글만 켜면 됩니다. **`00-13` §8-8은 이로써 해소됩니다**(제외 → 조건부 허용).
>
> ⚠️ 대안으로 검토했던 `text` 타입(이미지 없음)은 **카드가 작고 존재감이 약해** 부고 신뢰도에
> 불리하므로 채택하지 않습니다.

> 로고가 박힌 카드를 유족이 단톡방에 뿌리면 **유족이 상업 서비스를 홍보하는 것처럼 보입니다.**

> 물려뒀습니다(`config.ts`). 근조 이미지 확보 즉시 교체해야 하며, **그때까지 실사용 금지**입니다.
>
#### 3.3-3 🔴 카드 이미지 URL은 **고정 공개 URL**이어야 합니다 (2026-08-20 신설)

현재 구현은 `OBITUARY_CARD_IMAGE_URL = ${window.location.origin}/...` 입니다. **이러면 로컬에서
카드 이미지가 뜨지 않습니다** — 카드를 만들 때 **카카오 서버가 `imageUrl`을 직접 가져가는데**,
`localhost`·사설 IP(`192.168.x.x`)는 카카오 쪽에서 접근할 수 없습니다.

```ts
// ❌ 현재 — 접속 환경에 따라 URL이 바뀌고, 로컬에서는 카카오가 못 가져감
export const OBITUARY_CARD_IMAGE_URL = `${window.location.origin}/eobom-logo-hd.png`;

// ✅ 고정 공개 URL — 어느 환경에서 보내든 같은 이미지이므로 고정이 맞다
export const OBITUARY_CARD_IMAGE_URL = 'https://eobom.vercel.app/obituary-card.png';
```

> ✅ **프론트는 이미 Vercel에 배포돼 있으므로, 근조 이미지를 `public/`에 넣고 배포하면
> 로컬 테스트에서도 카드 이미지가 정상 표시됩니다. 백엔드 배포를 기다릴 필요가 없습니다.**
>
> ⚠️ 도메인 등록(Phase 0 ⓐ)과는 **별개 문제**입니다. 등록은 *"이 페이지가 SDK를 쓸 수 있는가"* 이고,
> 이건 *"카카오 서버가 그 이미지 파일에 닿을 수 있는가"* 입니다.

#### 3.3-4 ⚠️ 미리보기와 실제 발송은 **같은 이미지**를 씁니다

| | 누가 그리나 | 이미지 출처 |
| :--- | :--- | :--- |
| 작성 폼의 "카카오톡 카드 미리보기" | **우리 코드**(카톡 카드를 흉내 낸 것) | `OBITUARY_CARD_IMAGE_URL` |
| 실제 카톡에 뜨는 카드 | **카카오** | `OBITUARY_CARD_IMAGE_URL` |

**둘 다 같은 상수 하나를 봅니다.** 근조 이미지는 미리보기 전용이 아니라 **실제 발송용**이며,
**미리보기에 로고가 보인다는 것은 실제로 보내도 로고가 나간다는 뜻**입니다.

### 3.4 ② 재전파 경로 — `/o/:slug`만 서버가 OG를 넣어 응답

현재 프론트는 Vite SPA라 `index.html`이 정적입니다 — **어느 부고를 열어도 카드가 똑같이 뜹니다.**
`00-13` §7.2-2가 *"백엔드가 `/o/*`·`/m/*` 두 경로만 렌더하는 것이 가장 싸다"* 고 했으나,
**현재 배포 구조에서는 재검토가 필요합니다.**

| 구현안 | 평가 |
| :--- | :--- |
| 백엔드(Render)가 `/o/:slug` HTML 셸 렌더 | 🟡 원 권고. 단 **프론트는 Vercel·백엔드는 Render라 도메인이 갈립니다** — 부고 링크가 `onrender.com`으로 나가면 신뢰도·일관성이 무너짐 |
| Vercel **rewrite로 `/o/*`를 백엔드로 프록시** | 🟡 도메인은 지켜지나 백엔드 배포에 완전히 종속 |
| 🟡 **Vercel 서버리스 함수 1개**가 백엔드 API를 호출해 OG 주입 셸 반환 | ✅ **권고.** 도메인 일관 + 프론트 배포 파이프라인 안에서 완결. `vercel.json` rewrite 1줄 + 함수 1개 |

```
GET https://eobom.vercel.app/o/{slug}
  → vercel.json rewrite → /api/obituary-og?slug={slug}
  → 함수가 백엔드 GET /api/obituaries/{slug} 호출 (공개 화이트리스트 응답)
  → index.html + <meta property="og:*"> 주입 + <meta name="robots" content="noindex"> 반환
  → 브라우저는 그대로 SPA로 하이드레이트되어 /o/:slug 라우트를 렌더
```

- 크롤러 UA 분기는 **하지 않습니다.** 항상 같은 셸을 주는 편이 단순하고, 분기 실패 시 카드가 깨집니다.
- ⚠️ **`noindex`와 카톡 스크랩이 충돌하는지 실측 검증이 필요합니다.** 검색 색인은 막아야 하고
  (`05-01` §7.1) 카톡 카드는 떠야 하는데, 카카오 스크랩이 `meta robots`를 어떻게 취급하는지는
  **문서가 아니라 실기기로 확인**해야 합니다(§9 Phase 2 판정 기준).
- ⚠️ **카카오는 스크랩 결과를 캐시합니다.** 오타를 고쳐도 카드가 안 바뀝니다.
  카카오 디벨로퍼의 캐시 초기화 도구 사용법을 **운영 절차로 문서화**해야 합니다.

### 4.1 `Deceased` — 07이 필요한 최소 범위만

```prisma
// 고인(00-12 §2.1). 07 착수의 전제이므로 여기서 최소 범위로 도입한다.
// ⚠️ DeathVerification·BereavedRelation·PreDeathDirective는 이번 범위 밖 —
//    00-12가 확정될 때 이 모델에 붙는다(관계 필드만 미리 열어두지 않는다).
model Deceased {
  id           String    @id @default(uuid())
  userId       String?   @unique   // 이어봄 회원이었으면 연결. 비회원 고인이면 null(케이스 B)
  name         String
  birthDate    DateTime?           // ⚠️ 공개 응답에서 제외(05-01 §4.1과 동일 사상)
  deathDate    DateTime?
  registeredBy String              // 등록한 User — 자칭 유족일 수 있음(00-12 §2.3)

```

> 🔴 **`Memorial`에 `deceasedId` FK를 추가하는 마이그레이션이 동반됩니다.** 기존 `Memorial`은
> `deceasedName`을 문자열로 들고 있습니다. **`systems.md` §4 경고 — 스키마 변경 전 `pg_dump` 필수**
> (2026-08-05 데이터 유실 사고 이력). 기존 레코드는 `deceasedName` → `Deceased` 역생성 후 연결합니다.

### 4.2 `Obituary` — 07 소유

```prisma
// 부고장 — Domain 07 소유. 단명(장례 전후), 배포되는 유일한 링크(00-13 §4.5)
model Obituary {
  id              String   @id @default(uuid())
  slug            String   @unique   // 배포용 추측 불가 토큰(§4.4)
  deceasedId      String
  deceased        Deceased @relation(fields: [deceasedId], references: [id])
  memorialId      String   @unique   // 개설 시 함께 생성된 추모관(00-13 §4.5 · 권고 #3)
  memorial        Memorial @relation(fields: [memorialId], references: [id])
  createdByUserId String              // 개설자(상주)
  createdByUser   User     @relation(fields: [createdByUserId], references: [id])

  // 장례 실무 정보 — 05가 아니라 여기 있다(00-13 §4.5-2)
  funeralHall     String?             // 빈소(장례식장명)
  mourningRoom    String?             // 호실
  funeralHallAddr String?             // 빈소 주소 — 지도/길찾기용
  facilityId      String?             // FK → Facility. 목록에서 고른 경우만(01 연결)
  coffinAt        DateTime?           // 입관 — 화면에서는 접어둠(§6.2)
  funeralAt       DateTime            // 발인 — ✅ 2026-08-20 필수 확정(§6.2-1). 수명 계산 기준(§6.2-4)
  burialSite      String?             // 장지 — 화면에서는 접어둠(§6.2)

  // 연락처 — ✅ 2026-08-20 개발자 지정. 입력하면 랜딩에 노출(별도 토글 없음, §6.2-2)
  // ⚠️ 암호화하지 않는다: 입력=공개가 전제라 DB값과 공개값이 항상 같다. 계좌(기본 OFF라
  //    꺼진 값이 DB에 쌓임)와 달리 암호화가 막아주는 위협이 없다 — 보안 연극을 만들지 않는다.
  contactPhone    String?

  // 조의금 계좌 — ✅ 2026-08-20 개발자 확정: 기능 도입. 기본 OFF + 유족 토글(§8 #3)
  accountEnabled  Boolean  @default(false)
  accountBankCode String?
  accountNumberEnc String?            // AES-256-GCM. utils/crypto.ts encryptField 재사용
  accountHolder   String?

  // 카톡 카드에 영정 사용 — ✅ 2026-08-20 확정(§3.3-1). Phase 1~2에는 화면에 노출하지 않는다.
  // ⚠️ 이미지 스토리지 전환(00-11) 전까지 true로 켤 수 없다 — 켜면 재배포 시 카드가 깨진다.
  portraitShareEnabled Boolean @default(false)

  // 게이트 — 05-01 §2.3을 07이 승계(00-13 §4.5-3)
  falseReportAgreedAt DateTime         // 허위 개설 고지 동의 시각
  resharedNoticeAckAt DateTime         // 재전파 고지 확인 시각(00-13 §8-6)

  shareCount      Int      @default(0) // 집계값만. 수신자 식별 정보는 저장하지 않음
  viewCount       Int      @default(0)

  // 카드 반영 필드(고인 성함·빈소·호실·발인)가 마지막으로 바뀐 시각(§5.4-2).
  // ⚠️ updatedAt으로 대체할 수 없다 — 연락처만 고쳐도 updatedAt은 바뀌므로
  //    "다시 공유하세요" 안내가 잘못 뜬다. 카드 반영 필드에서만 갱신한다.
  cardFieldsUpdatedAt DateTime?
  closedAt        DateTime?
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt

  mourners        ObituaryMourner[]

  @@index([createdByUserId])

// 상주·유족 — 부고는 관계별로 여러 명을 나란히 적는 것이 관행이다(§4.3)
model ObituaryMourner {
  id           String   @id @default(uuid())
  obituaryId   String
  obituary     Obituary @relation(fields: [obituaryId], references: [id], onDelete: Cascade)
  relationship String            // 배우자 | 장남 | 차녀 | 사위 | 며느리 ...
  name         String
  isChief      Boolean  @default(false)  // 상주 표시
  sortOrder    Int      @default(0)

  @@index([obituaryId, sortOrder])
}
```

### 4.3 왜 상주를 별도 테이블로 두나

현행 목업은 *"상주: 홍상주"* 한 줄입니다. **실제 부고는 관계별로 여러 명을 나란히 적습니다** —
배우자·장남·차녀·사위·며느리. 문자열 1필드로 두면 **정렬·표기 규칙을 화면에서 문자열 파싱으로
풀어야 하고, 그러면 못 고칩니다.** 테이블 1개면 미리보기·랜딩·카톡 카드가 같은 데이터를 각자
포맷할 수 있습니다.

> 🟡 **다만 입력 부담이 늘면 안 됩니다**(§6.2 — 3분 제약). **필수는 상주 1명뿐**이고,
> 나머지는 *"유족 추가"* 로 선택입니다.

### 4.4 🔴 slug — 두 링크가 서로 유추 가능하면 안 됩니다

`00-13` §4.5-3 #3의 요구입니다.

```ts
// memorialController.ts의 generateSlug와 같은 함수를 쓰되, 값을 파생시키지 않는다.
const generateObituarySlug = () => crypto.randomBytes(16).toString('hex');
```

- ❌ **금지**: `memorial.slug`를 해시·치환·접두어로 변형해 `obituary.slug`를 만드는 것.
  한쪽을 알면 다른 쪽이 뚫립니다.
- ✅ 두 slug는 **각각 독립된 `randomBytes(16)`** 입니다. 트랜잭션 안에서 따로 두 번 뽑습니다.
- ✅ URL은 `/o/{slug}`(부고장)·`/m/{slug}`(추모관) — **`/memorial/1` 같은 순번 금지**(`05-01` §2.2).

### 5.1 엔드포인트

### 5.2 개설 트랜잭션 — E안의 핵심

```
POST /api/obituaries
  ├ 1. falseReportAgreed !== true       → 400 (05-01 §2.3-4 승계)
  ├ 2. resharedNoticeAck !== true       → 400 (00-13 §8-6)
  ├ 3. deceasedName·상주·빈소·funeralAt 없음 → 400 (필수 4개, §6.2)
  └ prisma.$transaction([
       Deceased 생성   (registeredBy = 로그인 유저)
       Memorial 생성   (deceasedId 연결, visibility='LINK', falseReportAgreedAt 기록, slug A)
       Obituary 생성   (deceasedId·memorialId 연결, slug B)
     ])
응답: { obituarySlug, memorialSlug, obituaryUrl, memorialUrl }
```

> ✅ **`00-13` §7.3 #3 그대로입니다** — *"07 부고장 개설 시 추모관 자동 동반 생성(빈 상태)"*.
> 유족은 **한 번만 만들고, 한 개만 뿌립니다.**
>
> 🔴 **추모관 개설 게이트가 07 화면으로 옮겨오는 것이 여기서 실행됩니다**(`00-13` §4.5-3 #2).
> 이 검증을 빼면 **`POST /api/memorials`의 고지 동의를 우회하는 뒷문**이 생깁니다.
> ⚠️ 기존 `createMemorial` 컨트롤러를 재사용하지 말고, **동의 검증 로직을 공용 함수로 추출**해
> 두 경로가 같은 규칙을 타게 합니다.

### 5.3 공개 응답 화이트리스트

`05-01` §4.1·`memorialController.getMemorialBySlug`와 **같은 사상**입니다 — 구조분해로 필요한
필드만 뽑아 응답합니다.

| 포함 | 제외 |
| :--- | :--- |
| 고인 성명 · 사망일 | ❌ **고인 생년월일** (`05-01` §4.1 사상) |
| 빈소 · 호실 · 주소 · 입관 · 발인 · 장지 | ❌ **개설자 `userId`·이메일** |
| 상주·유족 성명 + 관계 | ❌ `deceasedId`·`memorialId` 등 내부 PK |
| **연락처** — 입력돼 있으면 그대로 포함 (✅ §10 #3 확정, §6.2-3) | ❌ `portraitUrl` — **Phase 3+ `portraitShareEnabled`가 켜졌을 때만**(§3.3-1) |
| 추모관 링크(`memorialSlug`) | — |
| 조의금 계좌 — **`accountEnabled === true`일 때만 복호화해 포함** | ❌ 꺼져 있으면 **필드 자체를 응답에 넣지 않음**(`null`도 넣지 않음) |

- `closedAt`이 있거나 slug가 없으면 **404** — 존재를 숨깁니다(`05-01` §4.1, `00-13` §7.3 #5).
- ⚠️ **404 응답 본문·상태코드는 두 경우가 완전히 동일해야** 합니다. 미묘한 차이가 존재 탐지 경로가 됩니다.

### 5.4 ✅ "노출"의 정의와 수정 반영 범위 (2026-08-20 개발자 질문)

> 개발자 질문: *"노출이라는 게 사용자가 웹에 접속했을 때, 한번 입력하고 남아있는 걸 의미하나."*

**화면이 둘이고 "노출"은 항상 두 번째를 가리킵니다.**

| | 화면 | 보는 사람 | 역할 |
| :--- | :--- | :--- | :--- |
| **입력** | `/obituary` 작성 폼 | **유족만** | 값을 채우는 곳 |
| **노출** | `/o/{slug}` 랜딩 | **카톡 링크를 받은 조문객** | 그 줄이 그려지느냐 |

- 입력값은 **서버 DB의 `Obituary` 레코드**에 저장됩니다 — 브라우저 로컬이 아닙니다.
  유족이 기기를 바꾸거나 재로그인해도 남아 있고, **마이페이지에서 언제든 수정**할 수 있습니다.
- 링크(`slug`)는 그대로이므로 **수정하면 조문객이 보는 페이지도 즉시 바뀝니다.**
  `PATCH`가 장식이 아닌 이유입니다 — **빈소 이전·발인 시각 조정은 실제로 자주 일어납니다.**

#### 5.4-1 🔴 그런데 **이미 뿌려진 카톡 카드는 바뀌지 않습니다**

카드는 **공유한 시점의 스냅샷**입니다. 유족이 빈소를 고쳐도 단톡방에 올라간 카드에는 **옛 빈소가
그대로 남습니다.** 링크를 누르면 맞는 정보가 나오지만, **카드만 보고 안 누른 사람은 틀린 곳으로
갑니다.** 하필 §3.2 카드 설명란에 넣기로 한 **빈소·발인이 가장 자주 바뀌는 정보**입니다.

| 대응안 | 평가 |
| :--- | :--- |
| 카드에서 빈소·발인을 빼고 성명만 남김 | ❌ 카드가 *"[부고] 故 ○○○ 님"* 만 남아 **§3에서 카드를 중요하게 다룬 이유가 사라집니다** |
| **정보는 두되 갱신 안내로 푼다** | ✅ **2026-08-20 개발자 확정** — §5.4-2 |

> ⚠️ 이것은 §3.4의 **카카오 스크랩 캐시와는 다른 문제**입니다. 스크랩 캐시는 *URL을 붙여넣어
> 생긴 카드*의 문제이고, 여기는 *공유 버튼으로 보낸 카드*가 애초에 그 시점 값으로 굳는 것입니다.
> **캐시 초기화로 해결되지 않습니다** — 이미 전송된 메시지이기 때문입니다.

#### 5.4-2 ✅ 책임 경계 — 링크는 자동, 카드는 유족이 다시 보냄 (2026-08-20 확정)

> 개발자 지시: *"링크의 경우에는 자동 수정 good. 카톡 메시지 같은 경우에는 수정 사항 발생 시
> 이용자가 다시 보내든지 하는 방식으로 알아서 해야 함."*

| 대상 | 갱신 방식 | 주체 |
| :--- | :--- | :--- |
| **`/o/{slug}` 페이지** | **자동** — `PATCH` 즉시 반영, slug 불변 | 시스템 |
| **이미 보낸 카톡 카드** | **재공유** — 유족이 다시 보냄 | **유족** |

> **이 경계는 구조적으로 강제된 것이기도 합니다.** 이어봄이 정정 메시지를 대신 보내려면
> B안(직접 발송, §2.1)이어야 하는데, A안에서 **이미 나간 메시지는 유족의 카톡 안에 있습니다.**
> 즉 *"알아서"* 가 아니라 **그 방법밖에 없습니다.**
>
> ✅ **이어봄의 책임은 "알려주는 데까지"입니다.** 유족이 수정 사실을 모르면 조치할 수 없으므로,
> **안내를 띄우는 것까지는 시스템의 의무**입니다.

**시스템이 하는 일 2가지:**

1. **카드 반영 필드가 수정되면** *"이미 보낸 카드에는 반영되지 않습니다. 다시 공유해 주세요"*
   안내 + **그 자리에 공유 버튼**을 노출합니다.
2. **랜딩 상단에 최종 수정 시각**을 표시합니다 — 조문객 쪽 방어선입니다.

##### 🔴 안내를 띄우는 필드 목록 (구현자가 판단하지 않습니다)

**카드에 실리는 필드가 바뀔 때만** 띄웁니다. 전부 띄우면 노이즈가 되고,
**연락처를 고쳤는데 *"다시 공유하세요"* 가 뜨면 유족은 뭐가 잘못됐나 싶어 불필요하게 또 뿌립니다.**

| 필드 | 카드 반영 | 수정 시 안내 |
| :--- | :---: | :---: |
| 고인 성함 | ⭕ `title` | **띄움** |
| 빈소 위치 · 호실 | ⭕ `description` | **띄움** |
| 발인 일시 | ⭕ `description` | **띄움** |
| 연락처 | ❌ | 안 띄움 |
| 마음 전하실 곳(계좌) | ❌ | 안 띄움 |
| 입관 · 장지 · 유족 추가 · 별세 일시 | ❌ | 안 띄움 |

##### ✅ 재공유 카드에 `·변경` 표기 (2026-08-20 개발자 확정)

다시 보내면 단톡방에 **부고 카드가 두 장** 쌓입니다. 시간순으로 아래가 최신이지만
**대화가 바쁜 방에서는 조문객이 어느 게 맞는지 헷갈립니다.**

```
[부고] 故 ○○○ 님              ← 처음 보낸 것
[부고·변경] 故 ○○○ 님          ← 다시 보낸 것
```

- 카드 반영 필드에 **수정 이력이 있으면**(`cardFieldsUpdatedAt != null`, §4.2) `title`에 `·변경`을 붙입니다.
- **카드 제목 생성 함수의 조건문 하나**입니다 — §3.2·§6.2 미리보기와 같은 포맷터를 쓰므로
  세 곳이 자동으로 일치합니다.

| 구분 | 항목 | 비고 |
| :--- | :--- | :--- |
| **필수 (4)** | 고인 성함 · 상주 성함 · 빈소 위치 · **발인 일시** | 개발자 지정 + **발인은 2026-08-20 추가 승인**(§6.2-1) |

#### 6.2-1 ✅ 발인 일시 — **필수 항목으로 확정** (2026-08-20 개발자 승인)

| | |
| :--- | :--- |
| **조문객 관점** | 빈소 주소만 있고 발인이 없으면 **"언제까지 가면 되는지"를 모릅니다.** 카톡 링크는 며칠씩 떠돌기 때문에, 발인이 없으면 **이미 끝난 장례식에 찾아가는 사람이 생깁니다.** 실제 부고에서 빈소와 발인은 한 쌍입니다 |
| **시스템 관점** | **부고장 수명(§10 #4)을 판단할 유일한 기준**입니다. 발인이 없으면 이 페이지를 언제 닫아야 할지 시스템이 알 방법이 없습니다 |
| **비용** | `Obituary.funeralAt`에 이미 자리가 있습니다(§4.2). 입력 1회 |

> 🔵 **발인이 필수가 되면서 §10 #4(부고장 수명)의 선택지가 바뀝니다** → §6.2-4.

**별세 일시**는 승인 대상이 아니었으므로 **선택(접어둠)으로 둡니다.** 부고 첫 문장의 관행이고
(*"8월 20일 별세하셨기에"*) 랜딩의 `故 ○○○ (~2026.08.20)` 표기에 쓰이지만, 없어도 `故 ○○○`로
성립합니다. `Deceased.deathDate`에 자리는 이미 있으므로 필요해지면 펼치기만 하면 됩니다.

> 🟡 **호실·입관·장지·유족 추가는 스키마에는 남기되 기본 화면에서 접어둡니다.** 개발자 지시
> (*"추후에 추가할 것이 생기면 그때 추가"*)를 따르되, **필드를 지우면 나중에 마이그레이션이
> 필요해지므로** 화면에서만 숨깁니다.

#### 6.2-2 ✅ "마음 전하실 곳"은 체크가 아니라 **토글**입니다

개발자 질문(*"토글 혹은 체크? 필요함"*)에 대한 답. **토글이 필요한 진짜 이유는 켜고 끄기가
아니라 "경고를 보여줄 자리"를 만드는 것**입니다.

| 항목 | 방식 | 이유 |
| :--- | :--- | :--- |
| **연락처** | **입력하면 노출** (별도 토글 없음) | **입력 여부가 곧 토글**입니다. 비워두면 그 줄 자체가 랜딩에 안 나옵니다 |
| **마음 전하실 곳** | **명시적 토글, 기본 OFF** | 켜는 순간 *"이 계좌번호는 부고장을 받은 분이 다시 공유할 수 있습니다"* 를 띄웁니다. **입력=노출 방식에는 이 경고를 붙일 자리가 없습니다** — `00-13` §6.3이 *"유족이 명시적으로 켤 때만"* 이라 한 것이 이 뜻입니다 |

#### 6.2-3 🔴 연락처 — 완화책처럼 보이지만 아닌 것

**`[전화 걸기]` 버튼(`tel:`)으로 감싸도 번호는 페이지 소스에 그대로 남습니다.** 길게 누르면
보이고 소스 보기로도 보입니다. **표시상의 정리이지 보호가 아닙니다** — 보호로 착각하면 안 됩니다.

실제로 작동하는 완화는 **하나뿐**입니다:

> ✅ **부고장을 닫으면 연락처도 함께 404가 됩니다.** 그래서 §10 #4를 "수동 종료"로 두되,
> **마이페이지에 종료 버튼을 눈에 띄게** 배치합니다(Phase 3 #9).

- ⚠️ 입력란 아래 안내 1줄 상시 표시: *"입력하신 번호는 부고장을 받은 모든 분에게 보입니다."*

##### 🔴 연락처는 **랜딩에만 싣고 카톡 카드에는 넣지 않습니다** (2026-08-20 신설)

카드 `description`은 빈소·발인까지입니다. **연락처를 카드에 박으면 위 완화책이 통째로 무력화됩니다** —
부고장을 닫으면 랜딩은 404가 되지만 **단톡방에 남은 카드의 번호는 회수할 방법이 없습니다**(§5.4-1).
계좌도 같은 이유로 카드에 넣지 않습니다.

> **즉 "카드는 문 앞까지, 민감 정보는 문 안에서"** 가 원칙입니다. 카드는 *누구의 부고이고 어디서
> 언제인지*까지만 알리고, **연락처·계좌는 링크를 눌러 들어온 사람에게만** 보입니다.

#### 6.2-4 🔵 발인이 필수가 되면서 §10 #4(부고장 수명)의 권고가 바뀝니다

§6.2-3에서 *"연락처·계좌 노출의 실효 완화는 부고장 종료 하나뿐"* 이라고 했는데, **수동 종료는
유족이 잊으면 작동하지 않습니다.** 사별 직후에 *"부고장을 닫아야지"* 를 기억할 유족은 많지 않고,
그러면 **연락처와 계좌가 실린 페이지가 무기한 살아 있게** 됩니다.

**발인 일시가 필수가 되면서 이 문제가 풀립니다.**

| | 이전 권고 | 🟡 **갱신 권고** |
| :--- | :--- | :--- |
| 종료 방식 | 수동 종료만 | **발인 + N일 자동 종료 + 유족의 수동 조기 종료** |
| 근거 | 발인 입력이 선택이라 자동 계산 불가 | **발인이 필수라 계산 기준이 항상 존재** |

- ✅ **N = 3일** (2026-08-20 개발자 확정). **`발인일 + 3일 자정`에 자동 종료**됩니다.
  발인 직후 끊으면 늦게 소식을 접한 조문객이 정보를 못 보므로 여유를 둔 값입니다.
- 종료돼도 **추모관은 계속 삽니다** — 부고장만 404가 되고, 이미 추모관에 들어온 사람은 영향 없습니다.
- ⚠️ 종료 임박 시 유족에게 알리지 않습니다 — **알림은 이 도메인의 본체가 아니고**(`07-01` §3.1은
  체크리스트 얘기입니다), 부고장은 원래 단명해야 정상입니다.

> ⚠️ **이것은 `00-13` §4.3의 "phase 전환 트리거" 문제를 다시 여는 것이 아닙니다.**
> 거기서 문제였던 것은 **하나의 레코드가 성격을 바꾸는 사건**(`OBITUARY`→`MEMORIAL`)이었고,
> E안은 레코드를 둘로 나눠 그 사건을 없앴습니다(§4.5-2). **여기서 말하는 것은 부고장 레코드
> 하나의 만료일 뿐이며, 추모관은 처음부터 따로 살아 있습니다.** 전환은 여전히 없습니다.
- 미리보기는 **입력과 동시에 갱신**되며, **실제 카톡 카드와 같은 문구**를 씁니다(§3.2와 같은 포맷터 공용).
- 빈소는 🟡 **`Facility` 검색 연동 권고**(1,552건 실데이터 적재됨) — 고르면 주소·좌표가 자동으로 채워져
  랜딩의 길찾기가 살아납니다. 미검색 시 자유 입력.

## 🪜 7. 공유가 실패할 때 — 폴백 사다리

**카카오 공유는 생각보다 자주 실패합니다.** 유족이 부고를 못 보내는 것은 이 서비스에서 **가장
치명적인 실패**이므로, 실패를 전제로 설계합니다.

| 순위 | 수단 | 발동 조건 |
| :---: | :--- | :--- |
| 1 | **`Kakao.Share.sendDefault`** | SDK 로드 성공 + `Kakao.isInitialized()` |
| 2 | **`navigator.share`** (Web Share API) | SDK 실패. 모바일에서 OS 공유 시트 → 카톡 선택 가능 |
| 3 | **링크 복사** (`navigator.clipboard`) | 위 둘 실패. **PC·인앱브라우저의 실질적 기본값** |
| 4 | **문자로 보내기** (`sms:?body=`) | 카톡을 안 쓰는 조문객용 보조 버튼 |

- ⚠️ **SDK 로드 타임아웃이 필요합니다.** `KakaoMapModal.tsx:135-153`이 이미 폴링+타임아웃
  패턴을 갖고 있으니 **`config.ts` 상수로 같은 방식**을 씁니다(`KAKAO_SDK_LOAD_TIMEOUT_MS`).
- ⚠️ **`sendDefault`는 클릭 핸들러 안에서 동기 호출**돼야 합니다. `await fetch(...)` 뒤에 호출하면
  **팝업 차단**에 걸립니다 → **부고장 생성을 먼저 끝내고, 공유는 별도 버튼**으로 분리합니다.
- 🔴 **3번(링크 복사)은 폴백이 아니라 상시 노출**합니다. 유족이 이미 열어둔 단톡방에 직접
  붙여넣는 것이 가장 빠른 경로인 경우가 많습니다.
