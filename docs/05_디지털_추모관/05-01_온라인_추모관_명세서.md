### 1.1 목업의 근본 문제: 추모관이 하나뿐이다

목업의 추모관은 **전역 싱글턴**입니다. 헌화 수가 42로 하드코딩돼 있고 방명록도 하나입니다.
누구의 추모관인지가 없으므로 실제 서비스로는 성립하지 않습니다.

**추모관은 고인 1명당 1개**이며, **유족이 개설**하고, **고유 URL로 조문객이 방문**합니다.
이것이 이 기능의 최소 성립 조건입니다.

## 🕯️ 2. 설계

### 2.1 공개 범위 — 기본값은 "링크를 아는 사람만"

| 값 | 의미 | 검색 노출 |
| :--- | :--- | :---: |
| `PRIVATE` | 개설자와 지정 유족만 | ❌ |
| **`LINK`** | **URL을 아는 사람만 (기본값)** | ❌ |
| `PUBLIC` | 이어봄 내 추모관 목록에 노출 | ⭕ |

**기본값을 `PUBLIC`이 아니라 `LINK`로 두는 이유**: 사망 사실과 유족 구성이 공개적으로 색인되면
**부고 사칭 보이스피싱의 표적 정보**가 됩니다. 실제로 부고 문자를 가장한 피싱은 이미 사회 문제입니다.
부고는 널리 알리는 것이 본래 성격이지만, **"널리"의 주체는 유족이어야 하며 검색엔진이 아닙니다.**

- `PUBLIC`이어도 **생년월일·주소·유족 실명 등은 공개 응답에서 제외**합니다(§4.1 화이트리스트).

> 🔴 **`00-13` §2.2가 이 조항의 전제를 흔듭니다.** *"URL을 아는 사람만"* 이라는 표현은 **1차 수신자
> 에만 참이고 2차 재전파 이후에는 거짓**입니다. 링크 모델 확정 시 이 절을 정정해야 합니다.

### 2.2 링크(`slug`) — 🔴 `00-13` 결정 대기

- 비공개 URL은 추측 불가능한 토큰(`slug`)을 씁니다 — 순번(`/memorial/1`)이면 열람이 가능해집니다.
- **현행 설계는 `slug` 1개 영구 불변**입니다. `00-13`이 이를 *"비밀번호 없는 영구 마스터 키 한 장"* 으로
  진단하고 4개 안(A 단일영구 / B 회전가능 / C 단계분리 / D 초대기반)을 제시했습니다.
- **C안이 채택되면** `Memorial.phase`(`OBITUARY` → `MEMORIAL`)와 **장례 정보 컬럼(빈소·발인일시·장지·
  조의금 계좌)이 이 문서에 신설**되며, Domain 07의 모바일 부고장이 이 도메인으로 흡수됩니다.

### 2.3 허위 추모관 방지

살아있는 사람의 추모관을 만드는 것은 **심각한 명예훼손**이며, 실제로 발생할 수 있는 악용입니다.
그렇다고 개설 시 사망진단서를 요구하면 아무도 쓰지 않습니다. 균형점:

1. **개설은 로그인 필수** — 최소한 누가 만들었는지 추적 가능해야 합니다(비회원 개설 불가).
2. **기본 비공개(`LINK`)** — 확산이 제한적입니다(단 §2.1의 `00-13` 경고 참조).
3. **신고 창구 + 즉시 비공개 전환** — 신고가 접수되면 **운영자 확인 전까지 자동 비공개**로 전환합니다.
   사후 확인보다 선차단이 맞습니다. 피해가 되돌릴 수 없는 종류이기 때문입니다.
4. 개설 시 **"허위 개설은 법적 책임을 질 수 있다"는 고지 동의**를 받고 시점을 기록합니다.

> 🔵 **`00-12` §4 사다리 적용**: 추모관 개설은 **L1**(자기신고+로그인), **`PUBLIC` 전환만 L2**(운영자
> 검토)입니다. 이것이 `05-02` §6.1이 미결로 남긴 개설 게이트의 답입니다.

### 2.4 헌화 — 🔴 로그인 요구 여부 재검토 중

**현행 스펙**: 조문객 대부분은 **비회원**이므로 비회원 헌화를 허용하되 중복을 억제합니다.

- 로그인 사용자: `userId`로 **1인 1회** 보장(DB 유니크 제약).
- 비회원: 브라우저 토큰 + IP 해시 조합으로 중복을 **억제**합니다.
  **완벽하지 않다는 점을 명시합니다** — 브라우저를 바꾸면 우회됩니다. 헌화 수는 정확한 집계가 아니라
  **추모의 표현**이므로 이 수준이 적정합니다. 정확성이 필요한 지표로 쓰지 마십시오.
- **IP는 원문 저장하지 않고 해시로만 보관**합니다(개인정보 최소 수집).

> 🔴 **개발자 지적(2026-08-12)**: *"비로그인 사용자가 서비스를 이용한다? 나는 별로라고 생각해."*
> **로그인 필수로 전환하면** 위 "억제만 가능" 문단과 IP 해시 수집이 통째로 사라집니다.
> `00-13` §6.1에 링크 모델별 함의가 정리돼 있으며, **링크 모델 확정 후 결정**합니다.

### 2.5 방명록 — UGC 관리

방명록은 사용자 생성 콘텐츠이므로 악성 글·스팸이 들어옵니다. 유족이 사별 직후에 그런 글을 보게
되는 것은 서비스가 만든 2차 피해입니다.

- **개설자(상주)는 자기 추모관의 방명록을 삭제할 수 있습니다.** 별도 심사 없이 즉시.
- **운영자는 강제 비공개(`hiddenAt`) 처리**가 가능합니다 — 하드 삭제가 아니라 소프트 삭제로
  분쟁 대비 원문을 보존합니다(`SocialAccount.unlinkedAt`에서 검증된 패턴).
- 비회원 작성 허용 — 이름·관계는 스냅샷 저장(§3.3). **§2.4와 같은 재검토 대상입니다.**

> 🔴 **`05-02` §4가 지적한 공백**: **작성자 본인의 방명록 삭제 권한이 없습니다.** 로그인 유저가
> 자기 글을 못 지우는 건 부자연스럽습니다. 로그인 필수로 가면 자동 해소됩니다.

### 2.6 사진 앨범 — 저장소 한계를 먼저 인정한다

추모 사진은 유족이 **영구 보존을 기대하는 자산**입니다. 그런데 현재 이미지 저장은
**백엔드 로컬 디스크**입니다(→ `systems.md` §5).

**이 상태로 추모 사진 업로드를 실서비스로 열면 안 됩니다.** 유실 시 복구가 불가능하고, 그 성격상
"죄송합니다"로 끝나지 않습니다.

- **Stage 1에서는 사진 업로드를 구현하되, 실서비스 오픈은 오브젝트 스토리지(S3 등) 전환 이후**로 묶습니다(`00-11`).
- 업로드 용량·장수 상한은 `policy.ts`(→ `01-05` §12.3)에 둡니다. 하드코딩 금지.

> 🔴 **`00-13` C안 채택 시**: `phase` + 장례 정보 컬럼 신설(§2.2).

### 3.5 `User` 변경 — `03-01` §2 원칙 반영

```prisma
model User {
  // ... 기존 필드
  memorials           Memorial[]            // docs 05-01 — 개설한 추모관
  memorialTributes    MemorialTribute[]
  memorialGuestbooks  MemorialGuestbook[]
  memorialPhotos      MemorialPhoto[]
}
```

**비회원이 만드는 데이터(헌화·방명록)는 `userId`가 nullable**이므로, 회원 상세에서는 그 회원이 남긴
것만 보입니다. 나머지는 추모관 단위로 조회합니다. 이 비대칭은 의도된 것입니다 —
비회원 조문객을 회원으로 강제하지 않기 위한 대가입니다. **§2.4 결정에 따라 이 비대칭이 사라질 수 있습니다.**

## 🔌 4. API 명세

### 4.1 공개 (인증 불필요)

| 메서드 | 경로 | 설명 |
| :--- | :--- | :--- |
| GET | `/api/memorials/:slug` | 추모관 조회. `PRIVATE`면 **404**(존재를 숨김) |
| GET | `/api/memorials/:slug/guestbook` | 방명록 목록 (삭제·비공개 건 제외) |
| POST | `/api/memorials/:slug/tributes` | 헌화 (**비회원 허용 — §2.4 재검토 중**) |
| POST | `/api/memorials/:slug/guestbook` | 방명록 작성 (**비회원 허용 — §2.5 재검토 중**) |
| POST | `/api/memorials/:slug/report` | 신고 접수 → **즉시 비공개 전환**(§2.3-3) |

- 공개 대상이 아닌 추모관은 **403이 아니라 404**로 응답합니다(`02-03` §9.1-4와 동일 원칙).
- 공개 응답 **화이트리스트**: `deceasedName`, `deceasedDeathDate`, `portraitUrl`, `epitaph`만.
  **`deceasedBirthDate`·개설자 정보·`createdByUserId`는 제외**합니다(§2.1).

### 4.2 로그인 유저 (JWT B2C)

| 메서드 | 경로 | 설명 |
| :--- | :--- | :--- |
| POST | `/api/memorials` | 추모관 개설 (**허위 개설 고지 동의 필수**, 없으면 400) |
| GET | `/api/me/memorials` | 내가 개설한 추모관 목록 |
| PATCH | `/api/memorials/:id` | 추모관 정보·공개범위 수정 (**개설자만**) |
| DELETE | `/api/memorials/:id/guestbook/:gid` | 방명록 삭제 (**개설자만**, §2.5) |
| POST/DELETE | `/api/memorials/:id/photos` | 사진 등록·삭제 (**개설자만**) |

**소유권 검증 필수** — 남의 추모관을 수정하면 403(`02-03` §5.3에서 검증된 패턴).

> 🔴 **미구현**: "추모관 닫기"(`closedAt`)가 스키마에만 있고 API가 없습니다(`05-02` §4).

### 4.3 운영자 (JWT `aud=admin`)

| 메서드 | 경로 | 설명 |
| :--- | :--- | :--- |
| GET | `/api/admin/memorials?reported=true` | 신고 접수 추모관 큐 |
| PATCH | `/api/admin/memorials/:id/review` | 신고 확인 — 복구 또는 유지 |

### 4.4 운영자 회원 상세

| 메서드 | 경로 | 설명 |
| :--- | :--- | :--- |
| GET | `/api/admin/users/:id` | 회원 상세 — 이 도메인 데이터 **조인 표시** |

**응답에 포함**: 개설한 추모관 목록(고인명·공개범위·개설일), 본인이 남긴 방명록 건수.

> **Domain 06(엔딩노트)과의 차이를 분명히 합니다.** `06-01` §3이 제기한 "운영자가 본문까지 볼
> 것인가"는 **06에서는 미해결 쟁점**이지만, **여기서는 본문 열람을 허용**합니다. 근거가 다릅니다 —
> 방명록은 애초에 **조문객에게 공개를 전제로 작성된 글**이고, 운영자가 신고 처리를 하려면
> 반드시 내용을 봐야 합니다. 반면 엔딩노트는 **생전에 비밀 보장을 명시적으로 약속**한 콘텐츠입니다.
> **이 문서의 결정을 06에 유추 적용하지 마십시오.**

## 🔒 5. 개인정보 (→ `.harness/security.md`)

1. **고인의 개인정보는 본인이 동의할 수 없습니다.** 개설자가 대신 등록하는 구조이므로,
   공개 범위 기본값을 좁게(`LINK`) 두는 것으로 위험을 상쇄합니다(§2.1).
2. **IP는 해시로만 저장**합니다(§2.4). 원문 저장 금지. **§2.4가 로그인 필수로 바뀌면 이 항목은 삭제됩니다.**
3. 방명록·헌화는 **비회원 데이터**를 포함하므로 최소 수집 원칙을 지킵니다 — 이름·관계·본문 외에
   연락처·이메일을 받지 않습니다. 받을 이유가 없습니다.
4. ✅ **추모관 보존기간 확정(2026-08-28)** — **활성 395일 → 동결 → 3년 후 파기**(정본 `00-20`).
   무기한 보관은 스토리지 비용과 개인정보 최소보유 원칙 양쪽에 걸리는데, **동결이 그 둘을 함께
   푼 답**입니다 — 지우지 않으면서 쓰기 부하와 운영 부담을 0으로 만듭니다(`00-20` §5.1).
   🔴 **구현 시 `frozenAt` 가드를 방명록·헌화·사진 3경로 전부에** — 하나라도 빠지면 동결이 아닙니다.
