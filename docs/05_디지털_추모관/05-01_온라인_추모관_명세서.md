### 1.1 목업의 근본 문제: 추모관이 하나뿐이다

**추모관은 고인 1명당 1개**이며, **유족이 개설**하고, **고유 URL로 조문객이 방문**합니다.
이것이 이 기능의 최소 성립 조건입니다.
지금 구조는 이를 갖췄습니다 — 추모관마다 `slug`가 있고(§2.2), `Memorial.deceasedId`가 고인(`Deceased`)을 가리킵니다(§3.1).

🟡 **다만 "고인 1명당 1개"는 강제할 수 없는 권고입니다**(`05-02` §7 T7). 같은 고인의 추모관을 다른 유족이 따로 만들 수 있고
막는 장치는 없습니다 — `/memorial`에서 만들 때마다 고인(`Deceased`)도 새로 만들어집니다. 유족 간 관리권 분쟁은 나중에 다루기로 했습니다(`05-02` §11 #9).
처음 진단(목업의 전역 싱글턴)은 부록 §1.1.

## 🕯️ 2. 설계

### 2.1 공개 범위 — 기본값은 "링크를 아는 사람만"

| 값 | 화면 이름 | 의미 | 검색·목록 노출 |
| :--- | :--- | :--- | :---: |
| **`LINK`** | 링크로만 공개 **(기본값)** | 주소(`/m/:slug`)를 가진 사람은 누구나 볼 수 있음 | ❌ |
| `PRIVATE` | 비공개 — 나만 보기 | 공개 주소가 **모두에게 404**(개설자 포함). 개설자는 `/memorial`에서만 봅니다 | ❌ |

✅ 서버는 이 두 값만 받습니다(`memorialController.ts` `VALID_VISIBILITY` — 그 밖의 값은 400). 이어봄에는 추모관 목록·검색 화면이 없습니다.

**목록·검색 공개를 두지 않는 이유**: 사망 사실과 유족 구성이 공개적으로 색인되면
**부고 사칭 보이스피싱의 표적 정보**가 됩니다. 실제로 부고 문자를 가장한 피싱은 이미 사회 문제입니다.
부고는 널리 알리는 것이 본래 성격이지만, **"널리"의 주체는 유족이어야 하며 검색엔진이 아닙니다.**

- 공개 응답은 **생년월일·주소·유족 실명 등을 빼고** 화이트리스트만 돌려줍니다(§4.1).

> 🔴 **"링크를 아는 사람만"은 통제가 아닙니다**(`00-13` §2.2). 받은 사람이 링크를 다시 넘길 수 있어 1차 수신자 밖으로
> 퍼지는 것을 막을 수단이 없습니다. `LINK`의 실제 뜻은 *"목록·검색에 나오지 않는다"* 까지입니다.
> 유족에게 재전파를 알리는 고지는 미확정입니다(`00-13` §8 #6).
>
> 🔴 **코드 잔재**: `schema.prisma`의 `Memorial.visibility` 주석은 아직 `PRIVATE | LINK | PUBLIC`입니다. 09-29 이전에 `PUBLIC`으로
> 저장된 행이 있다면 공개 열람은 `LINK`와 똑같이 동작합니다(`findViewableMemorialBySlug`가 `PRIVATE`만 거름) — 남아 있는지는 DB 조회가 필요합니다(미확인).

처음 공개 범위 표(`PUBLIC` 포함 3가지)는 부록 §2.1.

### 2.2 링크(`slug`) — `00-13` E안 확정(2026-08-14)

- 공개 주소는 **`/m/:slug`** 이고 `slug`는 **추측 불가 토큰**입니다 — 128비트 무작위값(`memorialController.ts` `generateSlug`).
  순번(`/memorial/1`)이면 남의 추모관을 열 수 있게 됩니다.
- **링크 모델은 `00-13` E안**입니다(정본, 2026-08-14 확정): **부고장(07)이 봉투, 추모관(05)이 목적지.** 조문객에게 나가는 링크는
  부고장 링크 하나이고, 부고장 랜딩의 버튼이 추모관으로 이어집니다(`00-13` §4.5-1).
- 부고장과 추모관은 **0..1 선택 연결**입니다(2026-09-07, `00-13` §4.5-4) — 부고장 폼의 체크박스(기본 꺼짐)로 함께 만들거나
  `/memorial`에서 따로 만듭니다. 따로 만든 추모관은 유족이 그 주소를 직접 보냅니다(`00-13` §4.5-4-2).
- 🔴 `slug`는 지금 **바뀌지 않습니다.** `00-13` §7.3 #4(추모관 `slug`만 회전 가능)는 미구현 — 재발급 API가 없습니다.

처음 서술(C안 채택 시 `phase`·장례 정보 컬럼 신설)은 부록 §2.2.

### 2.3 허위 추모관 방지

살아있는 사람의 추모관을 만드는 것은 **심각한 명예훼손**이며, 실제로 발생할 수 있는 악용입니다.
그렇다고 개설 시 사망진단서를 요구하면 아무도 쓰지 않습니다. 균형점:

1. ✅ **개설은 로그인 필수** — 최소한 누가 만들었는지 추적 가능해야 합니다(비회원 개설 불가, `createMemorial` 401).
2. ✅ **기본 `LINK`** — 목록·검색에 나오지 않습니다(단 §2.1의 재전파 한계).
3. ✅ **운영자 내리기**(2026-09-30) — 신고 기능은 없앴습니다(2026-09-29). 전화·카톡으로 알려온 문제를 운영자가 판단해
   **추모관 전체를 내립니다**(`Memorial.hiddenAt`, 사유 필수·감사 기록 `AdminAuditLog`). 공개 열람은 닫힌 추모관과 같이
   "찾을 수 없음"이고, 개설자가 풀 수 없으며, 자동 파기하지 않습니다(`00-20` §6.2).
   🔴 내려진 사실을 개설자에게 알리는 기능은 미구현입니다(알림 채널 결정 뒤 — `00-20` §6.2).
4. ✅ 개설 시 **"허위 개설은 법적 책임을 질 수 있다"는 고지 동의**를 받고 시점을 기록합니다(`falseReportAgreedAt`, 없으면 400).
   동의는 **07 부고장 폼과 `/memorial` 직접 개설 폼 양쪽**에서 받습니다(`validateFalseReportAgreed` — 한쪽만 걸면 우회로, `00-13` §8 주석).

> 🔵 **`00-12` §4 사다리**: 추모관 개설은 **L1**(자기신고+로그인)이고 **승인 단계가 없습니다**(`05-02` §6.1).
> `PUBLIC` 전환만 L2(운영자 검토)로 두던 안은 `PUBLIC` 폐지로 닫혔습니다(부록 §2.3).

### 2.4 헌화 — 비로그인 허용(2026-09-29 확정)

✅ **헌화는 로그인 없이 합니다**(`00-13` §8 #3). 조문객 대부분이 비회원이고, 헌화 수는 정확한 집계가 아니라
**추모의 표현**이기 때문입니다. **정확성이 필요한 지표로 쓰지 마십시오.**

- 화면은 헌화에 로그인 정보를 보내지 않습니다(2026-09-21 사용자 지시) — 로그인해 있어도 비회원과 똑같이 처리됩니다.
- **중복 제한은 브라우저 저장소 하나**입니다 — 추모관마다 한 번(`MemorialLandingPage.tsx`의 localStorage 키 `tributeStorageKey`).
  다른 브라우저·기기나 저장소 삭제로는 다시 할 수 있습니다(*"큰 문제 아님"*, 사용자 확인).
- 서버는 `visitorHash`(IP 기반 해시)를 **저장만** 하고 중복 판정에는 쓰지 않습니다. 로그인 토큰이 오면
  `@@unique([memorialId, userId])`가 1인 1회를 막지만, 지금 화면은 토큰을 보내지 않습니다.
- **IP는 원문 저장하지 않고 해시로만 보관**합니다(개인정보 최소 수집, `memorialController.ts` `hashVisitor` — sha256).

처음 서술(비회원 중복 억제 설계 · 로그인 재검토)은 부록 §2.4.

### 2.5 방명록 — UGC 관리

방명록은 사용자 생성 콘텐츠이므로 악성 글·스팸이 들어옵니다. 유족이 사별 직후에 그런 글을 보게
되는 것은 서비스가 만든 2차 피해입니다.

- ✅ **쓰기는 로그인 필요**(2026-09-29) — 비로그인은 401, 탈퇴 유예 중은 403(`blockDuringDeletionGrace`). 작성자 이름은 서버가
  **로그인 사용자 이름을 스냅샷**합니다(이름 칸 없음, §3.3). 보기는 비로그인도 됩니다.
- ✅ **개설자(상주)는 자기 추모관의 방명록을 삭제할 수 있습니다.** 별도 심사 없이 즉시(`deletedByOwnerAt`).
- ✅ **작성자 본인도 자기 글을 지울 수 있습니다**(`deletedByAuthorAt`, `00-36` §4.7-1). 상주 삭제와 칸을 나눠
  "누가 지웠나"가 섞이지 않게 했습니다.
- **운영자는 강제 비공개(`hiddenAt`) 처리**가 가능합니다 — 하드 삭제가 아니라 소프트 삭제로
  분쟁 대비 원문을 보존합니다(`SocialAccount.unlinkedAt`에서 검증된 패턴).
- 🟡 **선제 필터·새 글 알림은 없습니다** — 금칙어 필터와 개설자 알림 권고는 `05-02` §6.2·§11 #10.

처음 서술(비회원 작성 허용 · 작성자 삭제 공백)은 부록 §2.5.

### 2.6 사진 앨범 — 저장소 한계를 먼저 인정한다

추모 사진은 유족이 **영구 보존을 기대하는 자산**입니다. 그런데 추모관 사진은 지금도 **백엔드 로컬 디스크**에
저장됩니다(`config/upload.ts` `MEMORIAL_PHOTO_DIR` — 재배포 때 사라짐, `systems.md` §5).

**이 상태로 추모 사진 업로드를 실서비스로 열면 안 됩니다.** 유실 시 복구가 불가능하고, 그 성격상
"죄송합니다"로 끝나지 않습니다.

- ✅ 서버 API는 있습니다 — 개설자만 등록·삭제(`addMemorialPhoto`·`deleteMemorialPhoto`). 🔴 **화면은 없습니다** —
  랜딩(§6.1)은 사진을 감추고, `/memorial`에도 사진 칸이 없으며, 공개 조회 API(`GET photos`)도 없습니다.
- 🔴 **오픈 조건 = 추모관 사진을 R2로 옮긴 뒤.** 파일 저장소는 Cloudflare R2로 확정됐고(2026-09-03, `00-11` §5.4)
  R2 버킷도 있으나 추모관 사진 코드는 아직 연결되지 않았습니다(`00-11` 현황 표).
- ✅ 업로드 용량·장수 상한은 `policy.ts` `POLICY.memorial`에 있습니다 — 1장 5MB · 추모관당 20장(하드코딩 금지, `01-05` §12.3).

### 3.1 `Memorial` (신규) — 추모관

> 🔵 컬럼 전체와 주석의 정본은 `00-05` DB 사전(`schema.prisma`에서 자동 생성)입니다. 아래 표는 이 도메인 설계에 이유가 있는 칸입니다.

| 컬럼 | 타입 | 설명 |
| :--- | :--- | :--- |
| `id` | String @id | UUID |
| `slug` | String @unique | 공개 URL용 **추측 불가 토큰**(§2.2) — 순번 금지 |
| `createdByUserId` | String | **FK → User** — 개설자(상주) |
| `deceasedId` | String | **FK → `Deceased`**(필수) — 부고장(`Obituary`)과 같은 고인을 가리킴(`00-12` §2.1 · `07-03` §4.1) |
| `obituary` | Obituary? | 부고장 1:1 역참조(선택 — 연결 칸은 `Obituary.memorialId`, §2.2) |
| `deceasedName` | String | 고인 성명 |
| `deceasedBirthDate` | DateTime? | 생년월일 (공개 응답 제외) |
| `deceasedDeathDate` | DateTime? | 사망일 |
| `portraitUrl` | String? | 영정 사진 |
| `epitaph` | String? | 추모 문구 |
| `visibility` | String @default("LINK") | `LINK` \| `PRIVATE` (§2.1) — **유족(개설자)만** 바꿈 |
| `falseReportAgreedAt` | DateTime | 허위 개설 책임 고지 동의 시각(§2.3-4) |
| `closedAt` | DateTime? | 개설자가 닫음 (소프트 삭제) — 30일 뒤 파기(`purgeAt`) |
| `hiddenAt` | DateTime? | **운영자가 내림**(§2.3-3) — 운영자만 바꿈, 개설자가 풀 수 없음 |
| `expiresAt` / `frozenAt` / `purgeAt` | DateTime? | 보존기간 — 활성 만료 · 동결 시각 · 파기 예정(`00-20` §8.1) |

| `reportedAt` / `reviewedAt` | DateTime? | 🔴 **쓰지 않음** — 신고 폐지(09-30). 다음 스키마 변경 때 삭제(`schema.prisma` 주석) |

**인덱스**: `[createdByUserId]`, `[visibility]` — `slug`는 `@unique`라 따로 두지 않습니다.
**관계**: `tributes` · `guestbook` · `photos` · `notices`(`MemorialNotice` — 만료 통지·파기 전 재확인·연장 기록, `00-20` §8.1-3·§8.1-4).

✅ **유족의 의사와 운영자의 조치를 칸으로 나눴습니다** — `visibility`는 개설자만, `hiddenAt`은 운영자만 바꿉니다.
운영자가 되돌려도 유족이 정한 공개범위가 그대로 남습니다(`05-02` §5). 공개 열람 조건 =
`visibility ≠ PRIVATE` 그리고 `closedAt`·`hiddenAt`이 비어 있음(`findViewableMemorialBySlug`).

처음 표와 정정 예정 3건(`moderationState` · `deceasedId` · C안 `phase`)은 부록 §3.1.

### 3.5 `User` 변경 — `03-01` §2 원칙 반영

```prisma
model User {

  memorials           Memorial[]            // docs 05-01 — 개설한 추모관
  memorialTributes    MemorialTribute[]
  memorialGuestbooks  MemorialGuestbook[]
```

**헌화는 비회원 데이터라 `userId`가 비어 있고**, 회원 상세에서는 그 회원이 남긴 방명록만 보입니다. 헌화는 추모관 단위로
조회합니다. 이 비대칭은 의도된 것입니다 — 비회원 조문객을 회원으로 강제하지 않기 위한 대가입니다(§2.4).
방명록은 쓰기가 로그인 필요라 새 글은 작성자 회원에 묶입니다(§2.5).

## 🔒 5. 개인정보 (→ `.harness/security.md`)

1. **고인의 개인정보는 본인이 동의할 수 없습니다.** 개설자가 대신 등록하는 구조이므로,
   공개 범위 기본값을 좁게(`LINK`) 두는 것으로 위험을 상쇄합니다(§2.1).
2. **IP는 해시로만 저장**합니다(§2.4 — 헌화가 비로그인이라 남는 항목). 원문 저장 금지.
3. 헌화는 **비회원 데이터**이므로 최소 수집 원칙을 지킵니다 — IP 해시 외에 받는 것이 없습니다. 방명록은 로그인 필요라
   이름은 회원 정보에서 스냅샷하고, 관계·본문 외에 연락처·이메일을 받지 않습니다. 받을 이유가 없습니다.
4. ✅ **추모관 보존기간 확정(2026-08-28)** — **활성 395일 → 동결 → 3년 후 파기**(정본 `00-20`).
   무기한 보관은 스토리지 비용과 개인정보 최소보유 원칙 양쪽에 걸리는데, **동결이 그 둘을 함께
   푼 답**입니다 — 지우지 않으면서 쓰기 부하와 운영 부담을 0으로 만듭니다(`00-20` §5.1).
   ✅ **`frozenAt` 가드는 방명록·헌화·사진 3경로 전부에 걸려 있습니다**(`memorialController.ts` `isMemorialFrozen` — 추가만 막고
   읽기·삭제는 둠). 닫은 추모관은 30일 뒤 파기하고, 운영자가 내린 추모관은 자동 파기하지 않습니다(`00-20` §6.2·§6.3-1).
