## 🧭 2. 도메인 정의와 경계

### 2.1 ✅ 이 도메인은 두 개의 다른 서비스다 — 시간축이 완전히 다르다

구 `03-02`는 "디지털 계정 정리"와 "온라인 추모관"을 한 화면(SCR-003)의 두 서브탭으로 묶었습니다.
그런데 **유족이 이 둘을 필요로 하는 시점이 완전히 다릅니다.**

| | 온라인 추모관 | 디지털 계정 정리 |
| :--- | :--- | :--- |
| **필요 시점** | 사망 직후 **D+0 ~ D+7** (장례 기간) | **D+30 이후**, 길게는 수개월~1년 |
| **긴급도** | 극도로 높음 — 부고를 알려야 함 | 낮음 — 서두를 이유가 없음 |

| **재방문** | 장례 기간 집중 후 급감 | 플랫폼별로 몇 주에 걸쳐 산발적 |

## 🔄 5. ✅ 추모관 생애주기 — 두 축을 분리한다

`visibility` 하나가 "유족의 의사"와 "운영자의 제재"를 동시에 표현하면, 운영자가 되돌릴 때 유족이 원래 정한 공개범위를
알 수 없습니다. 그래서 **두 축을 칸으로 나눕니다.**

✅ **지금 구현(2026-09-30)**: 운영자 축은 처음 설계한 `moderationState`(4값 상태 머신)가 아니라 **운영자 전용 `Memorial.hiddenAt`
한 칸**입니다. 신고 기능을 없애면서(2026-09-29) `REPORTED`·`CONFIRMED_OK`가 쓸 데가 없어졌고, 남은 운영자 조치(내리기·되돌리기)는
시각 한 칸이면 됩니다(`00-20` §6.2). 처음 진단과 설계는 부록 §5.

### 5.1 두 축으로 분리

| 축 | 필드 | 누가 정하나 | 값 |
| :--- | :--- | :--- | :--- |
| **공개범위** | `visibility` | **유족(개설자)** | `LINK` / `PRIVATE` |
| **운영자 조치** | `hiddenAt` | **운영자** | 비어 있음 / 내린 시각 |
| (개설자 닫기) | `closedAt` | 개설자 | 비어 있음 / 닫은 시각 — 30일 뒤 파기 |
| (보존기간) | `frozenAt` | 파기 배치(`00-20`) | 동결이면 추가만 막음 — 열람은 그대로 |

**실제 노출 여부 = 세 칸의 AND**입니다(`memorialController.ts` `findViewableMemorialBySlug`).

```
노출된다 = (visibility ≠ PRIVATE) AND (hiddenAt = null) AND (closedAt = null)
```

### 5.2 이 분리가 해결하는 것

운영자가 내려도 **`visibility`를 건드리지 않습니다.** `hiddenAt`만 채워지고, 노출은 AND 조건에서 자동으로 차단됩니다.
되돌릴 때는 `hiddenAt`만 비우면 **유족이 원래 설정했던 `visibility`가 그대로 살아납니다** — 운영자가 추측할 필요도,
유족의 의사를 덮어쓸 일도 없습니다. 반대로 개설자는 `hiddenAt`을 풀 수 없습니다.

### 5.3 상태 전이

```
[개설] → 활성 (expiresAt = 개설 + 395일)
활성 --운영자 내리기--> 내림 (hiddenAt) --운영자 되돌리기--> 활성     (내림은 자동 동결·파기 대상이 아님)
활성 --개설자 닫기--> 닫힘 (closedAt, purgeAt = +30일) --30일 뒤--> 파기
활성 --expiresAt 도래--> 동결 (frozenAt, purgeAt = +3년, 추가만 차단) --파기 30일 전 재확인 통지--> 파기
만료 통지 뒤·동결 --연장(통지 링크 또는 내 추모관 화면)--> 활성 (expiresAt = 지금 + 395일)
```

- 동결·파기는 런타임이 아니라 **사람이 돌리는 파기 배치**가 처리합니다(`memorialLifecycleService.ts`·`memorialPurgeService.ts` 머리 주석).
- 보존기간 단계의 정본은 `00-20` §5.2·§8.1입니다. 처음 상태 전이(`moderationState`)는 신고 폐지로 대상이 없어졌습니다(부록 §5.3).

### 6.1 ✅ 신원·사실 검증 (개설 게이트) — 승인 없이 즉시 개설

**문제**: Domain 01·02는 운영자 심사 게이트가 있는데 05는 자동 개설입니다. 그런데 05가 다루는 고인 정보는
**본인이 동의할 수 없는 유일한 개인정보**입니다.

**제약**: §3.2-2 — 승인 대기는 부고 기능에서 치명적. 전면 승인제는 불가.

✅ **지금(2026-09-29 이후)**: 공개범위가 `LINK`·`PRIVATE` 둘뿐이라 **모든 추모관은 승인 없이 즉시 개설**됩니다.
개설 문턱은 **로그인 + 허위 개설 고지 동의**(L1, `05-01` §2.3)이고, 사후 수단은 **운영자 내리기**(`hiddenAt`)입니다.
링크를 받은 사람에게만 도달해 확산이 제한적이고, 유족의 긴급성이 우선합니다.

처음 권고(공개범위별 차등 — `PUBLIC`만 운영자 승인)는 `PUBLIC` 폐지로 닫혔습니다(부록 §6.1).

### 6.2 🟡 콘텐츠 검증 (UGC)

- 방명록: 개설자 삭제 ✅ / 운영자 강제 비공개 ✅ / 작성자 본인 삭제 ✅(`00-36` §4.7-1) / 쓰기 로그인 필요 ✅(2026-09-29)
- 사진: 개설자 삭제 ✅ / 운영자 숨김 없음 — ✅ **사진 저장소·업로드 방식을 정할 때 함께 넣는다**(2026-10-08 개발자 결정, §11 #8). 지금은 사진 화면이 없어 노출 0
- **선제 필터 없음** — 욕설·스팸 자동 차단이 전혀 없습니다. 사별 직후 유족이 악성 글을 먼저 보게
  되는 건 서비스가 만든 2차 피해입니다(`05-01` §2.5가 인정한 위험인데 대책은 사후 삭제뿐).

## 🏢 8. 🔴 운영 부하 — 아직 아무도 계산하지 않았다

`05-01`은 운영자 화면(§6.3)을 정의했지만 **운영자가 하루에 몇 건을 처리해야 하는지 아무도 추정한
적이 없습니다.** 이 도메인은 다른 도메인과 부하 성격이 다릅니다:

- **01·02**: 사업자·전문가 가입 심사 — 건수가 적고(수십~수백), 급하지 않음
- **05**: 추모관 문제 제보(전화·카톡) 판단 → 내리기 — **건수 예측 불가, 시간 민감**(살아 있는 사람의 추모관이면 그날 안에 내려야 함)

정해야 할 것:
1. 제보 처리 **목표 응답 시간** — 부고 성격상 몇 시간 이내여야 합니까?
2. **야간·주말 대응** — 사망은 시간을 가리지 않습니다. 금요일 밤에 들어온 제보는?
3. 운영자 **인원과 근무 형태** — 현재 운영자 계정은 시드로만 만들고 실제 담당자가 정해진 적 없습니다.
4. ✅ **제보 창구 = 고객센터**(2026-10-08 개발자 결정). 신고 버튼 없이, 문제가 있으면 **고객센터(대표번호·카카오톡 채널)로 연락**하고 운영자가 판단해 내립니다.
   - 사이트 푸터에는 대표번호와 *"카카오톡으로 문의하기"*(`config.ts`의 `KAKAO_CHANNEL_CHAT_URL`)가 이미 있습니다.
   - 추모관 공개 페이지(`/m/:slug`, `MemorialLandingPage`)는 푸터 없이 뜨는 화면이라 연락처가 없습니다. ✅ **그대로 둡니다**(2026-10-08 개발자 결정) —
     문제가 있는 사람은 이어봄 홈페이지를 찾아 고객센터로 연락한다고 봅니다. 추모관 화면은 고인을 기리는 내용만 둡니다.
   - 약관(`00-21`)에 제보 경로를 적을지는 00 정리 때 함께 봅니다.

신고 기능을 없애면서(2026-09-29) 신고 큐의 부하는 사라졌지만 운영자 판단은 남았습니다. 처음 서술(신고 처리 부하 · `PUBLIC` 승인제)은 부록 §8.

## 💰 9. 🔴 비용·수익 구조 — 이 도메인만 수익 모델이 없다

| 도메인 | 수익 | 비용 |

### 9.1 추모관은 "영구 보존"을 약속하면 비용이 영구히 발생합니다

사진·방명록을 계속 보관해야 하고, 유족은 당연히 영구 보존을 기대합니다. 그런데 수익이 0입니다.

✅ **보존기간 축은 닫혔습니다**(2026-08-28, `00-20` §5.2-2: 활성 395일 → 동결 → 3년 후 파기). **비용은 "보관"이 아니라
"살아 있음"에서 발생**하므로(`00-20` §5.1), **동결이 §9.2 (A)의 비용 통제와 (C)의 신뢰를 동시에 가져갑니다** —
유족에게는 *"남아 있다"* 가 지켜지고 회사에는 쓰기 부하·모더레이션 부담이 사라집니다.

🔴 **남은 것은 수익모델뿐이며**(§11 #5), 여기에 `00-11` 스토리지 실측이 여전히 걸려 있습니다.

### 9.2 선택지

- **(A) 완전 무료 + 기간 제한** — ✅ 동결(§9.1)로 흡수됐습니다. 기간은 2026-08-28에 정해졌고, 남은 선택은 그 위의 수익 방식입니다.
- **(B) 무료 + 유료 영구보존** — 기본은 기간 제한, 유료로 영구 전환. PG 필요(사장님 승인 대상).
- **(C) 완전 무료 영구** — 브랜드 자산으로 간주하고 비용을 마케팅비로 처리. 규모 커지면 부담.
- **(D) 장례식장 제휴 상품** — 01 파트너가 유족에게 제공하는 부가 서비스로 묶어 B2B 과금.

🟡 **권고: (D)를 우선 검토.** 이어봄은 이미 01에 장사시설 파트너망을 갖고 있고, 추모관은 장례식장이
유족에게 제공하기 좋은 부가가치입니다. 소비자에게 직접 과금하지 않아 사별 상황에서의 거부감도
없습니다. 다만 **`00-11` 인프라 결정(스토리지 비용 실측)이 나와야 숫자를 붙일 수 있습니다.**

### 9.3 관련 — 장례식장이 추모관을 대신 개설하는 모델

(D)와 연결됩니다. 파트너(장례식장)가 유족 대신 추모관을 만들어주면 §3.2의 "경황 없는 유족" 문제가
크게 완화되고, §6.1 신원 검증도 **파트너가 실질적으로 보증**하는 효과가 생깁니다. 🟡 별도 검토 대상.

### 5. 처음 진단 — 상태 머신 부재 (2026-08-12)

**walkthrough (15) 편차 ②("복구 시 이전 공개범위를 모른다")의 근본 원인은 상태 머신 부재입니다.**
`Lead`(§4.3)·`ConsultRequest`에는 명시적 상태 머신이 있는데 `Memorial`에는 없어서, `visibility`
하나가 "유족의 의사"와 "운영자의 제재"를 동시에 표현하려다 충돌했습니다.

### 5.1 처음 설계 — `moderationState` 4값 (2026-08-12 · 09-29 신고 폐지로 대체)

| 축 | 필드 | 누가 정하나 | 값 |
| :--- | :--- | :--- | :--- |
| **공개범위** | `visibility` | **유족(개설자)** | `PRIVATE` / `LINK` / `PUBLIC` |
| **제재 상태** | `moderationState` (신규) | **운영자·시스템** | `NORMAL` / `REPORTED` / `CONFIRMED_OK` / `BLOCKED` |

**실제 노출 여부 = 두 축의 AND 연산**입니다.

```
노출된다 = (visibility ≠ PRIVATE) AND (moderationState ∈ {NORMAL, CONFIRMED_OK}) AND (closedAt = null)
```

### 5.2 처음 서술 — 신고 시 축 분리와 Sonnet 우회 판단 (2026-08-12)

신고가 들어와도 **`visibility`를 건드리지 않습니다.** `moderationState`만 `REPORTED`로 바뀌고,
노출은 AND 조건에서 자동으로 차단됩니다. 복구할 때는 `moderationState`만 되돌리면 **유족이
원래 설정했던 `visibility`가 그대로 살아납니다** — 운영자가 추측할 필요도, 유족의 의사를 덮어쓸
일도 없습니다.

> Sonnet이 "시스템이 이전 값을 추정하지 않게" 운영자 지정 방식으로 우회한 것은 **주어진 스키마
> 안에서는 옳은 판단**이었습니다. 다만 근본 해법은 스키마를 고치는 것입니다.

### 5.3 처음 상태 전이 — `moderationState` (2026-08-12 · 09-29 소멸)

```
[개설] → NORMAL
NORMAL --신고 접수--> REPORTED        (노출 즉시 차단, §7 정책에 따름)
REPORTED --운영자: 문제없음--> CONFIRMED_OK   (원래 visibility로 자동 복귀)
REPORTED --운영자: 위반 확인--> BLOCKED       (영구 차단, 개설자에게 사유 통지)
CONFIRMED_OK --재신고--> REPORTED     (단, 재신고 임계치는 §7에서 결정)
```

**`CONFIRMED_OK`를 `NORMAL`과 구분하는 이유**: 한 번 무혐의 판정된 추모관이 같은 방식으로 반복
신고당하는 걸 막으려면 "이미 확인됨" 이력이 필요합니다. §7 그리핑 대응의 핵심 재료입니다.

**익명 신고와 즉시 차단은 양립할 수 없습니다.** 둘 중 하나를 포기해야 합니다.

| 안 | 내용 | 장단 |
| :--- | :--- | :--- |
| **A** | **신고 로그인 필수** + 즉시 차단 유지 + 개설자 즉시 알림·이의제기 | T1 대응력 유지, 남용 추적 가능. 신고 문턱은 올라감 |
| **B** | 익명 유지 + **임계치 누적 후 차단**(N건 또는 운영자 확인 후) | 신고 접근성 유지. T1 대응이 느려짐 |
| **C** | 이원화 — 로그인 신고는 즉시, 익명 신고는 누적 | 가장 정교하나 복잡도 증가 |

**권고: A.** 실제 명예훼손 피해자는 로그인해서라도 신고할 동기가 충분하고, 장난 신고는 계정
추적이 가능해지는 순간 급감합니다. 무엇보다 **개설자 알림·이의제기 경로가 없는 게 지금 가장 큰
결함**이라, 어느 안을 고르든 이건 필수입니다.

> 🔴 개발자 확정 필요. (§11-2·§12-5와 동일 건 — 신고 UI 설계 사안)
