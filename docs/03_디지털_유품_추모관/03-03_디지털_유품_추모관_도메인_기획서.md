## 🧭 2. 도메인 정의와 경계

### 2.1 ✅ 이 도메인은 두 개의 다른 서비스다 — 시간축이 완전히 다르다

`03-02`는 "디지털 계정 정리"와 "온라인 추모관"을 한 화면(SCR-003)의 두 서브탭으로 묶었습니다.
그런데 **유족이 이 둘을 필요로 하는 시점이 완전히 다릅니다.**

| | 온라인 추모관 | 디지털 계정 정리 |
| :--- | :--- | :--- |
| **필요 시점** | 사망 직후 **D+0 ~ D+7** (장례 기간) | **D+30 이후**, 길게는 수개월~1년 |
| **긴급도** | 극도로 높음 — 부고를 알려야 함 | 낮음 — 서두를 이유가 없음 |
| **사용자 상태** | 경황 없음, 모바일, 밤낮 없음 | 어느 정도 안정, 사무 처리 모드 |
| **재방문** | 장례 기간 집중 후 급감 | 플랫폼별로 몇 주에 걸쳐 산발적 |
| **동반 도메인** | 01(장례식장), 04(부고·행정) | 02(행정사·세무사) |

**같은 탭에 두면 양쪽 다 손해입니다.** 사망 당일 부고를 알리려 들어온 유족에게 "네이버 계정 삭제
절차"를 보여주는 건 무의미하고, 두 달 뒤 계정 정리하러 온 사람에게 추모관 개설 버튼은 소음입니다.

> **결정**: 두 기능을 **하나의 페이지 안 두 탭이 아니라, 서로 다른 진입점**으로 다룹니다.
> 구체적 화면 구조는 §12-1에서 `03-02` §8.1 정정 사항으로 넘깁니다.

### 2.2 🔴 인접 도메인과의 경계 — 특히 04와 겹친다

| 인접 | 겹치는 지점 | 현재 상태 |
| :--- | :--- | :--- |
| **04 상중·행정 케어** | **모바일 부고장** — 추모관과 기능이 사실상 같음(고인 정보 + 링크 공유) | 🔴 **미해결.** `03-02` §2.4가 "04에서 다룰 것"이라며 제외했지만, 04는 **문서가 0건**이라 넘긴 곳이 비어 있음 |
| **02 전문가 매칭** | 위임 대행 → 행정사 연결 | ✅ `03-02` §3.4에서 정리됨 |
| **01 장사시설** | 장례식장이 추모관을 대신 만들어주는 모델 | 🟡 미검토 — §9.3 참조 |

**04 부고장과 03 추모관의 경계는 반드시 정해야 합니다.** 둘 다 "고인 정보 + 공유 링크 + 조문객
접근"이라 사실상 같은 것을 두 도메인이 각각 만들 위험이 있습니다. 선택지:

- **(A) 통합** — 추모관이 부고장을 흡수. 부고 = 추모관의 초기 상태(장례 정보 포함), 장례 후 추모관으로 전환.
- **(B) 분리** — 부고장은 04(일회성 알림, 장례 정보 중심), 추모관은 03(영구 보존, 추모 중심).
- **권고: (A) 통합.** 유족 입장에서 "부고 보내기"와 "추모관 만들기"를 두 번 하는 건 부담이고,
  실제로 조문객이 받는 링크는 하나여야 합니다. 다만 이건 **04 기획과 함께 결정**해야 하므로 여기서
  확정하지 않습니다.

## 🔄 5. ✅ 추모관 생애주기 — 두 축을 분리한다

**walkthrough (15) 편차 ②("복구 시 이전 공개범위를 모른다")의 근본 원인은 상태 머신 부재입니다.**
`Lead`(§4.3)·`ConsultRequest`에는 명시적 상태 머신이 있는데 `Memorial`에는 없어서, `visibility`
하나가 "유족의 의사"와 "운영자의 제재"를 동시에 표현하려다 충돌했습니다.

### 5.1 두 축으로 분리

| 축 | 필드 | 누가 정하나 | 값 |
| :--- | :--- | :--- | :--- |
| **공개범위** | `visibility` | **유족(개설자)** | `PRIVATE` / `LINK` / `PUBLIC` |
| **제재 상태** | `moderationState` (신규) | **운영자·시스템** | `NORMAL` / `REPORTED` / `CONFIRMED_OK` / `BLOCKED` |

**실제 노출 여부 = 두 축의 AND 연산**입니다.

```
노출된다 = (visibility ≠ PRIVATE) AND (moderationState ∈ {NORMAL, CONFIRMED_OK}) AND (closedAt = null)
```

### 5.2 이 분리가 해결하는 것

신고가 들어와도 **`visibility`를 건드리지 않습니다.** `moderationState`만 `REPORTED`로 바뀌고,
노출은 AND 조건에서 자동으로 차단됩니다. 복구할 때는 `moderationState`만 되돌리면 **유족이
원래 설정했던 `visibility`가 그대로 살아납니다** — 운영자가 추측할 필요도, 유족의 의사를 덮어쓸
일도 없습니다.

> Sonnet이 "시스템이 이전 값을 추정하지 않게" 운영자 지정 방식으로 우회한 것은 **주어진 스키마
> 안에서는 옳은 판단**이었습니다. 다만 근본 해법은 스키마를 고치는 것입니다.

### 5.3 상태 전이

```
[개설] → NORMAL
NORMAL --신고 접수--> REPORTED        (노출 즉시 차단, §7 정책에 따름)
REPORTED --운영자: 문제없음--> CONFIRMED_OK   (원래 visibility로 자동 복귀)
REPORTED --운영자: 위반 확인--> BLOCKED       (영구 차단, 개설자에게 사유 통지)
CONFIRMED_OK --재신고--> REPORTED     (단, 재신고 임계치는 §7에서 결정)
```

**`CONFIRMED_OK`를 `NORMAL`과 구분하는 이유**: 한 번 무혐의 판정된 추모관이 같은 방식으로 반복
신고당하는 걸 막으려면 "이미 확인됨" 이력이 필요합니다. §7 그리핑 대응의 핵심 재료입니다.

## 🛡️ 6. 검증 체계 — 4개 층

대표님이 지적한 "검증이 부족하다"를 층위별로 분해합니다. **`03-02`는 이 중 6.3만 다뤘습니다.**

### 6.1 🟡 신원·사실 검증 (개설 게이트) — 가장 중요

**문제**: Domain 01·02는 전부 운영자 심사 게이트가 있는데 **03만 자동승인**입니다. 게다가 03이
다루는 고인 정보는 **본인이 동의할 수 없는 유일한 개인정보**입니다. 제일 엄격해야 할 곳이 제일
느슨합니다.

**제약**: §3.2-2 — 승인 대기는 부고 기능에서 치명적. 전면 승인제는 불가.

**권고안: 공개범위별 차등 게이트**

| 공개범위 | 게이트 | 근거 |
| :--- | :--- | :--- |
| `PRIVATE`·`LINK` | **즉시 개설** | 링크를 아는 사람에게만 도달 — 확산 위험이 제한적. 유족의 긴급성이 우선 |
| `PUBLIC` | **운영자 승인 필요** | 검색·목록 노출은 위험도가 다른 층 |

Domain 02의 "승인(`status`)과 공개 노출(`isPublished`)은 별개 축"(`02-03` §4.3) 구조를 그대로
가져오는 것이라 플랫폼 일관성도 회복됩니다. 유족은 기다리지 않고 부고를 보낼 수 있고, 위험한
경로만 사람이 봅니다.

> 🔴 **대표 확정 필요.** 확정 시 §12-2로 `03-02`에 반영.

### 6.2 🟡 콘텐츠 검증 (UGC)

- 방명록: 개설자 삭제 ✅ / 운영자 강제 비공개 ✅ / **작성자 본인 삭제 🔴 없음**(§4 공백)
- 사진: 개설자 삭제 ✅ / **운영자 강제 삭제 🔴 없음**(§4 공백)
- **선제 필터 없음** — 욕설·스팸 자동 차단이 전혀 없습니다. 사별 직후 유족이 악성 글을 먼저 보게
  되는 건 서비스가 만든 2차 피해입니다(`03-02` §4.5가 인정한 위험인데 대책은 사후 삭제뿐).
- 🟡 **권고**: 최소한 **금칙어 필터 + 신규 방명록 작성 시 개설자 알림**은 있어야 합니다. 자동
  차단까지는 과하더라도, 상주가 "새 글이 달렸다"를 알아야 빨리 지울 수 있습니다.

### 6.3 ✅ 정보 품질 검증 (카탈로그) — 유일하게 이미 다뤄진 층

`03-02` §3.1의 `lastVerifiedAt` + Sonnet이 API 레벨로 강제한 규칙(공개 전환 시 확인일 필수).
**이건 잘 된 부분이고 그대로 유지합니다.** §12-3에서 스펙에 명문화합니다.

### 6.4 🔴 개발 검증 (회귀 테스트) — 프로젝트 전반 문제

Domain 03 백엔드 구현에서 **실제 HTTP 검증 65건을 수행했지만 전부 임시 스크립트였고 실행 후
삭제됐습니다.** Domain 01·02도 같은 방식이었습니다. 결과적으로 **이 프로젝트에는 회귀 테스트가
한 건도 없습니다.**

지금까지는 괜찮았지만, 도메인이 3개가 되고 서로 얽히기 시작하면(예: `User` 삭제가 03 데이터에
미치는 영향) 수동 검증으로는 회귀를 못 잡습니다.

> 🔴 이건 03만의 문제가 아니라 **플랫폼 전체 사안**이라 별도 논의가 필요합니다. 최소한
> "검증 스크립트를 지우지 말고 `eobom/backend/tests/`에 남긴다"는 규칙만 세워도 큰 차이가 납니다.

## ⚠️ 7. 🟡 위협 모델 — 체계적으로 다시

`03-02` §4.3은 **허위 추모관 하나만** 봤습니다. 그래서 그리핑을 놓쳤습니다. 전수 정리:

| # | 위협 | 피해자 | 현재 대응 | 평가 |
| :---: | :--- | :--- | :--- | :--- |
| T1 | 살아있는 사람의 추모관 개설 | 당사자(명예훼손) | 로그인+고지동의+기본 비공개+신고 | 🟡 부분적 |
| T2 | **신고 남용으로 정상 추모관 차단** | **유족** | **없음** | 🔴 **미대응** |
| T3 | 방명록 악성글·스팸 | 유족 | 사후 삭제만 | 🟡 §6.2 |
| T4 | 부적절 사진 업로드 | 유족·조문객 | 개설자 삭제만 | 🔴 운영자 수단 없음 |
| T5 | slug 무작위 대입으로 비공개 추모관 탐색 | 유족 | 128비트 랜덤 토큰 | ✅ 충분 |
| T6 | 고인 정보 공개 색인 → 보이스피싱 표적 | 유족 | 기본 `LINK`+화이트리스트 | ✅ 적절 |
| T7 | 유족 간 관리권 분쟁 | 유족 | 없음(선착순 개설자 독점) | 🔴 미대응(나중 논의) |

### 7.1 T2 — 신고 남용

**현재 구조의 문제**: 익명 1회 신고 → 즉시 전면 차단. 누구나 slug만 알면 남의 추모관을 반복해서
내릴 수 있습니다. §4.3-3에 *"피해가 되돌릴 수 없는 종류"* 라고 썼는데, **사별 직후 추모관이 갑자기
안 열리는 것도 되돌릴 수 없는 피해**입니다 — 조문객은 접속이 안 되고 상주는 이유를 모릅니다.

**익명 신고와 즉시 차단은 양립할 수 없습니다.** 둘 중 하나를 포기해야 합니다.

| 안 | 내용 | 장단 |
| :--- | :--- | :--- |
| **A** | **신고 로그인 필수** + 즉시 차단 유지 + 개설자 즉시 알림·이의제기 | T1 대응력 유지, 남용 추적 가능. 신고 문턱은 올라감 |
| **B** | 익명 유지 + **임계치 누적 후 차단**(N건 또는 운영자 확인 후) | 신고 접근성 유지. T1 대응이 느려짐 |
| **C** | 이원화 — 로그인 신고는 즉시, 익명 신고는 누적 | 가장 정교하나 복잡도 증가 |

**권고: A.** 실제 명예훼손 피해자는 로그인해서라도 신고할 동기가 충분하고, 장난 신고는 계정
추적이 가능해지는 순간 급감합니다. 무엇보다 **개설자 알림·이의제기 경로가 없는 게 지금 가장 큰
결함**이라, 어느 안을 고르든 이건 필수입니다.

> 🔴 대표 확정 필요.

## 🏢 8. 🔴 운영 부하 — 아직 아무도 계산하지 않았다

`03-02`는 운영자 화면(§8.3)을 정의했지만 **운영자가 하루에 몇 건을 처리해야 하는지 아무도 추정한
적이 없습니다.** 이 도메인은 다른 도메인과 부하 성격이 다릅니다:

- **01·02**: 사업자·전문가 가입 심사 — 건수가 적고(수십~수백), 급하지 않음
- **03**: 추모관 신고 — **건수 예측 불가, 시간 민감**(장례 기간 중 차단되면 그날 안에 풀어야 함)

정해야 할 것:
1. 신고 처리 **목표 응답 시간** — 부고 성격상 몇 시간 이내여야 합니까?
2. **야간·주말 대응** — 사망은 시간을 가리지 않습니다. 금요일 밤에 신고당한 추모관은?
3. 운영자 **인원과 근무 형태** — 현재 운영자 계정은 시드로만 만들고 실제 담당자가 정해진 적 없습니다.

**§6.1 게이트 설계도 이 답에 달려 있습니다** — `PUBLIC` 승인제를 도입하려면 승인을 처리할 사람이
있어야 합니다. 아무도 없으면 승인제는 그냥 "PUBLIC 기능이 없는 것"과 같습니다.

## 💰 9. 🔴 비용·수익 구조 — 이 도메인만 수익 모델이 없다

| 도메인 | 수익 | 비용 |
| :--- | :--- | :--- |
| 01 | 리드 수수료 | 낮음 |
| 02 | 월정액 광고·상담 수수료(Stage 2) | 낮음 |
| **03** | **없음** | **영구 스토리지 + 운영 인력** |

### 9.1 추모관은 "영구 보존"을 약속하면 비용이 영구히 발생합니다

사진·방명록을 계속 보관해야 하고, 유족은 당연히 영구 보존을 기대합니다. 그런데 수익이 0입니다.
`03-02` §10-1이 "보존기간"을 대표 확정 사항으로 넘겼지만, **비용 구조를 계산해본 적이 없어서
판단 근거가 없는 상태**입니다.

### 9.2 선택지

- **(A) 완전 무료 + 기간 제한** — 예: 1년 후 자동 정리(사전 고지·연장 옵션). 비용 통제 가능, 신뢰 손상 위험.
- **(B) 무료 + 유료 영구보존** — 기본은 기간 제한, 유료로 영구 전환. PG 필요(대표 승인 대상).
- **(C) 완전 무료 영구** — 브랜드 자산으로 간주하고 비용을 마케팅비로 처리. 규모 커지면 부담.
- **(D) 장례식장 제휴 상품** — 01 파트너가 유족에게 제공하는 부가 서비스로 묶어 B2B 과금.

🟡 **권고: (D)를 우선 검토.** 이어봄은 이미 01에 장사시설 파트너망을 갖고 있고, 추모관은 장례식장이
유족에게 제공하기 좋은 부가가치입니다. 소비자에게 직접 과금하지 않아 사별 상황에서의 거부감도
없습니다. 다만 **`00-11` 인프라 결정(스토리지 비용 실측)이 나와야 숫자를 붙일 수 있습니다.**

### 9.3 관련 — 장례식장이 추모관을 대신 개설하는 모델

(D)와 연결됩니다. 파트너(장례식장)가 유족 대신 추모관을 만들어주면 §3.2의 "경황 없는 유족" 문제가
크게 완화되고, §6.1 신원 검증도 **파트너가 실질적으로 보증**하는 효과가 생깁니다. 🟡 별도 검토 대상.

## 🎯 10. ✅ 성공 기준과 비목표

### 10.1 이 도메인이 성공했다는 것

1. 유족이 **사망 당일에** 추모관을 만들어 부고를 보낼 수 있다 (개설 소요 3분 이내)
2. 조문객이 **로그인 없이** 헌화·방명록을 남긴다 (링크 수신 → 조의 표현 전환율)
3. 유족이 디지털 계정 정리에서 **"뭘 해야 하는지 알게 된다"** — 대행이 아니라 안내가 목표(§2)
4. 신고 처리가 **목표 시간 내** 이뤄진다 (§8-1)

### 10.2 명시적 비목표 — 하지 않기로 한 것

| 안 하는 것 | 이유 |
| :--- | :--- |
| 고인 계정 대리 접속·대행 신청 | `03-02` §1.1 — 법적으로 불가 |
| 금융·가상자산·정산금 처리 | `03-02` §3.2 C분류 |
| 현물 유품 수거업체 매칭 | 계정 형태 기획 보류(`03-01` §3) |
| SNS 자동 연동으로 고인 계정 탐지 | 각 사 API 없음 + 개인정보 리스크 |
| 추모관 SNS 자동 공유 | §6 T6 — 확산 주체는 유족이어야 함 |
