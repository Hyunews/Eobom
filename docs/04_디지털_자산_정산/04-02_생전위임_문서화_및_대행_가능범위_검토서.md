# 🤝 04-02. 생전 위임 문서화 · 대행 가능 범위 — 검토서

> **문서 성격**: 검토서 · **외부 전문가 의뢰 전 내부 정리**. `[Claude:Opus]` 작성(2026-08-14).
> **계기**: `00-14` §5-1·§5-2에 대한 개발자 질의 —
> > **§5-1** *"엔딩노트 내용 실현 같은 건 법적 절차에 따라 전문가에게 맡기되, **디지털 정산 정도는
> > 맡아서 대행할 수 있지 않을까**. 법적 구속을 받지 않는 선에서 **대행자에게 미리 맡길 수 있을만한
> > 서비스가 있는지** 파악해줘."*
> > **§5-2** *"생전 위임 시 문서화를 해놓아도 **결국 효력이 없다는 얘기인건가?** 아니면 **법적인
> > 서식(양식)이 필요**하다는 건가?"*
>
> **정본 관계**: `00-12` §2.4·§8-1(생전 위임 개념) · `02-04` §4(위임 문서화) · `04-01` §9(①②③)를
> **한 곳에서 답하는 문서**입니다. 세 문서는 각자 *"법률 검토 필요"* 라고만 적고 넘겼습니다.
> **표기**: ✅ 확정 사실 / 🟡 권고 / 🔴 외부 확인 필요

> ⚠️ **이 문서는 법률 자문이 아닙니다.** 법령·판례 서술은 **의뢰 시 질문지의 초안**이지 결론이
> 아닙니다. §7이 그 질문지입니다. 플랫폼별 기능(§4)은 **수시로 바뀌므로 확인일 기준**입니다.

## 📌 1. 먼저 §5-2에 답합니다 — **"효력이 없다"가 아닙니다**

> 질문: *"문서화를 해놓아도 결국 효력이 없다는 얘기인건가?"*

**아닙니다. 정확히는 이렇습니다.**

| 오해 | 실제 |
| :--- | :--- |
| *"위임은 사망하면 무효니까 문서화가 헛일"* | ❌ **위임이 "무효"가 아니라 "종료"가 원칙**이고, **그 원칙은 특약으로 바꿀 수 있다**는 것이 통설입니다 |
| *"법정 서식(양식)만 갖추면 된다"* | ❌ **위임에는 법정 서식이 없습니다.** 유언과 달리 방식 요건이 없어서, **양식을 만든다고 강해지지 않습니다** |
| — | ✅ **문제는 "형식"이 아니라 "그릇"입니다.** 무엇을 맡기느냐에 따라 위임으로 충분한 것과 유언·신탁이 필요한 것이 갈립니다(§3) |

### 1.1 근거 — 민법 제690조와 그 한계

**민법 제690조**: *"위임은 당사자 한쪽의 사망이나 파산으로 종료된다."*
이유는 위임이 **당사자 사이의 신뢰(인적 신뢰관계)** 위에 서 있기 때문입니다.

**그런데 이 조문은 강행규정이 아니라는 것이 통설입니다.** 실무에서
**「사후사무 위임계약」**(장례·묘지 관리·유품 처리 등을 내용으로, *"위임인이 사망하더라도 이
계약은 종료되지 아니한다"* 는 특약을 붙인 계약)이 사용되는 것이 그 방증입니다.

> 🔵 **참고로 대법원은 위임의 해지에 관한 민법 §689에 대해, 당사자가 다르게 정했다면
> "약정에서 정한 해지사유·절차에 의하지 않고는 해지할 수 없다"고 판시했습니다**
> (대법원 2019. 5. 30. 선고 2017다53265). §690에 대한 직접 판시는 아니지만,
> **위임 규정이 당사자 약정에 양보한다는 태도**는 읽을 수 있습니다.
>
> 🔴 **§690 자체에 대한 판례 확인은 §7-1 의뢰 항목입니다.** 여기서 단정하지 않습니다.

### 1.2 🔴 그럼에도 위임이 약한 이유 2가지 — **이게 진짜 답입니다**

특약을 붙여도 남는 구멍이 있습니다.

| # | 구멍 | 결과 |
| :---: | :--- | :--- |
| **1** | 위임인의 지위가 **상속인에게 승계**된다면, 상속인이 민법 §689로 **해지**할 수 있습니다 | *"고인이 이렇게 맡겼다"* 를 **유족이 뒤집을 수 있음** |
| **2** | 위임은 **권한을 주는 것이지 재산을 옮기는 것이 아닙니다.** 사망 순간 재산은 상속인 것입니다 | **재산 처분은 위임으로 못 함** — 유언·신탁이 필요 |

> **✅ 그래서 결론은 "효력이 없다"가 아니라 "위임은 재산에 못 미친다"입니다.**
> 그리고 **디지털 계정 정리는 대부분 재산이 아닙니다**(`04-01` §1.1 — 금융·가상자산·정산금은
> 이미 배제했습니다). **개발자 직관대로, 이 영역은 위임으로 충분한 영역입니다.**

## 🧱 2. 그릇 3층 — 무엇을 맡기느냐로 갈립니다

| 층 | 그릇 | 사후 효력 | 방식 요건 | 이어봄이 다루는 것 |
| :---: | :--- | :--- | :--- | :--- |
| **1** | **플랫폼 내 사전 지정**(서비스 설정) | ⭕ **가장 확실** — 약관에 따른 계약 이행이라 §690 논점이 **생기지 않음** | 각 사 화면에서 클릭 | **§4 — 이 문서의 핵심 권고** |
| **2** | **사후사무 위임계약**(특약 서면) | 🟡 성립 가능. 단 §1.2의 구멍 | **법정 서식 없음**. 서면·의사 명확성이 실질 요건 | 계정 정리 지시(`PreDeathDirective`) |
| **3** | **유언 / 유언대용신탁** | ⭕ 확실 | 🔴 **민법 5방식 등 엄격**(`06-02` §4) | ❌ 이어봄이 만들지 않음 → 02 연결 |

> 게 아니라 연결한다"* 였습니다. **여기서도 같습니다 — 1층은 플랫폼이 이미 만들어놨습니다.**

## 🎯 3. §5-1에 답합니다 — 대행의 3단계

> 질문: *"디지털 정산 정도는 맡아서 대행할 수 있지 않을까?"*

**"대행"이라는 한 단어에 성격이 다른 셋이 섞여 있습니다. 갈라야 답이 나옵니다.**

| 단계 | 하는 일 | 법적 성격 | 이어봄이 할 수 있나 |
| :---: | :--- | :--- | :---: |
| **A** | 안내·알림·진행 추적·지정 여부 기록 | **법률행위 아님** | ✅ **가능** — 이미 `04-01` §2가 그것 |
| **B** | 고인 계정에 **대신 로그인**, 플랫폼에 **대신 신청서 제출** | **법률행위 대리** | ❌ **불가** — §3.1 |
| **C** | 위임에 근거한 유상 신청 대행 | **행정사 업무 영역** | ❌ 불가 → 02 행정사 연결(`04-01` §3.4) |

### 3.1 🔴 B가 막히는 이유는 법이 아니라 **문이 없어서**입니다

**이게 이 검토에서 가장 중요한 사실이고, 순서를 뒤집으면 안 됩니다.**

`04-01` §1.1이 이미 확인했습니다 — **주요 플랫폼(구글·메타·애플·네이버·카카오)은 유족 요청을
각 사 공식 폼으로 받아 자체 심사하며, 제휴사·대리인용 채널을 공개한 곳이 없습니다.**

> **즉 "생전 위임이 있으니 이어봄이 대행해도 되나?"를 변호사에게 물어 "됩니다"라는 답을 받아도,
> 구글이 이어봄을 대리인으로 받아주지 않으면 실행 경로가 없습니다.**
>
> 🔴 **그래서 §7 의뢰 순서를 바꿉니다** — 법률 검토를 먼저 하지 말고,
> **"주요 플랫폼 중 제3자 대리를 허용하는 곳이 하나라도 있는가"를 먼저 확인**합니다.
> 하나도 없으면 **법률 검토 자체가 불필요합니다.**

그리고 자격증명(ID/PW)을 받아 로그인하는 경로는 **생전 위임이 있어도 열리지 않습니다** —
`04-01` §1.1-2가 *"협상 대상이 아니다"* 라고 못박은 그대로입니다.
**본인이 생전에 허락해도 정보통신망법상 평가가 달라진다고 단정할 수 없고, 무엇보다
계정 이용권은 일신전속적 성격이 강해 상속되지 않는다는 것이 통설입니다.**

## 🔑 4. ✅ 그래서 실제 답 — **"이어봄이 대행자가 되는 게 아니라, 이용자가 미리 지정하게 한다"**

> 개발자 질문의 *"대행자에게 미리 맡길 수 있을만한 서비스가 있는지 파악해줘"* 에 대한 답입니다.
> **있습니다. 그리고 이미 만들어져 있으며, 무료이고, 법적 효력도 확실합니다.**

### 4.1 주요 플랫폼의 사전 지정 기능

**이용자가 생전에 각 플랫폼에서 직접 지정해두는 기능**입니다. 플랫폼과 이용자 사이의 계약이므로
**민법 §690의 위임 종료 논점이 아예 생기지 않습니다**(§2 1층).

| 플랫폼 | 기능 | 무엇을 미리 정하나 |
| :--- | :--- | :--- |
| **Google** | **휴면 계정 관리자**(Inactive Account Manager) | 일정 기간 미사용 시 **지정한 사람에게 데이터 일부를 공유**하고, **계정 삭제를 예약**할 수 있음 |
| **Apple** | **디지털 유산 관리자**(Legacy Contact) | 지정인이 **접근 키 + 사망증명서**로 계정 데이터에 접근 |
| **Meta**(Facebook·Instagram) | **추모 계정 관리자**(Legacy Contact) | 사후 **추모 계정 전환** 또는 **삭제**를 미리 선택 |
| **카카오** | 추모 프로필 | 사후 처리 방식 |
| **네이버** | 유족 요청 절차 | 🔴 **생전 사전 지정 기능 유무 확인 필요** |

> ⚠️ **위 표는 2026-08-14 확인 기준이며, 명칭·조건·제공 범위가 수시로 바뀝니다.**
> **그래서 이 정보는 문서가 아니라 `DigitalPlatform` 카탈로그(`04-01` §3.1)에 들어가야 하고,
> `lastVerifiedAt` 강제 규칙의 대상입니다.** 문서에 박아두면 반드시 썩습니다.

### 4.2 🟡 이어봄의 역할 — `06-02` §3과 완전히 같은 형태

`06-02`가 연명의료에 대해 내린 결론을 **그대로 복사할 수 있습니다.**

| | 연명의료(`06-02` §3) | **디지털 계정(이 문서)** |
| :--- | :--- | :--- |
| 진짜 효력이 생기는 곳 | **보건복지부 지정 등록기관** | **각 플랫폼의 사전 지정 설정** |
| 앱에 쓴 것 | 효력 없음 | 효력 없음(플랫폼이 안 봄) |
| **이어봄의 역할** | **안내 + 등록 여부 기록** | **안내 + 지정 여부 기록** |
| 비용 | 0 | 0 |
| 개인정보 수집 | 없음 | 없음 |

**설계**:

```prisma
// PreDeathDirective(00-12 §2.4)의 하위 — 플랫폼별 사전 지정 현황
model PreDeathPlatformSetting {
  id          String   @id @default(uuid())
  directiveId String              // FK → PreDeathDirective
  platformId  String              // FK → DigitalPlatform (04-01 §3.1 카탈로그)

  hasNativeFeature Boolean         // 이 플랫폼에 사전 지정 기능이 있나 (카탈로그에서 복사)
  configuredAt     DateTime?       // 본인이 "설정 완료" 체크한 시각 — 이어봄은 검증하지 않음
  intent           String?         // MEMORIALIZE | DELETE | TRANSFER_TO_FAMILY | KEEP (04-01 §4.1 어휘)
  note             String?         // 유족에게 남기는 한 줄

  // ⚠️ 지정한 사람의 이름·연락처는 저장하지 않는다 —
  //    그건 플랫폼에 이미 있고, 여기 두면 제3자 개인정보가 새로 생긴다(00-13 §4.4 D안이 걸린 지점)
}
```

> ✅ **`configuredAt`은 "본인이 체크했다"는 사실일 뿐 이어봄이 검증한 것이 아닙니다.**
> 검증하려면 계정에 접근해야 하고, 그건 §3.1에서 닫았습니다.
> **화면 문구도 *"설정하셨나요?"* 여야지 *"확인했습니다"* 가 되면 안 됩니다.**

### 4.3 ✅ 그리고 **이어봄 자신의 계정에 대해서는 100% 대행할 수 있습니다**

**놓치기 쉬운데, 가장 확실한 답입니다.**

§3.1이 막은 것은 *"남의 플랫폼"* 이었습니다. **이어봄 계정 안에서는 이어봄이 당사자**이므로
약관으로 정하면 그만이고, 제3자의 허락이 필요 없습니다.

| 이어봄이 자기 서비스 안에서 할 수 있는 대행 | 근거 |
| :--- | :--- |
| 고인 계정 **`MEMORIALIZED` 전환**(로그인 차단·알림 중단·데이터 보존) | `00-12` §5.3 |
| **엔딩노트 전달** — L3·L4 통과 시 지정 유족에게 | `06-02` §5 |
| **추모관 개설 권한**을 지정 유족에게 이양 | `05-01` |
| 진행 중인 리드·상담의 정리 | `01-05`·`02-03` |
| 사전 지정 현황(§4.2)을 **유족에게 요약해 전달** | 이 문서 |
| 🆕 **생전에 만든 계정 목록(`04-01` §0.4 ①)을 유족에게 전달** — 유족은 **발견 단계를 건너뜁니다** | `04-01` §0.4-2 |

> **✅ 이것이 "법적 구속을 받지 않는 선에서 미리 맡길 수 있는 서비스"의 실체입니다.**
> 이어봄이 파는 것은 *"구글 계정을 대신 지워드립니다"* 가 아니라
> **"당신이 미리 정해둔 것을 사후에 빠짐없이 꺼내 유족 손에 쥐여드립니다"** 입니다.
> **이건 지금 설계로 전부 가능하고, 법률 검토가 필요 없습니다.**

## 💰 5. 🟡 유상으로 하면 달라집니다

`00-12` §2.4가 ③(운영자 대행)에 **대행 수수료**를 적어둔 것이 논점을 키웠습니다.

| | 무상 부가서비스 | **유상 대행** |
| :--- | :--- | :--- |
| 행정사법 저촉 | 낮음 — 규제는 대체로 **"업으로" 하는 것**을 겨눔 | 🔴 **검토 필요** |
| 플랫폼 약관 | 여전히 §3.1 문제 | 동일 |
| 사고 시 책임 | 낮음 | **유상 = 채무불이행 책임** |

> 🟡 **권고: §4.2·§4.3 범위는 무상 부가서비스로 둡니다.**
> 이 범위는 **04를 무료 훅으로 두고 02(전문가)로 유입시키는** 기존 수익 구조(`04-01` §9 ①→②,
> `07-01` §6)와도 어긋나지 않습니다. **③을 유상 상품으로 세우는 것은 §3.1이 풀린 다음입니다.**

| 담아야 할 것 | 이유 |
| :--- | :--- |
| **플랫폼별 처리 의사**(`intent`) | ①②③ 어느 쪽이든 *"무엇을 원했나"* 가 본체 |
| **사전 지정 완료 여부**(§4.2) | 이게 실제 효력의 원천 |
| **위임 의사 문구 + 동의 시각** | §2 2층. 서식은 없어도 **의사가 명확해야** 함 |
| **지정 유족과의 연결**(`BereavedRelation`) | 집행 주체 |
| ❌ 계정 자격증명 | **절대 안 됨**(`04-01` §1.1-2) |
| ❌ 지정인의 제3자 개인정보 | §4.2 주석 |

> 🟡 **문구 권고 — 위임 의사 표시 (§2 2층의 실질 요건)**
>
> *"본인은 사망 이후 아래 계정들에 대한 처리 의사가 위와 같음을 밝히며, 이어봄이 이 내용을
> 보관하였다가 사망 확인 후 지정 유족에게 전달하는 것에 동의합니다. 이어봄은 본인을 대리하여
> 각 서비스에 신청·해지를 수행하지 않으며, 실제 처리는 유족 또는 유족이 선임한 전문가가
> 각 서비스의 절차에 따라 진행합니다."*
>
> **핵심은 마지막 문장입니다** — *"대리하지 않는다"* 를 이용자에게 먼저 말하는 것이
> `04-01` §2.1의 경계를 화면에서 지키는 방법입니다.

## ❓ 7. 확인이 필요한 것 — **의뢰 질문지**

`00-14` §5는 *"회의에서는 의뢰할지 말지만 정하면 된다"* 고 했습니다. **의뢰한다면 이 순서입니다.**

### 7.1 순서가 중요합니다

| 순서 | 확인 대상 | 누구에게 | 비용 | 이 답에 달린 것 |
| :---: | :--- | :--- | :--- | :--- |
| **0** | **주요 플랫폼이 제3자 대리를 허용하는가**(§3.1) | 🟡 **내부 조사로 가능** — 각 사 약관·고객센터 | **0** | 아래 전부. **NO면 1·2 불필요** |
| 1 | 민법 §690 특약의 유효성 · **상속인 해지 가능성**(§1.2-1) | 변호사 | 유료 | ② 행정사 위임(`02-04` §4) |
| 2 | **유상 대행의 행정사법 저촉**(§5) | 변호사 | 유료 | ③ 상품화 |
| 3 | 위임 의사 문구 검토(§6) | 변호사 | 유료 | 06 면책 문구(`06-02` §7-1)와 **함께 의뢰 가능** |

> **✅ 0번을 먼저 하십시오. 비용이 0이고, 결과에 따라 1·2가 통째로 사라집니다.**
> `00-14` §5-1·§5-2를 *"같은 법률가에게 함께"* 라고 묶은 판단은 유효하지만,
> **그 앞에 무료 단계가 하나 있다는 것이 이 검토의 결론입니다.**

### 7.2 착수를 막지 않는 것

| 지금 바로 가능 | 근거 |
| :--- | :--- |
| **§4.2 사전 지정 안내 + 지정 여부 기록** | 법률 검토 불필요. `06-02` §3과 동일 구조 |
| **§4.3 이어봄 자체 계정 처리** | 우리가 당사자 |
| `DigitalPlatform` 카탈로그에 **`hasNativeFeature` 컬럼 추가** | `04-01` §3.1 확장 |
| 🆕 **개인정보 포털 「본인확인 내역 조회」 안내**(생전 계정 발견) | `04-03` §2.2-1 · `04-01` §0.4 ①·§0.4-1 |

> **§5-1의 실질적 답은 "지금 할 수 있는 게 이미 있다"입니다.**
> 대행 권한을 얻으려 애쓰는 것보다, **각 플랫폼이 이미 열어둔 문을 이용자에게 알려주는 것**이
> 더 빠르고 확실하며 비용이 없습니다.
>
> 🆕 **2026-08-31 — 세 번째 사례가 붙었습니다.** 앞의 둘이 **각 플랫폼이 열어둔 문**이었다면,
> 이번 것은 **국가가 열어둔 문**입니다. `privacy.go.kr`의 본인확인 내역 조회는
> **유족에게는 닫혀 있고 본인에게만 열립니다**(`04-03` §2.2-1). **그래서 생전 축의 자산입니다.**
> 🔴 **이어봄은 대신 조회하지 않습니다** — 새 탭으로 보내고, 돌아온 이용자가 **카탈로그에서 체크**합니다.
> **조회 결과 원본은 이어봄 서버에 들어오지 않습니다**(`04-01` §0.4-1 · §8.1-6).
