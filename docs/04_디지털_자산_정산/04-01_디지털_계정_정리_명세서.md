## 🎁 0. 이 도메인이 제공하는 것 (2026-08-31 확정)

> 🔴 **이 절이 먼저 읽혀야 합니다.** §1~§5는 *"무엇을 안 하는가"* 를 먼저 정하느라
> **"무엇을 하는가"가 문서 어디에도 한 덩어리로 없었습니다.** 여기서 세웁니다.

### 0.1 한 문장

> **이어봄 04는 고인의 계정을 여는 서비스가 아닙니다.**
> **흩어진 계정을 찾아내 목록으로 만들고 · 급한 순서로 세우고 · 각 창구에 유족이 직접 낼 수 있게
> 하고 · 끝났는지까지 보이게 하는 서비스입니다.**

**"대신 해준다"가 아니라 "빠짐없이 끝내게 한다"** 입니다. 이 차이가 §1.1(대행 불가)과
§2.1(안내+추적)을 하나로 묶는 문장이고, 화면 첫 줄에 그대로 씁니다.

### 0.2 유족 축 — 화면 흐름 4단계 (`DigitalEstatePage`)

**STEP 0. 먼저 아셔야 할 것** *(펼침 없이 항상 보이는 4줄)*

1. **고인의 아이디·비밀번호는 어디서도 받으실 수 없습니다** — KISO 정책규정 §28①(`04-03` §1.1)
2. **받으실 수 있는 것**: 계정 폐쇄·구독 해지 · 추모 전환 · 공개 게시물 백업(사업자 재량) ·
   사이버머니 등 **경제적 가치가 있는 것의 청구**(KISO §28②)
3. **플랫폼은 사망 사실을 자동으로 알지 못합니다** — 알리지 않으면 그대로 남습니다
4. 🆕 **개인정보 포털(`privacy.go.kr`)의 「본인확인 내역 조회」는 본인만 이용할 수 있습니다** —
   고인 명의로는 유족이 조회하실 수 없습니다(`04-03` §2.2-1)

> 🔴 **이 4줄을 아끼면 그대로 CS가 됩니다**(`04-03` §1.3). **근거 조문을 인용해 둘 것.**
> 🆕 **4번은 "없는 경로"를 지우는 대신 "왜 안 되는지"를 남긴 것입니다.** **유족은 이 서비스를
> 검색해서 찾아옵니다**(2026-08-31 실제 문의로 확인). 화면이 먼저 답하지 않으면 문의가 됩니다.

**STEP 1. 계정 찾기** — 🆕 **신설. 이 도메인에서 유일하게 카탈로그보다 앞에 오는 화면**

> 🆕 **STEP 1을 통째로 건너뛰는 경우가 하나 있습니다 — 고인이 생전에 목록을 남겨둔 경우**(§0.4-2).
> 그때 유족은 **발견 없이 STEP 2에서 시작**합니다. **이것이 04의 생전 축이 유족 축에 주는 실질입니다.**

> ✅ **1-D는 새 데이터가 필요 없습니다** — **`DigitalPlatform` 카탈로그를

**STEP 3. 처리하고 끝을 보기** — 항목마다 카탈로그의 `actionType`·`requiredDocs`·`officialUrl`·
`estimatedDays`를 펴 보여주고, **유족이 직접 신청**한 뒤 상태를 스스로 체크합니다(§5.2).
화면 상단에 **진행률**과 **오래 멈춘 항목**(`PREPARING`·`SUBMITTED`에서 `estimatedDays` 초과)을 세웁니다.

### 0.3 🆕 우선순위 — **4순위 자동 정렬** (`04-03` §3.2를 순서로 바꾼 것)

| 순위 | 무엇 | 왜 먼저인가 |
| :---: | :--- | :--- |
| **1** | 💸 **구독·결제** (`actionType: CANCEL`) | **지금 이 순간에도 돈이 나갑니다.** 카드가 살아 있는 한 계속 결제됩니다 |
| **2** | 💰 **경제적 가치** (페이 잔액·포인트·마일리지) | KISO §28② — **청구하지 않으면 소멸**합니다 |
| **3** | 🔒 **보안** (메일·SNS·클라우드 `DELETE`) | 방치 계정은 사칭·스미싱에 재활용되고 **2차 피해가 유족에게** 옵니다 |
| **4** | 🕯️ **추모** (`MEMORIALIZE`) | 급하지 않고, **서두르면 되돌릴 수 없습니다** |

> 🔵 **정리는 삭제가 아닙니다.** 같은 유족이 어떤 계정은 지우고 싶고 어떤 계정은 남기고 싶습니다.
> §4.1의 `actionType` 3분류(`DELETE`·`MEMORIALIZE`·`CANCEL`)가 **그 선택 자체**이며,
> `04-03` §3.3이 이 3분류가 옳았음을 확인했습니다.
> 🔴 **정렬 기준은 `policy.ts`에 둡니다** — 화면 하드코딩 금지(§8.1-3).

### 0.4-1 🆕 🔴 조회 결과를 이어봄 데이터로 가져오는 방법 — **"보면서 체크"** (2026-08-31 확정)

**①의 실무 쟁점은 하나입니다: 포털에서 본 목록이 어떻게 우리 항목이 되는가.** 5가지를 검토했습니다.

| 방식 | 판정 |
| :--- | :--- |
| **공공 API 연동** | ❌ **개인정보 포털은 개방 API를 제공하지 않습니다.** 존재하지 않는 경로입니다 |
| **스크래핑·자동 로그인** | ❌ **본인인증을 이어봄이 대리 수행하는 것**이 됩니다. §0.5 1번(자격증명 불취급)의 정면 위반이고 위법 소지 |
| **결과 파일 임포트** | 🟡 다운로드 기능 유무 자체가 **미확인**(`04-03` §6-5). 있더라도 **파일을 서버에 올리는 순간 개인정보가 새로 생깁니다** |
| **화면 캡처 + OCR** | ❌ **§8.1-2의 "OCR 검증" 금지선과 정면 충돌.** 남의 인증 이력 이미지를 서버에 두는 일 |
| ✅ **카탈로그 체크 + 직접 입력** | ⭕ **권고 — 확정** |

**확정안 (3단계, 새 API·새 파서·새 모델 0개)**

1. 화면의 **「새 창에서 조회하기」** 버튼 → `privacy.go.kr` **새 탭**으로 보냅니다. *(우리는 아무것도 받지 않습니다)*
2. 돌아와서 **`DigitalPlatform` 카탈로그 그리드에서 해당하는 것을 체크**합니다 —
   🔵 **§0.2 STEP 1-D(회상 체크리스트)와 완전히 같은 컴포넌트**를 다시 씁니다.
3. 카탈로그에 없으면 **`customName` 한 줄 직접 입력**(§4.2).

> 🔴 **우리가 가져오는 것은 "조회 결과"가 아니라 "사용자의 선택"입니다.**
> 인증기관·인증일시·인증수단 같은 **조회 결과 원본은 이어봄 서버에 들어오지 않습니다.**
> 들어오는 것은 **"이 서비스에 가입돼 있다"는 사실 한 줄**뿐이며, 이는 §0.5와 정합합니다.

> 🔵 **수동이 열등한 대안이 아니라, 필터가 필요해서 수동인 것입니다.**
> 조회 결과에는 **단순 성인·실명인증이 섞여 가입하지 않은 사이트도 나옵니다**(`04-03` §2.2-1).
> **자동 임포트는 그 노이즈까지 그대로 들여와 목록을 오염시킵니다.** 사람이 한 번 걸러야 합니다.

### 0.4-2 🆕 생전 목록은 유족에게 넘어갑니다 — **STEP 1을 건너뛰게 하는 유일한 경로**

**①에서 만든 목록은 본인의 것으로 끝나지 않습니다.** 사망 확인 후 유족에게 열리고,
유족은 **발견 없이 STEP 2(목록)에서 시작**해 **각 사이트에 직접 정리를 요청**합니다.

| | 생전 목록이 **없을 때** | 생전 목록이 **있을 때** |
| :--- | :--- | :--- |
| 유족의 시작점 | STEP 1 — 안심상속·금감원·기억 | ✅ **STEP 2 — 목록이 이미 있습니다** |

## 🔐 3. 디지털 계정 정리 — 설계

### 3.1 플랫폼 안내 카탈로그는 코드가 아니라 데이터다

플랫폼별 유족 정책은 **자주 바뀌고 우리가 통제할 수 없습니다.** 절차를 코드나 문서에 하드코딩하면
바뀔 때마다 배포가 필요하고, 낡은 안내는 그 자체로 유족에게 피해를 줍니다.

따라서 **`DigitalPlatform` 테이블로 관리하고 운영자가 화면에서 갱신**합니다.
(`01-05` §12의 "하드코딩 제거" 원칙과 같은 판단입니다.)

각 레코드는 **`lastVerifiedAt`(최종 확인일)을 필수로 보유**하고, 화면에 함께 노출합니다.
확인일이 오래된 항목은 운영자 화면에서 경고 표시합니다.

> ⚠️ **초기 데이터 입력 시 주의**: 각 플랫폼의 실제 유족 처리 절차는 **입력 시점에 공식 고객센터
> 문서를 직접 확인해서** 채워야 합니다. 기억이나 추정으로 채우면 안 됩니다 — 유족이 그대로 따라
> 하다가 시간을 버리는 실질적 피해가 발생합니다. 확인 못 한 플랫폼은 **레코드를 만들지 않는 편이
> 낫습니다**(빈 카탈로그가 틀린 카탈로그보다 낫습니다).

### 3.2 지원 대상 분류

| 분류 | 처리 | 예 |
| :--- | :--- | :--- |
| **A. 안내 대상** | 카탈로그에 등록, 유족이 직접 신청 | 이메일·SNS·클라우드·구독 서비스 계정의 삭제/추모 전환/해지 |
| **B. 연결 대상** | 안내만 하고 **Domain 02 상담으로 유도** | 위임 대행이 필요한 건, 절차가 복잡한 건 |
| **C. 배제 대상** | **카탈로그에 넣지 않음** + 안내 문구로 명시적 차단 | 금융계좌, 가상자산, 정산금·포인트 등 재산적 청구권 |

**C를 화면에서 그냥 빼는 것으로 끝내지 않고, "이런 항목은 이어봄이 다루지 않으며 금융기관/거래소에
직접 문의하셔야 합니다"라고 적극적으로 안내**합니다. 목업이 이미 이 기능을 약속했었기 때문에,
조용히 사라지면 유족이 계속 찾게 됩니다.

### 3.3 증빙 서류는 받지 않는다

§2.2대로 **가족관계증명서·사망진단서를 이어봄 서버에 업로드받지 않습니다.**
현재 목업의 파일 업로드 UI는 **제거**합니다.

- 대신 각 플랫폼이 요구하는 서류를 **체크리스트로 안내**만 합니다("이 서류를 준비해 ○○에 제출하세요").
- 유족이 "준비 완료"를 스스로 체크할 수는 있지만, **파일 자체는 저장하지 않습니다.**
- 위임 대행 때문에 서류가 꼭 필요해지면, 그건 §3.4대로 행정사(Domain 02)와 유족 사이의 일이며
  이어봄 서버를 경유하지 않습니다.

> 이 결정은 **되돌리기 쉬운 방향입니다** — 나중에 필요하면 업로드를 추가하는 것은 간단하지만,
> 한 번 수집한 민감 서류는 유출되면 회수할 수 없습니다. 안 받는 쪽을 기본값으로 둡니다.

> 🔵 **`00-12` §4 사다리와의 관계**: 이 결정은 **L0~L1 행위(안내·체크리스트)에 대한 것**입니다.
> **L3 행위(운영자 대행·엔딩노트 개봉)에는 서류 확인이 필요**하며, 그건 §10과 `00-12` §4.2의
> 별개 사안입니다. **이 §3.3을 L3에 유추 적용하지 마십시오** — 층이 다릅니다.

### 3.4 Domain 02 연결 지점

### 4.2 `DigitalCleanupItem` (신규) — 유족 개인의 진행 추적

| 컬럼 | 타입 | 설명 |
| :--- | :--- | :--- |
| `id` | String @id | UUID |
| `userId` | String | **FK → User** (§4.3 원칙) — 🔵 **이 행을 소유하고 보는 사람** |
| `deceasedId` | String? | 🆕 **FK → `Deceased.id`** — **누구의 계정에 대한 정리인가.** `null`이면 *"내 것"*(생전 본인) |
| `origin` | String | 🆕 `MANUAL`(직접 추가) \| `DISCOVERED`(STEP 1 발견) \| `INHERITED`(생전 목록 승계) @default(`MANUAL`) |
| `platformId` | String? | FK → DigitalPlatform (직접 입력 항목이면 null) |
| `customName` | String? | 카탈로그에 없는 서비스를 유족이 직접 추가한 경우 |
| `status` | String | `TODO` \| `PREPARING`(서류 준비 중) \| `SUBMITTED`(신청함) \| `DONE` \| `BLOCKED` |
| `statusHistory` | Json | `[{status, at, note}]` |
| `memo` | String? | 유족 개인 메모 (접수번호 등을 본인이 적어두는 칸) |
| `createdAt` / `updatedAt` | DateTime | |

**인덱스**: 🆕 `[userId, deceasedId, status]` — 🔴 기존 `[userId, status]`를 **교체**합니다.
인덱스는 **왼쪽부터 순서대로만** 쓰이므로 `userId` 단독 조회는 그대로 유지되고,
*"이 유족이 보는 고인 A의 미완료 항목"* 이 색인 한 번에 잡힙니다.

**증빙 파일 컬럼은 없습니다** — §3.3. `02-03` §3.2와 같은 논리로 **없는 필드는 실수로 채워질 수 없습니다.**

#### 4.2-1 🆕 `deceasedId`는 `User`가 아니라 `Deceased`를 가리킵니다 (2026-08-31 확정 · §10 #5)

**`User.id`로 걸면 안 됩니다.** `Deceased.userId`는 `String?`이고 주석이 *"비회원 고인이면 null(케이스 B)"* 입니다
(`00-05` · `00-12` §2.1). 즉 **고인이 이어봄 회원이 아닌 경우가 오히려 다수**이고, 그 사람들에게는
`User` 행이 없습니다. `Deceased`를 가리켜야 회원·비회원 두 경우를 다 담습니다.

| 고인 | `Deceased` | `User` |
| :--- | :--- | :--- |
| 회원이었던 경우 | `userId="u-123"` → 원 계정에 닿음 | 있음 |
| 비회원 | `userId=null` | ❌ 없음 — `User.id`로 걸었다면 **담을 방법이 없음** |

> 🔵 **`userId`의 뜻이 흔들리는 게 아닙니다.** `userId`는 생전·사후 모두 일관되게 *"보는 사람"* 입니다.
> 없던 것은 *"대상이 누구냐"* 를 담는 칸이고, 그게 없어서 유족 화면에 **아버지 목록과 어머니 목록이
> 한 덩어리로** 쏟아졌습니다.

#### 4.2-2 🔴 승계 컬럼은 2단계로 나눕니다 — 생전 축 모델이 아직 없습니다

`PreDeathDirective`·`PreDeathPlatformSetting`은 **`schema.prisma`에 존재하지 않습니다**
(`00-05` 모델 28개 중 0건). 따라서 승계 원본을 가리킬 FK 대상이 아직 없습니다.

| 단계 | 컬럼 | 조건 |
| :---: | :--- | :--- |
| **A** (지금 가능) | `deceasedId` · `origin` · 인덱스 교체 | `Deceased`는 **이미 있음**(`20260820021848_obituary_deceased_phase1`) |
| **B** (생전 축 신설 때) | `sourceSettingId` String? · `inheritedIntent` String? · `inheritedNote` String? | `PreDeathPlatformSetting` 생성이 선행 |

🔴 **A·B 모두 실제 마이그레이션입니다** — `backup-db.ps1` 선행 + CONFIRM(§1 정정 주석).

### 4.3 `User` 변경 — `03-01` §2 원칙 반영

```prisma
model User {
  // ... 기존 필드
  digitalCleanupItems DigitalCleanupItem[]  // docs 04-01 — 디지털 정리 진행 항목
```

**`03-01` §2가 요구한 것이 바로 이것입니다** — 이 도메인의 모든 모델이 `userId` FK로 `User`에

## ⏳ 9. 🔴 생전 축 — 이 도메인이 "양쪽"인 이유

> 개발자 지시(2026-08-12): *"죽기 전의 고인이 정산에 대한 계획을 미리 신청해놓고, 처리 방식을 미리
> 선택하는 선택지를 주는 게 옳지 않나. 1)유족처리 2)행정사처리 3)운영자가 대신처리."*

`00-12` §2.4의 `PreDeathDirective`가 **이 도메인에 붙습니다.** 이것이 04를 생전·유족 양쪽 도메인으로
만드는 유일한 요소입니다.

| 처리 방식 | 이어봄 역할 | 수익 | 법적 근거 |
| :--- | :--- | :--- | :--- |
| **① 유족 처리** | 안내·진행 추적 | 없음(무료 훅) | 낮음 — 이 문서 §2~5가 그것 |
| **② 행정사 처리** | 연결·중개 | 중개 수수료 | `02-01` 기존 검토 활용 |
| **③ 운영자 대행** | **직접 처리** | **대행 수수료** | 🔴 **신규 법률 검토 필수** |

**②③은 이 문서의 범위가 아닙니다.** ③은 §1.1의 제약을 생전 위임으로 푸는 시도이며,
`00-12` §8-1(외부 전문가 법률 검토)이 선행되어야 합니다.

### 9.1 🟡 승계 원칙 — 04는 "전달"이 아니라 "위임"입니다

`00-12` 논의에서 확정된 구분입니다.

| | Domain 06 엔딩노트 | **Domain 04 (이 문서)** |
| :--- | :--- | :--- |
| 성격 | **전달** — "이걸 받아라" | **위임** — "이걸 처리해라" |
| 수신자 | 항상 유족 | 유족 / 행정사 / 운영자 |
| 유족의 역할 | 받는 사람 | **하는 사람** |

**고인이 유족에게 무언가를 남기는 통로는 06 하나**라는 원칙이 있는데, 04가 예외인 이유가 이것입니다 —
04의 지시는 수신자가 유족이 아닐 수도 있어서 06을 경유할 수 없습니다.

### 10.1 🆕 승계 흐름 — 시간순 (2026-08-31 확정 · #6)

| 시점 | 무슨 일이 일어나나 | DB |
| :---: | :--- | :--- |
| **T0** 생전 | 본인이 `intent`와 함께 계정 목록을 남김(§0.4 ①) | `PreDeathPlatformSetting` **생성**. 🔵 `status`가 없습니다 — 처리가 아니라 **의사 표시**이므로 |
| **T1** 사망 | — | 🔵 **아무 일도 일어나지 않습니다.** 아직 아무도 모릅니다 |
| **T2** 사망 확인 | 유족이 `00-12` §4 사다리를 통과(06 엔딩노트와 **같은 절차**) | `Deceased` 생성 + `FamilyDesignation` → `BereavedRelation` 승격(`00-27` §1.2). 🔵 **유족임을 아는 근거가 여기입니다** |
| **T3** 승계 | T0의 각 줄을 읽어 **유족 앞으로 새 행을 만듦** | `DigitalCleanupItem` **INSERT** — `userId`=유족 · `deceasedId`=고인 · `origin=INHERITED` · `status=TODO`(여기서 처음 생김). 🔴 **T0 원본은 손대지 않습니다** |
| **T4** 처리 | 유족이 `TODO → SUBMITTED → DONE` 진행 | 유족 행에만 기록. 고인 기록은 불변 |

**① 왜 이관이 아니라 복사인가** — 이관은 `UPDATE ... SET userId = 유족`으로 **주인을 바꿔치기**하는 것입니다.
그러면 T4에서 유족이 상태를 바꾸는 순간 **고인이 T0에 남긴 의사가 덮여 사라집니다.**

| | 이관 | ✅ 복사 |
| :--- | :--- | :--- |
| 고인의 T0 기록 | 🔴 **소실** | 보존 |
| *"아버지는 뭐라고 하셨나"* | 확인 불가 | 원본 조회 |
| 유족이 2명 | 🔴 행이 하나뿐이라 나눌 수 없음 | 각자 복사본 |
| 되돌리기 | 불가 | 복사본만 삭제 |

**② 고인의 기록은 증거입니다.** 유족의 *작업 진행 상황*과 고인의 *생전 의사*는 성격이 다릅니다.
후자 위에 전자를 덮어쓰면 나중에 **"고인이 정말 삭제를 원했는가"** 를 확인할 방법이 없어집니다.

**③ `inheritedIntent`는 조인이 아니라 복사**(§4.2-2 B단계) — 화면에 띄울 때마다 원본을 찾아가는 게
아니라 **승계 시점의 값을 찍어서 박아둡니다.** 원본이 어떻게 되든 유족이 보던 화면은 흔들리지 않습니다.

**④ 🆕 STEP 1을 건너뜁니다** — `origin=INHERITED` 행이 있으면 유족은 발견 단계 없이 STEP 2에서 시작합니다(§0.4-2).

**⑤ 🟡 유족이 여럿이면 각자 복사본을 가집니다** — 딸과 아들이 서로 모른 채 같은 곳에 두 번 요청할 수 있습니다.
🔵 **04에서 새로 설계하지 않습니다.** `FamilyDesignation.scope`(`PRIMARY`\|`VIEWER`)가 **이미 있고**,
`00-27` §6이 *"`PRIMARY` = 실제 절차를 밟을 사람"* 으로 정의해 두었습니다.
04가 할 일은 **처리 버튼을 `PRIMARY`에게만 여는 것 한 줄**이며, `PRIMARY` 복수 허용 여부는 `00-27` §6의 결론을 따릅니다(#7).
