## 📌 1. 현황 진단 — 목업이 약속한 것과 실제로 가능한 것

이 도메인은 **백엔드 모델이 0개**이고 `DigitalEstatePage.tsx`의 로컬 state로만 존재합니다.
그런데 단순 미구현보다 중요한 문제가 있습니다. **현재 목업이 화면에서 약속하는 기능 상당수는 구현이
어려운 게 아니라 법적으로 해서는 안 되는 것**입니다.

| 목업이 약속한 것 (`mockData/digitalEstate.json`) | 실제 판단 |
| :--- | :--- |
| "업비트/빗썸 — 상속 포트폴리오 자산 상속 출금" | ❌ **배제.** 가상자산 상속은 거래소 고유의 상속인 확인 절차. 중개하면 무인가 영업 리스크 |

### 1.1 왜 "대행"이 성립하지 않는가

1. **제3자 대행 창구가 존재하지 않습니다.** 주요 플랫폼(구글·메타·애플·네이버·카카오)은 유족 요청을
   **각 사 공식 폼으로 접수해 자체 심사**합니다. 제휴사·대리인용 API나 B2B 채널을 공개한 곳이 없습니다.
   즉 "이어봄이 대신 처리"할 기술적 경로 자체가 없습니다.
2. **고인 계정 자격증명(ID/PW)을 받아 로그인하는 것은 하면 안 됩니다.** 계정 이용권은 일신전속적
   성격이 강해 당연히 상속되지 않는다는 것이 통설이고, 유족이라 해도 타인 계정 접속은
   **정보통신망법상 침해행위**로 평가될 소지가 있습니다. **이어봄은 고인의 자격증명을 어떤 형태로도
   수집·저장·입력하지 않습니다.** 이것은 협상 대상이 아닙니다.
3. **위임에 의한 신청 대행이 필요하다면 그것은 행정사 업무 영역**입니다. 우리에게는 이미
   Domain 02에 `ADMINISTRATIVE_SCRIVENER`(행정사) 직역이 있고, `02-03` §7.1이 이 직역을
   **"디지털 유품 행정사"**로 이미 명명해 두었습니다.

> **그래서 이 도메인은 대행하지 않고, 대행이 필요한 유족을 Domain 02로 보냅니다.**

### 1.2 🟡 다만 이 제약은 생전 위임으로 풀릴 수 있습니다

`00-12` §2.4(개발자 제안)가 이 판단의 전제를 흔듭니다. 제가 "대행할 수 없다"고 단정한 근거는
*"고인의 위임 의사를 사후에 확인할 방법이 없다"* 였는데, **본인이 생전에 위임 의사를 명시해두면
전제가 달라집니다.** §10에서 다룹니다.

## 🎯 2. 이 도메인의 재정의 — "대행"이 아니라 "안내 + 진행 추적"

### 2.1 이어봄이 하는 일 / 하지 않는 일

| 이어봄이 하는 일 | 이어봄이 하지 않는 일 |
| :--- | :--- |
| 플랫폼별 **공식 유족 절차 안내**(필요 서류·신청 경로·예상 소요) | 고인 계정에 **대신 로그인** |
| 유족이 직접 신청한 건의 **진행 상태 추적**(체크리스트) | 플랫폼에 **대신 신청서 제출** |
| 필요 서류 **체크리스트 제공** | 증빙 서류 **수집·보관** (§3.3) |
| 대행이 필요하면 **Domain 02 행정사 연결** | 금융·가상자산·정산금 등 **재산 처리 개입** |

### 2.2 이 재정의가 만드는 이득

- **증빙 서류를 우리가 받지 않아도 됩니다.** 유족이 각 플랫폼에 직접 제출하므로,
  가족관계증명서·사망진단서(고유식별정보 포함 가능성이 높은 최고 민감도 서류)를
  이어봄 서버에 저장할 이유가 사라집니다. **가장 큰 개인정보 사고 경로를 설계 단계에서 제거**합니다.
- **법적 리스크가 "정보 제공"의 수준으로 내려갑니다.** 남는 의무는 안내 정보를 정확하게 유지하는 것뿐입니다.
- **Domain 02의 상담 인프라(`ConsultRequest`)를 그대로 재사용**합니다. 새 정산·과금 구조가 필요 없습니다.

### 2.3 이번 범위 (Stage 1)

1. **플랫폼 안내 카탈로그**(`DigitalPlatform`) — 운영자가 관리하는 마스터 데이터
2. **유족 개인의 정리 진행 추적**(`DigitalCleanupItem`) — 체크리스트 + 상태
3. 운영자 화면에서 **회원 상세 조인 조회**(→ `03-01` §2 원칙)

### 2.4 이번 범위 제외

| 제외 항목 | 이유 |
| :--- | :--- |
| 현물 유품 수거 | **Domain 03으로 분리**. 계정 형태 기획은 여전히 보류(→ `03-01` §3) |
| 온라인 추모관 | **Domain 05로 분리**(→ `05-01`) |
| 위임 대행 실행 | 행정사 업무 영역 → Domain 02 상담으로 연결(§3.4). 단 §10 생전 위임은 별개 |
| 금융·가상자산·정산금 | §1.1 — 상속재산 처리는 Domain 02(세무사·변호사) |
| 부고 문자 발송 | Domain 07(상중·행정 케어) 또는 05(추모관) — `00-13` 결정 대기 |

**Stage 1은 결제가 없으므로 사장님 승인 없이 착수 가능합니다**(`02-03` Stage 1과 동일 구조).

## 🔐 3. 디지털 계정 정리 — 설계

### 3.1 플랫폼 안내 카탈로그는 코드가 아니라 데이터다

플랫폼별 유족 정책은 **자주 바뀌고 우리가 통제할 수 없습니다.** 절차를 코드나 문서에 하드코딩하면
바뀔 때마다 배포가 필요하고, 낡은 안내는 그 자체로 유족에게 피해를 줍니다.

따라서 **`DigitalPlatform` 테이블로 관리하고 운영자가 화면에서 갱신**합니다.
(`01-05` §12의 "하드코딩 제거" 원칙과 같은 판단입니다.)

각 레코드는 **`lastVerifiedAt`(최종 확인일)을 필수로 보유**하고, 화면에 함께 노출합니다.
확인일이 오래된 항목은 운영자 화면에서 경고 표시합니다.

> ⚠️ **초기 데이터 입력 시 주의**: 각 플랫폼의 실제 유족 처리 절차는 **입력 시점에 공식 고객센터
> 문서를 직접 확인해서** 채워야 합니다. 기억이나 추정으로 채우면 안 됩니다 — 유족이 그대로 따라
> 하다가 시간을 버리는 실질적 피해가 발생합니다. 확인 못 한 플랫폼은 **레코드를 만들지 않는 편이
> 낫습니다**(빈 카탈로그가 틀린 카탈로그보다 낫습니다).

### 3.2 지원 대상 분류

| 분류 | 처리 | 예 |
| :--- | :--- | :--- |
| **A. 안내 대상** | 카탈로그에 등록, 유족이 직접 신청 | 이메일·SNS·클라우드·구독 서비스 계정의 삭제/추모 전환/해지 |
| **B. 연결 대상** | 안내만 하고 **Domain 02 상담으로 유도** | 위임 대행이 필요한 건, 절차가 복잡한 건 |
| **C. 배제 대상** | **카탈로그에 넣지 않음** + 안내 문구로 명시적 차단 | 금융계좌, 가상자산, 정산금·포인트 등 재산적 청구권 |

**C를 화면에서 그냥 빼는 것으로 끝내지 않고, "이런 항목은 이어봄이 다루지 않으며 금융기관/거래소에
직접 문의하셔야 합니다"라고 적극적으로 안내**합니다. 목업이 이미 이 기능을 약속했었기 때문에,
조용히 사라지면 유족이 계속 찾게 됩니다.

### 3.3 증빙 서류는 받지 않는다

§2.2대로 **가족관계증명서·사망진단서를 이어봄 서버에 업로드받지 않습니다.**
현재 목업의 파일 업로드 UI는 **제거**합니다.

- 대신 각 플랫폼이 요구하는 서류를 **체크리스트로 안내**만 합니다("이 서류를 준비해 ○○에 제출하세요").
- 유족이 "준비 완료"를 스스로 체크할 수는 있지만, **파일 자체는 저장하지 않습니다.**
- 위임 대행 때문에 서류가 꼭 필요해지면, 그건 §3.4대로 행정사(Domain 02)와 유족 사이의 일이며
  이어봄 서버를 경유하지 않습니다.

> 이 결정은 **되돌리기 쉬운 방향입니다** — 나중에 필요하면 업로드를 추가하는 것은 간단하지만,
> 한 번 수집한 민감 서류는 유출되면 회수할 수 없습니다. 안 받는 쪽을 기본값으로 둡니다.

> 🔵 **`00-12` §4 사다리와의 관계**: 이 결정은 **L0~L1 행위(안내·체크리스트)에 대한 것**입니다.
> **L3 행위(운영자 대행·엔딩노트 개봉)에는 서류 확인이 필요**하며, 그건 §10과 `00-12` §4.2의
> 별개 사안입니다. **이 §3.3을 L3에 유추 적용하지 마십시오** — 층이 다릅니다.

### 3.4 Domain 02 연결 지점

`DigitalPlatform.needsAgentHelp = true`인 항목, 또는 유족이 "직접 하기 어렵다"를 선택하면
**`CounselingPage`(SCR-007)의 행정사 카테고리로 연결**합니다.

- 새 API를 만들지 않고 기존 `POST /api/experts/:id/consult-requests`를 그대로 씁니다(`02-03` §5.2).
- 상담 신청 시 `content`에 어떤 플랫폼 건인지 프리필하면 전문가가 맥락을 바로 파악합니다.
- **주의**: 이 연결은 단순 화면 이동이며, 이 도메인이 상담 수수료를 갖는 구조를 만들지 않습니다.
  변호사법·`02-03` §3의 가드레일은 그쪽 문서가 정본이며 여기서 새로 만들지 않습니다.

## 🗄️ 4. 데이터 모델 (Prisma)

### 4.1 `DigitalPlatform` (신규) — 플랫폼 안내 카탈로그

운영자가 관리하는 마스터 데이터. 유저 데이터가 아닙니다.

| 컬럼 | 타입 | 설명 |
| :--- | :--- | :--- |
| `id` | String @id | UUID |
| `name` | String | 표시명 (예: `네이버`) |
| `category` | String | `EMAIL` \| `SNS` \| `CLOUD` \| `SUBSCRIPTION` \| `ETC` |
| `actionType` | String | `DELETE`(삭제) \| `MEMORIALIZE`(추모 전환) \| `CANCEL`(해지) |
| `officialUrl` | String? | 공식 유족 절차 안내 페이지 |
| `requiredDocs` | String[] | 필요 서류 체크리스트 |
| `guideSummary` | String | 절차 요약 (유족이 읽는 본문) |
| `estimatedDays` | Int? | 예상 소요일 (참고값) |
| `needsAgentHelp` | Boolean @default(false) | true면 행정사 상담 유도(§3.4) |
| `isPublished` | Boolean @default(false) | 확인 완료 전에는 노출 안 함 |
| `lastVerifiedAt` | DateTime? | **최종 확인일 — 화면에 함께 노출**(§3.1) |
| `sortOrder` | Int @default(0) | 노출 순서 |
| `createdAt` / `updatedAt` | DateTime | |

**금융·가상자산 플랫폼은 이 테이블에 넣지 않습니다**(§3.2 C분류).

> `actionType: MEMORIALIZE`는 **우리가 남에게 안내하는 처리**입니다. `00-12` §5.3은 **같은 개념을
> 이어봄 자신의 `User`에도 적용**하기로 했습니다(`MEMORIALIZED` 상태). 용어가 일치합니다.

### 4.2 `DigitalCleanupItem` (신규) — 유족 개인의 진행 추적

| 컬럼 | 타입 | 설명 |
| :--- | :--- | :--- |
| `id` | String @id | UUID |
| `userId` | String | **FK → User** (§4.3 원칙) |
| `platformId` | String? | FK → DigitalPlatform (직접 입력 항목이면 null) |
| `customName` | String? | 카탈로그에 없는 서비스를 유족이 직접 추가한 경우 |
| `status` | String | `TODO` \| `PREPARING`(서류 준비 중) \| `SUBMITTED`(신청함) \| `DONE` \| `BLOCKED` |
| `statusHistory` | Json | `[{status, at, note}]` |
| `memo` | String? | 유족 개인 메모 (접수번호 등을 본인이 적어두는 칸) |
| `createdAt` / `updatedAt` | DateTime | |

**인덱스**: `[userId, status]`
**증빙 파일 컬럼은 없습니다** — §3.3. `02-03` §3.2와 같은 논리로 **없는 필드는 실수로 채워질 수 없습니다.**

> 🔴 **재편으로 생긴 미결**: `DigitalCleanupItem`은 지금 `userId`(유족)에만 붙어 있고 **어느 고인의
> 정리인지가 없습니다.** `00-12` §2.1의 `Deceased` 엔티티가 도입되면 `deceasedId` FK가 필요합니다 —
> 한 사람이 부모 두 분의 정리를 각각 진행하는 경우를 지금 스키마로는 구분할 수 없습니다.

### 4.3 `User` 변경 — `03-01` §2 원칙 반영

```prisma
model User {
  // ... 기존 필드
  digitalCleanupItems DigitalCleanupItem[]  // docs 04-01 — 디지털 정리 진행 항목
}
```

**`03-01` §2가 요구한 것이 바로 이것입니다** — 이 도메인의 모든 모델이 `userId` FK로 `User`에
연결되어야 운영자가 회원 상세에서 `prisma.user.findUnique({ include: {...} })` 한 번으로
조인 조회할 수 있습니다(§5.4).

## ⏳ 9. 🔴 생전 축 — 이 도메인이 "양쪽"인 이유

> 개발자 지시(2026-08-12): *"죽기 전의 고인이 정산에 대한 계획을 미리 신청해놓고, 처리 방식을 미리
> 선택하는 선택지를 주는 게 옳지 않나. 1)유족처리 2)행정사처리 3)운영자가 대신처리."*

`00-12` §2.4의 `PreDeathDirective`가 **이 도메인에 붙습니다.** 이것이 04를 생전·유족 양쪽 도메인으로
만드는 유일한 요소입니다.

| 처리 방식 | 이어봄 역할 | 수익 | 법적 근거 |
| :--- | :--- | :--- | :--- |
| **① 유족 처리** | 안내·진행 추적 | 없음(무료 훅) | 낮음 — 이 문서 §2~5가 그것 |
| **② 행정사 처리** | 연결·중개 | 중개 수수료 | `02-01` 기존 검토 활용 |
| **③ 운영자 대행** | **직접 처리** | **대행 수수료** | 🔴 **신규 법률 검토 필수** |

**②③은 이 문서의 범위가 아닙니다.** ③은 §1.1의 제약을 생전 위임으로 푸는 시도이며,
`00-12` §8-1(외부 전문가 법률 검토)이 선행되어야 합니다.

### 9.1 🟡 승계 원칙 — 04는 "전달"이 아니라 "위임"입니다

`00-12` 논의에서 확정된 구분입니다.

| | Domain 06 엔딩노트 | **Domain 04 (이 문서)** |
| :--- | :--- | :--- |
| 성격 | **전달** — "이걸 받아라" | **위임** — "이걸 처리해라" |
| 수신자 | 항상 유족 | 유족 / 행정사 / 운영자 |
| 유족의 역할 | 받는 사람 | **하는 사람** |

**고인이 유족에게 무언가를 남기는 통로는 06 하나**라는 원칙이 있는데, 04가 예외인 이유가 이것입니다 —
04의 지시는 수신자가 유족이 아닐 수도 있어서 06을 경유할 수 없습니다.
