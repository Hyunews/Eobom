## 📌 1. 확정된 것 — 그리고 확정되지 **않은** 것

계정 형태는 세 선택지 중 **기존 `Partner` 확장**으로 확정됐습니다(2026-08-14, `00-14` §4-2).

| 선택지 | 결과 |
| :--- | :--- |
| 신규 계정 유형 신설 | ❌ |
| **기존 `Partner` 확장** | ✅ **채택** |
| 외주 제휴사로 처리(계정 없음) | ❌ |

**업종**: "유품 수거"라는 단일 업종은 없습니다(2026-10-06 개발자 확정). 유치 대상은 **특수청소 업체 · 폐기물 수거 업체 등 기존 업종의 사업자**이고, 이어봄 안에서는 이들을 **하나의 파트너 유형처럼 묶어** 다룹니다(업종마다 계정·목록을 나누지 않음). 업체 카드에는 업종을 표시합니다(`serviceTags`, §3.1 · §8 #3).

### 1.1 ✅ 이 선택이 옳은 이유 — 우연이 아니라 구조가 같습니다

| | Domain 01 장사시설 | **Domain 03 (이 문서)** |
| :--- | :--- | :--- |
| 사업자가 하는 일 | 유족의 문의를 받아 **오프라인에서 수행** | 동일 |
| 이어봄이 하는 일 | **리드 전달 + 수수료 정산** | 동일 |
| 필요한 계정 요소 | 사업자등록번호·상호·정산 계좌·승인 상태 | **동일** |
| 이어봄의 개입 깊이 | 매칭까지. 서비스 품질은 사업자 책임 | 동일 |

**`Partner` 모델(`schema.prisma`의 `model Partner`)의 필드를 하나도 버리지 않고 그대로 씁니다.**
`Expert`(02)를 따로 만든 것과 대조됩니다 — 전문가는 **자격증 검증·직역·변호사법 가드레일**이라는
전혀 다른 요구가 있었지만, 유품 수거 업체는 **장사시설과 요구가 같습니다.**

### 1.2 🔴 확정되지 않은 것 — "계정을 어떻게 만드나"와 "사업을 할 것인가"는 다릅니다

이 문서는 **계정·데이터·화면 설계까지만** 답합니다. 업체 모집 개시 여부·시점과 수수료 기준·요율은 사장님 결정이며, 미결 목록의 정본은 **§8**(#1·#4)입니다.

## 🔑 3. 계정 설계 — `Partner` 확장

### 3.1 🔴 현행 `Partner`는 "장사시설 사업자"를 암묵적으로 전제하고 있습니다

업종 축은 **`Partner.partnerType`** 으로 이미 들어가 있습니다(2026-08-18, §4.1 · `schema.prisma` 주석이 이 절을 가리킴).
`FUNERAL_FACILITY`(01 장사시설, 기본값) | `ESTATE_CLEANUP`(03) — 기본값이 01이라 기존 데이터·흐름에 영향이 없습니다.

남은 전제는 관계 필드입니다. 4개 중 2개가 **01 전용**입니다.

```prisma
facilities  Facility[]        // 01 전용 — 수거 업체는 시설을 갖지 않음
claims      FacilityClaim[]   // 01 전용 — 클레임할 공공데이터 시설이 없음(§3.2 · 03-03 결정 대기)
leads       Lead[]            // ✅ 공용
settlements Settlement[]      // ✅ 공용
```

**03 전용 필드 3개는 아직 넣지 않았습니다**(§7.1 1단계). 읽거나 쓰는 코드 없이 넣으면 필드만 있고 안 채워지는 문제(`00-14` §2.2류)를 새로 만들기 때문입니다.

```prisma
model Partner {
  // ... 기존 필드 + partnerType(✅ 있음)
  serviceAreas String[]  // ESTATE_CLEANUP 전용 — 출동 가능 시·군·구 코드
  serviceTags  String[]  // ESTATE_CLEANUP 전용 — 일반정리 | 특수청소 | 폐기물운반 | 기부연계 ... (화면 업종 표시, §6.3)
  licenseNo    String?   // ESTATE_CLEANUP 전용 — 폐기물처리업 허가·신고 번호(§6.1)
}
```

> 🔴 **`licenseNo` 자리는 `03-03` §5와 다릅니다** — `03-03`은 공공데이터 명부를 `Facility`에 적재하자며 허가번호를 `Facility`에 둡니다. **`03-03` 결정과 함께 정합니다**(§8 #11).

> ✅ **`contextType`(`02-04` §5) · `partnerType` 둘 다 "기본값으로 무해하게 축을 하나 더한다"는
> 같은 패턴입니다** — 열거형 컬럼 + 안전한 기본값 = 기존 데이터 무영향.

### 3.2 🟡 업체 목록은 **어디서 오나** — 01과 결정적으로 다른 점

| | Domain 01 | **Domain 03** |
| :--- | :--- | :--- |
| 초기 목록 | 공공데이터(보건복지부 장례식장 API · 봉안시설·자연장지 CSV) | 🔴 **`03-03` 결정 대기** — 지금은 예시 데이터 10건(`mockData/digitalEstate.json`)뿐 |
| 명부가 보장하는 것 | 업종 = 목적(장례식장) | 공공 명부(전국폐기물처리업소표준데이터)는 **허가 종류**일 뿐, 유품 정리를 하는지는 모름(`03-03` §2) |
| 사용자가 보는 것 | 전국 시설 + 제휴사 | 예시 업체(§7.2) |

**지금 정본**: 업체가 스스로 가입 신청 → 운영자 승인(`Partner.status` `PENDING → APPROVED`). 승인은 서류 심사가 아닙니다(§6.1 무심사).

> 🔴 **`03-03`이 이 절을 고치자고 제안했습니다** — 폐기물처리업 허가 명부(공공데이터)를 적재하고, 카카오 로컬 API의 "유품정리·특수청소" 상호와 겹치는 업체만 유족에게 보여 주는 안(C안 — 적재 ≠ 노출). 채택되면 01처럼 *"목록을 먼저 그리고 업체가 클레임하는"* 구조가 03에도 생깁니다. **확정 전이라 여기 반영하지 않았습니다**(§8 #11).
>
> ⚠️ 제휴 업체가 0건인 동안 화면에 보여줄 것이 없다는 문제는 그대로입니다 — 지금은 예시 데이터로 채우고 있고, 그 조건이 §7.2입니다.

## 🔄 4. 리드·정산 — 01 인프라를 그대로 재사용합니다

**새로 만들 것이 거의 없습니다.** `01-05`가 만든 것이 01 전용이 아니라 **파트너 공용**이기 때문입니다.

| 요소 | 재사용 여부 | 비고 |
| :--- | :---: | :--- |
| `Lead` (리드 로그) | ⭕ | ✅ `facilityId` nullable(2026-08-18). 업종별 강제 규칙 → §4.1 |
| `Lead.type` | ⭕ | 03 수거 견적은 `QUOTE`에 얹습니다. **새 `type` 값을 만들지 않고** 집계는 `partnerType`으로 가릅니다 |
| `leadNo` 발번(`EB-YYMMDD-NNNN`) | ⭕ | 그대로 |
| `CommissionPolicy` (요율 정책) | ⭕ | **`partnerType`별 기본 요율**을 둘 수 있음 |
| `Settlement` (월 정산) | ⭕ | 그대로 |
| 제3자 제공 동의 | ⭕ | **문구만 03용으로**(수거 업체에 연락처가 넘어감) |
| 사업자 가입·승인 화면(SCR-008·009) | 🟡 | **업종 선택 추가** — 미착수(§7.1 2단계) |

### 4.1 `Lead.facilityId`는 업종별로 앱에서 강제합니다

컬럼은 nullable이고(DB 제약 완화), 규칙은 **애플리케이션이 `partnerType`별로** 지킵니다(`schema.prisma`의 `Lead.facilityId` 주석).

| 업종 | 규칙 | 상태 |
| :--- | :--- | :--- |
| `FUNERAL_FACILITY` | `facilityId` **필수** | ✅ 서 있음 — 리드 생성의 유일한 경로 `leadService.ts`의 `createLead`가 `facilityId`를 필수 타입으로 받고, 시설이 없으면 `FacilityNotFoundError` |
| `ESTATE_CLEANUP` | `facilityId` **null 허용** | 🔴 **03 리드 생성 경로가 아직 없음** — §5 `CleanupRequest` 구현 때 분기 규칙을 반드시 신설 |

> ⚠️ **DB 제약을 앱 로직으로 옮긴 변경**이라 강제 코드가 빠지면 **조용히** 깨집니다(`00-15` §3 회귀 테스트 근거). `CleanupRequest` 착수 시 이 표를 먼저 볼 것. 2026-08-18 마이그레이션 기록과 변경 전 스키마는 부록.

### 4.2 🟡 수수료 기준은 01을 따릅니다

01의 수수료 기준(`01-05` §10 — 리드 건당 / 성사 건당 / 월 정액, 사장님 결정 대기)이 정해지면 **같은 기준을 03에 적용**하고,
요율만 다르게 둡니다. `CommissionPolicy` 레코드 입력으로 끝나므로 코드 수정이 필요 없습니다(`01-05` §12 정책 계층).

> 🟡 **03은 성사 건당이 더 잘 맞습니다** — 유품 정리는 단가가 크고 건수가 적어,
> 리드 건당 과금은 업체 저항이 큽니다.

## 🗄️ 5. 데이터 모델 — 신규는 최소한으로

`Partner` 확장(§3.1) 외에 **신규 모델은 1개**입니다. 🔴 **미구현**(§7.1 3단계).

```prisma
// 유품 수거 요청 — 유족이 남기는 견적 요청. Lead로 이어짐
model CleanupRequest {
  id         String   @id @default(uuid())
  userId     String              // FK → User (03-01 §2 원칙)
  deceasedId String?             // FK → Deceased (00-12 §2.1) — 확정 후 부착
  partnerId  String?             // 지정 요청이면 값, 지역 일괄 요청이면 null

  areaCode     String            // 작업 지역 시·군·구
  propertyType String            // APARTMENT | HOUSE | VILLA | OFFICE ...
  sizePyeong   Int?              // 평수 — 견적의 핵심 변수
  serviceTags  String[]          // 요청 항목(§3.1 serviceTags와 같은 어휘)
  preferredAt  DateTime?         // 희망 일정
  memo         String?

  status    String   @default("REQUESTED")  // REQUESTED | MATCHED | DONE | CANCELED
  createdAt DateTime @default(now())

  @@index([userId])
  @@index([areaCode, status])
}
```

> **`04-01` `DigitalCleanupItem` · `07-01` `AdminTaskProgress`와 같은 형태**입니다 —
> **유족 개인의 요청 1건 = 레코드 1건**.

> 🟡 **사진 첨부는 1차에서 넣지 않습니다.** 견적 정확도는 올라가지만 **고인의 주거 내부 사진**은
> 민감도가 높고, 파일 저장소 분리는 확정(2026-09-03, `00-11`)됐지만 아직 로컬 디스크라 재배포 때 사라집니다
> (`.harness/systems.md` §5 · `05-01` §2.6 추모 사진과 같은 제약).

## ⚠️ 6. 이 도메인 고유의 위험 — 01·02와 다릅니다

### 6.1 🔴 "유품정리업"은 법정 업종이 아닙니다

**유품정리업·특수청소업이라는 이름의 허가·등록 제도는 없습니다.**
업체들이 실제로 하는 일을 쪼개 보면 각각 다른 법에 걸립니다.

| 실제 행위 | 관련 규제 | 해당 업체 |
| :--- | :--- | :--- |
| 폐기물 수집·운반을 **업으로** 수행 | **폐기물관리법 §25** 폐기물처리업 허가 / 신고 | 허가·신고 번호 보유 |
| 재활용품·중고물품 매입·판매 | 지자체 신고 등 | 해당 시 |
| 청소·정리 용역만 수행(배출은 유족 명의) | 별도 규제 없음 | 사업자등록증 |

시장에서는 *"폐기물 처리 서비스 · 재활용센터 · 청소 전문업체"* 같은 **기존 업종 이름으로** 이미 영업 중입니다(2026-08-19 실측) — 위 3분류가 그대로 관측됩니다.

#### 🔵 2026-08-19 개발자 확정 — **업체 심사를 하지 않습니다. 이 절은 보류합니다.**
