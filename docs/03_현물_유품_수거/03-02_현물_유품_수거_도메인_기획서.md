> **문서 성격**: 상위 기획서 · **이 도메인의 첫 기획 문서**. `[Claude:Opus]` 작성(2026-08-14).

> > *"현물 유품 관련 **Partner로 운영**. 다른 Partner와 마찬가지 **별도의 Domain으로 운영**하는 것이

## 📌 1. 확정된 것 — 그리고 확정되지 **않은** 것

`03-01` §3은 세 선택지를 놓고 보류 중이었습니다. 개발자가 첫 번째를 골랐습니다.

| 선택지 | 결과 |
| :--- | :--- |
| 신규 계정 유형 신설 | ❌ |
| **기존 `Partner` 확장** | ✅ **채택** |
| 외주 제휴사로 처리(계정 없음) | ❌ |

### 1.1 ✅ 이 선택이 옳은 이유 — 우연이 아니라 구조가 같습니다

| | Domain 01 장사시설 | **Domain 03 (이 문서)** |
| :--- | :--- | :--- |
| 사업자가 하는 일 | 유족의 문의를 받아 **오프라인에서 수행** | 동일 |
| 이어봄이 하는 일 | **리드 전달 + 수수료 정산** | 동일 |
| 필요한 계정 요소 | 사업자등록번호·상호·정산 계좌·승인 상태 | **동일** |
| 이어봄의 개입 깊이 | 매칭까지. 서비스 품질은 사업자 책임 | 동일 |

**`Partner` 모델의 필드를 하나도 버리지 않고 그대로 씁니다**(`schema.prisma:98`).
`Expert`(02)를 따로 만든 것과 대조됩니다 — 전문가는 **자격증 검증·직역·변호사법 가드레일**이라는
전혀 다른 요구가 있었지만, 유품 수거 업체는 **장사시설과 요구가 같습니다.**

### 1.2 🔴 확정되지 않은 것 — "계정을 어떻게 만드나"와 "사업을 할 것인가"는 다릅니다

> **이 문서는 계정·데이터·화면 설계까지만 답합니다.** 아래 3가지는 여전히 사장님 결정입니다.

| 미확정 | 왜 이 문서가 못 정하나 |
| :--- | :--- |
| **업체 모집을 실제로 할 것인가 · 언제** | 영업 자원 배분 문제 |
| **수수료 기준·요율** | `00-14` §3-4(01 수수료 기준)와 같은 성격. 01이 정해지면 따라갑니다 |
| **특수청소(고독사 현장) 취급 여부** | §6.3 — 리스크 성격이 완전히 다릅니다 |

## 🧭 2. 도메인 정의와 경계

### 2.1 ✅ 하는 일 / 하지 않는 일

| 하는 일 | 하지 않는 일 |
| :--- | :--- |
| 유품 정리·수거 업체 **탐색과 연결** | 이어봄이 **직접 수거·정리** |
| 견적 요청 **리드 전달** | **견적 금액 보증·중재** |
| 업체 등록 심사(사업자등록증·인허가 확인) | **작업 품질·분실 사고에 대한 책임 인수** |
| 유품 중 **디지털 자산이 나오면 04로**, **상속 재산이면 02로** 연결 | 유품의 **가치 평가·감정·매입** |

> 문제가 03에서 반복됩니다.

### 2.2 인접 도메인 경계

| 인접 | 겹치는 지점 | 정리 |
| :--- | :--- | :--- |
| **01** 장사시설 | 같은 `Partner` 계정 유형 | ✅ **계정은 공유, 도메인은 분리**(§3.1). 한 사업자가 양쪽을 다 할 수도 있습니다 |
| **04** 디지털 계정 정리 | *"유품"* 이라는 단어 | ✅ **현물 ↔ 디지털**. 04는 계정, 03은 물건. 구 Domain 03에서 갈라진 이유(`00-12` §7) |
| **02** 전문가 | 유품 중 고가 물품 = 상속재산 | 🟡 **분할 협의가 안 끝난 유품은 처분하면 안 됩니다** → §6.2 |
| **07** 상중·행정 | 체크리스트에 *"유품 정리"* 항목 | 🟡 **07은 체크만, 실행은 03**. `07-01` §2.2가 01에 적용한 규칙과 동일 |

### 2.3 ✅ 유가족 전용입니다

`03-01`이 2026-08-12에 확정했습니다 — **생전(WellDying) 축이 없습니다.**
따라서 `PreDeathDirective`(`00-12` §2.4)의 대상이 아니고, `00-12` §7.2의 승계 논의에도 들어가지
않습니다. **이 도메인은 사후에만 존재합니다.**

> 🟡 **예외를 하나 열어둘 여지는 있습니다** — *"내 물건은 이렇게 정리해달라"* 는 의사는
> **엔딩노트(06)에 적히는 메시지**이지 03의 기능이 아닙니다. 06이 유일한 전달 통로라는
> `00-12` §7.2 원칙을 03도 그대로 따릅니다.

## 🔑 3. 계정 설계 — `Partner` 확장

### 3.1 🔴 현행 `Partner`는 "장사시설 사업자"를 암묵적으로 전제하고 있습니다

`schema.prisma:98`의 `Partner`에는 **업종을 구분하는 필드가 없습니다.** 지금까지 파트너가
장사시설뿐이었기 때문입니다. 그리고 관계 필드 3개가 **01 전용**입니다.

```prisma
facilities  Facility[]        // 01 전용 — 수거 업체는 시설을 갖지 않음
claims      FacilityClaim[]   // 01 전용 — 클레임할 공공데이터 시설이 없음
leads       Lead[]            // ✅ 공용 가능
settlements Settlement[]      // ✅ 공용 가능
```

**→ 최소 변경으로 업종 축을 추가합니다.**

```prisma
model Partner {
  // ... 기존 필드 전부 유지

  partnerType String @default("FUNERAL_FACILITY")
  // FUNERAL_FACILITY(01 장사시설) | ESTATE_CLEANUP(03 유품 수거)
  // 기본값을 01로 두어 기존 데이터·기존 흐름이 그대로 유효합니다(마이그레이션 무해)

  serviceAreas String[]  // ESTATE_CLEANUP 전용 — 출동 가능 시·군·구 코드
  serviceTags  String[]  // ESTATE_CLEANUP 전용 — 일반정리 | 특수청소 | 폐기물운반 | 기부연계 ...
  licenseNo    String?   // ESTATE_CLEANUP 전용 — 폐기물처리업 허가·신고 번호(§6.1)
}
```

> ✅ **`contextType`(`02-04` §5) · `partnerType` 둘 다 "기본값으로 무해하게 축을 하나 더한다"는
> 같은 패턴입니다.** 이 프로젝트에서 두 번째이므로 **패턴으로 굳혀도 좋습니다** —
> 열거형 컬럼 + 안전한 기본값 = 기존 데이터 무영향.

### 3.2 🟡 업체 목록은 **어디서 오나** — 01과 결정적으로 다른 점

**이것이 03에서 가장 과소평가되기 쉬운 문제입니다.**

| | Domain 01 | **Domain 03** |
| :--- | :--- | :--- |
| 초기 목록 | **공공데이터 1,552건**(e하늘 등) | **0건** |
| 제휴 전 상태 | 목록은 이미 있고, 사업자가 **자기 시설을 클레임** | **아무것도 없음** |
| 사용자가 보는 것 | 전국 시설 + 제휴사 강조 | **제휴 업체만** |

**01은 "먼저 지도를 그려놓고 사업자를 불러들이는" 구조였는데, 03에는 그릴 지도가 없습니다.**
유품정리업은 공공 데이터셋이 없습니다(§6.1 — 법정 업종이 아니기 때문).

> 🔴 **그래서 `FacilityClaim`에 해당하는 절차가 03에는 없고, 대신 "직접 등록 심사"가 그 자리를
> 대신합니다.** 업체가 스스로 가입 신청 → 운영자가 서류를 보고 승인. `Partner.status`
> (`PENDING → APPROVED`)를 그대로 씁니다.
>
> ⚠️ **부작용**: 제휴 업체가 0건인 동안 **화면에 보여줄 것이 없습니다.**
> `00-14` §2-5가 지적한 *"제휴 업체 10곳 목업 + 별점"* 문제가 여기서 나온 것이며,
> **업체를 모으기 전에 화면을 열면 같은 문제가 반복됩니다.** → §7.2

### 4.2 🟡 수수료 기준은 01을 따릅니다

`00-14` §3-4(리드 건당 / **성사 건당(권고)** / 월 정액)가 정해지면 **같은 기준을 03에 적용**하고,
요율만 다르게 둡니다. `CommissionPolicy` 레코드 입력으로 끝나므로 코드 수정이 필요 없습니다

> 리드 건당 과금은 업체 저항이 큽니다.

## 🗄️ 5. 데이터 모델 — 신규는 최소한으로

`Partner` 확장(§3.1) 외에 **신규 모델은 1개**입니다.

```prisma
// 유품 수거 요청 — 유족이 남기는 견적 요청. Lead로 이어짐
model CleanupRequest {
  id         String   @id @default(uuid())
  userId     String              // FK → User (03-01 §2 원칙)
  deceasedId String?             // FK → Deceased (00-12 §2.1) — 확정 후 부착
  partnerId  String?             // 지정 요청이면 값, 지역 일괄 요청이면 null

  areaCode     String            // 작업 지역 시·군·구
  propertyType String            // APARTMENT | HOUSE | VILLA | OFFICE ...
  sizePyeong   Int?              // 평수 — 견적의 핵심 변수
  serviceTags  String[]          // 요청 항목(§3.1 serviceTags와 같은 어휘)
  preferredAt  DateTime?         // 희망 일정
  memo         String?

  status    String   @default("REQUESTED")  // REQUESTED | MATCHED | DONE | CANCELED
  createdAt DateTime @default(now())

  @@index([userId])
  @@index([areaCode, status])
}
```

> **`04-01` `DigitalCleanupItem` · `07-01` `AdminTaskProgress`와 같은 형태**입니다 —
> **유족 개인의 요청 1건 = 레코드 1건**. 플랫폼 전체가 같은 모양을 반복하고 있고, 그게 맞습니다.

> 🟡 **사진 첨부는 1차에서 넣지 않습니다.** 견적 정확도는 올라가지만 **고인의 주거 내부 사진**은
> 민감도가 높고, `00-11` 오브젝트 스토리지 전환 전에는 저장할 곳도 마땅치 않습니다
> (`05-01` §2.6 추모 사진과 같은 제약).

## ⚠️ 6. 이 도메인 고유의 위험 — 01·02와 다릅니다

### 6.1 🔴 "유품정리업"은 법정 업종이 아닙니다

확인 결과, **유품정리업·특수청소업이라는 이름의 허가·등록 제도는 없습니다.**
업체들이 실제로 하는 일을 쪼개 보면 각각 다른 법에 걸립니다.

| 실제 행위 | 관련 규제 | 이어봄이 확인할 것 |
| :--- | :--- | :--- |
| 폐기물 수집·운반을 **업으로** 수행 | **폐기물관리법 §25** 폐기물처리업 허가 / 신고 | 🔴 **허가·신고 번호**(`licenseNo`) |
| 재활용품·중고물품 매입·판매 | 지자체 신고 등 | 🟡 해당 시 확인 |
| 청소·정리 용역만 수행(배출은 유족 명의) | 별도 규제 없음 | 사업자등록증 |

> 🔴 **그래서 등록 심사 기준을 이어봄이 직접 정해야 합니다.** 01은 공공데이터에 등재된 시설이라
> 존재 자체가 검증이었지만, **03은 "우리가 승인한 것"이 유일한 검증**입니다.
> **무허가 업체를 매칭해 불법 투기가 발생하면 플랫폼이 지목됩니다.**
>
> 🟡 **권고**: 사업자등록증 + **폐기물 관련 허가·신고증(해당 시)** 을 필수 제출로 두고,
> 해당 없음을 주장하는 업체는 **"폐기물은 유족 명의로 배출"** 임을 서면 확인받습니다.
> ⚠️ 지자체별 운용이 다를 수 있어 **모집 전 행정사·지자체 확인**이 필요합니다(§8-2).

### 6.2 🔴 유품은 상속재산입니다 — 이게 이 도메인의 가장 큰 함정

**분할 협의가 끝나기 전에 유품을 처분하면 상속인 간 분쟁이 됩니다.**
게다가 상속재산 처분은 **단순승인으로 간주될 수 있습니다**(민법 §1026① — `07-02` §2가 다루는
상속포기·한정승인의 전제를 깨뜨립니다).

> ⚠️ **즉 03의 서비스가 유족의 상속포기 권리를 날려버릴 수 있습니다.**
> `07-02`가 *"3개월을 놓치면 빚을 상속한다"* 를 경고해놓고, 03이 그 3개월 안에
> *"유품 정리해드립니다"* 를 팔면 **플랫폼이 스스로 모순**입니다.

🟡 **권고 — 요청 화면에 게이트 1개**:

> *"상속포기·한정승인을 고려 중이시라면, 유품 처분 전에 확인이 필요합니다."*
> → `07-02` 체크리스트 해당 항목 + Domain 02 상담 연결

**막지는 않되 반드시 보여줍니다.** `07-01` §4.3(기준일은 법률 판단이라 확정 불가)과 같은 태도이며,
**이 연결이 `07-01` §6이 말한 "07이 02의 유입구"와 같은 구조를 03에도 만듭니다.**

### 6.3 🔴 특수청소(고독사·유품 훼손 현장)는 별개 판단입니다

| | 일반 유품 정리 | **특수청소** |
| :--- | :--- | :--- |
| 작업 성격 | 이사와 유사 | **감염·악취·현장 훼손** |
| 단가 | 수십~수백만원 | 훨씬 높고 **분쟁 빈발** |
| 이용자 상태 | 정리 모드 | **충격 직후** |
| 플랫폼 위험 | 보통 | **높음** — 과다청구·2차 피해 보도 표적 |

🔴 **취급 여부는 사장님 판단입니다**(§1.2). 다만 **취급한다면 `serviceTags`로 분리하고 별도
심사 기준**을 두는 것을 권고합니다 — 같은 목록에 섞으면 안 됩니다.

### 6.4 🟡 분실·파손 클레임

유품에는 **금전 가치보다 감정 가치가 큰 물건**이 섞입니다. *"어머니 반지가 없어졌다"* 는
민형사 문제로 갑니다. **이어봄은 당사자가 아니지만 "여기서 소개받았다"의 대상**은 됩니다.

🟡 **권고**: 등록 심사에 **배상책임보험 가입 여부**를 항목으로 넣고, **가입 업체를 화면에
표시**합니다. 강제하지 않되 드러내면 시장이 정리됩니다.
