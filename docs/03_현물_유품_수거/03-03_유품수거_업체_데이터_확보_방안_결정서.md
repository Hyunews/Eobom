# 🚚 03-03. 유품수거 업체 데이터 확보 방안 결정서

> **문서 성격**: 결정서(권고 + 🔴 확정 대기). `[Claude:Opus]` 작성(2026-08-21).
> **계기**: 개발자 질문 — *"장사시설은 공공데이터가 있어서 수월했는데 유품수거는 따로 그런 게 없어서,
> 실제 서비스를 위해 업체를 연결하려면 우리가 발품 혹은 연락을 통해 일일이 데이터를 수집할 것인가에
> 대한 고민이 있음. 내 생각은 카카오맵에서 유품수거 등의 이름으로 검색 후 긁어오는 게 어떤가 싶음."*
> **+ 결정적 단서(개발자)**: *"**폐기물수집운반 < 허가증이 있긴 해.**"*
> **관계**: `03-02` §3.2(업체 목록은 어디서 오나)·§6.1(법정 업종 아님)·§7.2(더미 목업)를 **개정합니다.**

## 📌 1. 🔵 전제가 뒤집혔습니다 — 공공데이터가 **있습니다**

### 1.1 `03-02`가 어디서 멈췄나

`03-02` §3.2는 이렇게 단정했습니다.

> *"01은 '먼저 지도를 그려놓고 사업자를 불러들이는' 구조였는데, **03에는 그릴 지도가 없습니다.**
> 유품정리업은 공공 데이터셋이 없습니다(§6.1 — 법정 업종이 아니기 때문)."*

**진단은 맞았지만 거기서 멈춘 것이 문제였습니다.** 같은 문서 §6.1이 이미 답을 갖고 있었습니다 —
*"폐기물 수집·운반을 **업으로** 수행 → **폐기물관리법 §25 폐기물처리업 허가**"*.

> ✅ **허가제라면 행정이 명부를 갖고 있습니다.** *"유품정리업"* 이라는 이름으로 찾아서 없었을 뿐,
> **그 일을 하는 업체가 실제로 등록되어 있는 이름은 "폐기물처리업"** 입니다.
> 개발자의 *"폐기물수집운반 허가증이 있긴 해"* 가 정확히 이 지점을 짚었습니다.

### 1.2 데이터 실체 (2026-08-21 확인)

**[전국폐기물처리업소표준데이터](https://www.data.go.kr/data/15114147/standard.do)** — 공공데이터포털

| 항목 | 값 |
| :--- | :--- |
| 제공 | **지방자치단체 약 110곳** → 행정표준 스키마로 통합(소관 기후에너지환경부) |
| 형태 | CSV · XLS · XML · JSON · RDF **+ 오픈API** |
| 필드 | 시설명 · 소재지도로명주소 · 지번주소 · **위도 · 경도** · 업종명 · **전문처리분야명** · 처리폐기물정보 · 영업구역 · 시설·장비명 · **허가일자** · **전화번호** · 관리기관명 |
| 갱신 | 🔴 **연 1회** |

- ✅ **필드가 `Facility` 모델과 거의 1:1입니다.** 위경도가 들어 있어 지도 렌더링에 바로 씁니다.
- 🟡 보완 소스: 광역 단위 데이터셋이 별도로 존재합니다(예: [경기도_폐기물처리업체 현황](https://www.data.go.kr/data/15057767/openapi.do)).
  표준데이터의 공백·지연을 메우는 용도로만 쓰고, **정본은 표준데이터 하나**로 둡니다.
- 라이선스: 공공데이터법 §3·§26 — **영리 이용 제한 불가**. `01-02` §2.1이 e하늘에 대해 내린 결론이
  그대로 적용됩니다(출처 표시).

### 1.3 이것이 바꾸는 것 — **두 가지가 큽니다**

| # | 무엇이 | 어떻게 |
| :---: | :--- | :--- |
| **①** | **01의 구조를 03에서도 쓸 수 있습니다** | *"먼저 지도를 그려놓고 사업자를 불러들인다"*. `FacilityClaim`(내 업체 클레임) 패턴도 되살아납니다 — `03-02` §3.2가 *"03에는 해당 절차가 없다"* 고 한 것이 뒤집힙니다 |
| **②** | 🔴 **`03-02` §6.1의 "다시 열 것"이 구조적으로 해소됩니다** | 그 절은 *"심사를 안 하더라도 **무허가 업체를 매칭했을 때 플랫폼이 지목되는 구조 자체는 사라지지 않는다**"* 를 남겨뒀는데, **명부에 있는 업체만 노출하면 전원이 허가 업체**입니다 |

> ✅ **②는 2026-08-19 "업체 심사를 하지 않는다" 확정을 뒤집지 않습니다.** 심사를 도입하는 것이
> 아니라, **01에서 성립했던 *"공공데이터 등재 = 존재 자체가 검증"* 이 03에서도 성립**하게 되는 것입니다.
> 이어봄은 여전히 아무것도 심사하지 않습니다.

## 🔴 2. 그런데 이 데이터에는 함정이 있습니다

**폐기물처리업 허가 업체의 대다수는 유품수거를 하지 않습니다.** 건설폐기물·사업장폐기물이 주력입니다.

| | Domain 01 | **Domain 03** |
| :--- | :--- | :--- |
| 명부의 업종명 | *"장례식장"* | *"폐기물 수집·운반"* |
| 업종명이 보장하는 것 | **목적이 곧 업종** | ❌ **허가 종류일 뿐, 하는 일이 아님** |
| 명부를 그대로 띄우면 | 정상 | 🔴 **유족이 산업폐기물 업체에 전화한다** |

> 🔴 **이 도메인에서 나올 수 있는 최악의 매칭입니다.** 사별 직후의 유족(`07-01` §3.2 — *"D+0~3,
> 경황이 없습니다"*)이 건설폐기물 업체에 전화해 *"유품 정리 되나요"* 를 묻게 만드는 것은,
> 업체 0건으로 화면을 비워두는 것보다 나쁩니다.
>
> **그래서 이 기획의 실질적 핵심은 "데이터를 어디서 얻나"가 아니라 "무엇을 보여줄 것인가"입니다.**

## ✅ 3. 채택 — **2소스 하이브리드**

### 3.1 두 소스는 서로 다른 질문에 답합니다

| | **공공데이터**(표준데이터) | **카카오 로컬 API** |
| :--- | :--- | :--- |
| 답하는 질문 | **"허가가 있는가"** — 법적 안전판 | **"실제로 유품정리를 하는가"** — 시장 신호 |
| 근거 | 폐기물관리법 §25 허가 | 상호에 *"유품정리"·"특수청소"·"유품"* 이 들어감 |
| 커버리지 | 전국 전수 | 검색어에 걸리는 것만 |
| 약점 | 🔴 **갱신 연 1회** — 폐업·번호 변경 반영 안 됨 | 허가 여부를 모름 |
| 신선도 | 낮음 | 높음 |

> ✅ **교집합이 가장 좋은 후보**입니다 — 허가가 있으면서 유품정리를 간판으로 내건 업체.

### 3.2 🔵 이건 새 구조가 아닙니다 — **01이 이미 하이브리드입니다**

`schema.prisma`의 `Facility.id` 주석: *"소스별 규칙 있음(**CSV: `bongan_NNN`/`jayeon_NNN`,
카카오: `kakao_<placeId>`**, 수기 시드: `f_*`)"*.

- ✅ **소스를 구분해 한 테이블에 담는 패턴이 이미 코드에 있습니다.**
- ✅ 수집 스크립트도 있습니다 — `prisma/import-facility-csv.ts` · `prisma/sync-kakao-funeral.ts`.
  **03용은 이 둘을 복제·개작하는 수준**이지 새로 설계하지 않습니다.
- `systems.md` §2: 카카오 로컬 API는 **이미 시설 데이터 수집에 사용 중**입니다.

### 3.3 🔴 카카오는 **API로만** — 화면 스크래핑 금지

개발자 표현 *"긁어오는"* 을 구현 지침으로 정확히 옮깁니다.

| | 판정 | 근거 |
| :--- | :---: | :--- |
| **카카오 로컬 REST API 조회** | ✅ **허용** | `01-02` §2.1 — *"Kakao Developers 서비스 약관 §9에 의거 상업용 앱/웹 내 지도 렌더링 및 핀 표시 100% 허용"*. 이미 01에서 사용 중 |
| 카카오맵 **화면 HTML 스크래핑** | ❌ **금지** | 약관 위반 소지. 얻는 것도 API와 다르지 않습니다 |

> ⚠️ **`systems.md` §2에 이미 적힌 함정을 그대로 밟게 됩니다** — **시/도 단위 검색은 45건 캡**이라
> 일부 지역이 누락됩니다. **시/군/구 단위로 재검색**해야 전수에 가까워집니다. 01에서 겪은 그대로입니다.
>
> ⚠️ **위치정보법과 무관합니다** — `01-02` §2.2 **트랙 B**(지역명·검색어 기반)에 해당하므로
> 신고 의무 대상이 아닙니다. 수집은 서버에서 지역명으로 도는 배치이고 이용자 GPS를 쓰지 않습니다.

## 🔴 4. 노출 필터 — **확정이 필요합니다**

### 4.1 후보 3안

| 안 | 내용 | 장점 | 단점 |
| :---: | :--- | :--- | :--- |
| **A** | **업종·처리분야 필터만** — `전문처리분야명`·`처리폐기물정보`에 **생활폐기물**이 포함된 업체 | 전국 커버, 자동화 | 🔴 **여전히 유품정리를 안 하는 곳이 대다수** |
| **B** | **카카오 교집합만** — 상호에 *유품정리·특수청소* | 정확도 높음 | 🔴 **커버리지가 낮습니다.** `03-02` §6.1이 확인한 *"폐기물 처리 서비스·재활용센터·청소 전문업체"* 라는 **다른 간판의 업체가 통째로 누락**됩니다 |
| **C** | 🟡 **적재 범위와 노출 범위를 분리**(권고) | 아래 | 관리 규칙이 하나 늘어남 |

### 4.2 🟡 권고 — **C안: 적재 ≠ 노출**

**01은 적재한 것을 전부 노출했지만, 03은 갈라야 합니다.** §2의 함정 때문입니다.

| 군 | 정의 | 적재 | **유족에게 노출** |
| :---: | :--- | :---: | :---: |
| **1군** | **제휴 업체** — 직접 계약(`Partner.status = APPROVED`) | ✅ | ✅ **최상단** |
| **2군** | **교집합** — 허가 명부 ∩ 유품정리 간판 | ✅ | ✅ |
| **3군** | 허가 명부에만 있음(생활폐기물 취급) | ✅ | ❌ **노출하지 않음** |

> ✅ **3군은 "유족에게 보여줄 목록"이 아니라 "제휴 영업 대상 리스트"입니다.** 적재해두면
> **발품이 *"어디에 전화할지 찾는 일"* 에서 *"이미 아는 곳에 제안하는 일"* 로 바뀝니다**(§6).
>
> 🔵 **이 분리가 개발자의 원래 고민을 정면으로 해결합니다** — *"우리가 발품 혹은 연락을 통해
> 일일이 데이터를 수집할 것인가"*. 수집은 자동화하고, 사람은 **영업에만** 씁니다.

### 4.3 어느 안을 고르든 지켜야 할 것

- 🔴 **`03-02` §6.1의 문구 제약은 그대로입니다** — 심사를 하지 않으므로 *"검증·추천·엄선"* 표현
  금지, **"연결"·"안내"** 까지만. **1군·2군에도 예외가 아닙니다.**
- 🟡 **출처 표기**: 공공데이터 출처와 **"데이터기준일자"** 를 화면에 노출합니다. 갱신이 연 1회라
  **낡을 수 있다는 사실 자체가 고지 대상**입니다.
- 🔴 **번호·주소는 공공데이터 원본을 그대로 쓰되, 폐업 신고 경로를 둡니다**(§7).

## 🗄️ 5. 데이터 모델 — 🟡 `Facility` 확장을 권고합니다

| 안 | 판정 |
| :--- | :--- |
| **`Facility`에 `type` 값 추가**(`'유품수거'`) | 🟡 **권고** — 필드가 거의 겹칩니다(상호·주소·위경도·전화). `Lead.facilityId`가 이미 nullable로 전환돼 있어(`03-02` §4.1) 충돌도 없습니다 |
| 신규 `CleanupCompany` 모델 | ❌ 비권고 — 같은 모양을 두 벌 관리하게 되고, 지도·검색·리드 코드가 갈라집니다 |

추가가 필요한 필드는 **소수**입니다.

```prisma
// Facility에 추가 (03-03 §5) — 03 전용 필드는 전부 nullable, 01 레코드에는 null이 들어간다
licenseNo        String?   // 폐기물처리업 허가·신고번호(표준데이터)
licenseDate      DateTime? // 허가일자
wasteCategories  String[]  // 전문처리분야·처리폐기물정보 원문 토큰
serviceArea      String?   // 영업구역
sourceTier       String?   // TIER1_PARTNER | TIER2_MATCHED | TIER3_LICENSE_ONLY (§4.2)
dataBaseDate     DateTime? // 데이터기준일자 — 화면 고지용(§4.3)
```

- ✅ `id` 규칙은 01의 관례를 잇습니다 — **`waste_<허가번호>`**(공공데이터) · `kakao_<placeId>`(카카오).
- 🔴 **`sourceTier === 'TIER3_LICENSE_ONLY'` 는 공개 목록 쿼리에서 항상 제외**합니다(§4.2).
  **화면에서 거르지 말고 쿼리에서 거릅니다** — 화면 필터는 새 화면이 생길 때마다 빠집니다.

## 🔄 6. 수집 파이프라인

| 단계 | 내용 | 재사용 |
| :---: | :--- | :--- |
| 1 | 표준데이터 파일 적재 → 3군으로 전량 저장 | `import-facility-csv.ts` 개작 |
| 2 | 카카오 로컬 API를 **시/군/구 단위**로 순회(*유품정리·특수청소·유품* 등) | `sync-kakao-funeral.ts` 개작 |

| 4 | 제휴 계약 체결 시 1군으로 승격 | `Partner` 기존 흐름 |

> ⚠️ **3단계 매칭 키는 상호가 아니라 전화번호를 우선**합니다. 상호는 *"(주)"*·지점명·띄어쓰기로

> 01의 사업자등록번호 정규화(`normalizeBizRegNo`)와 같은 사상입니다.
>
> 🟡 **1·2단계는 배치이고 연 1회~분기 1회면 충분합니다.** 실시간 동기화를 만들지 않습니다.
