## 📌 1. 먼저 질문의 전제를 짚습니다 — **정책은 약속이지 보증이 아닙니다**

개발자 질문은 **"열람 정책"** 을 묻고 있습니다. 그런데:

> **서버가 복호화 키를 갖고 있으면 운영자는 기술적으로 언제든 볼 수 있습니다.**
> 그 상태에서 *"안 봅니다"* 는 **규칙일 뿐**이고, 규칙은 지키는 사람이 지킬 때만 지켜집니다.

`06-01`이 지적한 *"화면에 건 비밀보장 약속"* 과 충돌하는 지점이 정확히 여기입니다.
화면은 *"철저히 비밀이 보장되며"* 라고 **보증의 어투**로 말하는데, 뒷받침은 **약속**입니다.

> **✅ 따라서 `06-03`의 뼈대는 "특수 상황 목록"이 아니라 "약속을 구조로 뒷받침하는 층"입니다.**
> 특수 상황 열거(§4)는 그다음입니다. **이 순서를 뒤집으면 `00-12` §1이 지적한
> *"약속만 화면에 걸려 있다"* 의 재발**이 됩니다 — 목록만 늘고 뒷받침은 그대로인 상태.

### 1.1 그렇다고 "완전한 보증"이 답은 아닙니다

*"운영자가 절대 못 보게 하면 되지 않나"* — 이론적으로는 **이용자만 키를 갖는 방식**(E2E)이
있습니다. 하지만 이 서비스에서는 채택할 수 없습니다.

| 왜 안 되나 | |
| :--- | :--- |
| **이용자가 키를 잃으면 영구 소실** | 엔딩노트는 **본인이 사망한 뒤에 열려야 하는 데이터**입니다. 키를 아는 사람이 죽고 없습니다 |
| **L3·L4 자체가 성립 불가** | `00-12` §4의 사후 개봉은 **플랫폼이 복호화할 수 있어야** 동작합니다 |
| **6070 시니어가 주 페르소나**(`00-02`) | 키 관리를 이용자에게 넘기는 설계는 이 사용자층에서 실패합니다 |

> **✅ 그래서 이 도메인의 정직한 위치는 "완전한 보증"과 "말뿐인 약속" 사이입니다.**
> **§2가 그 사이를 어떻게 메우는지에 대한 답입니다.**

## ✅ 3. 결론 — **A안(메타데이터만) 채택 + 예외 열람 통제 4종**

### 3.1 A/B 결론

> ✅ **`06-01` §3 → A안(메타데이터만) — 2026-09-30 개발자 확정.** 코드: `deathVerificationAdminController.ts` 머리 주석과 필드별 `select`(운영자 응답에 본문·섹션 제목·섹션 작성 여부·편지 없음).

**B안(본문까지)을 기각하는 이유는 "위험해서"가 아니라 "필요가 없어서"입니다.**
`06-01` §3이 B안의 근거로 든 것은 **고객지원**(*"내 유언장이 왜 안 열리나요"*)인데,
그 문의는 **메타데이터로 전부 답할 수 있습니다.**

| 실제 문의 | A안으로 답할 수 있나 |
| :--- | :---: |
| *"저장이 됐나요?"* | ✅ 작성 여부·항목별 완료 상태 |
| *"왜 안 열리나요?"* | ✅ 봉인 여부·사망 확인 진행 상태(`00-41`)·미충족 조건 |
| *"누가 열었나요?"* | ✅ 개봉 이력(누가 언제 동의했는지) |
| *"제가 쓴 내용이 뭐였죠?"* | ❌ — **본인이 로그인해서 볼 일**이지 운영자가 읽어줄 일이 아님 |

> **✅ 마지막 줄이 핵심입니다.** 본문이 필요한 유일한 시나리오조차 **본인 열람으로 해결**되며,
> 운영자가 읽어서 알려주는 순간 **"철저히 비밀"은 그 통화에서 이미 깨집니다.**

### 3.2 그래도 예외는 생깁니다 — **4종 통제**

A안을 채택해도 **§4의 몇몇 상황에서는 본문 접근이 실제로 발생**합니다.
*"예외는 없다"* 고 적으면 그건 다시 지킬 수 없는 약속이므로, **예외를 인정하고 통제합니다.**

| # | 통제 | 왜 |
| :---: | :--- | :--- |
| **①** | **2인 승인(4-eyes)** — 운영자 1인이 단독으로 열 수 없음 | 단독 열람이 가능하면 나머지 통제가 다 무의미해집니다 |
| **②** | **열람 사유 필수 기록** — 자유 입력이 아니라 **§4의 사유 코드 선택 + 근거 첨부** | 자유 입력은 *"확인"* 두 글자로 채워집니다 |
| **③** | **불변 감사 로그** — 운영자도 지울 수 없음 | 지울 수 있는 로그는 로그가 아닙니다 |
| **④** | **본인 또는 지정 유족에게 열람 사실 사후 통지** | **가장 강한 억제력.** 들킨다는 것을 알면 열지 않습니다 |

> 🔴 **③의 "불변"은 구현 난도가 있습니다** — 같은 DB에 넣으면 DB 접근 권한자가 지울 수 있습니다.
> **최소선은 "애플리케이션에서 삭제·수정 경로를 만들지 않는다"** 이고, 그 이상(별도 저장소·WORM)은
> **`00-11` 인프라 확정 후**입니다. **여기서도 §6의 선 긋기가 적용됩니다.**

> ✅ **2026-09-30 — 1인 운영 동안의 실제 모습**(§8 #2 (가)안 확정). ①(2인 승인)은 **적용하지 않습니다.**
> ②③④는 기능이 생기기 전까지 **손 절차**로 지킵니다.
>
> | 순서 | 무엇을 |
> | :---: | :--- |
> | 1 | 열람 사유가 §4 ⭕ 두 가지(영장 등 적법한 요구 · 본인 요청) 중 하나인지 확인. 🔴 **아니면 열지 않는다** — 개발·디버깅·호기심은 사유가 아니다 |
> | 2 | 열기 **전에** 기록: 날짜·사유·근거 서류·대상 회원·**어느 섹션만**. 기록 위치는 git 밖 운영 기록(🔴 본문 내용은 적지 않는다) |
> | 3 | 필요한 섹션만 복호화. 결과를 파일로 남기지 않는다 |
> | 4 | 본인(사후엔 지정 유족)에게 열람 사실을 알린다. 🟡 수사기관이 통지 유예를 요구하는 경우 처리는 법률 검토(`00-18` §8.1)에 넣는다 |
>
> 🔴 **복호화 도구는 지금 없다**(A안 — 운영자 경로를 일부러 만들지 않았다). 필요해지면 그때 [Sonnet]이 위 순서를 강제하는 1회용 스크립트로 만든다(사유 입력 없이는 안 도는 형태).
>
> ✅ **2026-10-12 개발자 결정**: 2번 기록은 담당자 안내서 **`00-43`에 양식 한 쪽**(날짜·사유·근거 서류·대상 회원·섹션 칸)을 두고, 종이·파일로 git 밖에 보관합니다. 🔴 양식 추가는 docs 정리 00 3회차(`00-43` 범위)에서 합니다 — 그 전까지 `00-43`에 없습니다.

## 🔍 4. "특수한 상황"이 무엇인가 — 개발자 질문에 대한 직접 답

| 후보 | 판정 | 근거 |
| :--- | :---: | :--- |
| **법원 영장 · 수사기관의 적법한 요구** | ⭕ **인정** | **거부할 수 없습니다.** 정책으로 막을 수 있는 성질이 아니므로 **약관에 반드시 명시**해야 합니다 — 안 적어두면 그때 약속을 어기는 것이 됩니다 |
| **본인의 명시적 요청**(고객지원) | ⭕ **인정** | 정보주체 본인이므로 문제 없습니다. 단 **본인 확인 절차 필수** + §3.1대로 **본인 열람으로 유도하는 것이 우선** |
| **사망 확인 후 유족 전달 집행** | 🟡 **이건 열람이 아닙니다** | **§4.1 — 용어를 갈라야 합니다** |
| **시스템 장애·데이터 복구** | 🟡 **대상 아님** | 백업·복구는 **암호문을 다루는 작업**입니다. 복호화하지 않으므로 열람이 아닙니다. (복호화가 필요한 복구 시나리오가 생기면 그때 ①~④ 적용) |
| **생명 위협 징후(자살 암시) 감지** | 🔴 **권고하지 않습니다** | **순환 논리입니다** — 감지하려면 내용을 봐야 하고, 내용을 안 보는 것이 이 도메인의 약속입니다 |

### 4.1 ✅ "열람"과 "전달"을 가릅니다 — 용어가 설계를 좌우합니다

| | 열람(Access) | 전달(Delivery) |
| :--- | :--- | :--- |
| 누가 내용을 보나 | **운영자** | **지정 유족**(수신자) |
| 근거 | §4의 예외 사유 | **사망 확인 → 개봉**(`00-41`, 개념 `00-12` §4) — 정상 경로 |
| 통제 | §3.2 4종 | 사망 확인 게이트 자체 |
| 감사 로그 | **"운영자 열람"** 으로 기록 | **"유족 전달"** 로 기록 |

> **✅ 사망 확인 뒤 개봉은 "시스템이 유족에게 전달하는 것"이지 "운영자가 읽는 것"이 아닙니다.**
> 이 둘을 한 로그·한 화면에 섞으면 **감사 로그가 의미를 잃습니다** — 정상 전달 수천 건 사이에
> 예외 열람 한 건이 묻히기 때문입니다. **모델·로그·화면에서 분리하십시오.**

### 4.2 🔴 자살 징후 감지를 기각한 이유를 더 적어둡니다

*"사람을 살릴 수 있는데"* 라는 반론이 반드시 나오는 항목이라 근거를 남깁니다.

1. **순환 논리** — 감지하려면 상시 열람해야 하고, 그 순간 A안은 무너집니다.
2. **오탐의 대가가 큽니다** — 엔딩노트는 **원래 죽음을 다루는 글**입니다. 유서와 엔딩노트를 문장으로
   가르는 것은 사람도 어렵습니다.
3. **더 나은 자리가 있습니다** — 🟡 감지가 아니라 **상시 안내**로 답합니다. 엔딩노트 화면에
   **자살예방 상담전화(109) 등 공적 창구를 상시 노출**하면, 내용을 보지 않고도 같은 목적을
   더 확실하게 달성합니다. `06-02` §3(연명의료 등록기관)·`04-02` §4(플랫폼 사전지정)와 **같은
   패턴** — **우리가 하지 않고 제대로 된 곳으로 연결합니다.**

> 🔴 **다만 위 창구 번호·명칭은 확인일 기준으로 관리해야 합니다**(`04-01` §3.1 `lastVerifiedAt` 방식).

> 🔴 **미구현(2026-10-12 확인)**: 엔딩노트 화면에 공적 창구(109 등) 상시 노출이 **없습니다**(`EndingNotePage.tsx`·`components/endingNote` 검색 0건).
> ✅ **2026-10-12 개발자 결정 — 넣습니다(한 줄)**. 엔딩노트 화면 아래쪽에 상시 표시: *"마음이 힘드실 때 자살예방 상담전화 109(24시간)"* — 구현은 `[Sonnet]`. 🔴 번호·명칭·운영 시간은 **게시 전 외부 확인 목록**(확인일을 함께 적는다).

> 다만 아래 두 경우에는 예외적으로 열람할 수 있습니다.*
> ***① 법원의 영장 등 법령에 따른 적법한 요구가 있는 경우** — 이 경우 이어봄은 거부할 수 없습니다.*
> ***② 회원님이 직접 요청하신 경우.***
> *예외 열람은 사유가 기록되고, **열람 사실을 회원님(사후에는 지정 유족)께 알려드립니다.**
> 사망 확인 후 지정 유족에게 전달되는 절차는 **열람이 아니라 전달**이며,
> 회원님이 정하신 조건에 따라 진행됩니다."*

> ✅ **"담당자 2인의 승인을 거치며"는 넣지 않습니다**(2026-09-30 개발자 확정, §8 #2 (가)안).
> 운영 인력이 1인이라 지킬 수 없는 문장이고, 승인·로그·통지 기능도 아직 없습니다(`06-04` Phase 3).
> **기록·통지는 사람이 손으로 한다** — 절차는 §3.2 아래 블록. 🔵 운영 인력이 2인이 되면 다시 넣을지 본다.

**작성 원칙 3가지**:

1. **불리한 것을 먼저 말합니다** — ①(영장)을 앞에 둡니다. `04-02` §6이 *"대리하지 않는다를 먼저
   말한다"* 고 한 것과 같은 태도입니다.
2. **"절대"라고 쓰지 않습니다** — 지킬 수 없는 문장은 넣지 않습니다(§1).
3. **④(사후 통지)를 문구에 넣습니다** — 통제 중 이용자에게 **실제로 체감되는 유일한 항목**입니다.

> ⚠️ **`06-02` §6.1의 어휘 교체 원칙을 그대로 적용합니다** — 새 화면·문구를 만들 때도 *"철저히 비밀이 보장되며"* 같은
> **보증 어투**를 쓰지 않습니다(2026-10-12 확인: 지금 화면에 남은 곳 없음).

## 🔧 6. 🔴 기술적 강화 — 지금 정할 수 있는 선을 긋습니다

§2의 **2층(운영자 단독 복호화 불가)** 이 이 도메인 약속의 진짜 뒷받침입니다. 후보는 있습니다.

| 후보 | 내용 | 전제 |
| :--- | :--- | :--- |
| **봉투 암호화** | 데이터키로 본문을 암호화하고, 데이터키는 마스터키로 감쌈 | **마스터키를 어디에 두나** |
| **키 분할** | 마스터키를 나눠 **단독 복호화 불가**로 만듦 | 동일 |
| **관리형 키 서비스(KMS)** | 키를 앱 밖에 두고 사용 이력을 남김 | **클라우드 사업자 확정** |

> 🔴 **셋 다 `00-11` §8-1(클라우드 사업자 확정)에 걸립니다.** 키 관리 위치가 정해지지 않으면
> 설계할 수 없고, 지금 정하면 사업자 확정 시 다시 뒤집힙니다.
>
> ✅ **그래서 지금 확정하는 것은 두 가지뿐이고, 둘 다 지켜지고 있습니다.**
> **① 평문 저장 구현을 임시로라도 만들지 않는다**(`security.md` §6 — *"임시가 그대로 남는다"*) — ✅ 본문은 `bodyEnc`(암호문)로만 저장.
> **② 복호화 키를 애플리케이션 코드·이미지에 굽지 않는다**(`00-11` §7.2-1) — ✅ 키는 환경변수 `ENDING_NOTE_ENCRYPTION_KEY`.
> **나머지(봉투 암호화·키 분할·KMS)는 인프라 확정 후** 정합니다 — 🔴 `00-11` §8 인프라 전략 결정 대기(키 보관 체계 포함, `pending-approvals.md`).

## 🔗 7. 다른 문서와의 경계 — 06은 예외라는 것을 명문화합니다

`03-01` §2가 세운 원칙은 *"도메인 데이터는 `userId` FK로 연결해 **운영자 회원 상세에서 조인해
한 화면에 보여준다**"* 이고, `04-01` §4.3·`05-01` §3.5·`03-02` §5에 반영돼 있습니다.

> ✅ **06은 이 원칙의 유일한 예외입니다.**
> **연결은 합니다**(`userId` FK — 그래야 메타데이터를 볼 수 있습니다).
> **다만 조인 결과에 본문이 포함되지 않습니다.** 운영자 화면에는 **§3.1의 메타데이터만** 나갑니다.
>
> 🔴 **구현 시 주의**: `prisma.user.findUnique({ include: { ... } })` 형태로 통째로 조인하면
> **본문 컬럼이 자동으로 딸려옵니다.** 06 모델은 **`select`로 필드를 명시**하거나, 아예
> **본문을 별도 모델·별도 접근 경로로 분리**해야 합니다. **"실수로 열리는" 경로를 없애는 것이
> `04-01` §8의 *"필드가 없으면 채워질 수 없다"* 와 같은 원리입니다.**
