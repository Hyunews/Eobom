### 4.3 ⏸ `DeathVerification`은 06이 만들지 않습니다

**`00-41`(사후 개봉 최소안) 소관입니다** — 모델 = `00-41` §4.2.
개념(사다리)은 `00-12` §3·§4이고 `00-27` Phase 3과 **공용 모델**입니다. `00-12` §7.2의 *"통로는 06 하나"* 는
**데이터가 06으로 모인다**는 뜻이지 **06이 사망 확인을 소유한다**는 뜻이 아닙니다.
🔴 이 모델은 엔딩노트 본문과 조인하지 않습니다(`06-03` §3.1).

```
CLOVA_SPEECH_INVOKE_URL=   # 도메인별 고유. 도메인 식별자를 URL이 이미 품고 있다
CLOVA_SPEECH_SECRET=       # 🔴 절대 커밋 금지
CLOVA_STT_ENABLED=false    # 🔴 기능 플래그. 기본 꺼짐(§6.4-9-8-3)
```

✅ `.env`는 루트 `.gitignore:20`에 등록돼 있고 추적되는 것은 `.env.example`뿐입니다(2026-08-26 확인).
🔴 **`.env.example`에는 값이 아니라 자리표시자만** 넣습니다 — 기존 OAuth 항목과 같은 방식.

#### 6.4-11-6 🔵 **동의는 세 종류입니다 — 섞으면 안 됩니다** (2026-08-26 사장님 질문)

> 🔵 *"이미 동의한 것 같은데 어디서 다시 확인하는지 모르겠다. **고객의 동의 내용을 만들어야 하나?**"*

| | 무엇 | 방향 | 조항 |
| :---: | :--- | :--- | :--- |
| **ⓐ** | **서비스 이용약관 동의** | 이어봄 → 네이버 | 제3조 ① — *"고객이 본 약관에 동의하고 이용신청"*. **계약 체결 그 자체** |
| **ⓑ** | 🔴 **학습 활용 동의** | 이어봄 → 네이버 | 제4조 ② — *"**고객의 동의가 있는 경우**"* 음성을 취득·보관·활용 |
| **ⓒ** | **이용자 동의** | 엔딩노트 사용자 → 이어봄 | 제4조 ③ — **ⓑ에 동의했을 때만 발생하는 파생 의무** |

> 🔴 **ⓐ와 ⓑ는 별개입니다.** 약관 동의가 곧 ⓑ였다면 제4조 ②의 *"동의가 있는 경우"* 라는 **단서
> 자체가 무의미**해집니다. 조문이 단서를 단 이상 **별도의 의사표시**입니다.
> *"이미 동의한 것 같다"* 는 **ⓐ일 가능성이 높습니다.**

##### 🔴 ⓒ(이용자 동의 화면) — **필요합니다** (2026-08-26 정정)

> 🔵 **사장님 확인 결과: "부분동의 불가능"** — 즉 **ⓑ(제4조 ② 학습 활용)를 빼고 동의할 수 없습니다.**

**초판(같은 날 오전)은 *"위수탁계약을 맺으면 이용자 동의 화면이 불필요하다"* 고 적었습니다. 정정합니다.**
그건 **제7조 ②(위탁 vs 제3자 제공)** 에 대한 답이었고, **제4조 ③은 별개 의무**입니다.

> **제4조 ③**: *"고객은 이용자로부터 … 음성 및 동영상 데이터가 회사 등에게 전달되어, **서비스의
> 성능향상을 위해 활용될 수 있다는 점을 설명하고, 그에 대한 동의를 얻는 등** 관련 법령의 의무를
> 준수하여야 합니다."*

🔴 **법리도 같은 방향입니다.** 개인정보보호법상 **위탁**은 *"위탁자의 목적 범위 내에서 수탁자가 처리"*
입니다. 네이버가 **자기 엔진 개선**에 쓰는 것은 **위탁 범위를 넘어서므로** `00-17` §3.2의
*"처리방침 공개로 갈음"* 경로에 **올라타지 못합니다.** 별도 동의가 필요합니다.

##### 🔴 이것이 §6.4-9-2 #1 탈락 기준에 걸립니다

§6.4-9-2 #1 원문: *"입력 데이터의 모델 학습 활용을 거부할 수 있는가. **opt-out이 계약서에 없으면
탈락 — 가격을 볼 필요도 없습니다.**"* → **부분동의 불가 = opt-out 불가.**

**이 도메인에서 가벼운 문제가 아닌 이유:**

- ⑨는 §6.4-2가 **"본인 전용, 사후에도 유족에게 전달하지 않는다"** 로 **가장 강하게 격리한 데이터**입니다.
- 🔴 그러면 **유족에게도 주지 않는 것을 네이버 학습에는 주는** 모양이 됩니다.
- 🔴 **되돌릴 수 없습니다.** 모델에 들어간 데이터에는 삭제 개념이 없습니다(7조 ①의 7일 삭제와 다릅니다).

##### 6.4-11-6-1 🔵 ⓐ를 택할 경우 — **가입 시점이 아니라 "처음 쓸 때"** (2026-08-26 사장님 제안 검토)

> 🔵 **사장님 제안**: *"어차피 개인정보 관련해서, **가입 시에 관련 항목 넣어서 동의 받는 게** 좋아보임."*

**의도(*"어차피 받을 동의면 한 번에 정리하자"*)는 채택합니다. 다만 시점을 옮깁니다.**

🔴 **가입 시점이 걸리는 이유 4가지**

| # | | |
| :---: | :--- | :--- |
| **1** | **필수로 묶으면 위법 소지** | 개인정보보호법은 **서비스 이용에 필수적이지 않은 동의의 강제**를 막습니다. STT 학습 활용은 장사시설 매칭·부고장만 쓰는 이용자에게 **아무 관련이 없습니다** |
| **2** | **선택으로 넣으면 실효 없음** | 대부분 체크하지 않고, 그러면 STT를 쓸 때 **어차피 다시 받아야** 합니다. 가입 화면만 무거워집니다 |
| **3** | **가입 화면이 이미 포화** | `LoginModal`이 **만14세 + 필수 2 + 선택 1 = 4개**를 갖고 있고 문구는 `00-19` §9-2-1로 정본화 완료. 6070 대상에서 항목을 더 얹으면 **가입 이탈**이 늘어납니다 |
| **4** | 🔴 **동의가 실질적으로 무효해질 수 있음** | 가입 때 읽고 넘어간 사람이 **6개월 뒤 유언을 녹음할 때 그 동의를 기억하는가.** 개인정보보호법상 동의는 **정보주체가 인지한 상태**여야 유효합니다. 맥락에서 먼 동의는 형식만 남고, 하필 이 도메인은 **유언**입니다 |

> ⚠️ 게다가 가입 항목을 늘려도 **기존 회원은 동의한 적이 없어** 따로 받아야 합니다 —
> 문제가 사라지는 게 아니라 **두 벌**이 됩니다.

## 🔓 8. 개봉 절차

### 8.1 상태 기계

요청·확인 상태는 `EndingNote`가 아니라 **`DeathVerification.status`** 가 담고, 엔딩노트의 상태는 개봉 한 번만 바뀝니다.

```
[지정 유족(ACCEPTED, 계정 연결됨)의 사망 확인 요청] ──> DeathVerification: REQUESTED
REQUESTED ──[운영자 확인(평일 9~17시 기준)]──> VERIFIED (level = OPERATOR_REVIEWED)
           └─ 같은 트랜잭션에서 EndingNote: DRAFT ──> RELEASED (releasedAt)
REQUESTED ──> REJECTED / CANCELLED
RELEASED ──> 가족별 권한(EndingNoteGrant)대로 열람 · 편지(06-05)는 수신자에게
```

> 정본 = **`00-41`**(코드 `deathVerificationController.ts` · `deathVerificationAdminController.ts`). 개념 사다리 = `00-12` §4, 앞뒤 흐름 = `00-30` §9.
> 🔵 `SEALED`(봉인)는 모델 주석에만 있고 **코드에서 쓰지 않습니다** — 작성 중(`DRAFT`)에서 바로 개봉됩니다.
> 🔴 처음 설계의 **L4(지정 유족 이중 동의)는 2026-09-30 개발자 확정으로 폐기** — 운영자 확인 즉시 한 번에 `RELEASED`(`00-41` §7). 처음 상태 기계는 **부록: 경위**.

### 8.2 ⛔ "이중 동의"(L4) — 2026-09-30 폐기

L4가 없어져 *"이중 동의가 성립하지 않는 경우"* 표(1명·2명 이상)는 **부록: 경위**로 옮겼습니다.
✅ 그중 **지금도 유효한 한 줄**: 지정 유족이 **0명이면 사후에 아무에게도 전달되지 않습니다** — 작성 화면이 미리 알립니다
(보관함 *"수신자가 없으면 사후에도 전달되지 않습니다"* — `FarewellDesktopView.tsx`, `06-05` §7.3).

### 8.3 전달은 "권한 부여"이지 "발송"이 아닙니다

화면은 *"열람 키가 자동 발송"* 이라고 약속했지만(§2.2 ③), **키를 문자로 보내는 순간 그 문자가
곧 열쇠**가 되어 재전파·오배송 사고가 `00-27` §9.1-1과 똑같이 재현됩니다.

> ✅ **통지는 *"열람 가능해졌습니다"* 라는 알림뿐이고, 실제 열람은 로그인 후 계정 권한으로 합니다.**
> 이미 `acceptedUserId`로 계정이 연결돼 있으므로 **키를 보낼 이유가 없습니다.**

| 셈 | 가족(지정)마다 **철회 안 된 권한이 있는 섹션 수**(`EndingNoteGrant`, `revokedAt` null, 즉시·사후 합산, 같은 섹션 중복 1개). `WILL_DRAFT` 제외 |
| 대상 | 지정 상태 `ACCEPTED`·`PENDING`·`EXPIRED`·🔄 **`DRAFT`(초대 전)**. `DECLINED`만 빼고, 대상이 없으면 **줄 자체를 그리지 않는다**. 🔄 *09-30*: `DRAFT`도 §8.3-2로 기본 권한이 생기므로 **보이고 바꿀 수 있어야 한다**(Sonnet 질의) — 섹션별 공개 시점 화면(`SectionTimingControl`)도 같은 대상. 이름 옆 표시는 `DRAFT` = **`초대 전`**, `PENDING`·`EXPIRED` = `수락 전` |
| 🔴 모양 | 색·아이콘·경고 문구 없음 — **0개도 같은 글자색**(`00-39` 규칙 5). *"주의"·"공개해 주세요"* 같은 권유 없이 숫자만 |
| 모바일 | 같은 한 줄, 가족이 많으면 줄바꿈 허용. 새 상자·접기 장치를 만들지 않는다 |
| 갱신 | 공개 시점을 바꾸면 즉시 반영(이미 화면이 든 `grants` 상태로 셈 — 추가 API 없음) |

#### 8.3-2 🆕 가족을 지정하면 기본으로 "사후에만 공개" (2026-09-30 개발자 결정)

> **왜**: 가족 지정 자체가 *"내가 죽으면 이 사람이 보게 한다"* 는 뜻인데 기본값이 비공개라 그 뜻과 거꾸로 갔다(§8.3-1 배경).
> 사후 공개는 **생전에 아무도 못 보므로** 기본으로 둬도 생전 노출은 없다.
> 🔴 **"권한이 없으면 사후 공개로 간주"하지 않는다** — 기존 데이터의 뜻이 바뀌고 화면(비공개)과 실제가 어긋난다.
> **실제 권한 행을 만든다** — 화면 선택칸에 *"사후에만 공개"* 로 보이고, 본인이 섹션마다 바꾼다.

| | 스펙 |
| :--- | :--- |
| 언제 | **가족 지정을 새로 만들 때 한 번.** 그때 엔딩노트가 아직 없으면 **엔딩노트가 처음 생길 때** 그 시점의 지정 전원(`DECLINED` 제외)에 한 번 |
| 무엇 | `SECTION_ALLOWED_TIMINGS`에서 `POSTMORTEM`을 고를 수 있는 섹션 전부(현재 8개)에 `timing = POSTMORTEM` 권한. 🔴 `WILL_DRAFT` 제외 · 🔴 `IMMEDIATE`는 기본으로 두지 않는다(생전 공개는 본인이 직접 고른다) |
| 🔴 다시 만들지 않는다 | 이후 본인이 비공개로 바꾸면(철회) **그대로 둔다.** 그 (지정, 섹션)에 권한 행이 한 번이라도 있었으면(철회 포함) 건너뛴다 — 화면을 열 때마다 되살리지 않는다 |
| 기존 지정 | ✅ **소급하지 않는다**(개발자 결정 09-30) — 비공개를 일부러 고른 사람이 있을 수 있다. 일괄 스크립트 없음 |
| 규칙 | 권한 생성은 기존 검증 규칙(`DECLINED` 불가·`WILL_DRAFT` 불가)을 그대로 따르는 공용 로직으로 |
| 지정 화면 안내 | 가족 지정 폼 연락 순위 도움말 바로 아래, 같은 글 상자 안 줄바꿈: *"지정한 가족은 사후에 엔딩노트 전체를 볼 수 있으며, 공개 시점은 엔딩노트 페이지에서 바꿀 수 있습니다."* 🔄 10-16 디자인 개편 4단계 판 4-3(개발자 확정) — 옛 문구 *"지정하면 모든 섹션이 사후에 공개됩니다. 섹션마다 바꿀 수 있습니다."* 대체(개발용 단어 "섹션"을 이용자 화면에서 뺌) |
| 지정 폼 아래 고지 | 권한 행이 지정 때 생기므로 그에 맞춘 문구 — 문구 = `00-27` §8.3 |

> 🔵 §8.3-1 개수 한 줄이 새 지정에서 **"8개"** 로 보이므로 본인이 전부 열려 있음을 바로 안다. 여러 명을 지정하면 모두가 전부
> 받는다는 점도 이 줄이 드러낸다.
