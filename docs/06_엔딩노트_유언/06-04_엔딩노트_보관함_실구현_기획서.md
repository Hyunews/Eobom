## 🧱 3. 무엇을 만드는가 — 기능 4개

현재 화면이 하는 일은 **입력 칸 3개**뿐입니다. 실구현에서 새로 생기는 기능은 다음 4가지입니다.

| # | 기능 | 왜 필요한가 |
| :---: | :--- | :--- |
| **①** | **섹션별 공개 시점 설정** | 지금은 **자유 텍스트 한 칸**에 메시지·계좌·암호를 같이 받아서 *"이건 지금 보여주고 저건 사후에"* 가 **원리적으로 불가능**합니다(§7) |
| **②** | **수신자별 메시지** | 유족이 여럿일 때 **각자에게 다른 글**을 남기는 것이 이 도메인의 정서적 본체입니다. 지금은 한 덩어리라 전원이 같은 글을 봅니다 → 🔵 **`06-05`가 이 기능의 정본이 됐습니다**(별도 화면) |

| **④** | **04·07로 값 전달** | 열어서 읽는 것으로 끝나지 않고 **유족이 다음에 할 일**(부고장 작성·디지털 정리)에 값을 넘깁니다(§8.4) |

> 🔵 **④가 이 기능이 단독 앱이 아니라 이어봄 안에 있는 이유입니다.** 나머지 셋은 다른 서비스도
> 만들 수 있지만, ④는 **01·04·07이 같은 플랫폼에 있을 때만** 성립합니다.

## 🗄️ 4. 데이터 모델

### 4.1 설계 원칙 4가지

| # | 원칙 | 근거 |
| :---: | :--- | :--- |
| ① | **본문과 메타데이터를 다른 모델로 분리한다** | `06-03` §7 — `include`로 통째 조인하면 **본문이 자동으로 딸려옵니다.** 모델을 나누면 실수로 열리는 경로가 사라집니다 |
| ② | **수신자 모델을 새로 만들지 않는다** | `FamilyDesignation` 재사용. 만들면 **가족 목록이 두 벌**이 됩니다 |
| ③ | **평문 저장 경로를 "임시로라도" 만들지 않는다** | `security.md` §6 · `06-03` §6 — *"임시가 그대로 남는다"* |
| ④ | **열람과 전달을 다른 로그로 남긴다** | `06-03` §4.1 — 섞으면 정상 전달 수천 건 사이에 예외 열람 1건이 묻힙니다 |

### 4.2 신설 모델 4개

```
User ─1:1─ EndingNote ─┬1:N─ EndingNoteEntry   (본문·암호문. 여기만 격리)
                       ├1:N─ FarewellMessage   (🔵 06-05 — 유족 메시지. 수신자별 1:1)
                       ├1:N─ EndingNoteGrant   (누구에게 · 어떤 섹션 · 언제)
                       └1:N─ EndingNoteLog     (열람/전달/개봉요청 — 불변)
FamilyDesignation ─────┘ (수신자. 새 모델 만들지 않음)
```

#### `EndingNote` — 메타데이터 전용. **운영자 화면은 여기까지만**(`06-03` §3.1 A안)

| 필드 | 타입 | 설명 |
| :--- | :--- | :--- |
| `id` / `userId` | String | `User` 1:1(`@unique`) |
| `status` | String | `DRAFT` \| `SEALED`(작성 완료·봉인) \| `RELEASED`(개봉됨) \| `FROZEN` |
| `sealedAt` / `releasedAt` | DateTime? | 봉인·개봉 시각 |
| `policyAgreedAt` | DateTime | 🔴 **`06-03` §5 열람 정책 동의 시각** — 가입 약관이 아니라 **작성 시작 시점**에 받음 |
| `sectionState` | Json | 섹션별 작성 완료 여부만(`{"lifeSupport":true,…}`) — **내용 없음** |
| `lastConfirmedAt` | DateTime | 연 1회 재확인(`00-27` §7과 같은 기조) |

#### `EndingNoteEntry` — 본문. **운영자 쿼리에 절대 포함되지 않습니다**

| 필드 | 타입 | 설명 |
| :--- | :--- | :--- |
| `noteId` | String | FK |
| `section` | String | §6.1의 8개 섹션 코드 |
| `title` | String? | 🔴 평문 허용 여부 확정 필요(§13 #3) |
| `bodyEnc` | String | **AES-256-GCM 암호문**(`encryptField`). 평문 컬럼 없음 |
| `recipientId` | String? | FK → `FamilyDesignation`. **null이면 지정 유족 전원** |
| `releaseTiming` | String | `IMMEDIATE` \| `EMERGENCY` \| `POSTMORTEM`(§7) |
| `updatedAt` | DateTime | 본인 수정 이력 |

#### `EndingNoteGrant` — **누구에게 어떤 섹션을 언제 여는가**

| 필드 | 설명 |
| :--- | :--- |
| `noteId` · `designationId` | 어떤 노트를, 어떤 가족에게 |
| `section` | 섹션 코드. `ALL` 허용 |
| `timing` | `IMMEDIATE` \| `EMERGENCY` \| `POSTMORTEM` |
| `revokedAt` | 🔴 **철회 경로 필수** — 한 번 준 권한을 되돌릴 수 없으면 가족 관계 변화(이혼·절연)에 대응 불가 |

#### `EndingNoteLog` — 불변 감사 로그(`06-03` §3.2 ③)

| 필드 | 설명 |
| :--- | :--- |
| `type` | 🔴 **`ADMIN_ACCESS`(열람) / `FAMILY_DELIVERY`(전달) / `RELEASE_REQUEST` / `SELF_VIEW`** — `06-03` §4.1대로 분리 |
| `reasonCode` | 예외 열람 사유 코드(자유 입력 금지) |
| `actorId` · `approverId` | 2인 승인. 🔴 **운영 인력이 1인이면 성립하지 않음**(§13 #6) |
| `notifiedAt` | 본인·유족에게 열람 사실을 알린 시각 |

> ✅ **애플리케이션에 삭제·수정 경로를 만들지 않습니다.** WORM 저장소는 `00-11` 인프라 확정 후

> 🟡 **권고: 업로드 화면에서 *"본인 음성만"* 을 명시하고, 산출물을 본인 계정의 초안으로만

#### 6.4-4 🔴 외부 전송 고지 — **이건 회피할 수 없어 고지로 처리합니다**

**브라우저 내장 음성 인식도 대부분 제조사 서버로 음성을 보냅니다.** 온디바이스로 완결되는

> ✅ **처리 방법 3가지**
> 1. **녹음 시작 전 고지** — *"음성 인식을 위해 말씀하신 내용이 음성인식 서비스로 전송됩니다.
>    이어봄은 **변환된 글만 저장**하며 음성 파일은 보관하지 않습니다."*
> 2. **처리방침 반영** — 위탁·국외이전 항목. 🔵 **`00-19` 개정은 이미 `00-27`·`00-28`·`06-04`와
>    묶어 1회 예정**이므로 **여기 얹으면 추가 비용이 없습니다**(§12).
> 3. **대체 경로 유지** — 🔴 **직접 타이핑 입력을 항상 함께 제공**합니다. 음성이 유일한 입력이면
>    전송에 동의하지 않는 사용자가 기능 자체를 못 씁니다(개인정보보호법 §16③ 기조).

#### 6.4-5 정확도 — **오인식된 유언 초안은 오탈자와 무게가 다릅니다**

- 🔵 **정정(2026-08-27)**: 초판은 *"저장 전 편집 확인을 **필수 단계로**. 사용자가 텍스트를 한 번
  확인해야 저장이 활성화된다"* 였고, 그래서 *"이 내용을 확인했습니다"* 버튼이 생겼습니다.
  **요구를 과하게 구현한 것입니다.**
  ✅ **진짜 요구는 "오인식된 채로 자동 저장되지 않는 것"이고, 명시적 저장 버튼 하나로 충족됩니다.**
  사용자가 텍스트를 눈앞에 두고 **저장을 누르는 행위 자체가 확인**입니다. 확인 → 저장 2단계는
  마찰만 늘리며, 6070 대상에서 특히 그렇습니다.
  → **보관함: 버튼 라벨은 「저장」 하나.** 별도 확인 단계를 두지 않습니다.
  → 🔴 **엔딩노트 ⑨: 확인 버튼을 제거합니다.** 음성이 `06-05`로 이관돼(§6.4-2) **타이핑만 남았고**,
    사용자가 직접 친 글을 자기가 재확인하는 절차는 의미가 없습니다. 게다가 **⑨는 저장 자체를
    하지 않아**(인쇄·복사·`.txt`) 확인 뒤에 일어날 저장이 없습니다.
- 🟡 **문장을 임의로 다듬지 않습니다.** 받아쓰기이지 대필이 아닙니다 — 어투를 바꾸면
  *"내가 한 말이 아닌데"* 가 됩니다.
- 🟡 **요건 체크는 문안 삽입이 아니라 안내로.** 주소·연월일을 **시스템이 채워 넣으면** 그게
  대필에 가까워집니다. *"주소가 빠졌습니다 — 번지까지 쓰셔야 합니다"* 로 **알려만 줍니다.**

#### 6.4-10-3 🔴 Node에는 Web Audio API가 없습니다 — 디코딩이 별도 단계입니다

**이게 이번 구현의 진짜 작업량입니다.** Whisper는 **16kHz 모노 `Float32Array`** 를 받는데,
Node에는 `AudioContext`가 없어 **m4a·mp3를 그대로 못 먹입니다.**

```
업로드(m4a/mp3/wav) → ffmpeg(스트림) → 16kHz 모노 PCM → Transformers.js → 텍스트
                          └─ 🔴 stdin→stdout 스트림으로. 임시 파일 만들지 않는다(§6.4-9-4)
```

- 🟡 ffmpeg 바이너리는 **prebuilt npm 패키지**로 받아 설치 절차를 없앱니다(시스템 설치 요구 ❌).
- 🔴 **`-i pipe:0 ... pipe:1` 스트림으로 처리합니다.** 파일로 떨구면 §6.4-9-4의 *"디스크에 쓰지 않는다"* 가
  **디코더 단계에서 조용히 깨집니다** — 여기가 가장 놓치기 쉬운 지점입니다.

#### 6.4-10-4 ⚠️ 한국어 정확도 — 미리 인정하고 갑니다

작은 모델(tiny·base)은 **한국어 인식률이 낮습니다.** §6.4-5가 *"오인식된 유언 초안은 오탈자와
무게가 다릅니다"* 라고 경고한 지점입니다.

> ✅ **그런데 §6.4-5가 이미 대비해 뒀습니다** — **저장 전 편집 확인이 필수 단계**이고,
> **타이핑 입력이 항상 동등하게 열려 있습니다**(§6.4-4 #3). **초안이지 받아쓰기 완제품이 아닙니다.**
> 🔴 **다만 화면이 정확도를 약속하지 않습니다.** *"정확하게 옮겨 드립니다"* 류 문구 금지 —
> §2.2가 여덟 번 잡아낸 패턴입니다.
> 🟡 **모델 크기는 구현 중 실측으로 정합니다** — 지금 스펙에 못 박지 않습니다. 정확도와 변환
> 시간의 균형은 **실제 한국어 유언 발화로 재봐야** 알 수 있습니다.

> 성능향상을 위해 활용될 수 있다는 점을 설명하고, 그에 대한 동의를 얻는 등** 관련 법령의 의무를

🔴 **법리도 같은 방향입니다.** 개인정보보호법상 **위탁**은 *"위탁자의 목적 범위 내에서 수탁자가 처리"*

*"처리방침 공개로 갈음"* 경로에 **올라타지 못합니다.** 별도 동의가 필요합니다.

##### 🔴 이것이 §6.4-9-2 #1 탈락 기준에 걸립니다

탈락 — 가격을 볼 필요도 없습니다.**"* → **부분동의 불가 = opt-out 불가.**

- ⑨는 §6.4-2가 **"본인 전용, 사후에도 유족에게 전달하지 않는다"** 로 **가장 강하게 격리한 데이터**입니다.

##### 🔴 Storage 설정이 §4.1 ③과 충돌합니다 — 구현 시 실측 확인 필요

Storage 칸이 **둘**입니다: **인식 대상 저장 경로**(올릴 음성) · **결과 파일 저장 경로**(인식 스크립트).

🔴 **"결과 파일"은 유언 초안 텍스트입니다.** 그것이 Object Storage에 **암호화 없이 평문 오브젝트**로
남으면 — **§4.1 ③ *"평문 저장 경로를 '임시로라도' 만들지 않는다"* 를 정면 위반**하고,
§6.4-9-4의 *"메모리 버퍼만, 즉시 파기"* 도 깨집니다. §6.4-2가 **유족에게조차 주지 않기로** 한 데이터입니다.

> ✅ **해결됨 — 2026-08-26 실측 확인**(walkthrough, `[Sonnet]`):
> **`resultToObs:false`로 호출하면 결과가 Object Storage에 떨어지지 않습니다.**
> 로컬 파일 직접 업로드(multipart) + 동기 응답으로 결과가 HTTP 응답으로만 돌아옵니다.
> 콘솔이 도메인 생성 시 경로를 **필수 입력**으로 요구할 뿐, 실제로는 지나가지 않습니다.
> → **§4.1 ③ 위반 없음.** ③(KMS 키 권한)도 이 결과로 **무의미해졌습니다**(버킷을 안 쓰므로).
>
> 🔴 **다만 실측에서 반증된 것이 하나 있습니다** — **요청 파라미터에 `diarization.enable:false`를
> 명시하지 않으면 화자 인식이 매번 켜집니다.** 콘솔에서 끈 것과 **별개**입니다(§6.4-11-6-2 표는
> 콘솔 설정이고, 호출 파라미터는 따로 꺼야 합니다). **끄지 않으면 §6.3이 받지 않기로 한
> 화자 특징 추출이 조용히 수행되고, 무료 한도도 별도로 소모됩니다.**

##### 🟡 버킷 KMS 암호화 — **켭니다. 단 `bodyEnc`를 대신하지 않습니다** (2026-08-26)

> 🔵 콘솔 문구: *"암호화 관리 — KMS 상품과 연동하여 버킷에 저장되는 객체를 자동으로 암호화합니다."*

| | **KMS 버킷 암호화** | **`bodyEnc`**(§4.2) |
| :--- | :--- | :--- |
| 막는 것 | **저장 매체 수준**(디스크·백업본 유출) | **읽는 주체 수준**(앱 키 없으면 못 읽음) |
| 읽기 권한자에게는 | 🔴 **투명하게 복호화 — 평문으로 보입니다** | ❌ 여전히 암호문 |

🔴 **그러므로 KMS를 켜도 *"버킷에 평문이 없다"* 가 되지 않습니다.** §4.1 ③이 말하는
*"평문 저장 경로를 만들지 않는다"* 는 **애플리케이션 레벨 암호화**를 뜻하고, KMS는 그걸 대신하지 못합니다.

> 🔴 **이걸 근거로 위 Storage 항목을 완화하지 않습니다.** 버킷은 여전히 **비어 있는 것이 목표**이고,
> `[Sonnet]`은 *"결과가 버킷에 떨어지는지"* 를 실측해야 합니다.
> **KMS는 혹시 떨어졌을 때 바닥을 높이는 것**이지, 떨어져도 된다는 뜻이 아닙니다.

✅ **그래도 켜는 이유**: 코드에 영향 0(투명 처리) · **비어 있을 예정인 곳일수록 지금 켜는 게 쉽습니다**
(나중에 켜면 기존 객체 재암호화가 붙습니다) · `06-03` §6이 키 관리를 `00-11` 확정 이후로 미뤄둔
상태라 **지금 가능한 최소 조치**입니다.

🔴 **확인 2건**: ① **추가 과금**(KMS는 통상 키 관리+호출 건수 별도 과금 — Free로 시작하는 맥락이라
요금 안내 확인. 🔍 현재 단가는 단정하지 않습니다) ② 🔴 **CLOVA Speech의 KMS 키 사용 권한** —
암호화 버킷은 접근 주체가 **키 사용 권한까지** 가져야 하며, 누락되면 **조용히 실패**합니다.
도메인 생성 후 **테스트 호출 1회로 확인**할 것.

> ✅ **키 종류는 `NCP 관리형 키`로 충분합니다**(2026-08-26 — 콘솔에서 그것만 선택 가능).
> 고객 관리형 키(CMK)의 실익은 **키를 폐기해 데이터를 소각**하는 것인데, **이 버킷은 비어 있는 것이
> 목표**라 소각할 대상이 없습니다. 게다가 관리형이든 CMK든 **읽기 권한자에겐 투명 복호화**라
> 위 표의 결론이 달라지지 않습니다 — 유언 초안의 실제 보호막은 **`bodyEnc`(앱 레벨)** 입니다.
> ⏸ **CMK가 필요해지는 시점은 §6.4-3의 Phase 2·3(음성 원본 보관)** 이며, `00-11` 확정과 함께 봅니다.

##### 🟡 Object Storage 요금 — **금액이 아니라 감시 지표로 씁니다** (2026-08-26 요금표 확인)

저장 28원/GB-월 · PUT 0.0045원/건 · **DELETE 0원** · 아웃바운드 100원/GB 기준 실계산:

| 시나리오 | 월 요금 |

## 🔓 8. 개봉 절차

### 8.1 상태 기계

```
SEALED ──[유족의 개봉 요청]──> RELEASE_REQUESTED
   └─ 요청자: ACCEPTED 상태의 FamilyDesignation(PRIMARY 우선)
RELEASE_REQUESTED ──[L3: 사망 확인]──> DEATH_VERIFIED
DEATH_VERIFIED ──[L4: 지정 유족 이중 동의]──> RELEASED
RELEASED ──> 수신자별 전달(§8.3)
```

> ⏸ **L3·L4의 실제 판정과 사망 확인 모델은 `00-12` §4가 정본**이고, 그 앞뒤 흐름(누가 언제
> 확인하는가)은 **`00-30` §9**가 다룹니다. 여기서는 **06이 그 신호를 받아 무엇을 하는지**만 정합니다.

### 8.2 🔴 "이중 동의"가 성립하지 않는 경우

`06-01`이 화면에 약속한 *"지정 유족의 이중 동의"* 는 **지정 유족이 2명 이상일 때만** 성립합니다.

| 상황 | 처리 권고 |
| :--- | :--- |
| 지정 유족 **1명** | 🟡 **L3 + 대기기간(7일) + 통지**로 대체. *"이중 동의"* 라 적어두고 1명이 두 번 누르게 하는 것이 **가장 나쁩니다**(`06-03` §8-2와 같은 지적) |
| **2명 이상** | ✅ `PRIMARY` 1인 + 다른 `ACCEPTED` 1인의 동의 |
| **0명** | 🔴 **개봉 불가.** 작성 시점에 ***"수신자가 없으면 사후에 전달되지 않습니다"*** 를 명시 |

### 8.3 전달은 "권한 부여"이지 "발송"이 아닙니다

화면은 *"열람 키가 자동 발송"* 이라고 약속했지만(§2.2 ③), **키를 문자로 보내는 순간 그 문자가
곧 열쇠**가 되어 재전파·오배송 사고가 `00-27` §9.1-1과 똑같이 재현됩니다.

> ✅ **통지는 *"열람 가능해졌습니다"* 라는 알림뿐이고, 실제 열람은 로그인 후 계정 권한으로 합니다.**
> 이미 `acceptedUserId`로 계정이 연결돼 있으므로 **키를 보낼 이유가 없습니다.**
