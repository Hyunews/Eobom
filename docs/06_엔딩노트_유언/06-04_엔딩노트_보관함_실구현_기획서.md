## ⚠️ 4. 사장님 안과의 충돌 3건 — 정정 제안

### 4.1 🔴 "알림톡/문자 발송" ↔ 2026-08-21 개발자 확정

`00-27` §9.1은 **이어봄이 발송 주체가 되지 않는다**를 확정했습니다. 근거는 *"비용 0 · 발신번호
사전등록 불필요"* 이고, `07-03` §2.2(카톡 부고장)와 같은 사상입니다.

**두 판단이 충돌하는 것처럼 보이지만, 실제로는 트리거가 다릅니다.**

| 통지 트리거 | 발송 주체 | 판정 |
| :--- | :--- | :--- |
| **ⓐ 본인이 살아서 가족을 지정할 때** | **본인**(공유 버튼) | ✅ **현행 유지 권고.** 본인이 직접 보내는 것이 가장 자연스럽고, *"모르는 번호로 온 [이어봄] 문자"* 보다 수락률이 높습니다 |
| **ⓑ 사망 확인 후 유족에게 알릴 때** | 🔴 **이어봄일 수밖에 없습니다** | 본인이 죽었으므로 보낼 사람이 없습니다. `00-27` §11 #2도 *"Phase 3에는 발송 수단이 반드시 필요"* 라고 이미 남겨 뒀습니다 |

> 🟡 **권고: 사장님 안을 ⓑ에만 적용합니다.** ⓐ까지 알림톡으로 바꾸면 **발신번호 사전등록 · 카카오
> 비즈니스 채널 개설 · 템플릿 사전 심사**가 오픈 전 과제로 추가되는데, 얻는 것은 *"본인이 안 눌러도
> 된다"* 뿐입니다. **ⓑ는 어차피 필요하므로 그때 한 번에 도입합니다.**
> 🔴 **확인 필요** — 알림톡 템플릿의 정보성/광고성 판정, 발신번호 사전등록 요건은 §12로 넘깁니다.

### 4.2 🔴 "정부24 연계" — 지금 단정하지 않습니다

`00-27` §10 Phase 3이 이미 *"정부24 연계는 그 위에 L4로 얹습니다(개발자 지시로 후순위)"* 라고
적어 두었습니다. **여기서 한 걸음 더 나가지 않는 이유**는 다음과 같습니다.

- 행정정보 공동이용·전자증명서 유통은 **이용 주체(공공/민간)와 제공 범위가 제도로 정해져 있고**,
  민간 플랫폼이 **타인의 사망 사실을 조회**하는 것은 성격이 다릅니다.
- **가능 여부를 확인하기 전에 화면·모델에 반영하면**, 안 될 경우 되돌릴 곳이 많아집니다.

> ✅ **정본 경로는 `00-12` §4 L3(서류 기반)입니다.** 정부24·전자증명서는 **성립하면 L3를 대체하는
> 것이 아니라 L3를 자동화하는 것**이므로, **L3를 먼저 만들면 나중에 얹는 형태가 됩니다.**
> 🔴 확인 항목은 §12 표에 있습니다. **확인 전까지 화면에 *"행정망 연동"* 문구를 쓰지 않습니다** —
> §2.2 ④(*"국립연명의료관리기관 DB 호환"*)와 같은 실수를 반복하게 됩니다.

### 4.3 ⚠️ "Zero-Knowledge" — 요구는 타당하고, 용어만 정정합니다

사장님 정책 1은 *"유족으로 연결되었더라도 **생전에는** 자산 정보나 비밀 유언을 볼 수 없도록
UI와 API 레벨에서 **완벽히 격리**"* 입니다. **이 요구는 그대로 채택합니다.** 다만 —

| | 뜻 | 이 서비스에서 |
| :--- | :--- | :--- |
| **암호학적 Zero-Knowledge(E2E)** | 서버도 복호화할 수 없음 | ❌ **`06-03` §1.1이 기각.** 키를 아는 사람이 **죽고 없어** 사후 개봉이 원리적으로 불가능. 6070 시니어에게 키 관리를 넘길 수도 없음 |
| **권한 격리(사장님 의도)** | 유족 계정으로는 생전에 접근 경로 자체가 없음 | ✅ **채택.** API·UI·쿼리 3층에서 구현(§7.4) |

> 🟡 **용어 통일 권고: "Zero-Knowledge" 대신 「생전 봉인(Sealed)」을 씁니다.**
> 대외 문구에 *"Zero-Knowledge"* 를 쓰면 **서버도 못 본다는 뜻으로 읽히는데 사실이 아니고**,
> 그건 `06-03` §1이 경계한 *"보증의 어투로 말하는 약속"* 그 자체입니다.
> **`06-03` §5의 동의 문구가 이미 정직한 표현을 확정해 두었습니다** — 그것을 씁니다.

## 🗄️ 5. 데이터 모델 — 이번 실구현의 몸통

### 5.1 설계 원칙 4가지

| # | 원칙 | 근거 |
| :---: | :--- | :--- |
| ① | **본문과 메타데이터를 다른 모델로 분리한다** | `06-03` §7 — `include`로 통째 조인하면 **본문이 자동으로 딸려옵니다.** 모델을 나누면 실수로 열리는 경로가 사라집니다 |
| ② | **가족 모델을 새로 만들지 않는다** | `FamilyDesignation`을 그대로 씁니다. 06 전용 수신자 모델을 만들면 **가족 목록이 두 벌**이 됩니다 |
| ③ | **평문 저장 경로를 "임시로라도" 만들지 않는다** | `security.md` §6 · `06-03` §6 — *"임시가 그대로 남는다"* |
| ④ | **열람과 전달을 다른 로그로 남긴다** | `06-03` §4.1 — 섞으면 정상 전달 수천 건 사이에 예외 열람 1건이 묻힙니다 |

### 5.2 신설 모델 4개

```
User ─1:1─ EndingNote ─1:N─ EndingNoteEntry   (본문·암호문. 여기만 격리)
                       └1:N─ EndingNoteGrant   (누구에게 · 어떤 섹션 · 언제 열리나)
                       └1:N─ EndingNoteLog     (열람/전달/개봉요청 — 불변)
FamilyDesignation ─────────┘ (수신자는 여기서 옴. 새 모델 만들지 않음)
```

#### `EndingNote` — 메타데이터 전용. **운영자 화면은 여기까지만 봅니다**(`06-03` §3.1 A안)

| 필드 | 타입 | 설명 |
| :--- | :--- | :--- |
| `id` / `userId` | String | `User` 1:1(`@unique`) |
| `status` | String | `DRAFT` \| `SEALED`(작성 완료·봉인) \| `RELEASED`(사후 개봉됨) \| `FROZEN` |
| `sealedAt` / `releasedAt` | DateTime? | 봉인·개봉 시각 |
| `policyAgreedAt` | DateTime | 🔴 **`06-03` §5 열람 정책 동의 시각.** 작성 시작 시점에 받음 — 가입 약관과 별개 |
| `sectionState` | Json | 섹션별 작성 완료 여부만(`{"lifeSupport":true,"assets":false,…}`) — **내용 없음** |
| `lastConfirmedAt` | DateTime | 연 1회 재확인(`00-27` §7과 동일 기조) |

#### `EndingNoteEntry` — 본문. **운영자 화면 쿼리에 절대 포함되지 않습니다**

| 필드 | 타입 | 설명 |
| :--- | :--- | :--- |
| `noteId` | String | FK |
| `section` | String | §6.1의 8개 섹션 코드 |
| `title` | String? | 🔴 **평문 허용 여부 확정 필요**(§13 #4). 목록 표시에 필요하나 제목만으로도 내용이 새는 경우가 있음 |

| `recipientId` | String? | FK → `FamilyDesignation`. **null이면 지정 유족 전원** |
| `releaseTiming` | String | `IMMEDIATE`(즉시 공유) \| `EMERGENCY`(응급 시) \| `POSTMORTEM`(사후) — §7 |
| `updatedAt` | DateTime | 본인 수정 이력 |

#### `EndingNoteGrant` — 사장님 UX의 *"열람 범위 설정"* 이 저장되는 곳

| 필드 | 설명 |
| :--- | :--- |
| `noteId` · `designationId` | 어떤 노트를, 어떤 가족에게 |
| `section` | 섹션 코드. `ALL` 허용 |
| `timing` | `IMMEDIATE` \| `EMERGENCY` \| `POSTMORTEM` |
| `revokedAt` | 🔴 **철회 경로 필수** — 한 번 준 권한을 되돌릴 수 없으면 가족 관계 변화(이혼·절연)에 대응 불가 |

#### `EndingNoteLog` — 불변 감사 로그(`06-03` §3.2 ③)

| 필드 | 설명 |
| :--- | :--- |
| `type` | 🔴 **`ADMIN_ACCESS`(열람) / `FAMILY_DELIVERY`(전달) / `RELEASE_REQUEST`(개봉 요청) / `SELF_VIEW`** — `06-03` §4.1대로 **분리** |

| `actorId` · `approverId` | 2인 승인(4-eyes). 🔴 §13 #6 — **운영 인력이 1인이면 성립하지 않음** |
| `notifiedAt` | 본인·유족에게 열람 사실을 알린 시각 |

### 7.2 🔴 "응급 열람"이 이 설계에서 가장 위험한 문입니다

**본인이 죽지 않았는데 남이 내 기록을 여는 유일한 경로**이고, 현재 화면은 이미
*"보호자 휴대전화 SMS 인증 후 1회 열람"* 을 약속해 두었습니다(§2.2 ②).

| 위험 | 통제 |
| :--- | :--- |
| 보호자가 **응급이 아닐 때** 열어봄 | ✅ **열람 즉시 본인에게 통지**(`06-03` §3.2 ④와 같은 억제력) · 로그 필수 |
| 열람 범위가 넓음 | 🔴 **①②⑦만.** 자산·메시지는 **응급 열람 대상에서 원천 제외**(모델 레벨에서 `EMERGENCY` 부여 금지) |
| SMS 인증 수단 없음 | ⏸ **`User.phoneVerifiedAt`이 `00-28` Phase 3까지 항상 null** — 본인확인 수단이 서기 전에는 **응급 열람 기능을 열지 않습니다** |

> 🟡 **권고: 응급 열람은 Phase 3으로 미루고, 그때까지 화면 문구를 내립니다.**
> 지금 상태에서 ②를 남겨두면 **작동하지 않는 안전장치를 약속한 것**이 됩니다.

### 7.3 ⏸ 즉시 공유(생전)의 부작용 하나

*"장례 방식은 즉시 공유"* 는 편리하지만, **가족이 그것을 읽었다는 사실을 본인이 알 수 있어야
합니다.** 그러지 않으면 *"내가 쓴 걸 언제부터 보고 있었지"* 라는 역방향 불안이 생깁니다.
🟡 **본인 화면에 "가족 열람 이력"을 노출합니다**(`SELF_VIEW`가 아닌 `FAMILY_DELIVERY` 로그 재사용).

### 7.4 격리는 3층에서 (사장님 정책 1의 구현)

| 층 | 구현 |
| :--- | :--- |
| **API** | 가족용 조회 엔드포인트가 `timing`을 **서버에서 판정**합니다. 클라이언트가 보낸 값은 무시 |
| **쿼리** | `EndingNoteEntry`는 **`select`로 필드 명시**(`06-03` §7). `include` 통째 조인 금지 |
| **UI** | 잠긴 섹션은 **제목도 보이지 않습니다** — *"자산 정보(잠김)"* 라고 표시하면 **자산이 있다는 사실**이 이미 새어 나갑니다 |

## 🔓 8. 사후 개봉 — 사장님 2단계의 구체화

### 8.1 상태 기계

```
SEALED ──[유족의 개봉 요청]──> RELEASE_REQUESTED
   └─ 요청자: ACCEPTED 상태의 FamilyDesignation(PRIMARY 우선)
RELEASE_REQUESTED ──[L3: 서류 화면 확인]──> DEATH_VERIFIED
DEATH_VERIFIED ──[L4: 지정 유족 이중 동의]──> RELEASED
RELEASED ──> 수신자별 전달(§8.3)
```

### 8.2 🔴 L4 "이중 동의"가 성립하지 않는 경우

`06-01`이 화면에 약속한 *"지정 유족의 이중 동의"* 는 **지정 유족이 2명 이상일 때만** 성립합니다.

| 상황 | 처리 권고 |
| :--- | :--- |
| 지정 유족 **1명** | 🟡 **L3 + 대기기간(7일) + 통지**로 대체. *"이중 동의"* 라고 적어두고 1명이 두 번 누르게 하는 것이 **가장 나쁩니다**(`06-03` §8-2와 같은 지적) |
| 지정 유족 **2명 이상** | ✅ `PRIMARY` 1인 + 다른 `ACCEPTED` 1인의 동의 |
| 지정 유족 **0명** | 🔴 **개봉 불가.** 작성 시점에 ***"수신자가 없으면 사후에 전달되지 않습니다"*** 를 명시해야 합니다 |

> 🔴 **§13 #2가 이 표의 확정 항목입니다.** 여기가 안 정해지면 개봉 API를 짤 수 없습니다.

### 8.3 전달은 "열람 권한 부여"이지 "발송"이 아닙니다

화면은 *"열람 키가 자동 발송"* 이라고 약속했지만(§2.2 ③), **키를 문자로 보내는 순간 그 문자가
곧 열쇠**가 되어 재전파·오배송 사고가 `00-27` §9.1-1과 똑같이 재현됩니다.

> ✅ **권고: 통지는 *"열람 가능해졌습니다"* 라는 알림뿐이고, 실제 열람은 로그인 후 계정 권한으로
> 합니다.** 이미 `acceptedUserId`로 계정이 연결돼 있으므로 **키를 보낼 이유가 없습니다.**

### 8.4 04·07과의 연결 (사장님 2단계의 *"디지털 유품 리스트"*)

| 대상 | 어디 있나 | 개봉 시 |
| :--- | :--- | :--- |
| 엔딩노트 본문 | 06 `EndingNoteEntry` | 권한 부여 |
| 디지털 유품 목록 | **04** `DigitalCleanupItem` | 🟡 **의향(⑤)을 04 체크리스트에 자동 반영** — 목록 자체는 04가 소유 |
| 장례 의향 | 06 ②섹션 | 🟡 **07 부고장 작성 시 프리필** — 상주가 처음부터 다시 정하지 않아도 됨 |

> ✅ **이 연결이 실제 체감 가치입니다.** 엔딩노트를 "열어서 읽는 것"으로 끝내지 않고,
> **유족이 바로 다음에 해야 할 일(07 부고장·04 정리)에 값을 흘려보내는 것**이 이 도메인이
> 플랫폼 안에 있는 이유입니다.

## 👨‍👩‍👧 9. 다중 유족 — 사장님 정책 2

`00-27` §6이 이미 `PRIMARY`/`VIEWER` 2단과 `priority`를 두었고, **§11 #3(`PRIMARY` 복수 허용)이
확정 대기**로 열려 있었습니다. **사장님 지시가 그 답입니다.**

| 사장님 정책 | 반영 |
| :--- | :--- |
| **1:N 매핑**(첫째 아들·둘째 딸 동시 지정) | ✅ 이미 지원(상한 10명, `00-27` §4.2) |

> 🟡 **권고 확정안: `PRIMARY` 기본 1명 · 복수 허용 · 강제하지 않음.**
> 1명 강제는 **그 1명이 먼저 사망하거나 연락두절이면 되돌릴 방법이 없습니다**(`00-27` §6).
> 화면에서는 *"대표 1명"* 을 권하되, 시스템은 복수를 허용하고 `priority`로 순서를 둡니다.
