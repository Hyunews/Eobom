## 2. 무엇을 만드는가

### 2.1 흐름 — ⑨의 **반대 방향 입구**

| | 지금 ⑨ (`06-04` §6.4) | 🆕 이 기획 |
| :--- | :--- | :--- |
| 순서 | **타이핑** → 요건 안내 → 인쇄 → **손으로 베껴 씀** | **손으로 씀** → 사진 → **텍스트로 인식** → 요건 확인 → ⑨에 남김 |
| 산출물 | 텍스트 초안 | 텍스트 초안 **+ 요건 확인 결과** |

사용자가 올리는 사진은 두 종류다 — 둘 다 받는다.
- **ⓐ 손으로 쓴 초안** — 아직 확정 전. 다시 쓰기 전에 빠진 것을 보고 싶다.
- **ⓑ 이미 완성한 자필 유언장** — 원본은 집에 두고, **내용 기록**과 **빠진 것 확인**을 원한다.

### 2.2 기능 3개

| # | 기능 | 설명 |
| :---: | :--- | :--- |
| **F1** | **사진 → 텍스트** (사장님 지시) | 사진 1~여러 장 업로드 → OCR → 텍스트가 ⑨ 편집 영역으로 들어감 → 사용자가 고쳐서 저장 |
| **F2** | **요건 확인** (개발자 보완) | 인식 결과에서 **연월일·주소·성명**을 찾고, 사진에서 **날인**을 찾고, **전문이 손글씨인지** 본다 → 항목마다 결과 + 근거 표시 |
| **F3** | **근거 표시** | 사진 위에 찾은 위치를 박스로 표시. *"여기서 찾았다"* 를 보여 줘야 사용자가 오판을 잡는다 |

### 2.3 🔴 "4대 요건"의 정확한 범위

민법 §1066 자필증서 요건은 **다섯 가지**다: **전문·연월일·주소·성명을 직접 손으로 쓰고 + 날인**.
지금 ⑨ 화면(`EndingNotePage.tsx` 922행)은 *"4대 요건"* 으로 **주소·연월일·성명·날인**을 보여주고, **전문 자서(손글씨)** 는 별도 문장으로 안내한다.
→ 이 기획의 **요건 확인은 5개 항목**으로 한다. 화면 이름(*4대 요건*)을 바꿀지는 §7 결정 #6.

## 3. 요건 확인(F2) 설계 — 🔴 09-07에 한 번 뺀 기능이다

⑨에는 원래 정규식 자동 검증(`hasAddressHint`·`hasDateHint`)이 있었고, **09-07 개발자 지시로 삭제됐다** — *"초안 문맥에 따라 오판 가능성이 커서"*(`EndingNotePage.tsx` 918행 주석).
이번 설계는 그 이유를 정면으로 받는다.

| 09-07 문제 | 이번 설계의 답 |
| :--- | :--- |
| 결과가 *있음/없음* 둘뿐 → 틀리면 그대로 틀린 말 | **세 가지 결과**: `찾음`(근거 표시) · `찾지 못함` · `판단 못 함` |
| 왜 그렇게 판단했는지 안 보임 | **근거 표시(F3)** — 찾은 글귀와 사진 위 위치를 보여준다 |
| 기계 판정이 곧 결론 | **판정은 제안, 확인은 사람** — 항목마다 사용자가 직접 체크하는 칸은 **그대로 남긴다**. 자동 결과는 그 옆의 참고 |
| 타이핑 초안은 근거가 약함 | 🟡 **자동 확인은 사진 경로에만 켠다**. 타이핑 초안은 지금처럼 안내만(09-07 결정 존중) |

### 3.1 항목별 방법

| 항목 | 무엇을 찾나 | 방법 | `판단 못 함`이 되는 경우 |
| :--- | :--- | :--- | :--- |
| **연월일** | 연·월·일이 **모두** 있는 날짜 | 텍스트 규칙: `YYYY년 M월 D일` · `YYYY. M. D.` · 한자 숫자 등 | 연·월만 있음 · *"길일"* 같은 표현(→ `찾지 못함`으로, 사유 표시) · 날짜가 두 개 이상 |
| **주소** | 시·도부터 **번지/건물번호까지** | 텍스트 규칙: 시·도·시군구 + 도로명/지번 + 번호 | 동네 이름까지만 있음(→ 사유 *"번지 없음"*) |
| **성명** | 본인 이름 | 계정에 등록된 **이름과 일치하는 글귀** 검색 | 계정에 이름 없음 · 인식 결과에 비슷한 글귀만 있음 |
| **날인** | 도장 또는 지장 | 🔵 **이미지 분석**(OCR 아님): **붉은색(인주) 덩어리**를 찾고, 성명 근처인지 본다 | 검은 도장 · 흑백 사진 · 사진이 흐림 |
| **전문 자서** | 본문 전체가 손글씨인가 | 🔍 OCR 업체가 **손글씨/인쇄체 구분**을 돌려주면 사용, 아니면 `판단 못 함` 고정 | 업체가 구분을 안 줌 · 섞여 있음(→ *"인쇄된 글자가 섞여 있음"* 표시) |

- 🔴 **결과 문구는 사실만** — *"연월일: 2026년 9월 28일 (2쪽 맨 아래)"*, *"주소: 찾지 못함 — 번지 없음"*. **유효·무효·적합·안전 같은 말을 쓰지 않는다**(`00-39` 규칙 6-2). 전체 합계(*"5개 중 5개 충족"*)도 두지 않는다 — 합계가 곧 *"유효"* 로 읽힌다.
- 🔵 규칙은 **서버의 순수 함수 하나**(`checkWillRequirements(ocrResult, image, userName)`)로 둔다. 입력·출력이 고정돼 **테스트 사진 묶음으로 회귀 검사**가 된다.

## 4. OCR 업체 — 🔴 음성 때 탈락 기준을 그대로 쓴다

`06-04` §6.4-9-2의 표를 그대로 적용한다. **가격보다 1~3번이 먼저**다.

| # | 확인 항목 | 🟡 NCP **CLOVA OCR** (권고 후보) |
| :---: | :--- | :--- |
| 1 | 🔴 입력 데이터 **학습 활용 거부** 가능? | 🔍 약관 실독 필요 — CLOVA Speech는 *동의 기반(opt-in)*, 부분동의 불가였다(`06-04` §6.4-11-5 #1) |
| 2 | 🔴 위탁 계약 또는 이용자 제3자 제공 동의 경로 | 🔍 Speech와 같으면 **동의 경로**(§6.4-11-6 ⓐ 체크박스) 재사용 |
| 3 | 🔴 **인식 결과 보관 기간** | 🔍 Speech는 *텍스트 7일 보관*이었다(§6.4-11-2) — OCR 약관에서 같은 조항 확인, **처리방침에 그대로 적는다** |
| 4 | 🟡 국내 처리 | 네이버클라우드(국내). 🔴 단 백엔드가 Render `oregon`이라 **사진이 미국을 먼저 거친다** — 음성과 같은 상태(§6.4-11-1 #4) |
| 5 | 🔍 **한국어 손글씨** 인식 지원 · 품질 | 확인 필요 — 이 기능의 핵심. **고령자 필체 샘플로 실측** |
| 6 | 🔍 손글씨/인쇄체 구분 · 글자 위치(박스) 반환 | F2 전문 자서 · F3 근거 표시가 여기에 달렸다 |
| 7 | ✅ 지원 형식(09-28 개발자 확인) · 🔍 용량 · 쪽수 | ✅ **`jpg` · `png` · `pdf` · `tiff`** — 🔴 **HEIC 없음.** 아이폰 기본 사진 형식이라 **우리가 변환해서 넘긴다**(§4.1). 🔍 용량·쪽수 상한은 확인 필요 |
| 8 | 🔍 가격 · 무료 한도 | 확인 후 사장님 판단 |

### 4.0 ✅ 약관 실독 — *CLOVA OCR 서비스 이용약관*(2020-10-15 시행, 09-28 개발자 제공 전문)

| 기준 | 조항 | 판정 |
| :--- | :--- | :--- |
| **#1 학습 활용** | 🔵 **해당 조항이 없다.** CLOVA Speech에는 *"고객의 동의가 있는 경우 … 음성 데이터를 취득, 보관 및 활용"*(Speech 제4조 ②)이 있었고 **부분동의가 불가**해 문제였는데, OCR 약관에는 **올린 이미지를 엔진 개선에 쓴다는 문장 자체가 없다** | ✅ **Speech보다 낫다.** 🟡 단 *"정하지 않은 사항은 네이버 클라우드 플랫폼 서비스 이용약관 … 적용"*(제3조 ②) — **없다는 것이 금지한다는 뜻은 아니다.** 공통 약관·콘솔 신청 화면에 별도 동의 칸이 있는지 한 번 본다 |
| **#2 위탁·동의** | **제10조 ①** — *"필요하다면 회사 등과 개인정보 위수탁계약을 체결하거나 이용자로부터 개인정보의 제3자 제공에 관한 동의를 얻어야"* | ✅ **Speech 제7조 ②와 같은 문장.** 택일이라 **음성 때처럼 동의 체크박스로** 간다(`06-04` §6.4-11-6 ⓐ 재사용) |
| **#3 보관** | 🔵 **Speech의 "인식 결과 7일 보관"(Speech 제7조 ①) 같은 조항이 없다.** 제6조(데이터 백업)가 말하는 *"서비스 관련 데이터"* 는 제2조 ④의 정의상 **Custom 모델·학습 결과물** 쪽이다 | 🟡 **약관상 보관 조항 없음 — 그러나 "보관하지 않는다"는 조항도 없다.** 호출 이미지·인식 결과·로그를 남기는지 **NCP에 문의해 답을 받아 둔다**(처리방침에 적을 문장이 필요하다 — *없다고 추정해서 쓰지 않는다*) |
| #5 손글씨 | 약관 범위 밖 | 🔍 상품 문서 + **필체 샘플 실측** |
| 정확도 | **제12조 ②** — *"결과의 신뢰도 및 정확성 등에 대해 보증을 하지 않으며 … 진실성에 대하여 어떠한 확인도 하지 않습니다"* | ✅ Speech 제9조 ②와 같다 → **§8 #3의 답**: 업체가 보증하지 않으므로 **이어봄 화면도 정확도를 약속하지 않는다**. §6 단계 5의 *"틀릴 수 있습니다 … 고친 뒤 저장"* 고정 표시가 계약상 근거를 가진다 |
| 운영 | **제7조 ①** — **1년 이상 호출이 없으면** *휴면도메인*으로 30일 통지 후 해지 가능 | 🟡 기능 플래그를 오래 꺼 두면 도메인이 해지될 수 있다 — 운영 메모 |
| 책임 | 제5조 · 제10조 ② — 약관·법령 위반 시 **고객(이어봄)이 배상·면책** | 🟡 동의 없이 올리게 만드는 경로가 생기면 이어봄 책임 — 동의 체크 **없이는 업로드 불가**(§6 단계 1)가 그래서 필수 |

> ✅ **API Gateway 약관**(2020-10-15 시행, 09-28 개발자 제공 전문)도 실독 — **걸리는 조항 없음.** 학습 활용·데이터 보관 조항 **없음**(OCR 약관과 같은 상태). 이어봄에 걸리는 것은 둘:
> **제5조 ②** 인증키(Secret) 관리 책임 — 🔴 유출이 의심되면 **즉시 삭제·재발급**(커밋 금지는 §5 그대로) ·
> **제8조** 개인정보 법령 준수·면책 책임은 이어봄 — OCR 제10조와 같은 취지, 동의 체크박스로 대응.
> 🟡 **NCP 문의(§4.0 #3)에 API Gateway도 넣는다** — 게이트웨이가 **요청·응답 본문을 로그로 남기는지**(약관에 없다).
> ✅ **Stage `v1` 설정 실화면(09-28)**: **API 캐시 꺼짐**(기본값) · Throttling·IP ACL 꺼짐. 🔴 자동 생성 Product(*"Please do not modify or delete"*)라 **설정을 바꾸지 않는다.**
> 🟡 **같은 화면의 Endpoint 도메인이 `http://clovaocr-api-kr.ncloud.com/external/v1`** — 이어봄 → 게이트웨이는 HTTPS지만 **게이트웨이 → OCR 엔진 구간이 `http`로 적혀 있다.** 네이버 내부망일 가능성이 높으나 유언 내용이 지나가는 구간이라 **NCP 문의에 함께 넣는다**(자동 생성값이라 우리가 고치지 않는다).
> ✅ **호출 주소**는 OCR 도메인 화면의 Invoke URL(`…/custom/v1/{domainId}/{signature}/general` 형태 — 도메인값이 채워진 완성 주소)을 쓴다. Stage 화면의 주소는 공통 앞부분뿐이다.

> ✅ **결론: 탈락 사유 없음.** 음성(CLOVA Speech)보다 조건이 가볍다 — 학습 활용 동의 문제와 7일 보관 조항이 **둘 다 없다.**
> 🟡 남은 확인은 둘: ① 공통 약관·콘솔에 학습 활용 동의 칸이 따로 있는지 ② 호출 데이터 보관 여부(NCP 문의).

| 🔴 **크기 줄이기** | 휴대폰 사진은 긴 변이 보통 4,000px 안팎이라 **권장(1,960px)을 넘는다** → **긴 변 1,960px로 줄여서 보낸다.** 브라우저가 읽을 수 있으면 **올리기 전에 브라우저에서 줄이고**(업로드도 가벼워짐), 서버에서 한 번 더 확인해 넘치면 메모리에서 줄인다(§5 — 파일로 쓰지 않음). ✅ **PDF는 줄이지 않는다**(09-28 편차 검토) — 쪽수 상한(5쪽)만 확인하고 원본 그대로 넘긴다. 페이지 렌더링은 CLOVA 쪽이 한다 |
| 여러 장 상한 | 사진 5장(§7 #7) · PDF는 콘솔 한도 10쪽이지만 **이어봄은 5쪽까지**로 맞춘다. 🔄 **10-06 PDF는 1개만, 사진과 섞지 않는다**(개발자 결정) — 이전에는 PDF 여러 개·사진과 섞기가 막혀 있지 않아 한 번에 최대 25쪽(호출 25회)이 나갈 수 있었다. 한 번 올리기 = **사진 1~5장** 또는 **PDF 1개(5쪽까지)**. 어기면 *"PDF는 1개만 올릴 수 있고, 사진과 함께 올릴 수 없습니다."* 한 줄(화면에서 먼저 막고 서버도 다시 확인) |
| 변환도 실패하면 | *"이 사진 형식은 열 수 없습니다. jpg·png로 저장해 다시 올려 주세요"* 한 줄 + 타이핑 입력은 그대로(§6) |
| 여러 장 | 🟡 **최대 5장**, 올린 순서 = 쪽 순서. 순서 바꾸기 가능 |
| 용량 | 🔵 **사진(`jpg`·`png`·`heic`) 1장당 5MB · PDF 1개당 20MB**(🔄 10-06 개발자 결정 — 50MB→20MB(1차)→사진만 5MB(2차)) · **고르기 전에 화면에 표시**(§6.4-9-3과 같은 이유). 🔴 **브라우저는 `jpg`·`png`를 줄인 뒤의 크기로 검사한다** — 줄이기 전 원본으로 검사하면 줄이면 약 1MB가 될 고화소 휴대폰 사진이 막힌다(10-06 재검수 결함 ③). 서버는 받은 파일을 형식별로 같은 한도로 다시 확인한다. 넘으면 사진 *"사진 1장은 5MB까지 올릴 수 있습니다."* · PDF *"PDF 파일은 20MB까지 올릴 수 있습니다."* 한 줄. 근거: 앱 화면으로 올리는 사진은 긴 변 1,960px(약 1MB)로 줄어 들어오므로 5MB는 일반 이용자에게 영향이 없고, 큰 사진을 보내는 경로(API 직접 호출)만 4분의 1로 줄인다. - **사진 테두리** = `outline 3px #C4581A` + 옅은 주황 배경(사람 확인 "색 그대로"). 박스가 없는 항목(날인·전문 자서, 찾지 못함)은 테두리 없이 `이 항목은 사진에서 표시할 위치가 없습니다.`
- 요건 목록 아래 고정: `자동 확인은 참고용입니다. 요건 체크는 유언장 초안 화면에서 직접 해 주세요.` / 하단: `인식된 글은 틀릴 수 있습니다. 사진과 대조해 확인해 주세요.` / 버튼은 P1 그대로(취소·뒤에 붙이기·바꾸기, 초안이 비면 `초안에 넣기`).
- **처음 열 때 선택 없음**(캔버스는 보여 주려고 `주소`를 골라 둔 상태).

**모바일 규칙(사람 결정 09-29)**
1. **사진 탭** — 사진은 **가로 꽉 참, 비율 유지. 세로로 넘치면 스크롤 허용.** 쪽 넘기기는 사진 **위** 줄 오른쪽(사진에 겹치지 않음 — 스크롤하면 밀려나므로).
2. **요건 탭** — **스크롤 없이 한 화면.** 넘치면 근거를 1줄 말줄임. 박스가 있는 행만 오른쪽 `›`, 누르면 **사진 탭으로 전환 + 해당 쪽 + 테두리 + 테두리가 보이게 스크롤.**
3. **사진 탭 위 설명 줄**(`주소 · 찾음 — "…"`)은 🔴 **요건 행을 눌러 넘어왔을 때만** 보인다(A안). 사진 탭을 직접 누르면 설명 줄·테두리 **둘 다 없음**.
4. **인식된 글 탭** — 쪽별 제목(`1쪽`) + 글. 스크롤 허용.

**API가 줘야 하는 것**(§5 `checkWillRequirements` 출력): 항목 5개 `{ key, state: found|missing|unknown, evidence, page?, box? }` + 쪽마다 `{ width, height }`(박스 좌표 기준 = **OCR에 실제로 보낸 이미지** 크기). 화면은 사진을 **브라우저에 이미 있는 줄인 이미지**(object URL)로 그린다 — 서버는 이미지를 돌려주지 않는다(§5).
🟡 **PDF** — 브라우저가 쪽 이미지를 갖고 있지 않다. 1차는 **사진 칸 대신 `PDF는 사진 표시 없이 결과만 보여 줍니다.`** + 요건·글만(테두리 없음). pdf.js 렌더링은 별건.
