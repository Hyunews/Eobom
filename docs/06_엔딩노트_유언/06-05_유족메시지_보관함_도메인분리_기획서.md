## 🔴 4. 가장 위험한 지점 — STT 초안(⑨)과 음성 메시지의 혼동

**`06-04` §6.4-2가 세운 원칙**: 말로 남기는 유언장 **초안(⑨)은 본인 전용이고, 사후에도 유족에게
전달하지 않습니다.** 유족이 받으면 ***"이게 아버지 유언장인가"*** 로 읽기 때문입니다.

**그런데 이제 유족에게 실제로 전달되는 음성이 생깁니다.** 같은 마이크, 같은 녹음 버튼입니다.

| 혼동 방향 | 결과 |
| :--- | :--- |
| 보관함에 **유언 내용**을 말함 | 🔴 `06-02` §4.3이 기각한 **녹음유언이 이어봄을 통해 유족에게 배달**됩니다. 형제 분쟁 시 *"아버지가 이렇게 말했다"* 의 증거로 쓰입니다 |
| 엔딩노트 ⑨에 **작별 인사**를 말함 | 🟡 유족에게 영영 가지 않습니다. 사용자는 남겼다고 믿습니다 |

### 4.1 ✅ 분리가 이 문제를 완화합니다 — 그것이 분리의 두 번째 이유입니다

화면이 물리적으로 갈리면 *"여기는 마음을 전하는 곳, 저기는 유언장을 쓰기 위한 도구"* 라는
경계가 생깁니다. **한 화면에 있으면 어떤 문구를 써도 이 경계가 서지 않습니다.**

### 4.2 🔵 **정정(2026-08-26) — 말로 남기기(STT)는 보관함으로 옵니다**

> 🔵 **사장님 지시**: *"말로 남기는 초안 → Text로 변환 → **그 Text가 보관함에 담겨야 한다**."*

**초판은 정반대였습니다** — *"⑨는 엔딩노트에 남긴다. 전달되는 곳에 두면 사용자가 유족에게
간다고 믿는다."* **틀렸습니다.**

**이유는 `06-04` §6.4-2가 정본**입니다. 요지: 초판은 *"⑨ = 유언장 초안"* 이라는 깨끗한 카테고리를
가정했는데 **실제 발화는 마음과 재산 얘기가 한 녹음에 섞여 나옵니다.** 그러면 초판 설계는
**마음을 담은 부분까지 유족에게 영영 가지 않게** 만들고, 본인은 남겼다고 믿습니다.

| | 어디 | 입력 | 전달 |
| :--- | :--- | :--- | :--- |
| **말로 남기는 메시지** | 🔵 **보관함(여기)** | **음성(STT)** + 타이핑 | ✅ **사후 전달** |
| 유언장 쓰기 도구 | 엔딩노트 ⑧⑨ | **타이핑** | ❌ 본인 전용(필사 도구) |

✅ **음성 입력이 보관함으로 일원화**되어 *"음성 기능이 두 도메인에 흩어진다"* 는 문제도 함께 풀립니다.
✅ **§4.3의 경고 문구가 그대로 이 상황을 받습니다** — 보관함에 담기는 것은 **유언장이 아니라 편지**입니다.

> 🔴 **§4.1(분리가 혼동을 완화한다)은 여전히 유효합니다.** 경계가 *"어느 화면에 마이크가 있나"* 에서
> **"무엇을 남기는 곳인가"** 로 옮겨졌을 뿐입니다 — 보관함은 **마음을 전하는 곳**,
> 엔딩노트 ⑨는 **유언장을 손으로 쓰기 위한 도구**입니다.

### 4.3 🔴 양쪽에 상반된 고지를 상시 노출합니다

| 화면 | 문구 |
| :--- | :--- |
| 엔딩노트 ⑨ | *"이 초안은 **유족에게 전달되지 않습니다.** 직접 손으로 옮겨 쓰시기 위한 도구입니다.<br>마음을 전하고 싶으시면 **유족 메시지 보관함**을 이용해 주세요."* 🔵 뒷문장 추가(08-26) — **막다른 길로 두지 않습니다** |
| **보관함** | *"여기에 남기신 글과 음성은 **사망 확인 후 지정하신 분에게 전달됩니다.** 재산 분배·상속에 관한 내용은 **남기지 마세요** — 유언의 효력이 없고 유족 간 다툼의 씨앗이 됩니다."* |

> 🔴 **검증은 약속하지 않습니다.** 무엇을 말했는지 이어봄은 알 수 없습니다 —
> `06-04` §6.4-2-3 · `06-03` §1의 *"지킬 수 없는 문장은 넣지 않는다"* 와 같은 태도입니다.

## 🎙️ 5. 음성 — 원안(mp3)과 현실의 거리

### 5.1 🔴 지금 넣지 못하는 이유

`.harness/systems.md` §5 실측:

> 업로드 사진이 백엔드 **로컬 디스크(`eobom/backend/uploads/`)**에 저장된다.
> **Render는 재배포 시 디스크가 초기화**된다. **추모 사진도 여기 묶인다** — 스토리지 교체 전
> **추모관 오픈 금지**(`05-01` §2.6).

| 사진과 음성 메시지의 차이 | |
| :--- | :--- |
| 추모관 사진 | 소실되면 다시 올릴 수 있습니다 |
| **유족 메시지 음성** | 🔴 **소실 시점에 본인이 이미 없습니다.** 다시 올릴 사람이 없습니다 |

> 🔴 **이 도메인의 음성은 "수십 년 뒤 사후 전달"이 전제**라 **로컬 디스크가 원리적으로 불가**합니다.
> 사진보다 **더 엄격한** 선행 조건입니다.

### 5.2 추가로 서야 하는 것 — 스토리지만이 아닙니다

| # | 항목 | 왜 |
| :---: | :--- | :--- |
| ① | ✅ **오브젝트 스토리지** — **해소(2026-09-03)** | **Cloudflare R2 확정** → `00-11` §5.4. 버킷 3개 분리(§5.4-6) |
| ② | 🟡 **파일 단위 암호화** — **재평가(2026-09-03)** | 06 전용 키 `ENDING_NOTE_ENCRYPTION_KEY`와 `encryptNoteField`가 **이미 배선돼 있습니다**(`crypto.ts:94`) — *"새로 설계"* 가 아니라 **Buffer 버전 함수를 더 다는 일**입니다. 🔴 다만 **R2는 고객 관리 키가 없어**(`00-11` §5.4-4) **앱단 선암호화가 선택이 아니라 필수**입니다. 남는 과제는 **① 20MB 스트리밍**(통째로 메모리에 올리면 동시 접속에 서버가 눕습니다) **② 수십 년 뒤 열 수 있는 키 백업·교체** — `crypto.ts`의 `v1/v2` 버전 접두어가 토대입니다 |
| ③ | 🔴 **보유기간** | ⏸ `00-20`. *"사망 확인 전까지 무기한"* 이 성립하는지 확인 필요. 🆕 **탈퇴 시 30일 유예**는 §5.4-2에서 별도로 답합니다 |
| ④ | 🟡 **길이·용량 상한** | `06-04` §6.4-2-2 #2와 같은 항목. 화면에 **먼저** 표시 |
| ⑤ | 🟡 **포맷** | `06-04` §6.4-2-2 #1 — **아이폰 음성 메모 기본 형식은 `m4a`**입니다. mp3만 받으면 대부분 못 올립니다 |

### 5.3 ✅ 단계화 — 두 번 만들지 않는 순서

| Phase | 입력 | 상태 |
| :---: | :--- | :--- |
| **1** | **텍스트만** (수신자별 편지) | ✅ 지금 가능 |
| **2** | **직접 녹음 + 파일 업로드** | ⏸ §5.2 ①②③ 선행 |

> 🔴 **Phase 1 화면에 *"음성 메시지"* 를 약속 문구로 쓰지 않습니다.**
> `06-04` §2.2가 잡아낸 패턴(*"화면이 약속했는데 뒷받침이 없다"*)이 **새 화면에서 처음부터
> 재발하는 것**이 이 분리 작업의 가장 흔한 실패 방식입니다.
> ✅ 표기가 필요하면 `06-04` §2.2 ⑤ 방식 — ***"🎙️ 음성 메시지 (준비중)"*** 한 줄까지입니다.

> 🔵 **사장님 원안과의 차이는 여기 하나뿐입니다** — **mp3를 빼는 것이 아니라 순서를 뒤로
> 놓는 것**입니다. Phase 1에서 수신자 지정·편지 작성·개봉 배선을 완성해 두면,
> Phase 2는 **입력 경로 하나를 얹는 작업**이 됩니다(`06-04` §6.4-2의 Ⓑ→Ⓐ 논리와 동일).

### 🆕 5.4 반출 — 사망·탈퇴 시 데이터를 손에 남긴다 (2026-09-03 개발자 지시)

> 🔵 **신규 요구입니다.** *"고인 사망 or 탈퇴 등의 사유의 경우, 관련 데이터 백업 가능하도록

#### 5.4-1 두 사건은 성격이 정반대입니다

| 반출 후 서버 | 남김(보유기간까지) | 🔴 **파기** |

#### 5.4-2 ✅ 탈퇴 — **30일 유예 후 파기**, 그 사실을 알린다

> 🔴 **2026-09-03 정정.** 이전 논의에서 *"유예 보관은 '지웁니다' 약속 위반"* 이라고 적었는데
> **틀렸습니다.** 처리방침에 **"탈퇴 후 30일 보관 후 파기"라고 명시하면 위반이 아닙니다.**
> 위반은 *"즉시 삭제"* 라고 써놓고 들고 있을 때만 생깁니다.

🔴 **이 도메인에서는 유예가 오히려 필수입니다.** 수십 년치 유족 메시지를 가진 분이 실수로
(혹은 가족이 대신) 탈퇴를 누르고 즉시 삭제되면 **되돌릴 방법이 없습니다** — §5.1이 말한
*"다시 올릴 사람이 없다"* 가 삭제 경로에서 그대로 재발합니다.

**절차**

```
탈퇴 신청 → [30일 유예] → 탈퇴 완료 · 파기
             ├─ 철회(계정 복구) 가능
             └─ 반출(백업) 내려받기 가능
```

> ✅ **보유 근거**: 유예 기간에는 **탈퇴 처리가 아직 완료되지 않은 상태**로 둡니다. 계약이 살아
> 있으므로 보관 근거가 있습니다. 🔴 *"탈퇴는 끝났는데 데이터만 30일 갖고 있다"* 로 설계하면
> **표준 개인정보 보호지침의 "지체 없이 파기"** 와 부딪힙니다 — **순서를 이렇게 잡는 이유입니다.**
> ⏸ 30일이라는 숫자 자체는 `00-20`에 등재합니다.

#### 5.4-2-1 ✅ 30일 유예의 **구현 형태 = 소프트 삭제** (2026-09-03 확정)

> 🔴 **09-03 정정 2건**(`00-11` §5.4-5-1-1 · §5.4-5-3). 앞서 *"`Age` 30일 Bucket lock으로
> 실수 삭제를 막는다"* 고 적었으나 **락은 미채택**으로 뒤집혔습니다. `Age`는 **업로드 후 N일
> 동안만** 보호해 **31일째부터 무효**라 수십 년 보관에는 맞지 않고, 그 좁은 구간은 아래
> 소프트 삭제가 이미 덮습니다. **유예 30일 ↔ 락 30일 일치 조건도 함께 소멸**합니다.

**🔴 유예는 "R2에 남겨두는 것"이 아니라 "R2를 안 건드리는 것"으로 구현합니다.**

| 시점 | DB | R2 |
| :--- | :--- | :--- |
| 이용자 삭제·탈퇴 클릭 | `삭제대기`로 전이 · 목록에서 숨김 | 🔴 **아무 것도 하지 않음** |
| 유예 중 철회 | 상태 복구 | 그대로 |
| 유예 종료 | 행 파기 | **사람 승인 배치**가 원본+아카이브 삭제 |

🔴 **런타임 요청 경로에서 `DeleteObject`를 호출하지 않습니다.** 사용자 액션이 스토리지 삭제로
직결되지 않으므로, 프론트 버그·중복 요청·잘못된 ID가 곧바로 유실이 되지 않습니다.
🔴 **객체 키는 UUID·타임스탬프**로 만들어 재녹음이 **덮어쓰기가 아니라 새 키 쓰기**가 되게 합니다.
🔴 **파기 시 원본 버킷과 아카이브 사본을 함께** 지웁니다(`00-11` §5.4-5-2 ②층). 아카이브에도
무기한 락은 걸지 않습니다 — 파기 의무는 사본에도 적용됩니다.

> ⚠️ **소프트 삭제는 *정책*이지 *강제*가 아닙니다.** R2는 우리 DB의 `삭제대기` 플래그를 보지
> 않으므로 **정리 스크립트·마이그레이션·토큰 유출**에는 무력합니다(이 프로젝트가 두 번 겪은
> 경로입니다 — `db-safety.md`). 그래서 **아카이브 버킷이 Phase D 필수**입니다.

**🔴 안내 접점 — 한 번만 알리면 못 봅니다**

| 시점 | 내용 |
| :--- | :--- |
| **탈퇴 클릭 시** | 🔴 **건수를 구체적으로** — *"편지 8건, **음성 12건**이 30일 뒤 삭제됩니다"*. 숫자가 없으면 안 읽습니다 |
| 탈퇴 신청 완료 | 이메일 — 파기 예정일(날짜 명시) + 반출 링크 + 철회 방법 |
| **파기 D-7** | 🔴 **리마인드 필수.** 30일 전 안내 한 번만으로는 대부분 놓칩니다 |
| 파기 완료 | 완료 통지 |

#### 5.4-3 반출 꾸러미

```
eobom_유족메시지_20260903.zip
├─ 편지_01_아들에게.txt      (평문)
├─ 편지_01_아들에게.mp3      (음성, 복호화된 상태)

└─ 안내.txt                  (누가 언제 남겼는지 · 이어봄 없이 열리는 형식임을 설명)
```

- 🔴 **zip에 암호를 걸지 않습니다.** 수십 년 뒤 유족이 비밀번호를 알 리 없습니다. `06-03`의
  봉인 원칙은 **"열람 자격"** 에 걸리는 것이지 **파일 포맷**에 걸리는 것이 아닙니다 —
  방어선은 **전달 경로(로그인·본인확인·`RELEASED` 상태)** 이며 거기서 이미 섭니다.
- 🔴 **포맷은 `mp3`·`txt`로 변환해 내보냅니다.** `m4a`·`webm` 원본 그대로 주면 수십 년 뒤
  재생 프로그램이 없을 수 있습니다. **가장 흔한 포맷**으로 떨굽니다(`audioConvert` 재사용).
- ✅ **R2는 Egress 무료**라(`00-11` §5.4-2) 재다운로드 횟수를 인색하게 제한할 이유가 없습니다.

### 🆕 5.5 직접 녹음(Ⓑ) — 저장 옵션 (2026-09-03 개발자 지시)

#### 5.5-1 🔴 지금 구조로는 "옵션 추가"가 안 됩니다

현행 Ⓑ는 **Web Speech API**입니다(`VoiceToTextInput.tsx:35~59`). 브라우저가 마이크를 자체적으로
잡고 **글자만 돌려주는** 물건이라 **여기서 오디오를 꺼낼 수 없습니다.** 통역만 해주고 녹음은
안 하는 통역사입니다. 녹음하려면 `getUserMedia` + `MediaRecorder`를 **따로 물려야** 합니다.

⚠️ 마이크를 둘이 동시에 잡으면 브라우저·OS에 따라 충돌하거나 인식률이 떨어질 수 있고,
**iOS Safari는 Web Speech API 지원이 원래 불안정**합니다.

#### 5.5-2 ✅ 설계 — 녹음이 본체, 실시간 자막은 보조

```
[마이크 버튼] → getUserMedia 스트림
   ├─ MediaRecorder → 오디오 blob        ← ✅ 본체(저장 대상)
   └─ Web Speech API 병행 → 실시간 자막   ← 되면 좋고, 안 되면 생략
[녹음 종료]
   ├─ Web Speech 결과 있음 → 그대로 사용
   └─ 없음·실패(iOS 등) → blob을 Ⓐ 경로(Clova)로 보내 변환   ← 폴백
[사용자 편집 → 저장]
   ├─ 텍스트 → DB (encryptNoteField)
   └─ blob → 앱단 암호화 → R2 → mediaKey 기록
```

| 얻는 것 | |
| :--- | :--- |
| **iOS에서도 완결** | Web Speech가 없어도 녹음 + 서버 STT로 끝납니다 |
| **Ⓐ·Ⓑ 종착점 통일** | 저장 로직이 하나입니다(암호화 → R2 → `mediaKey`) |
| **인식 실패해도 음성이 남음** | 🔴 지금은 인식이 실패하면 **아무것도 안 남습니다** |

> ⚠️ **감수할 것**: 폴백이 돌면 Clova 변환 건수가 늘어 **무료 15분/월 한도를 더 빨리 태웁니다**
> (`06-04` §6.4-11-6-2). 유료 전환 시점이 앞당겨집니다.

#### 5.5-3 ✅ 저장 옵션 기본값 — **켬** (2026-09-03 개발자 확정)

**음성을 서비스의 핵심으로 삼겠다는 판단과 기본 끔은 서로 모순됩니다.** 6070 시니어가 옵션을
못 찾아 목소리를 놓치면 이 기능의 존재 이유가 사라집니다.

🔴 **대신 첫 녹음 시 1회 전면 안내가 반드시 따라야 합니다** — *"내 목소리가 저장되는 줄 몰랐다"*
를 막는 것이 기본 ON의 유일한 조건입니다. 체크박스 문구는 *"목소리도 함께 남기기"*.

#### 5.5-4 🔴 포맷 — 허용 목록을 넓혀야 합니다

## 🔊 5.6 🆕 저장된 음성의 **듣기·삭제** (2026-09-04 신설)

> 🔵 **왜 지금 신설하나** — D-1~D-3으로 음성이 **올라가기만** 합니다. 올린 사람이 **다시 듣거나
> 떼어낼 수단이 없습니다.** §5.4-2-1이 다루는 것은 *탈퇴* 축이고, *"첨부한 녹음만 떼어내기"* 는
> 어느 절에도 없었습니다. 개발자 요청(09-04)으로 채웁니다.

### 5.6-1 🔴 듣기는 **반드시 서버를 경유**합니다 — presigned URL로는 안 됩니다

| | |
| :--- | :--- |
| 왜 | R2에 있는 것은 **이어봄 키로 잠근 바이트**입니다(`00-11` §5.4-4 선암호화). presigned URL을 주면 브라우저가 **암호문을 받아 재생에 실패**합니다 |
| 그래서 | 백엔드가 `downloadVoiceObject`(복호화 포함, **이미 구현돼 있고 부르는 곳이 없습니다**)로 받아 응답 본문으로 내보냅니다 |
| 대가 | 트래픽이 서버를 탑니다. 🔵 20MB 상한 · **본인이 자기 것을 듣는 경로뿐**이라 규모 문제가 아닙니다 |

🔴 **이 절을 맨 앞에 두는 이유** — presigned URL은 오브젝트 스토리지의 *교과서적 정답*이라, 선암호화 전제를 잊으면 **반드시 그쪽으로 갑니다.** 가서 재생이 안 되는 것을 확인하고 되돌아오게 됩니다.

### 5.6-2 ✅ 재생 경로는 둘로 갈립니다

| 언제 | 어떻게 | 서버 왕복 |
| :--- | :--- | :---: |
| 방금 녹음·업로드하고 **아직 저장 전** | 브라우저 메모리의 blob을 `URL.createObjectURL`로 바로 재생 | ❌ 없음 |
| **저장된 메시지를 다시 열 때** | `GET /api/farewell-messages/:id/audio` | ✅ 있음 |

🔵 위쪽은 이미 손에 blob이 있는데 R2를 다녀올 이유가 없습니다. **업로드 직후 듣기는 서버를 안 탑니다.**
🔴 `URL.revokeObjectURL`로 정리합니다 — 안 하면 최대 20MB blob이 탭 수명 내내 남습니다.

### 5.6-3 ✅ 엔드포인트 `GET /api/farewell-messages/:id/audio`

- 소유권은 **메시지 기준**으로 봅니다(기존 컨트롤러의 `verifyBearerToken` 패턴).
  🔴 **`mediaKey`를 파라미터로 받는 엔드포인트를 만들지 않습니다** — 키만 알면 남의 음성이 열립니다.
- **404 조건 3가지**: `R2_ENABLED=false` · 첨부 없음 · `mediaDeletedAt != null`
- 헤더: `Content-Type` = `mediaMime` · `Content-Disposition: inline` ·
  🔴 `Cache-Control: no-store` — 유언 성격의 음성이 디스크 캐시에 남지 않게 합니다.
- 🔴 **`<audio src="…">`에는 `Authorization` 헤더를 실을 수 없습니다.** `fetch`로 받아 **blob URL을
  만들어** `<audio>`에 물립니다. 🔴 **쿠키 인증·쿼리스트링 토큰으로 우회하지 않습니다** —
  이 프로젝트는 Bearer 하나로 통일돼 있고, 여기서만 예외를 만들면 인증 경로가 둘이 됩니다.

### 5.6-4 ✅ 삭제 = 소프트 삭제. 🔴 **`mediaKey`를 지우지 않습니다**

🔴 **`mediaKey`를 `null`로 만들면 안 됩니다.** 그 값이 R2 객체를 가리키는 **유일한 실마리**입니다.
지우는 순간 원본과 아카이브 사본이 **양쪽 다 영원히 못 지우는 고아**가 됩니다 — 파기 의무가 있는
데이터에서 가장 나쁜 결과이고, *"지웠으니 깨끗하다"* 는 착각까지 같이 남습니다.

| 시점 | DB | R2 |
| :--- | :--- | :--- |
| 이용자가 "녹음 삭제" | `mediaDeletedAt = now()` · 응답에서 음성 숨김 | 🔴 **아무 것도 하지 않음** |
| 유예 30일 경과 | `mediaKey` 정리 | **사람 승인 배치**가 원본+아카이브 삭제 |

§5.4-2-1과 같은 원칙입니다 — **런타임 요청 경로에서 `DeleteObject`를 호출하지 않습니다.**
🔵 유예는 탈퇴와 같은 **30일**입니다. 숫자를 새로 만들지 않습니다.
⏸ **복구(되돌리기) UI는 넣지 않습니다** — 탈퇴 철회와 한 화면으로 다룹니다. 대신 삭제 확인
문구에 유예를 밝힙니다: *"30일 뒤 완전히 삭제됩니다."* 🔴 *"즉시 삭제됩니다"* 라고 쓰면
§5.4-2의 판단이 뒤집힙니다 — **쓴 대로 동작해야 합니다.**

### 5.6-5 ✅ 업로드 시점 = **확인 모달의 "저장"** (2026-09-04 개발자 확정)

> 🔄 **스펙갱신**(`roles.md` §2-1). D-3 구현은 **녹음을 멈추는 즉시** R2에 올립니다(확인 없음).
> 개발자가 흐름을 다시 정리하면서 **중지와 업로드 사이에 확인 모달**을 넣기로 했습니다.
> 🔵 **§5.6-5의 "고아 객체 확정 필요"가 이것으로 닫힙니다** — 취소하면 R2에 아무것도 안 갑니다.

**🔴 저장을 누르기 전에는 어디에도 쓰지 않습니다.** 녹음이 끝난 blob은 **브라우저 메모리에만**
있습니다. STT·R2·DB 셋 다 "저장" 이후에 일어납니다.

| | 취소 | 저장 |
| :--- | :--- | :--- |
| STT 변환 | ❌ | ✅ |
| R2 업로드 | ❌ **아무것도 안 올라감** | ✅ |
| DB 기록 | ❌ | ✅ |
| 남는 것 | **없음** — blob 폐기 + `revokeObjectURL` | 저장된 메시지 |

🔵 **이 한 가지 변경이 §5.6-5의 원래 문제를 없앱니다.** *"올려놓고 저장 안 하고 나가는"* 구간이
**존재하지 않게** 됩니다. 취소 버튼이 그 자리를 대신합니다.

**🔴 "저장"은 메시지 저장까지 한 번에 끝냅니다.** R2에만 올리고 메시지 저장을 따로 남겨두면
*"올렸는데 저장 안 함"* 구간이 그대로 돌아옵니다. 모달의 저장은 **STT → R2 → 메시지 기록**까지
한 흐름입니다. 본문 다듬기는 그 뒤 **수정**으로 합니다(카드가 이미 지원).

⚠️ **완전히 0이 되지는 않습니다** — R2 업로드는 됐는데 **메시지 기록이 실패**하면 1건이 남습니다
(네트워크 끊김 등). 🟡 **그때를 위한 수거 배치는 남겨둡니다**(D-6 #29) — R2 키 목록 ↔ DB
`mediaKey` 대조 후 **참조 없고 N일 지난 것**만 사람 승인으로 정리. `00-11` §5.4-5-2-2의
*"참조 확인 후 정리"* 가 그대로 절차입니다. ⏸ 구현은 급하지 않습니다 — 이제 **예외 상황에서만**
생기고, 비용은 0에 가깝습니다.

### 5.6-6 ✅ 화면 흐름 (2026-09-04 개발자 확정)

**Ⓑ 직접 녹음**

```
① "음성으로 말하기" 클릭 → 녹음 시작
② "녹음 중지" 클릭
③ 확인 모달 — "텍스트로 변환해서 저장할까요?"
④ [저장] → STT + R2 + DB     ┆     [취소] → 전부 폐기, 아무 데도 안 감
⑤ 듣기 · 삭제 버튼 활성화
```

**Ⓐ 파일 업로드**

```
① "파일 선택" → 파일 지정
② "업로드" → STT + R2 + DB
③ 듣기 · 삭제 버튼 활성화
```

🔵 **Ⓐ에는 별도 확인 모달을 두지 않습니다** — "업로드" 버튼 자체가 확인입니다. Ⓑ에 모달이 필요한
이유는 **중지가 곧 확정이 되어버리기 때문**이고, Ⓐ는 파일을 고르는 행위와 올리는 행위가 이미
나뉘어 있습니다.

🟡 **권고 — 모달 안에 "먼저 들어보기"를 넣습니다.** blob이 손에 있으니 **서버를 안 타고**
바로 재생됩니다(§5.6-2). 들어보지 않고 저장 여부를 정하라는 건 무리한 요구이고, 잘못 녹음된
파일이 R2·아카이브까지 가는 것을 **입구에서** 막습니다.
🔴 모달에 **"취소하면 녹음이 사라집니다"** 를 명시합니다 — 되돌릴 수 없는 폐기입니다.
🔵 STT는 몇 초 걸립니다 — 저장을 누른 뒤 **진행 표시**가 필요합니다(모달을 즉시 닫지 않습니다).

⏸ **⑤의 "듣기"는 방금 저장한 직후라면 로컬 blob으로 재생**합니다(§5.6-2). 새로고침 뒤에는
서버 경유(§5.6-3)로 자동 전환됩니다 — 같은 버튼, 다른 소스입니다.

### 5.6-7 🔴 편지 삭제도 **소프트 삭제**입니다 (2026-09-04 신설)

> 🔴 **제 스펙 누락입니다.** §5.6-4는 *"음성만 떼어내기"* 만 다뤘고 **편지 자체를 지우는 경로를
> 안 적었습니다.** 구현은 `prisma.farewellMessage.delete()` **하드 삭제**로 나갔고, Sonnet이
> 주석에 *"후속 필요"* 를 남기며 **이 절(§5.6-7)을 가리켰습니다** — 없는 절이었습니다.

**🔴 왜 하드 삭제가 안 되나** — `mediaKey`는 **행 안에만** 있습니다. 행을 지우면 R2 원본과
아카이브 사본을 가리키는 **유일한 실마리가 함께 사라집니다.** §5.6-4가 *"`mediaKey`를 `null`로
만들지 말라"* 고 한 것과 **같은 사고**이고, 행 삭제 쪽이 더 큽니다 — 본문까지 같이 없어져
**되돌릴 수단이 아예 없습니다.**

🔴 **이 도메인에서 즉시 삭제는 특히 위험합니다** — §5.4-2가 말한 *"수십 년치 유족 메시지를
가진 분이 실수로 눌렀을 때 되돌릴 방법이 없다"* 가 편지 단위에서 그대로 재발합니다.

| 시점 | DB | R2 |
| :--- | :--- | :--- |
| 이용자가 "편지 삭제" | `deletedAt = now()` · 목록·상세에서 제외 | 🔴 **아무 것도 하지 않음** |
| 유예 30일 경과 | **사람 승인 배치**가 행 파기 | 배치가 원본+아카이브 삭제 |

🔵 **유예는 30일** — 음성 삭제(§5.6-4)·탈퇴(§5.4-2)와 같은 숫자입니다.
🔴 확인 문구도 같습니다: *"30일 뒤 완전히 삭제됩니다."*
⏸ **이미 하드 삭제된 행이 있으면 되살리지 않습니다** — 검증 중 생긴 dev 데이터이고, 남은 R2
객체는 §5.6-8 ③(고아 수거)이 걷습니다. 🔴 **찾아서 지우려 들지 않습니다**(`00-11` §5.4-5-2-2).

### 5.6-8 ✅ 파기 배치 — **한 배치가 세 가지 만료를 봅니다** (2026-09-04 신설)

소프트 삭제만 있고 파기 경로가 없으면 화면에 *"30일 뒤 완전히 삭제됩니다"* 라고 써놓고
**안 지키는 상태**가 됩니다. §5.4-2가 경고한 바로 그 자리입니다 — **쓴 대로 동작해야 합니다.**

| | 대상 | 조치 |
| :---: | :--- | :--- |
| **①** | `mediaDeletedAt + 30일 < now` | 원장 기록 → R2 **원본** 삭제 → `mediaKey`·`mediaMime` 정리. 🔵 **행은 남깁니다**(편지 본문은 살아 있음). 아카이브는 2단계(§5.6-8-1) |
| **②** | `deletedAt + 30일 < now` | `mediaKey`가 있으면 ①을 먼저 하고, **그다음 행 파기** |
| **③** | ⏸ 고아 객체(§5.6-5) | R2 키 ↔ DB `mediaKey` 대조. **참조 없고 N일 지난 것**만. 🔴 대조 없는 삭제 금지 |

🔴 **`db-safety.md` 전 과정이 걸립니다** — 사람 승인 → 백업 → **파일 생성 확인** → 실행.
🔴 **`--confirm` 없이는 dry-run**(무엇을 몇 건 지울지 출력만). `rotate-keys.ts`와 같은 방식입니다.
🔴 **원본과 아카이브를 함께** 지웁니다(`00-11` §5.4-5-2). 아카이브만 남기면 파기 의무 위반입니다.
🔴 **단, 한 프로세스가 둘 다 지우는 것이 아닙니다** — 아래 §5.6-8-1.
🔴 **런타임 코드가 이 배치를 부르지 않습니다** — 별도 실행 스크립트입니다(§5.4-2-1).
🔵 ③은 이번에 만들지 않아도 됩니다 — ①②가 먼저입니다.

### 5.6-8-1 🔴 아카이브는 **2단계**로 지웁니다 (2026-09-04 신설 — 편차 판정)

> **경위**: 구현 중 위 "함께 지웁니다"가 `00-11` §5.4-5-2-1과 충돌한다는 지적이 올라왔습니다
> (`walkthrough.md` 편차). **지적이 맞고 위 문장이 부실했습니다** — *무엇을* 만 쓰고 *어떻게* 를
> 안 썼습니다. 백엔드는 아카이브에 닿는 **수단이 없고, 그것이 ②층의 정의**입니다.

**🔴 백엔드에 아카이브 키를 주는 선택지는 없습니다.** 그 키가 생기는 순간 *"앱이 털려도 사본은
남는다"* 가 거짓이 되고, ②층을 만든 이유가 통째로 사라집니다. 파기 편의와 침해 방어를 맞바꾸지
않습니다.

| 단계 | 실행 주체 | 수단 | 대상 |
| :---: | :--- | :--- | :--- |
| **1** | **어드민 화면**(§5.6-8-3) · 스크립트는 개발·비상용 | 버킷별 S3 키(기존) | R2 **원본** |
| **2** | 🆕 **파기 운영자(사람)** | **본인 Cloudflare 로그인** — 대시보드 또는 `wrangler` | R2 **아카이브** |

✅ **사람 로그인 방식으로 확정**(2026-09-04). 🔴 **새 자격증명을 발급하지 않습니다.**

> 🔴 **09-04 정정 — 최초 서술에서 "Admin 자격"이라 적었으나 오해를 부르는 표현이었습니다.**
> R2 토큰 등급 이름의 `Admin Read & Write`는 *관리자* 가 아니라 **계정의 모든 버킷**을 뜻합니다
> (§5.4-5-2). 아카이브 하나 지우자고 그 토큰을 만들면 원본·미디어·서류까지 한 문자열에 걸립니다.
> **필요한 건 새 토큰이 아니라, 이미 있는 사람의 로그인**입니다.

🔴 **"아카이브 버킷 전용 토큰을 발급해 스크립트에 붙인다"는 선택지는 없습니다.** 얼핏 기존
버킷별 토큰 3개(§5.4-6-1)와 같은 패턴으로 보이지만 **놓을 자리가 없습니다** — 운영 파기는
Render에서 돌고(§5.6-8-2), 거기 넣는 순간 그게 곧 "백엔드가 아카이브 키를 가진 것"입니다.
경로만 한 칸 늘어난 채 ②층이 무너집니다. **2단계 분리는 편의가 아니라 구조의 귀결입니다.**

🔵 **`00-11` §5.4-5-2-1 표에 행이 하나 늘어납니다**: `파기 운영자(사람) | 본인 로그인 | ✅ | ✅`.
상시 존재하지 않고 파기 때만 나타난다는 점, **저장되는 문자열이 없다**는 점이 백엔드와 다릅니다.

#### 5.6-8-1-1 🔴 그 사이 키를 잃어버리면 안 됩니다 — **원장은 DB 테이블입니다**

**stdout 출력은 조치가 아닙니다.** 1단계가 `mediaKey`를 비우고 목록을 콘솔에만 뿌리면,
터미널을 닫는 순간 **그 아카이브 객체를 가리키는 문자열이 세상에서 사라집니다.** DB에도 없고
화면에도 없습니다. 남는 길은 버킷 전수와 DB를 대조하는 것뿐인데 그게 ③이고 ⏸ 보류입니다.

> 🔴 **09-04 재판단 — 최초에 "파일로 append"라고 썼으나 운영에서 성립하지 않습니다.**
> 운영 1단계는 **Render에서 돌고**(§5.6-8-2), **Render 파일시스템은 재배포하면 사라집니다.**
> 이 프로젝트가 이미 같은 함정을 알고 있습니다 — 추모관 사진을 로컬디스크에 두어 오픈을
> 막아둔 그 건입니다(`systems.md` §5). **원장을 파일로 두면 D-9가 막으려던 사고가 그대로
> 납니다.** 파일 원장은 로컬 실행에서만 유효한 설계였습니다.

**✅ 원장은 DB 테이블로 둡니다** — `ArchivePurgeQueue`(§6.4).

- 🔴 1단계는 R2 원본 삭제 **전에** 이 테이블에 행을 만듭니다. 순서가 뒤집히면 위 사고가 납니다.
  🔵 **행을 만들고 실제 삭제에 실패하는 쪽이 안전합니다** — 그건 "지울 게 남았다"로 끝나지만,
  반대는 "지울 게 있는지조차 모른다"가 됩니다.
- 🔴 그다음 `mediaKey`·`mediaMime`을 비웁니다(①) / 행을 파기합니다(②).
- 2단계를 마치면 사람이 `purgedAt`을 채웁니다. **삭제하지 않고 남깁니다** — 파기 이력은
  개인정보 파기 의무의 증빙이고, 이 테이블에는 개인정보가 아니라 **오브젝트 키만** 있습니다.
- 🟡 **파기는 2단계까지 끝나야 완료입니다.** 1단계만 돌고 멈춘 상태는 *"지웠다"* 가 아니라
  **"절반 지웠다"** 입니다 — 화면 문구(*"30일 뒤 완전히 삭제됩니다"*)를 아직 안 지킨 상태입니다.
  🔵 `purgedAt IS NULL` 건수가 곧 **미이행 잔량**입니다. 세어볼 수 있어야 합니다.
- 🔵 **로컬 실행은 이 테이블에 쓰지 않습니다**(§5.6-8-2 — dev는 아카이브가 없음).

🔵 **2단계 자동화는 뒤로 미룹니다**(사람 판단, 09-04). 지금은 파기 대상이 소수라 손으로 처리
가능하고, 원장이 있으면 **미룬 것이 사라지지는 않습니다.** 건수가 늘면 그때 Worker에 삭제
엔드포인트를 두는 설계를 다시 봅니다(→ `backlog.md`).

### 5.6-8-2 🔴 **어느 환경에서 돌리나** (2026-09-04 신설 — 누락 보완)

> 🔴 **최초 §5.6-8은 이 항목을 통째로 빠뜨렸습니다.** 스크립트는 `R2_BUCKET_FAREWELL_VOICE`가
> 가리키는 곳을 지웁니다 — **즉 어느 환경에서 실행하느냐가 무엇을 지우느냐를 결정합니다.**
> 08-27 사고(정리 스크립트)가 정확히 이 종류였습니다.

| | 대상 DB | 대상 버킷 | 아카이브 | 2단계 |
| :--- | :--- | :--- | :---: | :--- |
| **로컬 실행** | 로컬 Docker | `eobom-farewell-voice-dev` | 🔴 **없음** | **불필요** |
| **운영 실행** | Supabase | `eobom-farewell-voice` | ✅ 있음 | **필요** |

🔴 **dev 버킷에는 아카이브가 없습니다.** Worker가 운영 버킷만 감시하기 때문이며 **의도된
동작**입니다(`00-11` §5.4-6-3 — 개발 데이터가 아카이브에 쌓이지 않게 하려는 것).
→ **로컬 실행은 원장에 한 줄도 쌓지 않고, 2단계 안내도 출력하지 않습니다.** 운영 아카이브
이름을 안내하면 사람이 **거기 존재한 적 없는 키**를 찾으러 갑니다. 객체 키가 `Date.now()-uuid`
라 **dev 키와 운영 키는 생김새로 구분되지 않습니다** — 한 원장에 섞이면 *"안 보임"* 이
**이미 처리함**인지 **애초에 없던 것**인지 영영 알 수 없게 됩니다.

🔴 **스크립트가 스스로 판별합니다.** 버킷명이 `-dev`로 끝나면 개발 모드로 간주해 원장·2단계
안내를 건너뜁니다. 🔴 **환경을 사람의 기억에 맡기지 않습니다.**

🔴 **운영 파기는 Render에서 돕니다.** 운영 DB와 운영 R2 키가 동시에 필요한데 그 둘이 함께
있는 곳은 Render뿐입니다. 🔴 **운영 자격증명을 로컬로 내려받아 돌리지 않습니다** —
`security.md` §1(운영 개인정보를 로컬로 가져오지 않는다)에 정면으로 걸립니다.
✅ **운영 실행 방법은 §5.6-8-3으로 확정됐습니다**(어드민 화면). 위 ⏸는 해소됐습니다.
🔵 스크립트는 **개발용·비상용**으로 남습니다 — 로직은 어드민과 같은 서비스 함수를 씁니다.

### 5.6-8-3 ✅ **누가 실행하나 — 어드민 화면** (2026-09-04 확정, 사람 판단)

> **경위**: §5.6-8-2가 *"운영 파기는 Render에서 돈다"* 까지만 정하고 **어떻게 돌리는지**를
> ⏸로 남겼습니다. 사람이 **웹 어드민 계정**을 쓰자고 제안했고, 채택합니다. 어드민은 이미
> Render 위에서 돌며 **운영 DB·운영 R2 키를 갖고 있습니다** — 쉘 진입도, 운영 자격증명을
> 로컬로 내리는 일도 없어집니다(`security.md` §1). **누가 언제 파기했는지도 남습니다.**

#### 5.6-8-3-1 🔴 경계 — **앱은 규칙을 집행만 하고, 덮어쓰지 못합니다**

| 무엇 | 어디서 | 왜 |
| :--- | :--- | :--- |
| **정상 만료분** — 유예 30일이 지난 것(①②) | ✅ **어드민 화면** | 규칙대로 때가 된 것. 판단이 필요 없음 |
| **강제 삭제** — 만료 전인데 지금 지워야 하는 것 | 🔴 **Cloudflare 대시보드만** | 법적 요구·오업로드 등. **판단이 필요한 일** |

🔴 **어드민에 강제 삭제 경로를 만들지 않습니다.** API·버튼·`--force` 플래그 전부 해당합니다.
**한번 만들어둔 우회로는 반드시 쓰입니다.**

🔵 **이것이 실제로 지키는 것**: 어드민 세션이 통째로 침해돼도 공격자가 할 수 있는 최대치가
**"어차피 30일 뒤 지워질 것을 며칠 일찍 지우는 것"** 으로 묶입니다. 피해 상한이 운영 수칙이
아니라 **코드 구조**로 잡힙니다. 강제 삭제를 하나라도 열면 이 성질이 사라집니다.

🔴 **만료 여부는 서버가 다시 검증합니다.** 화면이 보낸 `id`를 그대로 믿지 않습니다 —
서버가 `mediaDeletedAt`·`deletedAt`을 다시 읽어 30일이 지났는지 확인하고, 아니면 **거부**합니다.
이 검증이 없으면 위 경계는 화면 장식일 뿐입니다.

#### 5.6-8-3-2 🔴 화면이 하는 일 / 하지 않는 일

**합니다**
- 만료 대상 **목록 조회**(①②를 구분해서 표시)
- **건별 선택 → 1단계 실행**(원장 기록 → R2 원본 삭제 → `mediaKey` 정리 / 행 파기)
- **아카이브 미이행 목록**(`purgedAt IS NULL`) 표시 — 사람이 대시보드에서 지울 키 목록
- 2단계를 마친 뒤 **완료 표시**(`purgedAt` 기록)

**하지 않습니다**
- 🔴 **아카이브 삭제.** 백엔드에 수단이 없고, 주면 ②층이 사라집니다(§5.6-8-1)
- 🔴 **일괄 파기 버튼.** 목록에서 **건별 선택**만 합니다 — *"전부 파기"* 는 사고가 나는 모양입니다
- 🔴 **만료 전 데이터에 대한 어떤 조작도**(§5.6-8-3-1)

#### 5.6-8-3-3 🔴 실행 가드

- 🔴 실행 직전 **대상 건수를 사람이 직접 입력**해 확인시킵니다. 오클릭으로 지워지지 않게 합니다.
- 🔴 **감사 로그** — 누가·언제·몇 건·어떤 키. 파기는 법적 의무이므로 **이행 증빙**이 필요합니다.
- 🟡 **파기 화면에 한해 재인증**(실행 직전 비밀번호 재입력). `Admin` 모델은 현재
  **이메일+비밀번호뿐**이라(2FA 없음), 비밀번호 하나가 곧 삭제 권한이 되는 것을 값싸게 막습니다.
  🔵 2FA 도입은 별건으로 미룹니다.
- 🔴 **스크립트를 없애지 않습니다.** 어드민이 못 뜰 때의 경로로 남기되, **어드민과 같은 서비스
  함수**를 부릅니다. 두 경로가 각자 로직을 갖게 두면 한쪽만 고쳐지는 날이 옵니다.
- 🟡 **화면 대장 등재 필요** — `00-06`에 어드민 파기 화면을 올려야 합니다(→ `context.md` Opus).

**D-6-1. 🆕 업로드 시점 이동** (§5.6-5·§5.6-6) — 🔄 **D-3 구현 변경**입니다
