## 🔴 4. 가장 위험한 지점 — 보관함 편지가 "유언"처럼 쓰이는 것

✅ **지금 구조**: 음성 입력은 **보관함에만** 있고(§4.2), ⑨ 유언장 초안은 **타이핑·사진 인식만** 받는 본인 전용 도구입니다(`06-04` §6.4).
처음 걱정한 *"⑨에 작별 인사를 말해 유족에게 영영 가지 않는"* 혼동은 ⑨에서 음성이 빠져 **사라졌습니다**(처음 서술은 **부록: 경위**).

🔴 **남은 위험은 한 방향입니다**:

| 위험 | 결과 |
| :--- | :--- |
| 보관함에 **유언 내용(재산 분배 등)**을 말하거나 씀 | 🔴 `06-02` §4.3이 기각한 **녹음유언이 이어봄을 통해 유족에게 배달**되는 모양이 됩니다. 형제 분쟁 시 *"아버지가 이렇게 말했다"* 의 증거로 쓰입니다 |
| 🆕 **고인의 육성 파일**을 다른 가족이 올려 편지로 만듦 | 🔴 처음엔 *"초안이 유족에게 가지 않아 분쟁 자료가 안 된다"* 고 봤으나(`06-04` §6.4-2-3), 이제 업로드 음성은 **편지로 유족에게 갑니다** — 🔴 결정 대기(`06-04` §6.4-2-3) |
| 🔵 지금 화면이 막는 방법 | 편지라는 이름 · 전달 고지 한 문장(§4.3) · 업로드 안내 *"본인의 음성만 올려 주세요."* — 🔴 *"재산 분배·상속 내용은 남기지 마세요"* 는 **두지 않기로 확정**(2026-09-30, §4.3) |

### 4.1 ✅ 분리가 이 문제를 완화합니다 — 그것이 분리의 두 번째 이유입니다

화면이 물리적으로 갈리면 *"여기는 마음을 전하는 곳, 저기는 유언장을 쓰기 위한 도구"* 라는
경계가 생깁니다. **한 화면에 있으면 어떤 문구를 써도 이 경계가 서지 않습니다.**

### 4.2 🔵 **정정(2026-08-26) — 말로 남기기(STT)는 보관함으로 옵니다**

> 🔵 **사장님 지시**: *"말로 남기는 초안 → Text로 변환 → **그 Text가 보관함에 담겨야 한다**."* (초판은 정반대였음 — **부록: 경위**)

**이유는 `06-04` §6.4-2가 정본**입니다. 요지: 초판은 *"⑨ = 유언장 초안"* 이라는 깨끗한 카테고리를
가정했는데 **실제 발화는 마음과 재산 얘기가 한 녹음에 섞여 나옵니다.** 그러면 초판 설계는
**마음을 담은 부분까지 유족에게 영영 가지 않게** 만들고, 본인은 남겼다고 믿습니다.

| | 어디 | 입력 | 전달 |
| :--- | :--- | :--- | :--- |
| **말로 남기는 메시지** | 🔵 **보관함(여기)** | **음성(STT)** + 타이핑 | ✅ **사후 전달** |
| 유언장 쓰기 도구 | 엔딩노트 ⑧⑨ | **타이핑** | ❌ 본인 전용(필사 도구) |

✅ **음성 입력이 보관함으로 일원화**되어 *"음성 기능이 두 도메인에 흩어진다"* 는 문제도 함께 풀립니다(✅ 구현 — `components/farewell/VoiceToTextInput.tsx`).
✅ 보관함에 담기는 것은 **유언장이 아니라 편지**입니다. 🔴 다만 이를 받쳐 주던 고지 *"재산 분배·상속 내용은 남기지 마세요"* 는 지금 화면에 없습니다(§4.3 2026-09-30 확정) — 위 §4 표.

> 🔴 **§4.1(분리가 혼동을 완화한다)은 여전히 유효합니다.** 경계가 *"어느 화면에 마이크가 있나"* 에서
> **"무엇을 남기는 곳인가"** 로 옮겨졌을 뿐입니다 — 보관함은 **마음을 전하는 곳**,
> 엔딩노트 ⑨는 **유언장을 손으로 쓰기 위한 도구**입니다.

### 4.3 🔴 양쪽에 상반된 고지를 상시 노출합니다

| 화면 | 문구 |
| :--- | :--- |
| 엔딩노트 ⑨ | *"이 초안은 **유족에게 전달되지 않습니다.** 직접 손으로 옮겨 쓰시기 위한 도구입니다.<br>마음을 전하고 싶으시면 **유족 메시지 보관함**을 이용해 주세요."* 🔵 뒷문장 추가(08-26) — **막다른 길로 두지 않습니다** |

## 🎙️ 5. 음성 — 원안(mp3)과 현실의 거리

### 5.1 ✅ 음성은 오브젝트 스토리지(R2)에 — 로컬 디스크를 쓰지 않습니다

✅ 음성 원본은 **Cloudflare R2에 이어봄 키로 암호화**해 둡니다(`00-11` §5.4 · 2026-09-03 확정). 서버 로컬 디스크(`eobomDev/backend/uploads/`)는 재배포 때 지워져 쓰지 않습니다.
🔴 **이 도메인의 음성은 "수십 년 뒤 사후 전달"이 전제**라 **소실 시점에 본인이 이미 없습니다** — 다시 올릴 사람이 없으므로 로컬 디스크는 원리적으로 불가입니다.
🔵 추모관 사진은 별건으로 **여전히 로컬 디스크**라 오픈 금지 상태입니다(`systems.md` §5 · `context.md`). 처음 서술(*"지금 넣지 못하는 이유"*)은 **부록: 경위**.

#### 5.4-3 반출 꾸러미

```
eobom_유족메시지_20260903.zip
├─ 편지_01_아들에게.txt      (평문)
├─ 편지_01_아들에게.mp3      (음성, 복호화된 상태)
├─ …
└─ 안내.txt                  (누가 언제 남겼는지 · 이어봄 없이 열리는 형식임을 설명)
```

- 🔴 **zip에 암호를 걸지 않습니다.** 수십 년 뒤 유족이 비밀번호를 알 리 없습니다. `06-03`의

  재생 프로그램이 없을 수 있습니다. **가장 흔한 포맷**으로 떨굽니다(`audioConvert` 재사용).
- ✅ **R2는 Egress 무료**라(`00-11` §5.4-2) 재다운로드 횟수를 인색하게 제한할 이유가 없습니다.

#### 5.4-3-1 🆕 편지 **단건 반출** (2026-09-07 개발자 지시)

전체 반출만으로는 부족합니다. 유족이 원하는 건 대개 **그 한 통**인데, 8건짜리 꾸러미를 받아
압축을 풀어 찾게 하는 건 경황 없는 시기에 맞지 않습니다.
**목록·상세 양쪽에서 편지 한 통을 그 자리에서 내려받을 수 있어야 합니다**(§5.6-6 흐름에 버튼 추가).

- 🔴 **단건도 zip입니다.** 음성이 있으면 `txt`+`mp3`, 없으면 `txt` 하나지만 **꾸러미 규격은 같게**
  갑니다. 음성 유무·`mediaDeletedAt` 여부에 따라 응답이 `text/plain` ↔ `application/zip`으로
  갈리면 프론트가 확장자·`Content-Type`을 분기해야 하고, **음성 삭제 한 번에 그 분기가 뒤집힙니다.**
- **`안내.txt`는 단건에도 넣습니다.** 이어봄 없이 열리는 형식임을 알리는 게 목적이라(§5.4-3)
  꾸러미가 작다고 뺄 이유가 없습니다.

**파일 이름**

```
eobom_유족메시지_아들에게_20260907.zip
```

- 제목을 파일명에 씁니다 — 여러 통을 받아두면 `_01_` 같은 번호로는 못 찾습니다.
- 🔴 **제목을 그대로 쓰지 않습니다**: 경로 문자(`/ \ : * ? " < > |`)·개행 제거 → 앞뒤 공백 정리 →
  **40자 절단** → 빈 문자열이면 `제목없음`. 파일명은 **사용자가 쓴 값이 그대로 들어가는 자리**입니다.
- 🔴 `Content-Disposition`의 한글은 **RFC 5987 `filename*=UTF-8''…`** 로 냅니다.

**엔드포인트 `GET /api/farewell-messages/:id/export`**

- 소유권은 **§5.6-3과 같은 규칙** — **메시지 기준**, 기존 `verifyBearerToken` 패턴.
  🔴 `mediaKey`나 R2 키를 파라미터로 받는 엔드포인트를 만들지 않습니다.
- **404 조건**: 메시지 없음 · 소유자 아님 · 편지가 소프트 삭제됨(§5.6-7).
  ⚠️ **음성이 없거나 `mediaDeletedAt != null`인 것은 404가 아닙니다** — `txt`만 든 꾸러미를 줍니다.
- 🔴 `Cache-Control: no-store` — §5.6-3과 같은 이유입니다.
- 🔴 **`<a href="…">`로는 못 받습니다.** Bearer를 실을 수 없습니다(§5.6-3). `fetch` → blob URL →
  `a.download` → `revokeObjectURL`. **전체 반출도 같은 방식**입니다.

**전체 반출과의 관계**

- 🔴 **꾸러미 생성기는 하나입니다.** 전체 = "이 사용자의 살아있는 편지 전부", 단건 = "id 하나" —
  **같은 함수에 대상 목록만 다르게** 넘깁니다. 두 벌로 두면 포맷·`안내.txt` 문구가 갈라지고,
  수십 년 뒤에 열리는 물건에서 그 차이는 확인할 사람이 없습니다.
- 사망 시 반출(§5.4-4)에서도 유족 화면에 **전체 + 건별**을 함께 노출합니다.

#### 5.4-4 사망 시 반출

**§3.3의 개봉(1회, 양쪽 동시)에 얹습니다** — 별도 절차를 만들지 않습니다.
`RELEASED` 이후 유족 화면에 **내려받기**를 상시 노출합니다. 🔴 **이때가 유일한 기회가 아니게**

### 5.6-1 🔴 듣기는 **반드시 서버를 경유**합니다 — presigned URL로는 안 됩니다

| | |
| :--- | :--- |
| 왜 | R2에 있는 것은 **이어봄 키로 잠근 바이트**입니다(`00-11` §5.4-4 선암호화). presigned URL을 주면 브라우저가 **암호문을 받아 재생에 실패**합니다 |
| 그래서 | 백엔드가 `downloadVoiceObject`(복호화 포함, **이미 구현돼 있고 부르는 곳이 없습니다**)로 받아 응답 본문으로 내보냅니다 |
| 대가 | 트래픽이 서버를 탑니다. 🔵 20MB 상한 · **본인이 자기 것을 듣는 경로뿐**이라 규모 문제가 아닙니다 |

🔴 **이 절을 맨 앞에 두는 이유** — presigned URL은 오브젝트 스토리지의 *교과서적 정답*이라, 선암호화 전제를 잊으면 **반드시 그쪽으로 갑니다.** 가서 재생이 안 되는 것을 확인하고 되돌아오게 됩니다.

### 5.6-2 ✅ 재생 경로는 둘로 갈립니다

| 언제 | 어떻게 | 서버 왕복 |
| :--- | :--- | :---: |
| 방금 녹음·업로드하고 **아직 저장 전** | 브라우저 메모리의 blob을 `URL.createObjectURL`로 바로 재생 | ❌ 없음 |
| **저장된 메시지를 다시 열 때** | `GET /api/farewell-messages/:id/audio` | ✅ 있음 |

🔵 위쪽은 이미 손에 blob이 있는데 R2를 다녀올 이유가 없습니다. **업로드 직후 듣기는 서버를 안 탑니다.**
🔴 `URL.revokeObjectURL`로 정리합니다 — 안 하면 최대 20MB blob이 탭 수명 내내 남습니다.

### 5.6-3 ✅ 엔드포인트 `GET /api/farewell-messages/:id/audio`

- 소유권은 **메시지 기준**으로 봅니다(기존 컨트롤러의 `verifyBearerToken` 패턴).
  🔴 **`mediaKey`를 파라미터로 받는 엔드포인트를 만들지 않습니다** — 키만 알면 남의 음성이 열립니다.
- **404 조건 3가지**: `R2_ENABLED=false` · 첨부 없음 · `mediaDeletedAt != null`
- 헤더: `Content-Type` = `mediaMime` · `Content-Disposition: inline` ·
  🔴 `Cache-Control: no-store` — 유언 성격의 음성이 디스크 캐시에 남지 않게 합니다.
- 🔴 **`<audio src="…">`에는 `Authorization` 헤더를 실을 수 없습니다.** `fetch`로 받아 **blob URL을
  만들어** `<audio>`에 물립니다. 🔴 **쿠키 인증·쿼리스트링 토큰으로 우회하지 않습니다** —
  이 프로젝트는 Bearer 하나로 통일돼 있고, 여기서만 예외를 만들면 인증 경로가 둘이 됩니다.

### 5.6-4 ✅ 삭제 = 소프트 삭제. 🔴 **`mediaKey`를 지우지 않습니다**

🔴 **`mediaKey`를 `null`로 만들면 안 됩니다.** 그 값이 R2 객체를 가리키는 **유일한 실마리**입니다.
지우는 순간 원본과 아카이브 사본이 **양쪽 다 영원히 못 지우는 고아**가 됩니다 — 파기 의무가 있는
데이터에서 가장 나쁜 결과이고, *"지웠으니 깨끗하다"* 는 착각까지 같이 남습니다.

| 시점 | DB | R2 |
| :--- | :--- | :--- |
| 이용자가 "녹음 삭제" | `mediaDeletedAt = now()` · 응답에서 음성 숨김 | 🔴 **아무 것도 하지 않음** |
| 유예 30일 경과 | `mediaKey` 정리 | **사람 승인 배치**가 원본+아카이브 삭제 |

🔄 **10-07** — 삭제 유예 중인 편지에 **새 음성을 붙이는 경우**는 §5.6-9-4(이전 키를 `FarewellMediaRetired`로 옮김).

§5.4-2-1과 같은 원칙입니다 — **런타임 요청 경로에서 `DeleteObject`를 호출하지 않습니다.**
🔵 유예는 탈퇴와 같은 **30일**입니다. 숫자를 새로 만들지 않습니다.
⏸ **복구(되돌리기) UI는 넣지 않습니다** — 탈퇴 철회와 한 화면으로 다룹니다. 대신 삭제 확인
문구에 유예를 밝힙니다: *"30일 뒤 완전히 삭제됩니다."* 🔴 *"즉시 삭제됩니다"* 라고 쓰면
§5.4-2의 판단이 뒤집힙니다 — **쓴 대로 동작해야 합니다.**

> 🔄 업로드 시점·화면 흐름(처음 §5.6-5 *"확인 모달의 저장 = STT → R2 → DB 한 흐름"* · §5.6-6)은 **2026-10-07 §5.6-9로 대체**됐고 원문은 **부록: 경위**.
> 그중 지금도 유효한 것: ⚠️ **R2 업로드는 됐는데 편지 기록이 실패하면 고아 1건이 남을 수 있습니다** — 수거 배치(§5.6-8 ③)는 ⏸ 아직 만들지 않았습니다(예외 상황에서만 생기고 비용은 0에 가까움).

### 5.6-7 🔴 편지 삭제도 **소프트 삭제**입니다 (2026-09-04 신설)

> 🔴 **제 스펙 누락입니다.** §5.6-4는 *"음성만 떼어내기"* 만 다뤘고 **편지 자체를 지우는 경로를
> 안 적었습니다.** 구현은 `prisma.farewellMessage.delete()` **하드 삭제**로 나갔고, Sonnet이
> 주석에 *"후속 필요"* 를 남기며 **이 절(§5.6-7)을 가리켰습니다** — 없는 절이었습니다.

**🔴 왜 하드 삭제가 안 되나** — `mediaKey`는 **행 안에만** 있습니다. 행을 지우면 R2 원본과
아카이브 사본을 가리키는 **유일한 실마리가 함께 사라집니다.** §5.6-4가 *"`mediaKey`를 `null`로
만들지 말라"* 고 한 것과 **같은 사고**이고, 행 삭제 쪽이 더 큽니다 — 본문까지 같이 없어져
**되돌릴 수단이 아예 없습니다.**

🔴 **이 도메인에서 즉시 삭제는 특히 위험합니다** — §5.4-2가 말한 *"수십 년치 유족 메시지를
가진 분이 실수로 눌렀을 때 되돌릴 방법이 없다"* 가 편지 단위에서 그대로 재발합니다.

| 시점 | DB | R2 |
| :--- | :--- | :--- |
| 이용자가 "편지 삭제" | `deletedAt = now()` · 목록·상세에서 제외 | 🔴 **아무 것도 하지 않음** |
| 유예 30일 경과 | **사람 승인 배치**가 행 파기 | 배치가 원본+아카이브 삭제 |

🔵 **유예는 30일** — 음성 삭제(§5.6-4)·탈퇴(§5.4-2)와 같은 숫자입니다.
🔴 확인 문구도 같습니다: *"30일 뒤 완전히 삭제됩니다."*
⏸ **이미 하드 삭제된 행이 있으면 되살리지 않습니다** — 검증 중 생긴 dev 데이터이고, 남은 R2
객체는 §5.6-8 ③(고아 수거)이 걷습니다. 🔴 **찾아서 지우려 들지 않습니다**(`00-11` §5.4-5-2-2).

### 5.6-8 ✅ 파기 배치 — **한 배치가 네 가지 만료를 봅니다** (2026-09-04 신설 · 🔄 2026-09-21 ④ 추가)

소프트 삭제만 있고 파기 경로가 없으면 화면에 *"30일 뒤 완전히 삭제됩니다"* 라고 써놓고
**안 지키는 상태**가 됩니다. §5.4-2가 경고한 바로 그 자리입니다 — **쓴 대로 동작해야 합니다.**

| | 대상 | 조치 |
| :---: | :--- | :--- |
| **①** | `mediaDeletedAt + 30일 < now` | 원장 기록 → R2 **원본** 삭제 → `mediaKey`·`mediaMime` 정리. 🔵 **행은 남깁니다**(편지 본문은 살아 있음). 아카이브는 2단계(§5.6-8-1) |
| **②** | `deletedAt + 30일 < now` | `mediaKey`가 있으면 ①을 먼저 하고, **그다음 행 파기** |
| **③** | ⏸ 고아 객체(§5.6-7 위 주석 · 부록 §5.6-5) — **미구현, 비차단** | R2 키 ↔ DB `mediaKey` 대조. **참조 없고 N일 지난 것**만. 🔴 대조 없는 삭제 금지 |
| **④** 🆕 | `User.deletionScheduledAt < now` | **회원 탈퇴 유예(30일) 만료** — `00-36` M-3. 🔴 그 회원의 유언장 사진(`06-06` §5-2-5)·①②를 **먼저** 돌린 뒤 계정을 파기합니다. 🔵 부고장은 ④가 함께 지우고, 추모관은 ④가 지우지 않습니다(탈퇴 요청 때 비공개 → 30일 뒤 추모관 파기 — `00-20` §6.3-2). 🔴 파기 방식은 **행 삭제가 아니라 익명화**입니다 → §5.6-8-4. 🔵 `Lead`·`ConsultRequest`는 `userId`가 `SetNull`이라 **연결만 끊기고 건은 남습니다**(정산 증거) |

🔴 **`db-safety.md` 전 과정이 걸립니다** — 사람 승인 → 백업 → **파일 생성 확인** → 실행.
🔴 **`--confirm` 없이는 dry-run**(무엇을 몇 건 지울지 출력만). `rotate-keys.ts`와 같은 방식입니다.
🔴 **원본과 아카이브를 함께** 지웁니다(`00-11` §5.4-5-2). 아카이브만 남기면 파기 의무 위반입니다.
🔴 **단, 한 프로세스가 둘 다 지우는 것이 아닙니다** — 아래 §5.6-8-1.
🔴 **런타임 코드가 이 배치를 부르지 않습니다** — 별도 실행 스크립트입니다(§5.4-2-1).
🔵 ③은 이번에 만들지 않아도 됩니다 — ①②가 먼저입니다.

### 5.6-8-1 🔴 아카이브는 **2단계**로 지웁니다 (2026-09-04 신설 — 편차 판정)

> **경위**: 구현 중 위 "함께 지웁니다"가 `00-11` §5.4-5-2-1과 충돌한다는 지적이 올라왔습니다
> (`walkthrough.md` 편차). **지적이 맞고 위 문장이 부실했습니다** — *무엇을* 만 쓰고 *어떻게* 를
> 안 썼습니다. 백엔드는 아카이브에 닿는 **수단이 없고, 그것이 ②층의 정의**입니다.

**🔴 백엔드에 아카이브 키를 주는 선택지는 없습니다.** 그 키가 생기는 순간 *"앱이 털려도 사본은
남는다"* 가 거짓이 되고, ②층을 만든 이유가 통째로 사라집니다. 파기 편의와 침해 방어를 맞바꾸지
않습니다.

| 단계 | 실행 주체 | 수단 | 대상 |
| :---: | :--- | :--- | :--- |
| **1** | **어드민 화면**(§5.6-8-3) · 스크립트는 개발·비상용 | 버킷별 S3 키(기존) | R2 **원본** |
| **2** | 🆕 **파기 운영자(사람)** | **본인 Cloudflare 로그인** — 대시보드 또는 `wrangler` | R2 **아카이브** |

✅ **사람 로그인 방식으로 확정**(2026-09-04). 🔴 **새 자격증명을 발급하지 않습니다.**

> 🔴 **09-04 정정 — 최초 서술에서 "Admin 자격"이라 적었으나 오해를 부르는 표현이었습니다.**
> R2 토큰 등급 이름의 `Admin Read & Write`는 *관리자* 가 아니라 **계정의 모든 버킷**을 뜻합니다
> (§5.4-5-2). 아카이브 하나 지우자고 그 토큰을 만들면 원본·미디어·서류까지 한 문자열에 걸립니다.
> **필요한 건 새 토큰이 아니라, 이미 있는 사람의 로그인**입니다.

🔴 **"아카이브 버킷 전용 토큰을 발급해 스크립트에 붙인다"는 선택지는 없습니다.** 얼핏 기존
버킷별 토큰 3개(§5.4-6-1)와 같은 패턴으로 보이지만 **놓을 자리가 없습니다** — 운영 파기는
Render에서 돌고(§5.6-8-2), 거기 넣는 순간 그게 곧 "백엔드가 아카이브 키를 가진 것"입니다.
경로만 한 칸 늘어난 채 ②층이 무너집니다. **2단계 분리는 편의가 아니라 구조의 귀결입니다.**

🔵 접근 주체 표 = `00-11` §5.4-5-2-1(`파기 운영자(사람)` 행). 파기 운영자는 상시 존재하지 않고 파기 때만 나타난다는 점, **저장되는 문자열이 없다**는 점이 백엔드와 다릅니다.

#### 5.6-8-1-1 🔴 그 사이 키를 잃어버리면 안 됩니다 — **원장은 DB 테이블입니다**

**stdout 출력은 조치가 아닙니다.** 1단계가 `mediaKey`를 비우고 목록을 콘솔에만 뿌리면,
터미널을 닫는 순간 **그 아카이브 객체를 가리키는 문자열이 세상에서 사라집니다.** DB에도 없고
화면에도 없습니다. 남는 길은 버킷 전수와 DB를 대조하는 것뿐인데 그게 ③이고 ⏸ 보류입니다.

> 🔴 **09-04 재판단 — 최초에 "파일로 append"라고 썼으나 운영에서 성립하지 않습니다.**
> 운영 1단계는 **Render에서 돌고**(§5.6-8-2), **Render 파일시스템은 재배포하면 사라집니다.**
> 이 프로젝트가 이미 같은 함정을 알고 있습니다 — 추모관 사진을 로컬디스크에 두어 오픈을
> 막아둔 그 건입니다(`systems.md` §5). **원장을 파일로 두면 D-9가 막으려던 사고가 그대로
> 납니다.** 파일 원장은 로컬 실행에서만 유효한 설계였습니다.

**✅ 원장은 DB 테이블로 둡니다** — `ArchivePurgeQueue`(§6.4).

- 🔴 1단계는 R2 원본 삭제 **전에** 이 테이블에 행을 만듭니다. 순서가 뒤집히면 위 사고가 납니다.
  🔵 **행을 만들고 실제 삭제에 실패하는 쪽이 안전합니다** — 그건 "지울 게 남았다"로 끝나지만,
  반대는 "지울 게 있는지조차 모른다"가 됩니다.
- 🔴 그다음 `mediaKey`·`mediaMime`을 비웁니다(①) / 행을 파기합니다(②).
- 2단계를 마치면 사람이 `purgedAt`을 채웁니다. **삭제하지 않고 남깁니다** — 파기 이력은
  개인정보 파기 의무의 증빙이고, 이 테이블에는 개인정보가 아니라 **오브젝트 키만** 있습니다.
- 🟡 **파기는 2단계까지 끝나야 완료입니다.** 1단계만 돌고 멈춘 상태는 *"지웠다"* 가 아니라
  **"절반 지웠다"** 입니다 — 화면 문구(*"30일 뒤 완전히 삭제됩니다"*)를 아직 안 지킨 상태입니다.
  🔵 `purgedAt IS NULL` 건수가 곧 **미이행 잔량**입니다. 세어볼 수 있어야 합니다.
- 🔵 **로컬 실행은 이 테이블에 쓰지 않습니다**(§5.6-8-2 — dev는 아카이브가 없음).

🔵 **2단계 자동화는 뒤로 미룹니다**(사람 판단, 09-04). 지금은 파기 대상이 소수라 손으로 처리
가능하고, 원장이 있으면 **미룬 것이 사라지지는 않습니다.** 건수가 늘면 그때 Worker에 삭제
엔드포인트를 두는 설계를 다시 봅니다(→ `backlog.md`).

🔵 스크립트는 **개발용·비상용**으로 남습니다 — 로직은 어드민과 같은 서비스 함수를 씁니다.

### 5.6-8-3 ✅ **누가 실행하나 — 어드민 화면** (2026-09-04 확정, 사람 판단)

### 5.6-8-4 🆕 ④의 계정 파기는 **행 삭제가 아니라 익명화**입니다 (2026-09-21 Opus 판정)

구현 중에 드러났습니다 — **④를 행 삭제로 만들 수 없습니다.** `Memorial.createdByUserId`와
`MemorialPhoto.uploadedByUserId`가 **`onDelete` 없는 필수 FK**라, 추모관을 남기라는 ④의 지시와
회원 행을 지우라는 지시가 **서로를 막습니다.**

#### 🔴 FK를 `SetNull`로 바꾸지 않습니다

바꾸면 **개설자가 영구히 사라집니다.** 그러면 `00-20`이 정한 추모관 **동결·연장·폐쇄 요청·신고
처리**를 할 주체가 없어집니다. 고인 정보와 조문객의 방명록은 그대로 남는데 **관리할 사람만
없는 추모관**이 됩니다 — 보존정책을 지키라고 남긴 것이 지킬 수 없는 것이 됩니다.

🔵 **억지로 끊을 이유도 없습니다.** 추모관에는 이미 자기 수명이 있습니다(`purgeAt` — 13개월
동결 + 3년, §8.1). 그때 행이 지워지면서 FK도 **저절로 풀립니다.**

#### ✅ 대신 `User` 행을 익명화해 남깁니다 (tombstone)

🔴 개인정보보호법이 요구하는 것은 **"복원 불가능한 파기"**이지 **행 삭제가 아닙니다.**
식별정보를 지우면 파기가 성립합니다. 남는 것은 **고인·조문객의 기록을 지탱하는 빈 껍데기**입니다.

| | 무엇 |
| :--- | :--- |
| 🔴 **비웁니다** | `email` · `profileImage` · `refreshToken` · `contactPhone` · `addressZonecode` · `addressRoad` · `addressDetail` · `contactTimePref` · `marketingAgreedAt` → 전부 `null` |
| 🔴 **바꿉니다** | `name` → `'탈퇴한 회원'` (필수 필드라 `null`을 넣을 수 없습니다) |
| 🔴 **지웁니다(행)** | `SocialAccount` **전량** — 로그인 경로를 끊습니다. 남기면 같은 소셜 계정으로 **되살아납니다** |
| 🔵 **남깁니다** | `id`(FK 지탱) · `createdAt` · 🆕 `purgedAt` · 🆕 **`termsAgreedAt`·`privacyAgreedAt`**(동의 입증) · 🆕 **`deletionRequestedAt`·`deletionScheduledAt`**(30일 유예를 지켰다는 증빙) · `role` |
| 🔴 **비웁니다(추가)** | `phoneVerifiedAt` · `profileUpdatedAt` — 개인정보에 딸린 상태값입니다 |

- 🆕 **`purgedAt DateTime?` 한 개를 추가합니다**(`User` — 등재처는 `00-36` M-3, `deletionRequestedAt`·
  `deletionScheduledAt`과 같은 자리입니다). 값이 있으면 파기된 껍데기입니다.
- 🔴 **`purgedAt: null` 가드를 조회 경로 전수에 넣습니다.** 이게 빠지면 **유령 계정이 조회됩니다** —
  `verifyBearerToken` 뒤에 `User`를 읽는 모든 컨트롤러가 대상입니다.
- 🔴 스키마 변경이므로 **`db-safety.md` 전 과정**이 선행합니다(승인 → 백업 → **파일 생성 확인** → `migrate`).

##### 🔴 `purgedAt`이 유예 판정보다 **우선합니다**

`deletionRequestedAt`을 남기므로, 파기가 끝난 껍데기도 §4.3-1의 *"유예 중"* 조건
(`deletionRequestedAt != null`)에 **계속 걸립니다.** 두 상태가 겹칩니다 — 순서를 정합니다.

1. `purgedAt != null` → **파기 완료.** 로그인·조회 전부 차단(복구 안내도 띄우지 않습니다. 되살릴 것이 없습니다)
2. `purgedAt == null && deletionRequestedAt != null` → **유예 중**(§4.3-1)
3. 둘 다 `null` → 정상 회원

🔵 남기는 두 시각은 *"30일 유예를 지키고 파기했다"* 는 **이행 증빙**입니다 — 되살리기 위한 값이 아닙니다.

##### 🔴 `SetNull` 관계는 **배치가 직접 끊습니다**

`Lead.userId`·`ConsultRequest.userId`·`MemorialTribute.userId`는 `onDelete: SetNull`이고 스키마
주석도 *"(탈퇴 시 null)"* 이라고 적고 있습니다. 🔴 **그런데 행을 지우지 않으면 `SetNull`이
발동하지 않습니다** — 연결이 tombstone에 그대로 남아, `Lead.applicantPhone`(평문 연락처) 같은
신청 스냅샷과 회원 `id`가 **계속 묶여 있습니다.** 익명화의 뜻이 반감됩니다.

✅ **배치가 파기 시 이 세 컬럼을 명시적으로 `null`로 만듭니다.** 그래야 `00-36` M-3의 고지
*"연결만 끊기고 건은 남습니다"* 가 **사실이 됩니다.** 🔵 건 자체는 정산 증거로 남습니다.

##### ✅ 내가 **수락한** 가족 지정 — 파기 때 §9.2 철회와 같은 처리 (2026-09-21 추인)

`FamilyDesignation.acceptedUserId`는 **FK가 아니라** `SetNull`도 걸리지 않습니다. 그냥 두면
지정자 화면에 **유령 가족**이 남고, 더 나쁘게는 **익명화된 계정에 남의 엔딩노트 열람 권한
(`EndingNoteGrant`)이 살아 있습니다.**

✅ **`00-27` §9.2와 똑같이 처리합니다** — `status = DECLINED` · `declinedAt` 스탬프 ·
`acceptedUserId = null` · 그 `designationId`의 `EndingNoteGrant` 전부 `revokedAt`.
🔵 **탈퇴는 가장 강한 형태의 동의 철회**이므로 별도 경로를 만들 이유가 없습니다.

🔴 **지정자에게 "탈퇴하셨습니다"를 알리지 않습니다.** §9.2 3의 표시 조합
(`acceptedAt != null && status == DECLINED`)에 그대로 섞이는 것이 **맞습니다** —
탈퇴 사실은 **탈퇴자의 개인정보**이고, 지정자가 할 행동은 어느 쪽이든 *"다시 지정한다"* 로 같습니다.
🟡 그래서 그 표기 문구는 *"거두셨습니다"* 처럼 **상대의 행위를 단정하지 않는 말**로 둡니다
(→ `00-36` §4.6-2-1 마지막 줄, 후순위).

##### ⏸ ⑤ tombstone 수거 — 아직 만들지 않습니다

tombstone을 **영원히** 두면 보존기간 없는 보관이 됩니다. 언젠가 걷어야 합니다.
조건은 **`purgedAt + N년 < now`이고, 그 회원을 참조하는 필수 FK(`Memorial`·`MemorialPhoto`)가
0건**일 때입니다 — 추모관이 `purgeAt`(13개월 동결 + 3년)로 사라지면 저절로 충족됩니다.
🟡 **N은 `00-19`(개인정보처리방침)의 보존기간과 같아야 하므로 여기서 정하지 않습니다.**
🔵 ③(고아 객체)과 같이 **비차단·후순위**입니다. 할 일은 `.harness/memory/backlog.md`에 등재돼 있습니다.

| :--- | :--- |

| 저장 전 음성이 있는 채로 페이지를 떠남·새로고침 | 🔴 브라우저 **떠나기 경고**. 떠나면 글·음성 모두 사라짐(R2·DB에 없음) |
| 저장 전 음성이 있는 채로 편지 작성 창을 닫음(취소·X·바깥 클릭) | 🔄 **10-07 개발자** — 확인창 *"저장하지 않은 음성과 글이 있습니다. 닫으면 사라집니다."* `계속 작성`·`닫기`. 저장 전 음성이 없으면 묻지 않음 |
| 저장 ① 성공 · ② 실패 | 받은 `mediaKey`를 **메모리에 보관** — 다시 `저장`하면 ①을 건너뛰고 ②만. 🔴 이 상태로 떠나면 고아 1건(§5.6-5 ⚠️ 그대로, 수거 ③ ⏸) |
| "저장 전 음성"의 `삭제` | 메모리에서 버림. 입력창 글은 남김(사용자가 지움) |
| 업로드·녹음 동의 체크 | 🔵 **변환이 끝나도 풀지 않습니다**(10-07 개발자) — 같은 편집 중에는 유지, 편집기를 닫으면 초기화. ✅ 구현(`FarewellMessageCard.tsx`) |

#### 5.6-9-3 🔴 편지 한 통에 음성은 하나 — 붙어 있으면 새 음성을 막습니다

- **화면**: 저장된 음성(`hasAudio`) 또는 저장 전 음성이 있으면 업로드·녹음 버튼을 막고 안내합니다.
  🔄 **10-07 개발자 — 안내 문구를 두 경우로 나눕니다**(한 문구면 "저장만 하면 되는" 때에 오류처럼 읽힘):

  | 막힌 이유 | 문구 |
  | :--- | :--- |
  | 저장 전 음성 | *"변환이 끝났습니다. 아래 '저장'을 누르면 글과 음성이 저장됩니다. 다른 음성으로 바꾸려면 위의 '삭제'를 누르세요."* |
  | 저장된 음성 | *"이미 저장된 음성이 있습니다. 위의 '음성 삭제'를 누르면 다시 올리거나 녹음할 수 있습니다."* (업로드 탭에도 맞게 — 〔이전: "음성을 삭제한 뒤 다시 녹음해 주세요."〕) |
- **서버**: 편지에 `mediaKey`가 있고 `mediaDeletedAt`이 `null`이면 새 `mediaKey`를 **409로 거절**합니다 — ✅ 구현(`farewellMessageController.ts` 편지 수정).
  덮어쓰면 이전 키가 사라져 **영구 고아**가 됩니다(구현 전 결함 — D-12 #66으로 해소).

#### 5.6-9-4 🔴 음성을 지운 편지에 새 음성 — 이전 키를 **파기 대기로 옮깁니다** (10-07 개발자 결정 "나")

편지에 `mediaKey`가 있고 `mediaDeletedAt`이 있으면(삭제 유예 중) 새 음성을 받습니다. **한 트랜잭션에서**:

1. 이전 `mediaKey`·`mediaMime`·`mediaDeletedAt`을 `FarewellMediaRetired`(§6.6)에 한 행으로 옮깁니다.
2. 편지에 새 `mediaKey`·`mediaMime`·`mediaDurationSec`를 적고 `mediaDeletedAt = null`로 되돌립니다.

🔴 1이 실패하면 2를 하지 않습니다 — 이전 키를 잃는 순간 원본·아카이브가 영구 고아가 됩니다(§5.6-4).
🔵 파기 시계는 **원래 삭제 시각**을 이어받습니다(새로 30일을 주지 않음).
🔵 파기 배치 ①이 이 표도 봅니다: `deletedAt + 30일 < now` → 원장(`ArchivePurgeQueue`) → R2 원본 삭제 →
`purgedAt` 기록. 🔵 행은 지우지 않습니다(이력). 편지 행과 **FK로 묶지 않습니다** — 편지가 ②로 파기돼도 남아야 합니다.
🔵 탈퇴(④)와의 순서: 탈퇴 유예 중에는 새 자료 생성이 막혀 있으므로(`00-36` §4.3-1) 이 표의 행은 항상 ④보다
먼저 만료됩니다.

`FamilyDesignation`이 없으면 **수신자 카드가 하나도 없습니다.** 빈 화면이 아니라
**가족 지정으로 유도하는 화면**이어야 합니다(`MyPageFamilyDesignation` 재사용 —
`06-04` Phase 2 #6과 같은 진입점).

> 🔴 `06-04` §8.2의 경고를 그대로 적습니다 — ***"수신자가 없으면 사후에 전달되지 않습니다."***

### 7.4 ✅ 메인 진입 — **슬라이드 2개로 분리 확정**(2026-08-26 사장님)
