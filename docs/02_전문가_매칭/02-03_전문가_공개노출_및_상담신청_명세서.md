## 📌 1. 현황 진단 — 무엇이 비어 있나

`02-02`로 **전문가 B2B 계정 체계는 완성**됐지만, **소비자(B2C) 쪽이 통째로 목업**입니다.

| 영역 | 상태 |

## 🎯 2. 이번 범위와 제외 (Stage 1 = 무과금 루프)

Domain01에서 **리드 인프라를 먼저 깔고 정산은 나중에** 한 것과 같은 순서를 따릅니다(→ `01-05`).

### 2.1 이번 범위 (Stage 1)
1. 승인된 전문가 **공개 목록/상세 API** + `CounselingPage` 실연동
2. **상담 신청(`ConsultRequest`)** 접수 — 개인정보 제3자 제공 동의 포함
3. 전문가 대시보드에서 **받은 상담 신청 목록** 조회 및 상태 변경
4. 신청번호 발번(`EC-YYMMDD-NNNN`)

### 2.2 이번 범위 제외 — 이유가 있는 미착수
| 제외 항목 | 이유 |
| :--- | :--- |
| Tier 2 유료 상담 결제 | **PG(결제대행) 연동 필요 = 돈이 드는 외부 연동** → `roles.md` §4 대표 승인 대상 |
| Tier 3 월정액 광고 과금 | 동일. 다만 초기엔 §6.3 수동 처리 권장 |
| Tier 4 대행 수수료 정산 | Tier 2가 서야 의미가 생김 |
| Tier 1 AI 상속세 계산기·Q&A 게시판 | 별도 콘텐츠 도메인 — 이번 루프와 독립 |
| 자격증 자동 진위확인 | §6.1 참고 — **연동하지 않는 것을 권장** |

**Stage 1은 결제가 전혀 없으므로 대표 승인 없이 착수 가능합니다.**

## ⚖️ 3. 변호사법 가드레일 (설계의 제1 제약)

`02-01` §4가 "변호사는 Tier 3 고정 월정액만"으로 확정했습니다. 이번 설계에서 그 원칙을
**코드 구조로** 지키는 방법을 정의합니다.

### 3.1 판단 근거
변호사법 제34조는 **"금품·향응 등 이익을 받거나 약속하고" 당사자를 특정 변호사에게 소개·알선**하는 것을 금지합니다.
따라서 **대가 없는 연결 자체는 금지 대상이 아닙니다.** 위험한 것은 *연결의 대가를 받는 구조*입니다.

### 3.2 그래서 이렇게 만든다
1. **`ConsultRequest`에 과금 필드를 두지 않는다.** `billable`·`billedAmount`·`commissionPolicyId` 같은 컬럼을
   아예 만들지 않습니다. `02-02` §2가 `Lead` 재사용을 거부한 것과 같은 논리 — **없는 필드는 실수로 채워질 수 없습니다.**
2. **과금은 별도 테이블로 분리한다**(Stage 2). 상담 신청 기록과 과금 근거를 물리적으로 떼어 놓고,
   과금 테이블은 `LAWYER` 카테고리를 애플리케이션·DB 양쪽에서 배제합니다.
3. **월정액은 상담 건수와 완전히 무관해야 한다.** 노출 순서·건수 상한 등 어떤 것도 상담 실적과 연동하지 않습니다.
   연동하는 순간 "고정 광고료"라는 성격이 무너지고 실질이 알선 대가로 평가될 여지가 생깁니다.
4. **변호사 프로필에 성과·성공보수 표현 금지** — 변호사법 광고 규제. 노출 문구 검수는 `02-02` §2-3 참고.

> ⚠️ 이 문서는 법률 자문이 아닙니다. 실제 과금 개시 전 변호사 검토를 받으십시오(`02-02` 사장님 보고 항목).

## 🗄️ 4. 데이터 모델

### 4.1 `ConsultRequest` (신규) — 상담 신청
`Lead`(장사시설)와 **의도적으로 분리**합니다. 대상 주체가 다르고(`Expert` vs `Partner`),
과금 가능 여부가 직역별로 갈리기 때문입니다.

| 컬럼 | 타입 | 설명 |
| :--- | :--- | :--- |
| `id` | String @id | UUID |
| `requestNo` | String @unique | `EC-YYMMDD-NNNN` — 표시·대조용 불변 번호 (`Lead`의 `EB-` 와 접두어로 구분) |
| `expertId` | String | 신청 대상 전문가 (FK → Expert) |
| `categorySnapshot` | String | 신청 시점의 전문가 직역 — 전문가가 나중에 카테고리를 바꿔도 당시 기준 보존 |
| `userId` | String? | 로그인 유저면 참조 (탈퇴 시 null) |
| `applicantName` | String? | 신청자 이름 스냅샷 |
| `applicantPhone` | String? | 신청자 연락처 스냅샷 (`utils/phone.ts` 정규화) |
| `maskedAt` | DateTime? | 마스킹 처리 시각 |
| `channel` | String | `ALIMTALK` \| `PHONE` \| `VIDEO` \| `VISIT` — 희망 상담 방식 |
| `preferredAt` | DateTime? | 희망 일시 (선택) |
| `content` | String | 상담 희망 내용 |
| `thirdPartyConsentAt` | DateTime? | 개인정보 제3자 제공 동의 시각 — **없으면 접수 거부** |
| `consentSnapshot` | Json? | 동의 시점 고지 문구 버전 (분쟁 대비) |
| `status` | String | `REQUESTED` \| `ACCEPTED` \| `COMPLETED` \| `CANCELLED` \| `INVALID` |
| `statusHistory` | Json | `[{status, at, by, note}]` |
| `createdAt` / `updatedAt` | DateTime | |

**인덱스**: `[expertId, status]`, `[createdAt]`
**과금 관련 컬럼은 없습니다** — §3.2-1.

### 4.2 `ConsultNumberCounter` (신규)
`LeadNumberCounter`와 동일한 일자별 원자적 카운터. **테이블을 공유하지 않습니다** —
`EB-`(리드)와 `EC-`(상담)의 일련번호가 서로를 건너뛰면 대조가 어려워집니다.

### 4.3 `Expert` 변경
- `consultRequests ConsultRequest[]` 관계 추가
- `isPublished Boolean @default(false)` 추가 — 승인(`status=APPROVED`)과 **공개 노출**을 분리.
  승인은 됐지만 프로필이 미비해 아직 노출하고 싶지 않은 경우가 실제로 생깁니다
  (`Facility.isPartner`가 `partnerId`의 파생 캐시인 것과 달리, 이건 운영자가 직접 켜는 독립 플래그).
- **`officeAddress String?` 추가** (2026-08-11, 대표 지시) — 사무실 주소. 선택 입력.

> **`officeAddress`를 직역별로 나누지 않은 이유**: 요청은 "변호사 사무실 주소"였으나 세무사·행정사·장례지도사도 동일하게 사무실을 갖습니다. `category`로 분기하면 스키마·API·화면 세 곳에 조건문이 생기는데, 그 분기가 만들어내는 차이가 없습니다. **4대 직역 공용 단일 필드**로 둡니다.
>
> 이 필드는 §5.1 공개 API의 제외 목록에 **넣지 않습니다** — 사무실 주소는 의뢰인이 방문하기 위해 알아야 하는 정보이고, 실제로 각 협회 공개 명부에도 등재되는 항목입니다. `contactPhone`(개인 연락처)과 성격이 다릅니다.

### 4.4 재사용하는 것
`utils/phone.ts`(연락처 정규화), `utils/crypto.ts`(정산계좌 암호화), 동의 스냅샷 패턴 — 전부 `01-05`에서 검증된 것.

## 🔌 5. API 명세

### 5.1 공개 (인증 불필요)
| 메서드 | 경로 | 설명 |
| :--- | :--- | :--- |
| GET | `/api/experts` | 공개 전문가 목록. **`status=APPROVED` AND `isPublished=true`만** 반환 |
| GET | `/api/experts/:id` | 전문가 상세 |

### 5.2 상담 신청 (로그인 불필요 — 비회원도 가능)
| 메서드 | 경로 | 설명 |
| :--- | :--- | :--- |
| POST | `/api/experts/:id/consult-requests` | 상담 신청. `thirdPartyConsent` 없으면 **400** |

- 대상 전문가가 미승인/미공개면 **404**(존재 자체를 숨김).
- 로그인 상태면 `userId` 연결, 아니면 이름·연락처만으로 접수.
- 응답에 `requestNo`를 돌려주어 사용자가 접수번호를 확인할 수 있게 합니다(`01-05`의 `leadNo` UX와 동일).

### 5.3 전문가 본인 (JWT `aud=expert`)
| 메서드 | 경로 | 설명 |
| :--- | :--- | :--- |
| GET | `/api/expert/consult-requests` | 내게 온 신청 목록 (`status` 필터) |
| PATCH | `/api/expert/consult-requests/:id/status` | 상태 변경 (`ACCEPTED`/`COMPLETED`/`CANCELLED`) |

**소유권 검증 필수** — 남의 신청을 조회·변경하면 403. (`01-05` 클레임 API에서 검증된 패턴)

### 5.4 운영자 (JWT `aud=admin`)
| 메서드 | 경로 | 설명 |
| :--- | :--- | :--- |
| GET | `/api/admin/experts?status=` | 전문가 조회 (상태 필터, 빈 값이면 전체) |
| PATCH | `/api/admin/experts/:id/status` | 승인/반려/정지 (+사유) |
| PATCH | `/api/admin/experts/:id/publish` | `isPublished` 토글. **미승인 전문가는 400** |
| PATCH | `/api/admin/experts/:id` | 연락처·사무실 주소·소개 수정 (2026-08-11 추가) |
| GET | `/api/admin/consult-requests` | 전체 신청 조회 (분쟁 대응·품질 모니터링) |

**운영자 수정 범위는 `01-05` §6.2 원칙을 그대로 따릅니다** — 연락처·사무실 주소·소개(운영 편의 정보)는 직접 수정 허용, **자격증 등록번호·등록기관·성명·직역(검증된 신원 정보)은 수정 금지**입니다. 자격증 번호가 틀렸다면 고쳐주는 것이 아니라 반려하고 재신청을 받습니다. 여기서 임의 수정을 허용하면 §6.1이 "3중 수동 방어로 충분하다"고 판단한 근거가 무너집니다 — 운영자가 승인 당시 무엇을 보고 승인했는지 증명할 수 없게 되기 때문입니다.

## 📱 6. 결정 사항 — `02-02`가 남긴 3가지 질문에 대한 답

### 6.1 자격증 자동 진위확인 → **연동하지 않는 것을 권장**
대한변협·국세청·행정사회는 **제3자가 자격을 조회할 수 있는 공개 API를 제공하지 않습니다.**
연동하려면 기관 제휴가 필요하고 비용·기간이 큽니다. 대신 **3중 수동 방어**로 충분합니다:
1. 등록번호 **형식 검증**(직역별 자릿수·패턴) — 오타·장난 입력 차단
2. `licenseDocUrl` 사본 **필수화** (현재 선택 → 필수로 변경 권장)
3. 운영자 **수동 승인** (이미 구현됨, 자동승인 없음)

전문가 수가 수백 명을 넘어 수동 심사가 병목이 될 때 재검토하면 됩니다. **지금은 비용 0으로 충분합니다.**

### 6.2 변호사 Tier 3 결제 수단 → **초기엔 계좌이체 + 수동 확인**
PG 연동은 심사·수수료·개발이 모두 듭니다. 입점 전문가가 두 자릿수일 때는
**세금계산서 발행 + 계좌이체**가 더 싸고 빠릅니다. 전문가 대상 B2B 월정액은 소비자 결제와 달리
수동 처리에 대한 저항이 낮습니다. 자동화는 규모가 생긴 뒤에 하십시오. → 대표 승인 대상(`pending-approvals`).

### 6.3 나머지 3직역 리드 수수료를 `Lead`처럼 만들지 → **아니오, §4.1대로 분리**
`ConsultRequest`(과금 필드 없음) + 별도 과금 테이블(Stage 2, `LAWYER` 배제) 구조를 권장합니다.
`Lead`를 재사용하면 변호사만 예외 처리해야 해서 `02-02` §2가 지적한 스키마 오염이 그대로 재현됩니다.
