## ⚖️ 3. 변호사법 가드레일 (설계의 제1 제약)

`02-01` §4가 "변호사는 Tier 3 고정 월정액만"으로 확정했습니다. 이번 설계에서 그 원칙을
**코드 구조로** 지키는 방법을 정의합니다.

### 3.1 판단 근거
변호사법 제34조는 **"금품·향응 등 이익을 받거나 약속하고" 당사자를 특정 변호사에게 소개·알선**하는 것을 금지합니다.
따라서 **대가 없는 연결 자체는 금지 대상이 아닙니다.** 위험한 것은 *연결의 대가를 받는 구조*입니다.

### 3.2 그래서 이렇게 만든다
1. **`ConsultRequest`에 과금 필드를 두지 않는다.** `billable`·`billedAmount`·`commissionPolicyId` 같은 컬럼을
   아예 만들지 않습니다. `02-02` §2가 `Lead` 재사용을 거부한 것과 같은 논리 — **없는 필드는 실수로 채워질 수 없습니다.**
2. **과금은 별도 테이블로 분리한다**(Stage 2). 상담 신청 기록과 과금 근거를 물리적으로 떼어 놓고,
   과금 테이블은 `LAWYER`·`JUDICIAL_SCRIVENER`(법무사) 카테고리를 애플리케이션·DB 양쪽에서 배제합니다.
   법무사는 법무사법 확인 전까지 변호사와 동일 취급입니다(`02-05` §3.2).
3. **월정액은 상담 건수와 완전히 무관해야 한다.** 노출 순서·건수 상한 등 어떤 것도 상담 실적과 연동하지 않습니다.
   연동하는 순간 "고정 광고료"라는 성격이 무너지고 실질이 알선 대가로 평가될 여지가 생깁니다.
4. **변호사 프로필에 성과·성공보수 표현 금지** — 변호사법 광고 규제. 노출 문구 검수는 `02-02` §2-3 참고.

> ⚠️ 이 문서는 법률 자문이 아닙니다. 실제 과금 개시 전 변호사 검토를 받으십시오(`02-02` 사장님 보고 항목).

## 🗄️ 4. 데이터 모델

### 4.1 `ConsultRequest` (신규) — 상담 신청
`Lead`(장사시설)와 **의도적으로 분리**합니다. 대상 주체가 다르고(`Expert` vs `Partner`),
과금 가능 여부가 직역별로 갈리기 때문입니다.

| 컬럼 | 타입 | 설명 |
| :--- | :--- | :--- |
| `id` | String @id | UUID |

| `categorySnapshot` | String | 신청 시점의 전문가 직역 — 전문가가 나중에 카테고리를 바꿔도 당시 기준 보존 |

**인덱스**: `[expertId, status]`, `[createdAt]`

### 4.2 `ConsultNumberCounter` (신규)
`LeadNumberCounter`와 동일한 일자별 원자적 카운터. **테이블을 공유하지 않습니다** —
`EB-`(리드)와 `EC-`(상담)의 일련번호가 서로를 건너뛰면 대조가 어려워집니다.

### 4.3 `Expert` 변경
- `consultRequests ConsultRequest[]` 관계 추가
- `isPublished Boolean @default(false)` 추가 — 승인(`status=APPROVED`)과 **공개 노출**을 분리.
  승인은 됐지만 프로필이 미비해 아직 노출하고 싶지 않은 경우가 실제로 생깁니다
  (`Facility.isPartner`가 `partnerId`의 파생 캐시인 것과 달리, 이건 운영자가 직접 켜는 독립 플래그).
- **`officeAddress String?` 추가** (2026-08-11, 개발자 지시) — 사무실 주소. 선택 입력.

> **`officeAddress`를 직역별로 나누지 않은 이유**: 요청은 "변호사 사무실 주소"였으나 세무사·행정사·장례지도사도 동일하게 사무실을 갖습니다. `category`로 분기하면 스키마·API·화면 세 곳에 조건문이 생기는데, 그 분기가 만들어내는 차이가 없습니다. **5개 직역 공용 단일 필드**로 둡니다.
>
> 이 필드는 §5.1 공개 API의 제외 목록에 **넣지 않습니다** — 사무실 주소는 의뢰인이 방문하기 위해 알아야 하는 정보이고, 실제로 각 협회 공개 명부에도 등재되는 항목입니다. `contactPhone`(개인 연락처)과 성격이 다릅니다.

### 4.4 재사용하는 것
`utils/phone.ts`(연락처 정규화), `utils/crypto.ts`(정산계좌 암호화), 동의 스냅샷 패턴 — 전부 `01-05`에서 검증된 것.

### 5.2 상담 신청 (🔄 로그인 필수 — 2026-09-29 사람 확정)
| 메서드 | 경로 | 설명 |
| :--- | :--- | :--- |
| POST | `/api/experts/:id/consult-requests` | 상담 신청. **로그인(소비자 JWT) 없으면 401** · `thirdPartyConsent` 없으면 **400** |

## 📱 6. 결정 사항 — `02-02`가 남긴 3가지 질문에 대한 답

### 6.1 자격증 자동 진위확인 → **연동하지 않는 것을 권장**
대한변협·국세청·행정사회는 **제3자가 자격을 조회할 수 있는 공개 API를 제공하지 않습니다.**
연동하려면 기관 제휴가 필요하고 비용·기간이 큽니다. 대신 **3중 수동 방어**로 충분합니다:
1. 등록번호 **형식 검증**(직역별 자릿수·패턴) — 오타·장난 입력 차단
2. `licenseDocUrl` 사본 **필수화** (현재 선택 → 필수로 변경 권장)
3. 운영자 **수동 승인** (이미 구현됨, 자동승인 없음)

전문가 수가 수백 명을 넘어 수동 심사가 병목이 될 때 재검토하면 됩니다. **지금은 비용 0으로 충분합니다.**

### 6.2 변호사 Tier 3 결제 수단 → **초기엔 계좌이체 + 수동 확인**
PG 연동은 심사·수수료·개발이 모두 듭니다. 입점 전문가가 두 자릿수일 때는
**세금계산서 발행 + 계좌이체**가 더 싸고 빠릅니다. 전문가 대상 B2B 월정액은 소비자 결제와 달리
