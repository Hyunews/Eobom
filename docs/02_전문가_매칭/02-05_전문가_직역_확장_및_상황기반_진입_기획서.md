> **문서 성격**: 기획서 · 일부 사장님 확정 대기. `[Claude:Opus]` 작성(2026-08-13).

> ① *"메인의 법무사 → 매칭되는 전문가 없는 것이라는 소린데, 그렇다면 추가해줘."*
> ② *"고인의 사망 시 관련 서비스 진행을 위해 변호사, 법무사, 세무사, 행정사, 장례지도사 <<

> **관계**: `02-01`(직역·수익 마스터)·`02-03`(확정 스펙)·`02-04`(생전 축)의 후속.

## 📌 1. 두 질문은 사실 하나입니다

①은 *"법무사를 넣을까"* 이고 ②는 *"직역으로 나누는 게 맞나"* 인데, **②의 답이 ①의 형태를 정합니다.**
결론부터 적습니다.

> **✅ 법무사는 추가합니다. 다만 "직역 탭"을 하나 더 만드는 방식이 아닙니다.**
> **유족에게는 직역이 아니라 "상황"으로 물어야 합니다.**

---

## 🙋 2. ✅ ②의 답 — 유족은 자기가 누구를 만나야 하는지 모릅니다

### 2.1 지금 화면은 공급자 중심입니다

`CounselingPage.tsx`의 `CATEGORY_TABS`는 **직역 4개로 필터링**합니다.

```
[전체] [상속 변호사] [상속세 세무사] [디지털 유품 행정사] [장례 지도사]
```

**이건 "우리가 가진 것"의 분류이지 "유족이 가진 문제"의 분류가 아닙니다.**

사별 직후 유족의 머릿속에 있는 것은 이렇습니다.

| 유족이 실제로 하는 생각 | 답이 되는 직역 |
| :--- | :--- |
| *"빚이 있는 것 같은데 어떡하지"* | 변호사 · **법무사** |
| *"집 명의를 바꿔야 한다는데"* | **법무사** |
| *"세금이 얼마나 나오지"* | 세무사 |
| *"형제끼리 얘기가 안 된다"* | 변호사 |
| *"서류가 너무 복잡하다"* | 행정사 |
| *"장례를 어떻게 치러야 하나"* | 장례지도사 |

**어느 것도 "나는 법무사가 필요하다"로 시작하지 않습니다.** `07-01` §3.2가 정리한 대로 이 시점의
유족은 **결정 피로 상태**이고, 직역 이름을 놓고 고르라는 것은 **판단을 유족에게 떠넘기는 것**입니다.

### 2.2 ✅ 상황 선택 모달 — 상황을 먼저 묻고, 직역은 결과로 보여줍니다 (2026-09-29 사람 확정)

> **시안(정본)**: [캔버스 — 전문가 상담 상황 선택 모달](https://claude.ai/artifact/JNySuy2B3iuPn4fxypkEpH) —
> 데스크톱 2판(모달·고른 뒤) + 모바일 2판(바텀시트·고른 뒤). 배치·색·글자는 `00-39` §3·§4·§6 값.

**① 여는 때**
- `CounselingPage`에 **처음 들어왔을 때 한 번 자동으로** 연다. "봤음"은 브라우저에 남긴다(`localStorage`, 계정 기준 아님).
- 그 뒤로는 제목 아래 **[어떤 도움이 필요하세요?]** 버튼으로 다시 연다. 🔄 상속세 계산기 배너는 이 버튼 옆 **[상속세 계산하기]** 버튼으로 바꾼다(시안).

**② 모달 내용** — 제목 *"어떤 도움이 필요하세요?"* + 아래 6줄. 각 줄 = 상황(굵게) + 직역 이름(회색).

| # | 상황 (화면 문구 그대로) | 보여줄 직역(`category`) | 기한 표시 |
| :---: | :--- | :--- | :--- |
| 1 | 고인에게 빚이 있을 수 있습니다 | `LAWYER` · `JUDICIAL_SCRIVENER` | 🔴 붉은 글자 `기한 3개월` |
| 2 | 부동산·자동차 명의를 바꿔야 합니다 | `JUDICIAL_SCRIVENER` | — |
| 3 | 상속세·취득세를 알아봐야 합니다 | `TAX_ACCOUNTANT` | — |
| 4 | 가족 간에 의견이 다릅니다 | `LAWYER` | — |
| 5 | 행정 서류·신고가 남아 있습니다 | `ADMINISTRATIVE_SCRIVENER` | — |
| 6 | 장례 절차를 상담하고 싶습니다 | `FUNERAL_DIRECTOR` | — |

- 닫기: 데스크톱은 오른쪽 위 × + 아래 **[닫기]**, 모바일은 **바텀시트 + 아래 [닫기]**(`00-39` 규칙 12). 닫으면 지금 탭 화면 그대로.
- 🔴 이 표는 **데이터 한 곳**(배열 상수)에 둔다 — JSX에 줄마다 박지 않는다(`01-05` §12). 파일 위치는 구현이 정한다.
- 🔴 문구는 위 표 그대로. 평가·권유 말(*"꼭"*, *"가장"*)을 더하지 않는다(`00-39` 규칙 6-2).

**③ 고른 뒤**
- 모달이 닫히고, 목록 위에 **고른 상황 한 줄** + **[다시 고르기]**(= 모달 다시 열기). 1번만 그 위에 붉은 12px 한 줄
  *"사망을 안 날부터 3개월 안에 상속포기·한정승인 신청"*(민법 §1019 ①)을 단다.
- 분야 탭은 **표의 직역이 전부 켜진 상태**(1번이면 `상속 변호사`·`상속 법무사` 둘 다). 목록 = 그 직역들 합집합.
- 탭을 직접 누르면 상황 줄이 사라지고 **지금처럼 탭 하나만** 켜진다(`전체` 포함).

**④ API** — `GET /api/experts?category=`가 **쉼표로 여러 값**을 받는다(`LAWYER,JUDICIAL_SCRIVENER`).
값마다 `EXPERT_CATEGORIES`(`expertController.ts`)로 검사하고, 모르는 값은 버린다. 한 값·`전체`·빈 값은 지금과 같다.

**범위 밖**: 07 체크리스트에서 상황이 미리 골라진 채 도착하기(§2.3)는 이번에 하지 않는다.

> 🔵 **법률 검토** — 직역을 안내할 뿐 특정 변호사를 유상 소개하지 않으므로 변호사법 §34 대상이 아니라고 판단했다(`02-03` §3.1).
> 과금 개시 전 변호사 검토(`02-03` §10 #4) 때 함께 확인한다. 구현은 막지 않는다.

### 2.3 ✅ 이 구조가 07과 맞물립니다

`07-01` §6이 *"07의 체크리스트가 02의 최상위 유입구"* 라고 했는데, **그 유입이 도착할 자리가
바로 §2.2입니다.** 체크리스트에서 "상속포기·한정승인"에 막힌 유족이 [전문가 상담]을 누르면,
직역 목록이 아니라 **"고인에게 빚이 있을지 걱정됩니다"가 이미 선택된 상태**로 도착해야 합니다.

`02-03` §5.2의 `ConsultRequest.content` 프리필이 그 수단입니다 — 새 API가 필요 없습니다.

## ⚖️ 3. ✅ ①의 답 — 법무사를 추가합니다

### 3.1 왜 필요한가 — 빠뜨릴 수 없는 직역이었습니다

법무사가 없으면 **`07-02`가 정리한 가장 중요한 두 항목의 실행 파트너가 없습니다.**

| `07-02` 항목 | 주 직역 |
| :--- | :--- |
| §2.3-10 **상속포기·한정승인 신청** (3개월) | **법무사** — 법원 제출 서류 작성·제출 대리가 본업 |
| §2.5-17 **부동산 상속등기** | **법무사** — 등기 대리의 주 직역 |

변호사도 할 수 있지만 **비용대가 다르고, 실무상 이 두 건은 법무사가 주력**입니다.
**즉 4직역 체계는 "가장 자주 필요한 일"을 담당할 직역이 빠진 상태였습니다.**

> `HomePage:354`의 *"공증 법무사 매칭"* 문구는 **틀린 것이 아니라 앞서간 것**이었습니다.
> 다만 "공증"은 부정확합니다 — 유언 공증은 **공증인**의 직무입니다(`06-02` §4).

### 3.2 🔴 확인이 필요한 것 — 법무사법 규제

변호사법 §34(알선 대가 금지) 때문에 `02-03` §3에 가드레일을 세웠습니다.
**법무사법에도 유사한 규정이 있는지 확인해야 합니다.**

| 확인 항목 | 왜 |
| :--- | :--- |
| 법무사법상 **알선·소개 대가 수수 제한** 유무 | 있으면 **변호사와 동일 취급**(Tier 3 고정 월정액만) |
| 광고·표시 규제 | 프로필 문구 검수 필요 여부 |

> 🔴 **확인 전까지는 안전한 쪽으로 둡니다** — **법무사도 변호사와 동일하게 성과 연동 수수료
> 배제**로 시작합니다. `02-03` §3.2-1의 "없는 필드는 실수로 채워질 수 없다" 원칙 그대로,
> 과금 테이블에서 `LAWYER`와 함께 배제합니다.

### 3.3 🟡 직역 재정리 (5직역)

| 카테고리 값 | 표시명 | 주 업무 | 성과 연동 수수료 |
| :--- | :--- | :--- | :---: |
| `LAWYER` | 상속 변호사 | 유류분·분쟁, 유언장 검토, 공정증서 유언 | ❌ 금지(변호사법 §34) |
| **`JUDICIAL_SCRIVENER`** | **상속 법무사** | **상속포기·한정승인, 상속등기** | 🔴 **§3.2 확인 전 금지** |
| `TAX_ACCOUNTANT` | 상속세 세무사 | 상속세·취득세, 사전 증여 설계 | ⭕ 조건부 허용 |
| `ADMINISTRATIVE_SCRIVENER` | 행정사 | 행정 신고 대행, 디지털 계정 정리 | ⭕ 허용 |
| `FUNERAL_DIRECTOR` | 장례지도사 | 장례 절차, 사전 장례 계획 | ⭕ 허용 |

> ⚠️ **행정사 표시명에서 "디지털 유품"을 뺐습니다.** 재편으로 그 업무가 Domain 04로 갔고
> (`04-01` §3.4), 행정사의 역할은 그보다 넓습니다.

### 3.4 반영 대상

> 🔄 **2026-08-14 스펙갱신** — 아래 표에 **백엔드 검증 화이트리스트가 빠져 있었습니다.**
> 구현 중 발견돼 함께 처리했고(walkthrough (19)), 게이트가 `🔄스펙갱신`으로 판정해 표를 보강합니다.

| 위치 | 변경 |
| :--- | :--- |
| `schema.prisma` `Expert.category` 주석 | 5개 값으로 |
| 🔄 **`expertController.ts` `EXPERT_CATEGORIES`** | **값 추가 — 빠뜨리면 가입 API가 400으로 거부** |
| `CounselingPage.tsx` `CATEGORY_TABS` | 항목 추가 + §2.2 상황 진입 신설 |
| `PartnerPortalPage`(SCR-008) 가입 폼 | 직역 선택지 추가 |
| `02-01` §2 4대 버티컬 표 | 5대로 갱신 |
| `HomePage:354` | *"유언장 작성 가이드 및 공증 법무사 매칭"* → **"상속 등기·유언장 전문가 연결"** |

> **마이그레이션은 필요 없습니다** — `category`가 문자열이라 값만 추가하면 됩니다.
> 기존 데이터 영향 없음.

> ⚠️ **왜 빠졌었나 — 다음 직역 추가 때 같은 실수를 막기 위해 남깁니다.**
> `category`가 Prisma `enum`이 아니라 **`String`**이라 "스키마 주석만 고치면 끝"으로 보였습니다.
> 그러나 타입 안전장치가 없는 대신 **애플리케이션 레벨 화이트리스트**(`expertController.ts`)가
> 그 역할을 대신하고 있어, **DB가 느슨한 만큼 코드가 조이고 있었습니다.**
> **`String` 컬럼에 허용값을 추가할 때는 그 값을 검사하는 코드도 함께 찾는다** — `Expert.category`
> 외에 `Facility.type`, `DigitalPlatform.category`·`actionType`, `Partner.status` 등도 같은 구조입니다.
