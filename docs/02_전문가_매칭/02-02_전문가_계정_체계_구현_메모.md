## 1. 왜 `Partner`(장사시설)와 별도 모델인가

기존 `Partner`(`01-05`)를 전문가에게도 재사용하는 대신 `Expert` 모델을 새로 만들었습니다. 개발자 지시("따로 되어야 향후 기능·조건 추가가 쉽다")와도 일치하고, 기술적으로도 3가지 이유가 있습니다.

1. **검증 기준이 다름** — 장사시설은 사업자등록번호, 전문가는 자격증 등록번호(변호사 등록번호·세무사 등록번호 등). 검증 절차·근거 기관이 다릅니다.
2. **연결되는 도메인이 다름** — `Partner`는 시설(`Facility`)에 클레임으로 붙고, 전문가는 상담 신청(`ConsultRequest` — `02-03` §4.1, 화면 `CounselingPage`·`ConsultRequestModal`)에 붙습니다.
3. **수익 모델이 직역별로 갈라짐** — 아래 §2 참조. `Partner`의 `Lead`/`CommissionPolicy` 구조를 그대로 재사용하면 변호사만 예외 처리해야 해서 스키마가 지저분해집니다.

## 2. ⚖️ 법적 리스크 메모 (참고용 — `docs/15` §4에 이미 상세 분석 있음)

`02-01`(옛 번호 `docs/15`) §4가 이미 이 부분을 깊게 다뤘습니다. 여기서는 **계정 시스템 구현 관점**에서 새로 확인된 것만 추가합니다.

| # | 리스크 | 상세 | 현재 구현에서의 처리 |
| :---: | :--- | :--- | :--- |
| 1 | **변호사법 제34조**(수임료 분배·알선 금지) | 이미 `02-01` §2·§4에서 "변호사는 순수 고정 월정액 광고만" 확정됨 | `Expert` 스키마에 리드/수수료 관련 필드·관계를 **아예 만들지 않음**(§3). 나중에 실수로 이어붙이는 사고를 구조적으로 방지 |
| 2 | **자격증 진위 확인 의무** | 세무사법·행정사법도 무자격 대리를 금지 — 가짜 자격증으로 가입하면 플랫폼이 무자격자를 알선한 꼴이 될 위험 | 지금은 `licenseDocUrl`(사본 업로드, **선택 입력**)만 받고 **자동 검증 없음** — 운영자가 육안으로 확인 후 수동 승인(`Partner`와 동일한 수동 심사 원칙). 대한변협·국세청 등 공식 조회 API 연동 여부는 사장님 결정 필요 |
| 3 | **직역별 표시·광고 규제** | 변호사는 변호사법상 광고 규제(성공보수 표방 금지 등)가 있어 프로필 문구에도 제약 가능 | 계정 가입 단계에서는 자유 입력(`bio`)만 받음 — 지금 `bio`는 공개 목록·상세 모달에 그대로 보임(`02-03` §7.1). 문구 검수 절차는 아직 없음 |

> **사장님께 보고 필요한 결정 사항**: (1) 자격증 자동 진위확인 API 연동 여부·예산 (2) 변호사 회원의 정산(Tier 3 월정액) 결제 수단을 언제 붙일지 (3) 나머지 3개 직역(세무사·행정사·지도사 — 직역은 08-14 법무사 추가로 5개, 법무사는 변호사와 같게 월정액만: `02-05` §3.2)의 리드 수수료 정산 시스템을 `Partner`의 `Lead`/`CommissionPolicy`처럼 만들지, 아니면 별도로 설계할지.
>
> 🔴 **사장님 보고 대기**(`pending-approvals` "전문가 계정 법적 리스크 3건"). 3건 각각에 대한 권고 답은 `02-03` §6(진위확인 = 연동하지 않음 · 결제 = 초기 계좌이체 · 수수료 = `Lead`와 분리). 미결 목록 = `02-03` §10 #5.

## 3. 데이터 모델 요약

`Expert` 모델(`schema.prisma`) — `Partner`와 인증 방식(이메일+비밀번호, JWT, 승인 플로우)은 동일하되 도메인 필드만 다릅니다.

- `category`: `LAWYER` | `JUDICIAL_SCRIVENER` | `TAX_ACCOUNTANT` | `ADMINISTRATIVE_SCRIVENER` | `FUNERAL_DIRECTOR` (5개 직역 — `02-01` §2. `JUDICIAL_SCRIVENER`(법무사)는 08-14 추가, `02-05` §3). 문자열 컬럼이라 허용값은 `expertController.ts` `EXPERT_CATEGORIES`가 검사합니다.
- `licenseNo` + `licenseOrg`: 사업자등록번호가 아니라 **자격증 등록번호**
- `@@unique([category, licenseNo])`: 같은 자격증 번호 중복 가입 방지
- 공개 노출용 `isPublished`·`officeAddress`는 Stage 1에서 추가(`02-03` §4.3).
- **의도적으로 없는 것**: `Lead`·`CommissionPolicy` 관계, `facilities`류 관계 — §2의 이유로 지금 단계에서 만들지 않음

## 4. 구현 범위 (2026-08-10)

08-10 첫 구현은 계정 체계(스키마 · 가입/로그인/refresh/내정보 API · 가입·로그인 폼)까지였습니다.
그 뒤 **운영자 승인 화면 · 공개 목록 · 상담 신청 · 전문가 대시보드 "받은 상담 신청"** 이 08-11 Stage 1로 구현됐습니다 — 지금 범위의 정본은 `02-03` §1·§9.
승인(`status=APPROVED`)과 공개 노출(`isPublished`)은 별개 플래그입니다(`02-03` §4.3). 08-10 범위표는 부록 §4.
