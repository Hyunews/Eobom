## 2026-08-19 (16) — 모드별 네비게이션 개편 `[Sonnet]`

- 스펙(00-26 §4.2)의 "박스 클릭 → 모드 확정 + 맞춤 메뉴 등장" 다이어그램을 처음엔 "박스 클릭이 곧바로 도메인 페이지로 이동한다"는 뜻으로 오독할 뻔했음. 그런데 실제 코드(EntryBoxes)는 박스①②가 이미 BoxDetailOverlay라는 미니 프리뷰를 여는 구조(00-23/(32)/(34) 사이클에서 만들어짐)라, 두 스펙을 어떻게 합칠지 잠깐 고민함. 결론은 "박스 클릭 = 모드 확정 시점"과 "오버레이 CTA 클릭 = 실제 페이지 이동 시점"을 분리하는 것 — 모드는 박스를 누르는 즉시 정하고(사용자가 미리보기만 보고 닫아도 모드는 이미 정해진 채로 남는다), 실제 라우트 이동은 기존 오버레이 CTA 로직을 그대로 재사용. 이러면 기존 오버레이 UX(00-23이 확정한 부분)를 하나도 안 건드리고 00-26을 얹을 수 있어서 위험이 제일 적었음.
- ①(생전 준비)의 로그인 게이트를 어디에 걸지가 두 번째 고민이었음. "박스 전체에 로그인을 걸라"는 건 아니고(그건 00-23 §4.1이 이미 금지한 패턴) §4.2-1이 "①은 전부 로그인 필수 도메인이 목적이라 예외적으로 박스 단위 게이트가 맞다"고 명시적으로 근거를 대놔서, EntryBoxes의 handleBox1Click 맨 앞에서 `!currentUser` 체크 후 얼리 리턴하는 걸로 확정함 — 오버레이도 안 열리고 모드도 안 바뀜(로그인 취소하면 아무 흔적도 안 남아야 한다고 판단).
- lucide-react 아이콘(Package·Flower2)과 커스텀 MenuIcons(HouseLeafIcon 등)를 같은 배열(MODE_MENUS)에 넣으려다가 tsc가 막힘 — `ComponentType<{size?:number,color?:string}>`로 타입을 좁혔더니 lucide 아이콘의 propTypes 시그니처(size가 string|number 허용)가 안 맞다고 에러남. 처음엔 각 아이콘을 얇은 래퍼로 감싸서 시그니처를 통일할까 했는데, 그러면 파일이 하나 더 늘고 아이콘 4~5개 전부 래핑해야 해서 배보다 배꼽이 커짐. `ElementType`(제네릭 없이)으로 낮추니 한 줄로 해결됨 — 런타임은 어차피 JSX가 각 컴포넌트의 실제 시그니처를 따로 체크하니 안전하다고 판단.
- 헤더 모드 칩을 처음엔 `position:absolute;left:50%;transform:translateX(-50%)`로 짜고 "중앙 고정이니 깔끔하다"고 생각하며 넘어갔는데, 브라우저로 직접 로그인 상태에서 `/counseling`을 열어보니 창 폭이 (아마 이전 스크린샷 작업 중 리사이즈된) ~950px대일 때 "생전 준비 모드" 칩 텍스트와 "네이버 테스트회원 (NAVER)님" 텍스트가 그대로 겹쳐서 렌더링됨. 절대배치는 "항상 정중앙"을 보장하지만 그 대가로 다른 요소와 절대 안 겹친다는 보장을 전혀 안 해준다는 걸 다시 깨달음. 로고-칩-유저정보를 실제 3개의 flex 형제 아이템으로 바꾸고 칩을 담는 가운데 아이템에 `flex:'1 1 auto'`+`justify-content:center`를 줘서, 칩이 "로고와 유저정보 사이에 실제로 존재하는 여유 공간" 안에서만 중앙 정렬되게 고침 — 이러면 공간이 모자라면 칩 자체가 눌리거나 잘릴 뿐 절대 다른 형제를 침범할 수 없음. 이 버그를 실기동으로 못 잡았으면(코드 리뷰만 했으면) 못 찾았을 것 같음 — 절대배치+중앙정렬 조합은 항상 겹침 가능성을 의심하고 실제로 좁은 폭에서 눌러봐야 한다는 교훈.

## 2026-08-18 (9) — `00-18` §11 + `00-19` 처리방침 초안 `[Opus]`

- **"표준 양식이 있는가"에 답하려고 웹 조사를 했는데, 조사 전 내 머릿속 답과 조사 후 답이 달랐음.** 처음엔 *"둘 다 표준이 있으니 베끼면 된다"* 쪽으로 생각했는데, 실제로는 **처리방침은 기재사항이 법으로 열거돼 있고(§30①+시행령 §31) 약관은 그런 게 아예 없음.** 규제 방향이 반대라는 게 핵심이었음 — 하나는 *"이걸 써라"*, 다른 하나는 *"이건 쓰면 무효"*. 이 대비를 잡고 나서야 §11이 써졌음. **안 찾아봤으면 "표준약관 받아서 고치면 됩니다"라고 잘못 답할 뻔했음.**

- **수정**: `SocialAccount`에 `unlinkedAt DateTime?` 추가, 연동 해제를 하드 삭제 대신 `unlinkedAt = now()` 소프트 삭제로 변경. 로그인 1단계는 `unlinkedAt` 무관하게 provider+providerId로 계정을 찾으므로, 예전에 해제했던 계정이면 그대로 발견해서 `unlinkedAt = null`로 되돌리고 로그인시킴(신규 생성 없음). `/api/auth/me`·마이페이지 목록·최소 1개 유지 카운트는 전부 `unlinkedAt: null` 필터 추가. `handleLinkCallback`(마이페이지 재연동)과 `confirmLink`의 MERGE/CREATE_NEW도 동일하게 "과거 소프트 삭제된 행 발견 시 재생성 대신 복구"로 처리.
- **검증**: 연동 해제(soft) → 로그아웃 → 구글 재로그인 시 `User` 개수 그대로 1개 유지, 같은 `providerId`·`userId`로 `unlinkedAt`만 복구되는 것 확인.
