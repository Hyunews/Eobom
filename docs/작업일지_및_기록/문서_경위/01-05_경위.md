### 4.1 리드 유형 — 정정 기록
* **2026-08-11 — `BOOKING`(답사예약) 유형 폐기.** 개발자·사장님 논의로 답사예약 기능 자체를 도입하지 않기로 확정(→ `01-01` 부록 2.5, `01-04` 폐기 배너)되면서 `FacilityBooking` 모델·API가 제거됐고, `BOOKING` 리드를 만들 생산자가 사라졌다. 스키마의 `Lead.type`에서도 값이 삭제됐다(구현: walkthrough `2026-08-11 (6)`). 같은 날 견적 비교도 폐기(→ `01-01` 부록 2.3)되면서 `QUOTE`의 화면 문구가 "견적요청"에서 "업체 문의"로 바뀌었다.
* 🔴 **2026-09-21 — *"익명"* 이 구현에서 지켜지지 않았다.** `leadController.createCallEvent`가 로그인 상태면 **`userId`를 붙여 저장**하고 있었고, 그 탓에 마이페이지 *"내 상담 내역"* 에 **전화 버튼 클릭이 *"접수됨"* 으로** 떴다(`00-36` §4.4-1). 청구에도 쓰지 않는 이벤트에 개인 식별자를 남길 이유가 없어(`00-19` 최소수집) **`userId`를 항상 `null`로** 바꿨다. 이미 쌓인 행은 지우지 않고 조회에서 거른다.

### 5.3 ~~기존 `FacilityBooking`과의 관계~~ → **폐기 (2026-08-11)**

> **이 절은 더 이상 유효하지 않습니다.** 답사예약 기능 자체를 도입하지 않기로 확정(→ `01-01` §2.5)되면서 `FacilityBooking` 모델과 관련 API(`POST /api/facilities/:id/bookings`)가 **삭제**됐습니다. 삭제 시점에 적재 데이터 0건임을 확인했습니다(구현: walkthrough `2026-08-11 (6)`).
>
> 원안은 "`FacilityBooking`(업무 실체)과 `Lead`(정산 근거)는 생명주기가 달라 합치지 않는다"였고 그 판단 자체는 여전히 타당했으나, **답사예약이라는 업무 실체가 사라져** 분리할 대상이 없어졌습니다.

### 5.1·5.2 처음 모델 코드 (2026-08-10)

처음 문서에 실었던 Prisma 코드. 그 뒤 스키마가 바뀌어(`refreshToken`→`refreshTokenHash` · `partnerType` 추가 · `LeadNumberCounter` 추가 · `Lead.facilityId` 선택값) 2026-10-08 본문은 "필드별 이유" 표로 바꾸고 필드 목록은 `00-05`로 넘겼다.

**신규 모델**

```prisma
// 사업자 (법인격 단위) — B2C User와 완전 분리
model Partner {
  id            String   @id @default(uuid())
  email         String   @unique          // 로그인 ID
  passwordHash  String
  refreshToken  String?

  bizRegNo      String   @unique          // 사업자등록번호 (하이픈 제거 10자리)
  companyName   String                    // 상호
  ownerName     String                    // 대표자명
  contactName   String                    // 담당자명
  contactPhone  String
  bizLicenseUrl String?                   // 사업자등록증 사본 (비공개 스토리지)

  status        String   @default("PENDING") // PENDING | APPROVED | REJECTED | SUSPENDED
  rejectReason  String?
  approvedAt    DateTime?

  settlementBank    String?
  settlementAccount String?               // 암호화 저장 (평문 금지)

  facilities   Facility[]
  claims       FacilityClaim[]
  leads        Lead[]
  settlements  Settlement[]
  commissionPolicies CommissionPolicy[]    // 이 파트너 전용 특약 요율 (없으면 기본 요율 적용)

  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  @@index([status])
}

// 시설 소유권 클레임
model FacilityClaim {
  id          String   @id @default(uuid())
  partnerId   String
  partner     Partner  @relation(fields: [partnerId], references: [id], onDelete: Cascade)
  facilityId  String
  facility    Facility @relation(fields: [facilityId], references: [id], onDelete: Cascade)

  status      String   @default("PENDING") // PENDING | APPROVED | REJECTED
  evidenceUrl String?                      // 시설 인허가증 등 소유 증빙
  reviewNote  String?                      // 운영자 심사 메모
  reviewedAt  DateTime?
  createdAt   DateTime @default(now())

  @@unique([partnerId, facilityId])        // 같은 사업자의 중복 신청 방지
  @@index([status])
}

// 리드 (업체 문의 · 상담신청 · 전화클릭)
model Lead {
  id          String   @id @default(uuid())
  leadNo      String   @unique             // EB-260810-0001 (표시·대조용, 불변)
  type        String                       // QUOTE | CONSULT | CALL (BOOKING 폐기 → §4.1)

  facilityId  String
  facility    Facility @relation(fields: [facilityId], references: [id])
  partnerId   String?                      // 발생 시점 귀속 파트너 (없으면 비제휴)
  partner     Partner? @relation(fields: [partnerId], references: [id])

  userId      String?                      // 로그인 유저면 참조 (탈퇴 시 null)
  user        User?    @relation(fields: [userId], references: [id], onDelete: SetNull)

  // 신청자 스냅샷 (§4.4) — 정산 확정 후 마스킹
  applicantName  String?
  applicantPhone String?
  maskedAt       DateTime?

  payload     Json                         // type별 요청 내용 (희망일시/하객수/종교/예산 등)

  thirdPartyConsentAt DateTime?            // 개인정보 제3자 제공 동의 시각 (§7)
  consentSnapshot     Json?                // 동의 시점의 고지 문구 버전 — 분쟁 대비

  status        String  @default("REQUESTED") // §4.3
  statusHistory Json    @default("[]")        // [{status, at, by, note}]

  billable      Boolean @default(false)    // 청구 대상 여부 (운영자 확정)
  billedAmount  Int?                       // 청구 금액 스냅샷
  commissionPolicyId String?               // 어느 요율로 계산했는지 (분쟁 시 유일한 증거)
  commissionPolicy   CommissionPolicy? @relation(fields: [commissionPolicyId], references: [id])
  settlementId  String?
  settlement    Settlement? @relation(fields: [settlementId], references: [id])
  disputeReason String?

  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  @@index([partnerId, status])
  @@index([facilityId, createdAt])
  @@index([createdAt])
}

// 수수료 정책 — 값이 아니라 "유효기간이 붙은 레코드"로 관리 (§12.2)
model CommissionPolicy {
  id            String    @id @default(uuid())
  basis         String                          // PER_CONVERSION | PER_LEAD | MONTHLY_FLAT
  amount        Int?                            // 정액(원)
  rate          Decimal?  @db.Decimal(5, 4)     // 정률 (0.0500 = 5%)
  currency      String    @default("KRW")

  partnerId     String?                         // null = 기본 요율 / 값 = 해당 파트너 특약
  partner       Partner?  @relation(fields: [partnerId], references: [id])

  effectiveFrom DateTime                        // 적용 시작 시점
  effectiveTo   DateTime?                       // null이면 현재 유효

  memo          String?                         // 이 요율인 이유 (특약 사유 등)
  createdBy     String?                         // 변경한 운영자 User.id
  createdAt     DateTime  @default(now())

  leads         Lead[]

  @@index([partnerId, effectiveFrom])
}

// 월 정산
model Settlement {
  id         String   @id @default(uuid())
  partnerId  String
  partner    Partner  @relation(fields: [partnerId], references: [id])
  periodYm   String                        // '2026-08'
  leadCount  Int
  amount     Int
  status     String   @default("DRAFT")    // DRAFT | ISSUED | DISPUTED | PAID
  issuedAt   DateTime?
  paidAt     DateTime?
  leads      Lead[]
  createdAt  DateTime @default(now())

  @@unique([partnerId, periodYm])          // 같은 달 중복 발행 방지
}
```

### 6.4 인증 분리 원칙 — 2026-08-11 정정 기록
초안은 "`User.role === 'ADMIN'`으로 보호(기존 `role` 필드 활용)"였으나, 구현 단계에서 **독립 `Admin` 모델**로 바꿨다(구현: walkthrough `2026-08-10 (3)`). 초안 스스로 "`demo-login`의 ADMIN 발급 경로를 실배포 전 반드시 차단할 것"이라는 위험을 적어뒀는데, 이는 차단해야 할 구멍이 애초에 생기는 설계라는 뜻이었다. 결과적으로 `demo-login` ADMIN 발급 문제는 **경로 자체가 사라져** 해소됐다(`demo-login`은 프로덕션 가드도 별도로 적용됨). 처음 토큰은 3종(`user`/`partner`/`expert`)이었고 `admin`이 더해져 4종이 됐다. §11 "지킬 것"에 있던 *"`demo-login`의 ADMIN 발급 차단"* 항목도 이로써 지웠다.

### 7.1 고지 문구 — 2026-08-11 정정 기록
답사예약 폐기에 따라 고지 문구에서 "답사 예약 연락"을 뺐다. 코드의 고지 문구와 `noticeVersion`도 함께 갱신됐다(구현: walkthrough `2026-08-11 (6)`). **문구를 바꿔도 과거 동의 건의 `consentSnapshot`은 그대로 보존**되므로, 그 시점에 무엇에 동의했는지는 계속 증명된다. 처음 표는 제공받는 자를 "해당 장사시설 사업자(상호 명시)", 목적을 "업체 문의 연락"으로 적었다 — 본문은 코드 문구 기준으로 맞췄다(2026-10-08).

### 7.2 비제휴 시설 — 처음 설계
