### A. 구현 전 결론과 옛 hashField 구조 (09-01)

## 📌 1. 결론 먼저

| 질문 | 답 |
| :--- | :--- |
| **뭐가 문제인가** | 키가 유출돼도 **바꿀 방법이 없습니다.** DB에 이미 잠긴 데이터를 옛 키로 풀어 새 키로 다시 넣는 수단이 없음 |
| **키가 하나인가** | ❌ **아닙니다.** 이미 2개(`SETTLEMENT_`·`ENDING_NOTE_`). 외부 지적은 이 점에서 틀렸습니다 |
| **그럼 `keyVersion` 칸 하나면 되나** | ❌ **아닙니다.** 그건 **암호문에만** 통합니다. **결정적 해시(`hashField`)는 그 방법으로 못 바꿉니다**(§3.2) |
| **가장 급한 것은** | 🔴 **`hashField`의 키 소스 분리**(§4). 지금은 **정산 키를 바꾸면 가족지정 중복방지가 조용히 깨집니다** |
| **왜 지금인가** | ✅ **해시 교체는 원자적**이라 행이 적을수록 쌉니다. 오픈 후에는 같은 작업이 훨씬 위험해집니다 |
| **KMS·Vault 도입하나** | ❌ **하지 않습니다**(§7). 팀 여건(`00-11` §3.3, 전담 보안 인력 0명)에 비해 과합니다 |

### 4.1 지금 구조와 그 대가

```ts
// utils/crypto.ts — 현재
const raw = process.env.SETTLEMENT_ENCRYPTION_KEY;          // 🔴 정산 키
const hmacKey = crypto.createHash('sha256').update(`${raw}:${domain}`).digest();
```

`00-27` §4.1이 이 설계를 정한 근거는 명시돼 있습니다 —
*"**새 환경변수를 추가하지 않으면서** 암호화 키와 인덱스 키를 분리합니다
(env를 늘리면 `render.yaml`·Render 대시보드가 같이 늘어납니다)."*

**절약의 대가가 도메인 결합입니다:**

```
01(정산 계좌) 키 교체  →  00-27(가족 지정) 중복방지 무효화
```

**두 도메인이 env var 하나로 묶여 있고, 그 사실이 코드에도 문서에도 적혀 있지 않습니다.**
정산 키를 교체하는 사람은 가족지정이 깨질 것을 알 수 없습니다.


### B. 선행 조치 — 스키마 주석 오류 (고쳐짐)

### 6.1 ✅ 선행 — 스키마 주석 오류 수정 (**비용 0 · 즉시**)

```prisma
model FarewellMessage {
  bodyEnc String  // ❌ 현재: "…(utils/crypto.ts encryptField)"
                  // ✅ 수정: "…(utils/crypto.ts encryptNoteField, ENDING_NOTE_ENCRYPTION_KEY)"
}
```

실제 코드는 `encryptNoteField`입니다(`farewellMessageController.ts:149·191`).
08-27 키 분리 때 주석만 갱신되지 않았습니다.

> 🔴 **로테이션 스크립트를 이 주석 기준으로 짜면 정산 키로 복호화를 시도합니다.**
> AES-GCM은 `authTag` 불일치로 예외를 던지므로 **조용한 파손은 아니지만**, 전량 작업 중간에
> 터지면 **어디까지 처리됐는지 모르는 상태로 멈춥니다.** 유실 2회 프로젝트에서 가장 나쁜 상태입니다.
