Storage classes이며 **versioning이 없다.** → `00-11` **§5.4-5-1 신설**로 정정하고 §5.4-1 표도 수정.

### 5. [사용자] 토큰 분리·`.env` 완료 → [Claude:Opus] **정정 ③ — 락을 과대평가했다**

**셋업 마무리**: 개발자가 **버킷별 토큰 3개를 새로 발급해 교체**하고 `.env` 기입을 끝냈다.
§5.4-6-1의 🟡 권고(운영 전 분리)가 **당일 해소**됐다. → §5.4-6-1·§5.4-6-2 갱신.

**발단**: 개발자 질문 — *"bucket lock, 보존기간만 30일 맞추면 우리 취지대로 되는 것인가?"*

**🔴 정정 ③ — 아니다. §4의 `Age` 30일 서술이 과장이었다** (공식 Bucket locks 문서 재확인)

`Age`는 **"업로드 후 N초 동안 보호"** 다. 나이가 그 값을 **넘으면 보호가 풀린다**
(문서의 목적어가 *accidental **premature** deletions*). 즉 **0~30일만 잠기고 31일째부터
무방비**인데, **이 도메인 데이터의 수명은 거의 전부가 그 뒤**다. §4에서 *"실수 삭제를 막으면서
정당한 파기는 통과"* 라고 적었는데 **뒷문장만 맞았다** — 앞문장은 "갓 올린 파일을 즉시 지우는
버그"에만 해당한다.

**근본 제약**: 락은 **시간 기반**이지 **의도 기반**이 아니라, `수십 년 보존`과 `탈퇴 시 파기`를
동시에 만족시킬 수 없다. `Indefinite`는 파기 의무와 충돌(§4에서 이미 금지), 이용자별 프리픽스
우회는 **1,000규칙 상한** + **버킷 설정 편집 권한 필요**라 더 위험하다.
⚠️ R2엔 **S3 compliance mode가 없다** — 설정 편집 권한 토큰이면 규칙을 지우고 바로 삭제된다.
**보안 경계는 락이 아니라 토큰 범위**이고, 그래서 위 토큰 분리가 락보다 실효가 크다.

→ `00-11` **§5.4-5-1-1**(정정) · **§5.4-5-2**(3층 방어) 신설, §5.4-1 표 수정,
`06-05` §5.4-2 상호참조 문구 교체.

| 층 | 막는 것 | 한계 |
| :---: | :--- | :--- |
| ① `Age` 30일 락 | 업로드 직후 즉시 삭제 버그 | 🔴 31일째부터 무효 |
| ② 🆕 **아카이브 버킷**(앱 토큰 없음) | 런타임 토큰 침해·앱 버그 **전 기간** | 계정 전체 침해엔 무력 |
| ③ **반출**(`06-05` §5.4) | 이어봄 소멸·계정 침해 | 이용자가 안 받으면 없음 |

### 6. [Gemini 검토] → [Claude:Opus] **락 미채택 확정 · 아카이브 필수 승격**

**Gemini 의견**: *"클라우드 물리적 락은 한 번 걸면 개발자도 못 풀어 사용자 기능(재녹음·즉시

**판정: 처방 2건 채택 · 근거 1건 정정 · 결론(락 미채택)은 다른 이유로 동의.**

| Gemini 주장 | 판정 |
| :--- | :--- |
| UUID 고유키로 덮어쓰기 방지 | ✅ **채택** (5번에 이미 반영돼 있었음) |
| 소프트 삭제 30일 유예 | ✅ **채택** — `06-05` **§5.4-2-1 신설**로 구현 형태 확정 |
| *"락은 개발자도 못 푼다"* | 🔴 **틀림** — 그건 **S3 Object Lock compliance mode**다. **R2엔 compliance mode가 없어** 설정 편집 권한 토큰이면 규칙째 지워진다 |
| *"락이 재녹음·즉시삭제를 막는다"* | 🔴 **성립 안 함** — 고유키면 재녹음은 덮어쓰기가 아니고, 소프트 삭제면 0일차에 `DeleteObject`를 안 부른다. **락이 막을 기능 자체가 없다** |
| *"락 **대신** 앱단"* | 🟡 **층이 다르다** — 앱단은 *정책*, 스토리지단은 *강제*. 앱을 우회하면(정리 스크립트·토큰 유출) 소프트 삭제는 **아무 역할도 못 한다.** 🔴 **이 프로젝트가 두 번 잃은 경로가 정확히 그것**(08-05·08-27) |
| *"전 세계 표준"* | 🔵 **절반만** — 표준은 소프트 삭제 *단독*이 아니라 **소프트 삭제 + 스토리지 버저닝/복제**다(S3 Versioning 기본 켬). R2에 versioning이 없어 **아카이브 버킷으로 그 자리를 직접 만드는 것**뿐 |

**✅ 결론 — 락은 미채택.** 단 *"못 풀어서"* 가 아니라 **효용이 좁아서**다. 락의 유효 구간
(0~30일)은 소프트 삭제가 이미 덮고, 남는 위험(앱 우회 삭제)은 아카이브가 **전 기간** 더 잘 막는다.
