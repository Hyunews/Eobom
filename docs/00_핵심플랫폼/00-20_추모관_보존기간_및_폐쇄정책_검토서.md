## 🔴 2. 먼저 짚을 것 — **하나의 숫자로는 못 정합니다**

개발자 질문은 **"3개월이냐 장기냐"** 라는 한 축인데, **실제로는 세 축이 겹쳐 있습니다.**
**한 숫자를 고르려 하면 반드시 어느 한쪽이 틀립니다.**

### 2.1 축 ①: **부고(07) ↔ 추모(05) — 수명이 정반대입니다**

**`00-13` §2가 이미 이 진단을 해두었습니다** — *"부고 시기와 추모 시기의 링크 요구가 정반대"*.
**보유기간도 정확히 같은 구조입니다.**

| | **부고장(07)** | **추모관(05)** |
| :--- | :--- | :--- |
| 목적 | *"장례가 언제 어디서"* — **행사 안내** | *"고인을 기억하는 곳"* — **기록** |
| 유효 기간 | **발인까지**. 지나면 정보가 **틀린 정보**가 됨 | 길수록 가치 |
| 민감도 | 🔴 **빈소·발인일시·조의금 계좌**(`00-13` §6.3 사기 표적) | 상대적으로 낮음 |
| **적정 보존** | 🟡 **짧을수록 좋음 — 발인 후 1~3개월** | 🟡 **1년 이상** |

> ✅ **개발자가 말씀하신 "3개월"은 부고장 쪽으로는 정확합니다.**
> **틀린 것은 숫자가 아니라 "둘을 같은 것으로 본 것"** 입니다.
> 🔵 **`00-13` E안(부고=봉투 / 추모관=목적지)이 08-14에 확정됐으므로, 보유기간도 그 확정을
> 따라가면 됩니다** — **이미 갈라 놓은 것을 여기서 다시 합칠 이유가 없습니다.**
> ✅ **지금 코드(07 결정 — `07-03` §6.2-4)**: 부고장은 **발인일 + 3일**에 자동으로 닫힙니다(공개 조회 404, 개설자 본인은 계속 열람 — `obituaryController` `isAutoExpired`).
> 🔴 닫힌 부고장 **행을 언제 지우는지**(파기)는 탈퇴 때 말고는 규칙이 없습니다 — 처리방침 `00-19` 제4조에도 부고장 행이 없음(`00-18` §6).

### 2.2 축 ②: **텍스트 ↔ 사진 — 비용이 두 자릿수 이상 차이 납니다**

**"스토리지 비용" 문제의 실체는 사진 하나입니다.**

| 데이터 | 1건당 대략 | 비고 |
| :--- | :--- | :--- |
| 방명록 10건 + 추모 문구 + 고인 정보 | **수 KB** | DB 텍스트 |
| 추모 사진 10장 | **수 MB ~ 수십 MB** | `MemorialPhoto` |

> ✅ **결론: 텍스트는 사실상 영구 보존해도 비용 문제가 없습니다.**
> **정책이 필요한 것은 사진뿐입니다.**
> 🟡 **이 구분이 실무에서 큰 차이를 만듭니다** — *"1년 뒤 추모관을 지웁니다"* 는 유족에게 잔인하지만,
> *"1년 뒤 사진은 원본 대신 축소본으로 보관합니다"* 는 훨씬 받아들이기 쉽습니다.
> `05-01` §2.6이 *"추모 사진은 유족이 영구 보존을 기대하는 자산"* 이라고 한 것과도 충돌하지 않습니다.

### 2.3 🔴 축 ③: **유족의 데이터 ↔ 조문객의 데이터 — 권리 주체가 다릅니다**

**이 축이 가장 자주 빠지고, 법적으로는 가장 위험합니다.**

방명록에는 **비회원 조문객의 이름**이 들어갑니다(`MemorialGuestbook.authorName`).
이 사람들은 **이어봄 회원이 아니고**, 자기 이름이 언제까지 남는지 **안내받은 적이 없습니다.**

> 🔴 **유족이 *"영구 유지"* 를 선택했다고 해서, 조문객의 개인정보를 영구 보관할 권한이 생기는
> 것은 아닙니다.** 유족은 **자기 정보의 주체이지 조문객 정보의 주체가 아닙니다.**
>
> 🟡 **다만 실무적 해법이 있습니다** — **조문록은 "고인에 대한 기록"으로서 보존하되,
> 일정 기간 후 작성자명을 축약(`홍길동` → `홍*동`)** 하는 것입니다.
> **리드 마스킹(`01-05` §7.3)에서 이미 검증된 패턴**이고, **조문의 의미는 남기고 식별성만
> 낮춥니다.** 조문록의 가치는 *"누가 왔는지"* 보다 *"이만큼 왔다"* 와 **메시지 자체**에 있습니다.

개발자 말씀대로 *"장례와 함께 소통하는 용"* 이라면 3개월로 충분합니다.
**문제는 유족이 추모관을 다시 찾는 시점이 3개월 이후에 몰려 있다는 것입니다.**

| :--- | :--- | :---: |

| D+100일 | 졸곡·백일 | ✅ (턱걸이) |
| **D+365** | 🔴 **첫 기일(소상) — 양력** | ❌ **이미 없음** |
| **D+354 ~ D+384** | 🔴 **첫 기일 — 음력.** 🆕 **윤달이 끼는 해는 양력 기준 19일까지 뒤로 밀림**(2026-08-28 추가) | ❌ |
| 설·추석 | 명절 차례 | ❌ **최소 한 번은 못 만남** |

> 🔴 **가장 나쁜 지점은 "첫 기일"입니다.** 유족이 **1년 만에 다시 찾아왔는데 사라져 있는 것**은
> 서비스가 줄 수 있는 최악의 경험 중 하나입니다. 일반 서비스라면 *"데이터 정책"* 이지만,
> **이 도메인에서는 "고인을 두 번 잃는 것"처럼 받아들여집니다.**
>
> ✅ **1년이 기준선인 이유가 이것입니다 — 임의의 숫자가 아니라 첫 기일을 지나는 최소 기간**입니다.

#### 3.1 🔵 **2026-08-28 정정 — "1년 정각"으로는 부족합니다**

> 🔴 **이 자리에 있던 문장을 폐기합니다** — *"만료 통지를 30일 전에 보내면 실질적으로 13개월이
> 된다"*. **틀린 계산입니다.** 30일 전 통지는 기간을 늘리는 것이 아니라 **D+335에 알림이 한 번
> 가는 것**일 뿐이고, 만료는 그대로 D+365입니다. 이 문장을 남겨두면 나중에 *"1년으로 해도
> 13개월이나 마찬가지"* 라는 **없는 근거**로 재인용됩니다.

**개발자 지적(2026-08-28)** — *"기일을 생각하면 1년보다 조금 많아야 하는 것 아닌가."* 맞습니다.
**1년 정각이 위험한 이유가 셋인데, 셋 다 같은 방향으로 밉니다.**

| # | 요인 | 왜 1년으로 안 되나 |
| :---: | :--- | :--- |
| ① | 🔴 **음력 기일** | 상당수 가정이 기일을 음력으로 지냅니다. 음력 기일은 보통 양력 기준 11일쯤 **앞당겨지지만**(안전), **윤달이 끼는 해에는 약 19일 뒤로 밀립니다 → D+384.** 윤달은 19년에 7번이라 예외가 아닙니다 |
| ② | 🔴 **동결 확정으로 사고의 모양이 바뀜** | 이제 첫 기일에 추모관이 *사라지진* 않습니다(동결도 열람은 됩니다). 대신 **기일 당일에 헌화·방명록이 잠깁니다.** **기일은 유족이 1년 중 글을 가장 많이 남기는 날**인데, 열람만 되고 *"보고 싶습니다"* 한 줄을 못 씁니다 |
| ③ | 🔴 **통지가 기일과 충돌** | 만료 30일 전 규칙이면 통지가 **D+335 — 기일 한 달 전**에 갑니다. *"곧 기일인데 없어진대"* 는 §4.2가 세운 **"더하는 질문"** 원칙의 정반대입니다 |

> ✅ **그래서 넘어야 할 선은 하나입니다 — `D+384`.** "1년"이나 "13개월"이라는 이름이 아니라
> 이 숫자를 덮느냐로 판단합니다.
>
> 🟡 **기산점은 사망일이 아니라 개설일로 둡니다.** 개설은 항상 사망일 +2~5일이라 실제 만료가
> **D+397~400**이 되어 **자동으로 안전한 쪽으로 틀립니다.** 반대로 사망일 기준이면 D+365가
> **기일 당일 = 만료일**이 되어 최악이고, `Memorial.deceasedDeathDate`가 nullable이라
> (`eobomDev/backend/prisma/schema.prisma:475`) **값이 없는 추모관용 2번째 규칙**이 따로 필요해집니다.
> 규칙이 둘이 되면 *"왜 우리 추모관만 날짜가 다르냐"* 는 문의가 생깁니다.

## 🤔 4. "사용자에게 결정하게 할 것인가" — **예. 단 시점이 전부입니다**

### 4.1 🔴 개설 시점에 물으면 안 됩니다

**추모관을 개설하는 시점은 유족이 인생에서 판단력이 가장 낮은 며칠 중 하나입니다.**
그 화면에서 *"이 추모관을 얼마나 유지하시겠습니까? (3개월 / 1년 / 영구)"* 를 묻는 것은:

| 문제 | 내용 |
| :--- | :--- |
| **① 답할 수 없는 질문** | 장례 이틀째에 *"1년 뒤에도 이걸 볼 것 같나"* 를 판단할 수 있는 사람은 없습니다 |
| **② 잔인한 질문** | *"3개월"* 을 고르는 행위 자체가 **고인을 3개월짜리로 값매기는 느낌**을 줍니다 |
| **③ 기능이 아니라 부담** | `00-02` 6070 시니어 페르소나에서 **선택지는 배려가 아니라 장벽**입니다 |

> ✅ **그래서 권고는 "묻지 않고 기본값으로 시작"입니다.** 선택권을 없애자는 게 아니라
> **선택 시점을 뒤로 미루자**는 것입니다.

### 4.2 ✅ 물어야 할 시점은 **만료가 다가올 때**입니다

**1년쯤 지나 물으면 위 세 문제가 전부 사라집니다.**

- 유족은 이미 **1년을 지나 판단할 수 있는 상태**입니다.
- *"계속 두시겠습니까"* 는 **더하는 질문**이지 **값매기는 질문이 아닙니다.**
- 실제 사용 여부를 **본인이 이미 알고 있습니다** — 자주 봤으면 연장하고, 안 봤으면 안 합니다.

> 🔵 **2026-08-28 확정 — 정확히는 "첫 기일 + 1주"입니다.** 이 논리를 한 칸 더 밀면 여기까지
> 옵니다: **기일 전에 물으면 압박이고, 기일 직후에 물으면 확인**입니다. 기일에 다시 찾아와

## ❄️ 5. 🟡 핵심 권고 — **만료 시 "삭제"가 아니라 "동결"**

**`00-13` §7.2-3에 이미 나와 있던 아이디어를 여기서 정식 권고로 올립니다** —
*"N년 후 동결 + 정적 스냅샷 보존"*.

### 5.1 왜 동결인가 — **비용은 "보관"이 아니라 "살아 있음"에서 나옵니다**

| | 활성 추모관 | **동결 추모관** |
| :--- | :--- | :--- |
| 방명록·헌화·사진 **추가** | ⭕ | ❌ |
| 기존 내용 **열람** | ⭕ | ⭕ |
| DB 쓰기 부하 | 있음 | **0** |
| 운영 부담(신고 대응·모더레이션) | 있음 | **거의 0** |
| 스토리지 | 원본 | 🟡 **축소본으로 대체 가능**(§2.2) |

> ✅ **동결은 "지우지 않으면서 비용을 거의 0으로 만드는" 상태입니다.**
> 유족에게는 **"남아 있다"** 가 지켜지고, 회사에는 **비용이 안 생깁니다.**
> **이 도메인에서 삭제는 마지막 수단이어야 합니다.**

> 🔵 **2026-08-27 개발자 확정 — 위 표대로 진행합니다.**
> **동결 상태에서 방명록·헌화·사진 *추가*는 차단하고, 기존 내용 열람은 유지**합니다.
> ⚠️ **구현 시 §8.1의 경고를 그대로 지킬 것** — `frozenAt` 가드를 **방명록·헌화·사진 3개 쓰기
> 경로에 전부** 걸어야 합니다. 한 곳이라도 빠지면 동결이 동결이 아닙니다.
> 🟡 **삭제는 막지 않습니다** — 동결이 막는 것은 *추가*입니다. 개설자가 부적절한 방명록 1건을
> 지우는 것(`00-21` 제17조 2항)까지 막으면, **동결된 추모관은 신고가 들어와도 손댈 수 없는
> 상태**가 됩니다. §6.2의 조치가 동결 추모관에도 닿아야 합니다.

### 8.1 🟡 구현은 **작습니다** — 이 결정이 무거워 보이는 것에 비해

```prisma
model Memorial {
  // ... 기존 유지
  expiresAt DateTime?  // 활성 만료 시점 — 연장 시 갱신
  frozenAt  DateTime?  // 동결 시각. 값이 있으면 쓰기 API 전면 차단(읽기는 유지)
  purgeAt   DateTime?  // 🔵 08-27 추가 — 완전 파기 예정 시각.
                       //   동결 만료(+3년, §5.2-1) 또는 폐쇄 요청(+30일, §6.3)이 채운다
}
```

> ✅ **필드 3개 + 쓰기 경로에 가드 1줄 + 배치**입니다. `Partner.partnerType`(`03-02` §3.1)과
> 같은 **"기본값으로 무해하게 축을 하나 더한다"** 패턴 3회차입니다.
> ⚠️ **단 `frozenAt` 가드는 방명록·헌화·사진 3개 경로에 전부 걸어야 합니다** —
> 한 곳이라도 빠지면 동결이 동결이 아닙니다. **`00-15` §3이 말한 "조용히 깨지는" 유형**입니다.

- 🔴 **발송 기능은 STT·OCR처럼 "설정값으로 켜고 끄는 provider"로 만든다**(`EMAIL_ENABLED`·`ALIMTALK_ENABLED`, 기본값 꺼짐). 꺼져 있으면 실제로 보내지 않고 "통지 실패"로 남긴다 → **업체를 정하기 전에 코드를 먼저 짜도 위험하지 않다.**
- 🟡 **업체 선정은 사람이 한다** — 이메일 발송 업체 + 보내는 주소용 도메인(지금 `eobom.vercel.app`이라 자체 도메인이 없음), 알림톡 대행사. 정해지면 환경변수만 넣는다.
- 같은 통지 기능을 **만료 통지(§8.1-2)·파기 30일 전 재확인(§8.1-1)·폐쇄/탈퇴 유예 안내(§6.3)**가 같이 쓴다. 통지마다 발송 수단·결과·시각을 기록한다(통지 실패 판정 근거).

**파기 단계 — 기존 수동 파기 스크립트(`prisma/destroy-farewell-media.ts`)에 추가.** 새 스케줄러는 만들지 않는다(§8.1-1 09-30 확정과 같음).

#### 8.1-4 🆕 연장(활성 복귀) 경로 — **링크 한 번 + 버튼 한 번** (2026-10-06 [Opus] 스펙, §4.3·§5.2-2 확정분의 구현)

> 연장 자체는 08-28 확정(§4.3 "통지 링크 한 번으로", §5.2-2 "연장한 날부터 395일")이다. 받을 API·화면이 없어 통지에 링크를 못 넣고 있었다.

| 항목 | 스펙 |
| :--- | :--- |
| 효과 | `expiresAt = 지금 + 395일` · `frozenAt = null` · `purgeAt = null`. **동결 전(만료 통지)·동결 후(파기 재확인) 같은 동작** — 둘 다 "다시 395일 활성" |
| 할 수 없는 경우 | `closedAt` 있음(닫힘·탈퇴 유예) · `hiddenAt` 있음(운영자 내림) · 이미 파기됨 → *"이 추모관은 연장할 수 없습니다."* + 사유 한 줄 |
| ① 통지 링크 | 통지마다 **무작위 토큰**을 만들어 DB엔 해시만 저장(`MemorialNotice`에 칸 추가). 유효 = 그 추모관의 `purgeAt`(없으면 `expiresAt` + 30일)까지 · **한 번 쓰면 끝** |
| ①-가 🔴 링크를 여는 것만으로 연장하지 않는다 | 링크(GET) = **확인 화면**(추모관 이름·고인 이름·삭제 예정일 + `계속 보존하기` 버튼 하나). **버튼(POST)이 연장**. 이유: 메일 보안 검사기가 링크를 미리 열어 저절로 연장되는 사고 방지. **로그인 요구 안 함**(§4.3 "로그인→마이페이지→…면 아무도 못 함") |
| ② 로그인 경로 | `/my-obituaries-memorials`의 각 추모관 카드에 **만료·동결 상태와 날짜 + `계속 보존하기`** — 개설자 본인만. 같은 API(인증으로 본인 확인). 🔄 **2026-10-20 디자인 개편**: 자리가 **추모관 관리 화면**(`/memorial?slug=…`)으로 옮겨 갑니다 — 마이페이지 추모관 상세 창을 없애고 줄을 누르면 관리 화면으로 감(`00-36` §4.8-3, 8단계). 조건(②-가)·날짜 줄은 그대로 |
| ②-가 🆕 버튼 표시 시점 (10-06 개발자 결정 A) | **만료 통지 시점(§8.1-2 계산값)이 지났거나 동결 상태일 때만** 버튼을 보인다. 그 전에는 날짜 줄만. 이유: 갓 만든 추모관에 "계속 보존하기"가 떠 있으면 어색하고, 통지를 받은 때와 화면이 맞아야 한다. 🔴 **판정은 서버가 한다** — 목록 API(`GET /api/me/memorials`)가 추모관마다 `canExtend`를 내려주고 화면은 그 값만 본다(통지 시점 계산을 화면에 복제하지 않음). 연장 API도 같은 조건으로 거부(`아직 연장할 수 있는 기간이 아닙니다.`). 통지 링크(①)는 통지가 나간 뒤에만 존재하므로 따로 막을 필요 없음. `expiresAt`이 비어 있는 행(정상 데이터 아님)은 통지 시점을 못 구하므로 **동결일 때만** 허용(10-07 Sonnet 편차 승인 — 이상 데이터에 연장을 열어 주지 않는 쪽) |
| 기록 | 연장마다 `MemorialNotice`(또는 같은 기록)에 경로(링크/로그인)·시각. 통지 실패로 묶여 있던 건도 연장되면 일반 경로로 돌아감 |
| 통지 문구 | 지금 문구(삭제 예정일 + `/my-obituaries-memorials`)에 **`계속 보존하기` 링크 한 줄 추가**. 링크 없는 지금 문구도 ②로 연장 가능하므로 틀린 안내는 아님 |
| 문구 | 사실만(`feedback_no_ai_tone`) — *"○○○님 추모관이 ○월 ○일에 삭제됩니다. 계속 보존하려면 아래 버튼을 누르세요."* · 완료 후 *"○년 ○월 ○일까지 보존됩니다."* |

#### 8.1-5 🆕 원본 마스킹 범위 — **문의 내용·상담 내용도 같이 지운다** (2026-10-06 [Opus] 판정)

- `00-19` 제4조가 마스킹 뒤에도 남긴다고 약속한 것은 **거래 근거(접수번호·일시·대상 시설·금액)뿐**이다. 자유 입력(`Lead.payload` — 업체 문의 `message` 등 · `ConsultRequest.content` — 상담 희망 내용)은 고인 이름·빚·가족 사정이 들어가기 쉽고, 남길 근거가 없다.
- → 이름·연락처를 가리는 **같은 단계(종결 후 90일)에서 함께 처리**: `Lead.payload` = `{}`로 비움 · `ConsultRequest.content` = `"(보관 기간이 지나 삭제됨)"`. 처리 건수는 같은 실행 이력에.
- 사업자·전문가 화면에서 이 값이 보이면 그대로 *"(보관 기간이 지나 삭제됨)"*으로 보인다 — 별도 화면 작업 없음.
- `00-19` 제4조 문구도 "이름·연락처·문의 내용"으로 맞춘다(10-06 반영).
