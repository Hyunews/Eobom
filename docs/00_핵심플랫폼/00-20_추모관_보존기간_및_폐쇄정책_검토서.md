## 🔴 2. 먼저 짚을 것 — **하나의 숫자로는 못 정합니다**

사장님 질문은 **"3개월이냐 장기냐"** 라는 한 축인데, **실제로는 세 축이 겹쳐 있습니다.**
**한 숫자를 고르려 하면 반드시 어느 한쪽이 틀립니다.**

### 2.1 축 ①: **부고(07) ↔ 추모(05) — 수명이 정반대입니다**

**`00-13` §2가 이미 이 진단을 해두었습니다** — *"부고 시기와 추모 시기의 링크 요구가 정반대"*.
**보유기간도 정확히 같은 구조입니다.**

| | **부고장(07)** | **추모관(05)** |
| :--- | :--- | :--- |
| 목적 | *"장례가 언제 어디서"* — **행사 안내** | *"고인을 기억하는 곳"* — **기록** |
| 유효 기간 | **발인까지**. 지나면 정보가 **틀린 정보**가 됨 | 길수록 가치 |
| 민감도 | 🔴 **빈소·발인일시·조의금 계좌**(`00-13` §6.3 사기 표적) | 상대적으로 낮음 |
| **적정 보존** | 🟡 **짧을수록 좋음 — 발인 후 1~3개월** | 🟡 **1년 이상** |

> ✅ **사장님이 말씀하신 "3개월"은 부고장 쪽으로는 정확합니다.**
> **틀린 것은 숫자가 아니라 "둘을 같은 것으로 본 것"** 입니다.
> 🔵 **`00-13` E안(부고=봉투 / 추모관=목적지)이 08-14에 확정됐으므로, 보유기간도 그 확정을
> 따라가면 됩니다** — **이미 갈라 놓은 것을 여기서 다시 합칠 이유가 없습니다.**

### 2.2 축 ②: **텍스트 ↔ 사진 — 비용이 두 자릿수 이상 차이 납니다**

**"스토리지 비용" 문제의 실체는 사진 하나입니다.**

| 데이터 | 1건당 대략 | 비고 |
| :--- | :--- | :--- |
| 방명록 10건 + 추모 문구 + 고인 정보 | **수 KB** | DB 텍스트 |
| 추모 사진 10장 | **수 MB ~ 수십 MB** | `MemorialPhoto` |

> ✅ **결론: 텍스트는 사실상 영구 보존해도 비용 문제가 없습니다.**
> **정책이 필요한 것은 사진뿐입니다.**
> 🟡 **이 구분이 실무에서 큰 차이를 만듭니다** — *"1년 뒤 추모관을 지웁니다"* 는 유족에게 잔인하지만,
> *"1년 뒤 사진은 원본 대신 축소본으로 보관합니다"* 는 훨씬 받아들이기 쉽습니다.
> `05-01` §2.6이 *"추모 사진은 유족이 영구 보존을 기대하는 자산"* 이라고 한 것과도 충돌하지 않습니다.

### 2.3 🔴 축 ③: **유족의 데이터 ↔ 조문객의 데이터 — 권리 주체가 다릅니다**

**이 축이 가장 자주 빠지고, 법적으로는 가장 위험합니다.**

방명록에는 **비회원 조문객의 이름**이 들어갑니다(`MemorialGuestbook.authorName`).
이 사람들은 **이어봄 회원이 아니고**, 자기 이름이 언제까지 남는지 **안내받은 적이 없습니다.**

> 🔴 **유족이 *"영구 유지"* 를 선택했다고 해서, 조문객의 개인정보를 영구 보관할 권한이 생기는
> 것은 아닙니다.** 유족은 **자기 정보의 주체이지 조문객 정보의 주체가 아닙니다.**
>
> 🟡 **다만 실무적 해법이 있습니다** — **조문록은 "고인에 대한 기록"으로서 보존하되,
> 일정 기간 후 작성자명을 축약(`홍길동` → `홍*동`)** 하는 것입니다.
> **리드 마스킹(`01-05` §7.3)에서 이미 검증된 패턴**이고, **조문의 의미는 남기고 식별성만
> 낮춥니다.** 조문록의 가치는 *"누가 왔는지"* 보다 *"이만큼 왔다"* 와 **메시지 자체**에 있습니다.

## 📅 3. 🔴 3개월을 권고하지 않는 이유 — **한국 상례의 리듬**

사장님 말씀대로 *"장례와 함께 소통하는 용"* 이라면 3개월로 충분합니다.
**문제는 유족이 추모관을 다시 찾는 시점이 3개월 이후에 몰려 있다는 것입니다.**

| 시점 | 사건 | 3개월 정책이면 |
| :--- | :--- | :---: |
| D+0 ~ D+5 | 장례 | ✅ |
| **D+49일** (약 7주) | **49재** | ✅ |
| D+100일 | 졸곡·백일 | ✅ (턱걸이) |
| **D+1년** | 🔴 **첫 기일(소상)** | ❌ **이미 없음** |
| 설·추석 | 명절 차례 | ❌ **최소 한 번은 못 만남** |
| D+2년 | 대상·탈상 | ❌ |

> 🔴 **가장 나쁜 지점은 "첫 기일"입니다.** 유족이 **1년 만에 다시 찾아왔는데 사라져 있는 것**은
> 서비스가 줄 수 있는 최악의 경험 중 하나입니다. 일반 서비스라면 *"데이터 정책"* 이지만,
> **이 도메인에서는 "고인을 두 번 잃는 것"처럼 받아들여집니다.**
>
> ✅ **1년을 권고하는 이유가 이것입니다 — 임의의 숫자가 아니라 첫 기일을 지나는 최소 기간**입니다.
> 🟡 정확히는 **"첫 기일 + 여유"** 이므로 **13개월**도 후보입니다만, 이용자에게 설명하기 쉬운
> **1년**을 권고하고 **만료 통지를 30일 전에 보내면 실질적으로 13개월**이 됩니다.

## 🤔 4. "사용자에게 결정하게 할 것인가" — **예. 단 시점이 전부입니다**

### 4.1 🔴 개설 시점에 물으면 안 됩니다

**추모관을 개설하는 시점은 유족이 인생에서 판단력이 가장 낮은 며칠 중 하나입니다.**
그 화면에서 *"이 추모관을 얼마나 유지하시겠습니까? (3개월 / 1년 / 영구)"* 를 묻는 것은:

| 문제 | 내용 |
| :--- | :--- |
| **① 답할 수 없는 질문** | 장례 이틀째에 *"1년 뒤에도 이걸 볼 것 같나"* 를 판단할 수 있는 사람은 없습니다 |
| **② 잔인한 질문** | *"3개월"* 을 고르는 행위 자체가 **고인을 3개월짜리로 값매기는 느낌**을 줍니다 |
| **③ 기능이 아니라 부담** | `00-02` 6070 시니어 페르소나에서 **선택지는 배려가 아니라 장벽**입니다 |

> ✅ **그래서 권고는 "묻지 않고 기본값으로 시작"입니다.** 선택권을 없애자는 게 아니라
> **선택 시점을 뒤로 미루자**는 것입니다.

### 4.2 ✅ 물어야 할 시점은 **만료가 다가올 때**입니다

**11개월 뒤에 물으면 위 세 문제가 전부 사라집니다.**

- 유족은 이미 **1년을 지나 판단할 수 있는 상태**입니다.
- *"계속 두시겠습니까"* 는 **더하는 질문**이지 **값매기는 질문이 아닙니다.**
- 실제 사용 여부를 **본인이 이미 알고 있습니다** — 자주 봤으면 연장하고, 안 봤으면 안 합니다.

> 🟡 **문구도 중요합니다.** *"보존기간이 만료되어 삭제됩니다"* 가 아니라
> **"○○○님의 추모관을 계속 열어둘까요?"** — `06-03` §5·`04-02` §6이 세운 문구 원칙과 같은 계열입니다.

### 4.3 🟡 그리고 **연장은 1클릭이어야 합니다**

로그인 → 마이페이지 → 추모관 → 설정 → 연장이면 **아무도 못 합니다.**
**통지 메시지의 링크 한 번으로 연장**되어야 합니다.
🔴 **연장 실패로 사라지는 추모관이 생기면, 정책이 아니라 사고입니다.**

## ❄️ 5. 🟡 핵심 권고 — **만료 시 "삭제"가 아니라 "동결"**

**`00-13` §7.2-3에 이미 나와 있던 아이디어를 여기서 정식 권고로 올립니다** —
*"N년 후 동결 + 정적 스냅샷 보존"*.

### 5.1 왜 동결인가 — **비용은 "보관"이 아니라 "살아 있음"에서 나옵니다**

| | 활성 추모관 | **동결 추모관** |
| :--- | :--- | :--- |
| 방명록·헌화·사진 **추가** | ⭕ | ❌ |
| 기존 내용 **열람** | ⭕ | ⭕ |
| DB 쓰기 부하 | 있음 | **0** |
| 운영 부담(신고 대응·모더레이션) | 있음 | **거의 0** |
| 스토리지 | 원본 | 🟡 **축소본으로 대체 가능**(§2.2) |

> ✅ **동결은 "지우지 않으면서 비용을 거의 0으로 만드는" 상태입니다.**
> 유족에게는 **"남아 있다"** 가 지켜지고, 회사에는 **비용이 안 생깁니다.**
> **이 도메인에서 삭제는 마지막 수단이어야 합니다.**

> 🔵 **2026-08-27 사장님 확정 — 위 표대로 진행합니다.**
> **동결 상태에서 방명록·헌화·사진 *추가*는 차단하고, 기존 내용 열람은 유지**합니다.
> ⚠️ **구현 시 §8.1의 경고를 그대로 지킬 것** — `frozenAt` 가드를 **방명록·헌화·사진 3개 쓰기
> 경로에 전부** 걸어야 합니다. 한 곳이라도 빠지면 동결이 동결이 아닙니다.
> 🟡 **삭제는 막지 않습니다** — 동결이 막는 것은 *추가*입니다. 개설자가 부적절한 방명록 1건을
> 지우는 것(`00-21` 제17조 2항)까지 막으면, **동결된 추모관은 신고가 들어와도 손댈 수 없는
> 상태**가 됩니다. §6.2의 조치가 동결 추모관에도 닿아야 합니다.

### 5.2 🟡 권고 3단계

| 단계 | 시점 | 상태 |
| :---: | :--- | :--- |
| **활성** | 개설 ~ 🔴 **[1년 — 확정 필요, §5.2-2]** | 전 기능 |
| **동결** | 활성 만료 후(연장 안 함) | **읽기 전용.** 링크는 그대로 살아 있음 |
| **파기** | 🔵 **동결 후 3년** — 또는 **개설자 요청 시**(§6.3 유예 적용) | 완전 삭제 |

#### 5.2-1 🔵 **2026-08-27 사장님 확정 — 동결 후 3년 + 파기 전 재확인**

> 원안은 *"지금 정하지 말고 실제 규모를 보고"* 였습니다. **사장님이 3년으로 정하셨고, 여기에
> `파기 전 유족에게 되묻기`를 붙이셨습니다.** 되묻기가 붙으면서 **원안이 우려한 "근거 없는
> 숫자" 문제가 실질적으로 해소됩니다** — 숫자가 틀려도 파기 직전에 사람이 한 번 막을 수 있습니다.

| | 값 | 근거 |
| :--- | :--- | :--- |
| 동결 → 파기 | **3년** | 활성 1년 + 동결 3년 = **총 4년**. 첫 기일(1년)·대상 탈상(2년)·**3주기(3년)** 를 전부 지납니다 |
| 파기 전 통지 | 🟡 **파기 30일 전**(만료 통지와 같은 리듬 — §4.3 재사용) | 새 채널·새 UI를 만들지 않습니다 |

**🔴 되묻기에 "예"라고 하면 어디로 가나** — 이 빈칸을 남기면 구현이 멈춥니다.

> 🟡 **권고: 동결 연장이 아니라 *활성 복귀*(다시 1년)** 로 보냅니다.
> **4년 뒤 통지에 응답했다는 것은 아직 쓰고 있다는 뜻**입니다. 읽기 전용으로 3년 더 묶어두면
> *"살아 있다고 답했는데 여전히 아무것도 못 쓰는"* 상태가 됩니다. 활성 복귀는 §4.2의
> *"더하는 질문"* 원칙과도 같은 방향입니다.

**🔴 통지가 닿지 않으면 파기하지 않습니다.**

### 6.2 🔵 **"허위·부적절 신고"란 무엇인가** — 2026-08-27 사장님 요청

> **사장님 질문**: *"허위 부적절 신고? → 예를 들어 설명해줬으면 함. 왜냐하면, 그것에 대한

> 전환"* 이라고만 적혀 있고, 무엇이 신고 사유인지가 어디에도 없습니다.** 사유 없는 신고
> 버튼은 조항이 아니라 **아무나 누를 수 있는 정지 버튼**입니다.

#### 6.2-1 🔴 먼저 — **현재 설계는 조치 단위가 틀렸습니다**

**이 절에서 가장 중요한 한 가지입니다.** 사유를 나열하기 전에 이것부터 고쳐야 합니다.

| | 현재 `Memorial.reportedAt` | 실제로 들어올 신고 |
| :--- | :--- | :--- |
| 조치 대상 | **추모관 전체** | 🔴 **대부분은 방명록 1건**입니다 |
| 발동 조건 | **신고 접수 = 즉시 비공개** | — |

> 🔴 **문제 ①: 조문객이 남긴 악의적 방명록 1건 때문에 추모관 전체가 닫힙니다.**
> 유족이 피해자인데 **유족의 추모관이 벌을 받습니다.**
> 🔴 **문제 ②: 신고 1건으로 즉시 전면 비공개는 그 자체가 공격 수단입니다.**
> **장례 중에 조문객들이 카톡으로 받은 링크를 못 엽니다.** 되돌리는 데 운영자 확인이
> 필요한데, 이어봄에는 **24시간 대응 인력이 없습니다.**
> ✅ **`Memorial.reportedAt`은 유지하되, 조치를 세 단위로 나눕니다** —
> **① 게시물 1건 비공개 / ② 추모관 비공개 / ③ 계정 제재.** 대부분의 신고는 ①에서 끝납니다.

#### 6.2-2 🅰️ **추모관 자체가 문제인 경우 — "허위"**(조치 = 추모관)

> 🔴 **A-4는 "허위 신고"가 아닙니다.** 사망은 사실이고 개설자도 유족입니다. **회사가 누가 더

> **개설 시점에 다른 유족에게 알림**을 보내 이 분쟁 자체를 줄일 수 있습니다.

```text
   통지합니다. 통지를 받은 자는 회사에 이의를 제기할 수 있고, 회사는 확인 후
   조치를 해제하거나 유지합니다.

⑥ 정당한 사유 없이 반복하여 허위의 신고를 한 이용자에 대하여 회사는 신고 기능의
   이용을 제한할 수 있습니다.
```

### 6.3 🔵 **폐쇄 유예기간 30일** — 2026-08-27 사장님 확정

> **사장님 제안**: *"계정 소멸, 요청에 따른 폐쇄의 경우 요청이 들어온 즉시 폐쇄가 아닌
> 1달의 유예기간이 있으면 어떨까 싶음."*
>
> ✅ **채택합니다.** 다만 **"폐쇄"라는 한 단어를 두 층으로 쪼개야** 이 제안이 성립합니다.

#### 6.3-1 🔴 "즉시 폐쇄"가 아니라 "즉시 안 보이게, 30일 뒤 지움"

| 시점 | 무엇을 | 왜 |
| :--- | :--- | :--- |
| **요청 즉시** | **외부 접근 차단** — 링크를 열어도 보이지 않음 | 🔴 **여기를 미루면 안 됩니다.** 닫아달라는 사람의 뜻이 30일간 무시됩니다 |
| **~30일** | 데이터는 **복구 가능 상태로 보관** | 오조작·번복·유족 간 협의 |
| **30일 후** | **완전 파기** | |

> 🔴 **이 구분이 없으면 개인정보보호법의 *"지체 없이 파기"* 원칙과 부딪칩니다.**
> 위 구조는 부딪치지 않습니다 — **처리는 즉시 정지하고 파기만 유예**하는 형태이며,
> **개설자 계정의 개인정보 파기는 유예와 무관하게 탈퇴 즉시** 진행합니다.
> ✅ 흔한 휴지통(soft delete) 패턴이고, `Memorial.closedAt`이 **이미 소프트 삭제**라
> 필드 하나(`purgeAt`)만 더하면 됩니다.

#### 6.3-2 🔴 탈퇴 화면에 고지가 없으면 이 정책은 사고가 됩니다

**사장님이 *"계정 소멸 = 요청에 따른 폐쇄와 동일시"* 로 정하셨습니다. 그대로 갑니다.**
다만 짚어둘 것이 하나 있습니다 — **추모관은 개설자 한 사람의 것이 아닙니다.** 조문객들의
방명록과 다른 유족의 기록이 함께 들어 있고, **그것이 개설자의 탈퇴 한 번으로 사라집니다.**

> 🟡 **정책을 바꾸자는 것이 아니라, 반드시 붙여야 할 것이 있다는 뜻입니다.**
> 🔴 **탈퇴 화면에 *"회원님이 개설한 추모관 N개가 함께 폐쇄됩니다(30일 후 삭제)"* 를 명시하고
> 확인을 받습니다.** 이게 없으면 유족은 **모르고 탈퇴하고, 30일도 모른 채 지나갑니다.**
> 🟡 30일 유예 안내 메일·알림톡을 **폐쇄 시점에 1회** 보냅니다 — 되돌릴 통로가 있다는 것을
> 알려야 유예기간이 의미를 갖습니다.
> ✅ **`Memorial.createdByUser`가 `SetNull`이 아니라 탈퇴가 막히던 문제(§6.1)도 이 확정으로
> 함께 풀립니다** — 이제 탈퇴 시 추모관을 어떻게 할지가 정해졌습니다.

### 8.1 🟡 구현은 **작습니다** — 이 결정이 무거워 보이는 것에 비해

```prisma
model Memorial {
  // ... 기존 유지
  expiresAt DateTime?  // 활성 만료 시점 — 연장 시 갱신
  frozenAt  DateTime?  // 동결 시각. 값이 있으면 쓰기 API 전면 차단(읽기는 유지)
  purgeAt   DateTime?  // 🔵 08-27 추가 — 완전 파기 예정 시각.
                       //   동결 만료(+3년, §5.2-1) 또는 폐쇄 요청(+30일, §6.3)이 채운다
}
```

> ✅ **필드 3개 + 쓰기 경로에 가드 1줄 + 배치**입니다. `Partner.partnerType`(`03-02` §3.1)과
> 같은 **"기본값으로 무해하게 축을 하나 더한다"** 패턴 3회차입니다.
> ⚠️ **단 `frozenAt` 가드는 방명록·헌화·사진 3개 경로에 전부 걸어야 합니다** —
> 한 곳이라도 빠지면 동결이 동결이 아닙니다. **`00-15` §3이 말한 "조용히 깨지는" 유형**입니다.

#### 8.1-1 🔵 08-27 확정으로 늘어난 구현 범위

| 항목 | 내용 | 근거 |
| :--- | :--- | :--- |
| `purgeAt` 배치 | 도래분 완전 파기. 🔴 **통지 실패 기록이 있으면 건너뛴다** | §5.2-1 |
| 파기 전 재확인 통지 | 파기 30일 전 1회. **응답 시 활성 복귀**(`expiresAt` 재설정 + `frozenAt` 해제) | §5.2-1 |
| 폐쇄 유예 | 폐쇄 요청 시 `closedAt`=즉시 · `purgeAt`=+30일. **접근 차단은 `closedAt` 기준** | §6.3-1 |
| 🔴 탈퇴 화면 고지 | *"개설한 추모관 N개가 함께 폐쇄됩니다(30일 후 삭제)"* + 확인 | §6.3-2 |
| 🔴 신고 조치 분리 | **게시물 단위 비공개**를 신설. 지금은 추모관 단위만 있다 | §6.2-1 |
| 신고 사유 코드 | A-1~A-5 · B-1~B-7 · C. **즉시 차단 사유는 한정 열거** | §6.2-5 |

> 🔴 **이 중 "신고 조치 분리"만 성격이 다릅니다** — 나머지는 필드·배치인데 이것은
> **새 모델(게시물 신고)이 필요할 수 있습니다.** 착수 전에 `05-02` §4와 함께 봐야 합니다.
