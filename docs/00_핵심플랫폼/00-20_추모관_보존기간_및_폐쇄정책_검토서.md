# 🕯️ 00-20. 추모관 보존기간 · 폐쇄 정책 — 검토서

> **문서 성격**: 검토서 · **`00-14` §4-3 산출물**. `[Claude:Opus]` 작성(2026-08-18).
> **계기**: 사장님 질문 —
> > *"추모관 및 고인 관련 정보에 대한 너의 의견 듣고 싶어. **내 생각엔 추모관을 폐쇄하는 기준을
> > 만들어야할 거 같아.** 보통, 장례와 함께 소통하는 용으로 이용할거면 3개월이면 충분할 것이고,
> > 가족들이 지속적으로 이용하기 위해서는 장기 유지가 필요할 텐데, **그것을 사용자에게 결정하게
> > 할 것인지..** 등과 관련해서.."*
>
> **정본 관계**: 추모관 기능의 정본은 `05-01`·`05-02`, 링크 모델은 `00-13`,

> **표기**: ✅ 확정 사실 / 🟡 권고 / 🔴 확정 필요 / 🔵 개발자·사장님 확정

## 🔴 2. 먼저 짚을 것 — **하나의 숫자로는 못 정합니다**

사장님 질문은 **"3개월이냐 장기냐"** 라는 한 축인데, **실제로는 세 축이 겹쳐 있습니다.**
**한 숫자를 고르려 하면 반드시 어느 한쪽이 틀립니다.**

### 2.1 축 ①: **부고(07) ↔ 추모(05) — 수명이 정반대입니다**

**`00-13` §2가 이미 이 진단을 해두었습니다** — *"부고 시기와 추모 시기의 링크 요구가 정반대"*.
**보유기간도 정확히 같은 구조입니다.**

| | **부고장(07)** | **추모관(05)** |
| :--- | :--- | :--- |
| 목적 | *"장례가 언제 어디서"* — **행사 안내** | *"고인을 기억하는 곳"* — **기록** |
| 유효 기간 | **발인까지**. 지나면 정보가 **틀린 정보**가 됨 | 길수록 가치 |
| 민감도 | 🔴 **빈소·발인일시·조의금 계좌**(`00-13` §6.3 사기 표적) | 상대적으로 낮음 |
| **적정 보존** | 🟡 **짧을수록 좋음 — 발인 후 1~3개월** | 🟡 **1년 이상** |

> ✅ **사장님이 말씀하신 "3개월"은 부고장 쪽으로는 정확합니다.**
> **틀린 것은 숫자가 아니라 "둘을 같은 것으로 본 것"** 입니다.
> 🔵 **`00-13` E안(부고=봉투 / 추모관=목적지)이 08-14에 확정됐으므로, 보유기간도 그 확정을
> 따라가면 됩니다** — **이미 갈라 놓은 것을 여기서 다시 합칠 이유가 없습니다.**

### 2.2 축 ②: **텍스트 ↔ 사진 — 비용이 두 자릿수 이상 차이 납니다**

**"스토리지 비용" 문제의 실체는 사진 하나입니다.**

| 데이터 | 1건당 대략 | 비고 |
| :--- | :--- | :--- |
| 방명록 10건 + 추모 문구 + 고인 정보 | **수 KB** | DB 텍스트 |
| 추모 사진 10장 | **수 MB ~ 수십 MB** | `MemorialPhoto` |

> ✅ **결론: 텍스트는 사실상 영구 보존해도 비용 문제가 없습니다.**
> **정책이 필요한 것은 사진뿐입니다.**
> 🟡 **이 구분이 실무에서 큰 차이를 만듭니다** — *"1년 뒤 추모관을 지웁니다"* 는 유족에게 잔인하지만,
> *"1년 뒤 사진은 원본 대신 축소본으로 보관합니다"* 는 훨씬 받아들이기 쉽습니다.
> `05-01` §2.6이 *"추모 사진은 유족이 영구 보존을 기대하는 자산"* 이라고 한 것과도 충돌하지 않습니다.

### 2.3 🔴 축 ③: **유족의 데이터 ↔ 조문객의 데이터 — 권리 주체가 다릅니다**

**이 축이 가장 자주 빠지고, 법적으로는 가장 위험합니다.**

방명록에는 **비회원 조문객의 이름**이 들어갑니다(`MemorialGuestbook.authorName`).
이 사람들은 **이어봄 회원이 아니고**, 자기 이름이 언제까지 남는지 **안내받은 적이 없습니다.**

> 🔴 **유족이 *"영구 유지"* 를 선택했다고 해서, 조문객의 개인정보를 영구 보관할 권한이 생기는
> 것은 아닙니다.** 유족은 **자기 정보의 주체이지 조문객 정보의 주체가 아닙니다.**
>
> 🟡 **다만 실무적 해법이 있습니다** — **조문록은 "고인에 대한 기록"으로서 보존하되,
> 일정 기간 후 작성자명을 축약(`홍길동` → `홍*동`)** 하는 것입니다.
> **리드 마스킹(`01-05` §7.3)에서 이미 검증된 패턴**이고, **조문의 의미는 남기고 식별성만
> 낮춥니다.** 조문록의 가치는 *"누가 왔는지"* 보다 *"이만큼 왔다"* 와 **메시지 자체**에 있습니다.

## 📅 3. 🔴 3개월을 권고하지 않는 이유 — **한국 상례의 리듬**

사장님 말씀대로 *"장례와 함께 소통하는 용"* 이라면 3개월로 충분합니다.
**문제는 유족이 추모관을 다시 찾는 시점이 3개월 이후에 몰려 있다는 것입니다.**

| 시점 | 사건 | 3개월 정책이면 |
| :--- | :--- | :---: |
| D+0 ~ D+5 | 장례 | ✅ |
| **D+49일** (약 7주) | **49재** | ✅ |
| D+100일 | 졸곡·백일 | ✅ (턱걸이) |
| **D+1년** | 🔴 **첫 기일(소상)** | ❌ **이미 없음** |
| 설·추석 | 명절 차례 | ❌ **최소 한 번은 못 만남** |
| D+2년 | 대상·탈상 | ❌ |

> 🔴 **가장 나쁜 지점은 "첫 기일"입니다.** 유족이 **1년 만에 다시 찾아왔는데 사라져 있는 것**은
> 서비스가 줄 수 있는 최악의 경험 중 하나입니다. 일반 서비스라면 *"데이터 정책"* 이지만,
> **이 도메인에서는 "고인을 두 번 잃는 것"처럼 받아들여집니다.**
>
> ✅ **1년을 권고하는 이유가 이것입니다 — 임의의 숫자가 아니라 첫 기일을 지나는 최소 기간**입니다.
> 🟡 정확히는 **"첫 기일 + 여유"** 이므로 **13개월**도 후보입니다만, 이용자에게 설명하기 쉬운
> **1년**을 권고하고 **만료 통지를 30일 전에 보내면 실질적으로 13개월**이 됩니다.

## 🤔 4. "사용자에게 결정하게 할 것인가" — **예. 단 시점이 전부입니다**

### 4.1 🔴 개설 시점에 물으면 안 됩니다

**추모관을 개설하는 시점은 유족이 인생에서 판단력이 가장 낮은 며칠 중 하나입니다.**
그 화면에서 *"이 추모관을 얼마나 유지하시겠습니까? (3개월 / 1년 / 영구)"* 를 묻는 것은:

| 문제 | 내용 |
| :--- | :--- |
| **① 답할 수 없는 질문** | 장례 이틀째에 *"1년 뒤에도 이걸 볼 것 같나"* 를 판단할 수 있는 사람은 없습니다 |
| **② 잔인한 질문** | *"3개월"* 을 고르는 행위 자체가 **고인을 3개월짜리로 값매기는 느낌**을 줍니다 |
| **③ 기능이 아니라 부담** | `00-02` 6070 시니어 페르소나에서 **선택지는 배려가 아니라 장벽**입니다 |

> ✅ **그래서 권고는 "묻지 않고 기본값으로 시작"입니다.** 선택권을 없애자는 게 아니라
> **선택 시점을 뒤로 미루자**는 것입니다.

### 4.2 ✅ 물어야 할 시점은 **만료가 다가올 때**입니다

**11개월 뒤에 물으면 위 세 문제가 전부 사라집니다.**

- 유족은 이미 **1년을 지나 판단할 수 있는 상태**입니다.
- *"계속 두시겠습니까"* 는 **더하는 질문**이지 **값매기는 질문이 아닙니다.**
- 실제 사용 여부를 **본인이 이미 알고 있습니다** — 자주 봤으면 연장하고, 안 봤으면 안 합니다.

> 🟡 **문구도 중요합니다.** *"보존기간이 만료되어 삭제됩니다"* 가 아니라
> **"○○○님의 추모관을 계속 열어둘까요?"** — `06-03` §5·`04-02` §6이 세운 문구 원칙과 같은 계열입니다.

### 4.3 🟡 그리고 **연장은 1클릭이어야 합니다**

로그인 → 마이페이지 → 추모관 → 설정 → 연장이면 **아무도 못 합니다.**
**통지 메시지의 링크 한 번으로 연장**되어야 합니다.
🔴 **연장 실패로 사라지는 추모관이 생기면, 정책이 아니라 사고입니다.**

## ❄️ 5. 🟡 핵심 권고 — **만료 시 "삭제"가 아니라 "동결"**

**`00-13` §7.2-3에 이미 나와 있던 아이디어를 여기서 정식 권고로 올립니다** —
*"N년 후 동결 + 정적 스냅샷 보존"*.

### 5.1 왜 동결인가 — **비용은 "보관"이 아니라 "살아 있음"에서 나옵니다**

| | 활성 추모관 | **동결 추모관** |
| :--- | :--- | :--- |
| 방명록·헌화·사진 **추가** | ⭕ | ❌ |
| 기존 내용 **열람** | ⭕ | ⭕ |
| DB 쓰기 부하 | 있음 | **0** |
| 운영 부담(신고 대응·모더레이션) | 있음 | **거의 0** |
| 스토리지 | 원본 | 🟡 **축소본으로 대체 가능**(§2.2) |

> ✅ **동결은 "지우지 않으면서 비용을 거의 0으로 만드는" 상태입니다.**
> 유족에게는 **"남아 있다"** 가 지켜지고, 회사에는 **비용이 안 생깁니다.**
> **이 도메인에서 삭제는 마지막 수단이어야 합니다.**

### 5.2 🟡 권고 3단계

| 단계 | 시점 | 상태 |
| :---: | :--- | :--- |
| **활성** | 개설 ~ **1년** | 전 기능 |
| **동결** | 1년 경과 후(연장 안 함) | **읽기 전용.** 링크는 그대로 살아 있음 |
| **파기** | 🔴 동결 후 **[N년]** — 또는 **개설자 요청 시 즉시** | 완전 삭제 |

> 🔴 **동결 후 N년만 남은 빈칸입니다.** 다만 이 숫자는 **1년보다 훨씬 덜 급합니다** —
> 최초 파기가 발생하는 시점은 **오픈 후 최소 1년 + N년 뒤**이기 때문입니다.
> 🟡 **지금 정하지 말고 "동결까지"만 확정**하시는 것을 권합니다. **그때 가서 실제 데이터 규모를
> 보고 정하는 편이 훨씬 정확합니다.** — 지금 정하면 근거 없는 숫자가 됩니다.

## 🚪 6. 🔴 "폐쇄 기준" — 기간만으로는 부족합니다

**사장님 표현대로 "기준"이 필요한데, 그것은 기간 하나가 아니라 목록입니다.**
**아래 4개 중 2개는 이미 구현돼 있고, 2개는 대비가 없습니다.**

| # | 폐쇄 사유 | 현재 | 처리 |
| :---: | :--- | :---: | :--- |
| 1 | **개설자가 닫음** | ✅ `Memorial.closedAt` | 즉시 비공개(소프트 삭제) |
| 2 | **허위·부적절 신고 접수** | ✅ `Memorial.reportedAt` | 자동 `PRIVATE` 전환 후 운영자 확인 |
| 3 | **보존기간 만료** | ❌ **없음** | 🟡 **§5 — 동결** |
| 4 | 🔴 **개설자 계정 소멸(탈퇴 또는 사망)** | ❌ **없음** | 🔴 **§6.1** |

### 6.1 🔴 4번이 이 문서에서 가장 놓치기 쉬운 항목입니다

> **추모관 개설자도 언젠가 죽습니다. 이어봄에서 이것은 가정법이 아니라 사업 그 자체입니다.**

배우자가 개설한 추모관에서 **그 배우자가 사망하면** 지금 설계로는:

- 연장 통지를 **받을 사람이 없습니다** → 조용히 동결/파기됩니다.
- 자녀가 이어받을 **경로가 없습니다** — `Memorial.createdByUserId`는 **단일 FK**입니다.
- 🔴 **탈퇴 시에도 같습니다.** `Memorial.createdByUser`는 `Lead.userId`와 달리 **`SetNull`이 아니어서**
  탈퇴 자체가 막히거나 추모관이 고아가 됩니다.

> 🟡 **권고: "공동 관리자" 1인 이상을 둘 수 있게 합니다.** `00-12` §2.3 `BereavedRelation`이
> 이미 유족 관계를 모델링하고 있으므로 **새 개념이 아니라 연결**입니다.
> 🔴 **다만 이것은 `Deceased` 확정(`00-12` §2.1)에 걸리므로 지금 설계할 수 없습니다.**
> **이 문서는 "빠져 있다"는 것을 등재하는 데서 멈춥니다** — `05-02` §11에 항목으로 올립니다.

| **동결 후 파기까지 N년** | 🟡 **지금 정하지 않음** — 실제 규모를 보고(§5.2) | — |
| 공동 관리자 | 🔴 **필요하나 `Deceased` 확정 후**(§6.1) | — |

> 🔵 **사장님께 필요한 결정은 실질적으로 2개입니다**:
> **① 활성 기간을 1년으로 할지** ② **만료 시 동결로 갈지(삭제가 아니라)**.

### 8.1 🟡 구현은 **작습니다** — 이 결정이 무거워 보이는 것에 비해

```prisma
model Memorial {
  // ... 기존 유지
  expiresAt DateTime?  // 활성 만료 시점 — 연장 시 갱신
  frozenAt  DateTime?  // 동결 시각. 값이 있으면 쓰기 API 전면 차단(읽기는 유지)
}
```

> ✅ **필드 2개 + 쓰기 경로에 가드 1줄 + 만료 배치**입니다. `Partner.partnerType`(`03-02` §3.1)과
> 같은 **"기본값으로 무해하게 축을 하나 더한다"** 패턴 3회차입니다.
> ⚠️ **단 `frozenAt` 가드는 방명록·헌화·사진 3개 경로에 전부 걸어야 합니다** —
> 한 곳이라도 빠지면 동결이 동결이 아닙니다. **`00-15` §3이 말한 "조용히 깨지는" 유형**입니다.
