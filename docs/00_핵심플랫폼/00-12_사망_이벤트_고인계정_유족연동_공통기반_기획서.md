## 🧩 2. ✅ 핵심 개념 4개

> 개념(무엇을 표현해야 하나)은 이 절이 정본이고, **실제 필드는 `schema.prisma`·`00-05`** 가 정본입니다.

> | :--- | :--- | :--- |

> | `DeathVerification` | `DeathVerification` — **사망했다고 신고된 회원(`subjectUserId`)** + 요청한 지정 유족 기준. 운영자가 장례식장 전화로 확인(`00-41`) | ✅ 있음 · 모양 다름 |
> | `BereavedRelation` | **`FamilyDesignation`**(`00-27`) — 생전 지정 + 수락(`ACCEPTED`). 자칭 유족 모델은 없음 | ✅ 이름 다름 |

### 2.1 `Deceased` — 고인은 문자열이 아니라 엔티티다

고인을 독립 엔티티로 만들고, **이어봄 회원이었으면 그 계정과 연결**합니다.

두 경우를 하나의 모델로 다룹니다.

| 케이스 | 상황 | `Deceased.userId` |
| :--- | :--- | :---: |
| **A. 회원이었던 고인** | 생전에 엔딩노트를 쓰거나 가족을 지정해둔 사람 | 값 있음 |
| **B. 비회원 고인** | 유족이 부고장·추모관만 개설한 경우 (대다수 예상) | `null` |

`Deceased`가 있으면 부고장·추모관이 **같은 고인을 가리킬 수 있습니다.** B 케이스도 자연스럽게 담깁니다 — 계정 없는 고인도 고인입니다.
지금 `Deceased`는 부고장·추모관 개설자가 입력한 이름·날짜만 담습니다(`registeredBy` = 개설자). 🔴 **케이스 A 연결(`userId` 채우기)은 아직 경로가 없습니다** — 사후 개봉(`00-41`)은 `Deceased`가 아니라 `DeathVerification.subjectUserId`로 고인 회원을 가리킵니다.

### 2.2 `DeathVerification` — 사망 확인은 "있다/없다"가 아니라 강도다

`04-01` §3.3은 증빙서류를 안 받기로 했고, `06-01`은 사망진단서를 약속했습니다. **이 둘은 충돌이
아니라 층위 차이입니다** — 행위마다 필요한 확인 강도가 다릅니다. §4에서 사다리로 정리합니다.
실제 모델은 회원(`subjectUserId`) 기준이며 확인 강도 값은 `level = OPERATOR_REVIEWED`(이 문서 §3 값 그대로)를 씁니다.

### 2.3 `BereavedRelation` — 유족에는 두 종류가 있다

| 종류 | 누가 정하나 | 신뢰도 | 권한 | 지금 |
| :--- | :--- | :---: | :--- | :--- |
| **지정 유족** | **본인이 생전에 지정** + 지정받은 사람이 수락 | 높음 | 엔딩노트 개봉 요청 | ✅ `FamilyDesignation`(`ACCEPTED`) — `00-27` |
| **자칭 유족** | 사후에 스스로 주장 | 낮음 | 부고장·추모관 개설·관리 정도 | 별도 모델 없음 — 로그인 회원이면 누구나 개설(L1) |

**이 구분이 §4 검증 사다리의 바탕입니다.** 개념 이름 `BereavedRelation`은 문서에만 있고, 실제로는 만들지 않았습니다(`00-27` §1.2 — 지정자가 살아 있으므로 `Deceased`가 아니라 `User`에 붙음).

### 2.4 `PreDeathDirective` — 생전 위임 (개발자 제안의 자리)

> 개발자 지시(2026-08-12): *"죽기 전의 고인이 정산에 대한 계획을 미리 신청해놓고, 처리 방식을 미리
> 선택하는 선택지를 주는 게 옳지 않나. 1)유족처리 2)행정사처리 3)운영자가 대신처리 를 모두 제공."*

**지금: 모델 없음.** 04(디지털 정산) 백엔드를 2026-09-30 삭제하며 이 자리도 사라졌고, 04는 안내 화면만 남았습니다.
생전 위임의 법적 검토(특히 ③ 운영자 대행)는 **`04-02`가 정본**입니다(§8 #1). 처리 방식 3안 비교와 당시 논거는 부록 경위 B.

## 🪜 4. ✅ 검증 강도 사다리 — 이것이 "검증 체계"의 정본

개발자가 지적한 *"검증이 부족하다"* 의 답입니다. **검증은 도메인별이 아니라 행위의 위험도별**입니다.

| 단계 | 확인 수준 | 어떤 행위에 요구되나 | 근거 |
| :---: | :--- | :--- | :--- |
| **L0** | **없음** | 안내 열람, 추모관 보기·헌화 | 정보 제공·조의 표현일 뿐 |
| **L1** | **자기신고 + 로그인** | 부고장·추모관 개설, 방명록 쓰기 | 확산 제한적, 되돌릴 수 있음 |
| **L2** | **운영자 검토** | (지금 해당 행위 없음 — 추모관 `PUBLIC` 공개 설정은 폐지, `05-01`) | 색인·공개 노출은 위험도가 다른 층 |
| **L3** | **사망 확인** | **엔딩노트 개봉**(운영자 대행은 `04-02` 검토 대상) | 되돌릴 수 없음. 재산·비밀에 접근 |
| **L4** | **L3 + 지정 유족** | 엔딩노트 중 민감 항목 | `06-01`이 화면에서 약속한 수준 |

> ✅ **지금 구현(`00-41`)** — 엔딩노트 개봉은 **지정 유족(`FamilyDesignation` `ACCEPTED`)이 요청**하고 **운영자가 장례식장에 전화로 사망을 확인**합니다(`DeathVerification.method = FUNERAL_HALL`, `level = OPERATOR_REVIEWED`).
> L3를 **서류가 아니라 "서류를 안 보는 경로"** 로 채운 것입니다(`00-16` §4.2 권고 그대로). 서류 기반 확인은 만들지 않았습니다.

### 4.1 이 사다리가 해결하는 것

- **`04-01` §3.3(서류 미수집)과 `06-01`(사망진단서 확인)이 더 이상 충돌하지 않습니다.** 전자는
  L0~L1 행위였고 후자는 L3~L4 행위입니다. **층이 다른 얘기였습니다.**
- 추모관에 게이트가 없다는 `05-02` §6.1 지적도 여기서 풀립니다 — 추모관 개설은 L1이 적정입니다(`PUBLIC` 공개 설정은 없앴습니다).
- **운영자 대행(③)이 왜 어려운지가 분명해집니다** — L3가 필요하고, 대행은 재산에 손대는 일이라 전화 확인만으로 충분한지부터 따로 따져야 합니다(`04-02`).

### 4.2 ✅ L3의 서류를 저장할 것인가 → **`00-16`으로 해소(2026-08-18)**

**결론: 저장하지 않는다.** 확인 사실(누가·언제·어떤 방법으로)만 기록합니다.

- **근거는 "판단"이 아니라 "제약"** — **개인정보보호법 §24조의2**는 법령 근거 없이는 **주민등록번호를 처리할 수 없다**고 정하며, **동의로도 풀리지 않는** 예외입니다. 사망 관련 서류에는 주민등록번호가 인쇄돼 있고 이어봄에는 처리 근거 법령이 없습니다. 상세와 구현 절차는 **`00-16`이 정본**입니다.
- **L3는 ①사망 사실만** 말합니다. **②신청인이 유족인지**는 다른 문제인데, **생전 지정(`FamilyDesignation` `ACCEPTED`)이 있으면 ②는 서류 없이 성립**합니다 — `00-16` §4.2가 그 경로를 **기본값**으로 권고했고 `00-41`이 그대로 구현했습니다.

## 🔐 5. ✅ 고인 계정 처리 정책 — "계속 남겨두는 게 옳은가"

**결론: 그냥 두면 안 되고, 그냥 지워서도 안 됩니다. 새로운 상태가 필요합니다.**

### 5.1 왜 방치하면 안 되나

- 로그인이 살아있습니다 — 비밀번호를 아는 사람이면 누구나 고인 행세를 할 수 있습니다
- 마케팅·알림 발송 대상에 남습니다 (유족에게 2차 상처)
- 개인정보 보유기간이 무기한이 됩니다

### 5.2 왜 삭제해서도 안 되나

- **엔딩노트가 그 계정 안에 있습니다** — 삭제하면 유족에게 전달할 대상이 사라집니다
- 상속·분쟁 대비 기록 보존 필요
- `Lead`·`ConsultRequest` 등 거래 이력이 FK로 물려 있습니다

### 5.3 ✅ 권고 — `MEMORIALIZED`(사망 처리) 상태 신설

```
User.status:  ACTIVE  →  MEMORIALIZED  (사망 확인 L3 완료 시)
```

| | `MEMORIALIZED` 계정의 동작 |
| :--- | :--- |
| 로그인 | **차단** |
| 마케팅·알림 | **전면 중단** |
| 데이터 | **보존** (삭제 아님) |
| 접근 | **지정 유족만**, 사다리 L3~L4를 통과한 행위에 한해 |
| 추모관 | `Deceased.userId`로 연결되어 표시 |

소셜 플랫폼들의 "추모 계정 전환"과 같은 개념이고, `04-01` §4.1의 `actionType: MEMORIALIZE`와도
용어가 맞습니다 — **우리가 남에게 안내하는 처리를 우리 플랫폼에도 적용하는 셈**입니다.

> 🔴 **미구현** — `User`에 상태 칸이 없어 사망 확인(`00-41`) 뒤에도 로그인·알림이 그대로입니다
> (약관 `00-21` 제16조도 보완 대기).
>
> ✅ **2026-10-12 개발자 결정 — 로그인 차단(비활성 계정)만 먼저 구현합니다.** 위 표의 나머지(알림 중단 ·
> 지정 유족 접근)와 **보유기간**은 `00-20`(추모관 보존기간)·`00-11` 인프라 결정(스토리지 비용)과 함께 정합니다.

```prisma
// 사망 확인 — 강도별로 여러 건이 쌓일 수 있다(§4)
model DeathVerification {
  id         String    @id @default(uuid())
  deceasedId String
  level      String    // SELF_DECLARED | OPERATOR_REVIEWED | DOCUMENT_VERIFIED
  reviewedBy String?   // 운영자 확인 시
  verifiedAt DateTime?
  // ⚠️ 서류 파일 자체를 저장하지 않는다 — 파일 경로·이미지·주민등록번호 컬럼 금지(→ 00-16 §4.3)
}

// 유족 관계 — 지정(생전) vs 자칭(사후)(§2.3)
model BereavedRelation {
  id           String  @id @default(uuid())
  deceasedId   String
  userId       String
  kind         String  // DESIGNATED(본인이 생전 지정) | SELF_CLAIMED(사후 자칭)
  relationship String? // 자녀·배우자 등
  designatedAt DateTime?  // DESIGNATED일 때, 본인이 지정한 시각
  @@unique([deceasedId, userId])
}

// 생전 위임 — 본인이 살아있을 때 작성(§2.4)
model PreDeathDirective {
  id         String @id @default(uuid())
  userId     String @unique          // 작성자(생전 본인)
  handlerType String                 // FAMILY | AGENT | OPERATOR (①②③)
  // 대상 플랫폼별 처리 지시는 하위 테이블로
  createdAt  DateTime @default(now())
}
```

실제와 다른 점: `DeathVerification`은 `deceasedId`가 아니라 회원(`subjectUserId`)·요청 지정 유족 기준 · `BereavedRelation`은 만들지 않고 `FamilyDesignation`(`User`에 붙음) · `PreDeathDirective`는 없음 · `Deceased`에는 검증·관계 필드가 없음.

§4 사다리의 08-12 행: L1 = *"추모관 개설(`LINK`), 정리 체크리스트 사용"* · L2 = *"추모관 `PUBLIC` 전환, 유족 관계 자칭 등록"* · L3 = *"서류 기반 사망 확인 — 운영자 대행 신청, 엔딩노트 개봉"*. `PUBLIC`은 폐지됐고(05), 정리 체크리스트(04)는 백엔드 삭제, L3는 서류 대신 장례식장 전화 확인으로 구현(`00-41`).
§4.2의 08-12 절충안: *"운영자가 화면에서 확인하되 서버에 파일을 남기지 않는다 — 또는 단기 보관 후 자동 파기"*. 08-18 `00-16`이 미저장을 "제약"으로 확정.

### D. §6 사용자 여정과 계정 모드 — 08-12 제안 원문

> 개발자 지시(2026-08-12): *"사용자 여정 순으로 재배치와 함께… 이것을 사용자와 엮어서 따로
> 보여주거나 하는 방식은 어떤가? 뭔가 계정별로 나눌 수 있으면 좋을 것 같기도."*

§6.1 기능 칸(당시): 생전 = 엔딩노트, 생전 정산 위임, 지정 유족 설정 · 유족 = 장사시설, 상중·행정, 추모관, 현물 수거, 정산 실행.
`00_DOCS_INDEX`도 이 구분을 인식하고 있었습니다 — *"01~04는 유족이 고인을 위해 쓰는 사후 기능이고, 05만 본인이 자신을 위해 미리 쓰는 생전 기능"*(구 번호 기준). 인식은 했는데 화면에 반영이 안 됐습니다.

§6.2 **C 권고 이유**(당시): `Deceased`를 등록하는 순간(= 추모관 개설, 정산 실행 신청) *"이 사람은 지금 유족이다"* 가 데이터로 확정됩니다. 반대로 엔딩노트를 시작하면 생전 준비 모드입니다. 자동으로 맞춰주되 언제든 수동 전환 가능하게 둡니다. B는 *"단순하지만 전환 존재를 모르면 무용"* 으로 평가했습니다. → 08-19 `00-26`이 홈 진입 + 헤더 모드 드롭다운 + 모드별 사이드바로 구현(§8 #5 닫힘), 자동 판정은 덧붙임 대상으로 남김.

§6.3 메뉴 초안(당시):

```
[내 준비]            ← 생전 준비 모드 (기본: 신규 가입자)
  · 엔딩노트
  · 디지털 자산 정산 계획   ← 생전 위임(§2.4)
  · 지정 유족 설정

[○○○님 보내드리기]   ← 유족 모드 (Deceased 등록 시 자동 활성)
  · 장사시설 찾기
  · 상중 · 행정 케어
  · 온라인 추모관
  · 현물 유품 수거
  · 디지털 자산 정산 실행
  · 상속 · 법률 상담
```

*"유족 모드 헤더에 고인 이름이 들어가는 것이 중요합니다 — 기능 목록이 아니라 '누구를 위한 일인지'가 먼저 보여야 합니다."*

### F. §7.3 — 08-12 권고 → 08-19 사장님 논의 → 08-21 `00-27` 착수

- **08-12 권고(🟡 사장님 상의 대기)**: *"생전 지정 시점에 지정된 유족에게 즉시 통지하면 순환이 끊깁니다. 덤으로 `BereavedRelation`에 없는 '지정당한 사람의 수락' 절차도 생깁니다 — 지금은 본인 동의 없이 남을 지정 유족으로 박아넣을 수 있는 상태입니다."*
- **🔵 2026-08-19 사장님 논의** — *"유언 및 상속과 관련하여, **이용자에게 관련 가족 등의 이름과 연락처를 받고**, 이를 통해 진행될 것으로 기획 예정."*(`03-02` §6.2 답변에 첨부). 연락처가 있으면 이어봄이 사망 이후 먼저 연락할 수 있어 순환이 끊기고, 수락 절차도 만들 수 있습니다.
- **당시 짚은 개인정보 쟁점** — 수집 대상이 이용자 본인이 아니라 **제3자(가족)** 정보입니다.

  | 쟁점 | 내용 |
  | :--- | :--- |
  | 🔴 **동의 주체** | 개인정보보호법상 동의는 **정보주체 본인**이 합니다. **이용자가 가족을 대신해 동의할 수 없습니다.** |
  | 🔴 **수집 고지** | 정보주체(가족)에게 **수집 사실·목적·보유기간을 알려야** 합니다 — 수락 절차와 **같은 동작**입니다. |
  | 🔴 **오·남용** | 지정된 사람이 **실제 가족이 아닐 수 있습니다.** 사망 후 권한이 걸리므로 **잘못 지정된 연락처는 그대로 권한 오지급**입니다. |
  | 🟡 **보유기간** | 사망 이벤트는 **수십 년 뒤**일 수 있습니다. 별도 규칙이 필요합니다(`00-20` 계열). |

  권고: *"지정 즉시 통지를 '부가 기능'이 아니라 '수집의 일부'로 설계하십시오 — 통지가 곧 정보주체 고지, 수락이 곧 동의."*
