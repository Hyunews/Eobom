## 🔍 2. 원인 — 실측

### 2.1 인라인 스타일이 3배 많습니다

```
eobom/frontend/src/**/*.tsx
  style={{  …………………………………  982곳
  className= ……………………………  361곳
```

**미디어쿼리는 스타일시트에만 존재할 수 있습니다.** 인라인 `style` 속성에는 `@media`를 넣을
문법 자체가 없습니다. 즉 지금 화면 요소의 **약 3/4은 폭이 좁아져도 반응할 방법이 없습니다.**

`index.css`에 미디어쿼리가 **9개** 있지만, 이들이 손댈 수 있는 건 `className`을 가진 나머지
1/4뿐입니다. 그래서 *"고쳤는데도 여전히 안 보인다"* 가 반복됩니다 — 고칠 수 있는 부분만
고쳐 왔기 때문입니다.

### 2.2 좁은 폭을 직접 깨뜨리는 값들

인라인으로 **고정 픽셀·고정 단수**를 박아둔 곳이 20개 파일 35곳입니다.

| 패턴 | 무슨 일이 나나 | 대표 위치 |
| :--- | :--- | :--- |
| `minmax(300px, 1fr)` | 375px 화면에서 좌우 여백을 빼면 300px가 안 나와 **가로 스크롤** | `MemorialPage.tsx:80` · `CounselingPage` · `EndingNotePage` |
| `gridTemplateColumns: 'repeat(3, 1fr)'` | 3칸이 그대로 유지돼 숫자·라벨이 **한 글자씩 세로로** 쪼개짐 | `MyPage.tsx:169`(예약중/상담내역/보관문서 카운터) |
| `fontSize: '2rem'` 페이지 제목 | 32px 제목 + 아이콘 32px가 한 줄을 다 먹음 | `CareGuidePage` · `MemorialPage` 등 페이지 헤더 공통 |
| `width: '84px'` 등 고정 | 프로필·아이콘 블록이 안 줄어 옆 텍스트를 밀어냄 | `MyPage.tsx` 프로필 카드 |

### 2.3 🔵 이미 잘 돼 있는 것 — 여기는 손대지 않습니다

**`ObituaryLandingPage.tsx`(조문객이 카톡으로 여는 화면)는 모바일 우선으로 작성돼 있습니다.**
`maxWidth: 360~480px` 중앙 정렬 카드 구조라, 넓은 화면에서 카드가 가운데 놓일 뿐 좁은 화면에서
깨지지 않습니다(08-21 `부고장페이지_최적화` 커밋 반영분 포함).

> ✅ **이게 중요한 근거입니다.** 이 프로젝트가 모바일을 못 하는 게 아니라, **모바일을 전제로 쓴
> 화면만 모바일에서 멀쩡합니다.** 나머지는 데스크톱을 보며 인라인으로 쌓아 올렸습니다.

## 🛠️ 6. 전환 방식 — 세 단계

### 6.1 1단계 · 반응형 프리미티브를 `index.css`에 만든다 (선행 1회)

페이지를 고치기 전에, **페이지들이 공통으로 반복하는 4가지 패턴**을 클래스로 뽑습니다.
이게 없으면 페이지마다 다른 브레이크포인트를 쓰게 되고, 그게 지금 상태의 재생산입니다.

| 클래스 | 대체하는 인라인 패턴 | 동작 |
| :--- | :--- | :--- |
| `.page-title` | `fontSize:'2rem'` 페이지 헤더 | `clamp(1.4rem, 5vw, 2rem)` |
| `.auto-grid` | `minmax(300px,1fr)` | `minmax(min(280px, 100%), 1fr)` — **100% 폴백이 가로 스크롤을 막는 핵심** |
| `.stat-row` | `repeat(3,1fr)` 카운터 | ≤480px에서 3열 유지하되 숫자/라벨 축소 (~~≤360px 1열~~ → 아래 🔄) |
| `.stack-sm` | `display:flex` 가로 배치 카드 | ≤640px에서 `flex-direction: column` |

> ⚠️ **브레이크포인트를 새로 만들지 않습니다.** `index.css`가 이미 쓰는 **480 / 640 / 768**
> 세 개만 씁니다(현재 9개 미디어쿼리가 이 값들을 씁니다). 네 번째 값을 도입하는 순간
> 어디서 접히는지 아무도 예측 못 하게 됩니다.
>
> 🔄 **2026-08-25 모순 해소 — `.stat-row`의 "≤360px 1열"은 폐기합니다.** 같은 절이 위에서
> "480/640/768 세 개만"이라고 못박고 아래 표에서 네 번째 값(360)을 요구하는 자기모순이었습니다.
> 구현(`index.css:462~483`)은 480 하나로 접었고(walkthrough 55 편차), **그 구현이 맞습니다.**
> 375px 실측에서 3열 유지로도 가로 스크롤이 없습니다(§10) — 1열 폴백은 필요하지 않았습니다.

### 6.2 2단계 · 페이지별 이관 (§5 순서대로)

**한 페이지를 통째로 다시 쓰지 않습니다.** 그 페이지에서 §2.2 표에 걸리는 인라인 값만
1단계 클래스로 바꿉니다. 나머지 인라인(색·여백·정렬)은 그대로 둡니다 — 좁은 폭에서
깨지지 않는 값들이기 때문입니다.

> ✅ **판정 기준을 하나로 둡니다: `375px`에서 가로 스크롤이 생기지 않고 본문 글자가 15px 이상.**
> (375px = iPhone SE/미니 계열 실폭. 이보다 좁은 기기는 대응 대상에서 제외합니다.)

### 6.3 3단계 · 새 코드 규칙 — 다시 쌓이지 않게

🔴 **이관보다 이 규칙이 중요합니다.** 규칙이 없으면 §5를 다 끝낸 다음 달에 같은 상태가 됩니다.

> **새로 쓰는 코드에서 §2.2의 4개 패턴(고정 px 폭 · `minmax(≥300px)` · `repeat(n,1fr)` 고정 ·
> `fontSize ≥ 1.5rem`)은 인라인으로 쓰지 않는다. 1단계 클래스를 쓴다.**
> 색·여백 등 나머지 인라인 스타일은 계속 허용합니다 — **전면 금지는 지키지 못할 규칙입니다.**

## 🔬 11. 2차 원인 — **`rem`의 기준선이 디자인 시스템과 어긋나 있습니다**

### 11.1 `00-09` §2.3의 접근성 토큰이 무효화돼 있습니다

```css
/* index.css */
:root { --base-font-size: 18px; }   /* 00-09 §2.3 "협상 대상이 아님" */
body  { font-size: var(--base-font-size); }   /* ← body만 18px */
/* html은 브라우저 기본값 16px 그대로 */
```

**`rem`은 `body`가 아니라 `html`을 기준으로 계산됩니다.** 그래서 인라인에 쓴 `0.85rem`은
쓴 사람이 의도한 *"본문의 85%"*(=15.3px)가 아니라 **16px의 85% = 13.6px**이 됩니다.
본문 기준선 18px 대비 **76%**입니다.

| 인라인 값 | 의도(18px 기준) | **실제(16px 기준)** | 15px 기준 |
| :--- | :---: | :---: | :---: |
| `0.85rem` (102곳) | 15.3px | **13.6px** | ❌ |
| `0.8rem` (56곳) | 14.4px | **12.8px** | ❌ |
| `0.78rem` (17곳) | 14.0px | **12.5px** | ❌ |
| `0.75rem` (20곳) | 13.5px | **12.0px** | ❌ |

> 🔴 **6070 시니어를 주 페르소나로 잡고 본문 18px를 "협상 대상이 아니라"고 문서에 못박아 둔 채,
> 실제 화면의 본문은 12~13.6px로 나가고 있었습니다.** 이게 "모바일 가독성"의 진짜 몸통입니다.
> 모바일 전용 문제도 아닙니다 — 데스크톱도 같은 크기이고, 화면이 작아 먼저 티었을 뿐입니다.

### 11.2 §2.1의 진단을 일부 정정합니다

08-21은 *"인라인 스타일 982곳이라 미디어쿼리가 구조적으로 불가능"* 이라고 썼습니다.
**폰트에 한해서는 반은 틀렸습니다.**

```
fontSize 인라인 선언 …………………… 377곳
  ├ rem 단위 ………………………………… 377곳  (100%)
  └ px 단위 …………………………………… 0곳
```

**전부 `rem`입니다.** 상대 단위이므로 **루트 폰트 한 줄을 바꾸면 377곳이 전부 따라 움직입니다.**
"982곳을 하나씩 이관해야 한다"는 08-21의 비용 추정은 폰트 부분에 대해서는 과대평가였습니다.
(레이아웃 쪽은 §12.2 표대로 사정이 다릅니다.)

## 🛠️ 12. 조치 — 3개. 안전성은 실측으로 확인했습니다

### 12.1 무엇을 하는가

| | 조치 | 내용 | 규모 |
| :---: | :--- | :--- | :--- |
| **A** | **루트 기준선 정렬** | `@media (max-width:768px) { html { font-size: var(--base-font-size); } }` — 모바일에서 `1rem`을 18px로. 효과 ×1.125 | **1줄** |
| **B** | **최소 티어 상향** | 인라인 `0.7`·`0.75`·`0.78`·`0.8rem` → **`0.85rem`**. A만으로는 이 티어가 12.6~14.4px로 여전히 미달 | **97곳** (0.7:4 / 0.75:20 / 0.78:17 / 0.8:56) |
| **C** | **재발 방지 규칙** | §6.3에 *"본문 텍스트는 `0.85rem` 미만으로 쓰지 않는다"* 추가 + `00-09` §2.2에 기준선 규칙 등재 | 문서 |

**A+B 적용 후 본문 최소값 = 0.85rem × 18px = 15.3px** → §6.2 판정 기준 ②를 만족합니다.

### 12.2 부작용 — 무엇이 같이 움직이나

루트를 올리면 `rem`으로 쓴 것이 전부 따라 커집니다. 무엇이 `rem`이고 무엇이 `px`인지 실측했습니다.

| 속성 | rem | px | 조치 A의 영향 |
| :--- | :---: | :---: | :--- |
| `fontSize` | **377** | 0 | ✅ 의도한 효과 |
| `padding` / `margin` / `gap` | **869** | 0 | 🟡 여백도 +12.5% — §13 스크롤 길이로 되돌아옴 |
| `width` / `height` | 1 | **130** | ⚠️ **안 커짐** — 고정폭 박스 안에서 글자만 커져 넘칠 수 있음 |
| `borderRadius` | 0 | 163 | 무관 |

### 12.3 실측 — 루트를 키워도 레이아웃이 깨지지 않습니다

배포본 프레임에서 루트 폰트만 바꿔가며 재계측했습니다(375px 고정).

| 배율 (루트) | 가로 오버플로 | 텍스트 잘림 | 15px 미만 텍스트 | 문서 높이 |
| :---: | :---: | :---: | :---: | :---: |
| ×1.0 (16px, 현재) | 0 | 0 | 160 / 227 | 19,698px |
| **×1.125 (18px, 조치 A)** | **0** | **0** | — | 약 +11% |
| ×1.15 (18.4px) | 0 | 0 | 97 / 227 | 21,900px |
| ×1.2 (19.2px) | 0 | 0 | 67 / 227 | 23,899px |

> ✅ **어느 배율에서도 가로 오버플로 0, 텍스트 잘림 0입니다.** §12.2의 ⚠️(고정 px 박스 넘침)는
> 이론적 위험이었고 실제로는 발생하지 않았습니다 — 폭이 `%`인 컨테이너가 대부분이기 때문입니다.
> ❗ ×1.15에서도 97곳이 남는 이유가 **조치 B가 필요한 근거**입니다. 루트만으로는 안 됩니다.

### 12.4 왜 데스크톱은 건드리지 않는가

조치 A를 전역으로 걸면 여백 869곳이 데스크톱에서도 +12.5% 늘어나, **2026-08-11에 "한 화면에
담기는 정보가 너무 적다"고 판단해 25~30% 줄인 결정**(`00-09` §2.4)을 되여는 일이 됩니다.
지적은 모바일에 대한 것이므로 **모바일에만 겁니다**(§8 #5).
