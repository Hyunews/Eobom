## ✅ 2. 이 제안이 해결하는 것

### 2.1 `00-12` §6.2의 미결을 푼다 — **B안의 유일한 약점을 구조로 없앱니다**

`00-12` §6.2는 모드 전환 방식을 3안으로 비교하고 **개발자 확정 대기**로 남겨뒀습니다(§8 #5, *막는 것: **"프론트 전반"***).

| 안 | 방식 | `00-12`의 평가 |
| :--- | :--- | :--- |
| A | 계정 유형 분리 | ❌ 한 사람이 둘 다 필요합니다 |
| B | **수동 모드 전환** | 🟡 단순하지만 **전환 존재를 모르면 무용** |
| C | 컨텍스트 자동 + 수동 | ✅ 권고 — `Deceased` 등록으로 자동 판정 |

🔵 **개발자 제안은 B안이되, 기각 사유가 성립하지 않습니다.** B안이 밀린 유일한 이유가 *"전환 존재를 모르면 무용"* 인데, **4박스가 첫 화면이면 전환 존재를 모를 수가 없습니다** — 선택이 곧 진입이기 때문입니다. **화면 구조가 B안의 약점을 제거합니다.**

### 2.2 🔵 `Deceased` 의존을 끊는다 — **이것이 가장 큰 실익입니다**

C안 권고의 자동 판정은 **`Deceased` 등록**(추모관 개설·정산 실행)을 신호로 씁니다. 그런데 **`Deceased`는 현재 04·05·07을 전부 묶고 있는 블로커**입니다(`context.md` "지금 막고 있는 것", `00-13` §4.5-3).

> 🔵 **즉 C안은 "블로커가 풀려야 만들 수 있는" 안이었습니다.**
> 개발자 제안은 **데이터로 추론하는 대신 사용자가 직접 고르게** 하므로 **지금 만들 수 있습니다.**
> ⚠️ 다만 이건 **C안의 폐기가 아니라 선후 배치**입니다 — `Deceased`가 확정되면 자동 판정을 **덧붙일** 수 있고, 그때 수동 선택은 그대로 남습니다(= C안의 "수동" 부분).

### 2.3 홈의 경로 이중화가 해소된다

`00-23` §5.3이 지적한 문제 — **같은 목적지로 가는 경로가 홈에 2개**(4박스 / 사이드바) — 가 사라집니다. 홈에서 메뉴를 걷어내면 **4박스가 유일한 진입점**이 됩니다.
