## 🔴 3. 넓히기 전에 그어야 할 3개의 선

> *"거의 모든 것을 다룬다"* 는 요구는 옳습니다. 다만 **무엇을 다루는가**를 먼저 정의해야 합니다.

### 3.1 🔴 첫 번째 선 — **상태는 다루고, 내용은 보지 않는다**

이어봄이 보관하는 것 중 **운영자도 봐서는 안 되는 것**이 있습니다.

| 자산 | 운영자가 볼 수 있는 것 | 🔴 볼 수 없는 것 | 근거 |
| :--- | :--- | :--- | :--- |
| 유족 메시지(편지) | 존재 여부 · 건수 · 만료일 · 삭제 상태 | 🔴 **본문**(`bodyEnc`) | `06-05` §8 Phase B |
| 음성 | 존재 여부 · 용량 · 만료일 | 🔴 **재생·다운로드** | `06-05` §5.6-1 |
| 엔딩노트 | 섹션 완료 수 · 상태 | 🔴 **항목 내용** | `06-03` §7 `select` 명시 규칙 |
| 회원 개인정보 | 🟡 **필요할 때만**, 기록을 남기고 | — | §3.2 |

- 🔴 **이 선은 "안 보여주기"로 지키지 않습니다.** 화면에서 감춰도 API가 내려주면 새는 것입니다.
  `06-03` §7의 **`select` 명시 규칙**(응답에 담을 필드를 일일이 적는다)을 **운영자 API 전체에 적용**합니다.
- 🔵 이 선이 있어야 *"거의 모든 것"* 이 안전하게 성립합니다. 운영자 콘솔은 **내용 열람 도구가 아니라
  상태 관리 도구**입니다.

### 3.2 🔴 두 번째 선 — **조회도 기록한다** (`AdminAuditLog` 신설)

`GET /admin/users/:id`는 **회원 1명의 개인정보를 여는 API**인데 **누가 언제 누구를 열었는지 기록이 없습니다.** 화면이 없어서 지금까지 문제가 안 됐을 뿐이고, §4에서 회원 관리 화면을 만들면 그날부터 실제 열람이 시작됩니다.

**남길 것**: 운영자 ID · 시각 · 행위(`VIEW`/`APPROVE`/`REJECT`/`SUSPEND`/`PURGE` · 이후 추가 `HIDE`/`UNHIDE`(09-30 추모관 내리기) · `MEMORIALIZE`(10-12 사망 확인 → 회원 로그인 차단, `00-12` §5.3)) · 대상 종류 · 대상 ID · 사유(선택 — 🆕 단 **회원 상세 `VIEW`는 필수**, §7 #1 10-15). 정본 목록 = `schema.prisma` `AdminAuditLog.action` 주석(`00-05` 자동 생성)
🔴 **대상의 내용은 로그에 남기지 않습니다** — 로그가 두 번째 유출 경로가 됩니다.

> 🔵 09-07에는 *"`FarewellPurgeAuditLog`를 일반화할지, 나란히 둘지"* 를 §7 #2로 남겼고 → ✅ **신설 + 파기 로그는 그대로**로 구현됐습니다(아래).

> ✅ **현행(10-07 코드 대조 · `00-42` §5.1 ②·§9 반영)** — `AdminAuditLog` **신설 + 파기로그는 그대로**(§7 #2 권고대로).
> - **남기는 칸 추가**: IP(프록시 뒤 실제 주소) · 결과(`SUCCESS`/`FAIL` — 응답 4xx·5xx면 FAIL) · 요청 번호(접속·오류 기록과 연결).
>   행동 추가: `LOGIN`·`LOGIN_FAIL`·`LOCKED` · `LIST`·`VIEW`·`CREATE`·`UPDATE`·`DELETE` · `HIDE`·`UNHIDE`.
> - **자동화**: 핸들러마다 한 줄이 아니라 **운영자 라우터 미들웨어 한 곳**(`adminRoutes.ts` `router.use(adminAudit)`) — 새 엔드포인트도 기록에서 빠지지 않는다.
> - 🔴 **열람 기록 실패 시 응답 거부**: 성공한 조회(GET)는 기록이 DB에 들어간 뒤에 응답을 내보내고, 기록을 못 쓰면 **503**.
>   예외 = `/me`(본인 세션 확인 — 막히면 로그인 불가) · 오류 응답(내보낼 개인정보 없음) · 쓰기 요청(응답 뒤 기록).
> - **보관 2년**(`00-42` §9 #2) — 파기 배치가 지난 행을 지운다. 요청·응답 본문은 담지 않는다(위 🔴와 같은 원칙).

### 3.3 🔴 세 번째 선 — **권한 등급 2단계**

✅ **구현** — `Admin.role`(기존 계정은 `SUPERADMIN`). 확인된 사용처: 사망 확인의 `OTHER` 방법은 `SUPERADMIN`만(`00-41` §5.2). 그 밖에 어느 기능을 `SUPERADMIN`으로 묶을지는 아래 표가 기준입니다.
(09-07 당시: 운영자 계정이 하나의 등급이고 그 계정으로 **파기 실행**까지 됐습니다. 파기는 되돌릴 수 없습니다.)

| 등급 | 할 수 있는 것 |
| :--- | :--- |
| `OPERATOR` (운영) | 심사(사업자·전문가·클레임) · 조회 (🔄 10-14: "신고 처리" 삭제 — 신고 기능 09-29 폐지, `00-21` 제14조) |
| `SUPERADMIN` (최고) | 위 전부 + **파기 실행** · **회원 정지/탈퇴 처리** · **정산·수수료 값 변경** · 운영자 계정 관리 |

🔵 계정이 몇 개 없더라도 등급은 지금 넣는 편이 쌉니다 — 나중에 넣으면 **모든 엔드포인트를 다시 훑어야** 합니다.

🆕 **화면 표시(2026-10-19 디자인 개편 6단계 묶음 3·4 점검 · 2026-10-21 반영)**
- `SUPERADMIN`만 하는 일엔 **열쇠 그림**, 왼쪽 메뉴 아래 범례 *"SUPERADMIN만"*, 이름 아래 등급 글자.
- `OPERATOR`로 들어오면 그 메뉴·버튼을 **숨기지 않고 흐리게**(눌리지 않음) + *"SUPERADMIN만"* — 숨기면 왜 없는지 알 수 없다. 열쇠는 그대로 남긴다.
- 🔴 **열쇠는 위 표에 적힌 것에만** 붙인다: 파기 실행([선택 파기] · 창 안 [파기 실행]) · 회원 [정지] [탈퇴 요청 처리] · 요율 [등록]·[저장](**메뉴는 `OPERATOR`도 열어 본다** — 막는 것은 "값 변경"뿐) · 운영자 계정(메뉴째 · [비밀번호 변경] · 🆕 [등급 변경] · 창 안 [변경]) · 사망 확인 *"기타"* 방법(`00-41` §5.2).
- 열쇠를 **붙이지 않는 것**: 사업자·전문가 [정지]·[해제](심사 일 — `SUPERADMIN`만 하는 것은 **회원** 정지) · 추모관 보존기간 [동결]·[연장](표에 없음).

## 🔐 5. 접근 분리 검토 — *"`/admin` 아닌 별개의 페이지"*

### 5.1 🔴 먼저: 지금 방식의 한계

현재는 *"어디에도 링크하지 않고 직접 URL로만"* 입니다. 이것은 **은폐이지 차단이 아닙니다.**

🔴 **더 중요한 사실** — `AdminPage.tsx`는 **일반 사용자와 같은 프론트 번들에 함께 빌드됩니다.**
경로를 바꿔도 **번들 안에 운영자 화면 코드와 API 경로 문자열이 그대로 들어 있습니다.**
누구나 받아볼 수 있습니다. 그러니 **경로 변경만으로는 얻는 것이 거의 없습니다.**

### 5.3 🔴 순서 — 지금 할 수 있는 것과 없는 것

**B·C는 인프라 확정 대기에 종속됩니다.** 도메인·배포 위치가 `pending-approvals.md`에서 대기 중이고, 백엔드는 Render `oregon`↔DB 서울로 갈려 있어 **이전이 예정된 상태**입니다. 지금 서브도메인을 붙이면 **이전 때 두 번 일합니다.**


🔵 **①②③이 오히려 실질 보안입니다.** ④⑤는 노출면을 줄이지만, 가드 누락 한 줄과 기록 없는 열람은
서브도메인을 나눠도 그대로 남습니다.

✅ **①②③은 끝났습니다**(10-12 코드 확인 — 머리 블록). ④⑤⑥은 인프라 결정(`pending-approvals` "인프라 전략 확정") **대기**.
