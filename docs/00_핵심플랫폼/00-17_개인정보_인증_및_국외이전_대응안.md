## 🏛️ 2. ISMS/ISMS-P 의무대상 여부

### 2.1 근거 법령과 현행 규모

| 항목 | 내용 |
| :--- | :--- |
| 근거 법 | **정보통신망법 §47**(ISMS) · **개인정보보호법 §32조의2**(ISMS-P) |
| 현행 의무대상 규모 | **2026-02 기준 593개사** |
| 미인증 시 | **과태료 3,000만원** |

의무대상은 **매출액·이용자 수·업종**으로 정해집니다. 이어봄은 **오픈 전이며 매출·이용자가 0**입니다.
정보통신서비스 제공자 기준(매출·일평균 이용자 수) 어디에도 걸리지 않습니다.

### 2.2 🔴 인증체계 개편이 진행 중입니다 — 이것 때문에 "지금 아님"으로 끝내면 안 됩니다

| 항목 | 내용 |
| :--- | :--- |
| 개편 방향 | 인증체계를 **강화(Advanced) · 표준(Standard) · 간편(Lite) 3단계**로 재편 |
| 개편 의무대상(안) | 주요 공공시스템운영기관 · 이동통신사업자 · 본인확인기관 · **매출액과 처리하는 개인정보 수를 고려한 대규모 개인정보처리자** |
| 강화 인증군(안) | **매출 1조원 이상 주요 ISP·IDC**, **매출 3조원 이상 정보통신서비스 제공자** |
| 시행 일정(안) | 사후관리 **2026 하반기**부터 / **의무화·차등 적용은 2027년부터** |
| **확정 여부** | 🔴 **미확정.** 개인정보보호법 **시행령**과 보호위원회 **고시**로 확정될 예정 |

> **개편안 기준으로도 이어봄은 대상이 아닙니다.** 강화군의 문턱이 조 단위 매출이고, 표준·간편의
> 문턱도 *"대규모 개인정보처리자"* 입니다. **다만 그 "대규모"의 숫자가 아직 안 나왔습니다.**
> → 그래서 §5의 재확인 트리거가 필요합니다. **"오픈 전 확인"으로는 부족합니다** — 오픈 시점과
> 시행령 공포 시점이 어긋나면 확인이 헛돌기 때문입니다.

### 2.3 CSAP는 별개입니다 — `00-11` §5.2가 같이 묶어 놓은 것을 갈라둡니다

`00-11` §5.2 ⚠️ 는 *"공공기관 연계 시 CSAP 필요 여부"* 를 ISMS-P와 한 문장에 묶었는데, **성격이 다릅니다.**

| | ISMS-P | CSAP |
| :--- | :--- | :--- |
| 누가 받나 | **서비스 사업자**(= 이어봄) | **클라우드 사업자**(= NCP·AWS 등) |
| 이어봄에게 | 의무대상이면 **직접 받아야 함** | **받은 사업자를 고르면 되는 것** |
| 언제 문제되나 | 규모 요건 충족 시 | **공공기관에 서비스를 납품할 때** |

> ✅ **이어봄은 B2C·B2B(장사시설·전문가) 서비스이지 공공 납품 사업이 아닙니다.**
> `01-02`가 다루는 **공공데이터 이용은 "데이터를 받아오는 것"이지 "공공기관에 시스템을 파는 것"이
> 아니므로 CSAP 논점이 생기지 않습니다.** → **CSAP는 현재 검토 대상에서 내립니다.**
> 공공 조달을 사업 방향으로 잡을 때 되살리면 됩니다(그때는 사업자 선택 기준에 한 줄 추가하는 일).

## 🌏 3. 국외이전 — `00-11` §5.2 서술을 정정합니다

### 3.1 무엇이 부정확했나

`00-11` §5.2 원문: *"개인정보의 국외 이전에는 **별도 고지·동의 등 추가 의무가 따릅니다**."*

**"별도 동의"를 기본값처럼 적은 것이 부정확합니다.**
**개인정보보호법 §28조의8**은 국외 이전의 **근거를 5가지**로 열어두었고, 동의는 그중 하나일 뿐입니다.

| 이전 근거 | 별도 동의 | 이어봄 해당 |
| :--- | :---: | :--- |
| ① 정보주체의 **별도 동의** | 필요 | — |
| ② **법률·조약**에 규정 | 불요 | — |
| ③ **계약의 체결·이행을 위해 필요한 처리위탁·보관** | **불요** — **개인정보처리방침 공개 등으로 갈음** | ✅ **여기에 해당** |
| ④ 이전받는 자가 **§32조의2 인증(ISMS-P 등)** 을 받고 안전조치·권리보장 조치를 이행 | 불요 | 🟡 보조 근거 |
| ⑤ 이전 대상국의 보호수준이 국내와 동등하다고 **보호위원회가 인정** | 불요 | — |

> ✅ **따라서 "AWS 해외 리전 = 불법"이 아닙니다.** 클라우드 호스팅은 전형적인 ③(처리위탁·보관)이며,
> **처리방침에 공개하면 별도 동의 없이 적법**합니다. 국내 기업들이 해외 리전을 쓰는 근거가 이것입니다.

### 3.2 그래도 ③에는 **조건**이 붙습니다 — 공짜가 아닙니다

③으로 가려면 **개인정보처리방침에 국외이전 사항을 공개**해야 합니다. 공개할 항목은 실무상 다음입니다.

1. 이전되는 **개인정보 항목**
2. 이전되는 **국가·시기·방법**
3. 이전받는 자의 **명칭·연락처**
4. 이전받는 자의 **이용 목적·보유 기간**

**즉 ③은 "아무것도 안 해도 된다"가 아니라 "동의 대신 공개를 한다"입니다.**
🔴 **그런데 이어봄에는 그 처리방침 문서가 아직 없습니다**(§3.4).

### 3.3 그래서 국내 리전 권고는 **유지하되, 근거를 바꿉니다**

`00-11` §5.2 마지막 문장은 이미 옳게 적혀 있었습니다 — *"국내 리전을 쓰면 이 논점을 아예 만들지
않습니다."* **이 문장이 진짜 근거이고, 앞 문장(위법 프레임)이 군더더기였습니다.**

| 프레임 | 평가 |
| :--- | :--- |
| ❌ *"국외는 위법이라 국내로 간다"* | **틀림.** 정정 대상 |
| ✅ *"국외도 적법하지만, 공개 항목·사업자 실사·문의 대응이 늘어난다. 국내 리전이면 그 일이 통째로 없다"* | **채택** |

> 🟡 이 구분이 실무에서 중요한 이유: **위법 프레임으로 적어두면 "해외 SaaS는 무조건 못 쓴다"는
> 잘못된 운영 규칙이 파생됩니다.** 실제로는 §3.4처럼 **이미 쓰고 있고, 앞으로도 쓸 수밖에 없는
> 국외 요소가 있습니다.** 규칙이 현실과 어긋나면 규칙이 무시됩니다.

### 3.4 🔴 현행·계획 스택의 국외 요소 점검 — **이미 국외 요소가 있습니다**

`00-11` §5.1은 **프론트엔드는 Vercel 유지**를 권고했고, 현재 배포 계획(`render.yaml`)은 백엔드·DB가
Render입니다. 둘 다 해외 사업자입니다. **"국내 리전 권고"만 적어두면 이 부분이 점검에서 샙니다.**

| 요소 | 현재/계획 | 개인정보가 지나가나 | 처리 방향 |
| :--- | :--- | :--- | :--- |
| **Vercel** (프론트) | `00-11` §5.1 **유지 권고** | 🟡 정적 자산 배포. 다만 **접속 로그·IP**는 남음 | 🟡 처리방침 **국외이전 항목에 등재**. 민감정보는 백엔드에만 |
| **Render** (백엔드+DB) | `render.yaml` — **`plan: free`** | 🔴 **전부 지나감** | ✅ `00-11` §4.1이 이미 **프로덕션 부적합**으로 판정(백업 없음). **§7 단계 4에서 교체** |
| **소셜 로그인 3사** | 카카오·네이버(국내) / **구글**(국외) | 🟡 프로필·이메일 | 🟡 **구글은 국외이전 등재 대상.** `00-08` 연동 |
| **카카오맵 JS SDK** | `VITE_KAKAO_MAP_KEY` | 국내 | — |
| **Unsplash 외부 이미지** | 목업 추모 사진(`00-14` §2.2) | ❌ 개인정보 아님 | ✅ **다른 이유로 이미 제거 대상**(`00-14` §2.2 — 프로덕션이 외부 호스트에 의존) |

> ✅ **가장 중요한 결론**: **국외이전 논점의 실질적 해소는 "국내 리전 선택"이 아니라
> "Render 이탈"입니다.** `00-11` §7.1 단계 4가 그 일이며, **이 문서는 새 과제를 만들지 않고
> 기존 이행 계획에 국외이전 사유를 하나 더 붙일 뿐입니다.**
> **Vercel은 남습니다** — 그래서 **국외이전 공개 항목은 어차피 0이 되지 않습니다.** §4.2가 필수인 이유입니다.

> 🔴 **①이 §2(인증)보다 훨씬 급합니다.** 인증은 *"우리 규모면 언젠가"* 이지만,
> **처리방침은 화면이 이미 있다고 말하고 있고, 국외이전의 적법 근거이며, 오픈 시점에 없으면
> 그 자체로 위반**입니다. **`00-14` §2가 잡아낸 "화면이 약속했는데 뒷받침이 없음"과 같은 종류이고,
> §2 전수조사가 `HomePage`·`EndingNotePage` 계열만 훑느라 `Footer`를 안 봐서 빠진 건입니다.**

> 🟡 **①②는 이 문서의 범위가 아니라 별도 문서(`00-18` 후보)입니다.** 여기서는 **등재만** 합니다 —
> 한 문서가 두 일을 하면 둘 다 낡습니다.

## ⏰ 5. 재확인 트리거 — **"오픈 전 확인"을 대체합니다**

`00-11` §5.2의 *"오픈 전 전문가 확인"* 은 **시점이 우리 사정(오픈)에 묶여 있어 헛돕니다.**
기준이 바뀌는 시점은 **법령 쪽 사정**이므로, 트리거를 그쪽에 겁니다.

| # | 트리거 | 무엇을 재확인 | 확인 주체 |
| :---: | :--- | :--- | :--- |
| **T1** | **개인정보보호법 시행령·보호위 고시로 인증체계 개편이 확정될 때(2027 예정)** | *"대규모 개인정보처리자"* 의 **구체적 숫자**. 이어봄이 그 문턱에 근접했는지 | 🔴 외부 |
| **T2** | **누적 회원 또는 처리 개인정보 건수가 유의미한 규모에 도달할 때** | 동일. **숫자가 나온 뒤에는 내부에서 판정 가능** | 내부 |
| **T3** | **국외 사업자 스택이 추가·변경될 때**(결제 PG, 알림, AI API 등) | §3.4 표 갱신 + **처리방침 국외이전 항목 갱신** | 내부 |
| **T4** | **공공 조달·공공기관 연계를 사업 방향으로 검토할 때** | §2.3 CSAP를 되살릴지 | 내부 |

> ✅ **T1·T2는 유료 자문이 필요 없습니다** — 확정된 숫자와 우리 숫자를 비교하는 일입니다.
> 🔴 **유료 자문이 실제로 필요한 것은 이 문서가 아니라 `00-16`(주민등록번호)·`04-02`(대행 적법성)입니다.**
> `00-14` §5의 의뢰 목록에서 **5-4는 우선순위를 내려도 됩니다.**
