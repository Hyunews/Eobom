# 📄 00-16. L3 사망확인 서류 — 검토서

> **문서 성격**: 검토서 · **`00-14` §7-4 산출물**. `[Claude:Opus]` 작성(2026-08-14 조사 / 2026-08-18 문서화).
> **계기**: 개발자 지시 — *"7 기술확인 **권고안대로 가되**, **7-4 L3 서류에 대한 정보가 부족해서
> 문서화해서 검토 필요**."*
> **정본 관계**: 검증 사다리(L0~L4)의 정본은 **`00-12` §4**입니다. 이 문서는 그 사다리의
> **L3 한 칸만** 파고들며, 사다리 자체를 다시 설계하지 않습니다.
> **표기**: ✅ 확정 사실 / 🟡 권고 / 🔴 외부 확인 필요 · 🔵 개발자 확정

> ⚠️ **이 문서는 법률 자문이 아닙니다.** 다만 §3은 **"해석"이 아니라 조문 자체가 금지하는 사안**이라
> 다른 절보다 강한 어조로 씁니다. 그 이유도 §3에 적었습니다.

## 📌 1. 결론 먼저 — 권고가 바뀌지는 않습니다. **근거가 바뀝니다**

| | 검토 전(`00-12` §8-2 · `04-01` §10-2) | 검토 후 |
| :--- | :--- | :--- |
| **권고** | 화면 확인 후 **미저장** | ✅ **동일 — 유지** |
| **근거** | *"민감 서류는 유출되면 회수할 수 없다"* (운영 리스크·되돌리기 쉬운 방향) | 🔴 **개인정보보호법 §24조의2 — 주민등록번호는 법령 근거 없이는 처리 자체가 금지**(§3) |
| **성격** | 절충안·판단 사항 | **선택지가 아님에 가까움** |
| **미결 상태** | `00-12` §8-2 = 사장님·전문가 확인 대상 | 🟡 **사장님 확정 항목에서 내릴 수 있음**(§6) |

> **이 문서가 실제로 바꾸는 것은 두 가지입니다.**
> **① 미저장 권고가 "운영 편의"가 아니라 "법적 요구에 가깝다"로 승격**됩니다(§3).
> **② L3 설계가 "서류 한 장 확인"에서 "시간축 + 두 가지 확인"으로 정밀해집니다**(§2).
> ②가 없으면 **L3는 가장 급한 시점에 작동하지 않습니다.**

## 🗂️ 2. 서류를 먼저 정확히 압니다 — 개발자가 *"정보가 부족하다"* 고 한 부분

### 2.1 서류 4종

| 서류 | 누가 발급 | 무엇을 증명 |
| :--- | :--- | :--- |
| **사망진단서** | 병원 진료 중 사망 시 **담당 의사** | **사망 사실** |
| **시체검안서** | 병원 밖 사망·사고사 등 **검안 의사** | 사망 사실 — **사망진단서와 같은 증명력** |
| **기본증명서(상세)** | 가족관계등록 관서 / 정부24 | **사망 사실**(단, **사망신고 처리 후**에만 기재됨) |
| **가족관계증명서(상세)** | 동일 | **신청인이 유족임** — ⚠️ **사망 증명이 아님** |

### 2.2 🔴 시간축 — **L3를 기본증명서로 설계하면 가장 급한 시점에 작동하지 않습니다**

사망신고는 **의사가 발급한 원본**을 가지고 **관할 읍·면·동에 1개월 내**에 합니다(`07-02` #6).
**신고가 처리되기 전에는 기본증명서에 사망이 뜨지 않습니다.**

```text
D+0 ─────────── D+수일 ─────────── D+1개월
 │                  │                  │
 사망               사망신고            (신고 기한)
 │                  │
 └ 사망진단서·검안서만 존재            └ 이 시점 이후에야 기본증명서에 사망 기재
   (기본증명서로는 확인 불가)
```

> **L3를 요구하는 행위가 무엇이었는지 보면 문제가 분명해집니다** — **엔딩노트 개봉**과
> **운영자 대행**입니다(`00-12` §4). 그리고 **엔딩노트에는 장례 방식·연명의료 의향이 들어갑니다.**
> **D+0~수일 구간에 못 열면 열어야 할 이유의 절반이 사라집니다.**
>
> ✅ **따라서 L3의 1차 서류는 사망진단서·시체검안서이고, 기본증명서는 대체 수단입니다.**
> 순서를 반대로 적으면 안 됩니다.

### 2.3 ✅ 두 가지를 갈라야 합니다 — **한 서류로 둘 다 안 됩니다**

| 확인해야 하는 것 | 서류 | 데이터 모델 |
| :--- | :--- | :--- |
| ① **사망 사실** | 사망진단서 · 검안서 · 기본증명서(상세) | **`DeathVerification`**(`00-12` §3) |
| ② **신청인이 유족임** | **가족관계증명서(상세)** | **`BereavedRelation`**(`00-12` §3) |

> 🔴 **`00-12` §4의 L3는 ①만 말하고 있었습니다.** 그런데 **엔딩노트 개봉을 신청하는 사람이
> 유족이 맞는지는 ②의 문제**입니다. ①만 통과시키면 **"고인이 사망한 것은 맞는데 아무나 열 수 있는"**
> 구멍이 생깁니다.
>
> ✅ **다만 `00-12`가 이미 답을 갖고 있습니다** — **L4 = L3 + 지정 유족 이중동의**이고,
> `BereavedRelation.kind = DESIGNATED`(생전 지정)는 **서류 없이 성립하는 확인**입니다.
> **생전에 지정해두면 ②를 서류로 확인할 필요가 아예 없습니다.**
> → **§4.2의 설계 권고가 여기서 나옵니다.**

## ⚖️ 3. 🔴 미저장 권고의 법적 근거 — **이 문서의 핵심**

### 3.1 조문

**개인정보보호법 §24조의2(주민등록번호 처리의 제한)** — 다음을 **제외하고는 주민등록번호를
처리할 수 없습니다.**

1. **법률·대통령령·국회규칙·대법원규칙·헌법재판소규칙·중앙선거관리위원회규칙·감사원규칙**에서
   구체적으로 주민등록번호의 처리를 **요구하거나 허용**한 경우
2. 정보주체 또는 제3자의 **급박한 생명·신체·재산의 이익**을 위하여 명백히 필요하다고 인정되는 경우
3. 위에 준하여 주민등록번호 처리가 불가피한 경우로서 **보호위원회가 고시로 정하는 경우**

### 3.2 ✅ 이것이 왜 다른 개인정보와 다른가 — **가장 흔한 오해**

| 오해 | 실제 |
| :--- | :--- |
| *"민감정보라도 별도 동의를 받으면 처리할 수 있다"* | 고유식별정보 일반(여권번호·운전면허번호 등)은 그렇습니다 |
| *"그러니 주민등록번호도 동의받으면 된다"* | ❌ **주민등록번호는 예외입니다.** **법령 근거가 없으면 동의를 받아도 처리할 수 없습니다** |

> **✅ 즉 "유족이 동의했으니 괜찮다"는 성립하지 않습니다.**
> 그리고 §2.1의 서류에는 **주민등록번호가 인쇄되어 있습니다.**
> **이어봄에는 이를 처리할 법령 근거가 없습니다** — 금융기관·보험사가 서류를 받을 수 있는 것은
> 각자의 근거 법령이 있기 때문이지, 서류를 받는 업무라서가 아닙니다.

### 3.3 그래서 `00-12` §8-2·`04-01` §10-2의 위상이 바뀝니다

- 종전: *"안 받는 쪽을 기본값으로"* — **되돌리기 쉬운 방향을 고른 판단**(`04-01` §3.3)
- 개정: **"받으면 안 되는 쪽에 가깝다"** — 판단이 아니라 **제약**

> 🟡 **"가깝다"라고 쓴 이유**: 화면에 띄워 **읽는 행위(열람)** 도 개인정보보호법상 "처리"에
> 포함되므로, **엄밀히는 저장뿐 아니라 화면 확인도 논점이 됩니다.** 그래서 §4가 필요합니다.
> **저장을 안 하는 것만으로 끝나지 않습니다.**

## 🛠️ 4. 그럼 L3를 어떻게 구현하나 — 설계 권고

### 4.1 🟡 제출 **전** 마스킹 — 서류를 받되 번호를 받지 않습니다

**주민등록번호가 문제이지 서류가 문제가 아닙니다.** 따라서:

| 단계 | 설계 |
| :--- | :--- |
| **① 안내** | 업로드 화면에서 **"주민등록번호 뒷자리를 가린 뒤 제출하십시오"** 를 **제출 버튼 앞 단계에** 요구. 예시 이미지 제공 |
| **② 제출** | 🟡 **가능하면 파일 업로드 자체를 만들지 않습니다**(§4.3). 불가피할 경우에만 임시 채널 |
| **③ 확인** | 운영자가 **화면으로 확인만** |
| **④ 기록** | **`DeathVerification`에 `level`·`reviewedBy`·`verifiedAt`만.** 파일·번호·이미지는 남기지 않음 |
| **⑤ 파기** | 임시 채널을 썼다면 **확인 완료 시점 즉시 파기**하고 파기 사실을 기록 |

> ⚠️ **①을 "안내 문구"로만 두면 지켜지지 않습니다.** `00-14` §2가 반복해서 확인한 패턴입니다 —
> **화면이 말하는 것과 시스템이 강제하는 것은 다릅니다.** 마스킹은 **제출 단계의 체크박스 확인 +
> 운영자 1차 반려 사유**로 이중으로 걸어야 실효가 있습니다.

### 4.2 ✅ 더 나은 답 — **서류를 안 보는 경로를 기본값으로**

§2.3에서 확인했듯 **생전 지정(`DESIGNATED`)이 있으면 ②(유족 확인)는 서류가 필요 없습니다.**
그리고 ①(사망 사실)은 **운영자 검토(L2)와 결합하면 서류 원본 보관 없이도 확인 가능**합니다.

| 경로 | 서류 | 언제 |
| :--- | :--- | :--- |
| **A. 생전 지정 경로** 🟡 **기본값 권고** | **불필요**(지정 유족 본인확인 + 사망 사실 확인만) | 본인이 생전에 `BereavedRelation.DESIGNATED`를 남긴 경우 |
| **B. 사후 자칭 경로** | 필요 — §4.1 절차 | 지정이 없는 경우 |

> ✅ **이것은 새 설계가 아니라 `00-12`가 이미 만든 구조를 L3에 적용하는 것입니다.**
> **그리고 06(엔딩노트)의 UX 방향과도 맞습니다** — *"미리 지정해두면 유족이 훨씬 수월합니다"* 는
> 생전 작성 유도의 근거가 되고, `04-02` §4(플랫폼 사전지정 안내)·`06-02` §3(연명의료 등록)과
> **같은 형태의 문장**입니다. **세 곳에서 같은 말을 하고 있다면 그게 이 서비스의 핵심 동작입니다.**

### 4.3 ✅ 지금 당장 지켜야 할 구현 제약

`04-01` §8이 이미 *"고인 자격증명·증빙서류 관련 컬럼을 만들지 말 것 — 필드가 없으면 채워질 수
없습니다"* 라고 못 박았습니다. **이 문서는 그 제약을 L3까지 확장합니다.**

- ❌ `DeathVerification`에 파일 경로·이미지·주민등록번호 컬럼을 **만들지 않습니다.**
- ❌ 오브젝트 스토리지에 `death-documents/` 같은 버킷·프리픽스를 **만들지 않습니다.**
- ✅ `00-12` §3의 모델 주석(*"서류 파일 자체는 저장하지 않는 것을 기본으로 한다"*)을 **유지**하되,
  **주석 근거를 `§5`에서 `00-16`으로 갱신**합니다.

## 🔗 5. 경계 정리 — 헷갈리기 쉬운 세 가지

| 건 | 이어봄이 서류를 보나 | 왜 |
| :--- | :--- | :--- |
| **04 계정 정리 안내**(`04-01` §3.3) | ❌ **안 봄** | 유족이 **각 플랫폼에 직접** 제출. L0~L1 행위 |
| **07 안심상속 원스톱**(`07-02` #7) | ❌ **안 봄** | **정부24에서 처리되는 절차**입니다. 이어봄은 **기한 관리와 안내**만 하고 신청을 대행하지 않습니다 |
| **L3 엔딩노트 개봉·운영자 대행** | 🟡 **화면 확인만** | 되돌릴 수 없는 행위. §4 절차 적용 |

> 전제하며, 심사할 사람이 없으면 L3는 **"기능이 없는 것"과 같습니다.**
> `00-14` §6-1(신고 처리 담당자·응답시간)과 **같은 뿌리의 미결**이며, 그쪽이 정해질 때 함께 정해집니다.

> 다만 **`04-02` §7 의뢰 질문지에 한 줄 덧붙이면 되는 수준**이며, 이 건만으로 별도 의뢰를 낼
> 필요는 없습니다.
