### 1.2 🔴 `BereavedRelation`을 그대로 쓸 수 없습니다 — 구조적 발견

`00-12` §2.3의 `BereavedRelation`은 **`deceasedId`를 가집니다.** 즉 **사망 이후 모델**입니다.
그런데 지금 만드는 것은 **생전 지정**이고, 그 시점의 지정자는 살아 있는 `User`입니다.

| 안 | 내용 | 판정 |
| :---: | :--- | :---: |
| **A** | 생전 지정 시 `Deceased` 레코드를 미리 만들어 붙인다 | ❌ **기각** — 살아 있는 사람에게 *"고인"* 레코드가 생깁니다. 이름이 거짓말이 되고, `Deceased`에는 `obituaries`·`memorials`가 매달려 있어 **실수로 부고장·추모관이 걸릴 수 있습니다** |
| **B** | **`FamilyDesignation`을 `userId` 기준으로 신설**하고, 사망 확인 시 `BereavedRelation`으로 **승격** | ✅ **채택** |

> ✅ **B가 `00-12` §2.1과 정확히 맞물립니다.** `Deceased.userId`가 이미 `@unique`이므로,
> 사망 확인 시 **케이스 A(회원이었던 고인)** 로 `Deceased`를 만들고 그때 `FamilyDesignation`을
> `BereavedRelation(kind: DESIGNATED)`로 옮기면 됩니다. **생전/사후 모델이 섞이지 않습니다.**

## 🎯 2. ✅ 핵심 결정 — **기록과 통지를 분리합니다** (2026-08-21 개발자 확정)

> 개발자 확정: *"기록만 먼저, 통지는 본인이 원하거나 사망 확인 시."*

### 2.1 왜 이 분리가 필요했나

`00-12` §7.3은 *"지정 즉시 통지"* 를 권고했지만, 그대로 두면 **엔딩노트를 가족 몰래 준비하는
이용자가 이 기능을 아예 못 씁니다.** 반대로 통지를 아예 없애면 §7.3이 경고한 셋(정보주체 고지 ·
수락 = 동의 · 순환 차단)이 전부 미해결로 남습니다.

**✅ 확정된 해법은 "기록은 하되, 통지 전에는 권한이 0"입니다.**

| 상태 | 뜻 | 권한 |
| :--- | :--- | :---: |
| `DRAFT` | 본인만 아는 기록 | **0** — 사후에도 **자동 권한 없음**(운영자 심사 경로만) |
| `PENDING` | 통지 발송됨, 응답 대기 | **0** |
| `ACCEPTED` | 가족이 수락 | ✅ 지정 유족(`00-12` §2.3) |
| `DECLINED` | 가족이 거절 | **0** — 재지정하려면 다시 통지 |
| `EXPIRED` | 초대 토큰 만료 | **0** |

### 2.2 ✅ 통지 트리거는 **2개**입니다

| # | 트리거 | 누가 보내나 | 무엇을 해결하나 |
| :---: | :--- | :--- | :--- |
| ⓐ | **본인이 원할 때** (마이페이지 *"알리기"*) | 🟡 **본인이 링크 전달**(§8) | 정보주체 고지 + 수락 = 동의 |
| ⓑ | **사망 확인 시** (`DeathVerification` 통과) | 이어봄 | 🔴 **`00-12` §7.3의 순환을 여기서 끊습니다** |

> ✅ **ⓑ가 이 설계의 핵심입니다.** *"유족은 고인의 계정 존재를 모른다"* 는 순환은, 본인이 생전에
> 알리지 않았더라도 **사망이 확인되면 이어봄이 그 번호로 먼저 연락할 수 있으므로** 끊깁니다.
> 즉 **몰래 준비해도 순환 차단은 유지됩니다** — `00-12` §7.3이 즉시 통지를 요구한 이유가
> 여기서 다른 방식으로 충족됩니다.

## 🔴 3. 불변식 — **구현자가 판단하지 않습니다**

| # | 불변식 | 어기면 |
| :---: | :--- | :--- |
| **1** | **`DRAFT`·`PENDING`에는 어떤 권한도 없다.** 사후 자동 승격도 없다 | 잘못 적은 번호가 **엔딩노트 개봉 동의권**이 됩니다(`00-12` §2.3) |
| **2** | **연락처·이메일은 암호화 저장**(`crypto.ts`)하고 **어떤 공개 응답에도 넣지 않는다** | 부고장 연락처와 정반대입니다 — 여긴 **입력=비공개**라 평문 보관이 막는 위협이 실재합니다(`07-03` §4.2 논리의 반대편) |
| **3** | 🔴 **"내가 누군가에게 지정됐는지" 조회하는 API를 만들지 않는다** | 번호만 넣어보며 **남의 지정 여부를 캘 수 있는 조회기**가 됩니다. 가족은 **통지 링크(토큰)로만** 자기 건에 접근합니다 |
| **4** | **법정상속순위를 계산·표시하지 않는다** | 순위 판단은 법률 판단입니다. `priority`는 **연락 순서**일 뿐이며 화면에도 그렇게 적습니다 |
| **5** | **본인은 언제든 삭제할 수 있다**(하드 삭제) | 보유기간 규칙이 서기 전까지 이것이 **유일한 최소 방어**입니다(§7) |

## 🗄️ 4. 데이터 모델

```prisma
// 생전 가족지정 — 00-27. 지정자가 아직 살아 있으므로 Deceased가 아니라 User에 붙는다(§1.2)
model FamilyDesignation {
  id              String    @id @default(uuid())
  userId          String                        // 지정한 본인(생전)
  user            User      @relation(fields: [userId], references: [id], onDelete: Cascade)

  name            String                        // 가족 성함
  phoneEnc        String                        // 🔴 AES-256-GCM 암호문(불변식 2)
  phoneHash       String                        // 중복 지정 방지용 인덱스 — 아래 §4.1
  emailEnc        String?                       // 선택. 연락수단 이중화(§5 ⑥)
  relationship    String                        // SPOUSE|CHILD|PARENT|SIBLING|OTHER
  relationshipEtc String?                       // OTHER일 때만
  scope           String    @default("VIEWER")  // PRIMARY | VIEWER (§6)
  priority        Int       @default(1)         // 연락 순서. ⚠️ 상속순위 아님(불변식 4)

  status          String    @default("DRAFT")   // DRAFT|PENDING|ACCEPTED|DECLINED|EXPIRED
  inviteToken     String?   @unique             // 통지 링크 토큰(Phase 2). 추측 불가
  tokenExpiresAt  DateTime?                     // 초대 링크 만료 시각. 지나면 status=EXPIRED
  notifiedAt      DateTime?                     // 통지를 보낸 시각(§2.2 ⓐ 본인 / ⓑ 사망 확인)
  acceptedAt      DateTime?                     // 가족이 수락한 시각 = 정보주체 동의 시각(§2.1)
  declinedAt      DateTime?                     // 가족이 거절한 시각. 재지정하려면 다시 통지
  acceptedUserId  String?                       // 수락한 가족의 User — 계정 연결 결과(§9)

  lastConfirmedAt DateTime  @default(now())     // 정확도·보유기간 재확인 기준(§7)
  createdAt       DateTime  @default(now())
  updatedAt       DateTime  @updatedAt

  @@unique([userId, phoneHash])                 // 같은 사람을 두 번 지정하지 못하게
  @@index([userId, status])
}
```

`User`에 역참조 `familyDesignations FamilyDesignation[]` 한 줄을 추가합니다.

### 4.1 ⚠️ `phoneHash`가 필요한 이유 — 구현 함정

**AES-256-GCM은 IV가 매번 랜덤이므로 같은 번호도 매번 다른 암호문이 됩니다**(`crypto.ts:21`).
따라서 `phoneEnc`로는 `@@unique`도 중복 검사도 **원리적으로 불가능합니다.**

- 🟡 `crypto.ts`에 **`hashField(plaintext, domain)` 신설** — HMAC-SHA256, 결정적 출력.
- 🔴 **키를 그대로 쓰지 말고 용도 분리**: `sha256(SETTLEMENT_ENCRYPTION_KEY + ':phone-index')`를
  HMAC 키로 씁니다. **새 환경변수를 추가하지 않으면서** 암호화 키와 인덱스 키를 분리합니다
  (env를 늘리면 `render.yaml`·Render 대시보드가 같이 늘어납니다 — `systems.md` §5).
- 입력은 반드시 `normalizePhone`을 거친 **숫자만** 문자열입니다(`utils/phone.ts` 원칙 그대로).

### 4.2 🟡 지정 인원 상한 — **10명**

상한이 없으면 이 기능이 **연락처 수집기로 악용**될 수 있습니다. 실무상 10명이면 충분하고,
넘길 이유가 생기면 그때 올립니다.

## 🔐 6. 권한 범위 — 2단

| `scope` | 뜻 | 사후 권한 |
| :--- | :--- | :--- |
| **`PRIMARY`** (대표 지정인) | 실제 절차를 밟을 사람 | 엔딩노트 **전달** 대상(`06-03` §4.1) · 정산 실행 요청(`00-12` §2.3) |
| **`VIEWER`** (연락 대상) | 알림만 받는 사람 | 사망 통지 수신 · 추모관 접근 |

> 🔴 **전원 동일 권한으로 두면 안 됩니다.** 형제간 이견이 생겼을 때 통제할 수단이 사라집니다.
> `06-03` §4.1이 이미 **열람(운영자) ≠ 전달(지정 유족)** 을 갈라놨으므로, 여기서도
> *"전달 대상인가 / 연락만 받는가"* 를 갈라야 그 구분이 실제로 동작합니다.
>
> 🔴 **확정 필요** — `PRIMARY`를 **1명으로 강제**할지, 복수 허용하고 `priority`로 순서만 둘지.
> 🟡 권고: **복수 허용 + `priority` 순서**. 1명 강제는 그 1명이 먼저 사망·연락두절인 경우
> 되돌릴 방법이 없습니다.

사망 이벤트는 **수십 년 뒤**일 수 있어 *"쓸 일이 올 때까지 보관"* 은 기간 산정이 안 됩니다
(`00-12` §7.3 표). `00-20`(활성 1년/동결) 결정이 나와야 규칙이 섭니다.

- Phase 1에서 하는 것: **`lastConfirmedAt` 기록** + **본인 삭제 경로**(불변식 5)뿐입니다.
- 🟡 후속 권고: **연 1회 재확인**(*"이 연락처가 아직 맞습니까?"*) — 정확도와 보유기간을
  한 동작으로 해결합니다. **번호가 틀린 채 20년 묵으면 권한이 엉뚱한 사람에게 갑니다.**

## 🔌 8. API · 화면 (Phase 1 범위)

### 8.1 엔드포인트 — **본인 인증 필수, 전부 본인 것만**

| 메서드 | 경로 | 비고 |
| :--- | :--- | :--- |
| `POST` | `/api/family-designations` | 생성. `status`는 항상 `DRAFT`로 고정(클라이언트 값 무시) |
| `GET` | `/api/family-designations` | **본인 목록만.** 연락처는 **마스킹**해서 응답(`010-****-5678`) |
| `PATCH` | `/api/family-designations/:id` | 소유자 검증 필수 |
| `DELETE` | `/api/family-designations/:id` | 하드 삭제(불변식 5) |

> 🔴 **`GET` 응답에 평문 연락처를 넣지 않습니다.** 수정 화면에서도 마스킹된 값을 보여주고,
> 바꾸려면 **새로 입력**하게 합니다 — 화면에 평문을 띄우는 순간 XSS·어깨너머 노출이 생기고,
> 그 이득은 *"내가 뭘 적었더라"* 를 확인하는 것뿐입니다.

### 8.2 화면 — **마이페이지 > 가족 지정**

`MyPageAuthSettings.tsx`와 같은 패턴으로 `MyPageFamilyDesignation.tsx`를 신설합니다.

> 🟡 **엔딩노트(06) 안이 아니라 마이페이지에 둡니다.** 가족 지정은 06 전용이 아니라
> **04·05·06 공통기반**(`00-12`)이고, 06은 아직 미리보기 상태입니다(`00-26` §3.1).
> 06이 구현되면 **그 흐름에서 이 화면으로 보내는 진입점만** 추가합니다.

### 8.3 🔴 화면 고지 문구 (필수 — 제3자 정보 수집이므로)

> **입력 폼 하단에 고정 노출합니다.**
>
> *"여기 입력하신 가족의 성함·연락처는 이어봄에 저장됩니다. **가족에게 알리기 전까지는 어떤
> 권한도 부여되지 않으며**, 이어봄이 먼저 연락하지도 않습니다. 알리기를 누르시면 가족이
> 직접 수락한 뒤에야 열람 권한이 생깁니다. 언제든 삭제하실 수 있습니다."*

동의항목은 비즈앱 요건이 걸립니다.

> ✅ **초대 토큰 링크로 해결합니다.** 통지에 담긴 `inviteToken` 링크로 로그인하면

> `07-03`의 slug 방식과 같은 패턴이라 **추측 불가 토큰 생성 코드도 재사용**됩니다.

### 9.1 ✅ 공유 버튼 · 초대 링크 설계 (2026-08-21 개발자 확정 — §11 #2 해소)

> 개발자 지시: *"가족 등록 관련 **공유버튼 추가** + **해당링크로 회원가입시 연결** 필요함."*

**§11 #2(통지 수단)의 권고가 그대로 확정된 것이며, 이로써 Phase 2 차단이 풀립니다.**
이어봄이 문자를 발송하지 않으므로 **비용 0 · 발신번호 사전등록 불필요**이고, `07-03` §2.2와
같은 사상(**이어봄이 발송 주체가 되지 않는다**)입니다.

#### 9.1-1 🔴 이 링크는 부고장 링크와 **성질이 정반대**입니다

**같은 "공유"라도 목적이 반대라, `07-03`의 판단을 그대로 가져오면 사고가 납니다.**

| | 부고장 slug(`07-03`) | **초대 토큰(여기)** |
| :--- | :--- | :--- |
| 목적 | **널리 퍼지는 것**(확산이 기능) | **한 사람에게만 닿는 것** |
| 재전파 | 허용(§13 고지만) | ❌ **금지** |
| 퍼졌을 때 | 정상 동작 | 🔴 **사고** |

🔴 **카톡 가족방에 공유되면 형제 중 아무나 수락할 수 있습니다.** 그런데 `acceptedAt`은 단순
상태값이 아니라 **정보주체의 동의 시각**(§2.1)이고, 수락자는 `scope`에 따라 **엔딩노트 개봉

**→ 필수 3종**: ① **1회용**(수락 즉시 토큰 무효화) ② **만료**(`tokenExpiresAt`)
③ **재발급 시 이전 토큰 폐기** — 잘못 보냈을 때의 **유일한 회수 수단**.

#### 9.1-2 ⚠️ 구현 함정 — 로그인 왕복에서 토큰 컨텍스트가 소실됩니다

```
/invite/{token} → 소셜 로그인 → 백엔드가 /#loginSuccess?token=... 로 리다이렉트
                                (App.tsx:139) ← 여기서 초대 토큰이 사라진다
```

로그인 콜백은 **항상 `/`로 돌아오고 해시만 붙습니다.** 초대 토큰을 로그인 진입 **전에**
`sessionStorage`에 보관했다가 로그인 성공 직후 소비해야 합니다.

> 🔴 **단, `sessionStorage`는 "어디로 돌아갈지" 기억용일 뿐입니다. 수락 권한 판정은 반드시
> 서버가 `초대토큰 + JWT`로 합니다.** `07-03` §5.3-2가 신설된 이유가 정확히 이것입니다 —
> 부고장이 **소유권을 `localStorage`로 판정해 남의 관리화면을 띄운** 사고. **같은 실수를 두 번
> 하지 않습니다.**

⚠️ `/invite/:token`은 **껍데기 없는 라우트**여야 합니다(`App.tsx`의 `isObituaryLandingRoute`·
`isMemorialLandingRoute`와 같은 처리) — 수신자는 아직 회원이 아니라 사이드바·모드가 무의미합니다.

#### 9.1-3 ✅ 불변식은 하나도 완화되지 않습니다

| 불변식 | 공유 버튼이 생겨도 |
| :---: | :--- |
| **1** | **링크를 열었다고 권한이 생기지 않습니다.** `PENDING`은 권한 0, `ACCEPTED`만 권한 |

#### 9.1-4-1 🔴 **데스크톱에서 `navigator.share`가 오히려 길을 막습니다** (2026-08-26 사장님 실기기 확인)

> 🔵 **사장님 확인 결과**: *"모바일 환경에서 카톡 전송 잘됨. **데스크톱 웹에서는 보완 필요** — 공유
> 창은 뜨지만 적합한 메뉴들이 없음. 카톡 메뉴가 있긴 하나 클릭 시 **PC 카톡이 있음에도 MS Store로** 감."*

**원인은 §9.1-4의 전제입니다.** `navigator.share`를 *"모바일 기본 공유 시트"* 로만 봤는데,
**Windows의 크롬·엣지에도 `navigator.share`가 존재**합니다. 그래서 구현이
`MyPageFamilyDesignation.tsx:221`에서 **데스크톱에서도 share 분기를 타고**, Windows 공유창은
카톡 등록 앱이 없어 스토어로 보냅니다. 🔴 **결정적인 것은 그다음입니다** — share가 성공으로
처리돼 `shared = true`가 되므로 **`:230`의 링크 복사 폴백이 영영 실행되지 않습니다.**
즉 데스크톱 사용자에게는 **쓸 수 있는 경로가 하나도 남지 않습니다.**

> ✅ **`navigator.share` **존재 여부**로 분기하지 않습니다.** 존재는 사용 가능을 뜻하지 않습니다.
> 🔴 **어느 경로든 "링크 복사"는 항상 함께 보이게** 합니다 — 공유가 실패해도 빠져나갈 문이 남아야 합니다.
>
> 🔵 **2026-08-26 갱신**: §9.1-4에서 **카카오 공유 SDK 도입이 확정**돼, 데스크톱의 주 경로는
> *"링크 복사"* 가 아니라 **카카오톡 공유**가 됩니다. 그래도 **이 항목은 그대로 유효합니다** —
> 카카오 공유가 실패할 때 `navigator.share`로 흘러가면 **여기서 또 폴백이 죽습니다.**
> **우선순위: ① 카카오톡 공유 → ② 링크 복사(항상 노출).** `navigator.share`는 모바일에서만 보조로.

🟡 **함께 고칠 것** — `:233` 문구 *"링크가 복사되었습니다. **대화방에** 붙여넣어 전달해 주세요"* 는
§9.1-1(1명 전용·재전파 금지)과 어긋나 단톡방을 유도합니다. ***"1:1로 전달해 주세요"*** 로 고치고,
`:218` `shareText`도 같은 기조로 맞춥니다.

#### 9.1-4-2 🔴 **수락 완료 화면이 막다른 길입니다** (2026-08-26 사장님 지적)

> 🔵 *"초대장 수락완료 창에 **홈으로 가기 등이 없음.** 이용자가 수락 후 **다시 웹에 접속**해야 함."*

`FamilyInvitePage.tsx:176~186`의 `accepted` 화면은 *"수락되었습니다"* 만 띄우고 **끝납니다.**
이 페이지는 `App.tsx` 레이아웃(Header/Sidebar/Footer) **밖**이라(§9.1 주석) **헤더조차 없어
빠져나갈 링크가 하나도 없습니다.**

🔴 **이건 단순 편의 문제가 아닙니다.** 수락한 사람은 **방금 이어봄과 처음 접촉한 신규 이용자**이고,
그 순간이 **가족 계정이 연결된 직후**라 서비스로 유입시킬 유일한 접점입니다. 여기서 끊으면
`acceptedUserId` 연결만 남고 사람은 돌아오지 않습니다.

> ✅ **권고: `accepted`·`declined`·에러 3개 화면 전부에 진입 CTA를 답니다.**
> - `accepted` — **"이어봄 홈으로"**(주) + 🟡 *"내 엔딩노트 만들기"*(부). §8.3이 약속한
>   *"가족이 직접 수락한 뒤에야 권한이 생깁니다"* 의 **반대편 끝을 사용자에게 보여주는 자리**이기도 합니다.
> - `declined` — **"이어봄 홈으로"** 하나만. 🔴 거절한 사람에게 서비스 권유를 붙이지 않습니다.
> - 에러(`:170`) — **"이어봄 홈으로"**.
>
> ⚠️ **수락 결과를 CTA 문구로 과장하지 않습니다** — *"이제 ○○님의 엔딩노트를 볼 수 있습니다"* 류는
> 사실이 아닙니다(열람은 사망 확인 이후, `06-04` §8.1).
