### 4.4 🆕 내 상담 내역 — **두 테이블을 한 목록으로** (2026-09-21)

`Lead`(업체 상담)와 `ConsultRequest`(전문가 상담)는 **사용자에게 같은 것**입니다 — 2026-09-10
사람 정정이 통계를 `상담 = consultCount + leadCount`로 합친 것이 그 근거입니다. 목록도 합칩니다.

| 표시 | `Lead` | `ConsultRequest` |
| :--- | :--- | :--- |
| 접수번호 | `leadNo`(`EB-`) | `requestNo`(`EC-`) |
| 어디에 | 시설명(없으면 *"비제휴 업체"*) | 전문가명 + `categorySnapshot` |
| 어떻게 | `type` 견적/상담/전화 | `channel` 알림톡/전화/화상/방문 |
| 언제 | `createdAt` | `createdAt` |
| 상태 | 아래 4단계로 접어서 | 〃 |

🔴 **내부 상태를 그대로 보여주지 않습니다.** `CONVERTED`·`LOST`·`billable`은 **정산용**이고
사용자에겐 뜻이 통하지 않습니다(`01-05` 영역). 네 단계로 접습니다.

| 보이는 것 | `Lead` | `ConsultRequest` |
| :--- | :--- | :--- |
| **접수됨** | `REQUESTED` `NOTIFIED` | `REQUESTED` |
| **진행 중** | `RESPONDED` | `ACCEPTED` |
| **완료** | `CONVERTED` | `COMPLETED` |
| **종료** | `LOST` `INVALID` | `CANCELLED` `INVALID` |

🔴 **응답 화이트리스트** — `billable`·`billedAmount`·`commissionPolicyId`·`settlementId`·
`disputeReason`·`partnerId`·`applicantPhone`·`payload` **원문**을 내리지 않습니다.
🔵 `payload`를 보여주려면 **서버가 `type`별 한 줄 요약**으로 만들어 내립니다.
🔴 `Lead`는 **비회원 문의도 담는 테이블**이라 `where: { userId }` 가 빠지면 남의 문의가 보입니다.
🔵 마스킹된 건(`maskedAt != null`)도 **본인 목록에는 남습니다** — 애초에 스냅샷 필드를 안 내리므로
표시가 달라지지 않습니다.
빈 목록이면 *"아직 신청하신 상담이 없습니다"* + 상담 신청 버튼.

#### 4.4-1 🔴 **`CALL`은 목록에 넣지 않습니다** — 상담이 아니라 클릭입니다 (2026-09-21 정정)

§4.4가 `type`을 그대로 열거한 탓에 **전화 버튼 클릭이 *"접수됨"* 으로 떴습니다.** 잘못입니다.

`01-05` §4.1은 `CALL`을 **"❌ 익명 이벤트 · 기본 비청구"** 로, §9는 *"클릭했다고 통화한 것이
아니고 통화했다고 계약한 것도 아니다"* 로 규정합니다. **접수된 상담이 아닙니다.**

🔴 **게다가 구현이 문서와 다릅니다** — `leadController.createCallEvent`가 `userId`를 붙여
저장합니다(로그인 상태면). 문서는 **익명**이라고 했습니다. **청구에도 안 쓰는 이벤트에 개인
식별자를 남길 이유가 없습니다**(`00-19` 최소수집).

| 고칠 것 | 어떻게 |
| :--- | :--- |
| ① 적재 | 🔴 `createCallEvent`에서 **`userId`를 넣지 않습니다**(항상 `null`) → `01-05` §4.1과 일치 |
| ② 조회 | 🔴 `GET /api/me/leads`에 **`type: { not: 'CALL' }`** — ①을 고쳐도 **이미 쌓인 행**이 남아 있습니다 |
| ③ 기존 행 | 🔵 **지우지 않습니다.** `updateMany`는 DB 쓰기라 백업+CONFIRM 대상인데, ②로 화면에서 사라지므로 **급할 이유가 없습니다** |

##### 🟡 그러면 카카오톡 상담은 남겨야 하나 — **지금은 남기지 않습니다**

🔴 **같은 이유로 걸립니다.** 우리가 아는 것은 **버튼을 눌렀다**뿐이고, 대화를 했는지·해결됐는지는
모릅니다. `CALL`을 뺀 근거가 그대로 적용됩니다.
🔴 **`Lead`에 얹지 않습니다.** `Lead`는 **수수료 청구의 증거** 테이블(`01-05` §4)인데 카톡 채널은
시설·전문가 **어디에도 귀속되지 않는 전사 채널**이라 넣을 자리가 없습니다. 비청구 이벤트를 더
얹으면 정산 테이블이 지표 테이블로 흐려집니다.
✅ **정말로 세야 하면 §6 #6(상담톡 API)으로 제대로 셉니다.** 클릭 수는 그 대체재가 아닙니다 —
*"몇 명이 눌렀나"* 와 *"몇 건이 상담으로 이어졌나"* 는 다른 숫자입니다.
🔵 **클릭 지표가 필요하면** 도메인 테이블이 아니라 **웹 분석 이벤트**(별도 지표 계층)로 셉니다.

7-2. 🆕 **`family-view` 응답에 `scope`·`acceptedAt` 추가**(§4.6-1-1) + 제목 줄 문구 교체.

     질의합니다(노트·권한·항목을 지정마다 따로). Render(오리건)↔DB(서울) 왕복이 회당 **~1.3초**라

     **왕복 수를 지정 건수와 무관하게** 만듭니다.
