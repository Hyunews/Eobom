### 3.1 🔴 #6·#7이 왜 심각한가

**`06-05`(유족 메시지 보관함)는 2026-09-07 기준 D-1~D-11이 전부 구현됐습니다** — 편지 저장·음성 녹음·R2 업로드·듣기·소프트 삭제·반출(zip)·단건 반출까지. 그런데 **사이드바에만 있고 마이페이지에는 입구가 없습니다.**

마이페이지는 *"내가 이 서비스에 무엇을 남겨 뒀는가"* 를 확인하는 자리입니다. 이어봄에서 **사용자가 남기는 것 중 가장 되돌리기 어려운 것**(사후에만 열리는 편지·음성)이 바로 그 자리에서 빠져 있습니다.

같은 논리로 **부고장·추모관**도 카드가 없습니다. 🔄 다만 통계 *"내 부고장"* 칸이 **wt144에서 클릭 가능해져** `/my-obituaries-memorials`로 연결됐고, 동시에 **헤더 메뉴가 삭제돼 마이페이지가 그 화면의 유일한 통로**가 됐습니다(`00-06` §8.2-1).

> 🔴 **그래서 M-1의 성격이 바뀌었습니다.** 통계 칸 하나가 **화면 하나를 통째로 물고 있습니다.**
> B구역 카드(§4.1)는 이제 *"있으면 좋은 것"* 이 아니라 **그 단일 진입점을 이중화하는 안전장치**입니다.
> 🔴 구역을 재배치할 때 **통계 칸의 링크를 떨어뜨리면 화면 전체가 닫힙니다.**

> 🔵 **6070 대상 서비스에서 "눌러도 안 되는 숫자"는 고장으로 읽힙니다**(`00-24`·`00-29`의 일관된 지적).
> 셋 다 링크가 되거나, 링크가 안 되는 것은 숫자를 빼는 편이 낫습니다.

| 어디에 | 시설명(없으면 *"비제휴 업체"*) | 전문가명 + `categorySnapshot` |
| 어떻게 | `type` 견적/상담/전화 | `channel` 알림톡/전화/화상/방문 |
| 언제 | `createdAt` | `createdAt` |
| 상태 | 아래 4단계로 접어서 | 〃 |

🔴 **내부 상태를 그대로 보여주지 않습니다.** `CONVERTED`·`LOST`·`billable`은 **정산용**이고
사용자에겐 뜻이 통하지 않습니다(`01-05` 영역). 네 단계로 접습니다.

| 보이는 것 | `Lead` | `ConsultRequest` |
| :--- | :--- | :--- |
| **접수됨** | `REQUESTED` `NOTIFIED` | `REQUESTED` |
| **진행 중** | `RESPONDED` | `ACCEPTED` |
| **완료** | `CONVERTED` | `COMPLETED` |
| **종료** | `LOST` `INVALID` | `CANCELLED` `INVALID` |

🔴 **응답 화이트리스트** — `billable`·`billedAmount`·`commissionPolicyId`·`settlementId`·
`disputeReason`·`partnerId`·`applicantPhone`·`payload` **원문**을 내리지 않습니다.
🔵 `payload`를 보여주려면 **서버가 `type`별 한 줄 요약**으로 만들어 내립니다.
🔴 `Lead`는 **비회원 문의도 담는 테이블**이라 `where: { userId }` 가 빠지면 남의 문의가 보입니다.
🔵 마스킹된 건(`maskedAt != null`)도 **본인 목록에는 남습니다** — 애초에 스냅샷 필드를 안 내리므로
표시가 달라지지 않습니다.
빈 목록이면 *"아직 신청하신 상담이 없습니다"* + 상담 신청 버튼.

### 4.5 🆕 개인정보·동의 — **역할별이 아니라 성격별 3층** (2026-09-21)

> 사람 요청은 *"역할별 on/off"* 였는데, 코드를 전수 확인한 결과 **끌 수 있는 동의는 하나뿐**이고
> 전문가·사업자 계정에는 **동의 필드가 아예 없습니다**. 그래서 축을 바꿔 정리합니다.

| 층 | 항목 | 화면에서 |
| :--- | :--- | :--- |
| **계정 필수** | `termsAgreedAt`(약관) · `privacyAgreedAt`(개인정보 수집·이용) | 🔴 **토글 없음.** 동의한 **날짜만** 표시 + *"동의를 거두시려면 회원 탈퇴가 필요합니다"* → 탈퇴 행으로 |
| **선택** | `marketingAgreedAt` | ✅ **토글 1개.** 🔴 "내 정보" 모달의 체크박스를 **여기로 옮깁니다**(복제 금지 — 같은 값을 두 곳에서 고치게 됩니다) |
| **건별** | `thirdPartyConsentAt`(상담·문의 건마다) | 🔴 **토글 대상이 아닙니다.** 이미 제3자에게 **제공된 사실**이라 끌 수 없습니다. §4.4 상세에 **동의 시각만** 표시 |

- 위치: **D구역 "개인정보·동의" 행 → 모달**(`00-39` §6.8-1 규칙 21).
  🔵 "내 정보"는 **연락처·주소를 고치는 곳**이고 동의는 성격이 달라 한 모달에 섞지 않습니다.
- 🔴 **전문가·사업자 계정은 범위 밖**입니다 — `Partner`·`Expert`에 동의 필드가 없어 켜고 끌 대상이
  없습니다. 필요해지면 `02-02`·`00-37`에서 별건으로 봅니다.

### 4.6 🆕 나에게 공유된 것 — C구역 (2026-09-21)

**행은 하나입니다** — *"나를 가족으로 지정한 분"*. ⑧(공유된 엔딩노트)과 ⑨(수락한 가족 지정)은
**같은 `FamilyDesignation` 한 줄에서 나오므로**, 두 행으로 나누면 같은 것을 두 번 보여줍니다.

#### 4.6-1 화면 (`SCR-020`)

지정자별 카드 — **성함 · 관계 · `scope`(주 연락자/열람자) · 수락한 날짜 · 지금 볼 수 있는 섹션**.
섹션을 누르면 본문을 엽니다. 데이터는 `GET /api/ending-note/family-view`(**이미 구현됨**).

| 🔴 보이지 않아야 하는 것 | 이유 |
| :--- | :--- |
| 지정자 **연락처·이메일** | `00-27` §3 불변식 2 — 어떤 응답에도 평문을 넣지 않습니다 |
| 같은 노트의 **다른 수락자** | 가족 구성을 서로 알려줄 이유가 없습니다 |
| `POSTMORTEM` 섹션의 **존재 자체** | `06-04` §7.4 *"잠긴 섹션은 제목도 보이지 않는다"* — API가 이미 그렇게 내려줍니다 |

🔴 **과장 금지**(`00-27` §9.1-4 경고와 같은 것) — *"○○님의 엔딩노트를 볼 수 있습니다"* 는
사실이 아닙니다. 실제로 열리는 것은 **`IMMEDIATE`로 부여된 섹션뿐**입니다.
🔴 **빈 상태에 권유를 붙이지 않습니다** — *"아직 공유받은 것이 없습니다"* 한 줄. 누가 나를
지정했기를 **기대하게 만드는 자리가 아닙니다.**

#### 4.6-1-1 🔄 서버 응답 확장 — `scope`·`acceptedAt`을 더합니다 (2026-09-21 확인)

M-1.5 구현에서 드러났습니다 — §4.6-1이 요구한 **`scope`(주 연락자/열람자)와 수락한 날짜**가
`GET /api/ending-note/family-view` 응답에 **없습니다**(지금은 `designationId`·`ownerName`·
`relationship`·`relationshipEtc`·`entries`). ✅ **확장을 승인합니다** — M-2에서 두 필드를 더합니다.

| 추가 | 내려도 되는 근거 |
| :--- | :--- |
| `scope` | `00-27` §9.1-6 b가 **수락 화면 표시 항목**으로 확정한 셋(성함·관계·`scope`) 중 하나입니다 |
| `acceptedAt` | §2.1이 정의한 **본인의 동의 시각**입니다. 자기가 언제 동의했는지는 본인에게 보이는 것이 맞습니다 |

🔴 **그 외에는 늘리지 않습니다** — 연락처·이메일은 불변식 2, `priority`는 불변식 4(연락 순서일
뿐 상속순위가 아니라 표시하지 않습니다).

##### 🔴 문구 — *"지정 관계 · 자녀"* 는 **방향이 빠진 말입니다**

`relationship`은 **지정자가 적은 값**이라 *"자녀"* 는 **내가 그분의 자녀**라는 뜻입니다. 그런데
*"지정 관계 · 자녀"* 만 보면 **그분이 내 자녀인가**로 읽힙니다.
🔵 초대 수락 화면은 *"○○○님이 당신을 가족으로 지정했습니다 / 관계: 자녀"* 처럼 **문장이 방향을
잡아 줍니다.** 그 문장 없이 값만 목록으로 옮기면서 방향이 사라졌습니다.

| 자리 | 🔴 확정 문구 |
| :--- | :--- |
| 구간 제목 | `홍길동 님` (그대로) |
| 제목 줄 오른쪽 | **`나를 자녀로 지정 · 주 연락자`** (관계 + `scope`) |
| 카드 맨 아래 흐린 줄 | **`2026-09-14 수락함`** |

🔵 **초대 화면과 같은 말을 씁니다.** 두 화면이 다르게 말하면 같은 관계가 다른 것으로 보입니다.

#### 4.6-2 ✅ 수락 철회 — 허용합니다 (스키마 변경 없음)

수락 시각은 `00-27` §2.1이 **정보주체의 동의 시각**이라고 정의합니다. **동의에는 철회가 따라야**
합니다. 다만 새 상태를 만들지 않고 **기존 `DECLINED` 경로를 그대로 씁니다.**

1. `POST /api/family-designations/accepted/:id/withdraw`(본인만)
2. 한 트랜잭션에서 — `status = DECLINED` · `declinedAt` 스탬프 · `acceptedUserId = null` ·
   **그 `designationId`의 `EndingNoteGrant` 전부 `revokedAt`**
3. 지정자 화면에는 `acceptedAt != null && status == DECLINED` 조합으로 **"수락 후 거두심"** 으로
   구분해 표시합니다(새 필드 불필요). 🔴 **사유는 받지 않습니다**(`00-27` §9.1-6 c와 같은 규칙)

🔵 지정자 쪽 되돌리기는 이미 있습니다 — 불변식 5(본인은 언제든 하드 삭제).
