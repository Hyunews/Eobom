## ✅ 2. 선택지가 아니라 전제 — 먼저 인정해야 할 사실 3가지

**아래 3가지는 안(案)이 아니라 사실입니다.** 어느 모델을 고르든 바뀌지 않으므로 전제로 깔고 갑니다.

### 2.1 배포 주체는 유족이고, 채널은 플랫폼 밖입니다

구 `03-02` §2.4는 부고 문자 발송을 *"Domain 04(당시 상중·행정 케어 = 현 07)에서 다룰 것"* 이라며
넘긴 곳이 비어 있습니다.

이어봄이 부고를 직접 발송하는 모델은 무겁습니다 — 대량 발송 비용, **수신자 연락처 수집**(사망 당일
개설이 3분 안에 끝나야 한다는 `05-02` §3.2-1 제약과 정면 충돌), 발송 주체로서의 법적 책임.

> **실제 배포는 유족이 카카오톡으로 합니다. 이어봄이 제공하는 것은 "공유하기 버튼"까지입니다.**

### 2.2 따라서 링크는 발송 즉시 통제를 벗어납니다

카톡방에서 재전파되고, 캡처되고, 어디까지 갔는지 아무도 모릅니다. 추측이 불가능할 뿐 **전파는 무제한**입니다.

> **결론: "링크 소지 = 유족이 허락한 사람"이라는 전제는 성립하지 않습니다.**

이 전제는 현행 스펙 곳곳에 암묵적으로 깔려 있습니다 — `LINK` 기본값의 근거(*"URL을 아는 사람만"*,
`05-01` §2.1), 개설 게이트를 `PRIVATE`·`LINK`에 두지 않는 근거(*"링크를 아는 사람에게만 도달 — 확산 위험이
제한적"*, `05-02` §6.1). **이 문장들은 "1차 수신자"에만 참이고, 2차 이후에는 거짓입니다.**

### 2.3 조문객이 받는 링크는 한 개여야 합니다

부고 링크와 추모관 링크가 따로 있으면 — 유족은 사망 당일에 두 번 만들어 두 번 뿌려야 하고,
조문객은 어느 게 진짜인지 모릅니다.

정확한 요구는 **"조문객이 받는 링크가 한 개"** 이지 **"레코드가 한 개"** 가 아닙니다.
**부고장 안에 추모관을 넣으면 05·07이 분리된 채로도 배포 링크는 한 개**입니다 → §4.5 E안(채택).

> 🔴 **이 원칙에 구멍이 하나 있습니다**(2026-09-07~). 추모관을 부고장과 따로 만들 수 있게 되면서(§4.5-4),
> **추모관을 먼저 따로 만든 유족은 링크 2개를 들게 됩니다.** 원칙을 폐기한 것이 아닙니다 — 메우는 방법과 판단은 **§4.5-4-2**.
> 처음엔 *"05·07 통합이 사실상 유일한 답"* 이라고 잘못 적었다가 08-14에 정정했습니다(부록 경위 B).

## ⏳ 3. 링크가 감당해야 하는 두 시기 — 요구가 정반대입니다

고인 한 명의 링크는 **성격이 반대인 두 시기를 살아야 합니다.** 이것이 이 결정의 진짜 난점이고, E안은 시기마다 레코드를 따로 두어(부고장 ↔ 추모관) 풉니다(§4.5-2).

| | **부고 시기** (D+0 ~ 장례 종료) | **추모 시기** (장례 후 ~ 영구) |
| :--- | :--- | :--- |
| 링크의 목적 | **널리 퍼지는 것** | **좁혀 지키는 것** |
| 주 내용 | 빈소·발인·장지·조의금 계좌 (실용 정보) | 영정·추모 문구·사진·방명록 (기억) |
| 재전파 | **오히려 바람직** — 알려야 하니까 | **위험** — 유족이 통제하고 싶어짐 |
| 유족 심리 | 경황 없음, 결정 피로 (`05-02` §3.2) | 정리·보존 모드 |
| 접근 마찰 | **0이어야 함** | 어느 정도 허용 가능 |
| 존속 기간 | 며칠 | 영구 (스토리지 비용 — 보존기간 정본 `00-20`) |

**같은 링크 정책을 두 시기에 적용하는 것은 불가능합니다.** 부고 때 좁히면 부고가 성립하지 않고,
추모 때 열어두면 영구히 통제 불능입니다. 08-12 당시의 단일 영구 링크(A안)는 **후자를 암묵적으로 택한 것**이었습니다.

#### 4.5-1 이 안이 §2.3(링크는 한 개)을 어떻게 만족시키나

> ⚠️ **개발자 지시의 *"부고장에 추모관 링크 전송을 더한다"* 는 두 가지로 읽힙니다. 갈림길입니다.**

| | 읽는 방식 | 조문객이 받는 것 | 평가 |
| :---: | :--- | :--- | :--- |
| (가) | 카톡 메시지에 **링크 2개**를 넣어 보낸다 | 부고 링크 + 추모관 링크 | ❌ **§2.3 정면 위반.** 어느 게 진짜인지 모르고, 재전파되며 한쪽만 살아남습니다 |
| (나) | **부고장 페이지 안에** 추모관 버튼이 박혀 있다 | **부고 링크 1개** | ⭕ **이쪽이어야 합니다** |

**(나)로 확정하는 것을 권고합니다.** 배포 단위는 언제나 부고장 링크 하나이고, 추모관 주소는
**부고장을 연 사람에게만** 보입니다. 이러면 §2.3을 지키면서도 05·07을 합치지 않아도 됩니다.

> 🔴 **2026-09-07 — (나) 원칙은 유지, 조건이 하나 붙습니다.** 추모관이 선택이 되었으므로
> 부고장 랜딩의 **[추모관 들어가기] 버튼은 연결된 추모관이 있을 때만** 뜹니다. 없으면 버튼이
> 아예 없습니다 — 🔴 **"준비 중"·빈 추모관으로 보내지 않습니다.** 조문객이 빈 페이지를 만나는
> 것은 유족에게 결례이고, 링크가 하나 더 도는 값도 못 합니다(구현: `ObituaryLandingPage.tsx`).

> **✅ 전환 트리거 문제가 사라지는 것이 E안의 가장 큰 실익입니다.** §4.3에서 "발인일 자동 /
> 수동 / 고정기간" 중 무엇을 고르든 부작용이 있었는데, **두 레코드로 나누면 전환이라는 사건
> 자체가 없습니다.** 부고장은 그냥 오래된 페이지가 되고, 추모관은 처음부터 따로 있었습니다.

#### 4.5-3 🔴 E안이 지불하는 대가 — 정직하게

1. **`Deceased`(`00-12` §2.1)가 전제가 됩니다.** 부고장과 추모관이 서로 다른 도메인의 서로 다른 모델인데
   **같은 고인**을 가리켜야 합니다. ✅ 지금 둘 다 `deceasedId`로 `Deceased`를 가리킵니다(`Obituary`·`Memorial` 필수 FK, `07-03` §4.1).
   🔴 **다만 따로 만들면 고인이 두 번 입력됩니다** — 부고장 개설(`obituaryController.ts` `createObituary`)과
   추모관 단독 개설(`memorialController.ts`)이 **각자 새 `Deceased`를 만들고**, 같은 고인인지 잇는 수단이 없습니다.
   `Memorial`에는 표시용 `deceasedName` 문자열도 그대로 남아 있습니다. 함께 만들 때(체크박스)는 같은 `Deceased`를 씁니다.
2. **추모관 개설 게이트(허위 개설 고지 동의, `05-01` §2.3)는 추모관이 만들어지는 두 자리 모두에** 걸려야 합니다 —
   07 부고장 폼(체크박스를 켰을 때)과 `/memorial` 직접 생성 폼. ✅ 구현은 양쪽 다 동의를 받고, 검증은 `utils/consentGates.ts`
   `validateFalseReportAgreed` 하나를 같이 씁니다. **한쪽만 걸면 그게 곧 뒷문**입니다.
3. **링크가 2종류라 `05-01` §4.1의 "404로 존재를 숨긴다" 원칙을 두 번 적용**합니다.
   부고장 slug와 추모관 slug는 **서로 유추 가능하면 안 됩니다**(같은 난수에서 파생 금지).

추모관만 *"바깥 사람이 링크를 타고 들어오는 도착지"* 입니다. **성격이 다르므로 운영도 달라야

#### 7.2-1 🟡 해석 A — **배포 묶음마다 링크를 따로 발급** (`ShareLink`) · 권고: 2차

D안(수신자 1인당 토큰)이 무거웠던 이유는 **명단을 받아야 했기 때문**입니다.
**"사람" 대신 "뿌리는 곳" 단위로 쪼개면 개인정보를 하나도 안 받고 D안의 이점 절반을 얻습니다.**

| | 유족이 하는 일 | 결과 |
| :--- | :--- | :--- |
| 기본 | 아무것도 안 함 | 개설 시 **기본 링크 1장 자동 발급** — 지금과 동일, 마찰 0 |
| 선택 | *"링크 따로 만들기"* → 이름표 입력(`회사`·`친척`·`동창`) | 링크 3장. **어느 방에서 새는지 구분되고, 한 장만 죽일 수 있음** |

```prisma

  id         String   @id @default(uuid())
  memorialId String
  slug       String   @unique     // 이 묶음의 링크
  label      String?              // "회사", "친척" — 유족만 봄. 조문객에게 노출 금지

}
```

| 얻는 것 | 잃는 것 |
| :--- | :--- |
| **부분 회수** — B안은 전부 아니면 전무였는데, 여기선 문제 생긴 한 장만 죽입니다 | 유족이 "굳이 나눠야 하나" 하고 안 쓸 가능성. **그래도 기본 1장이 있으니 손해는 없습니다** |
| **재전파 추적 절반** — 누가 퍼뜨렸는지는 몰라도 **어느 묶음에서 샜는지는** 압니다 | 모델 1개 증가. `Memorial.slug`가 `ShareLink`로 옮겨가는 마이그레이션 |
| **개인정보 추가 수집 0** — D안의 유일한 결격 사유가 없습니다 | `label`이 유족 화면에 남습니다 — *"이 사람은 회사에 안 알렸다"* 같은 정보가 되므로 **조문객 응답에 절대 싣지 않습니다** |
