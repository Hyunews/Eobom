## 📌 1. 문제 — 링크에 대해 정의된 것이 한 줄뿐입니다

현행 스펙(`05-01` §2.1·§3.1)이 링크에 대해 말하는 전부:

> `slug` — 공개 URL용 **추측 불가 토큰**. 순번(`/memorial/1`) 금지.

즉 **개설 시점에 1개 발급되고, 영구 불변이며, 아는 사람은 누구나 들어옵니다.**
**비밀번호 없는 영구 마스터 키 한 장**입니다. 나머지는 전부 공백입니다.

| 질문 | 현행 스펙의 답 |
| :--- | :--- |
| 누가 배포하나 | **없음** |
| 어떤 채널로 나가나 | **없음** |
| 재전파(단톡방 재공유)되면 | **없음** — 막을 방법도, 알 방법도 없음 |
| 유출되면 회수할 수 있나 | **불가.** `slug`가 1개뿐이라 회전 불가 |
| 만료되나 | **없음** — 영구 |
| 누가 들어왔는지 아나 | **없음** |

유출 시 유족이 할 수 있는 건 **추모관을 통째로 닫는 것(`closedAt`)** 뿐이고,
그 "닫기"조차 아직 미구현입니다(`05-02` §4 — 🔴 미구현으로 표기됨).
**전부 아니면 전무입니다.**

## ✅ 2. 선택지가 아니라 전제 — 먼저 인정해야 할 사실 3가지

**아래 3가지는 안(案)이 아니라 사실입니다.** 어느 모델을 고르든 바뀌지 않으므로 전제로 깔고 갑니다.

### 2.1 배포 주체는 유족이고, 채널은 플랫폼 밖입니다

구 `03-02` §2.4는 부고 문자 발송을 *"Domain 04(당시 상중·행정 케어 = 현 07)에서 다룰 것"* 이라며
넘긴 곳이 비어 있습니다.

이어봄이 부고를 직접 발송하는 모델은 무겁습니다 — 대량 발송 비용, **수신자 연락처 수집**(사망 당일
개설이 3분 안에 끝나야 한다는 `05-02` §3.2-1 제약과 정면 충돌), 발송 주체로서의 법적 책임.

> **실제 배포는 유족이 카카오톡으로 합니다. 이어봄이 제공하는 것은 "공유하기 버튼"까지입니다.**

### 2.2 따라서 링크는 발송 즉시 통제를 벗어납니다

카톡방에서 재전파되고, 캡처되고, 어디까지 갔는지 아무도 모릅니다. 추측이 불가능할 뿐 **전파는 무제한**입니다.

> **결론: "링크 소지 = 유족이 허락한 사람"이라는 전제는 성립하지 않습니다.**

이 전제는 현행 스펙 곳곳에 암묵적으로 깔려 있습니다 — `LINK` 기본값의 근거(*"URL을 아는 사람만"*,
`05-01` §2.1), 개설 게이트를 `PRIVATE`·`LINK`에 두지 않는 근거(*"링크를 아는 사람에게만 도달 — 확산 위험이
제한적"*, `05-02` §6.1). **이 문장들은 "1차 수신자"에만 참이고, 2차 이후에는 거짓입니다.**

### 2.3 조문객이 받는 링크는 한 개여야 합니다

부고 링크와 추모관 링크가 따로 있으면 — 유족은 사망 당일에 두 번 만들어 두 번 뿌려야 하고,
조문객은 어느 게 진짜인지 모릅니다. `05-02` §2.2가 권고한 **(A) 05·07 통합**이 링크 관점에서는
사실상 유일한 답입니다.

> 🔴 **다만 "통합한다"는 결정 자체는 사장님 확정 사항입니다**(§8-1). 아래 4개 안 중 A·B는 분리
> 상태에서도 성립하지만, 그 경우 **07이 별도 링크를 만들 것인지**를 07 기획에서 다시 정해야 합니다.

> 🔵 **2026-08-14 정정** — *"통합이 사실상 유일한 답"* 이라는 위 문장은 **틀렸습니다.**
> 정확한 요구는 **"조문객이 받는 링크가 한 개"** 이지 **"레코드가 한 개"** 가 아닙니다.
> **부고장 안에 추모관을 넣으면 분리 상태에서도 배포 링크는 한 개**입니다 → §4.5 E안.
> 위 두 문단은 그 오해를 남겨두기 위해 지우지 않습니다.

## ⏳ 3. 링크가 감당해야 하는 두 시기 — 요구가 정반대입니다

통합하면 **한 링크가 성격이 반대인 두 시기를 살아야 합니다.** 이것이 이 결정의 진짜 난점입니다.

| | **부고 시기** (D+0 ~ 장례 종료) | **추모 시기** (장례 후 ~ 영구) |
| :--- | :--- | :--- |
| 링크의 목적 | **널리 퍼지는 것** | **좁혀 지키는 것** |
| 주 내용 | 빈소·발인·장지·조의금 계좌 (실용 정보) | 영정·추모 문구·사진·방명록 (기억) |
| 재전파 | **오히려 바람직** — 알려야 하니까 | **위험** — 유족이 통제하고 싶어짐 |
| 유족 심리 | 경황 없음, 결정 피로 (`05-02` §3.2) | 정리·보존 모드 |
| 접근 마찰 | **0이어야 함** | 어느 정도 허용 가능 |
| 존속 기간 | 며칠 | 영구 (스토리지 비용 — `05-02` §9) |

**같은 링크 정책을 두 시기에 적용하는 것은 불가능합니다.** 부고 때 좁히면 부고가 성립하지 않고,
추모 때 열어두면 영구히 통제 불능입니다. 현행 A안은 **후자를 택한 것**이며, 그 선택을 명시적으로
한 적은 없습니다.

## 🧭 4. 선택지 4안

### 4.1 A안 — 단일 영구 링크 (현행 유지)

**작동**: 개설 시 `slug` 1개 발급. 영구 불변. 유족이 카톡으로 공유. 끝.

| | |
| :--- | :--- |
| **유족 경험** | 가장 단순. 만들고 뿌리면 끝. 배울 게 없음 |
| **조문객 경험** | 마찰 0 |
| **구현 비용** | **0** — 이미 설계된 그대로 |
| **유출 회수** | ❌ 불가. 추모관 통째로 닫기만 가능(그마저 미구현) |
| **재전파 추적** | ❌ 불가 |
| **개인정보 추가 수집** | 없음 |

**장점**: 사망 직후 제약(`05-02` §3.2 — 3분 개설, 승인 대기 금지)을 완벽히 만족합니다.
구현이 이미 끝난 설계라 일정에 영향이 없습니다.

**단점**: §3의 두 시기 중 **부고 시기에만 최적화**되어 있습니다. 장례가 끝나고 1년 뒤에도 링크는
살아 있고, 그 사이 어디까지 퍼졌는지 유족은 알 수 없으며, 되돌릴 수단이 "전체 삭제"뿐입니다.
**추모관의 본질이 "영구 보존 자산"인데 그 자산에 대한 통제권이 없습니다.**

**이 안이 성립하려면**: 개설 화면에서 *"이 링크는 전달받은 분이 다시 공유할 수 있으며,
한 번 만든 링크는 변경할 수 없습니다"* 를 **명시적으로 고지**해야 합니다. 지금은 고지도 없습니다.

### 4.2 B안 — 회전(재발급) 가능한 링크

**작동**: A안 + 유족이 **"링크 새로 만들기"** 를 누르면 새 `slug` 발급, 구 `slug` 무효화.

| | |
| :--- | :--- |
| **유족 경험** | 통제권 획득. 단 "언제 눌러야 하는지"를 스스로 판단해야 함 |
| **조문객 경험** | 평소 마찰 0. **회전된 뒤 구 링크로 오면 접근 불가** |
| **구현 비용** | **낮음** — `slug` 재발급 + 구 slug 이력 테이블(선택) |
| **유출 회수** | ⭕ 가능 |
| **재전파 추적** | ❌ 불가 |
| **개인정보 추가 수집** | 없음 |

**장점**: 최소 비용으로 "전부 아니면 전무"를 깹니다. 유출·그리핑(`05-02` §7 T2) 상황에서
추모관을 삭제하지 않고도 대응할 수 있습니다.

**단점**: **유족이 언제 눌러야 할지 모릅니다.** 부고 기간 중에 잘못 누르면 이미 뿌린 링크가 전부
죽어서 조문객이 못 들어옵니다 — 사망 당일 경황 없는 유족에게 되돌릴 수 없는 실수를 만들 수 있는
버튼을 쥐여주는 셈입니다. **시기 구분 없이 회전 버튼만 주는 것은 위험합니다.**

### 4.3 🟡 C안 — 단계(phase) 분리 + 단계별 링크 정책 **[권고]**

**작동**: `Memorial`에 **세 번째 축 `phase`** 를 추가하고, 링크 정책을 단계에 매답니다.

```
Memorial.phase:  OBITUARY(부고)  →  MEMORIAL(추모)
```

| | `OBITUARY` | `MEMORIAL` |
| :--- | :--- | :--- |
| 화면 내용 | 빈소·발인·장지·계좌 **우선** | 영정·추모 문구·사진·방명록 **우선** |
| 링크 | 개설 시 발급, **회전 불가** | **유족이 회전 가능** |
| 기본 `visibility` | `LINK` | `LINK` (유족이 좁힐 수 있음) |
| 회전 버튼 | **노출 안 함** | 노출 |

`05-02` §5가 이미 `visibility`(유족 의사)와 `moderationState`(운영자 제재)를 2축으로 분리했습니다.
**C안은 여기에 "시간" 축을 더하는 것**이며, 같은 설계 사상의 연장입니다.

| | |
| :--- | :--- |
| **유족 경험** | 부고 때는 선택지가 없어 실수할 수 없음. 장례 후 통제권이 **생김** |
| **조문객 경험** | 부고 시기 마찰 0. 추모 전환 후 구 링크는 B안과 동일 논점 |
| **구현 비용** | **중** — `phase` 컬럼 + 전환 트리거 + 화면 2벌 + 장례 정보 컬럼 신설 |
| **유출 회수** | ⭕ 추모 단계에서 가능 |
| **재전파 추적** | ❌ 불가 |
| **개인정보 추가 수집** | 없음 (장례 정보는 고인·유족 정보이지 조문객 정보가 아님) |

**장점 3가지**:
1. **§3의 모순을 정면으로 해결하는 유일한 안**입니다. 시기별 요구가 반대라면 시기를 나누는 것이 답입니다.
2. **05↔07 경계가 자동으로 정해집니다**(`05-02` §2.2 미결 해소). 부고장 = `OBITUARY` 단계의 추모관.
   07에는 **D-Day 행정 체크리스트·안심상속 원스톱 안내**가 남고, 그게 07의 본래 정체성에 더 맞습니다.
3. B안의 치명적 단점(경황 없는 유족의 오조작)을 **버튼을 안 보여주는 것으로** 제거합니다.

**단점**: 구현 비용이 가장 큽니다. 화면이 사실상 2벌 필요하고, `Memorial` 스키마에 **장례 정보
컬럼이 신설**되어야 합니다(현행 `05-01` §3.1에는 빈소·발인일시·장지·계좌 컬럼이 **하나도 없습니다** —
부고장을 당시 04에 넘겼기 때문입니다). 통합하면 이 컬럼들이 05로 들어옵니다.

   `visibility` 문제였고, 지금 `slug`가 같은 실수를 반복하고 있습니다 — **"부고용 링크"와
   "추모용 링크"라는 두 역할을 필드 하나가 지고 있습니다.**

### 7.1 C안을 고르지 말아야 할 경우 — 정직한 반론

- **오픈 일정이 급하면 A입니다.** C는 화면 2벌 + 스키마 확장이라 05 착수 일정을 늘립니다.
  05는 아직 **전 기능 목업**이고(`00_DOCS_INDEX`), 오브젝트 스토리지 전환(`00-11`)이라는
  선행 조건도 걸려 있습니다.
- **07을 독립 도메인으로 키울 계획이 있다면** 통합은 그 여지를 줄입니다. 부고장은 07의 유일한
  "제품다운" 기능이고, 이걸 05로 넘기면 07은 정보 안내 도메인만 남습니다.
- **B는 "지금 A로 가되 나중에 C로 갈 수 있게" 하는 중간 기착지가 됩니다.** `phase` 없이 회전만
  먼저 넣어도 유출 회수는 확보됩니다. 다만 §4.2의 오조작 위험을 어떻게 막을지는 답이 필요합니다.

### 7.2 🟡 *"추모관은 다르게 운영"* — 개발자 아이디어 요청에 대한 답 3가지

> 개발자 지시: *"추모관 도메인은 다른 도메인과 조금 다르게 운영해야 할 걸로 판단됨.
> **예를 들어, 링크에 따른 페이지가 따로 생성**된다던지.. (아이디어가 필요함)"*

**이 직관은 맞습니다.** 다른 도메인은 전부 *"로그인한 사용자가 앱 안에서 쓰는 기능"* 인데,
추모관만 *"바깥 사람이 링크를 타고 들어오는 도착지"* 입니다. **성격이 다르므로 운영도 달라야
합니다.** 다만 *"페이지가 따로 생성된다"* 는 말은 **세 가지로 해석**될 수 있고, 셋 다 가치가
있으나 **채택 시점이 다릅니다.** 아래는 그 셋을 갈라놓은 것입니다.

#### 7.2-1 🟡 해석 A — **배포 묶음마다 링크를 따로 발급** (`ShareLink`) · 권고: 2차

D안(수신자 1인당 토큰)이 무거웠던 이유는 **명단을 받아야 했기 때문**입니다.
**"사람" 대신 "뿌리는 곳" 단위로 쪼개면 개인정보를 하나도 안 받고 D안의 이점 절반을 얻습니다.**

| | 유족이 하는 일 | 결과 |
| :--- | :--- | :--- |
| 기본 | 아무것도 안 함 | 개설 시 **기본 링크 1장 자동 발급** — 지금과 동일, 마찰 0 |
| 선택 | *"링크 따로 만들기"* → 이름표 입력(`회사`·`친척`·`동창`) | 링크 3장. **어느 방에서 새는지 구분되고, 한 장만 죽일 수 있음** |

```prisma
model ShareLink {
  id         String   @id @default(uuid())
  memorialId String
  slug       String   @unique     // 이 묶음의 링크
  label      String?              // "회사", "친척" — 유족만 봄. 조문객에게 노출 금지
  revokedAt  DateTime?            // 이 장만 회수
  viewCount  Int      @default(0) // 집계값만. 방문자 식별 정보는 저장하지 않음(05-01 §2.4 사상)
  createdAt  DateTime @default(now())
}
```

| 얻는 것 | 잃는 것 |
| :--- | :--- |
| **부분 회수** — B안은 전부 아니면 전무였는데, 여기선 문제 생긴 한 장만 죽입니다 | 유족이 "굳이 나눠야 하나" 하고 안 쓸 가능성. **그래도 기본 1장이 있으니 손해는 없습니다** |
| **재전파 추적 절반** — 누가 퍼뜨렸는지는 몰라도 **어느 묶음에서 샜는지는** 압니다 | 모델 1개 증가. `Memorial.slug`가 `ShareLink`로 옮겨가는 마이그레이션 |
| **개인정보 추가 수집 0** — D안의 유일한 결격 사유가 없습니다 | `label`이 유족 화면에 남습니다 — *"이 사람은 회사에 안 알렸다"* 같은 정보가 되므로 **조문객 응답에 절대 싣지 않습니다** |

> 🟡 **1차에는 넣지 않는 것을 권합니다.** E안의 기본 골격(부고장↔추모관)을 먼저 세우고,
> `slug`를 처음부터 **`ShareLink`로 분리해 둘 수 있게 설계만 열어두면** 나중 추가가 쌉니다.
> **지금 확정할 것은 "`Memorial`이 slug를 직접 들고 있지 않게 한다" 하나뿐입니다.**

#### 7.2-2 ✅ 해석 B — **앱 화면이 아니라 독립 랜딩 페이지로 렌더** · 권고: **1차에 함께**

*"페이지가 따로 생성된다"* 의 **가장 실질적인 형태이며, 사실 선택이 아니라 요구사항입니다.**

| | 다른 도메인 화면 | **부고장·추모관** |
| :--- | :--- | :--- |
| 방문자 | 로그인한 회원 | **처음 온 조문객** |
| 껍데기 | GNB·사이드바·모드 전환 | **없어야 함** — 조의 화면에 서비스 메뉴가 붙으면 광고로 읽힙니다 |
| URL | `/care-guide` 같은 기능 이름 | **`/o/{slug}`·`/m/{slug}`** — 기능이 아니라 대상을 가리킴 |
| 색인 | 허용 | **`noindex` 필수**(`05-01` §7.1·`00-14` §7-6) |

> 🔴 **그리고 기술적으로 반드시 짚어야 할 것 하나 — 카카오톡 미리보기(OG 태그)입니다.**
>
> 부고 링크는 **카톡에 붙여넣는 순간 미리보기 카드가 떠야** 합니다. *"○○○님 부고"* 라는 카드
> 없이 정체불명 URL만 뜨면 **조문객이 클릭하지 않거나, 피싱으로 의심합니다.**
> 그런데 현재 프론트는 **Vite SPA(`00-03`)라 OG 태그가 정적**입니다 — 어느 부고를 열어도
> 카드가 똑같이 뜹니다.
>
> **→ 부고장·추모관 URL만은 서버가 고인별 OG 태그를 넣어 응답해야 합니다.** 이것이
> *"페이지가 따로 생성되어야 한다"* 는 직관의 **진짜 기술적 실체**라고 봅니다.
> 구현은 세 가지(백엔드가 해당 경로만 HTML 셸 렌더 / 별도 SSR 라우트 / 프리렌더)이고,
> **백엔드가 `/o/*`·`/m/*` 두 경로만 렌더하는 것이 가장 쌉니다.**
>
> ⚠️ 다만 이때 **OG 카드에 무엇을 넣을지가 개인정보 판단**입니다 — 고인 성명·영정 사진이
> 카톡 서버와 캐시에 남습니다. 🟡 **성명과 "삼가 고인의 명복을 빕니다" 수준까지만, 영정은 제외**를
> 권고합니다. `05-01` §3.1이 생년월일을 공개 응답에서 뺀 것과 같은 사상입니다.

#### 7.2-3 🟡 해석 C — **물리적으로 정적 파일을 생성**(SSG) · 권고: 개설 시점에는 ❌ / **동결 시점에는 ⭕**

| 시점 | 판단 |
| :--- | :--- |
| **개설 시 생성** | ❌ **부적합.** 방명록·헌화가 실시간으로 늘어나고, 신고 시 즉시 비공개 전환(`05-01` §4.3)이 필요합니다. 정적 파일은 **회수가 느린 것이 아니라 어렵습니다** — 캐시 무효화가 곧 사고 대응 지연이 됩니다 |
| **동결 후 생성** | ⭕ **가치 있음.** 개설 N년 뒤 *"방명록·헌화를 닫고 기억만 남긴 상태"* 로 전환하면서 **스냅샷 1장으로 굳히면**, DB·API 부담 없이 영구 보존이 가능합니다 |

> 🔵 **두 번째 칸은 `00-14` §4-3(추모관 보존기간 + 수익 모델 — "수익 0인데 영구 스토리지 비용")의
> 답이 될 수 있습니다.** *"영구 보존"* 의 비용이 무서운 이유는 **살아 있는 서비스로 영구히
> 유지**하기 때문입니다. **"3년 뒤 동결, 이후는 정적 보존"** 이면 약속은 지키면서 비용 곡선이
> 꺾입니다. 유족에게도 *"삭제합니다"* 보다 *"이제 방명록은 닫고 기억만 남깁니다"* 가 훨씬 낫습니다.
>
> 🔴 이건 아이디어 단계이며 **§4-3 결정과 함께 다뤄야** 합니다 — 여기서 확정하지 않습니다.
