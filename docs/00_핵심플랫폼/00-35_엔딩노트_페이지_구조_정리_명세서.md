### 5.1 지금

8곳이 같은 형태를 반복한다. **6개 prop 중 5개가 섹션 코드에서 그대로 유도**된다.

<AccordionSection

### 5.2 바꿀 형태

본문과 저장 페이로드만 코드별로 모으고, 나머지는 순회한다.

```tsx
const sectionBodies: Record<string, React.ReactNode> = {
  LIFE_SUPPORT: (<>…기존 본문 그대로…</>),
  FUNERAL: (<>…</>),
  // … 8개
};

const sectionPayloads: Record<string, () => unknown> = {
  LIFE_SUPPORT: () => ({ lifeSupport }),
  FUNERAL: () => ({ funeralType }),
  // … 8개 — 🔴 기존 onSave가 넘기던 객체와 키·형태가 완전히 같아야 한다
};

{SECTIONS.map((s) => (
  <AccordionSection
    key={s.code}
    meta={s}
    expanded={expandedSection === s.code}
    completed={!!sectionState[s.code]}
    saveState={savingState[s.code]}
    onToggle={() => handleToggleSection(s.code)}
    onSave={() => saveSection(s.code, sectionPayloads[s.code]())}
  >
    {sectionBodies[s.code]}
  </AccordionSection>
))}
```

### 5.3 🔴 주의

- **`SECTIONS` 배열 순서 = 화면 표시 순서**가 된다. 현재 DOM 순서(①②④⑤⑥⑦⑧⑩)와 **같은지 확인하고 바꾸지 않는다.**
- **⑨ 유언장 초안(`WILL_DRAFT`)은 이 순회에 넣지 않는다.** `SECTIONS`에 없고 별도 블록이다(`06-04` §6.1-1). 건드리지 않는다.
- `sectionPayloads`를 **`useMemo`로 감싸지 않는다** — 값이 바뀌어도 최신 상태를 읽어야 한다. 매 렌더 재생성이 맞다.
- 저장 페이로드 키가 하나라도 달라지면 **§9 A 때문에 에러 없이 통과**한다. §7 체크 1번으로만 잡힌다.

## 6. 🔴 프론트엔드 전역 규칙 — 이 작업뿐 아니라 앞으로 계속

### 6.1 컴포넌트는 **모듈 최상위**에만 정의한다

렌더 함수 안에서 정의하면 매 렌더마다 새 컴포넌트 타입이 생겨 React가 서브트리를 **언마운트·재마운트**하고, **입력 포커스가 키 입력마다 끊긴다.**

> 🔴 **이 프로젝트가 이미 밟은 사고**다 — `EndingNotePage.tsx` 144~147·174~177줄에 주석으로 남아 있다.

✅ **함수 호출은 괜찮다.** `{renderSomething(...)}`처럼 **JSX를 반환하는 함수를 호출**하는 것은 새 컴포넌트 타입을 만들지 않으므로 안전하다. **`<RenderSomething/>` 처럼 태그로 쓰는 순간 위험해진다.**

### 6.2 사용자 **입력값**은 자식 컴포넌트로 내리지 않는다

`AccordionSection`은 접히면 `{expanded && …}` 로 **children을 언마운트**한다(161줄). 자식이 입력값을 소유하면 **접을 때마다 저장 안 한 입력이 사라진다 — 에러 없이.**

| 내려도 되는 것 | 내리면 안 되는 것 |
| :--- | :--- |
| 닫히면 초기화돼도 무방한 **표시용 상태** (`largeText`·`copyFeedback`) | **사용자가 입력한 값 전부** |

### 6.3 저장 페이로드는 **명시적으로** 만든다

서버(`endingNoteController.ts` `saveEndingNoteSection`)는 **값의 형태를 검증하지 않는다**(§9 A). 상태 객체를 그대로 넘기지 말고, 보낼 필드를 코드에 적어서 만든다.

### 10.3 🆕 2.5단계 — `SectionTimingControl` 호출부 승격 **(신설 · 🔴 착수 확정 필요)**

재판단 중 **2단계가 남긴 반복 하나**를 찾았다. 8개 섹션 본문이 **끝에서 똑같은 6줄**을 반복하며, `section=` 값만 다르다.

```tsx
// 8곳 전부 동일 — 376·394·419·449·495·526·549·578줄
<SectionTimingControl
  section="LIFE_SUPPORT"          // ← 섹션 코드에서 유도된다
  family={family}
  grants={grants}
  onChange={(designationId, timing, grantId) => handleGrantChange('LIFE_SUPPORT', designationId, timing, grantId)}
/>
```

**바꿀 형태** — `sectionBodies`에서 8곳을 지우고, 순회 안 `{sectionBodies[s.code]}` **바로 뒤**에 한 번만 둔다.

```tsx
<AccordionSection …>
  {sectionBodies[s.code]}
  <SectionTimingControl
    section={s.code}
    family={family}
    grants={grants}
    onChange={(designationId, timing, grantId) => handleGrantChange(s.code, designationId, timing, grantId)}
  />
</AccordionSection>
```

| 항목 | 값 |
| :--- | :--- |
| 감소 | **−48줄** (8×6) → **859 → 811줄** |
| 위험 | 🟢 **낮음.** DOM 순서가 보존된다 — 8곳 모두 **본문의 마지막 자식**이므로 순회 뒤로 옮겨도 같은 자리다 |
| 새 배선 | **없음.** props 4개가 이미 부모 스코프에 있다 |
| 검증 | §7 전체 + **체크 8번(공개 시점 select)을 8섹션 전부** — 지금은 표본 1개만 본다 |

🔴 **주의 3가지**
1. `SectionTimingControl`은 **`SECTION_ALLOWED_TIMINGS[section]`이 없으면 `null`을 반환**한다. `SECTIONS` 8개는 모두 항목이 있으므로 출력은 안 바뀌지만, **`SECTIONS`에 섹션을 추가할 때 timing 항목을 빼먹으면 조용히 사라진다** — 추가 시 두 곳을 같이 본다.
2. **⑨ `WILL_DRAFT`는 순회 밖이므로 영향 없다**(§5.3 그대로).
3. **`section={s.code}`와 `handleGrantChange(s.code, …)`의 코드가 같아야 한다.** 지금은 두 곳에 문자열을 손으로 적고 있어 어긋날 수 있었다 — 이 변경이 그 가능성을 없앤다.
