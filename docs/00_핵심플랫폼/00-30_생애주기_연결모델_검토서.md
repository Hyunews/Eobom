## 📄 2. 사장님 제공 자료 — 원문 보존

> **판단의 근거가 되는 원문은 요약하지 않고 남깁니다.** 이후 절의 대조는 전부 이 표를 기준으로 합니다.

### 2.1 3단계 생애주기별 연결 모델

| 단계 | 이름 | 내용 |
| :---: | :--- | :--- |
| **1** | **생전 초대 모델**(Pre-Mortem Link) | 회원이 디지털 엔딩노트 작성 시 **지정 유족(보호자)의 이름과 연락처(휴대폰/이메일)** 입력 → 유족에게 *"[이어봄] 000님이 회원님을 안심 엔딩 수신자로 지정하셨습니다"* **카카오 알림톡/문자 발송** → 유족이 해당 링크로 가입하면 **즉시 가족 관계 매핑 완료**, 생전에는 민감 정보 **잠금(Lock)** 유지 |
| **2** | **사후 승계 및 조회 모델**(Post-Mortem Verification) | 회원 사망 시 유족이 웹에서 **'사후 승계 요청'** → **사망진단서 또는 행정망(정부24 연계) 확인** 후, 잠겨 있던 **엔딩노트·디지털 유품 리스트·사전 장례 의향서**의 열람 권한이 **유족 계정으로 활성화** |
| **3** | **상중 긴급 연결 모델**(Emergency Onboarding) | 사전에 회원이 가입하지 않았더라도, **상주가 긴급 장례·행정 지원을 신청하며 가입**할 때 **고인의 기본 정보를 등록**하여 사후 유족 계정으로 즉시 생성·연결 |

### 2.2 사용자 여정(UX Flow)

| 주체 | 흐름 |
| :--- | :--- |
| **본인(시니어)** | 엔딩노트/상속 메뉴 → **[수신 가족 지정]** → 자녀 이름·휴대폰 입력 및 **열람 범위 설정**(*"장례 방식은 즉시 공유, 자산·비밀번호는 사후 공유"*) → **초대장 공유** |

## 🧩 4. 이 모델이 실제로 만드는 것 — **연결**

### 4.1 🔵 가장 큰 기여는 기능이 아니라 **순서**입니다

지금까지 이 프로젝트의 문서들은 **각자 옳지만 서로 이어져 있지 않았습니다.**

```
[가입]───[00-27 가족지정]───[?????]───[06 엔딩노트]
                              │        [04 디지털유품]
                              │        [07 부고·행정]
                        여기가 비어 있었다
```

사장님 모델은 **그 빈칸의 이름이 "사망 확인"이고, 그 앞뒤에 무엇이 와야 하는지**를 말합니다.
**`00-12`가 2026-08-12에 이미 같은 결론에 도달했지만**(사다리 L0~L4 · *"통로는 06 하나"*),
**그것을 사용자가 지나가는 순서로 다시 쓴 것은 이 자료가 처음입니다.**
그 빈칸은 09-30 `00-41`(사망 확인 → 한 번에 개봉)로 채워졌습니다.

### 4.2 🔴 그래서 드러나는 것 — **"유족 계정"이 두 종류입니다**

| 경로 | 검증 수준 | 할 수 있는 것 | 할 수 없는 것 |
| :--- | :---: | :--- | :--- |
| **1→2단계**(생전 지정 후 사망 확인) | **운영자 확인**(`00-41`) | 부고·행정 + **엔딩노트 개봉** | — |
| **3단계**(긴급 온보딩) | **L1** | 부고장·장례·행정 체크리스트 | 🔴 **엔딩노트를 열 수 없습니다** |

> 🔴 **이 구분을 화면에서 미리 말하지 않으면 그대로 CS가 됩니다** — *"가입했는데 왜 안 열리냐."*
> 3단계로 들어온 상주는 **자기가 유족이라고 신고했을 뿐**이고, 고인이 생전에 그를 지정한 적이
> 없습니다. **같은 "유족 계정"이라는 말이 두 가지를 가리키고 있습니다.**
>
> ✅ `00-41`도 같은 구분을 씁니다 — 개봉 요청은 **생전에 지정되고 수락한 가족만** 할 수 있고, 자칭 유족(생전 지정 없음)은 범위 밖입니다(`00-41` §10).
>
> 🟡 **권고(미구현): 3단계 온보딩 화면에서 *"생전에 지정받으신 분은 추가 절차 없이 열람하실 수 있습니다"*
> 를 안내**해, 1단계의 존재를 **사후에 알게 되는 경로**를 만듭니다. 이건 마케팅이 아니라
> **1단계 가입 동기가 가장 강해지는 순간**입니다.

### 4.3 데이터가 흐르는 방향

| 시점 | 무엇이 어디로 | 정본 |
| :--- | :--- | :--- |
| 1단계 | 가족 연락처 → `FamilyDesignation` | `00-27` |
| 생전 | 의향·메시지 → `EndingNote*`(암호화·봉인) | `06-04` §5 |
| 2단계 | 사망 확인 → `DeathVerification` → `EndingNote.RELEASED` → 권한대로 열림 | `00-41` §7 |
| 2단계 직후 | **장례 의향 → 07 부고장 프리필** — ⏸ 미구현 · ~~디지털 계정 의향 → 04 체크리스트~~(04 생전 계획 접음 · `DigitalCleanupItem` 삭제로 소멸) | `06-04` §8.4 |
| 3단계 | 고인 기본정보 → `Deceased` → 부고장·추모관 | `07-03` |

> ✅ **마지막 줄이 이 모델의 실익입니다.** 엔딩노트를 *"열어서 읽는 것"* 으로 끝내지 않고
> **유족이 바로 다음에 해야 할 일에 값을 흘려보내는 것** — 그게 이 기능이 플랫폼 안에 있는
> 이유이고, 단독 앱과 다른 점입니다.

## ⚠️ 5. 충돌·정정 3건

### 5.1 🔴 알림톡 발송 — **2026-08-21 확정과 정반대입니다**

`00-27` §9.1(08-21)은 **이어봄이 발송 주체가 되지 않는다**를 개발자 확정으로 정했습니다. 사장님 안(알림톡/문자 발송)과는 **반대**입니다.

| 트리거 | 발송 주체 | 지금 |
| :--- | :--- | :--- |
| **ⓐ 본인이 살아서 가족을 지정할 때** | **본인**(공유 버튼) | ✅ 현행 — `00-27` §9.1 |
| **ⓑ 사망 확인 후 다른 가족에게 알릴 때** | **개봉을 요청한 유족**(공유 버튼) | ✅ `00-41` §6(09-30) — 이어봄은 보내지 않는다 |

- 알림톡 도입 여부는 `00-14` §11-1(사장님 결정 대기). 들어오더라도 위 두 줄을 **보조**하는 수단입니다.
- 별건(10-01 개발자 메모): 시설·전문가(파트너)에게 **문의 알림**이 필요할 수 있음 → `00-14` §11-1에 함께 적음. 지금 코드는 상담 연락 채널 선택지에 알림톡만 있고 자동 발송은 없습니다(`ConsultRequestModal`).

> 08-25 원문(ⓑ = 이어봄이 보낼 수밖에 없다)은 문서 끝 **부록: 경위 B**.

### 5.2 🔴 정부24 연계 — **확인 전에는 설계에 넣지 않습니다**

`00-27` §10 Phase 3이 이미 *"정부24 연계는 그 위에 L4로 얹습니다(개발자 지시로 후순위)"* 라고
적어 두었습니다. 여기서 더 나가지 않는 이유:

- 민간 사업자가 **타인의 사망 사실을 행정망에서 조회**할 수 있는지는 제도로 정해지는 문제이고,
  **확인되지 않았습니다.**
- 안 될 경우 되돌릴 곳이 많아집니다(화면·모델·약관·처리방침).

> ✅ **지금 확인 방식은 `00-41` §5.2 — 서류를 받지 않고 운영자가 장례식장에 전화로 확인**합니다(09-30).
> 정부24가 성립하면 이 확인을 **대체하는 것이 아니라 자동화**하는 것이므로, 나중에 얹는 형태가 됩니다.
> 🔴 **확인 전까지 화면에 *"행정망 연동"* 문구를 쓰지 않습니다** — `00-14` §2.5(*"KISA 기준 최고
> 등급 보안"*)와 정확히 같은 종류의 사고가 됩니다.

### 5.3 ⚠️ Zero-Knowledge — **요구는 채택, 용어는 정정**

| | 뜻 | 판정 |
| :--- | :--- | :--- |
| **암호학적 ZK(E2E)** | 서버도 복호화 못 함 | ❌ **`06-03` §1.1이 이미 기각** — 키를 아는 사람이 **죽고 없어** 사후 개봉이 원리적으로 불가능. 6070 시니어에게 키 관리를 넘길 수도 없음 |
| **권한 격리**(사장님 의도) | 유족 계정으로는 생전에 접근 경로 자체가 없음 | ✅ **채택** — API·쿼리·UI 3층 구현(`06-04` §7.4) |

> 🟡 **대외 용어는 「생전 봉인(Sealed)」으로 통일 권고.** *"Zero-Knowledge"* 는 **서버도 못 본다는
> 뜻으로 읽히는데 사실이 아니고**, 그 상태로 화면에 쓰면 `06-03` §1이 경계한
> *"보증의 어투로 말하는 약속"* 이 됩니다. 정직한 표현은 `06-03` §5가 이미 확정해 두었습니다.

### 6.1 🟡 "보호 중" 배너를 권고하는 이유

**지정을 수락한 유족은 그 뒤로 이어봄에 올 이유가 없습니다.** 사망은 수십 년 뒤일 수 있고,
그 사이 **연락처가 바뀌거나 앱의 존재를 잊습니다**(`00-27` §7이 *"번호가 틀린 채 20년 묵으면
권한이 엉뚱한 사람에게 간다"* 고 지적한 문제).

> 🟡 **배너는 장식이 아니라 `lastConfirmedAt` 재확인의 자연스러운 자리**입니다.
> *"ooo님의 안심 보호자로 등록되어 있습니다 · 연락처가 바뀌셨나요?"* 한 줄이
> **연 1회 재확인**(`00-27` §7)을 **별도 통지 없이** 수행합니다.
