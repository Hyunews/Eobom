## 🗄️ 4. ① 모델 — `DeathVerification` 하나

### 4.1 왜 하나만

`00-12` §3 초안은 `Deceased`·`DeathVerification`·`BereavedRelation` 3개를 묶었다. 이번에는
**`DeathVerification`만** 만든다.

| 초안 모델 | 이번에 안 만드는 이유 |
| :--- | :--- |
| `BereavedRelation` | **`FamilyDesignation`(ACCEPTED)이 이미 "지정 유족"이다**(`00-16` §4.2 경로 A). 자칭 유족(경로 B)은 이번 범위 밖 |
| `Deceased` 연결 | 부고장용 `Deceased`와 회원을 잇는 일은 **07 프리필(`06-04` §8.4)** 때 필요하다. 개봉 자체에는 필요 없다 |

### 4.2 스키마

```prisma
// 00-41 §4 — 사후 개봉 요청·사망 확인·동의를 한 행에. 🔴 서류 파일·이미지·주민등록번호 컬럼을
// 만들지 않는다(00-16 §4.3). 🔴 엔딩노트 본문과 조인하지 않는다(06-03 §3.1).
model DeathVerification {
  id                   String    @id @default(uuid())
  subjectUserId        String    // 사망했다고 신고된 회원(엔딩노트 주인). FK User
  requestedByDesigId   String    // 요청한 지정 유족. FK FamilyDesignation — ACCEPTED + acceptedUserId=요청자여야 함

  status               String    @default("REQUESTED") // REQUESTED | VERIFIED | REJECTED | CANCELLED

  // 요청자가 입력(§8.1). 장례식장 정보는 업체 정보라 개인정보가 아니다
  deceasedName         String    // 고인 실명 — User.name은 닉네임일 수 있어 따로 받는다
  deathDate            DateTime
  funeralHallName      String?   // null이면 "장례식장 없음" 선택
  funeralHallPhone     String?

  requestedAt          DateTime  @default(now())
  dueAt                DateTime  // requestedAt + 12시간. 대시보드 정렬·지연 표시용(§5.1)

  // 운영자 처리(§5)
  level                String?   // VERIFIED일 때 OPERATOR_REVIEWED (00-12 §3 값 그대로)
  method               String?   // FUNERAL_HALL | OTHER
  reviewedByAdminId    String?   // FK 아님(AdminAuditLog와 같은 원칙)
  reviewedAt           DateTime?
  rejectReason         String?   // HALL_NOT_FOUND | NAME_MISMATCH | UNREACHABLE | OTHER — 코드만, 자유 서술 없음

  // 2단계 개봉(§7)
  consentByDesigId     String?   // 요청자가 아닌 다른 ACCEPTED 지정 유족의 동의
  consentAt            DateTime?
  releaseEligibleAt    DateTime? // 지정 유족이 1명일 때만: reviewedAt + 7일

  cancelledAt          DateTime?
  cancelledBy          String?   // SUBJECT | REQUESTER

  @@index([status, dueAt])
  @@index([subjectUserId])
}
```

- **개봉의 최종 상태는 여전히 `EndingNote.status = RELEASED` 하나다**(`06-05` §3.3 — 상태 소유자는 `EndingNote`뿐).
  `DeathVerification`은 거기까지 가는 과정만 담는다.
- 🔴 **한 회원에 진행 중인 요청은 하나만** — `REQUESTED` 또는 `VERIFIED`(아직 `RELEASED` 전)가 있으면 새 요청 거부. 컨트롤러에서 강제.
- 🔴 **마이그레이션 = DB 스키마 변경** → `db-safety.md` 절차(백업 파일 확인 + CONFIRM).

## 🕛 5. ② 사람이 처리 — 12시간 · 운영자 대시보드

### 5.1 처리 기준

| 항목 | 값 |
| :--- | :--- |
| 처리 시한 | **요청 후 12시간**(`dueAt`) |
| 🟡 시간 계산 | **달력 기준 — 밤·주말·공휴일 포함**(권고). 장례는 보통 3일이라 영업일로 세면 장례가 끝난다. → §12 #1 |
| 지연 표시 | 대시보드에서 남은 시간 표시, **넘으면 빨간색**. 자동 알림은 없다(§10) |

### 5.2 확인 방법 — 서류를 받지 않는다

`00-16` §4.2 **경로 A**(생전 지정 유족 → 서류 불필요)를 그대로 쓴다. 남는 것은 **"정말 돌아가셨나"** 하나이고,
이것을 **장례식장에 전화로 확인**한다.

| 방법 | 운영자가 하는 일 | 누가 쓸 수 있나 |
| :--- | :--- | :--- |
| **`FUNERAL_HALL`** 기본 | 요청자가 적은 장례식장에 전화해 **"고 ○○○님 빈소(또는 장례)가 있었는지"** 확인 | 모든 운영자 |
| **`OTHER`** 예외 | 장례식장이 없는 경우. 요청자에게 전화해 확인 방법을 정한다 | 🔴 **`SUPERADMIN`만**(`00-37` §3.3 등급) |

> ✅ **이 방법이 좋은 이유**: 주민등록번호가 찍힌 서류를 보지 않으므로 `00-16` §3의 법적 문제가 **생기지 않는다.**
> 장례식장은 빈소 정보를 공개적으로 안내하는 곳이라 확인 전화가 이상한 요청이 아니다.

### 5.3 운영자 화면 — 대시보드 새 탭 「사망 확인」

| 보이는 것 | 안 보이는 것 |
| :--- | :--- |
| 요청 시각 · **남은 시간** · 상태 | 🔴 **엔딩노트 본문·섹션 제목·편지** — 어떤 필드도 응답에 넣지 않는다(`06-03` §3.1) |
| 고인 실명(요청자 입력) · 회원 이름(`User.name`) · 사망일 | 섹션별 작성 여부(`sectionState`)도 넣지 않는다 |
| 장례식장 이름·전화 | |
| 요청자 이름·관계 · **요청자 전화번호**(되걸기용, `phoneEnc` 복호화) | |

- 버튼 2개: **[확인 완료]**(방법 선택) · **[반려]**(사유 코드 선택).
- 목록은 `REQUESTED`만, `dueAt` 오래된 순. 탭 이름 옆에 **대기 건수**.
- 🔴 **감사 로그**: 상세 열람 = `VIEW`, 확인 = `APPROVE`, 반려 = `REJECT`로 `AdminAuditLog`에 남긴다(`targetType = DeathVerification`).

## 📣 6. ④ 알림 — 이어봄은 보내지 않는다

`00-30` §5.1은 *"사망 통지는 이어봄이 보낼 수밖에 없다 — 본인이 죽었으므로"* 였다.
**그런데 개봉을 요청하는 사람은 살아 있는 유족이다.** 그가 보내면 된다.

| 누구에게 | 무엇을 | 어떻게 |
| :--- | :--- | :--- |
| 운영자 ← 새 요청 | 대기 건수 | **대시보드 탭**(운영자가 들어와서 본다) |
| 요청자 ← 결과 | 확인됨·반려·남은 시간 | **요청 상태 화면**(`/family-shared`) |
| 다른 지정 가족 ← 열렸음·동의 요청 | *"○○님의 기록을 이어봄에서 보실 수 있습니다"* | 요청자 화면의 **[가족에게 알리기]** → `navigator.share` / 링크 복사. 🔴 **링크에 토큰을 넣지 않는다** — `/family-shared` 주소만. 권한은 로그인 계정으로 판정(`06-04` §8.3) |
| 본인 ← (살아 있다면) | *"가족이 개봉을 요청했습니다"* | 본인 로그인 시 **배너 + [취소]**(§8.3) |

- ✅ **`00-27` §9.1(08-21, 이어봄은 발송 주체가 아니다)이 그대로 유지된다.** `00-14` §11-1(알림톡 도입)은
  **이 최소안을 막지 않는다** — 나중에 들어오면 표의 세 번째 줄을 보조하는 수단이 된다.
- 🔴 **화면에 "문자·알림톡으로 알려드립니다"를 쓰지 않는다.** 보내지 않으니까.

## 🔁 7. 흐름 — 두 번에 나눠 연다

```
[요청] ──> REQUESTED ──운영자 확인(≤12h)──> VERIFIED ──(다른 가족 동의 | 7일)──> EndingNote.RELEASED
              │                                 │
              ├─반려──> REJECTED (다시 요청 가능)   └─ 1단계 섹션 열림
              └─취소(본인·요청자)──> CANCELLED      (VERIFIED에서 취소해도 CANCELLED — 1단계도 다시 닫힘)
```

### 7.1 무엇이 언제 열리나

| 단계 | 열리는 것 | 근거 |
| :--- | :--- | :--- |
| **1단계 · `VERIFIED`** | **② 장례 희망 · ⑦ 중요 연락처 · 장기·시신 기증** | 장례를 치르는 데 필요한 것만. 반나절이 급한 이유가 이것 |
| **2단계 · `RELEASED`** | 나머지 사후 섹션 전부 + **유족 편지(`FarewellMessage`)** | 🔴 **편지는 2단계와 함께 한 번에**(`06-05` §3.3 "동시" 유지) |
| 어느 단계도 아님 | 🔴 **⑨ 유언장 쓰기 도구(`WILL_DRAFT`)** | `06-04` §7.1 — 본인 전용, 영영 안 열림 |

- 각 가족에게 보이는 섹션은 **지금 `/family-view`가 쓰는 판정(섹션 `recipientId`·`EndingNoteGrant`)을 그대로** 쓰고,
  "이 단계에서 열리는 섹션인가"만 조건으로 더한다. 편지는 **자기 앞으로 온 것만**(`FarewellMessage.recipientId`).
- 🔴 **안 열린 섹션은 제목도 응답에 없다**(`06-04` §7.4, `00-30` §7.1).

### 7.2 2단계로 넘어가는 조건 (`00-14` §11-5)

| 지정 유족(ACCEPTED) 수 | 조건 |
| :--- | :--- |
| **1명** | 확인 후 **7일**(`releaseEligibleAt`) — `06-04` §8.2 권고 그대로 |
| **2명 이상** | **요청자가 아닌 다른 ACCEPTED 1명의 [동의]** — 누르는 즉시 `RELEASED`. 7일 대체 없음 |
| 0명 | 요청 자체가 불가(요청자가 ACCEPTED여야 하므로) |

- 🟡 `06-04` §8.2는 *"PRIMARY 1인 + 다른 1인"* 이었다. 여기서는 **PRIMARY를 요구하지 않는다** — PRIMARY는
  복수·없음이 모두 가능하고(`00-30` §7.2) 그가 연락이 안 되면 멈추기 때문. → §12 #3
- **7일 전환은 예약 작업을 만들지 않는다.** 가족이 화면을 열 때(`GET`) 서버가 `releaseEligibleAt ≤ 지금`이면
  그 자리에서 `RELEASED`로 바꾼다(한 트랜잭션, 여러 번 불려도 결과 같음).

### 7.3 `RELEASED` 뒤

- `EndingNote.status = RELEASED`, `releasedAt` 기록.
- 🔴 **본인 쪽 저장 API는 `RELEASED`면 거부한다**(409). 고인 휴대폰으로 누군가 내용을 고치는 것을 막는다.

## 🖥️ 8. 화면

### 8.1 유족 — 개봉 요청 (`/family-shared` 안)

- 지정해 준 분 목록 옆에 **[돌아가셨음을 알리고 기록 열기]**. 🟡 버튼 문구는 구현 때 `ux-copy` 한 번 거칠 것.
- 입력: **고인 성함(실명)** · **돌아가신 날** · **장례식장 이름 · 전화번호** 또는 **[장례식장 없음]**.
- 안내 문구(사실만): *"운영자가 장례식장에 확인한 뒤 열립니다. 접수 후 12시간 안에 확인합니다. 결과는 이 화면에서 보실 수 있습니다."*
- 🔴 **파일 첨부 칸을 만들지 않는다**(`00-16` §4.3).

### 8.2 유족 — 요청 상태

| 상태 | 화면 |
| :--- | :--- |
| `REQUESTED` | 접수 시각 · *"○시 ○분까지 확인합니다"* · [요청 취소] |
| `VERIFIED` | 1단계 섹션 내용 · [가족에게 알리기] · 2단계 조건 안내(*"다른 가족 한 분이 동의하면 나머지가 열립니다"* / *"○월 ○일에 나머지가 열립니다"*) |
| `VERIFIED`(다른 가족 화면) | 1단계 섹션 + **[나머지 기록 열기에 동의]** |
| `RELEASED` | 전체 섹션 + 편지 |
| `REJECTED` | 반려 사유(코드 → 정해진 문장) · [다시 요청] |

### 8.3 본인 — 배너

본인이 로그인했는데 자기 앞으로 `REQUESTED`·`VERIFIED` 요청이 있으면 상단 배너:
*"○○님이 엔딩노트 개봉을 요청했습니다. 본인이시면 취소해 주세요."* [취소] → `CANCELLED`.

- 🔴 **로그인만으로 자동 취소하지 않는다** — 가족이 고인 휴대폰(자동 로그인)을 쓰는 경우가 흔하다.

| 본인 | `GET /ending-note/release-requests/about-me` · `POST …/:id/cancel-by-subject` | 배너·취소 |
| 운영자 | `GET /admin/death-verifications` | `REQUESTED` 목록, `dueAt` 순 |
| 운영자 | `GET /admin/death-verifications/:id` | 상세(`VIEW` 로그) |
| 운영자 | `PATCH /admin/death-verifications/:id/verify` `{method}` | `OTHER`는 `SUPERADMIN`만. `releaseEligibleAt` 계산(지정 유족 1명일 때) |
| 운영자 | `PATCH /admin/death-verifications/:id/reject` `{reasonCode}` | |

- 🔴 **단계 판정은 서버만** — 클라이언트가 보낸 상태·섹션 값은 무시(`06-04` §7.4).
- 🔴 운영자 응답은 `select`로 필드를 적는다. `include`로 `EndingNote`를 통째 붙이지 않는다.
