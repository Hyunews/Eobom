## 🗄️ 4. ① 모델 — `DeathVerification` 하나

### 4.1 왜 하나만

`00-12` §3 초안은 `Deceased`·`DeathVerification`·`BereavedRelation` 3개를 묶었다. 이번에는
**`DeathVerification`만** 만든다.

| 초안 모델 | 이번에 안 만드는 이유 |
| :--- | :--- |
| `BereavedRelation` | **`FamilyDesignation`(ACCEPTED)이 이미 "지정 유족"이다**(`00-16` §4.2 경로 A). 자칭 유족(경로 B)은 이번 범위 밖 |
| `Deceased` 연결 | 부고장용 `Deceased`와 회원을 잇는 일은 **07 프리필(`06-04` §8.4)** 때 필요하다. 개봉 자체에는 필요 없다 |

### 4.2 스키마

```prisma
// 00-41 §4 — 사후 개봉 요청·사망 확인을 한 행에. 🔴 서류 파일·이미지·주민등록번호 컬럼을
// 만들지 않는다(00-16 §4.3). 🔴 엔딩노트 본문과 조인하지 않는다(06-03 §3.1).
model DeathVerification {
  id                   String    @id @default(uuid())
  subjectUserId        String    // 사망했다고 신고된 회원(엔딩노트 주인). FK User
  requestedByDesigId   String    // 요청한 지정 유족. FK FamilyDesignation — ACCEPTED + acceptedUserId=요청자여야 함

  status               String    @default("REQUESTED") // REQUESTED | VERIFIED | REJECTED | CANCELLED

  // 요청자가 입력(§8.1). 장례식장 정보는 업체 정보라 개인정보가 아니다
  deceasedName         String    // 고인 실명 — User.name은 닉네임일 수 있어 따로 받는다
  deathDate            DateTime
  funeralHallName      String?   // null이면 "장례식장 없음" 선택
  funeralHallPhone     String?

  requestedAt          DateTime  @default(now())
  dueAt                DateTime  // 대외 약속 — 운영시간(평일 9~17시)만 세서 12시간(§5.1). 화면 표시·정렬용
  targetAt             DateTime  // 내부 목표 — 운영시간만 세서 1시간(§5.1). 운영자 화면에만

  // 운영자 처리(§5)
  level                String?   // VERIFIED일 때 OPERATOR_REVIEWED (00-12 §3 값 그대로)
  method               String?   // FUNERAL_HALL | OTHER
  reviewedByAdminId    String?   // FK 아님(AdminAuditLog와 같은 원칙)
  reviewedAt           DateTime?
  rejectReason         String?   // HALL_NOT_FOUND | NAME_MISMATCH | UNREACHABLE | OTHER — 코드만, 자유 서술 없음

  cancelledAt          DateTime?
  cancelledBy          String?   // SUBJECT | REQUESTER

  @@index([status, dueAt])
  @@index([subjectUserId])
}
```

- **개봉의 최종 상태는 여전히 `EndingNote.status = RELEASED` 하나다**(`06-05` §3.3 — 상태 소유자는 `EndingNote`뿐).
  `DeathVerification`은 거기까지 가는 과정만 담는다.
- 🔴 **한 회원에 진행 중인 요청은 하나만** — `REQUESTED`가 있거나 이미 `VERIFIED`(=개봉됨)면 새 요청 거부. 컨트롤러에서 강제.
- 🔴 **마이그레이션 = DB 스키마 변경** → `db-safety.md` 절차(백업 파일 확인 + CONFIRM).

## 🕛 5. ② 사람이 처리 — 12시간 · 운영자 대시보드

### 5.1 처리 기준

| 항목 | 값 |
| :--- | :--- |
| 접수 | **24시간 받는다**(요청 화면은 늘 열려 있다) |
| 운영시간 | **평일 9~17시.** 주말·공휴일 휴무. 🔵 **나중에 바꿀 수 있게 값 하나로 둔다**(설정 상수) |
| 대외 약속(`dueAt`) | **운영시간만 세서 12시간.** 운영시간 밖 접수는 다음 운영일 9시부터 센다. 예: 월 10시 접수 → 화 14시 |
| 내부 목표(`targetAt`) | **운영시간만 세서 1시간.** 화면에는 내보내지 않는다 |
| 공휴일 | 1차는 **코드 상수 목록**(연 1회 갱신). 대체공휴일 포함 |
| 지연 표시 | 대시보드: 내부 목표 넘으면 **노란색**, 대외 약속 넘으면 **빨간색**. 자동 알림은 없다(§10) |

### 5.2 확인 방법 — 서류를 받지 않는다

`00-16` §4.2 **경로 A**(생전 지정 유족 → 서류 불필요)를 그대로 쓴다. 남는 것은 **"정말 돌아가셨나"** 하나이고,
이것을 **장례식장에 전화로 확인**한다.

| 방법 | 운영자가 하는 일 | 누가 쓸 수 있나 |
| :--- | :--- | :--- |
| **`FUNERAL_HALL`** 기본 | 요청자가 적은 장례식장에 전화해 **"고 ○○○님 빈소(또는 장례)가 있었는지"** 확인 | 모든 운영자 |
| **`OTHER`** 예외 | 장례식장이 없는 경우. 요청자에게 전화해 확인 방법을 정한다 | 🔴 **`SUPERADMIN`만**(`00-37` §3.3 등급) |

> ✅ **09-30 개발자 결정 — `OTHER` 확인 순서: ① 화장장·장지 전화 확인 → ② 안 되면 `SUPERADMIN` 판단.**
> ①은 장례식장 확인과 같은 방식(요청자에게 화장장·장지 이름·연락처를 전화로 받아 확인). ②는 기준을 따로 두지 않고
> 최고 관리자가 판단하며, 무엇으로 확인했는지 **감사 로그 메모에 한 줄** 남긴다. 🔴 서류(사망진단서 등)를 보여달라고
> 하지 않는다(`00-16` §4.3) — 확인이 안 되면 반려(`OTHER`)하고 대표번호로 개별 처리. 운영 절차이며 코드 변경 없음.

> ✅ **이 방법이 좋은 이유**: 주민등록번호가 찍힌 서류를 보지 않으므로 `00-16` §3의 법적 문제가 **생기지 않는다.**
> 장례식장은 빈소 정보를 공개적으로 안내하는 곳이라 확인 전화가 이상한 요청이 아니다.

### 5.3 운영자 화면 — 대시보드 새 탭 「사망 확인」

| 보이는 것 | 안 보이는 것 |
| :--- | :--- |
| 요청 시각 · **남은 시간** · 상태 | 🔴 **엔딩노트 본문·섹션 제목·편지** — 어떤 필드도 응답에 넣지 않는다(`06-03` §3.1) |
| 고인 실명(요청자 입력) · 회원 이름(`User.name`) · 사망일 | 섹션별 작성 여부(`sectionState`)도 넣지 않는다 |
| 장례식장 이름·전화 | |
| 요청자 이름·관계 · **요청자 전화번호**(되걸기용, `phoneEnc` 복호화) | |

- 버튼 2개: **[확인 완료]**(방법 선택) · **[반려]**(사유 코드 선택).
- 목록은 `REQUESTED`만, `dueAt` 오래된 순. 탭 이름 옆에 **대기 건수**.
- 🔴 **감사 로그**: 상세 열람 = `VIEW`, 확인 = `APPROVE`, 반려 = `REJECT`로 `AdminAuditLog`에 남긴다(`targetType = DeathVerification`).

## 📣 6. ④ 알림 — 이어봄은 보내지 않는다

`00-30` §5.1은 *"사망 통지는 이어봄이 보낼 수밖에 없다 — 본인이 죽었으므로"* 였다.
**그런데 개봉을 요청하는 사람은 살아 있는 유족이다.** 그가 보내면 된다.

| 누구에게 | 무엇을 | 어떻게 |
| :--- | :--- | :--- |
| 운영자 ← 새 요청 | 대기 건수 | **대시보드 탭**(운영자가 들어와서 본다) |
| 요청자 ← 결과 | 확인됨·반려·남은 시간 | **요청 상태 화면**(`/family-shared`) |
| 다른 지정 가족 ← 열렸음 | *"○○님의 기록을 이어봄에서 보실 수 있습니다"* | 요청자 화면의 **[가족에게 알리기]** → `navigator.share` / 링크 복사. 🔴 **링크에 토큰을 넣지 않는다** — `/family-shared` 주소만. 권한은 로그인 계정으로 판정(`06-04` §8.3) |
| 본인 ← (살아 있다면) | *"가족이 개봉을 요청했습니다"* | 본인 로그인 시 **배너 + [취소]**(§8.3) |

- ✅ **`00-27` §9.1(08-21, 이어봄은 발송 주체가 아니다)이 그대로 유지된다.** `00-14` §11-1(알림톡 도입)은
  **이 최소안을 막지 않는다** — 나중에 들어오면 표의 세 번째 줄을 보조하는 수단이 된다.
- 🔴 **화면에 "문자·알림톡으로 알려드립니다"를 쓰지 않는다.** 보내지 않으니까.

## 🔁 7. 흐름 — 확인되면 한 번에 연다 (09-30 확정 · 가안)

```
사망 → 유족이 개봉 요청(장례식장 정보) → 운영자 장례식장 전화 확인 → 개봉 → 지정 가족 각자 열람
                 REQUESTED ──────────────────> VERIFIED  = 같은 트랜잭션에서 EndingNote.RELEASED
                     ├─반려──> REJECTED (다시 요청 가능)
                     └─취소(본인·요청자)──> CANCELLED   (취소는 REQUESTED에서만)
```

> 🔵 **09-30 개발자 확정 — "가" 안.** 초판의 2단계 개봉(장례 3섹션 먼저 → 다른 가족 동의 또는 7일 뒤 나머지)은
> **폐기**한다. 근거: 가족마다 볼 섹션은 본인이 생전에 이미 정했고(`EndingNoteGrant`), 운영자가 사망을
> 확인한 뒤라 동의 단계가 추가로 막는 것이 적다. **`06-04` §8.1의 L4(지정 유족 이중 동의)와 §8.2,
> `00-14` §11-5는 이 결정으로 대체된다.**

### 7.1 무엇이 열리나

| 열리는 것 | 누구에게 |
| :--- | :--- |
| 사후 섹션 전부(`POSTMORTEM`) | 그 섹션을 볼 권한이 있는 지정 가족 — **지금 `/family-view`가 쓰는 판정(섹션 `recipientId`·`EndingNoteGrant`)을 그대로** 쓴다 |
| 유족 편지(`FarewellMessage`) | **자기 앞으로 온 것만**(`recipientId`). 섹션과 **같은 순간에** 열린다(`06-05` §3.3) |
| 🔴 ⑨ 유언장 쓰기 도구(`WILL_DRAFT`) | **아무에게도 안 열림**(`06-04` §7.1) |
| 🆕 편지 **음성**(`mediaKey`) | **편지와 같다 — 자기 앞 편지의 음성만.** 09-30 스펙갱신(3-B 중 Sonnet 발견: 수신자용 재생 API가 없어 음성 편지를 들을 수 없었다). 음성은 이미 R2에 있으므로 새 저장소가 필요 없다 — 아래 §9 추가 줄 |

- 🔴 **권한이 없는 섹션은 제목도 응답에 없다**(`06-04` §7.4, `00-30` §7.1).

### 7.2 개봉 뒤

- 운영자 [확인 완료] 한 번으로 `DeathVerification.status = VERIFIED` + `EndingNote.status = RELEASED`·`releasedAt`을 **한 트랜잭션에서** 기록한다.
- 🔴 **본인 쪽 저장 API는 `RELEASED`면 거부한다**(409). 고인 휴대폰으로 누군가 내용을 고치는 것을 막는다.

- 🔴 **되돌리기(잘못 연 경우)는 1차 범위 밖** — 운영자가 장례식장에 확인한 뒤라 드물다. 생긴다면 개발자가 수동 처리(`db-safety.md`).

### 7.3 🆕 사망 뒤에 수락하는 가족 (09-30 지시)

생전에 지정됐지만 **초대를 아직 수락하지 않은 가족**(`PENDING`·`EXPIRED`)도 **사망 뒤에 수락하면 똑같이 볼 수 있다.**

| 상황 | 처리 |
| :--- | :--- |
| 초대 링크가 아직 유효 | 기존 `/invite/:token` 수락 절차 그대로(성함 대조 포함). 수락 즉시 자기 권한만큼 열린 것을 본다 |
| 🔴 **링크가 만료됨** — 다시 만들어 줄 본인이 없다 | `VERIFIED` 이후, **이미 수락한 유족 화면**에 *"아직 수락하지 않은 가족"* **이름·관계만** 보여주고 **[초대 링크 다시 만들기·공유]**. 토큰 발급은 기존 `inviteFamilyDesignation`과 같은 로직, 권한만 *"본인 또는 그 회원의 `VERIFIED` 요청에 속한 ACCEPTED 유족"* 으로 넓힌다 |
| 생전에 **거절(`DECLINED`)** 한 가족 | ❌ **제외** — 거절은 그 가족의 의사다 |
| 수락한 가족이 **한 명도 없고** 링크도 만료 | ⏸ 1차 범위 밖 — 요청할 사람이 없다. 대표번호 문의로 개별 처리, 후속 설계 |

- 전화번호는 보여주지 않는다 — 수락한 유족에게는 이름·관계만. 링크는 그가 아는 경로로 전달한다(§6과 같은 방식).
- 🆕 **09-30 스펙갱신(3-A 구현 중 Sonnet 발견)** — 열람 권한(`EndingNoteGrant`)을 **`ACCEPTED`에만** 줄 수 있어서,
  사후에 수락한 가족은 **편지만 보이고 섹션은 0개**였다. → **본인이 생전에 `PENDING`·`EXPIRED` 가족에게도 권한을
  지정할 수 있게 연다.** 권한은 수락 전까지 아무도 못 읽으므로(조회가 `acceptedUserId`로만 찾는다) 새 위험이 없고,
  *"무엇을 누가 보나는 본인이 생전에 정한다"*(§7) 원칙이 그대로 선다. `DECLINED`는 여전히 불가.
  권한을 **하나도 안 받은** 가족은 사후 수락해도 섹션 0개 — 본인이 정하지 않은 것을 서비스가 대신 열지 않는다.
- 🆕 **09-30 판정(3-B 중 Sonnet 질의) — 수락 전 가족에게 준 `IMMEDIATE` 섹션 권한은 막지 않는다.**
  그 가족이 **생전에** 수락하면 그 순간부터 보인다. 이것은 부수효과가 아니라 **`IMMEDIATE`의 뜻 그대로**다 —
  이미 수락한 가족과 같은 결과이고, 공개 시점(섹션 단위)과 받는 사람(권한)은 본인이 생전에 정했다.
  막으면 본인이 수락 뒤에 권한을 다시 줘야 하는데, 그걸 잊고 돌아가시면 **그 가족에게 영영 안 열린다** — 더 나쁘다.
  🔴 **대신 본인이 알고 주게 한다**: 수락 전 가족에게 `IMMEDIATE` 섹션 권한을 줄 때 그 자리에 사실 한 줄 —
  *"초대를 수락하면 바로 볼 수 있습니다."* (`POSTMORTEM` 섹션에는 띄우지 않는다.)
  🔄 **초대 전(`DRAFT`) 가족도 같다** — `06-04` §8.3-1(09-30)로 화면 대상에 들어왔고, 판단은 이 줄 그대로(막지 않음 + 같은 안내).
  수락 전 가족보다 한 단계(초대) 더 멀 뿐 결과가 같다. **다시 묻지 않는다.**

## 🖥️ 8. 화면

### 8.1 유족 — 개봉 요청 (`/family-shared` 안)

- 지정해 준 분 목록 옆에 **[돌아가셨음을 알리고 열람 요청]**.
  🔄 **09-30 문구 확정**(원안 *"…기록 열기"*, 3-B는 원안으로 구현됨) — 누르면 바로 열리지 않고 **운영자 확인 뒤** 열리므로
  *"열기"* 는 없는 동작을 약속한다. *"열람 요청"* 이 실제 동작이다. 안내 문구(아래)와도 맞는다.
- 입력: **고인 성함(실명)** · **돌아가신 날** · **장례식장 이름 · 전화번호** 또는 **[장례식장 없음]**.
- 안내 문구(사실만): *"운영자가 장례식장에 확인한 뒤 열립니다. 확인은 평일 9시~17시에 하며(주말·공휴일 휴무), 운영시간 기준 12시간 안에 마칩니다. 결과는 이 화면에서 보실 수 있습니다."*
- 🔴 **파일 첨부 칸을 만들지 않는다**(`00-16` §4.3).

### 8.2 유족 — 요청 상태

| 상태 | 화면 |
| :--- | :--- |
| `REQUESTED` | 접수 시각 · *"○시 ○분까지 확인합니다"* · [요청 취소] |
| `VERIFIED`(= 개봉) | 자기 권한만큼의 섹션 + 자기 앞 편지 · [가족에게 알리기] · 아직 수락 안 한 가족 목록(§7.3) |
| `REJECTED` | 반려 사유(코드 → 정해진 문장) · [다시 요청] |

**반려 사유 문장** — ✅ 09-30 확정(3-B에서 Sonnet이 쓴 문장을 검토, 그대로 정본). 코드 위치 `deathVerificationController.ts` `REJECT_REASON_TEXT`.

| 코드 | 문장 |
| :--- | :--- |
| `HALL_NOT_FOUND` | 입력하신 장례식장에서 확인되지 않았습니다. |
| `NAME_MISMATCH` | 고인 성함이 확인한 내용과 맞지 않았습니다. |
| `UNREACHABLE` | 장례식장과 연락이 닿지 않았습니다. |
| `OTHER` | 확인하지 못했습니다. 대표번호로 문의해 주세요. |

- 사실만 적고 탓하는 말이 없다. 문장을 바꿀 때는 이 표부터 고친다.

### 8.3 본인 — 배너

본인이 로그인했는데 자기 앞으로 `REQUESTED` 요청이 있으면 상단 배너:
*"○○님이 엔딩노트 개봉을 요청했습니다. 본인이시면 취소해 주세요."* [취소] → `CANCELLED`.
이미 `VERIFIED`면 취소 버튼 대신 *"개봉되었습니다. 본인이시면 대표번호로 연락해 주세요."*(§7.2 되돌리기는 수동).

- 🔴 **로그인만으로 자동 취소하지 않는다** — 가족이 고인 휴대폰(자동 로그인)을 쓰는 경우가 흔하다.
