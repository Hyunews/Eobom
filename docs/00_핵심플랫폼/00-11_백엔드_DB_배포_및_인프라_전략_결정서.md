지금까지 인프라는 **결정된 적이 없고 흘러왔습니다.** 프론트는 Vercel에 올라가 있고, 백엔드는

지금이 정할 시점입니다.

## 🧭 2. 질문을 다시 세운다

### 2.1 "클라우드 vs 내부 서버"는 정확한 질문이 아니다

진짜 질문은 **"누가 24시간 365일 보안·패치·백업·복구를 책임지는가"** 입니다.

내부 서버를 두면 데이터를 물리적으로 손에 쥐는 대신 아래를 **전부 우리가** 떠안습니다.

| 항목 | 내용 |
| :--- | :--- |
| 물리 보안 | 서버실 출입통제, 도난·화재 대비 |
| 네트워크 | 방화벽, 포트 노출 관리, DDoS, VPN |
| 패치 | OS·PostgreSQL·Node 보안 패치 상시 추적 |
| 백업 | 자동 백업 + **복구 리허설**(백업은 복구해봐야 백업이다) |
| 가용성 | 정전·회선 장애·하드웨어 고장 시 복구, UPS |
| 감사 | 접근 로그 보존, 침입 탐지 |

**"우리 서버라서 더 안전하다"는 직관은 소규모 팀에서 대체로 거꾸로입니다.** 위 항목을 상시 수행할
사람이 없으면, 관리형 클라우드보다 **덜** 안전해집니다.

### 2.2 결정은 하나가 아니라 넷이다

네 가지는 **따로 정할 수 있습니다.** 묶어서 생각하면 판단이 흐려집니다.

| # | 대상 | 현재 | 민감도 |
| :---: | :--- | :--- | :---: |
| 1 | 프론트엔드(정적) | Vercel | 낮음 |
| 2 | 백엔드 API 서버 | 미배포 | 중 |
| 3 | **데이터베이스** | 개발자 PC Docker | **최상** |
| 4 | **파일 스토리지**(사진·서류) | 백엔드 로컬 디스크 | **높음** |

**3·4가 이 결정의 본체**입니다. 1은 이미 해결됐고 2는 상대적으로 교체가 쉽습니다.

## ⚖️ 3. 이 프로젝트 특유의 판단 근거

### 3.1 데이터 민감도가 일반 웹서비스가 아니다

이어봄이 담는 것: **사망 사실·가족관계·상속 상담 내용(재산 정보)·사업자등록증·자격증 사본·정산 계좌**,
그리고 Domain 05의 **유언·엔딩노트**.

특히 05는 화면에서 이미 *"생전에는 철저히 비밀이 보장되며, 사후 이중 동의 시에만 복호화"* 라고
**사용자에게 명시적으로 약속**했습니다(→ `05-01` §1). 이 약속을 지탱하지 못하는 인프라는 선택지가 아닙니다.

유출 사고 시 파장이 "죄송합니다"로 끝나지 않는 데이터입니다.

### 3.2 우리는 이미 백업 없이 데이터를 한 번 잃었다

`security.md` §6에 기록된 사실입니다 — **2026-08-05 마이그레이션 실수로 `User`/`SocialAccount` 유실,
백업 없음.** 로컬 개발이라 재로그인으로 수습됐습니다.

이것을 실패로 볼 게 아니라 **데이터로 봐야 합니다.** 현재 팀의 백업 운영 성숙도를 보여주는 실측치이고,
내부 서버 운영은 **이 사고 유형을 그대로 프로덕션으로 옮기는 선택**입니다.
반면 관리형 DB는 자동 백업·시점 복구(PITR)가 기본 제공이라 이 실수를 흡수합니다.

### 3.3 팀 여건 (2026-08-12 개발자 확인)

- **사내 서버: 있음**
- **전담 인프라/보안 인력: 없음**
- **온프레미스를 강제하는 외부 요구(제휴사·공공기관·경영진 방침): 없음**

**"장비는 있는데 운영할 사람이 없다"** — 이것이 온프레미스에서 가장 위험한 조합입니다. §4.2에서 따로 다룹니다.

## 🔍 4. 선택지 비교

| | A. 온프레미스(사내 서버) | **B. 관리형 클라우드(국내 리전)** | C. 무료 PaaS(현 `render.yaml`) |
| :--- | :--- | :--- | :--- |
| 백업·복구 | **직접 구축·리허설** | 자동 백업 + 시점 복구 기본 | **무료 티어는 백업 없음** |
| 패치·보안 | 전부 자체 | DB·OS는 제공사 책임 | 제공사 |
| 초기 비용 | 장비 보유로 낮아 보임 | 낮음(종량) | 0 |
| 운영 부담 | **매우 높음** | 낮음 | 낮음 |
| 확장 | 장비 증설 필요 | 즉시 | 제한적 |
| 데이터 위치 | 완전 통제 | 리전 선택으로 국내 고정 | **국외일 가능성** |
| 장애 시 | 우리가 밤에 일어남 | 대체로 제공사가 처리 | 슬립·불안정 |
| 적합 시점 | 전담 인력 확보 후 | **지금** | 목업·스테이징 한정 |

### 4.1 C(무료 PaaS)는 프로덕션 후보가 아니다

현재 `render.yaml`의 `plan: free` Postgres는 **백업이 없고 수명 제한이 있습니다.** §3.1 데이터를
담을 곳이 아닙니다. 목업·스테이징 용도로만 유효합니다.
(무료 Postgres 만료 시한은 아직 DB가 생성되지 않아 실제로 돌고 있지 않습니다 → `systems.md` §5.)

### 4.2 "이미 서버가 있는데 왜 안 쓰나" — 정면으로 답한다

**장비가 이미 있다는 사실은 이 결정에서 거의 무관합니다.** 장비값은 이미 지출된 매몰비용이고,
앞으로 드는 비용은 **운영 인건비와 사고 리스크**인데 그건 장비 유무와 무관하게 새로 발생합니다.

"서버가 놀고 있으니 쓰자"로 시작해 → 패치가 밀리고 → 백업 복구를 한 번도 테스트하지 않은 채
운영되다가 → 사고가 나는 것이 전형적인 경로입니다. **§3.2가 이미 그 경로의 첫 구간을 보여줬습니다.**

다만 그 서버를 **버리라는 뜻은 아닙니다.** 올바른 용도가 있습니다 → §6.

## ✅ 5. 권고

> **관리형 클라우드(국내 리전)를 프로덕션으로 채택하고, 온프레미스는 채택하지 않습니다.**
> 단, 전담 인프라 인력을 확보하면 재검토합니다.

### 5.1 구성 권고

| 대상 | 권고 |
| :--- | :--- |
| 프론트엔드 | **Vercel 유지** (정적 자산, 민감도 낮음) |
| 백엔드 API | 관리형 컨테이너/앱 서비스 — **국내 리전** |
| **DB** | **관리형 PostgreSQL — 자동 백업 + 시점 복구 필수, 국내 리전** |
| **파일 스토리지** | **S3 호환 오브젝트 스토리지** — 로컬 디스크 금지 |
| 백업 | 관리형 자동 백업 + **분기 1회 복구 리허설**(§7.3) |

### 5.2 국내 리전을 권고하는 이유

개인정보보호법은 온프레미스를 요구하지 않으며 **클라우드는 합법이고 일반적**입니다.

> 🔵 **2026-08-18 스펙갱신(`00-17` §3.1)** — 이 절의 구 서술 *"국외 이전에는 별도 고지·동의 등
> 추가 의무가 따른다"* 는 **부정확해서 내렸습니다.** **개인정보보호법 §28조의8**의 국외이전 근거는
> **5가지**이고 동의는 그중 하나일 뿐이며, **클라우드 호스팅은 "계약 이행을 위한 처리위탁·보관"에
> 해당해 별도 동의가 아니라 개인정보처리방침 공개로 갈음**합니다. **즉 해외 리전이 위법인 것이
> 아닙니다.** 정정 이유는 *"위법 프레임으로 적어두면 «해외 SaaS는 무조건 못 쓴다»는 잘못된 운영
> 규칙이 파생되는데, 실제로 Vercel·구글 로그인 등 국외 요소가 이미 있기 때문"* 입니다.

**국내 리전 권고는 그대로 유지합니다. 근거만 바뀝니다** — *"위법을 피한다"* 가 아니라
**"논점 자체를 만들지 않는다"**(공개 항목·사업자 실사·문의 대응이 통째로 없어짐)입니다.
§3.1 데이터 성격상 불필요한 논점은 만들지 않는 편이 낫습니다.

> ✅ **ISMS-P 의무대상 여부는 해소됐습니다 → `00-17` §2.** 현행 기준으로도 진행 중인 개편안
> 기준으로도 **이어봄은 대상이 아닙니다.** **CSAP는 클라우드 사업자가 받는 것이라 이어봄의
> 과제가 아니며**(공공 납품 시에만 논점, `00-17` §2.3) 이 절의 검토 대상에서 내립니다.
> 다만 인증체계 개편이 **2027년까지 유동적**이므로 재확인은 *"오픈 전"* 이 아니라
> **`00-17` §5의 트리거(T1~T4)** 로 겁니다 — 기준이 바뀌는 시점은 우리 사정이 아니기 때문입니다.
>
> ⚠️ 이 문서도 `00-17`도 **법률 자문이 아닙니다.**

### 5.4 ✅ 오브젝트 스토리지만 먼저 확정 — **Cloudflare R2** (2026-09-03 개발자 확정)

> 🔵 **§8의 4건 전체가 아니라 스토리지 하나만 떼어 확정합니다.** 근거는 **버킷이 서버 이전과
> 독립**이기 때문입니다 — 기존 Render를 그대로 둔 채 붙습니다. 이 하나가 `05-01` §2.6(추모관
> 사진 오픈)과 `06-05` Phase D(유족 메시지 음성)를 **동시에** 풀어 줍니다.

#### 5.4-1 요건 대조

| §5.1 요건 | R2 | |
| :--- | :--- | :---: |
| **S3 호환** | S3 호환 API — 기존 `@aws-sdk/client-s3` 그대로 | ✅ |
| 로컬 디스크 금지 | 오브젝트 스토리지 | ✅ |
| 전송 중 암호화 | TLS. 커스텀 도메인 + Always Use HTTPS로 평문 차단 | ✅ |
| 저장 시 암호화 | **AES-256-GCM 자동**(메타데이터 포함), 설정 불필요 | ✅ |
| 버킷 비공개 | 기본 비공개 | ✅ |
| 실수 삭제 방어 | 🔴 **Object Versioning 없음**. Bucket locks도 **단독으론 부족**(§5.4-5-1-1) → **3층 방어**(§5.4-5-2) | 🟡 |
| **국내 리전** | 🔴 **불가** → §5.4-3 | ❌ |

#### 5.4-2 비용 — 이 규모에서는 사실상 0원

**무료 한도는 매월 갱신**입니다(S3처럼 12개월 체험이 아닙니다) — 저장 **10GB-month** ·
Class A(쓰기) **100만/월** · Class B(읽기) **1,000만/월** · **삭제는 무료 연산**.
초과 시 저장 $0.015/GB·월 · Class A $4.50/백만 · Class B $0.36/백만. **청구는 올림 계산**입니다.

| 이어봄 환산 (음성 m4a 5분 ≈ 2.5MB) | 용량 | 월 비용 |
| :--- | :--- | :--- |
| 음성 메시지 **4,000건** | ≈ 10GB | **₩0** |
| 40,000건 | ≈ 100GB | 약 $1.5 |

> ✅ **`Egress(내려받기) 무료`가 이 프로젝트에 특히 중요합니다** — `06-05` §5.4의 반출
> (사망·탈퇴 시 백업)이 **몇 번을 내려받아도 0원**입니다. S3였다면 GB당 과금이라 반출 기능을
> 인색하게 설계해야 했습니다. **비용이 기능 설계를 제약하지 않습니다.**

#### 5.4-3 🔴 감수하는 것 ① — R2에는 "한국"도 "아시아"도 없습니다

R2의 위치 장치는 **두 종류이고 성격이 다릅니다.**

| | 값 | 성격 |
| :--- | :--- | :--- |
| **Location Hint** | `apac`·`wnam`·`enam`·`weur`·`eeur`·`oc` | 🟡 공식 문서 표현 — ***"최선 노력이며 보장이 아니다"*** |
| **Jurisdiction**(실제 보장) | **`default`·`eu`·`fedramp` 셋뿐** | 🔴 **APAC·한국 없음** |

🔴 **즉 보관 국가를 계약으로 보장받는 방법이 R2에는 없습니다.** `apac` 힌트는 노력 표시입니다.

🔴 **버킷 생성 시 한 번에 정해야 합니다** — jurisdiction은 **생성 후 변경 불가**이고,
힌트는 **최초 생성 시에만** 반영됩니다(같은 이름으로 지웠다 다시 만들면 원래 위치를 씁니다).

> ✅ **수용 근거**: `00-17` §3.1이 이어봄을 **개인정보보호법 §28조의8 ①3호**(계약 이행에 필요한
> 처리위탁·보관 → **별도 동의 불요, 처리방침 공개로 갈음**)에 해당한다고 이미 판정했습니다.
> **새 판단이 아니라 선 판단의 적용**입니다. 등재는 `00-17` §4.2.
> ✅ **실제 배치 확인(2026-09-03)**: 대시보드 표시 **`아시아 태평양(APAC)`** — `apac` 힌트가
> 반영됐습니다. **지연시간·서사 양쪽에 유리한 결과**입니다.
> 🔴 **다만 이것으로 "이전되는 국가"란을 채울 수 없습니다** — **APAC은 지역이지 국가가 아닙니다.**
> 법이 요구하는 것은 국가 단위 명시(미국·독일·일본 등)입니다. 그리고 jurisdiction은 여전히
> `default`라 **APAC 배치가 계약상 고정된 것도 아닙니다.**
> ⏸ **따라서 "국가"란은 계속 보류**하되, **관측값 `APAC`은 기록**해 둡니다(`00-17` §3.4).
> **`00-19`가 아직 미게시**(게시 블로커는 위치정보법 신고, `00-22` B-1)라 **지금 미확정이어도
> 노출 위험이 없습니다.** 🔴 **게시 전에는 반드시 국가 단위로 확정**해야 하며, 실무 표기는
> *"미국 및 Cloudflare 글로벌 네트워크 소재 국가(데이터센터 목록 링크)"* 형태가 됩니다.

#### 5.4-4 🔴 감수하는 것 ② — 키를 Cloudflare가 갖고 있습니다

R2는 AES-256으로 자동 암호화하지만 **키를 Cloudflare가 관리**합니다. AWS SSE-KMS 같은
**고객 관리 키(CMK)가 없습니다.** 금고에 넣되 열쇠는 금고 회사가 가진 구조입니다.

> 🔴 **따라서 앱단 선(先)암호화가 "권장"이 아니라 R2를 쓰는 이상 필수 조건입니다.**
> `ENDING_NOTE_ENCRYPTION_KEY` 파생 키로 **올리기 전에 잠급니다**(`06-05` §5.2 ②).
> R2에는 **이어봄 키로 잠근 덩어리**만 올라가고, R2 자동 암호화는 그 위 한 겹입니다.
> ✅ **이것이 §5.4-3을 실질적으로 무력화합니다** — 처리방침에 ***"음성 파일은 암호화된 상태로만
> 이전되며 복호화 키는 국외로 이전되지 않습니다"*** 라고 쓸 수 있습니다. 국외이전을 감수한 이상
> **이 문장 하나가 방어선 전부**입니다.

#### 5.4-5 🟡 남는 주의점

| | |
| :--- | :--- |
| **내구성 수치 미공개** | S3는 11 nines를 명시하는데 R2 문서는 *"designed for high data durability"* 뿐이고, 내구성은 **리전 내 복제**로 확보한다고만 서술합니다. 🔴 **R2 한 곳에만 두면 안 됩니다** — §5.4-5-1 + `06-05` §5.4 반출로 **이용자 손에 사본**을 만듭니다 |
| **권한 모델이 단순** | IAM 정책 JSON이 아니라 **버킷 범위 API 토큰**입니다. 세밀 제어 수단이 **버킷 분리뿐** → §5.4-6 |

##### 5.4-5-1 🔴 정정(2026-09-03) — **R2에는 Object Versioning이 없습니다**

> 🔴 **개발자 확인이 맞고 이전 서술이 틀렸습니다.** 이 문서 초판(같은 날 오전)은 *"Object
> Versioning(2024~) — 생성 시 활성화 필수"* 라고 적었으나, **출처가 서드파티 블로그였고
> 공식 문서에는 없습니다.** R2 공식 버킷 기능 목록은 Public buckets · CORS · Local uploads ·
> Delete buckets · **Bucket locks** · Event notifications · **Object lifecycles** · Storage
> classes이며 **versioning 토글이 없습니다.** 대시보드에서 켤 것이 애초에 없었습니다.

**대체 수단 — `Bucket locks`가 이 도메인에는 버저닝보다 낫습니다.**

| | |
| :--- | :--- |
| 막는 것 | **삭제 + 덮어쓰기** (버저닝은 지운 뒤 되살리는 것, 락은 **애초에 못 지우게** 하는 것) |
| 보존 방식 | ① 기간(`Age`, 초 단위) ② 지정일까지 ③ **`Indefinite`(무기한)** |
| 적용 범위 | 프리픽스별 규칙, 설정당 최대 1,000개. **기존 객체에도 소급 적용** |
| 우선순위 | 규칙이 겹치면 **가장 엄격한(긴) 것**이 이깁니다. **lifecycle 규칙보다 락이 우선** |
| 부수효과 | 락이 하나라도 있으면 **버킷 비우기·폴더 삭제가 차단**됩니다 |

##### 5.4-5-1-1 🔴 `Age` 락의 정확한 의미 — **보존기간 30일만으로는 취지가 달성되지 않습니다**

> 🔴 **2026-09-03 재확인 · 이 절의 이전 서술을 정정합니다.** *"`Age` 30일이면 실수 삭제를
> 막으면서 정당한 파기는 통과한다"* 고 적었는데, **뒷문장만 맞고 앞문장은 크게 과장**입니다.

**`Age`는 "업로드 시점부터 N초 동안 보호"입니다.** 나이가 그 값을 **넘어서면 보호가 풀립니다.**
공식 문서의 목적어가 *"accidental **premature** deletions"*(**이른** 삭제) 인 이유입니다.

| 객체 나이 | `Age` 30일 락 |
| :--- | :--- |
| 0~30일 | ✅ 삭제·덮어쓰기 차단 |
| **31일~수십 년** | 🔴 **완전 무방비** |

🔴 **이 도메인 데이터의 수명은 거의 전부가 아래쪽 칸에 있습니다.** 5년 전에 녹음된 음성은
락이 전혀 지켜주지 않습니다. **즉 `Age` 30일이 실제로 막는 것은 "갓 올린 파일을 즉시 지우는
버그" 하나뿐**이며, 값은 있지만 **`00-11` §5.4-5의 내구성 걱정에 대한 답이 아닙니다.**

**왜 길게 걸 수 없나 — 근본 제약**

락은 **시간 기반**이지 **의도 기반**이 아닙니다. 그래서 두 요구를 동시에 만족시킬 수 없습니다.

| 요구 | 필요한 락 |
| :--- | :--- |
| 수십 년 보존 | 길게 / `Indefinite` |
| **탈퇴·보유기간 만료 시 파기**(법적 의무) | 짧게 |

🔴 **`Indefinite`는 절대 걸지 않습니다** — 탈퇴자 음성을 영영 못 지워 **파기 의무와 정면충돌**
합니다(`06-05` §5.4-2). **가장 안전해 보이는 설정이 위법을 만드는 자리**입니다.
🔴 **프리픽스를 이용자별로 쪼개 개별 락을 거는 우회도 안 됩니다** — 설정당 **최대 1,000규칙**이라
이용자 1,000명에서 막히고, 규칙을 앱이 조작하려면 **버킷 설정 편집 권한**(삭제 권한보다 위험한)이
필요해집니다.

⚠️ **락은 금고가 아니라 난간입니다.** R2에는 S3의 **compliance mode가 없습니다** — 최소 보존
바닥값·승인 절차·해제 지연이 전부 없고, **버킷 설정 편집 권한이 있는 토큰이면 규칙을 지우고
바로 삭제**할 수 있습니다. **보안 경계는 락이 아니라 토큰 범위**입니다.
⚠️ 락 규칙이 하나라도 있으면 **버킷 비우기가 차단**됩니다(정리 시 규칙 먼저 제거).

##### 5.4-5-2 ✅ 그래서 방어는 3층으로 쌓습니다

**어느 한 층도 단독으로는 취지를 달성하지 못합니다.**

| 층 | 위치 | 막는 것 | 한계 | 상태 |
| :---: | :---: | :--- | :--- | :--- |
| **①** `Age` 30일 락 | 스토리지 | 업로드 직후 즉시 삭제 | 🔴 **31일째부터 무효** | 🔴 **미채택**(§5.4-5-3) |
| **②** 🆕 **아카이브 버킷 복제** | 스토리지 | 런타임 토큰 침해 · 앱 버그 · **정리 스크립트** *(전 기간)* | 계정 전체 침해엔 무력 | 🔴 **Phase D 필수** |
| **③** **반출**(`06-05` §5.4) | 이용자 | 이어봄 소멸 · 계정 침해 | 이용자가 안 받으면 없음 | ✅ 확정 |
| **④** 고유키 + 소프트 삭제 | 앱 | 정상 동작 중의 덮어쓰기·오삭제 | 🔴 **앱을 우회하면 무력** | ✅ 확정(§5.4-5-3) |

🆕 **② 아카이브 버킷** — R2 **Event notifications**로 쓰기 시 별도 버킷에 사본을 떨굽니다.
🔴 **핵심은 "그 버킷 토큰을 런타임 앱이 갖지 않는 것"** 입니다. 그래야 앱 토큰이 통째로
털려도 사본이 남습니다. R2 토큰 등급은 `Admin Read & Write`·`Admin Read`·`Object Read & Write`·
`Object Read only` 넷뿐이라 **"쓰기는 되고 삭제는 안 되는" 등급이 없습니다** —
`Object Read & Write`는 `DeleteObject`를 포함합니다. **권한으로 삭제를 못 막으니 사본을 분리**합니다.

🔴 **아카이브에도 `Indefinite`는 걸지 않습니다.** 파기 의무는 사본에도 그대로 적용되므로,
탈퇴 파기 시 **원본과 아카이브를 함께** 지웁니다(`06-05` §5.4-2 절차에 포함).

##### 5.4-5-2-1 🔴 ②층의 실제 형태 = **Cloudflare Worker 1개** (스펙 보정)

> 🔴 **09-03 보정 — 위 문장이 작업량을 크게 축소해 적었습니다.** *"Event notifications로 사본을
> 떨굽니다"* 라고 써서 **대시보드 스위치 하나**처럼 읽히게 했으나, 실제로는 **배포 대상 구성요소가
> 하나 늘어납니다.** 개발자가 구현 단계에서야 이를 알게 됐습니다 — **스펙이 미리 말했어야 합니다.**

**왜 Worker가 필요한가 — 선택이 아니라 귀결입니다**

```
요구: 아카이브 사본은 "런타임 앱 토큰이 닿지 않는 곳"에 있어야 한다 (§5.4-5-2 ②)
  └ 백엔드가 직접 2번 PUT? → 🔴 백엔드가 아카이브 키를 갖게 됨 → 요구가 무너짐
  └ R2 네이티브 버킷 복제?  → 🔴 없음 (S3의 CRR에 해당하는 기능이 R2엔 없다)
  └ 남는 유일한 경로:  Event notification → Queue → Queue를 읽는 건 Worker뿐
```

🔵 **"백엔드가 아카이브 키를 갖게 됨"이 이 구조의 전부입니다.** 사본을 두는 이유가
*"앱이 털려도 남게"* 인데, 앱이 사본에 쓸 수 있으면 앱이 사본을 지울 수도 있습니다
(§5.4-5-2 — R2 토큰에 *쓰기 O·삭제 X* 등급이 없습니다).

**✅ 키가 아예 존재하지 않는 구조** — Worker는 S3 액세스 키를 쓰지 않고 **바인딩**
(`wrangler.toml`의 `SOURCE_BUCKET`·`ARCHIVE_BUCKET`)으로 접근합니다.

| 주체 | 접근 수단 | 원본 | 아카이브 |
| :--- | :--- | :---: | :---: |
| 백엔드(Render) | S3 액세스 키 | ✅ | 🔴 **수단 없음** |
| Worker(Cloudflare) | 바인딩 | ✅ | ✅ |

🔴 **백엔드가 "아카이브 키를 안 받은 것"이 아니라 "훔칠 키가 애초에 없는 것"** 입니다.
`.env`가 통째로 유출돼도 아카이브에는 닿을 문자열이 없습니다.

**🔵 "서버가 하나 더 뜨는 것"이 아닙니다** — Worker는 상주 프로세스가 아니라 **이벤트가 올 때만
실행되는 함수**입니다. 인스턴스·헬스체크·재시작·스케일링이 없고, 코드는 22줄입니다.
배포 5단계는 **일회성**이며 이후 손댈 것이 없습니다(`eobom/workers/r2-archive-relay/README.md`).

**💰 비용 ₩0** (2026-09-03 공식 문서 확인) — Workers 무료 10만 req/일 · Queues 무료
**10,000 ops/일**(메시지당 3 ops ≈ **3,300건/일**). 음성 업로드가 이를 넘길 일은 한참 뒤입니다.
> 🟡 **무료 플랜은 큐 메시지 보관이 24시간 고정**입니다. Worker가 24시간 넘게 연속 실패하면 그
> 메시지는 버려집니다 — **원본은 멀쩡하고 사본만 안 만들어집니다.** 유료 전환 시 4~14일.

⏸ **배포 시점 = `R2_ENABLED`를 `true`로 켜는 때.** 플래그가 `false`인 동안은 음성이 R2에 올라가지
않으므로 급하지 않지만, 🔴 **켜는 순간부터는 앱 밖 방어가 0인 상태**가 됩니다(락 미채택, §5.4-5-3).

> 🔴 **아카이브 버킷은 Phase D 필수입니다**(09-03 승격, §5.4-5-3). **첫 음성이 올라가는 시점에
> 함께 서 있어야** 합니다 — 락을 미채택했으므로 **앱 밖의 방어는 이 층이 유일**합니다.
> ⏸ 지금 만들 필요는 없습니다(버킷명 예정: `eobom-farewell-voice-archive`).

##### 5.4-5-3 ✅ 앱단 ④층 — 고유키 + 소프트 삭제 **(채택)** · 락은 **미채택**

> 🔵 **출처**: `[Gemini]` 검토 의견(2026-09-03). **처방 두 건은 그대로 채택**하고,
> **근거 한 건은 정정**합니다. 아래 "전제 정정" 참조.

✅ **고유키**: 객체 키에 **UUID·타임스탬프**를 넣어 같은 키 덮어쓰기가 **원천적으로 발생하지
않게** 합니다. 재녹음은 *덮어쓰기가 아니라 새 키 쓰기* 가 됩니다.

✅ **소프트 삭제**: 이용자가 삭제를 눌러도 **R2를 즉시 지우지 않고 DB 상태만 `삭제대기`로**
바꿉니다. 실제 R2 삭제는 유예 종료 후 **사람 승인을 거친 배치**가 합니다(`AGENTS.md` §1
CONFIRM과 같은 취지). 🔴 **런타임 요청 경로에서 `DeleteObject`를 호출하지 않는 것**이 이 설계의
핵심이며, 이것 하나가 락보다 넓게 막습니다. → `06-05` §5.4-2 · Phase D.

**🔴 전제 정정 — "락은 개발자도 못 푼다"는 R2에 해당하지 않습니다**

*"한 번 걸면 못 풀어서 사용자 기능을 가로막는다"* 는 **AWS S3 Object Lock의 compliance mode**
설명입니다. **R2에는 compliance mode가 없습니다** — 버킷 설정 편집 권한이 있는 토큰이면
**규칙을 지우고 바로 삭제**할 수 있습니다(§5.4-5-1-1). 또한 위 ④층을 깔면 **락이 사용자 기능을
막을 일 자체가 없습니다** — 고유키라 재녹음이 덮어쓰기가 아니고, 소프트 삭제라 0일차에
`DeleteObject`를 부르지 않기 때문입니다.

**🔴 그럼에도 락을 미채택하는 진짜 이유** — *못 풀어서* 가 아니라 **효용이 좁아서**입니다.
락의 유효 구간(0~30일)은 ④층 소프트 삭제가 이미 논리적으로 덮고, 그 위에 남는 위험
(*앱을 우회한 직접 삭제*)은 **전 기간에 걸쳐 ②층 아카이브가 더 잘 막습니다.** 설정을 하나
줄이는 편이 낫습니다. 🔵 **다만 훗날 락을 걸게 되면 `Age`는 반드시 유예 30일과 일치**시킵니다
(길면 파기 대상을 락이 막습니다).

**🔴 그래서 ②층 아카이브 버킷이 🟡 권고 → 필수로 승격됩니다.** ④층은 **앱이 정상 동작할 때만**
성립하는 *정책*이지 *강제*가 아닙니다. R2는 우리 DB의 `삭제대기` 플래그를 조회하지 않으므로,
**정리 스크립트·마이그레이션·토큰 유출**에는 소프트 삭제가 아무 역할도 하지 못합니다.
🔴 **이 프로젝트는 정확히 그 경로로 데이터를 두 번 잃었습니다**(08-05 · 08-27, 루트 `CLAUDE.md`).
앱 밖에서 벌어지는 일은 **앱 밖의 사본**으로만 막힙니다.

> 🔵 **"소프트 삭제가 업계 표준"은 맞습니다.** 다만 표준 구성은 *소프트 삭제 **단독*** 이 아니라
> **소프트 삭제 + 스토리지 계층 버저닝/복제**입니다(S3 Versioning을 기본 켜는 이유가 그것입니다).
> R2에 versioning이 없어서 그 자리를 **아카이브 버킷으로 직접 만드는 것**뿐, 층을 빼는 게
> 아닙니다.

##### 5.4-6-1 ✅ 현재 토큰 — **버킷별 3개로 분리 완료**(2026-09-03)

> ✅ **09-03 갱신.** 최초 발급은 3버킷 공용 1개였고 아래 🟡 권고를 남겼는데, 개발자가 **같은 날
> 버킷별 토큰을 새로 발급해 교체**했습니다. **권고 해소** — 음성 서버가 침해돼도
> `eobom-biz-docs`(자격증 사본)는 열리지 않습니다. §5.4-6의 버킷 분리가 이제 실제로 작동합니다.

🔴 **이 조치의 무게** — R2 토큰 등급에는 **"쓰기는 되고 삭제는 안 되는" 선택지가 없습니다**
(`Admin Read & Write` · `Admin Read` · `Object Read & Write` · `Object Read only` 넷뿐이고,
`Object Read & Write`는 `DeleteObject`를 포함합니다). 게다가 **Bucket lock은 설정 편집 권한이
있는 토큰이면 규칙째로 지울 수 있습니다**(§5.4-5-1-1). 즉 **보안 경계는 락이 아니라 토큰 범위**
이고, 버킷별 분리가 이 도메인에서 가장 실효 있는 방어입니다.

> 🟡 **남은 것(비차단)**: **TTL 무제한 + 클라이언트 IP 필터 미지정** — 유출 시 무기한 유효를
> 뜻합니다. **키 회전 절차**를 `security.md`에 두고, 운영 전환 시 토큰에 만료를 겁니다.
> 🟡 **아카이브 버킷 토큰은 런타임 앱에 주지 않습니다**(§5.4-5-2 ②) — 분리의 연장선입니다.

##### 5.4-6-2 ✅ `.env` 변수명 (정본)

`eobom/backend/.env`. 🔴 **값은 커밋 금지**(`security.md`) — `.env.example`에는 자리만 둡니다.

```bash
# Cloudflare R2 (docs 00-11 §5.4). S3 호환이라 @aws-sdk/client-s3를 그대로 쓴다.
R2_ACCOUNT_ID=
R2_ENDPOINT=https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com
# ✅ 09-03 버킷별 토큰 3개로 분리 완료(§5.4-6-1). 접미사로 구분한다.
R2_ACCESS_KEY_ID_VOICE=
R2_SECRET_ACCESS_KEY_VOICE=
R2_ACCESS_KEY_ID_MEDIA=
R2_SECRET_ACCESS_KEY_MEDIA=
R2_ACCESS_KEY_ID_DOCS=
R2_SECRET_ACCESS_KEY_DOCS=
R2_BUCKET_FAREWELL_VOICE=eobom-farewell-voice
R2_BUCKET_MEMORIAL_MEDIA=eobom-memorial-media
R2_BUCKET_BIZ_DOCS=eobom-biz-docs
# 기능 플래그. 기본값 false — CLOVA_STT_ENABLED와 같은 취지(06-04 §6.4-9-8-3).
# 버킷·토큰이 서 있어도 이 값이 false면 업로드 경로를 열지 않는다.
R2_ENABLED=false
```

🔵 **`R2_ENDPOINT`는 계정 ID가 들어간 문자열**이라 `R2_ACCOUNT_ID`와 중복이지만, SDK에
그대로 넘기는 값이라 **조립하지 않고 통째로 둡니다** — `CLOVA_SPEECH_INVOKE_URL`과 같은 방식입니다.

🔴 **`[Claude:Sonnet]` Phase D 착수 시 첫 할 일** — 위 접미사 표기는 §5.4-6-1 분리를 반영한
**정본 안(案)** 입니다. 개발자가 이미 `.env`를 채워 뒀으므로, **실제 `.env`의 키 이름을 먼저
확인**하고 다르면 **코드를 `.env`에 맞추지 말고 이 문서와 `.env` 중 무엇을 바꿀지 물어봅니다.**
(값은 읽지 않습니다 — 키 이름만.) 버킷별로 S3 클라이언트를 **3개 따로** 만듭니다.

## 🖥️ 6. 사내 서버의 올바른 용도

프로덕션 DB를 올리지 않을 뿐, 놀릴 필요는 없습니다.

1. **개발·스테이징 환경** — 실데이터 없이 배포 리허설. 지금 개발자 PC Docker가 하던 역할을 승계.
2. **백업 보관 사본** — 클라우드 자동 백업과 별개로 주기적 사본을 사내에 보관(3-2-1 백업 원칙).
   **단, 개인정보가 포함된 백업은 암호화 저장하고 접근을 통제해야 합니다.**
3. **내부 도구** — 사내 대시보드, 배치 작업 등 개인정보를 다루지 않는 워크로드.

**금지**: 프로덕션 DB, 유족·고인 개인정보 원본, 엔딩노트 암호화 데이터.
