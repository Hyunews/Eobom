## 🧭 2. 왜 다시 잡았나 — 반복의 원인

**증상**: 2026-09-16~17 이틀 동안 *"측정 → 위반 목록 → 개별 수정 → 재측정"* 을 반복했고,
그 결과물은 토큰 치환·`44px` 맞추기·클래스 추출이었다. 실제로 화면이 나아진 것은 **사람이 직접
*"줄글 나열이 지저분하다"* 고 지적했을 때뿐**이었다(→ `walkthrough.md` 09-16 CounselingPage 4차 후속).

**원인 1 — 수치를 품질로 착각했다.** `00-38` §11의 DoD 9개(44px·1.8배·16px)는 **접근성 최저선**이지
디자인 품질 기준이 아니다. 전부 통과해도 답답하거나 촌스러울 수 있다.

**원인 2 — 규칙이 코드에 흩어져 있었다.** 2026-09-18 실측 기준 **인라인 스타일 1,426개**
(`.tsx` 53개 중 49개 파일). `00-38` §10 Phase 4 주석이 *"인라인이 982 → 1,304개로 늘었다"* 고
경고했는데 그 뒤로 더 늘었다. 화면 규칙이 공통 CSS가 아니라 컴포넌트마다 숫자로 박혀 있으니,
행간 하나 고치는 데 14곳을 찾아야 하고 다음 사람이 또 인라인으로 짠다.

**원인 3 — 규칙이 새 시도를 막았다.** `token-guard.js`(PreToolUse 훅)가 허용하는 글자 크기가
**`0.85`·`0.95`·`1.05`·`1.3rem` 네 개**뿐이고 HEX 색은 전부 위반으로 잡았다. `00-09` §2.3은
*"협상 대상이 아님"* 으로 `18px`·`56px`·`1.7`을 못박았고, §6.3은 *"세련됨은 이 6개"* 라며 미감까지
규정했다. **새 디자인을 하는 게 아니라 기존 틀 안에서 조립하는 상태**였다.
→ 훅은 2026-09-18 사람이 주석 처리했다.

## 🧩 6. 규칙

각 규칙은 기준 화면에서 실제로 정해진 것이고, 괄호 안은 그렇게 정한 이유다.
🔵 **번호를 제목에 세지 않는다** — §9.3대로 화면을 하나씩 구현하면서 **여기 계속 추가**되기 때문이다.
지운 번호는 비워 둔다(다른 문서가 `§6-14`처럼 참조한다).

### 6.1 구조

1. 🔴 **카드와 그림자를 쓰지 않는다.** 구분은 **1px 선과 여백**으로 한다.
   (카드 안에 카드, 그 안에 칩 트랙 — 상자가 3겹이었다)
2. 🔴 **본문 읽기 폭을 고정**하고 넓은 화면을 채우지 않는다. (§5)
3. 🔴 **사이드바 대신 헤더 드롭다운.** 좌측 72px 아이콘 바를 없애고, 헤더의 모드 버튼
   (`생전 준비` / `임종 및 사후 정리`)에 호버하면 하위 메뉴가 열린다. 메뉴 구성은
   `modeNav.ts`가 정본이고 `status: 'preview'`인 항목에는 **"준비 중"** 배지를 단다.

### 6.2 활자와 위계

4. 🔴 **제목은 명조, 본문은 산세리프.** (§4)
5. 🔴 **긴급도를 색 배지로 만들지 않는다.** *되돌릴 수 없음* 을 **12px 붉은 글자 한 줄**로
   제목 위에 둔다. (회색 알약 배지가 모든 항목에 붙어 위계가 사라져 있었다)
6. 🔴 **기한은 오른쪽 끝 열에 회색으로 정렬**한다. 제목 옆에 붙이지 않는다.
   (제목 길이에 따라 배지가 다음 줄로 밀려 레이아웃이 흔들렸다)

6-1. 🔴 **목록에는 설명문을 두지 않는다 — 웹·모바일 공통** (2026-09-18 사람 결정).
   한 줄은 **제목 + 기한**이 전부다. 설명이 필요하면 **제목을 눌러 모달**로 본다(규칙 9).
   🔵 처음에는 *"넓은 화면은 읽을 여유가 있으니 웹에는 남기자"* 고 했으나, **같은 문장이 모달에서는
   빠지고 목록에는 남는** 상태가 되어 규칙 11과 어긋났다. 목록은 **훑는 곳**이지 읽는 곳이 아니다.

### 6.3 조작

7. 🔴 **버튼은 밑줄이 아니라 테두리**로 만든다. (`내용 보기` · `전문가 상담` · `장사시설 찾기`)
8. 🔴 **체크는 체크박스를 눌러야만 된다.** 행 전체를 클릭 영역으로 삼지 않는다.
9. 🔴 **항목 제목을 누르면 안내가 열린다.** 체크와 안내는 다른 동작이다.

### 6.4 안내(모달)

10. 🔴 **모달은 세 줄뿐이다** — **제목 · 기한 · 근거**. 그 이상 넣지 않는다.
    🔵 *근거*와 *기관*을 따로 두지 않는다 — **근거 줄 자체가 링크**다(§6-14). 기관이 특정되는
    3건만 그 자리에 기관명이 오고, 나머지는 법령명과 조문이 온다.
11. 🔴 **해설하거나 조언하는 문장을 넣지 않는다.** 모달은 **사실만** 준다.
    (2026-09-18 사람 결정 — *"화장 후에는 부검·재확인이 불가능합니다"*, *"'언제까지'가 아니라
    '언제 이후에' 가능한지의 문제입니다"* 같은 문구를 뺐다. 해석은 사용자 몫이고, 더 필요하면
    전문가 상담으로 보낸다.)
    🔵 **모달에 완료 버튼을 두지 않는다** — 체크 경로가 둘이 되면 규칙 8과 어긋난다.

### 6.5 모바일

12. 🔴 **간소화하고 줄글을 최소로 한다.** (2026-09-18 사람 지시)
    🔵 목록에서 설명문을 빼는 것은 이제 **웹도 같다**(규칙 6-1). 아래는 **모바일에만** 해당한다.
    - *"가장 급한 것"* 같은 **상단 요약 블록을 두지 않는다**
    - 부제를 두지 않는다 (제목이 이미 말하고 있다)
    - 각 행 오른쪽에 **꺾쇠(›)** 로 "누르면 더 있다"를 표시한다
    - 모달은 **바텀시트**로 열고, 닫기는 X 아이콘이 아니라 **하단 버튼**으로 둔다
    - 모달 안에서도 더 줄인다 — 근거를 `장사법 제6조`까지만(웹은 `감염병 등 예외`도 표시)

### 6.6 공통

13. 🔴 **줄바꿈을 코드에 박지 않는다.** `<br>` 대신 `text-wrap: pretty`로 브라우저가 나누게 한다.
    (`사망 후 24시간 경과 전<br>화장·매장 금지`는 그 항목 하나에만 맞는 줄바꿈이었다)

14. 🔴 **기관을 못 찾으면 법령으로 보낸다** (2026-09-18 사람 결정 — *"따로 검색되지 않은 기관명은
    관련 법령을 따라갈 수 있도록 법령정보 사이트로 연결한다"*). 모달의 `기관` 줄은 아래 순서로 정한다.

| 순위 | 조건 | 링크 |
| :---: | :--- | :--- |
| **1** | 기관·서비스가 특정됨 | 그 사이트로. 지금 해당하는 것은 **3건** — `정부24`(id 7) · `e하늘 장사정보시스템`(id 4) · `안심상속 원스톱 서비스`(id 9·18, 정부24 안의 서비스) |
| **2** | `legalBasis`에 **법령**이 있음 | 🔴 **국가법령정보센터**로. **13건** 해당 |
| **3** | 둘 다 아님 | **`기관` 줄을 생략한다.** 빈 링크를 만들지 않는다. **5건** — *"확인 필요"*(id 17·22) · *"제도별 상이"*(id 21) · *"실무: …"*(id 1) · `-`(id 3·19) |

#### 🔗 국가법령정보센터 URL — **실측으로 확인한 규칙** (2026-09-18)

```
https://www.law.go.kr/법령/{법령명}/{제N조}
```

🔵 **세 가지를 실제로 열어보고 확인했다** — 추측이 아니다.

| 확인한 것 | 결과 |
| :--- | :--- |
| `…/법령/민법/제1019조` | ✅ **제1019조(승인, 포기의 기간)** 본문만 표시 — 조문 단위로 정확히 열린다 |
| `…/법령/장사법/제6조` | ✅ **약칭이 통한다.** "장사 등에 관한 법률(약칭: 장사법)" 제6조(매장 및 화장의 시기)가 열린다 |
| `…/법령/상속세 및 증여세법/제67조` | ✅ **공백이 들어가도 된다.** 인코딩만 하면 그대로 동작 |

🔵 **그래서 `legalBasis` 값을 거의 그대로 쓸 수 있다.** 변환은 두 가지뿐이다.
· `§` → `제N조` (예: `장사법 §6` → `장사법/제6조`)
· **항(`①②③`)은 떼고 조까지만** 건다 (예: `민법 §1019①` → `민법/제1019조`)
· 조문이 없으면 법령까지만 (예: `국민건강보험법` → `…/법령/국민건강보험법`)

🟡 **링크 라벨은 법령명과 조문을 그대로 보여준다** — `장사법 제6조 ↗`. *"법령정보센터"* 라는
사이트 이름을 라벨로 쓰지 않는다(사용자가 알고 싶은 건 **무슨 법 몇 조**다).

## ✅ 7. 웹과 모바일의 관계

🔴 **같은 화면이지만 밀도를 다르게 가져간다.** 기존 구현은 웹과 모바일이 **같은 카드 구조를
공유**해서 어느 쪽에도 맞지 않는 중간 형태가 됐다.

| | 웹 | 모바일 |
| :--- | :--- | :--- |
| 설명문 | 🔵 **둘 다 모달로 보낸다**(규칙 6-1) | ← 같음 |
| 상단 요약 | *가장 급한 것* 블록 있음 | **없음** |
| 기한 | 오른쪽 끝 열 | 제목 아래 한 줄 |
| 구간 이동 | 좌측 목차(세로) | 상단 탭(가로 스크롤) |
| 모달 | 가운데 540px · 근거에 부연 표시 | 바텀시트 · 근거는 조문까지만 |

🔵 **차이는 밀도가 아니라 배치다.** 규칙 6-1로 설명문이 양쪽에서 빠지면서, 웹과 모바일의 차이는
*"무엇을 보여주는가"* 가 아니라 *"어디에 놓는가"* 로 줄었다. 기존 구현이 **같은 카드 구조를 공유해**
어느 쪽에도 맞지 않던 것과 반대 방향이다.

## 🚀 9. 진행 방식 — **그룹별** (2026-09-18 사람 확정)

🔴 **21개 화면을 하나씩 시안 잡지 않는다.** `/care-guide` 하나에 캔버스를 **아홉 번** 고쳤다.
그 과정은 **규칙을 만들기 위한 것**이었고, 규칙이 선 지금은 반복할 이유가 없다.

### 9.1 화면 그룹과 시안 대상

**그룹의 첫 화면만 시안**을 잡아 규칙을 확장하고, 같은 그룹의 나머지는 **규칙 적용 후 결과만
확인**한다. 어긋나면 그때 시안으로 돌아간다.

| 그룹 | 화면 | 시안 | 대표 |
| :---: | :--- | :---: | :--- |
| **①** 목록·체크리스트 | `care-guide` · `facility` · `counseling` · `pickup` · `my-obituaries` | ✅ **완료** | `care-guide` |
| **②** 폼·입력 | `obituary` · `mypage` · `ending-note` · `farewell-messages` · `digital-estate` | 🔴 필요 | ✅ **`obituary`** |
| **③** 읽기(법정문서) | `privacy` · `terms` | 🟡 짧게 | `privacy` |
| **④** 랜딩(외부 유입) | `/o/:slug` · `/m/:slug` · `family-invite` | 🔴 필요 | ✅ **`/o/:slug`** |
| **⑤** 홈·진입 | `home` · `prep` · `bereaved` | 🔴 필요 | `home` |
| **⑥** 운영자 | `admin` · `biz` · `partner` | ⏸ 보류 | — |
| **⑦** 미정 | `memorial` | ⏸ 보류 | 추모관 재구현과 함께 |

🔵 **①은 시안 없이 바로 구현**할 수 있다 — `facility`·`counseling`·`pickup`·`my-obituaries` 4개.

✅ **대표 확정(2026-09-18)** — ② `obituary`(인라인 **108개로 최다** = 폼 패턴이 가장 많이 들어 있고,
유족이 장례식장에서 실제로 쓰는 화면) · ④ `/o/:slug`(조문객 유입 **100% 모바일**).
🟡 ②의 대안이던 `mypage`는 로그인 직후 첫 착지라는 강점이 있으나, **폼 규칙을 뽑는 것이 목적**이라
복잡한 쪽을 골랐다. `mypage`는 같은 그룹이므로 `obituary`에서 나온 규칙을 적용만 한다.

### 9.2 그룹마다 시안이 따로 필요한 이유

| 그룹 | 목록형 규칙으로 안 되는 것 |
| :---: | :--- |
| **②** | **입력 중 오류·저장 상태·필수 표시**를 다뤄야 한다. §6에 그 규칙이 없다 |
| **③** | 조문 번호·들여쓰기·목차 등 **법정문서 특유의 구조**. 다만 본문 위주라 §4 타입과 `--lh-reader`로 거의 해결된다 |
| **④** | **조문객이 카톡으로 여는 화면**이라 로그인도 네비게이션도 없다. `00-38` §8.4가 *"회귀 비용이 가장 크다"* 고 한 곳이다 |
| **⑤** | `00-23`(메인화면 진입구조)이 레이아웃 정본이라 **규칙 6-3(헤더 드롭다운)과 부딪힐 수 있다** |

### 9.3 각 화면에서 하는 일

1. **구현** — 🔴 **인라인이 아니라 클래스로.** `index.css`(100KB)에 넣지 말고 분리한다.
2. **패턴 추가** — 새로 나온 공통 클래스를 이 문서 §6에 등재. 다음 화면이 그걸 쓴다.
3. **확인** — 실기동은 사람. 🔵 수치 확인이 필요하면 `00-38` §11.2의 360px iframe 방식을 쓴다
   (창 리사이즈는 Chrome 최소폭에 걸려 500px까지밖에 안 줄어든다).

🔴 **하지 않는 것**: 화면을 순회하며 **수치 위반 목록을 만드는 일**. 그게 §2의 반복이었다.

### 9.4 🟡 순서 — 권고

**① 나머지 4개**(시안 불필요) → **② 폼형**(가장 크고 규칙 확장이 많다) → **③ 읽기형**(가장 쉽다) →
**④ 랜딩형** → **⑤ 홈**.
