> **문서 성격**: 구현 기획서(개발 착수용 스펙). `[Claude:Opus]` 작성(2026-08-21).
> **계기**: 개발자 지시 — *"우선 사용자 계정(간편가입) 이후에 개인의 정보를 입력할 수 있도록 먼저
> 만들어야겠다. 수집해야 할 정보 정리해서 추가해보자. **연락처 주소가 최우선**임."*

## 📌 1. 착수 지점 — 지금 있는 것과 없는 것

### 1.1 현황 (2026-08-21 코드 실측)

| 대상 | 상태 | 근거 |
| :--- | :--- | :--- |
| `User` 필드 | `email?`·`name`·`profileImage?`·`role` — **연락처·주소 없음** | `schema.prisma:19-38` |
| 연락처 정규화 | ✅ `normalizePhone`·`isValidPhoneLength` | `utils/phone.ts` |

### 1.2 🔵 이 기능은 **새 수집이 아니라 반복 입력의 제거**입니다

`Lead.applicantPhone`·`ConsultRequest.applicantPhone`이 **이미 있습니다** — 주석에 *"신청 시점
연락처 스냅샷"*(`schema.prisma:185·316`). **즉 이용자는 문의·상담을 넣을 때마다 이름과 연락처를
매번 다시 칩니다.**

> ✅ **그래서 처리방침 개정도 작습니다.** `00-19` §3-2(*"문의·견적·상담 신청 시 추가 수집 — 신청자
> 이름, **연락처**"*)가 **이미 담고 있는 항목을 §3-1(회원)로 앞당기는 것**이지, 없던 항목을 새로
> 만드는 것이 아닙니다. 주소만 신규입니다.

## 🔴 2. 가장 중요한 제약 — **프로필은 스냅샷을 대체하지 않습니다**

구현자가 가장 놓치기 쉬운 지점입니다. *"이제 `User`에 연락처가 있으니 `Lead`는 `userId`로 조인해서
보여주면 되지 않나"* 는 **틀렸습니다.**

| | 프로필(`User`) | 스냅샷(`Lead`·`ConsultRequest`) |
| :--- | :--- | :--- |
| 값의 성격 | **현재 값** — 언제든 수정 | **그때 값** — 불변 |
| 왜 필요한가 | 매번 안 치게 하려고 | **분쟁 시 증거**(*"신청 당시 무슨 번호였나"*) |
| 파기 | 회원 탈퇴 시 | **`maskedAt` 마스킹**(`01-05` §4.4) |

> 🔴 **조인해서 보여주면 두 가지가 동시에 깨집니다.** ①이용자가 번호를 바꾸는 순간 **과거 리드의
> 연락처가 소급해서 바뀝니다**(증거 변조) ②`maskedAt` 마스킹이 **아무것도 가리지 못합니다**
> (원본이 `User`에 살아 있으므로).
>
> ✅ **프로필은 폼의 기본값(prefill)일 뿐입니다.** 제출 시점에 **스냅샷 컬럼으로 복사**하고,
> 그 뒤로 둘은 남남입니다.

## 📝 3. 수집 항목

### 3.1 🔴 전부 **선택**입니다 — 필수로 걸면 안 됩니다

「개인정보 보호법」 §16③은 **필수가 아닌 정보의 수집에 동의하지 않는다는 이유로 서비스 제공을
거부하지 못한다**고 정합니다. 이어봄은 **로그인만 하고 둘러보는 것이 가능한 서비스**이므로
(`00-23` §4.1 — *"막을 것은 쓰기이지 보기가 아니다"*), 연락처·주소를 회원 가입의 **필수**로 걸고
전체를 막으면 위법 소지가 생깁니다.

> ✅ **프로필은 선택 수집이고, 개별 기능이 그 기능의 필수로 승격시킵니다.**
> 예: 03 방문 수거는 **상세주소가 없으면 신청이 성립하지 않으므로** 그 화면에서 필수입니다.
> **"회원의 필수"가 아니라 "그 기능의 필수"** 라는 점이 법적으로 다릅니다.

### 3.2 항목표

| | 항목 | 구분 | 비고 |
| :---: | :--- | :---: | :--- |
| ① | **연락처(휴대전화)** | 선택 | 🔵 **최우선**(개발자 지시). `normalizePhone`으로 **숫자만** 저장 — `Partner`·`Expert`와 같은 규칙 |
| ② | **주소** | 선택 | 🔵 **최우선**. 🔴 **한 덩어리로 받지 않습니다**(§3.3) |
| ③ | 이름 | 기존 | 소셜에서 온 값이 **닉네임일 수 있음** — 프로필에서 수정 가능하게 |
| ④ | 이메일 | 기존(선택) | 소셜이 안 주는 경우가 있어 직접 입력 허용 |
| ⑤ | **연락 가능 시간대** | 🟡 신규 권고 | `ANYTIME`/오전/오후/저녁. **이 도메인에서는 실질적입니다** — 업체가 아무 때나 거는 전화는 상중 유족에게 최악이고, `07-02`의 *"판단 순"* 사상과도 맞습니다 |
| ⑥ | 마케팅 수신 동의 | 🟡 신규 권고 | 🔴 **별도 동의 항목**이며 거부해도 서비스 제공(§3.1). 받아둘 거면 **지금이 그 자리**입니다 |

**🔴 받지 않습니다**

| 항목 | 왜 |
| :--- | :--- |
| **생년월일** | `00-19` §9-2가 **이미 기각했습니다** — 만 14세 확인을 위해 전 이용자 생년월일을 받는 것은 **최소수집 원칙과 정면 충돌**. 여기서 되살리면 그 결정이 무너집니다 |
| **성별** | 목적이 없습니다 |
| **주민등록번호** | `00-19` §3-5 — 법 §24조의2. **컬럼 자체를 만들지 않습니다** |

### 3.3 🔴 주소는 **2단으로 나눠 받습니다**

| 필드 | 예 | 쓰이는 곳 |
| :--- | :--- | :--- |
| `addressZonecode` | `04524` | 우편번호 |
| `addressRoad` | `서울시 중구 세종대로 110` | **지역 기반 안내**(01·02) — 여기까지면 충분합니다 |
| `addressDetail` | `○○동 ○○호` | **방문 서비스**(03 현물 수거)에서만 필요 |

> 🔴 **상세주소는 민감도가 다릅니다.** *"어느 동네 사는가"* 와 *"몇 동 몇 호에 사는가"* 는 유출
> 시 피해가 다릅니다. 한 칸에 합쳐 받으면 **지역 안내만 쓰는 기능도 상세주소를 들고 다니게**
> 됩니다. **최소수집을 화면 문구가 아니라 스키마로 구현하는 것**이 이 분리의 목적입니다.

### 3.4 ⚠️ `AddressSearchModal`을 그대로 쓸 수 없습니다

현재 시그니처가 **문자열 하나**입니다 — `onSelect(data.roadAddress || data.jibunAddress)`
(`AddressSearchModal.tsx:31`). **우편번호(`zonecode`)도 상세주소 입력칸도 없습니다.**

- `onSelect`를 `{ zonecode, roadAddress, jibunAddress }` 객체로 확장하고, 상세주소는 모달이 아니라
  **폼에서 직접 입력**받습니다(다음 우편번호 위젯은 상세주소를 받지 않습니다).
- ⚠️ **기존 호출부 2곳을 동반 수정**해야 합니다 — `AdminPage.tsx:604` · `PartnerPortalPage.tsx:387`.
  한쪽만 고치면 타입이 깨집니다.

기능도 함께 중단된 상태입니다(2026-08-18). 신고·면제 확인은 아직 사장님 결정 대기입니다.

> 🟡 **이용자가 직접 타이핑한 주소는 성격이 다릅니다.** 위치정보법 §2 1호의 개인위치정보는

> 자택 주소는 개인정보이지만 그 정의의 위치정보로 보기는 어렵습니다.**
>
> ⚠️ **단정하지 않습니다 — 법률 확인 항목입니다**(`00-14` §2.10 · `context.md` ②ⓑ와 함께 확인).
> 다만 확인 결과가 긍정이면, **geolocation을 못 쓰는 동안 지역 기반 안내를 대체할 유일한 경로**가

```prisma
model User {

  addressDetail     String?   // 동·호수 — 방문 서비스에서만 필요(§3.3)
  contactTimePref   String?   // ANYTIME | MORNING | AFTERNOON | EVENING
  marketingAgreedAt DateTime? // null이면 미동의. 철회 시 다시 null

```

> 🟡 **별도 `UserProfile` 테이블로 빼지 않습니다.** 1:1이고 **항상 `User`와 함께 읽히므로**
> 조인만 늘어납니다. 항목이 크게 늘거나 접근 권한을 분리해야 할 때 그때 나눕니다.
>
> ✅ **연락처는 평문 저장 + 응답 마스킹**입니다. `security.md` §1의 *"평문 금지"* 는 **저장소에
> 커밋하지 말라**는 규칙이지 DB 암호화 강제가 아니고, `Partner`·`Expert`·`Lead`가 전부 평문이라
> 여기만 암호화하면 조회·마스킹 코드가 갈립니다.
> ⚠️ **`00-27`의 가족 연락처는 암호화합니다** — 그쪽은 **제3자 정보 + 사후 권한이 결부**돼 있어
> 위협 모델이 다릅니다. 두 문서가 다르게 정한 것은 실수가 아닙니다.
> ⚠️ **`Obituary.contactPhone`(`07-03`)과도 다릅니다** — 그건 **입력=공개**가 전제인 상주 연락처입니다.

### 6.2 🟡 온보딩은 **강제하지 않습니다**

가입 직후 1회 노출하되 **건너뛰기를 둡니다.**

- **간편가입의 "간편"이 무너집니다** — 소셜 로그인을 고른 이유가 입력을 줄이는 것인데, 직후에
  폼을 세우면 그 이점이 사라집니다.

- 🟡 **실제 수집은 다른 곳이 더 효율적입니다** — 문의·상담 폼에서 어차피 연락처를 받으므로,
  그 자리에 *"다음에도 쓰게 프로필에 저장할까요?"* 체크 한 줄이 온보딩보다 전환이 좋습니다.

### 6.4 🔴 prefill은 **클라이언트가 채우지 않습니다** (2026-08-21 신설 — Phase 2 설계)

Phase 2를 설계하다 §6.1과 충돌 하나를 발견했습니다.

> **`GET /api/me/profile`은 연락처를 마스킹해서 응답합니다**(`010-****-5678`).
> **그러면 프론트가 그 값으로 폼을 채울 수 없습니다** — 마스킹된 문자열이 그대로 신청됩니다.

마스킹을 풀어 평문을 내려보내는 것은 §6.1을 되돌리는 것이라 채택하지 않습니다.

> ✅ **해법 — "값"이 아니라 "쓰겠다는 의사"를 보냅니다.**
>
> | | 동작 |
> | :--- | :--- |
> | 화면 | `☑ 내 정보 사용 (010-****-5678)` 체크박스. 켜면 입력칸은 **비활성 + 마스킹 표시** |
> | 전송 | 폼이 `useProfileContact: true`를 보냅니다. **연락처 값은 안 보냅니다** |
> | 서버 | 그 플래그를 보고 **자기가 가진 프로필 평문을 스냅샷 컬럼에 복사**합니다 |
>
> ✅ **부수 효과가 큽니다 — §2(스냅샷 원칙)가 자동으로 지켜집니다.** 복사를 서버가 하므로
> 구현자가 조인으로 우회할 여지 자체가 없습니다.
> ✅ **평문이 브라우저로 한 번도 내려가지 않습니다.**

#### 6.4-1 ⚠️ 기존 `localStorage` prefill을 함께 걷어냅니다

`InquiryModal.tsx`가 **이미 자체 prefill을 하고 있습니다** — `LAST_APPLICANT_KEY`로 마지막 신청자
이름·연락처를 `localStorage`에 저장해 다음 신청 때 채웁니다.

- 🔴 **그대로 두면 두 소스가 충돌합니다**(로컬 잔재 vs 서버 프로필). **제거합니다.**
- 🔴 **보안상으로도 걷어내는 것이 맞습니다** — 2026-08-21에 로그인 세션을 `sessionStorage`로
  옮긴 판단(`00-08`)과 어긋납니다. **이름·연락처가 `localStorage`에 무기한 남습니다.**
- 🟡 `ConsultRequestModal.tsx`에는 prefill이 없으므로 이번에 **같은 방식으로 함께 붙입니다** —
  두 폼이 다르게 동작하면 그 자체가 버그로 보입니다.

## 🚀 8. 구현 단계

### Phase 1 — 프로필을 저장할 수 있다 (**이번 착수 범위**)

4. `AddressSearchModal` `onSelect` 확장 + **기존 호출부 2곳 동반 수정**(§3.4)

> **완료 판정**: 로그인 후 연락처·주소(우편번호/도로명/상세)·연락 시간대를 저장·수정·삭제할 수
> 있고, `GET` 응답에 **평문 연락처와 상세주소가 없으며**, 하이픈을 넣어 입력해도 **숫자만**
> 저장되고, 기존 `AdminPage`·`PartnerPortalPage`의 주소 검색이 **그대로 동작한다**.

### Phase 2 — 안 치게 만든다

> 🔵 **2026-08-21 순서 변경 — 6번을 먼저 합니다.** 온보딩은 대부분 건너뛰지만, 문의 폼에서
> 어차피 연락처를 치는 사람에게 체크박스 하나를 주는 쪽이 **전환이 훨씬 좋습니다**(§6.2).

6. **문의·상담 폼 prefill + "프로필에 저장" 체크** — 🔴 **`useProfileContact` 플래그 방식**(§6.4).
   클라이언트가 값을 채우지 않습니다. ⚠️ `InquiryModal`의 기존 `localStorage` prefill 제거(§6.4-1)
5. 가입 직후 온보딩 1회(건너뛰기 有)

> **완료 판정**: 프로필에 연락처를 저장한 이용자가 문의 폼을 열면 `☑ 내 정보 사용 (010-****-5678)`이

> 연락처를 바꿔도 **그 리드의 값은 바뀌지 않는다.** 브라우저 `localStorage`에 이름·연락처가
> 남지 않는다.

### Phase 3 — 번호를 믿을 수 있게 한다
