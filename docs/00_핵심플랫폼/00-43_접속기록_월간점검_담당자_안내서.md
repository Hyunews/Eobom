## ✅ 4. 매달 하는 순서 — 체크리스트

> 아래를 위에서부터 차례대로 하면 됩니다. 각 항목의 자세한 설명은 §5에 있습니다.

- [ ] **1.** 점검 기록표에 새 줄을 만들고 **점검일 · 점검자 · 대상 기간(지난달)** 을 적는다
- [ ] **2.** Supabase에 로그인한다 → 이어봄 **운영** 프로젝트를 고른다
- [ ] **3.** 왼쪽 메뉴에서 **SQL Editor** → **New query**(새 쿼리)를 누른다
- [ ] **4.** §5의 쿼리 ①을 **통째로 복사**해 빈 칸에 붙여넣고 **Run**(실행)을 누른다
- [ ] **5.** 아래에 나온 결과를 §5 ①의 "이렇게 판단" 대로 보고, 기록표 ①칸에 **이상 없음 / 이상 있음(내용)** 을 적는다

- [ ] **7.** "이상 있음"이 하나라도 있으면 **§7(이상이 나오면)** 대로 조치를 시작하고 기록표에 적는다
- [ ] **8.** 기록표 줄을 마무리한다 — 조치가 없으면 "조치 없음", 조치가 끝나면 **조치 완료일**

🔴 **꼭 지킬 것 3가지**
1. **한 번에 쿼리 하나씩** 실행합니다. 여러 개를 한꺼번에 붙여넣으면 Supabase는 **마지막 것의 결과만** 보여 줘서 앞의 것을 놓칩니다.

3. 실행했을 때 **"되돌릴 수 없는 작업" 같은 경고 창**이 뜨거나 **빨간 오류**가 나오면 → **취소하고 멈춘 뒤 개발자에게 화면을 보여 줍니다.** 조회 쿼리에서는 경고 창이 뜰 일이 없습니다.

## 🔍 5. 항목별 — 쿼리 · 보는 법 · 판단

> 모든 쿼리는 **"지난달 1일 0시 ~ 이번 달 1일 0시(한국 시간)"** 를 자동으로 계산합니다. 날짜를 고칠 필요가 없습니다.
> 단, **반드시 그 달 안에 실행**해야 "지난달"이 맞게 잡힙니다(11월에 실행 → 10월치).
> 시각 칸(`createdAtKst`)은 **한국 시간**입니다.

### ① 운영자 로그인 실패 · 잠금

**무엇을 보나**: 비밀번호를 틀린 기록(`LOGIN_FAIL`)과, 5번 연속 틀려 15분 잠긴 기록(`LOCKED`).
남이 운영자 계정에 들어가려고 비밀번호를 찍어 본 흔적일 수 있습니다.

```sql
SELECT "createdAtKst", "adminName", action, ip FROM "AdminAuditLog"
WHERE action IN ('LOGIN_FAIL','LOCKED')
  AND "createdAtKst" >= date_trunc('month', now() AT TIME ZONE 'Asia/Seoul') - interval '1 month'
  AND "createdAtKst" <  date_trunc('month', now() AT TIME ZONE 'Asia/Seoul')
ORDER BY 1;
```

**이렇게 판단**
- **행이 없음**(`No rows returned`) → ✅ 이상 없음
- 행이 있음 → 나온 **운영자 이름**의 본인에게 *"○월 ○일 ○시에 비밀번호를 틀린 적 있으세요?"* 라고 묻습니다.
  - 본인이 "네, 제가 틀렸어요" → ✅ 이상 없음(기록표에 "본인 확인" 적기)
  - 본인이 기억 못 함 · 운영자 이름이 비어 있음 · 모르는 IP → ⚠️ **이상 있음** → §7

### ② 업무시간 밖 활동 (한국 시간 밤 10시 ~ 아침 7시)

**무엇을 보나**: 아무도 일하지 않을 시간에 운영자 화면이 쓰였는지.

```sql
SELECT "createdAtKst", "adminName", action, "targetType", "targetId", ip FROM "AdminAuditLog"
WHERE (EXTRACT(HOUR FROM "createdAtKst") >= 22 OR EXTRACT(HOUR FROM "createdAtKst") < 7)
  AND "createdAtKst" >= date_trunc('month', now() AT TIME ZONE 'Asia/Seoul') - interval '1 month'
  AND "createdAtKst" <  date_trunc('month', now() AT TIME ZONE 'Asia/Seoul')
ORDER BY 1;
```

**이렇게 판단**
- **행이 없음** → ✅ 이상 없음
- 행이 있음 → **운영자 명단**(§3)과 비교합니다. 그 사람이 원래 늦게 일하거나, 미리 말해 둔 야간 작업이면 ✅.
  그렇지 않으면 본인에게 그 시각에 무엇을 했는지 묻습니다. 설명이 안 되면 ⚠️ → §7
- 💡 `targetType`·`targetId` = **무엇을 봤는지**(예: `User` + 회원 번호). 이상할 때 이 두 칸을 기록표에 옮겨 적습니다.

### ③ 하루에 너무 많이 열어 본 사람 (하루 50건 초과)

**무엇을 보나**: 한 운영자가 하루에 회원 정보·목록을 50번 넘게 열었는지. 개인정보를 대량으로 빼 가는 흔적일 수 있습니다.

```sql
SELECT "adminName", "createdAtKst"::date AS day, count(*) AS n FROM "AdminAuditLog"
WHERE action IN ('VIEW','LIST')
  AND "createdAtKst" >= date_trunc('month', now() AT TIME ZONE 'Asia/Seoul') - interval '1 month'
  AND "createdAtKst" <  date_trunc('month', now() AT TIME ZONE 'Asia/Seoul')
GROUP BY 1, 2 HAVING count(*) > 50 ORDER BY 3 DESC;
```

**이렇게 판단**
- **행이 없음** → ✅ 이상 없음
- 행이 있음(`n` = 그날 연 횟수) → 그날 그 사람이 **대량으로 볼 일이 있었는지** 묻습니다(예: 가입 심사가 몰린 날). 이유가 있으면 ✅, 없으면 ⚠️ → §7
- 🟡 **50은 처음 정한 임시 기준**입니다. 화면을 여닫기만 해도 숫자가 오르므로, 정상 업무로 자주 넘으면 3개월 뒤 개발자와 기준을 올립니다(`00-22` 부록 1-2).

### ④ 처음 보는 장소(IP)에서의 접속

**무엇을 보나**: 지난달에 **처음 나타난** 접속 장소. 계정을 남이 쓰고 있으면 낯선 곳에서 들어옵니다.

```sql
SELECT ip, "adminName", min("createdAtKst") AS first_seen, count(*) AS n FROM "AdminAuditLog"
WHERE ip IS NOT NULL
  AND "createdAtKst" >= date_trunc('month', now() AT TIME ZONE 'Asia/Seoul') - interval '1 month'
  AND "createdAtKst" <  date_trunc('month', now() AT TIME ZONE 'Asia/Seoul')
  AND ip NOT IN (SELECT ip FROM "AdminAuditLog" WHERE ip IS NOT NULL
                 AND "createdAtKst" < date_trunc('month', now() AT TIME ZONE 'Asia/Seoul') - interval '1 month')
GROUP BY 1, 2 ORDER BY 3;
```

**이렇게 판단**
- **행이 없음** → ✅ 이상 없음
- 행이 있음 → 그 운영자에게 *"○월 ○일에 새로운 곳(집·출장지·새 와이파이 등)에서 접속했나요?"* 를 묻습니다. 맞으면 ✅, 모르면 ⚠️ → §7
- 🔵 **첫 점검(10월치)에는 IP가 전부 나옵니다** — 기록이 10월 1일에 시작돼서 그 전의 IP가 없기 때문입니다. 첫 달에는 운영자마다 *"이게 내 접속 장소가 맞다"* 를 확인받고 **기록표 비고에 IP 목록을 남겨 둡니다.** 다음 달부터는 새로 생긴 것만 나옵니다.

### ⑤ 기록이 끊긴 날

**무엇을 보나**: 접속기록이 **한 건도 없는 날**. 기록 장치가 고장 나면 이렇게 보입니다. 기록이 없으면 사고가 나도 무슨 일이 있었는지 알 수 없습니다.

```sql
SELECT d::date AS day FROM generate_series(
  date_trunc('month', now() AT TIME ZONE 'Asia/Seoul') - interval '1 month',
  date_trunc('month', now() AT TIME ZONE 'Asia/Seoul') - interval '1 day', interval '1 day') d
WHERE NOT EXISTS (SELECT 1 FROM "AccessLog" a WHERE a."createdAtKst"::date = d::date);
```

**이렇게 판단**
- **행이 없음** → ✅ 이상 없음
- 날짜가 나옴 → 개발자에게 그 날짜를 알리고 *"그날 서버가 멈췄었나요, 아니면 이용자가 아무도 없었나요?"* 를 묻습니다.
  🟡 **서비스 공개 전에는 이용자가 없는 날이 흔합니다**(접속기록은 로그인한 사람·저장·실패만 남기기 때문). 개발자가 "그날 이용이 없었다"고 확인하면 ✅.
  원인을 모르면 ⚠️ → §7

### ⑥ 오래된 기록이 제때 지워지는지

**무엇을 보나**: 표마다 **가장 오래된 기록이 며칠 전 것**인지. 기록은 정해진 기간이 지나면 지워야 합니다(우리가 처리방침에 약속한 것).

```sql
SELECT 'AccessLog' AS t, now()::date - min("createdAt")::date AS days FROM "AccessLog"
UNION ALL SELECT 'AdminAuditLog', now()::date - min("createdAt")::date FROM "AdminAuditLog"
UNION ALL SELECT 'ErrorLog', now()::date - min("createdAt")::date FROM "ErrorLog";
```

**이렇게 판단** — `days`(며칠 전) 칸을 아래 기준과 비교합니다.

| `t`(표 이름) | 뜻 | 이 숫자 **이하**면 ✅ |
| :--- | :--- | :---: |
| `AccessLog` | 전체 접속기록 | **365** |
| `AdminAuditLog` | 운영자 기록 | **730** |
| `ErrorLog` | 서버 오류 기록 | **90** |

- 기준보다 크면 ⚠️ → 개발자에게 *"파기 배치를 돌려 주세요"* 라고 요청합니다. 🔵 **이 파기는 자동이 아니라 개발자가 손으로 돌리는 작업**이라, 이 점검이 그 시기를 알려 주는 역할도 합니다.
- 🔵 기록이 10월 1일에 시작돼 **처음으로 기준을 넘는 것은 2026년 12월 말 `ErrorLog`(90일)** 입니다. 1월 점검에서 처음 걸릴 수 있습니다.

### ⑦ 오류 기록에 개인정보가 섞였는지

**무엇을 보나**: 서버 오류 기록에 **전화번호나 이메일 모양**의 글자가 남았는지. 오류 기록에는 개인정보를 가려서(마스킹) 남기게 돼 있는데, 그게 새는지 확인합니다.

```sql
SELECT "createdAtKst", "errorName", message FROM "ErrorLog"
WHERE (message ~ '01[0-9]-?[0-9]{3,4}-?[0-9]{4}'
       OR message ~ '[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}')
  AND "createdAtKst" >= date_trunc('month', now() AT TIME ZONE 'Asia/Seoul') - interval '1 month'
  AND "createdAtKst" <  date_trunc('month', now() AT TIME ZONE 'Asia/Seoul');
```

**이렇게 판단**
- **행이 없음** → ✅ 이상 없음
- 행이 있음 → ⚠️ 개발자에게 **시각만** 알립니다(`message` 내용을 기록표나 메신저에 **옮겨 적지 않습니다** — 그 안에 개인정보가 있습니다).
  🔴 **그 기록을 직접 지우지 않습니다.** 90일이 지나면 정해진 절차로 지워집니다. 개발자는 가리는 장치를 고칩니다.

### ⑧ 기록 표 크기

**무엇을 보나**: 기록이 데이터베이스 용량을 얼마나 쓰는지. 무료 요금제는 **전체 500MB**이고, 넘으면 **회원 가입·저장이 멈춥니다.**

```sql
SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) AS size, n_live_tup
FROM pg_stat_user_tables WHERE relname IN ('AccessLog','ErrorLog','AdminAuditLog');
```

**이렇게 판단** — `size` 칸 세 개를 더합니다(`kB` = 1/1000 MB).
- 합계 **300MB 이하** → ✅ (2026-10 기준 전체 DB가 약 30MB라 한동안은 넉넉합니다)
- 300MB 초과 → ⚠️ 개발자에게 알립니다. 요금제 변경·보관 단축 등은 개발자가 정합니다(`00-42` §6).

**먼저 침착하게** — 대부분은 본인이 기억하는 정상 업무입니다. 아래 순서대로 합니다.

   - 그 계정이 같은 기간에 **열어 본 회원 목록**(②의 `targetId`) 뽑기
3. **유출인지 판단** — 개발자와 함께, 회원 정보가 밖으로 나갔을 가능성이 있는지 봅니다.

4. **⑤·⑥·⑦·⑧(기계 쪽 문제)** — 개발자에게 알리기만 하면 됩니다. 담당자가 직접 고치거나 지우지 않습니다.
5. 무엇을 했는지 **기록표 "조치 내용"** 에, 끝난 날을 **"조치 완료일"** 에 적습니다.

## ❓ 9. 자주 묻는 것

- **Q. 실수로 뭔가 지우면 어떡하나요?** — 이 문서의 쿼리는 전부 `SELECT`(보여 달라)로 시작하며 아무것도 바꾸지 않습니다. 다른 글을 직접 쳐 넣지만 않으면 지워질 일이 없습니다.
- **Q. 결과가 너무 많아서 다 못 보겠어요.** — 개발자에게 화면을 보여 주고 같이 봅니다. 특히 첫 달은 ②·④가 많을 수 있습니다.
- **Q. 이번 달을 놓쳤어요.** — 알게 된 날 바로 합니다. 단, 쿼리는 "실행한 달의 지난달"을 보므로, 달이 바뀌었다면 개발자에게 **기간을 바꾼 쿼리**를 받아야 합니다. 기록표에는 늦어진 사실과 이유를 적습니다.
- **Q. 관리자 화면에 이런 기능이 생기면요?** — 운영자 기록을 보는 화면이 생기면(`00-42` L-3) SQL 대신 그 화면으로 같은 8개를 봅니다. 항목·기준·조치는 그대로입니다.

### 10.3 🔴 DB 접속 — 조회 전용 계정

- 새 환경변수 **`OPS_AUDIT_DATABASE_URL`** 만 읽는다. 🔴 **`DATABASE_URL`·`DIRECT_URL`·`BACKUP_DATABASE_URL`로 폴백하지 않는다** — 없으면 실행 거부(`backup-db.ps1`·`TEST_DATABASE_URL`과 같은 원칙).
- 그 주소의 계정은 **조회 전용 DB 계정 `eobom_auditor`** — 기록 표 3개만 읽을 수 있다(회원 · 엔딩노트 등 다른 표는 **읽기도 불가**).
  ```sql
  CREATE ROLE eobom_auditor LOGIN PASSWORD '<개발자가 정함>';
  GRANT USAGE ON SCHEMA public TO eobom_auditor;
  GRANT SELECT ON "AccessLog", "AdminAuditLog", "ErrorLog" TO eobom_auditor;
  ALTER ROLE eobom_auditor SET default_transaction_read_only = on;
  ```
  🔴 **계정 만들기는 DB 쓰기다** — 로컬 · 운영 모두 **백업 먼저**(`backup-db.ps1 -Target local|prod`) + **사람이 실행**(`AGENTS.md` §1 CONFIRM · `db-safety.md`). Sonnet은 위 SQL을 파일(`prisma/sql/create-auditor-role.sql`)로 두고 실행은 안내만 한다.
  🟡 Supabase 풀러 접속 시 사용자명은 **`eobom_auditor.[프로젝트 ref]`** 형식일 가능성(`systems.md` — `postgres.[ref]`와 같은 규칙) — `미확인`, **첫 운영 연결(11월 첫 주) 때 확인해 이 줄에 적는다.** ⑧ 표 크기 조회는 이 권한으로 됨(10-08 로컬 확인).
- 🔴 **이중 안전장치**: 스크립트는 시작할 때 ① 조회 전용 트랜잭션(`BEGIN READ ONLY`)으로 열고 ② `has_table_privilege(current_user, '"User"', 'SELECT')`가 **참이면 실행 거부**(관리자 계정 주소를 잘못 넣은 경우를 막음 — 메시지: *"점검 전용 계정이 아닙니다"*).

### 10.4 판정 규칙 — §5와 같은 기준(`00-22` 부록 1-2가 정본)

| # | 스크립트가 하는 일 | 결과지 표시 |
| :---: | :--- | :--- |
| ①②③④ | §5 조회와 같은 조건으로 행을 뽑음 | 0건 → **이상 없음** · 1건 이상 → **확인 필요 N건** + 목록(시각 · 운영자 · 행동 · 대상 · IP). 판정 칸은 **비워 둠**(담당자 기재) |
| ④ 첫 달 | 대상 달 이전 기록이 0건이면 | "**첫 점검 — 전부 표시됨(정상)**" 문구 |
| ⑤ | 접속기록 0건인 날 | 0일 → 이상 없음 · 1일 이상 → **확인 필요**(공개 전 이용 없음일 수 있음 — 개발자 확인 칸). 날짜 목록은 **한 줄에 6개씩** 묶어 표시(공개 전엔 날짜가 많아 인쇄가 길어지므로) |
| ⑥ | 표별 가장 오래된 기록 일수 | 365 / 730 / 90 이하 → 이상 없음 · 초과 → **이상 있음 — 파기 배치 실행 필요** |
| ⑦ | 전화번호 · 이메일 모양 건수 | 0 → 이상 없음 · 1 이상 → **이상 있음 N건** + **시각 · 오류 종류만**. 🔴 **`message` 본문은 결과지에 절대 싣지 않는다**(§5 ⑦과 같은 이유) |
| ⑧ | 세 표 크기 합 | 300MB 이하 → 이상 없음(합계 표시) · 초과 → **이상 있음** |

- 🔴 **기준값(50건 · 300MB · 365/730/90일)은 스크립트 맨 위 상수 한 곳**에 두고, 주석으로 `00-22` 부록 1-2와 묶는다. 기간은 `now()` 대신 **대상 달의 시작 · 끝(한국 시간)을 인자로** 넘긴다(§5 수기 조회는 `now()` 기준 그대로).
