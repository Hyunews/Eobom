## 3. 🔴 왜 이렇게 됐는가 — 원인은 코드가 아닙니다

`docs/`를 전수 검색했습니다. **`authFetch`·API 클라이언트·프론트 공통 레이어를 규정한 문서가 없습니다.** 일지(`260811.md`)에 사후 기록만 있습니다.

우리 구조는 **`docs/` 확정 스펙 → Sonnet 구현**이고, `roles.md` §2는 Sonnet에게 *"스펙을 재해석하지 말고 그대로 신뢰하라"* 고 합니다. 좋은 규칙인데 여기서 역효과가 납니다:

> **스펙에 없는 것은 만들어지지 않습니다.** 그리고 `docs/`는 **도메인별로 쪼개져 있습니다**(01 장사시설 · 02 전문가 · 06 엔딩노트 · 07 상중행정 …). **횡단 관심사는 어느 도메인에도 속하지 않으므로 주인이 없습니다.** 주인이 없으니 스펙이 없고, 스펙이 없으니 각 화면이 자기 자리에서 `fetch`를 직접 씁니다.

🔴 **그래서 `api.ts`만 만들면 재발합니다.** 다음 횡단 관심사에서 똑같이 반복됩니다.

### 3.1 이 문서가 소유하는 범위

**이 문서는 "프론트엔드 횡단 관심사"의 주인입니다.** 아래에 해당하면 도메인 문서가 아니라 **여기에 적습니다.**

| 관심사 | 상태 |
| :--- | :--- |
| HTTP 요청 파이프라인(인증·헤더·봉투·에러) | ✅ **이 문서 §5** |
| 클라이언트 저장소 키 | ✅ **이 문서 §4** |
| 세션 만료 처리 | ✅ **이 문서 §6** |
| 오류 표시(토스트) | ⏸ 미착수 — 정해지면 **여기에 절을 추가** |
| 로딩 상태 | ⏸ 미착수 — 〃 |
| 로깅·에러 리포팅 | ⏸ 미착수 — 〃 |
| 인라인 스타일·디자인 토큰 | ➡️ **`00-29`가 소유**(중복 금지) |

> 🔴 **판단 기준**: *"이 규칙을 어느 도메인 문서에 적어야 할지 애매하다"* 면 **횡단 관심사이고 여기가 주인입니다.**

## 4. 1층 — 저장소 키 상수화

### 4.1 요건

| 항목 | 내용 |
| :--- | :--- |
| 위치 | `eobom/frontend/src/lib/storage.ts` **신설** |
| 내용 | §2.2의 키 **12종에서 죽은 키 1종을 뺀 11종**을 상수로 선언 |
| 접근 | 계정군별 `getToken(audience)` / `setSession(...)` / `clearSession(audience)` |
| 🔴 금지 | 이 파일 **밖에서 저장소 키 문자열을 직접 쓰지 않습니다** |

### 4.2 🔴 키 문자열 값은 바꾸지 않습니다

**상수 이름만 통일하고 값은 그대로 둡니다.** `k_ending_token`을 `eobom_user_token`으로 개명하면 **이미 로그인해 있는 모든 사용자의 세션이 즉시 끊깁니다.** 접두사 불일치는 **보기 싫을 뿐 동작에 해가 없고**, 상수화하면 코드에서는 어차피 안 보입니다.

### 4.3 ✅ 비용 0 — 죽은 키 제거

`InquiryModal.tsx:34`의 `localStorage.removeItem('eobom_last_applicant')` **한 줄 삭제.** 저장하는 곳이 없으므로 아무 동작도 안 하는 줄입니다.

### 4.4 🔴 `App.tsx`의 옛 `localStorage` 정리 코드는 **유지합니다**

`App.tsx:80-81`은 2026-08-21 `localStorage`→`sessionStorage` 전환 때 남긴 한시적 청소 코드입니다. **아직 안 지웁니다** — 그 이전에 접속한 뒤 아직 안 돌아온 브라우저에 값이 남아 있을 수 있습니다. `storage.ts`로 옮기되 **한시적 코드임을 주석에 명시**하고, 제거 시점은 **정식 오픈 시**로 둡니다.

## 5. 2층 — `apiFetch`

### 5.1 요건

| 항목 | 내용 |
| :--- | :--- |
| 위치 | `eobom/frontend/src/lib/api.ts` **신설** |
| 역할 | URL 조립(§2.1-5) + 헤더(§2.1-3·6) + 토큰(§2.1-2) + 봉투 해석(§2.1-4) + 401(§2.1-1) |
| 인자 | 경로(`/api/...`), 계정군, 그 외 `RequestInit` |
| 🔴 `BACKEND_URL` | **함수 안에서 붙입니다.** 호출부는 `/api/...`만 씁니다 |

### 5.2 계정군

**`USER` · `ADMIN` · `PARTNER` 3종**입니다(§2.2 표 그대로). 계정군을 받아 **어느 저장소의 어느 키에서 토큰을 읽을지**를 `apiFetch`가 정합니다 — 호출부는 저장소를 몰라도 됩니다.

🔵 **비인증 요청도 같은 함수를 씁니다**(계정군 없음) — URL·헤더·봉투 이득은 그대로 받고 토큰만 안 붙입니다. **인증/비인증으로 함수를 둘로 쪼개지 마십시오** — 어느 걸 쓸지 매번 판단하게 되면 결국 다시 안 씁니다.

### 5.3 응답 봉투

백엔드는 `{ status, data, message }`로 통일돼 있습니다. `apiFetch`가 **풀어서 반환**하고, `status !== 'success'`면 `message`를 담은 오류로 던집니다. **호출부에서 55번 반복하던 판정이 사라집니다.**

🔴 **예외**: 파일 다운로드 등 봉투가 아닌 응답은 **원본 `Response`를 받는 경로를 따로 남깁니다.** 봉투를 강제하면 그 자리에서 다시 `fetch`를 직접 쓰게 됩니다.

### 5.4 🔴 401 — 이 작업의 본체

401을 받으면 **`apiFetch`가 세션을 정리하고 만료를 알립니다**(§6). 지금 관리자·사업자에만 있는 처리를 **일반 사용자 12파일에 자동으로 적용**하는 것이 이 스펙의 핵심 성과입니다.

문구는 기존과 동일하게 유지합니다: **"세션이 만료되어 로그아웃되었습니다. 다시 로그인해주세요."**

### 5.5 ❌ 이번에 하지 않는 것 — 자동 리프레시

§2.3의 발견은 **별건**입니다. 넣지 않는 이유: 동시 요청 중 여러 개가 동시에 401을 받으면 **갱신이 중복 실행**되고, 갱신 요청 자체가 401을 받으면 **무한루프**가 됩니다. 방어 설계가 따로 필요하며 **이 작업에 얹으면 끝나지 않습니다.**

## 6. 3층 — 세션 만료를 화면에 알리는 방법

`apiFetch`는 라이브러리 함수라 **화면 전환을 직접 하지 않습니다**(React 밖에서 라우팅을 건드리면 추적이 안 됩니다).

| 방식 | 판정 |
| :--- | :--- |
| **`api.ts`가 콜백을 하나 들고 있고, `App.tsx`가 마운트 때 등록** | ✅ **채택** — 의존 방향이 한 쪽이고 타입이 잡힘 |
| `window` 커스텀 이벤트 | ❌ 타입이 안 잡히고 등록 해제를 빠뜨리기 쉬움 |
| 전역 상태 라이브러리 도입 | ❌ §7 |

관리자·사업자는 **각자의 로그아웃 처리가 이미 있으므로**(`AdminPage.handleLogout` · `PartnerPortalPage`) 그것을 계정군별로 등록해 재사용합니다. **기존 동작을 바꾸지 않습니다.**

## 7. ❌ 도입하지 않는 것

| 후보 | 기각 사유 |
| :--- | :--- |
| `axios` | `fetch`가 이미 51곳에서 동작 중. 이득은 **인터셉터 하나뿐**인데 그건 래퍼 함수로 됩니다 |
| `TanStack Query` | 캐시·재검증이 필요한 화면이 아직 없습니다. 외부 리뷰의 Redis 지적과 같은 **우선순위 오판**입니다 |
| 전역 상태 라이브러리(Redux·Zustand 등) | 🔴 **지금 문제는 상태 공유가 아니라 요청 파이프라인입니다.** 상태 라이브러리를 넣어도 `fetch` 51곳은 그대로 남습니다 |

> 🔵 **외부 리뷰는 "전역 상태·API 클라이언트 부재"를 한 덩어리로 지적했지만, 조사해보니 둘은 별개였고 급한 쪽은 API 클라이언트였습니다.**

## 8. 마이그레이션 — 51곳을 한 번에 바꾸지 않습니다

| 단계 | 범위 | 판정 |
| :---: | :--- | :--- |
| **1** | `storage.ts`·`api.ts` 신설 + 죽은 키 제거 | ✅ 기존 동작 변화 없음 |
| **2** | 🔴 **일반 사용자 12파일**을 `apiFetch`로 이관 | **401 무방비가 여기서 닫힙니다 — 최우선** |
| **3** | 관리자·사업자 2파일의 `authFetch`를 `apiFetch`로 흡수 | 동작 동일, 중복 제거 |
| **4** | 나머지 비인증 `fetch` 이관 | 🟡 서두르지 않음 |
| **상시** | 🔴 **새로 쓰는 코드는 `fetch` 직접 호출 금지** | 이게 없으면 이관 속도보다 증가 속도가 빠릅니다 |

🔴 **2단계를 1단계와 같은 커밋에 넣지 마십시오.** 새 레이어 도입과 12파일 수정이 섞이면 문제가 생겼을 때 어느 쪽인지 못 가립니다.
