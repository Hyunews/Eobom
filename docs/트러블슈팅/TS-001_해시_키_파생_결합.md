## 1. 증상 — 눈에 보인 것

**아무것도 안 보입니다. 그게 증상입니다.**

- 마이페이지에서 **같은 가족을 두 번 지정해도** *"이미 등록된 연락처입니다."* 가 뜨지 않음
- 목록에 같은 사람이 두 줄 생김
- 🔴 **서버 에러 없음 · 콘솔 로그 없음 · DB 제약 위반 없음**

> 이 증상은 **키를 교체한 뒤부터** 나타납니다. 교체 전에는 정상 동작하므로, *"멀쩡하던 중복 검사가 어느 날부터 안 먹는다"* 로 체감됩니다.

## 2. 원인 — 실제로 무엇이었나

### 짐작

*"중복 검사 쿼리나 `@@unique` 제약이 잘못됐겠지."*

### 실제

**둘 다 멀쩡했습니다.** `@@unique([userId, phoneHash])`도, `P2002` 처리도 정상입니다.

문제는 **비교 대상인 값이 바뀐 것**입니다.

```
010-1234-5678  +  옛 열쇠  →  a3f9c2…   ← DB에 이미 저장된 값
010-1234-5678  +  새 열쇠  →  7e01b4…   ← 오늘부터 만들어지는 값
```

`@@unique`는 **글자가 같은가만** 봅니다. 같은 사람인데 지문이 달라졌으니 **다른 사람으로 판단하고 통과시킵니다.**

### 🔴 왜 열쇠가 바뀌었나 — 여기가 진짜 원인

`hashField`가 **전용 키를 안 쓰고 정산용 키에서 파생**하고 있었습니다.

```ts
const raw = process.env.SETTLEMENT_ENCRYPTION_KEY;          // 🔴 정산 키
const hmacKey = crypto.createHash('sha256').update(`${raw}:${domain}`).digest();
```

`00-27` §4.1에서 *"환경변수를 하나 더 만들지 말자"* 고 정한 결과였습니다. 그 자체로 틀린 판단은 아니었고 — **교체 시나리오를 고려하지 않았을 뿐**입니다.

그래서 이런 결합이 생겼습니다.

> **정산(도메인 01)에서 키를 교체하면 → 가족지정(도메인 00-27)의 중복방지가 깨진다.**

정산 담당자는 자기 도메인 일을 했을 뿐이고, **가족지정 코드는 한 줄도 안 바뀝니다.** 어느 쪽도 사고를 예상할 수 없는 구조입니다.

### 🔴 왜 이게 암호문보다 위험한가 — **잠금이 두 종류**

| | 암호문(`phoneEnc`) | 결정적 해시(`phoneHash`) |
| :--- | :---: | :---: |
| 판단 단위 | 행 하나 | **행 전체의 집합** |
| 버전 혼재 | ✅ 허용 | 🔴 **금지** |
| 전환 방식 | 점진(한 건씩) | 🔴 **원자적** |
| 실패 시 증상 | 그 행만 안 열림 — **즉시 발견** | 🔴 **중복 통과 — 발견 안 됨** |

암호문은 키가 틀리면 **복호화가 실패해서 바로 압니다.** 해시는 **틀린 값도 정상적인 해시처럼 생겼습니다.**

## 3. 어떻게 찾았나

외부 리뷰(Gemini)가 *"단일 암호화 키 의존"* 을 지적했고, **그 지적 자체는 사실이 아니었습니다**(키는 이미 2개). 그런데 확인하려고 `crypto.ts`를 전부 읽다가 `hashField`가 나왔습니다.

```bash
# 대상 컬럼 전수 — 암호문 7 + 해시 1
grep -n "Enc\|Hash" eobom/backend/prisma/schema.prisma

# 실제 파생 코드
sed -n '75,90p' eobom/backend/src/utils/crypto.ts
```

🔵 **교훈**: 지적이 틀렸어도 **확인하는 과정에서 다른 게 나왔습니다.** 틀린 지적을 *"틀렸다"* 로 끝내지 않은 것이 이 건을 찾은 이유입니다.

## 4. 조치

| # | 내용 | 상태 |
| :---: | :--- | :---: |
| 1 | `hashField`가 **전용 env `HASH_INDEX_KEY`** 를 읽도록 변경 | ✅ wt(95) |
| 2 | `00-27` §4.1 **철회** — 갱신 사유 기재(`roles.md` §2-1) | ✅ |
| 3 | `00-33` 정본 신설 — 3층 키 교체 전략 | ✅ |
| 4 | `rotate-keys.ts` — 재해시 스크립트(**단일 트랜잭션**) | ✅ 작성 |
| 5 | 🔴 **기존 `phoneHash` 재해시 실행** | ✅ **2026-09-01 완료** — 1건, dry-run 재검증 `처리 필요 0건` |

### 4.1 재해시가 가능한 이유 — **`phoneEnc`가 짝으로 있어서**

해시는 되돌릴 수 없습니다. 그런데 같은 행에 **암호문 `phoneEnc`가 있어서** 원본 번호를 복호화해 **새 키로 다시 계산**할 수 있습니다.

🔴 **짝이 없었다면 이 문제는 영원히 못 고쳤습니다.** → `00-33` §3.3이 규칙으로 승격됐습니다:
**"결정적 해시 컬럼은 반드시 대응하는 암호문 컬럼과 짝으로만 만든다."**

### 4.2 🔵 검증 방법을 바꿨습니다 (2026-09-01 스펙갱신)

원안은 해시에도 `v2:` 프리픽스를 붙여 `NOT LIKE 'v2:%'` = 0건으로 검증하려 했습니다. **철회했습니다** — 프리픽스는 *"형식이 v2"* 만 말하고 *"어느 키로 만들었는지"* 는 담지 못해서, **2차 교체 이후에는 옛 값도 통과시킵니다.** 탐지 장치가 탐지를 못 하고 **착각만 남깁니다.**

✅ 대신 **dry-run 값 비교**를 검증 수단으로 씁니다 — `phoneEnc`에서 재계산한 값과 저장값을 직접 비교하므로 **몇 번을 교체하든 정확**합니다(`00-33` §4.4).

## 5. 🔴 재발 방지 — 무엇으로 닫았나

| 수단 | 내용 |
| :--- | :--- |
| **코드 가드** | `hashField`가 `requireEnv('HASH_INDEX_KEY')` — 없으면 **기동 자체가 실패**. 조용히 다른 키로 넘어가지 않음 |
| **코드 가드** | 부팅 시 약한 키 점검(`checkEncryptionKeyStrength`) — 운영은 기동 차단 |
| **문서·스펙** | `00-33` **정본** + `00-27` §4.1 철회 기록 |
| **규칙** | 🔴 `00-33` §3.3 — **해시 컬럼은 암호문 컬럼과 짝으로만 만든다.** 이게 없으면 다음 해시 컬럼에서 똑같이 재발하고, 그때는 **고칠 수단조차 없음** |
| **규칙** | 재해시는 **`db-safety.md` 게이트** + `--confirm` 없으면 dry-run이 기본값 |

## 6. 남은 위험

- ✅ **재해시 — 2026-09-01 완료.** 중복 통과 창이 닫혔습니다(`대상 1건 · 이미 일치 1건 · 처리 필요 0건`).
  🔵 **검증을 다시 하려면** `--confirm` 없이 돌리기만 하면 됩니다 — 쓰지 않고 건수만 셉니다.
  🟡 **다만 이 검증은 로컬 DB 기준입니다.** 운영 DB에는 같은 절차를 **다시** 밟아야 합니다(→ TS-002).
- 🟡 `HASH_INDEX_KEY_V1` 등 옛 키 보관용 환경변수는 **아직 어디에도 없습니다** — 실제 유출 대응 시점에 관리자가 직접 추가해야 합니다(`00-33` §6.3).
- 🟡 키는 여전히 `.env` 평문입니다. 이 건이 막는 것은 *"유출 후 복구 불가"* 이지 *"유출 자체"* 가 아닙니다(`00-33` §8.4).
