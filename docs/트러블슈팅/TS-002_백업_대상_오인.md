# TS-002. 백업은 성공했는데 **다른 DB를 떴다** — `backup-db.ps1`의 기본 대상

| | |
| :--- | :--- |
| **발생·발견** | 2026-09-01 · [TS-001](TS-001_해시_키_파생_결합.md) 재해시 전 백업을 준비하다가 |
| **영역** | DB / 하네스 |
| **심각도** | 🔴 **조용한 실패** — 스크립트는 `exit 0`, 파일도 정상 생성 |
| **상태** | ✅ **닫힘** — 절차를 로컬 경로로 바꿔 진행 |

---

## 1. 증상 — 눈에 보인 것

```
powershell -File .harness/tools/backup-db.ps1
  ...
  출력: eobom/backend/backups/prod-20260901-HHMMSS.dump
```

**성공합니다.** 파일도 생깁니다. 크기도 정상입니다.

그런데 그 백업에는 **방금까지 작업하던 데이터가 없습니다.** 복구하려고 열어보기 전까지 알 수 없습니다.

🔴 **`db-safety.md` §2가 통과 조건으로 삼는 *"파일이 있다"* 를 만족하는데도 백업이 아닌 상태**입니다.

## 2. 원인 — 실제로 무엇이었나

### 짐작

*"백업 스크립트를 돌렸으니 지금 쓰는 DB를 떴겠지."*

### 실제

**스크립트는 `.env`의 `BACKUP_DATABASE_URL`을 먼저 읽습니다.** 그 값은 **운영(Supabase)** 을 가리킵니다.

```
eobom/backend/.env
  6: DATABASE_URL="postgresql://…@localhost:5433/eobom_db"        ← 지금 작업 중인 DB
 12: BACKUP_DATABASE_URL=…@aws-0-ap-northeast-2.pooler.supabase.com:5432/postgres
                                                                   ↑ 스크립트가 뜨는 DB
```

**스크립트가 잘못된 게 아닙니다** — 이름 그대로 *"운영 백업용"* 으로 만들어졌고(파일 머리말 1행: *"스키마 변경 전 **운영** DB 백업"*), 로컬이 대상이면 노란 경고까지 냅니다.

🔴 **틀린 것은 "백업 = `backup-db.ps1`" 이라는 반사적 연결입니다.** 두 개의 DB가 있는데 도구 이름에는 그 구분이 없습니다.

### 🔴 왜 이게 특히 위험한가

`db-safety.md` §7에 기록된 **데이터 유실 2건이 둘 다 로컬**이었습니다. 즉 **실제로 지켜야 할 쪽이 이 스크립트의 기본 대상이 아닌 쪽**입니다.

`db-safety.md` §2가 이미 이렇게 경고하고 있었습니다:

> 🔴 **로컬 작업 중 이걸 돌리고 "백업했다"고 여기는 것이 가장 위험한 오해다.**

**경고문이 이미 있었는데도 이번에 밟을 뻔했습니다** — 이 문서를 남기는 이유입니다.

## 3. 어떻게 찾았나

`db-safety.md`를 **DB 쓰기 직전에 여는 규칙**(`AGENTS.md` §0-1 조건부 로드) 덕분입니다. 열지 않았으면 그대로 진행했을 것입니다.

확인 방법:

```bash
# 지금 백엔드가 붙어 있는 DB
grep -n "DATABASE_URL" eobom/backend/.env

# 실행 중인 로컬 컨테이너 — 이어봄은 5433 (5432는 다른 프로젝트)
docker ps --format "{{.Names}}\t{{.Ports}}"
```

## 4. 조치

`db-safety.md` §2 표의 **로컬 경로**로 진행했습니다.

```bash
# 🔴 Git Bash는 /tmp를 Windows 경로로 바꿔버린다 → MSYS_NO_PATHCONV=1 필수
MSYS_NO_PATHCONV=1 docker exec eobom-postgres \
  pg_dump -U <유저> eobom_db -Fc -f /tmp/local-YYYYMMDD-<작업명>.dump

MSYS_NO_PATHCONV=1 docker exec eobom-postgres ls -la /tmp/local-…dump   # 컨테이너 안 확인
docker cp eobom-postgres:/tmp/local-…dump eobom/backend/backups/         # 꺼내기
ls -la eobom/backend/backups/local-…dump                                 # 🔴 호스트에서 재확인
```

> 🔵 **컨테이너 안 `pg_dump`를 쓰면 버전이 서버와 정확히 일치**하므로 `backup-db.ps1`이 겪던 `server version mismatch` 문제가 없습니다.

### 4.1 파일명으로 구분이 됩니다

`backup-db.ps1`은 대상에 따라 `local-` / `prod-` 접두사를 붙입니다. **백업 직후 접두사를 눈으로 확인하는 것이 30초짜리 방어선**입니다.

```
eobom/backend/backups/
  prod-20260828-101348.dump     ← 운영
  local-20260901-rehash.dump    ← 로컬 (이번 건)
```

## 5. 🔴 재발 방지 — 무엇으로 닫았나

| 수단 | 내용 |
| :--- | :--- |
| **문서·스펙** | `db-safety.md` §2에 이미 있었음 — **이번 건은 규칙 부재가 아니라 "규칙을 열었기 때문에 막힌" 사례** |
| **문서·스펙** | 🆕 이 문서 — **증상(*"백업했는데 데이터가 없다"*)으로 찾을 수 있는 색인**을 추가 |
| **규칙** | 백업 후 **파일명 접두사 확인**(§4.1)을 통과 조건에 포함 |
| ⏸ **코드 가드** | ❌ **없음** → §6 |

> 🔴 **"주의하겠다"로 닫지 않았습니다.** 다만 코드 가드가 없다는 것은 §6에 남깁니다.

## 6. 남은 위험

- 🔴 **`backup-db.ps1`에 `-Target local|prod` 같은 명시 인자가 없습니다.** 지금은 `.env` 상태에 따라 대상이 조용히 정해집니다. **다음에 다른 사람(또는 다른 세션)이 같은 오해를 할 수 있습니다.**
  🟡 **권고**: 대상을 인자로 **명시하게 하고, 안 주면 실패**시키는 것. `db-safety.md` §7.1의 *"규칙이 세 번 실패하면 도구로 간다"* 와 같은 방향입니다. **아직 착수 안 함.**
- 🟡 로컬 백업 경로가 스크립트가 아니라 **손으로 치는 명령 3줄**입니다. 손으로 치는 절차는 언젠가 건너뜁니다.
